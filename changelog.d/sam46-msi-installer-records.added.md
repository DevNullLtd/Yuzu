- **`msi_packages.installer_records` (Windows): what Windows Installer itself recorded for each machine-context product, and an `upgrade_code` on `list_inventory`.** A new read-only action reports, per product, the `InstallProperties` registry values the Installer keeps for the SYSTEM account (display name, version, publisher, install date, install location, install source, cached package path) together with the Property table of the product's cached package under the Windows Installer directory (ProductCode, UpgradeCode, ProductVersion, Manufacturer, ProductName). Nothing is executed: no product is opened, repaired, installed or configured, only the Installer cache is ever opened (a path that is not `<windir>\Installer\<name>.msi`, or that names a reserved device such as `CON`, is refused, only a local fixed drive is used, and the package is held open through a handle that follows no reparse point while it is read), and the registry is read with the wide APIs in the 64-bit view. The read is bounded: at most 5,000 products and 20 MB of text, 5 seconds per package and 45 seconds of package reads per dispatch, with at most one package read in flight in the whole agent, so a package that hangs the Installer API pins one worker however often the action is dispatched. A missing, refused or corrupt package keeps its row with a reason (`package_missing`, `package_path_refused`, `package_unreadable:<code>`) and does not constrain the answer; a failed registry read, a bound that cut the read short, or a package read that timed out or found the reader busy makes the status row `constrained` with a named token and never an empty success. An install location or source under the user profiles directory is reported as `withheld:user_path`; a UNC install source is reported as recorded. `list_inventory` rows gain a sixth token, `upgrade_code`: the product's UpgradeCode from the Installer's registry map, empty when no upgrade code (or more than one) names the product. It is a registry read only, so it is the same every day for the same installed set. The Windows leg is supported: it was verified against a real capture taken on a Windows host as SYSTEM and as an admin user. On the first sync after the agent upgrade each Windows device's MSI rows gain the `upgrade_code` attribute, so each row's record and `instance_key` change once and the `msi_packages.list_inventory` section is sent again once; an attribute-only change writes no change-feed entry.
