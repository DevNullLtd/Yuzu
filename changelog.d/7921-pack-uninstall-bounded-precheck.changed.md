- **The referrer check behind `DELETE /api/product-packs/{id}` does a bounded amount of work however many items the pack carries.** It reads each of the three sources (schedules, live workflows, policy fragments) once for all of a pack's definitions together, reads the policies that hold the pack's own fragments in one read (only each policy's id and name, so a policy whose detail rows cannot be loaded does not fail it), and stops as soon as it holds 21 referrers, so a pack with hundreds of referrers is refused at once. The `409` therefore counts at most 21 referrers (a lower bound), lists schedules first, then workflows, then policy fragments, and a failure of a source that comes after a full list cannot turn it into a `503` (the read for the pack's own policy fragments runs first, so it can still fail the check). The `503` from a failed reference check, or from the pack read before it, carries `retry_after_ms` (nothing was deleted, so the same `DELETE` can be retried as is); the `503` for a check that is not configured, the generic service-unavailable `503` and the `503` for a store error part-way through the deletes carry none.
