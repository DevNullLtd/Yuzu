- **`POST /api/v1/quarantine` now applies the dispatch approval check before it writes a record (#6065).** The route runs the same check as MCP `quarantine_device` for the `quarantine.quarantine` pair, after the scoped `Security:Execute` gate and `whitelist` validation, whether or not any approval feature is switched on. With RBAC on, a non-administrator who holds `Security:Execute` on the device (admitted with `201` before) now gets `403` `approval_required`, and a holder through a management group only gets `403` `forbidden`; with RBAC off nothing changes for non-administrators, because the legacy gate already requires the `admin` role. REST has no approval-ticket path, so non-administrators cannot create a quarantine record through REST or the dashboard; MCP `quarantine_device` on the supervised tier remains the approved path. A refusal writes no record, audits `quarantine.enable` as `denied`, increments `yuzu_server_dispatch_denied_total{reason}` and carries `message` and `remediation` but no `permission` field. A session that expires mid-request now ends at the `401` instead of writing a record attributed to `system`. See [Upgrading](docs/user-manual/upgrading.md).
