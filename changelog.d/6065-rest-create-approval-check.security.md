- **Breaking: `POST` and `DELETE /api/v1/quarantine` now apply the dispatch approval check before they write or release a record (#6065).** `POST` runs the same check as MCP `quarantine_device` for the `quarantine.quarantine` pair and `DELETE` runs it for the `quarantine.unquarantine` pair, so a caller who cannot create a record cannot end one; both run after the scoped `Security:Execute` gate and `whitelist` validation; it does not depend on any approval-workflow setting. "Administrator" means an account whose account role is `admin` (a live JIT elevation counts); the RBAC `Administrator` role alone does not. With RBAC on, a non-administrator who holds `Security:Execute` globally (admitted with `201` before) now gets `403` `approval_required`, and a holder through a management group only, or an administrator only through a JIT elevation with no global grant of their own, gets `403` `forbidden`; with RBAC off nothing changes for non-administrators, because the legacy gate already requires the `admin` role. REST has no approval-ticket path, so non-administrators cannot create or release a quarantine record through REST or the dashboard; MCP `quarantine_device` on the supervised tier remains the approved path for creation, and release has no non-administrator path. The check is per replica, so a rolling upgrade is uneven until every replica is upgraded. A refusal writes no record and releases none, audits `quarantine.enable` or `quarantine.disable` as `denied`, increments `yuzu_server_dispatch_denied_total{reason}` and carries `message` and `remediation` but no `permission` field. A session that expires mid-request now ends at the `401` instead of writing a record attributed to `system`. See [Upgrading](docs/user-manual/upgrading.md).
