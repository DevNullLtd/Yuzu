- **Breaking: `POST /api/v1/quarantine` now applies the dispatch approval check before it writes a record (#6065).** The route runs the same check as MCP `quarantine_device` for the `quarantine.quarantine` pair, after the scoped `Security:Execute` gate and `whitelist` validation; it does not depend on any approval-workflow setting. "Administrator" means an account whose account role is `admin` (a live JIT elevation counts); the RBAC `Administrator` role alone does not. With RBAC on, a non-administrator who holds `Security:Execute` globally (admitted with `201` before) now gets `403` `approval_required`, and a holder through a management group only, or an administrator only through a JIT elevation with no global grant of their own, gets `403` `forbidden`; with RBAC off nothing changes for non-administrators, because the legacy gate already requires the `admin` role. REST has no approval-ticket path, so non-administrators cannot create a quarantine record through REST or the dashboard; MCP `quarantine_device` on the supervised tier remains the approved path. The check is per replica, so a rolling upgrade is uneven until every replica is upgraded. `DELETE /api/v1/quarantine/{agent_id}` is unchanged and does not apply the check. A refusal writes no record, audits `quarantine.enable` as `denied`, increments `yuzu_server_dispatch_denied_total{reason}` and carries `message` and `remediation` but no `permission` field. A session that expires mid-request now ends at the `401` instead of writing a record attributed to `system`. See [Upgrading](docs/user-manual/upgrading.md).
