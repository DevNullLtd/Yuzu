- **`file_search` Windows leg: walk and extents on fixed volumes.** The on-demand name search now runs on Windows, with the same rows as Linux and macOS and the same walk, cursor and coverage rules. One search covers the one fixed local volume that holds the root (a drive path such as `C:\Users` or a volume GUID path), opened by its volume GUID path and then directory by directory through parent-handle-relative opens that follow no reparse point, so a junction, a mount point or a symbolic link is skipped and counted and never entered. Rows name paths in one canonical form (`/C:/Users/x`, `/Volume{guid}/dir`); a network (UNC) root answers `root_unc` and any other device path `root_device_path`; removable, optical, RAM and network drives are refused by their own volume row. Names compare upper-cased (`windows_upcase_v1`), and the longest name a cursor can hold is raised to 765 bytes (255 UTF-16 units). A matched file is opened for its attributes only, with no data right, so the search can neither read nor recall it; its extents come from two control calls on that handle (`FSCTL_GET_EXTERNAL_BACKING`, then `FSCTL_GET_RETRIEVAL_POINTERS`), mapping holes, NTFS compression and resident data onto the existing flags; a CompactOS file reads `unsupported:wof_external_backing` instead of a misleading single hole, and file ids are reported on NTFS only. A populated cloud-synced folder is searched (its fully local files read `ok:cloud`); a cloud placeholder or offline folder, or any folder marked recall, is never opened for use or listed (a `dataless` gap), and such a file is named in its match row but never read or recalled (`unsupported:placeholder`), and an entry with a reparse tag the leg does not understand is a new `reparse_unknown` gap. Profile directories under the profile list are tagged `user` whether the volume is named by drive letter or by volume GUID. Not measured and said so in the README: EFS, deduplication, ReFS, a commercial sync client.
