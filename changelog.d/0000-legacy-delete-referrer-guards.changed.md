- **Breaking: the released `DELETE /api/instructions/{id}` and `DELETE /api/product-packs/{id}` now refuse a definition that is still referenced.** A definition that a schedule, a live workflow or a policy fragment still names was previously deleted out from under them. `DELETE /api/instructions/{id}` now answers `409` listing the referrers (nothing deleted; one `instruction.delete` row, `denied` / `referenced`), and `503` when the reference check cannot be answered or the definition cannot be read first. `DELETE /api/product-packs/{id}` runs the same check for every InstructionDefinition item the pack carries before it deletes any item (the pack's own workflows are not counted, nor are its own policy fragments unless a policy still uses one, which survives the uninstall, is counted and has the policy named in the `409`) and answers `409` or `503` the same way, so a refusal never leaves a half-uninstalled pack (a database failure part-way through the deletes still can: the pack stays listed and a retry of the same `DELETE` finishes it, and a failed delete of one of the pack's own policy fragments now stops the uninstall with a `503` instead of being logged and the pack removed). A pack item that names a definition that no longer exists is still checked, so a schedule left dangling by an older build blocks the uninstall until it is removed. The check is advisory, not transactional. The Instructions page shows the refusal of its Delete button as an error toast. A `PUT /api/instructions/{id}` that sets a present `plugin` to an empty string is refused `400`. Installed product packs that contain a deleted definition do not block it: the `instruction.delete` success row (legacy, v1 and MCP) ends with `packs=<id>,...` (at most 5, then `,+N`).
