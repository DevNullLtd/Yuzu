- **Webhooks fire only four event types.** The server sends `agent.registered`, `execution.completed`, `dex.signal` and `dex.blast_radius`, and nothing else. `command.completed` and `policy.violation` appeared in the manual as webhook event types but the server never sent them, so a subscription that listed only those two never received an event and policy violations were never delivered by webhook. The manual now lists the four real types. `execution.completed` fires once per agent response to a command, not once per instruction, so an instruction sent to many devices produces one event per answering device.
- **`DELETE /api/v1/sessions/me` accepts a plain API token.** The manual said only an interactive cookie session could call it. A cookie session or a plain API token (no `mcp_tier`, no service scope) is accepted; an MCP-tier token or a service-scoped token is still refused with `403`.
- **The 90-day token expiry cap applies only to tiered tokens.** A token minted with an `mcp_tier` must expire within 90 days. A service-scoped token without a tier must still carry an `expires_at`, but the server does not cap it at 90 days. The manual had said both were capped.
- **Offload target batching does not flush on a timer.** With `batch_size` above 1 the buffer is sent only when it reaches that size and at graceful server shutdown. A partly filled buffer waits for more events, and it is lost if the server crashes or the target is deleted. The manual now says so.
- **Product pack signatures are verified.** The manual described pack signing as planned. A pack's Ed25519 signature is verified at install against the key inside the pack, a pack that fails verification is rejected, and an unsigned pack is refused unless the server runs with `--allow-unsigned-packs`. A trust chain anchored to an organization root key and staged review before activation are still planned.
- **Service management groups are filled once.** The `Service: {name}` group that Yuzu creates when a `service` tag is first written takes the agents carrying that tag at that moment. Later tag writes do not add or remove members, and the manual no longer says the group is refreshed.
- **Engine principal role assignment limits are stated exactly.** Assignment refuses `admin`, `Administrator` and every built-in role for an engine principal, but it does not inspect a custom role's permissions, so a custom role with a wildcard grant can be assigned; `GET /api/v1/engine-principals/audit/no-admin` reports such a grant afterwards. The three `/engine-principals/{id}/roles` routes do not check whether the caller's own session is engine-classed, and neither do the `list_engine_roles`, `assign_engine_role` and `unassign_engine_role` MCP tools. Every other engine-principal route and tool does. The manual had said an engine session is refused on every route and that a wildcard role is rejected with `400`.
