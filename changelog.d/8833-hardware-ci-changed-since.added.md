- **Delta pulls for the bulk device-CI read.** `GET /api/v1/hardware-ci` and MCP `list_hardware_ci_records` accept `changed_since` (epoch seconds, 0 up to the server's time plus 60 seconds) and return only the records whose content changed at or after it. Every row now carries a required `changed_at`, stamped from the database clock only when `content_hash` changes (the daily sync that finds nothing new leaves it alone, unlike `last_seen`). `next_changed_since`, the database clock minus 300 seconds, is present on the first response of a walk only (the one with no `cursor` and no `agent_id`); cursor pages and `agent_id` reads omit it, so keep the first value and never derive one from `max(changed_at)`, a later page or your own clock, and restart a failed walk from page 1 rather than resuming a saved cursor. Run the first full walk under the same global credential that will run the deltas (a scope-confined credential's first-page value is not valid for a later global delta). Delivery is at-least-once, so upsert by `agent_id` and run a periodic full walk as the backstop. A delta needs a credential with a fleet-wide `Inventory:Read` grant (a scope-confined, management-group or service-scoped caller is refused), it carries no removal signal, a delta page that has failed with the generic error (REST `503` or MCP `-32603` with `retry_after_ms` 5000 and no `Sec-Audit-Failed`) at least 3 times over at least 60 s while unfiltered pages succeed is the one case for dropping `changed_since` and running ONE full walk (once per walk, not on every scheduled run; every other hint is honoured, and if the fallback also fails, stop and alert), and an empty page with `changed_since` means nothing changed, not that no record exists: confirm a device with `agent_id` and no `changed_since`. Migration v5 adds the column and an index: its `ALTER` takes an `ACCESS EXCLUSIVE` lock on `device_ci` held through the index build (reads and writes blocked), waits up to 30 seconds for it, and then fails, after which the server refuses to start on every restart until the lock holder is gone. Existing rows read as changed at migration time, so the first delta pull returns the fleet once. Migration v6 then replaces the byte-ordered keyset index with a composite `(agent_id COLLATE "C", changed_at)` index (about 9 MB larger per million devices at rest, about 65 MB of free disk per million devices while both exist, built under an `ACCESS EXCLUSIVE` lock in about 0.6 s per million devices on an idle database), so a clustered delta stays fast, and drops the earlier index in the same start: do not pre-build either index, and plan the start delay on a large table; the same 30-second lock wait and refuse-to-start failure apply, and a start-time WARN now reports either read index when it is missing, invalid or differently defined. v5 and v6 are forward-only (no rollback), and this is a fresh-deployment change, not a rolling or mixed-version upgrade: a replica still on an earlier build leaves `changed_at` unstamped for good, so after the last one is gone do a full walk and take a fresh watermark.
