- **The gateway-upstream service now requires an authorized gateway peer, and the server refuses to start without one.** Before this change the service (`--gateway-upstream`) authenticated callers only by membership of the install CA, or by the network boundary on a plaintext listener, and because it is registered on the one gRPC server that also listens for agents it was reachable on the agent and management ports too: on a default-certificate install a caller with no client certificate could reach it on the agent port, and any holder of a CA-issued client certificate (an agent leaf included) could reach it elsewhere. Every call is now refused with `UNAUTHENTICATED` unless the caller's TLS-authenticated leaf certificate lists `serverAuth`, has a public key whose SHA-256 (over the SubjectPublicKeyInfo) is pinned, and is inside its validity window; the check applies on every port the service is served on. Pins are fixed at boot (`--gateway-peer-pin`, `--gateway-peer-pin-file`, env `YUZU_GATEWAY_PEER_PINS` / `YUZU_GATEWAY_PEER_PIN_FILE`); on the generated default certificates the server pins its own `default-gateway.pem` automatically. **Breaking:** with your own certificates the server exits at boot until you supply a pin; a plaintext (`--no-tls`) rig must pass `--insecure-gateway-peer` (env `YUZU_INSECURE_GATEWAY_PEER=1`), which disables the check on every port, is refused together with a pin, and is reported by a boot error line, a `server.gateway_peer_authz_disabled` audit row and `yuzu_server_gateway_peer_authz_mode`. Changing or withdrawing a pin is a server restart (a rolling restart with the old and new pins together for HA); there is no pin reload and no revocation check on this path, and after a refusal window the gateway nodes must be restarted too, because the gateway never retries a refused `NotifyStreamStatus`. Refusals are counted in `yuzu_server_gateway_peer_denied_total{rpc,reason}`, authenticated peers also write a bounded `session.gateway_peer_denied` audit row, and two alerts ship. The Docker reference gateway compose now mounts only the public CA certificate into the agent container (a one-shot `ca-export` service fills a `ca-public` volume) so an agent cannot read the gateway key the pin authorizes; recreate the whole stack to pick it up. Remove the new flags before rolling a binary back (an older binary rejects an unknown flag but ignores an unknown environment variable). See "Gateway upstream peer authorization" in `docs/user-manual/server-admin.md` and the breaking-change section of `docs/user-manual/upgrading.md`.
