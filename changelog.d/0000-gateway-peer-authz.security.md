- **The gateway-upstream service now requires an authorized gateway peer, and the server refuses to start without one.** Before this change the service (`--gateway-upstream`) authenticated callers only by membership of the install CA, or by the network boundary on a plaintext listener, and because it is registered on the one gRPC server that also listens for agents it was reachable on the agent and management ports too: on a default-certificate install a caller with no client certificate could reach it on the agent port, and any holder of a CA-issued client certificate (an agent leaf included) could reach it elsewhere. Every call is now refused with `UNAUTHENTICATED` unless the caller's TLS-authenticated leaf certificate lists `serverAuth`, has a public key whose SHA-256 (over the SubjectPublicKeyInfo) is pinned, and is inside its validity window; the check applies on every port the service is served on. Pins are fixed at boot (`--gateway-peer-pin`, `--gateway-peer-pin-file`, env `YUZU_GATEWAY_PEER_PINS` / `YUZU_GATEWAY_PEER_PIN_FILE`); on the generated default certificates the server pins its own `default-gateway.pem` automatically. **Breaking:** with your own certificates the server exits at boot until you supply a pin (this includes a Linux package install with its own certificates, because the shipped systemd unit passes `--gateway-upstream` unconditionally even if you run no gateway: the RPM restarts the service on upgrade, so it fails at once, and the deb only enables it, so it fails at the next restart; pin, or drop `--gateway-upstream` in a drop-in, before upgrading); a plaintext (`--no-tls`) rig must pass `--insecure-gateway-peer` (env `YUZU_INSECURE_GATEWAY_PEER=1`), which disables the check on every port, is refused together with a pin, and is reported by a boot error line, a `server.gateway_peer_authz_disabled` audit row and `yuzu_server_gateway_peer_authz_mode`. Changing or withdrawing a pin is a server restart (a rolling restart with the old and new pins together for HA); there is no pin reload and no revocation check on this path, and after a refusal window you compare the gateways' connected-agent count (`yuzu_gw_agents_current`) with the servers' (`yuzu_agents_connected`) and restart gateway nodes, one at a time, only if agents have not reappeared (the gateway never retries a refused `NotifyStreamStatus`, but a gateway restart is itself costly: agents without the #5183 fix stay wedged after one). The validity check runs on every call, so a gateway certificate that expires on an open connection is refused until the gateway redials: renew before `notAfter` and reconnect the gateway. Refusals are counted in `yuzu_server_gateway_peer_denied_total{rpc,reason}`, authenticated peers also write a bounded `session.gateway_peer_denied` audit row, and five alert rules ship (three on the server's metrics, including a critical one for the gateway's own heartbeat being refused, and two on the gateway's metrics, for upstream status 16 and for upstream TLS handshake failures). The Docker reference gateway compose now mounts only the public CA certificate into the agent container (a one-shot `ca-export` service fills a `ca-public` volume) so an agent cannot read the gateway key the pin authorizes; recreate the whole stack to pick it up. Remove the new flags before rolling a binary back (an older binary rejects an unknown flag but ignores an unknown environment variable). The Windows installer takes `/GATEWAY_PEER_PIN_FILE=<cert.pem>` or `/GATEWAY_PEER_PIN=<64 hex>` (mutually exclusive, stored as `certs\gateway-peer-pin`; the wizard has no pin page), `/GATEWAY /NOTLS` now passes `--insecure-gateway-peer` and is refused together with a pin parameter, and a silent `/NOTLS` clears any gRPC certificate parameters. See "Gateway upstream peer authorization" in `docs/user-manual/server-admin.md` and the breaking-change section of `docs/user-manual/upgrading.md`.
