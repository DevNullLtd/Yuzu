- **Guardian (agent, spark backend only, inert while `prefer_spark` is off, which is every released agent today): a baseline captured on arm under SparkEngine is now persisted, so a `full_sync` or agent restart no longer re-baselines a drifted file as compliant, apart from the residual cases below.** A `file-hash-equals` rule with no authored `expected_hash` takes the file's content at arm time as its known-good baseline. Since #4021 the legacy detection path saved that baseline to the agent's local KV store, but SparkEngine's own capture lived only in memory, so the next policy re-push or restart captured whatever the file then held and reported it compliant. The Spark runtime now stages each capture and the agent's engine writes it through the same overwrite-guarded #4021 record (before any teardown or re-arm, at shutdown, and from the background delivery worker, independent of the server connection; the write is wake-driven, typically within milliseconds, with a 5 to 60 second backoff after a failed write), and a re-armed rule is seeded from a capture that is still waiting to be written, so a capture recorded just as a policy push begins is not lost to the re-arm. A failing local KV store is deliberately fail-open (the rule keeps enforcing against its in-memory baseline) but the capture stays waiting and is retried, error-logged, and counted in the new sparse `yuzu.guardian_baseline_persist_failures` heartbeat tag (Spark path only, cumulative, per-agent: no server gauge or alert rule exists yet, so the agent error log is the primary signal and an absent tag is not evidence that baselines were saved). Remaining residuals: a crash or stop before a capture is written loses it; a capture is lost and counted if an allocation fails while it is noted or the rule's path is re-authored before it is written; two failed reads of the baseline record can let a fresh capture overwrite a good record (as on the legacy path); a record kept for a removed rule stays dormant (#4045).
