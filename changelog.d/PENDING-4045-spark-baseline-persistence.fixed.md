- **Guardian (agent, spark backend only, inert while `prefer_spark` is off, which is every released agent today): a baseline captured on arm under SparkEngine is now persisted, so a `full_sync` or agent restart no longer re-baselines a drifted file as compliant, apart from the residual cases below.** A `file-hash-equals` rule with no authored `expected_hash` takes the file's content at arm time as its known-good baseline. Since #4021 the legacy detection path saved that baseline to the agent's local KV store, but SparkEngine's own capture lived only in memory, so the next policy re-push or restart captured whatever the file then held and reported it compliant. The Spark runtime now stages each capture and the agent's engine writes it through the same overwrite-guarded #4021 record (before any teardown or re-arm, at shutdown, and from the background delivery worker, independent of the server connection; the write is wake-driven, typically within milliseconds, each pass is bounded to 64 writes, 3 failures and 2 seconds so a failing capture cannot hold up the ones behind it, and the worker backs off 5 to 60 seconds after a failed pass), and a re-armed rule is seeded from a capture that is still waiting to be written, so a capture recorded just as a policy push begins is not lost to the re-arm. A failing local KV store is deliberately fail-open (the rule keeps enforcing against its in-memory baseline) but the capture stays waiting and is retried, error-logged, and counted in the new sparse `yuzu.guardian_baseline_persist_failures` heartbeat tag (Spark path only, cumulative, per-agent: no server gauge or alert rule exists yet, so the agent error log is the primary signal and an absent tag is not evidence that baselines were saved). Remaining residuals: a crash loses a capture that was not yet written, and a stop does so only if its write is still failing (the stop flush runs first, and is skipped after a slow failed pass); a capture is lost or never written, and counted, if an allocation fails while it is noted (the rule then captures again at its next evaluation) or the rule's path is re-authored before it is written; two failed reads of the baseline record can let a fresh capture overwrite a good record (as on the legacy path); a record kept for a removed rule stays dormant; and if the read of the record fails at arm time while a valid record exists, the rule is judged against freshly captured content until its next re-arm or restart (the record stays intact) (#4045).
