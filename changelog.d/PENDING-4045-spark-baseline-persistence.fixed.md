- **Guardian (agent, spark backend only, inert while `prefer_spark` is off, which is every released agent today): a baseline captured on arm under SparkEngine is now persisted (Windows agents, where the file-hash guard runs), so a `full_sync` or agent restart no longer re-baselines a drifted file as compliant, apart from the residual cases below.** A `file-hash-equals` rule with no authored `expected_hash` takes the file's content at arm time as its known-good baseline. Since #4021 the legacy detection path saved that baseline to the agent's local KV store, but SparkEngine's own capture lived only in memory, so the next policy re-push or restart captured whatever the file then held and reported it compliant. The Spark runtime now stages each capture and the agent's engine writes it through the same overwrite-guarded #4021 record (before any teardown or re-arm, at shutdown, and from the background delivery worker, independent of the server connection; the write is wake-driven, typically within milliseconds (except during a policy push, which it waits for), each pass starts at most 64 writes, gives up after 3 failures and starts no new write after 2 seconds (plus the one write already in flight) so a failing capture cannot hold up the ones behind it, the shutdown flush has no write cap and allows 1 failure and 1 second between writes, and the worker backs off 5 to 60 seconds after a failed pass and steps aside for a policy push in progress), and a re-armed rule is seeded from a capture that is still waiting to be written, so a capture recorded just as a policy push begins is not lost to the re-arm. A failing local KV store is deliberately fail-open (the rule keeps enforcing against its in-memory baseline) but the capture stays waiting and is retried, error-logged, and counted in the new sparse `yuzu.guardian_baseline_persist_failures` heartbeat tag (Spark path only, cumulative, per-agent: no server gauge or alert rule exists yet, so the agent error log is the primary signal and an absent tag is not evidence that baselines were saved). Known residuals: a crash loses a capture that was not yet written; a stop loses waiting captures if its write fails, if its one second between writes runs out (a slow store, or more than roughly two to three thousand waiting captures), if it is skipped (after a write failed slowly during that shutdown, or because the earlier shutdown steps had already used 15 of the agent's 20 shutdown seconds and one of them had failed or taken a full busy timeout; both are logged, not counted) or if the agent's 20-second shutdown watchdog ends the process mid-stop (exit code 4, no log line); if an allocation fails while a capture is noted, the rule keeps the baseline (a later change is still reported as drift) and retries noting it at later evaluations, at a re-push, at a withdrawal and at shutdown, so the capture is exposed only until a retry succeeds (a crash in that window loses it, so does a shutdown whose own retry also fails (logged), and a re-push whose retries all fail captures afresh); a capture is lost, and counted, if the rule's path is re-authored before it is written; two failed reads of the baseline record can let a fresh capture overwrite a good record (as on the legacy path); if the read of the record fails at arm time while a valid record exists, the rule is judged against freshly captured content until its next re-arm or restart (the record stays intact); a record found malformed is discarded at arm and overwritten (as before this change); and a record kept for a removed rule stays dormant (#4045).
