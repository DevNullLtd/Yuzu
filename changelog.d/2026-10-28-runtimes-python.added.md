- **`runtimes.python`: installed Python interpreters on Windows, macOS and Linux, fed to the installed-software inventory.** The `runtimes` plugin gains a `python` action that reads install metadata only (no `python` process is ever started): on Windows the python.org PEP 514 keys under `HKLM\SOFTWARE\Python\PythonCore` in both registry views (per-user hives are never read), on macOS each version of `/Library/Frameworks/Python.framework/Versions` through its `Info.plist`, and on Linux the `python3.<minor>` files in `/usr/bin` and `/usr/local/bin` (`/var/usrlocal/bin` on rpm-ostree hosts, where `/usr/local` links there). Windows and macOS report the full `x.y.z`; **Linux reports major.minor only** (for example `3.11`), because the patch level is not stored anywhere without running the interpreter. Like its siblings it answers a `status` row first, and a failed or skipped read is a constrained status with a named token, never an empty success; on macOS and Linux a root on, under or containing a network mount is skipped and reported (`network_fs_skipped`), never opened. Each row becomes one `Python` entry (ecosystem `python`) in a device's installed software through the daily sync; a constrained read withholds only the Python rows from that day's report (the rest of the device's software is still sent, and its stored Python rows are removed until a read succeeds again). Interpreters under Homebrew, pyenv, conda, virtual environments and per-user Windows installs are not listed. The plugin's `dotnet` and `jvm` output is unchanged. The published `ecosystem` vocabulary on the REST and MCP software and crypto surfaces gains `python` as a 13th value, so `ecosystem=python` filters to these entries.
