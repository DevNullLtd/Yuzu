- **Decommissioning a device now erases its Guardian compliance-census rows (#5675).** `DELETE /api/v1/sle/agents/{id}` fans out across nine stores, and the response's `stores` map gains a `guaranteed_state` key. For that store, `deleted` means the device's compliance-census rows were erased and its pending census evidence retired; the Guardian event log and DEX observations are not erased by the decommission and are kept until retention expires (30 days by default; rows stamped while `guardian_event_retention_days` is 0 or below never expire). A decommissioned agent therefore stops counting in `errored_rules` and `uncertain_rules`, and the `yuzu_server_guardian_census_pending_events` gauge drops; re-registering the same `agent_id` after a decommission inherits no stale errored state, while a bare re-register without a decommission keeps the old row by design. A still-running agent re-creates its census row only at its next census-bearing state change, and a journal replay cannot rebuild the census from the retired evidence, so stop the agent first. A pending event committed during the decommission, after its pending list was read, is not retired (tracker #7147), and a later pending event for a decommissioned agent stays pending until something retires it. A rolling upgrade is outside the 0.15.0 deployment contract; if a mixed fleet exists anyway, a replica that has not been upgraded returns `200` without a `guaranteed_state` key and did not erase the census rows, so re-issue the DELETE once every replica is upgraded. An agent that is merely offline still counts with its last reported state, as before.
