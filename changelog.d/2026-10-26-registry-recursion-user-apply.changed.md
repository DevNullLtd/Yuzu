- **`registry` 2.1.0: `delete_key` can delete a whole tree or count it, and the audit binding covers six actions.** `delete_key` gains two optional parameters, `recursive` and `dry_run` (definition 1.2.0; without them it behaves as before). A recursive delete vets the tree first (at most 10,000 keys and values and 600 levels; a real run past that is refused `tree_too_large` with nothing deleted, a registry link anywhere in the tree is refused `key_is_link`) and then removes it post-order, each key by its own handle, re-checking every key it finds for a link; `RegDeleteTreeW` is never used. `dry_run` counts what a real run would remove and deletes nothing. The counts of a real run are what it removed, which can exceed a dry run's snapshot. **Mixed fleets:** a registry 1.x or 2.0.x agent (every agent released before 2.1.0, v0.14.1 included) reads neither flag, so a `delete_key` with `dry_run=true` sent to it deletes a key that has no subkeys, and the three new actions answer `unknown action`; the server does not compare plugin versions at dispatch, so upgrade the server, then the agents, scope any preview to devices verified at 2.1.0 and use the `delete_key` kill switch until then (`docs/user-manual/upgrading.md`). The server now treats six registry actions as mutating for the `registry.write` audit rows (`set_user_value`, `delete_user_value` and `apply` join `set_value`, `delete_value` and `delete_key`), and the three new actions are classified Mutating/Destructive in the command-capability catalogue and the risk table.
