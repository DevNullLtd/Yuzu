- **A Registry spark watch now notices a renamed parent key instead of staying silently deaf (Windows, #5719 item 5, #7836).** The watch held a notify handle that followed the renamed key, so it kept reporting Healthy and never saw a change at the watched path. No shipped agent arms spark watches (`prefer_spark_` is false); the behaviour is visible only on rig-flipped agents, and the Registry check is off by default even then. The detection is OFF by default and is enabled at boot with `--spark-registry-path-verify-interval SECONDS` (env `YUZU_AGENT_SPARK_REGISTRY_PATH_VERIFY_INTERVAL`; 0 = off, the default; 1 to 4 is raised to 5; at most 86400): each check opens the watched key, and on a key with an auditing SACL that open can write a Security-log event that pushes older events out, which cannot be undone and is not measured, so decide the interval per estate. With the default a renamed parent is not detected, as before. When enabled, an idle, healthy watch is verified at that interval on the mechanism's existing probe lane (no new long-lived thread; one short-lived worker per watched key per check): the registered path is re-opened, and a path that no longer names a key reports the watch faulted (`registry watch key renamed or replaced`), owes a resync fire, and re-opens the path on the ordinary retry (30 s, doubling on repeated failure to a 300 s cap). Detection is sampled, about one interval (5 s at the floor) by design (plus the sweep wake, the probe latency and, when the shared 16-slot probe lane refuses a check, the admission backoff of up to 30 s) and not measured. A verification that cannot decide is counted and does not fault the watch. Not covered (accepted residuals, tracked in #7877): a parent renamed away and a key re-created at the original path before the next sample, a rename away and back inside one interval, a verification that could not decide (it keeps the old handle, so a rename it saw is missed until the next one that decides), a renamed shelter ancestor of an Ancestor-mode watch (never verified, including one re-established after a verdict), a persistently access-denied verification open (the watch stays unverified), the HKCR merged view, and a write in the renamed tree during the faulted window that can still deliver one fire for the registered key (item 34, adjudicated low, the emission pre-dates this change). Not yet fixed, and not accepted (triaged in #7877 as needing code): a registry open that hangs while holding one of the 16 shared probe-lane slots (item 35), and a key deleted and re-created around a check that can fault a healthy watch until the 30 s retry (item 37). The re-open can raise object-access audit events on a key that carries an auditing SACL and adds one short-lived worker per watched key per check. Not mitigated by the default: the failure-driven retry opens (30 s doubling to 300 s) are unchanged and can write failure-audit events on an audited key; an estate that opts in carries the full hazard, which is unmeasured, as is the cost at 50, 200 and 500 keys; the File check, which does the same for directories, is on by default and unmitigated; a runtime off switch is still owed (#7876); the setting is boot-time only and a Windows service reads it only through the agent's own parse, so persistence there is not verified. A malformed or out-of-range value (or a trailing `#` comment on the environment line, which a systemd `EnvironmentFile` does not strip) refuses to start the agent on every OS, including where the flag is ignored and under `--spark-disable`; on a Windows service that shows as Service Control Manager error 1053 with nothing in the agent log (#7877 item 47). The agent logs the effective state once at boot.
