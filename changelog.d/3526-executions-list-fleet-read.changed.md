- **The dashboard executions list and MCP `summarize_working_set` (`kind=execution`) now use the management-group-aware fleet-read gate that `GET /api/v1/executions` uses.** This is hardening plus an admission change, not a fix for a reachable leak. On `GET /fragments/executions`, a group-scoped-only operator gets a confined view (scope applied in SQL before the 50-row limit, counters and error preview projected to their agents) where they got `403`; a service-scoped token gets one too when RBAC enforcement is on and the tag store is reachable, and sees executions only through in-scope agents, never through the owner rule. `summarize_working_set` keeps its `Infrastructure:Read` first gate, so a group-scoped-only operator is still refused there. With RBAC off (the shipped default) both surfaces stay unconfined for every authenticated non-service, non-engine caller whose tier allows it (an engine principal is refused with `403` with RBAC off). The gate now answers a retryable `503` when the RBAC or management-group store is not open, for every caller except a JIT-elevated non-service session and, for the management-group store, an engine principal. The fragment's own failure notes render at HTTP `200` with a `data-degraded` attribute, so a monitor that treats `200` as healthy will not see them. For `summarize_working_set`, a confined caller's absent or out-of-scope execution id is audited `result=denied`, and a NUL byte in a `summarize_working_set` `kind=execution` id or a `get_execution_status` id is rejected. The id in that audit detail is neutralised and capped at 128 bytes (the `success` row too, for every kind), and the same applies to the `get_execution_status` and `get_agent_details` `denied` and `failure` audit ids. The `ITServiceOwner` ceiling on this gate was applied by PR #5546. See Upgrading.
