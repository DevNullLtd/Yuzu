- **A cached Guardian rule whose re-arm fails at agent start-up is now retried by the server's catch-up push instead of staying unarmed until the next policy change or restart (#5513).** The live case is a legacy guard that cannot create its watcher thread. Until a push applies cleanly, the agent now reports policy generation `0` plus the sparse heartbeat tag `yuzu.guardian_boot_rearm_unresolved` = `1`, so the server's existing reconcile sends the deployed set. Only the reported value changes: the persisted generation is never rewritten, and the `guaranteed_state.reconcile` audit rows read `generation 0 -> N`. A rule that keeps failing is re-pushed about every 25 to 30 s per agent at the default 30 s heartbeat with no back-off (the back-off decision in #5504 would also cover this loop); to find it, look for the agent log line `N cached rule(s) failed to re-arm at boot` or repeated reconcile rows for one agent id, and fix the host condition. Removing or disabling the rule server-side clears the flag on the next clean push, but it removes enforcement of that rule for every agent in its scope, so it is a last resort, not a fix. Not covered: a legacy guard that returns false at arm (#2797), and a server whose current generation is `0`, which does not push. The tag has no server reader yet (#5558). The catch-up applies where a legacy guard actually arms: Windows, and Linux with libsystemd and a reachable system bus (Service rules only); macOS legacy guards are stubs. No upgrade action is needed. Refs #5513.
