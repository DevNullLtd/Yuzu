- **Breaking — policy and instruction-definition YAML is read as written whatever its line endings, and two kinds of input the server cannot read as written are now refused with `400` instead of being stored with a different meaning (#2123).** The server's YAML scanner split lines on LF only, so in a Windows-authored (CRLF) file a blank line inside a nested block ended that block early, and a comment line indented less than the block did the same with any line endings. The predicates after it were dropped silently: a policy written for Windows devices tagged `prod` was stored as `ostype == "windows"` and evaluated against every Windows device, and a valid definition was refused with "Missing spec.execution.plugin". LF, CRLF and a lone CR are now all line breaks, and blank and comment lines never end a block. A key is read only as the first word on its line, so `scope:` inside a one-line value such as `description: "see scope: x"`, a commented-out `# tags: [lab]`, or a longer key such as `extratags:` is no longer read in place of the real key (a `scope:` or `managementGroups:` line inside a multi-line `description: |` block can still be read; see below).

  **Now refused with `400` (fail closed), where it was accepted before:**
  1. **A `tags` or `managementGroups` list that cannot be read as written.** This covers an inline `[ ]` list that does not close on its own line, `- item` lines at different indents, an item continued on the next line, and a list followed directly by an outer list's next item. A line missing its `- `, a `- item` line indented to `selector:`'s own column, an empty-string item, a single value where a list is expected (`tags: prod` or `managementGroups: abc123def456`; write `tags: [prod]`), and list lines written after a value on the key line (`tags: null` or `tags: [a]` followed by `- prod`) are refused the same way. `tags: null` and `managementGroups: null` on their own still mean none. Each of these used to be stored with an entry missing (a dropped tag widens the policy) or with an outer list's item absorbed as an extra management group. The error names the field and the entry (for a `- item` outside `selector:` it names `spec.scope`). For a list followed directly by an outer list's next item, end the list with another key first.
  2. **A `managementGroups` entry that is not a management group id** (anything outside letters, digits and `_ . : * -`). These used to be stored as a group matching nobody, and because a non-empty group list replaces the scope, the policy silently targeted zero devices. Group ids are server-assigned, so no working reference changes. A display name never matched a group, before or after.

  Also fixed: trigger lists no longer lose every trigger when a comment containing a hyphen precedes the first item, and an instruction definition holding two `---`-separated documents is refused whatever its line endings. The `policy.create` audit row now records the stored targeting (`scope=<scope_expression> groups=<n>:<ids>`).

  Not covered by this change, and tracked as follow-ups: a list line indented at or shallower than `scope:` itself, a `- item` written after another key (such as `platform:` under `selector:`, or any key after `managementGroups:`), tab characters in indentation, a `scope:` or `managementGroups:` line inside a multi-line `description: |` block, a null list item (a bare `- `, `tags: [,]`, or the empty entry in `[a,,b]`), a quoted key (`"tags":`) or a space before the colon (`tags :`), neither of which is read as the key, a block-scalar value (`platform: >`), a duplicate key (the server reads the first, a YAML parser the last), a flow-mapped selector (`selector: {tags: [prod]}`), and a compact `triggers:` list can still drop or replace an entry without an error, which leaves the policy targeting a broader, narrower or different device set than its YAML says, so keep a list's `- item` lines together directly under their key, write keys unquoted with the colon straight after the name, each key once, in block style, indent with spaces only, and keep those key names out of multi-line descriptions; a lone CR is also a line break to the server, but terminals and diffs render it as nothing, so a key after one is read without showing on its own line; product-pack installs still split and read definitions with their own scanner; and the workflow `steps:` parser is separate.

  Upgrade note: **policies created before this release are not re-read**, and one created from CRLF YAML, from YAML with a comment line inside a block, or with a single-value `tags: prod` (stored with no tag filter) may still target a broader device set than its YAML says. Before upgrading, read "Policy YAML is read as written" in `docs/user-manual/upgrading.md`: it has a read-only query to find them. Correcting a policy means deleting and recreating it, which deletes its compliance history, so export that evidence first. Automatic re-derivation and flagging is tracked in #7004.
