- **Breaking:** stored responses of Forensics-tier plugins (`app_usage`, `browser_inventory`, `execution_artifacts`, `privacy_permissions`, `remote_access_audit`) are now served only to callers holding `Forensics:Read` in addition to `Response:Read` (#4990). The tier applies on the stored-response read paths of REST, MCP and the dashboard (including the executions drawer and the hardware result poll) and in the server's own consumers of those rows: bundle collation, result-set membership, policy checks (such a check scores `unknown` and stores no check output), the live output stream (nothing is published for a Forensics-tier frame, so the dashboard Console stays on "Waiting for results..."; read the rows through the execution results), and the failure text kept in execution records, the event outbox and stream, and copied into failure notifications, analytics events and webhook and offload payloads, which is reduced to a short machine token or `forensics_error`. Only a global `Forensics:Read` admits these rows: there is no management-group scoped read tier, and a hand-authored scoped grant reads nothing from these stored-response routes. Other readers see the rows as absent, with counts, caps and filter options computed over the rows they may read, so an empty result no longer implies that no data exists. A read whose authority cannot be determined (the authorization store is unavailable) is refused with a retryable error instead of a partial result (for sessions, API tokens, MCP tokens and engine principals; the engine-principal check treats a stale or degraded RBAC view as enforced, so an unavailable read reaches the permission check rather than reading as a refusal, and a service-scoped token is default-denied instead), and "create group from results" shows an error toast and creates nothing (`yuzu_server_forensics_tier_withheld_total`, alert `YuzuForensicsTierUnresolved`, which fires on a failure that recurs over about 10 minutes and not on one that recurs only every 5 minutes or longer). The plugin a response is stored under is the one the server recorded when it dispatched the command, not the one in the command id an agent echoes back; a response with no server record is stored as `~unverified`, which is treated as Forensics-tier (`yuzu_server_response_provenance_total`; the alerts `YuzuDispatchRecordWriteFailing`, `YuzuResponseProvenanceLookupDegraded` and `YuzuExecCorrelationReapSaturated` watch the dispatch record, and its hourly retention sweep now costs the per-pass cap instead of the table size and spares a record refreshed while it runs). Callers that held only `Response:Read` (the Viewer, Operator, PlatformEngineer and ITServiceOwner roles, and every non-administrator session while RBAC is off) no longer receive them; assign the new `ForensicsAnalyst` role to those who need them. A read that serves such rows also writes a `response.forensics.read` audit row, and an API-token, MCP-token or engine caller without a global `Forensics:Read` leaves an `auth.permission_required` denial row per read attempt. This release is a hard cutover: it supports initial deployment into a fresh database with no data imported from earlier builds, with every server writer and serving replica on the new build and earlier binaries excluded from the database. The server does not enforce this, so provisioning is a deployment responsibility; see "Deployment contract" under "Behaviour change: stored responses of Forensics-tier plugins need `Forensics:Read` (#4990, fresh deployment only)" in the upgrade guide.
