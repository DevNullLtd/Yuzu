- **Breaking — stored response rows are capped per command and device (256 by default).** The response store now refuses more than that many rows (`--response-max-rows-per-agent`, env `YUZU_RESPONSE_MAX_ROWS_PER_AGENT`, range 1-65536; the flag refuses `0`, an out-of-range env value is ignored and the default applies), so one agent can no longer grow a command's stored history without bound. Rows past the cap are dropped at ingest (the newest frames are lost, the first rows are kept, and the last kept row ends with a `...[rows past per-agent cap dropped]` marker), counted on `yuzu_server_response_ingest_dropped_total{reason="per_agent_cap"}` and logged with a rate-limited warning; one terminal-status frame is still recorded past the cap when none exists yet, so the command's outcome still shows. **Consequence:** an agent sends roughly one row per 64 KiB of streamed output, so a command whose output on one device exceeds about 16 MiB keeps its first part and drops the tail (approximate: a frame can be larger than 64 KiB); raise the flag for such commands. `per_agent_cap` is agent behaviour, not store health, so it is excluded from `YuzuResponseIngestDrops` and reported by the new informational `YuzuResponsePerAgentCapDrops`. A new database index is built once on first start of the new version. See "Upgrading" (#561).
