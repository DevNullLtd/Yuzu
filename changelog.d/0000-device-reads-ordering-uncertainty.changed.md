- **The Guardian device-compliance and per-device guards reads now report ordering uncertainty and unrepresented pending evidence (#7217).** `GET /api/v1/guaranteed-state/device-compliance` (MCP `get_guardian_device_compliance`) gains `order_uncertain` and `projection_pending` on each `guards[]` row, an `uncertain_guards` count (emitted guards with either flag, counted once, overlapping the verdict counts), `unrepresented_pending_guards` (the exact number of deployed-snapshot rules with a retained pending event and no census row for the device, excluded from `guards[]`, `total_guards` and the verdict counts) and `unrepresented_pending_rule_ids` (the first 50 in ascending byte order of the rule id; a count above the list length means truncation). `GET /api/v1/guaranteed-state/agents/{agent_id}/rules` (MCP `get_guardian_device_guards`) gains `unrepresented_pending_guards` and `unrepresented_pending_rule_ids` over all rules for the device, with `total_guards` still the number of `guards[]` rows. `assessable` and `last_updated` are unchanged. The device Guardian lens shows a notice for the unrepresented pairs and no longer draws the compliance tile as clean while any exist. The two reads behind each response are non-atomic observations (the pending count is read first, so a pair repaired between them can appear in both categories, never in neither), and a false flag or zero count does not establish freshness or completeness. A CMDB consumer must not render a clean state or a compliance percentage while `uncertain_guards` or `unrepresented_pending_guards` is nonzero, including under `assessable: true`, and a missing new key during a rolling upgrade means unknown, never `0`.

  The new count read runs under a 5 s statement timeout and fails closed, never as a zero. An ordinary store degrade is a `503` with `retry_after_ms: 5000` on REST and a retryable internal error on MCP. Expiry of the timeout, which means the retained pending backlog is too large to count in the budget, is answered honestly as non-retryable: a `503` with no `retry_after_ms` on REST and a non-retryable MCP error, because a retry fails identically until the backlog shrinks. These reads are counted on a new source of the existing counter, `yuzu_server_guardian_read_degrade_total{source="guardian_census_device"}` (with a `statement_timeout` reason on that source only), so `source="guardian_census"` again means only the `yuzu_server_guardian_census_pending_events` gauge read; the existing `YuzuGuardianReadDegraded` alert covers the new source unchanged. This closes the exception recorded in the #5690 census-ordering fragment, which said the device-compliance read did not yet report ordering uncertainty.
