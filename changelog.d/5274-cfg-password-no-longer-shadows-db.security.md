- **Breaking — `yuzu-server.cfg` can no longer override a stored password (#5274).** Login used to check the password hashes loaded from `yuzu-server.cfg` before the PostgreSQL auth store, so after a password change every restart brought the old config-file password back on that server, and other replicas kept accepting the old password until they restarted. Login now reads the auth store only; the config file only seeds the first administrator into an **empty** database (so an empty-database rebuild re-seeds whatever password the file holds — keep the file protected, and change that password after a rebuild). **Upgrade consequence:** a password you rotated by editing or regenerating `yuzu-server.cfg`, or by re-running the Windows server installer with a new `/ADMIN_PASS`, reverts on upgrade to the one stored in the auth database (usually the original first-boot password), and the rotated one stops working. If you rotated it because the old one was exposed, reset it in the product immediately after upgrading (Settings → User Management, or the direct-SQL fallback in the auth-store recovery runbook). At boot the server logs a warning naming each config-file account whose hash differs from the stored one and sets `yuzu_auth_cfg_credentials_stale` to their count. A login whose password could not be verified — the auth store could not be read, or the stored password changed while it was being checked (`yuzu_auth_credential_changed_during_verify_total`) — now gets `503` with `Retry-After` instead of `401`, writes no `auth.login_failed` row and does not count toward lockout. Editing the config file or re-running the installer no longer changes an existing account's password: use the in-product change/reset added in the #5342 entry, which also covers the installer's new upgrade refusal. See [Upgrading](docs/user-manual/upgrading.md).
