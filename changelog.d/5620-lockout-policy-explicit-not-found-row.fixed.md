- **`local_security_policy` `lockout_policy` no longer returns an empty result on a Linux host where no lockout key is found in the files read.** When at least one source (`/etc/login.defs`, `/etc/security/faillock.conf` and the PAM files `common-auth`, `common-account`, `system-auth`, `password-auth`) is read and none yields a lockout key (a `login.defs`/`faillock.conf` key or a `pam.<type>.<module>` line), the action now writes one `lockout_policy|lockout_keys|not_found|<files>` row (status OK), where `<files>` names exactly the files read. A source that is absent or unreadable keeps its own `source_state` row and no longer suppresses it (a host with no `faillock.conf` and no PAM lockout line gets both); if any key is found anywhere, `not_found` is not written. Every `faillock.conf` key counts as a key, and so do the `login.defs` keys `LOGIN_RETRIES`, `LOGIN_TIMEOUT`, `FAILLOG_ENAB` and `FAIL_DELAY`, which are login-prompt and faillog settings rather than account-lockout counters. It reports what was found in the files read, not that lockout is off or unenforced: `faillock.conf` drop-ins, PAM include/substack targets, other PAM services such as `sshd`, directory-server (IdM/SSSD) policy and `fail2ban` are not read, so do not treat the row as a control verdict. With no readable source there is no `not_found` row, and an unreadable sibling still leaves the status CONSTRAINED. **Mixed-version fleets:** an agent without this change never writes the row; it returns an empty result unless `login.defs` or `faillock.conf` is absent, every PAM file is absent or a file is unreadable, and then only the `source_state` rows for those, so an empty result from an older agent means "not known", not "has lockout". **Existing servers** keep the stored definition (the bundled reseed does not replace an existing id), so the new field descriptions reach fresh installs only until the definition is re-imported. (#5620)
- **`local_security_policy` reports a symlink whose target is missing as an unreadable source, not an absent one.** On Linux and macOS, `/etc/pam.d/system-auth` and `password-auth` are often links managed by `authselect`; one left dangling (mid-`apply-changes`, or its target removed) used to read as an absent PAM alternative, silently dropped, and `lockout_policy` could then answer `lockout_keys|not_found` over the files that remained with nothing saying one had been skipped. A link whose target path runs through a regular file is treated the same way. It is now its own `source_state|unreadable:dangling_symlink` row, the status is `CONSTRAINED`, and the reason carries `<path>:dangling_symlink`. A path that simply does not exist is unchanged (absent), and so is a link that resolves. (#5620)
- **`local_security_policy` reads PAM lines the way Linux-PAM does.** The type is matched case-insensitively (`AUTH required pam_faillock.so` is an `auth` line) and a module given with a directory path is reported by its file name only (the directory is not shown), so a `pam_faillock` or `pam_pwquality` configured either way is no longer missed by `lockout_policy` or `password_policy`. (#5620)
