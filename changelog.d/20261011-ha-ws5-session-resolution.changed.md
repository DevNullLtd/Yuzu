- **Gateway-fronted agents' heartbeats, inventory reports and stream-status notifications now resolve against the durable route directory** (HA WS-5, `#4246` item 3, ADR-2002 section 7f). The gateway-upstream service looks a gateway `session_id` up in the Postgres route directory (batched reads of up to 1,024 ids on one connection per RPC) instead of only a per-replica in-memory map, so a replica that did not process the agent's registration no longer answers "unknown session" for it. `BatchHeartbeat` renews the lease of every directory-resolved session and lists a session in `unknown_session_ids` when the directory does not know it OR the directory knows it but the answering replica holds no local entry (for example right after a server-only restart), so the gateway still replays registration and the server rebuilds its local device list. A `session_id` that matches more than one directory row is refused as ambiguous (neither acknowledged nor listed; `yuzu_server_gateway_route_desync_total{op="session_lookup",outcome="ambiguous_session"}`, with the new `YuzuGatewaySessionAmbiguous` alert), and a failed directory read is counted under `yuzu_server_gateway_route_write_failed_total{op="session_lookup"}`: during a Postgres read outage `BatchHeartbeat` falls back to the replica's local hints and still acknowledges and renews leases for them (counted per batch in the new `yuzu_server_gateway_route_degraded_renewal_total`), `ProxyInventory` still ingests for a locally hinted session, `NotifyStreamStatus` CONNECTED is accepted only when the replica holds the matching local session and is otherwise refused (`outcome="connected_unverified"`; the gateway does not retry it, so the agent regains dispatch placement at its next reconnect), a CONNECTED whose directory row carries a different session id is rejected, and DISCONNECTED proceeds on the local check. `ProxyRegister` now rejects a presented session id that is not `gw-session-` plus 32 lowercase hex characters (`outcome="malformed_session_id"`), and refuses to adopt an id that a different agent's directory row already holds (`outcome="session_held_by_other_agent"`, expected zero, with the new `YuzuGatewaySessionHeldByOtherAgent` alert); that check does not serialize two concurrent adopts, which the ambiguity refusal then catches until a unique index on `session_id` ships. The agent presence record no longer has its `hostname` blanked by a heartbeat carrying an empty value (a stored hostname is reset only by deleting the row). Run one server replica during a rolling upgrade or drain the old replicas first: an old replica reports directory-known sessions as unknown, which makes the gateway re-register those agents. This does not lift the HA safe-to-scale gate: running a second server replica is still unsupported.
