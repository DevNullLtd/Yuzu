- **New `virtualization` plugin with a `host` action: is this device a VM, which hypervisor, and is the agent in a container.** One read-only action on all three OS (securable `Inventory`, operation `Read`, no approval gate, on by default). It returns a leading `status` row, one `host` row (`is_virtual`, `kind`, `vendor`, `product`, `source`, `confidence`) and one `container` row. `kind` is `guest`, `host_with_hypervisor`, `bare_metal` or `unknown`: a Windows machine running Hyper-V, VBS or WSL2 sets the CPUID hypervisor bit but is the host, not a guest, and the Hyper-V root-partition bit tells them apart. Linux reads CPUID, DMI, `/sys/hypervisor/type`, the `/proc/cpuinfo` hypervisor flag, the container marker files and the agent's own `/proc/self/cgroup`; macOS reads `kern.hv_vmm_present` and `hw.model`; Windows reads CPUID and the SMBIOS System Information table. No subprocess and no network on any leg. A source that cannot be read never reads as bare metal: the kind is `unknown` and the reason is on the status row and in the host row's `source` field. Windows does not read container membership (`unknown`, `windows:virtualization:container:not_read`). A KVM host reads `bare_metal` and a Xen dom0 reads `guest` with vendor `xen`, and on cgroup v2 an agent inside a cgroup namespace reads container `unknown`. New instruction `crossplatform.virtualization.host`.
