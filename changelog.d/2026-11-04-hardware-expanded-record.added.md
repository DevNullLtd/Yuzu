- **`GET /api/v1/hardware/{id}` and the MCP `get_hardware_ci` tool now serve the expanded hardware record.** `ci` gains the chassis (type, serial, asset tag, source), baseboard (vendor, product, serial, source) and hashed machine-id (hash, algorithm, source) values, and a `sections` array with each reported section's `status`, `reason`, `source`, `complete` flag and rows (cpu, dimm, disk, swap, volume, partition, topology; chassis, baseboard and machine_id are status only). A `constrained` section reads as incomplete rather than as a device with fewer rows, and an `unavailable` or `permission_denied` section shows its reason and no rows. A new `sections_state` (`found`, `absent`, `degraded`) tells "no sections stored" (an older agent) from a record whose `ci` could not be read. The record and its sections are read in one consistent snapshot, and a failed read of the sections answers the same retryable failure on both surfaces: `503` on REST and a retryable error on MCP, each with `retry_after_ms` 5000 and the record withheld, so clients must handle a `503` with `retry_after_ms` on `GET /api/v1/hardware/{id}`. The MCP output schema declares the new keys. The Hardware list search (`q`, on the REST route, the MCP `list_hardware_ci` tool and the dashboard) also matches asset tag, chassis serial and board serial. The OpenAPI document describes the new keys and the new `HardwareCiSection` schema.
