- **`GET /api/v1/hardware/{id}` now serves the expanded hardware record.** `ci` gains the chassis (type, serial, asset tag, source), baseboard (vendor, product, serial, source) and hashed machine-id (hash, algorithm, source) values, and a `sections` array with each reported section's `status`, `reason`, `source`, `complete` flag and rows (cpu, dimm, disk, swap, volume, partition, topology; chassis, baseboard and machine_id are status only). A `constrained` section reads as incomplete rather than as a device with fewer rows, and an `unavailable` or `permission_denied` section shows its reason and no rows. A new `sections_state` (`found`, `absent`, `degraded`) tells "no sections stored" (an older agent) from a failed read. The sections are read in one consistent snapshot, and a failed read answers `503` with a retry hint rather than a `200` with an empty list. The Hardware list search (`q`, on the REST route and the dashboard) also matches asset tag, chassis serial and board serial. The OpenAPI document describes the new keys and the new `HardwareCiSection` schema. The MCP `get_hardware_ci` tool shares the serialiser and so returns the same keys; its output schema is updated in a later change.
