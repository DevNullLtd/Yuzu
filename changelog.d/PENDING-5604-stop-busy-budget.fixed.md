- **Agent shutdown no longer overruns its 20 s deadline against a locked local KV store (#5604).** The Guardian engine's `stop()` has several serial writes to the agent's shared `kv_store.db`, and each costs the whole 5 s SQLite busy wait when another connection holds the database locked, so a stop could pass the shutdown watchdog and be ended by `hard_exit(4)` with no log line, losing a staged Spark baseline capture (the next boot would recapture drifted content as the baseline). `KvStore` now waits through a busy handler that reads an atomic budget, and `stop()` lowers that budget once, terminally, from 5 s to 1 s before it waits for the engine mutex; the lowering also cuts a write that is already waiting. Measured under real `SQLITE_BUSY` at production values, the shutdown timelines that reached 21 to 29 s on earlier code took 2.0 to 5.0 s (Linux, one run per point). `kBaselineStopLatestStart` is now 18 s and `kBaselineStopTroubleThreshold` 750 ms. Trade-off: a different process that holds the store locked for 1 to 5 s at the shutdown instant now fails the stop-time writes that a 5 s wait would have survived, costing one baseline recapture at the next start and a stale (never corrupt) loss ledger, both logged; plugin writes made from a plugin's `shutdown()` run at the same 1 s budget. A stalled disk write is not a lock wait and can still reach the watchdog. The path is dormant while `prefer_spark` is off.
