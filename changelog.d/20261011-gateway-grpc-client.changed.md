- **Breaking — the gateway's upstream channel moves from `{grpcbox, [{client, ...}]}` to `{yuzu_gw, [{upstream_client, ...}]}`, and the gateway no longer contains grpcbox.** UPGRADE ACTION: move the value across unchanged and delete the `{grpcbox, ...}` block; this ships in the same release as the `grpc_listeners` move above, so one edit of your `sys.config` covers both (`{grpcbox, [{servers, L}]}` becomes `{yuzu_gw, [{grpc_listeners, L2}]}`, `{grpcbox, [{client, V}]}` becomes `{yuzu_gw, [{upstream_client, V}]}`). The old key cannot stay in place: OTP applies a `sys.config` entry only to a loaded application and nothing loads one named `grpcbox` any more, so a leftover block would be silently invisible. The gateway therefore **refuses to boot** (`Refusing to start: {grpcbox, [{client, ...}]} is set`, or `{grpcbox, servers} is set`) if it finds either block, in the application environment or in any config file the VM was started with. It also refuses to boot with no channel named `default_channel` in `upstream_client` (`Refusing to start: no upstream channel is configured`) unless `{yuzu_gw, [{allow_no_upstream, true}]}`, and with an unusable `upstream_client` value. The upstream TLS posture is stricter than before: **any** `https` endpoint without `{verify, verify_peer}` or without a `cacertfile` / `cacerts` of its own is refused (the OS trust store would otherwise be used), and so is a channel that lists both `http` and `https` endpoints (`YUZU_GW_ALLOW_UNVERIFIED_UPSTREAM=1`, dev only, excuses the first, nothing the second); the boot log says `mutual-TLS` only when every endpoint also has `certfile` and `keyfile`. The image and its `sys.config` stay an atomic pair, and the offline pre-flight in `docs/user-manual/upgrading.md` is rewritten for this release: the previous release's script loads `grpcbox`, which is no longer in the release, and fails. The connection to the server is now the gateway's own unary gRPC client over gun (`yuzu_grpc_client`, with a pool of HTTP/2 connections per endpoint that reconnects with a 100 ms to 5 s jittered backoff); the vendored, patched grpcbox, its integrity check in CI and release, and chatterbox, hpack, acceptor_pool and gproc are gone, and the direct dependencies are cowboy 2.19.0, gun 2.5.0 and ctx 0.6.0 beside gpb, telemetry, prometheus, prometheus_httpd and recon. The wire protocol, the protobuf contracts and the server are unchanged. Behaviour you may notice: the channel opens one connection per endpoint by default, as grpcbox did (`pool_size`, 1 to 64, is a channel option; raise it only if you accept that, behind a layer-4 VIP in front of several server replicas, the connections can reach different replicas); TCP_NODELAY on the upstream sockets is now a first-class default (`upstream_tcp_nodelay`, default true, applied to http and https endpoints alike, an endpoint's own `nodelay` socket option still wins) and the old mechanism that restarted the channel is gone, so the log line `Upstream channel default_channel: could not restart it with TCP_NODELAY` no longer exists (one live-stack measurement with TLS: `ProxyRegister` mean about 3 ms, against about 45 ms with nodelay off); a call that finds no live connection waits for one that is already connecting, and otherwise fails at once with the last connection error; responses are limited to 16 MiB and messages are never compressed; a new INFO line `Upstream channel <name> connection <n> down (<reason>); retrying in <ms> ms` appears per failed attempt; the grpcbox-era channel options `balancer`, `encoding` and `sync_start` are accepted and ignored. A running gateway presents the certificate it loaded when it opened a connection, and a reconnect reads the files again (measured with the new client; Erlang's `ssl` caches file contents for about 120 s). `upstream_addr`, `upstream_port` and `upstream_pool_size` in `sys.config` were read by nothing before and still are: the endpoints of the channel are what is dialled, and `YUZU_GW_UPSTREAM_ADDR` / `YUZU_GW_UPSTREAM_PORT` are now ignored with a boot warning instead of logging an `ENV override` line. See `docs/user-manual/upgrading.md`, "The upstream channel moves to `upstream_client`", and `docs/user-manual/gateway.md`, "The upstream client". A channel option (`pool_size`, `connect_timeout`, `max_receive_message_bytes`) that is out of range or not an integer is still replaced by its default, but the gateway now logs a warning for each at boot instead of staying silent. A CA, certificate or key file an `https` endpoint names that is missing, unreadable, empty or holds no certificate or key is now reported by name (an ERROR line at most once a minute, a boot warning, and `/readyz` 503 through a new `upstream_tls_files` check) instead of showing only as `bad_tls_options`; a directory where a file belongs refuses boot, a merely missing file does not.
