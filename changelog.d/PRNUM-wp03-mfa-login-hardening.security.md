- **Breaking — MFA codes now have a durable per-account failure budget that cannot be disabled; concurrent password hashing is capped by lane; first-run password prompt needs a terminal.** Wrong TOTP or recovery codes at `POST /login/mfa` and `POST /login/mfa/stepup` are counted per account in the auth store (new `auth.users.mfa_failed_count` / `mfa_locked_until` / `mfa_last_attempt_at`, auth schema v4, database clock, shared across replicas). The attempt is reserved in one row-locked statement before the code is checked, so an attempt that cannot be counted is refused (`503`) instead of verified; a verified code gives back only its own reservation. After `auth_lockout_threshold` failures (5 when it is `0`) within `auth_lockout_window_secs` (default 900 s; 300 s only if configured `<= 0`) the account's second factor answers the uniform `401` until the window passes, audited once as `auth.mfa.lockout.applied`. An operator unlock (REST and MCP), administrative password reset, reactivation, `--mfa-reset` and `--break-glass-arm` clear it; the break-glass account is not exempt from the budget. Concurrent PBKDF2 work on `/login`, the password-change proof and recovery-code checks is capped process-wide at a quarter of the HTTP worker pool (at least 8, never more than half the pool; 66 by default), split into lanes: a break-glass floor (16 by default) that no other lane can use, an unauthenticated lane (25) with a per-address share set by the new `--auth-pbkdf2-per-source-cap` / `YUZU_AUTH_PBKDF2_PER_SOURCE_CAP` (default 4; the address is the TCP peer, so raise it behind a proxy, load balancer or NAT), and an authenticated lane (25, at most 3 per principal), with a fixed split so neither shared lane can starve the other. The per-username serialisation that the lockout accounting needs now waits at most 150 ms and then answers the same `429` (`reason="stripe_busy"`), so a flood of logins for one name cannot pin the HTTP workers; the lanes bound concurrent hashing, not workers. A full lane answers `429` with `Retry-After` without hashing or counting anything; under `--auth-mode=sso-only` the sign-in gate runs before any slot is taken. An unknown username at login now spends the same PBKDF2 as a wrong password for an existing, unlocked account, narrowing the timing difference (a locked existing account still returns before hashing, and a malformed name returns earlier, as before). First-run setup on Linux and macOS no longer echoes the administrator password and refuses to prompt when stdin is not a terminal (Windows still accepts piped input), which breaks automation that pipes the password in. See `docs/user-manual/upgrading.md`.
