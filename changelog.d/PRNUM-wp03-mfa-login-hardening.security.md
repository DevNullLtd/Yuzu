- **Breaking — MFA codes have a durable per-account failure budget that cannot be disabled; concurrent password hashing is capped by lane; first-run password prompt needs a terminal.** Wrong TOTP or recovery codes at `POST /login/mfa` and `POST /login/mfa/stepup` are counted per account in the auth store (new `auth.users.mfa_failed_count` / `mfa_locked_until` / `mfa_last_attempt_at`, auth schema v4, database clock, shared across replicas). The attempt is reserved in one row-locked statement before the code is checked, so an attempt that cannot be counted is refused (`503`) instead of verified; a verified code gives back only its own reservation. After `auth_lockout_threshold` failures (5 when it is `0`) within `auth_lockout_window_secs` (default 900 s; 300 s only if configured `<= 0`) the account's second factor answers the uniform `401` until the window passes, audited once as `auth.mfa.lockout.applied`. An operator unlock (REST and MCP), administrative password reset, reactivation, `--mfa-reset` and `--break-glass-arm` clear it; the break-glass account is not exempt from the budget. Concurrent PBKDF2 work on `/login`, the password-change proof and recovery-code checks is capped process-wide at a quarter of the HTTP worker pool (at least 8, never more than half the pool; 66 by default), split into lanes with a fixed split so neither shared lane can starve the other: a break-glass lane (`min(4, cap/4)`, one per source address, taken without waiting), an unauthenticated lane (31 at the default pool) with a per-address share set by the new `--auth-pbkdf2-per-source-cap` / `YUZU_AUTH_PBKDF2_PER_SOURCE_CAP` (default 4; the address is the TCP peer, so raise it behind a proxy, load balancer or NAT), and an authenticated lane (31, at most 3 per principal). Every login attempt takes a slot, including a password over 1024 bytes (whose hash is skipped but which still takes a stripe and a database read), so a flood of them is bounded by the cap. A full lane answers `429` with `Retry-After` without hashing or counting anything; under `--auth-mode=sso-only` the sign-in gate runs first (its one database read, the break-glass arm state, is cached for 1 second, single-flight and fail closed: an armed answer is honoured only while the cache is younger than 1 second and a local deadline from the database clock's remaining arm time has not passed, and the read's lock wait and statement are each capped at 1 second; the decision to admit is bounded at 4.5 seconds whatever the read takes) and refuses every name except an armed break-glass account with the same `401`, and a busy break-glass lane is answered with that same generic `401` (never a distinguishable `429`); the break-glass lane is keyed on the TCP peer address (one slot per address, shared by everyone behind a proxy) and `--auth-pbkdf2-per-source-cap` does not apply to it. The per-username serialisation that the lockout accounting needs bounds each request's wait to 150 ms and caps the requests waiting at 2 per stripe and `max(2, pool/8)` overall; a flood from many addresses can still occupy a good part of the worker pool, and one colliding name can keep a victim's stripe busy (see `docs/user-manual/authentication.md`, Honest limits); a database-atomic reservation that removes the stripe is tracked as #8215, and lane starvation by a flood of distinct addresses (ordinary lane about 8 addresses at the default per-address cap of 4 and the default pool, break-glass lane 4 addresses at a pool of 64 or more) is open and tracked as #8307; the lanes are per replica. Under `--auth-mode=sso-only` the break-glass account keeps no lockout counter and takes no stripe. The break-glass arm window authorises the sign-in only: `POST /login/mfa` checks the arm state after the pending token is consumed and before a code is verified, and again before the session is created; if the arm was removed or its window ended since the password step, the login ends with the same generic `401` as a wrong code at that step (no `Retry-After`, no `Set-Cookie`), counted in `yuzu_auth_break_glass_pending_refused_total{reason,stage}`. An arm state that cannot be read is not treated as "not armed": before verification nothing is spent and the pending token stays usable; after verification the login completes only inside the bound the first check's read gives (`yuzu_auth_break_glass_pending_transient_admitted_total`), and a recovery code, which is consumed when it is checked, can be used and the login still refused whenever that second check refuses (the arm was removed, the window ended, or the arm state could not be read) or the session cannot then be created. The second check reads the arm state itself and does not wait for another request's read. The server stops honouring an "armed" answer once 4.5 seconds have passed since the start of the database read that produced it (about 2 seconds when the database answers inside its caps); this bounds the decision to admit, not the database writes that then create the session, and it is measured, like the local end of the window, on the server's monotonic clock, which does not advance while the host or virtual machine is suspended (after a resume a cached "armed" answer up to one second old on that clock can still be served at the password step and the first MFA check, but the second check asks the database, and when it cannot read, the login completes only if the wall clock also shows at most 4.5 seconds since the read behind the first check started; a virtual machine paused by its hypervisor may stop both clocks, and such a pause is then not seen); `yuzu_auth_break_glass_arm_gate_total{result=read_failed|refresh_busy|stale_read}` counts the answers where the arm state could not be established. A session minted inside the window is NOT revoked when the window ends and lives its full 8 hours: an API token minted from that session stays valid until its own expiry or revocation. After a break-glass login, as the break-glass user use Sign out everywhere (`DELETE /api/v1/sessions/me`), which ends its sessions and revokes every API token it owns (read the answer's `db_persisted` fields: the route answers `200` even when a write did not persist); `POST /logout` and the administrator's `DELETE /api/v1/sessions?username=<break-glass user>` leave its API tokens valid. Disclosed and not closed: response timing at `POST /login` shows which name is the break-glass user and whether it is armed, and a caller holding a break-glass pending token can tell at the MFA step whether the account is armed now: by timing, by a `503` in place of `401` while the auth store is failing but the arm state is still served, by whether the pending token stays usable, and by whether wrong codes count toward the second-factor lock (see `docs/user-manual/authentication.md`); otherwise body and headers do not differ. The server logs the resolved sizes at start and warns on a pool under 64. An unknown username at login spends the same PBKDF2 as a wrong password for an existing, unlocked account, narrowing the timing difference (a locked existing account still returns before hashing, and a malformed name returns earlier, as before). First-run setup on Linux and macOS reads the administrator password with echo off and refuses to prompt when stdin is not a terminal (Windows still accepts piped input), which breaks automation that pipes the password in. See `docs/user-manual/upgrading.md`.
