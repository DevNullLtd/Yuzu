- **`POST /api/v1/workflows/{id}/execute` and the MCP tool `execute_workflow`.** The two are twins of one shared sequence (authorize every step's `plugin.action` at the dispatch chokepoint before anything is sent, run the workflow, write the audit rows, publish the event), so they answer alike. A run is synchronous, bounded to 60 seconds, holds one of at most 2 concurrent workflow-run slots per principal drawn from the held-open budget (`--max-sse-streams`), and re-checks the caller's credential before every step: a token revoked mid-run stops the run (the check reads the token, and an engine token's backing principal, from the database at every step boundary rather than from the 60 second token cache, so a revoke made on any replica is seen at the next step; the step already sent is not recalled), and a credential whose state cannot be read after one more try also stops it. The MCP tool needs an approval ticket at the supervised tier (the ticket binds the ordered `plugin.action` of every step, see the security entry) and REQUIRES an `idempotency_key` (8 to 128 characters from `A-Z a-z 0-9 . _ : -`); the REST route takes an optional `Idempotency-Key` header. A repeat of a key with the same request sends nothing and answers with the status of the run the key is bound to (`running`, `completed`, `partial`, `failed`, `aborted`, `interrupted` or `indeterminate`, the last for a run whose outcome the stored rows cannot prove); the same key with a different request is `422` (MCP `-32602`) `idempotency_key_conflict`. A run is classified from each step's final result, so a first answer and its replay report the same outcome. Every `workflow.execute` audit row of a call carries the call's `correlation_id=` (and `approval_id=` on MCP when a ticket was presented), the run row records the caller's account name and correlation id, and both twins publish the `workflow.executed` platform event that the legacy route already published. New series: `yuzu_server_workflow_runs_in_flight`, `yuzu_server_workflow_run_refused_total{reason}`, `yuzu_server_workflow_run_idempotent_total{outcome}`, `yuzu_server_workflow_run_outcome_total{outcome,reason}`, `yuzu_server_workflow_finalize_failed_total`, and `yuzu_server_workflow_executions_rows`, `yuzu_server_workflow_executions_bytes` and `yuzu_server_workflow_executions_stats_unavailable_total` for the never-pruned `workflow_executions` table (see `docs/user-manual/metrics.md`). Five alert rules ship in the `yuzu-dispatch` group of `docs/prometheus/yuzu-alerts.yml`: `YuzuHeldOpenUtilisationHigh`, `YuzuWorkflowFinalizeFailed`, `YuzuWorkflowRunGlobalCapRefused`, `YuzuWorkflowIndeterminateReplays` and `YuzuWorkflowExecutionsTableLarge`, each with a `runbook_url`. The dashboard's Run now button, which posts to the legacy route, shows the refusal when the 2-run limit or a draining server stops a run, with the time to wait for the 2-run limit and, for a draining server, the server's advice to retry after the restart or against another replica (no retry time). `execute_workflow` is also the ticket path for a supervised-tier token, which the legacy route refuses (see the approval entry, #6949).
