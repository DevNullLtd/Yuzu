- **Agentic workers can read one device's live uptime or process list over MCP with `get_device_live`, the twin of `POST /api/v1/dex/devices/{id}/live`.** Required `agent_id` and `kind` (`uptime` or `processes`); strict input, so any other argument, a control character in `agent_id` or any other kind is refused before anything is sent. This is a probe, not a free read, and it is labelled so: it is served `readOnlyHint:false`, `idempotentHint:false`, `destructiveHint:false` and `openWorldHint:false`, because every call dispatches a command to the device (`processes` hashes each running executable and costs device CPU), writes audit rows and stores the result in the response store for `response_retention_days` (90 by default). The call is synchronous until the device answers or the 25 second poll deadline passes (plus at most one 0.5 second poll interval and one store read) and holds one server worker, so it is not for loops or fleet fan-out, and a client must not retry it blindly. It needs `GuaranteedState:Read` and, scoped to the device, `Execution:Execute`, and it refuses a `readonly` token, a `supervised` token (REST refuses that token too), `--mcp-read-only` and a draining server. While the audit store is on, each call that gets past those checks writes a fail-closed `device.live.uptime` or `device.live.processes` `requested` row before the dispatch (no durable row, no probe); both scoped permissions are decided again after that row and a withdrawn one sends nothing, while an unreadable permission store answers a retryable `gate_unreadable`. A refusal after the row writes one `failure` row of the same verb; the generic `mcp.get_device_live` row is written after a successful answer and for a tier, approval or read-only refusal, and a lost success row is flagged `audit_persisted:false`, and a `requested` row that cannot be stored (`audit_failed`, nothing sent) leaves one generic `mcp.get_device_live` `failure` row. The answer is given only after the device finished (partial output without a final row is never returned, except an answer already over the size cap, which this tool cuts and flags `truncated` at once and REST refuses; a chunk the server failed to store cannot be detected, so a complete-looking answer can have a hole in it, a response-store ingest property that affects every reader of stored results) and is capped at 1000 process rows and 1 MiB, setting `truncated` when either cut applies (an answer already over the cap is cut at once, and which rows survive a cut is not promised). Process paths can carry user names: the output is behavioural personal data. On every OS a `processes` row can carry an empty `sha256` and `path` or a `hash_unavailable:<cause>` marker in the `sha256` field, and an unprivileged Linux agent additionally cannot read other users' images. It draws on the same live-read limit as the REST route and the quarantine release confirmation (2 per principal, 4 in all; over it the tool answers `-32012` with `retry_after_ms` 2000). See the MCP reference (`get_device_live`).
