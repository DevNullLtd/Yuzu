- **Agentic workers can read one device's live uptime or process list over MCP with `get_device_live`, the twin of `POST /api/v1/dex/devices/{id}/live`.** Required `agent_id` and `kind` (`uptime` or `processes`); strict input, so any other argument or kind is refused before anything is sent. The call is synchronous for up to about 20 seconds, holds one server worker and costs the device CPU (`processes` hashes each running executable), so it is not for loops or fleet fan-out. It needs `GuaranteedState:Read` and, scoped to the device, `Execution:Execute`, and it refuses a `readonly` token, a `supervised` token (REST refuses that token too) and `--mcp-read-only`. Each call writes a fail-closed `device.live.uptime` or `device.live.processes` `requested` row before the dispatch (no durable row, no probe) and a generic `mcp.get_device_live` row after the answer; both scoped permissions are decided again after the `requested` row and a withdrawn one sends nothing. The answer is capped at 1000 process rows and 1 MiB with a `truncated` flag. It draws on the same live-read limit as the REST route and the quarantine release confirmation (2 per principal, 4 in all; over it the tool answers `-32012` with `retry_after_ms` 2000). See the MCP reference (row 246).
