- **Breaking — gateway listeners move from `{grpcbox, [{servers, ...}]}` to `{yuzu_gw, [{grpc_listeners, ...}]}`; the gateway image and its `sys.config` are an atomic pair.** The agent (`:50051`) and management (`:50063`) listeners are now served by the gateway's own gRPC layer over Cowboy and Ranch instead of grpcbox; the wire protocol, the protobuf contracts and the management-plane SPKI peer pin are unchanged, and the upstream channel (`{grpcbox, [{client, ...}]}`) moves too, in the same release, to `{yuzu_gw, [{upstream_client, ...}]}` (see the entry on the gun-based upstream client): convert both blocks in one edit. Every shipped config and compose file is converted, but a config you wrote is not: a `servers` block now **refuses to boot** (`Refusing to start: {grpcbox, servers} is set`), as does an unset or empty `grpc_listeners` (unless `{allow_no_listeners, true}`), and **an old gateway image given a new-shape config binds no listener, logs nothing and still answers `/healthz` and `/readyz` with 200**, so upgrade and roll back the image and the config together. Each listener is one map with the keys `name` (mandatory, unique), `service_protos`, `services`, `listen`, `tls`, `auth_fun`, `origin`, `acceptors`, `http2` and `limits`; the maps `tls` (`certfile`, `keyfile`, `cacertfile`, `verify`, `fail_if_no_peer_cert`, `ciphers`), `listen` (`port`, `ip`, `socket_opts`), `origin` (`mode`, `sources`, `trusted_hops`), `http2` and `limits` (`max_connections`, `max_message_bytes`, `send_timeout_ms`) are closed too, so a legacy key (`grpc_opts`, `listen_opts`, `transport_opts`, `pool_opts`, `ssl`) or a typo refuses boot by name instead of being ignored. An `auth_fun` on any listener that serves the agent service (`agent_pb` in `service_protos`, or the AgentService itself among its `services`) is refused, a non-empty `grpc_listeners` with no entry that routes the AgentService (its `services` map has the key `'yuzu.agent.v1.AgentService'`) refuses boot too (unless `{allow_no_listeners, true}`, the literal `true`), and `socket_opts` may no longer carry `ip`, `ifaddr`, `fd`, `port` or `{local, _}`. The old `transport_opts` could carry SSL options the closed `tls` map does not: `versions`, `depth`, `crl_check`, `partial_chain` and an encrypted-key `password` are not supported and refuse boot (decrypt the key first; supporting them is a follow-up). `YUZU_GW_AGENT_PORT` and `YUZU_GW_MGMT_PORT`, which changed nothing before, now rewrite the port of the one listener that serves the proto (ignored with a warning when zero or several do), and `/readyz` now also requires every configured listener to be running and at least one to route the AgentService. The TLS 1.2 floor and the mutual-TLS and pin postures are unchanged, but the TLS options are not the OTP defaults any more: the cipher list is chosen by the certificate's key type (ECDHE-ECDSA AEAD suites for an EC key, ECDHE-RSA AES-GCM suites for an RSA key) unless `tls.ciphers` is set, the gateway's cipher order decides the suite (`honor_cipher_order`), and TLS session reuse is off (`reuse_sessions` false), so every reconnect is a full handshake and a reconnect herd costs more CPU; FIPS mode is not claimed. The shipped production and reference configs now set `limits` on both listeners: `max_connections => 60000` on the agent listener and `256` on the management listener (neither had a ceiling before), and an explicit `max_message_bytes => 4194304` (the default). `max_connections` bounds file descriptors and is not protection against a hostile peer: a peer that completes the handshake and keeps sending can hold agent-listener connections open and fill the ceiling (an accepted residual risk of the unauthenticated agent port; limit connections per source at the L4 balancer or firewall), and about 256 held connections would stop the server making new connections to the gateway (before the TLS handshake anyone with layer-4 reach can hold one, after it any holder of a certificate issued by the install CA, which every enrolled agent has), a known limitation that will not be fixed in the gateway, so firewall the management port (`:50063`) to the server replicas, bind it to the management interface with `listen.ip` and, where you can, multi-home the server onto a separate interface. See `docs/user-manual/upgrading.md`, "Gateway listeners move to `grpc_listeners`" (key mapping, an offline pre-flight check, roll-forward and roll-back) and `docs/user-manual/gateway.md`, "gRPC listeners".
- **Gateway: the client address reported upstream is now decided by the gateway, and an older gateway still lets an agent forge it, so upgrade every gateway first.** `RegisterRequest.gateway_observed_peer` is set by the gateway to the TCP peer, or, for a listener behind a load balancer or router, to the address a trusted proxy vouched for, and whatever the agent sent is discarded; the server's audit `source_ip` follows it. A new per-listener `origin` option (`transport`, the default; `proxy_protocol` for an F5 iRule or HAProxy `send-proxy-v2`; `forwarded_for` for a router that terminates TLS, reading the `x-forwarded-for` entry `trusted_hops` places from the right and ignoring everything to its left) names the proxies to trust by their address (`sources`); a claim from any other peer is ignored and the call is attributed to that peer. When a configured proxy gives no usable address the call is sent with no observed address and the server records `origin_observed=false`. A listener left in `transport` mode behind a proxy you did not configure attributes every agent to the proxy and flags nothing. New counters `yuzu_gw_grpc_origin_ignored_total{mode,reason}` and `yuzu_gw_grpc_dropped_data_bytes_total{reason}` and two alerts, `YuzuGatewayOriginUnusable` and `YuzuGatewayOriginSourcesMismatch`. Also new on the gateway: a queued `Register` or `Inventory` upstream call whose requesting gRPC call has already ended (the client reset the stream or its deadline passed) is now skipped instead of run, counted in `yuzu_gw_upstream_calls_dropped_total{rpc_name}`; the reservation a dying `Register` held is released at once; and the handler-failure WARN is limited to one line per second per node (`grpc_runner_warn_interval_ms`). See `docs/user-manual/gateway.md`, "Client addresses behind a proxy" and "Moving the agent edge to mutual TLS".
- **The gateway's management listener receives up to 100,000 HTTP/2 frames per 10 s (ten times Cowboy's default) before it closes the connection.** The C++ server sends a whole fan-out over the one connection it holds to the management listener. A unary call is about two received frames, so Cowboy's own flood guard (10,000 frames per 10 s, `{10000, 10000}`) closed that connection with `enhance_your_calm` after about 5,000 calls. Every call in flight on it then failed: a 25,000-agent fan-out lost about 1,024 calls. A listener that routes the ManagementService now defaults `max_received_frame_rate` to `{100000, 10000}`, which is about 5,000 calls per second and still finite. `sys.config.prod` and the reference config also set it explicitly. A listener that serves only agents keeps Cowboy's default. An entry's `http2` map still overrides the value. Raising `max_concurrent_streams` does not change this ceiling.
- **The gateway now bounds the memory an unauthenticated peer on the agent port can make it hold, in three ways.** Before, a peer could open `max_concurrent_streams` streams on one connection, send a 4 MiB length prefix and all but the last byte of each request, send no `grpc-timeout`, and hold about 4 MiB per stream (roughly 128 MiB per connection at the shipped 32-stream limit) for the life of the connection; a few hundred such connections could exhaust the node and take the management plane with it. Now: (1) a new `limits.max_connection_memory_bytes` (default eight times `max_message_bytes`, i.e. 32 MiB, sized so that an agent sending messages of the full `max_message_bytes` never reaches it; `infinity` disables it, and an explicit value must be at least 1 MiB) caps each connection's memory with a `max_heap_size` on the Cowboy connection process that counts the refc buffers its streams hold, so a connection that buffers more than that of half-finished requests is killed and counted in `yuzu_gw_grpc_connection_killed_total`; (2) a new `limits.request_timeout_ms` (default 30000; `infinity` disables it) aborts a unary or server-streaming stream that buffers its one request that long without completing it with `DEADLINE_EXCEEDED`, counted in `yuzu_gw_grpc_recv_timeout_total`, and never cuts a long-lived bidirectional `Subscribe`, which runs before any message; (3) a new node-wide memory load shedder suspends the agent listener(s) — never the management listener — while `erlang:memory(total)` is above a high-water mark (default 0.75 of system memory) and resumes them below a low-water mark (default 0.65), configured under `{yuzu_gw, [{memory_shedding, #{...}}]}`, reported by the gauge `yuzu_gw_memory_shedding_active` and counter `yuzu_gw_memory_shedding_suspensions_total` and the alert `YuzuGatewayMemorySheddingActive`, and making `/readyz` report not-ready while shed so a load balancer drains the node. The shipped agent listener sets `max_connection_memory_bytes => 33554432` and `request_timeout_ms => 30000` (both the defaults); the shedder's defaults apply with no config. This does not change the credit/flow-control policy and does not close the accepted residual that a quiet held connection still occupies a connection slot. See `docs/user-manual/gateway.md`, "Connection ceilings and the unauthenticated ports" and "Node-wide memory load shedding".
- **The management-plane pin no longer reads a file on every call.** A `{cert_file, Path}` pin in `mgmt_peer_pins` is now re-checked in the background every `mgmt_pin_refresh_ms` (default 5000 ms; boot refuses a value outside 100 to 3600000). Each call checks the pin from memory, so a slow or stalled certificate volume can no longer stall the gateway's handling of the server's commands (#5696). A rotated server certificate can be refused for up to one interval after the swap. The refusal is fail-closed and the server does not retry it: commands it forwards to the gateway in that window fail as `gateway_unauthenticated` (visible as failed commands and in `yuzu_server_gateway_forward_total{status="unauthenticated"}`); commands after the interval go through. That window no longer pages (see the alert entry below). The log line for a refused management peer is now a WARNING, rate-limited to one line per reason per second with a count of suppressed lines. The rejection counter still counts every refusal.
- **A management pin file that fails to read no longer cuts the gateway off from the server's commands.** Before, one failed read of a `{cert_file, Path}` pin (the file missing for a moment, unreadable, or caught half-written) withdrew the pin, so every command forwarded to the gateway was refused while `/readyz` stayed green. Now the gateway keeps the key it last read, reports the file as unreadable (`yuzu_gw_cert_file_readable{role="mgmt_peer_pin"} = 0`, a WARNING log line) and `YuzuGatewayMgmtPinUnresolved` fires after 2 minutes with the action "fix the file". A file read successfully with a different key still replaces the pin. Deleting, emptying or corrupting the file therefore does **not** revoke the pinned key, which the gateway keeps admitting: to revoke it, replace the file with the new certificate, or remove the entry (which applies at the next gateway restart). The kept key is only ever one that was pinned, and a pin file that is unreadable when the gateway starts still pins nothing (fail closed). Revocation by identity instead of a pin is #6016.
- **A routine rotation of the server's certificate no longer pages; a real pin mismatch still does.** `YuzuGatewayMgmtAuthRejected` (`increase(...[1h]) > 0` on every reason) fired for about an hour after every rotation. It is split in two. `YuzuGatewayMgmtAuthRejected` keeps its name for every reason except `pin_mismatch` and fires at once (none of them comes from a rotation). The new `YuzuGatewayMgmtPinMismatch` (critical) fires on `pin_mismatch` unless the gateway's new gauge `yuzu_gw_mgmt_pin_rotated_timestamp_seconds` (the time it last pinned a different key; 0 until then) moved in the last 4 minutes; the counter is read one minute late because the rotation's rejections come just before that timestamp. Rejections that continue after a rotation, or with no rotation at all, fire. The suppression assumes the scrape interval plus `mgmt_pin_refresh_ms` is at most a minute.
- **The gateway now reports when its certificates expire, and alerts with rising urgency.** New gauges `yuzu_gw_cert_expiry_timestamp_seconds{role,name}` (the `notAfter` of every certificate file the gateway is configured with: each listener's certificate and CA, the upstream client certificate and CA, and each management pin file) and `yuzu_gw_cert_file_readable{role,name}`, refreshed on the pin watcher's tick. New alerts `YuzuGatewayCertificateExpiringSoon` (warning, under 30 days: schedule the renewal), `YuzuGatewayCertificateExpiryImminent` (critical, under 7 days: renew today), `YuzuGatewayCertificateExpiryCritical` (critical, under 24 hours: renew now) and `YuzuGatewayCertificateFileUnreadable` (warning, a listener or upstream certificate file unreadable for 10 minutes).
- **The server's certificate expiry alerts use the same ladder.** `YuzuCertificateExpiringSoon` now warns from 30 days (was 7) down to 7 days, the new `YuzuCertificateExpiryImminent` (critical) covers 7 days to 24 hours, and `YuzuCertificateExpiryCritical` still covers the last 24 hours. The bands no longer overlap, so a certificate pages once at a time. Alert routes keyed on the old 7-day warning should be checked.
