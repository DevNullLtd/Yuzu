- **Breaking - the agent reports installed software as a sectioned blob (contract v3), one section per source (a plugin action), and the v2 blob writer is gone.** Each of the eleven sources (`installed_apps.list_inventory`, `pkg_inventory.managers`/`packages`/`store_packages`, `windows_optional_features.list`, `msi_packages.list_inventory`, `runtimes.python`/`dotnet`/`jvm`, `middleware.ibm_mq` and the new `hardware.drivers_inventory`) is its own section: its rows in full the first time and after any `need_full`, then only a row-hash delta (`-` the rows that left, `+` the rows that arrived, with the section hash the agent will hold), and nothing at all while it is unchanged, so an unchanged device sends its report hash alone. The report has no weekly full resend any more: the server checks every delta against the section it holds and asks for that section in full when they differ. A source that cannot answer sends a status-only section naming why (`constrained`, `timeout`, `oversize`, `not_collected`) and costs only itself; its other sources are still reported, and the section is sent when its status or reason differs from the last acknowledged one, and again after a forced send (Sync now), a nack, a reconnect or restart, a send whose response was lost, and once the source has carried rows; not while it stays the same and acknowledged. A source that declares no result completeness at all is reported `constrained` (`unknown`) and its rows are not trusted as complete; the agent counts these in the heartbeat tag `yuzu.sync.installed_software.completeness_unknown_total`. **A constrained answer no longer replaces or removes what was stored.** Under v2 a constrained `runtimes.python` or `middleware.ibm_mq` read deleted that source's rows and a constrained `runtimes.dotnet`/`jvm` or `pkg_inventory.managers` read kept only the rows it had seen; now the server keeps the source's last confirmed rows and shows them as unconfirmed until a full section confirms them. An empty but clean read still retires the source's rows (an honest-empty full section), and an empty `installed_apps` listing is reported `constrained` (`no_rows`) rather than as "everything uninstalled". The agent and server of this build move together (hard cutover), server first: every server replica must ingest v3 before an agent of this build enrolls, because the agent has no v2 writer to fall back to and a server without v3 ingest cannot read the sectioned report (the upgrade note "the agent sends the sectioned installed-software report" has the order).
- **Each source runs on its own bounded worker.** `installed_apps`, `windows_optional_features` and `hardware.drivers_inventory` get 120 seconds, every other source 60. The daily sync never starts a second worker in a plugin: while an earlier worker of any action of a plugin is still running, every source of that plugin is reported `timeout` with token `busy` and none is started again; when no worker can be started the token is `rejected`. A first contact larger than one call (20,000 rows or 3 MiB) is split across successive collections, 30 seconds apart; a source whose full section alone cannot fit is reported `oversize` (`rows=<n>` or `bytes=<n>`) and sends no rows. Shutdown waits up to 3 seconds for any worker still inside a plugin and then exits with code 3 rather than unload the plugin under it. A stop that arrives while a source is waiting out its 120 seconds still ends in the existing 20-second shutdown watchdog (exit code 4), as an unbounded collection did before.
- **Device drivers are now reported by the daily sync.** `hardware.drivers_inventory` is a software source: kind `driver`; ecosystem `windows` (Windows PnP signed drivers, publisher the driver provider, else the signer) or `kernel_module` (Linux loaded kernel modules; the fixed provider `kernel` is a label, not a vendor, so the publisher is `via:kernel_module`). macOS reports the source `not_collected`. `driver` is a new `kind` value on the software catalogue, inventory REST and MCP filters, and `kernel_module` a new ecosystem (family `linux`). Drivers carry no CPE identity and are not assessed for vulnerabilities.
- **The agent reports an install location only under a known machine root, and spells epoch and release one way.** `install_location` (now filled: the Windows `InstallLocation`, the macOS `.app` path) is an allowlist: the value is canonicalised (quotes, padding, doubled separators, `.` and `..`, the `\\?\` prefix, the macOS `/System/Volumes/Data` spelling) and kept, in one spelling, only under Windows `Program Files`, `Program Files (x86)`, `ProgramData` or `Windows` on any drive, macOS `/Applications`, `/Library`, `/System/Applications` or `/Developer`, `/opt` or `/usr`, or Linux `/snap`, `/var/lib/flatpak`, `/nix` or `/app`; a location outside those roots, and every spelling the agent cannot resolve (a UNC path, an unexpanded `%ProgramFiles%`, an 8.3 name, a drive-relative or NT-namespace path), is blanked, while the row's name, version, publisher and hash are still reported; an rpm epoch of `0` or `(none)` and a release of `(none)` are written empty, so one package reads the same on every collection. The `installed_apps` `list_inventory` row gains a fourteenth token (`install_location`; a `|` in it is replaced with U+FFFD), and a clean pass of `installed_apps` and `windows_optional_features` now declares its result complete (`OK`/`FULL`) the way a degraded one already declared `CONSTRAINED`/`PARTIAL`. On Windows a failed read of the agent identity's own `HKCU` Uninstall key no longer marks the machine inventory degraded (its entries may be missing from a section sent as complete until the next clean read), and a missing `WOW6432Node` Uninstall key does on a 64-bit OS, so a 64-bit host without that key reports `installed_apps` constrained every cycle.
