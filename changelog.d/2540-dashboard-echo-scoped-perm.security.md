- **The dashboard Echo Purge and Re-enable actions now authorize through the same per-device scoped-permission gate as the REST purge route.** Both decide the posted device with the action's own permission (`Infrastructure:Delete` for Purge, `Execution:Execute` for Re-enable) and decide it again after the audit record is stored, so a grant withdrawn in between dispatches nothing. A caller the gate refuses now gets the same "Agent not reachable" answer (404) as an offline device, where a caller with no grant used to get a 403, and a missing gate, or a gate that answers 503 itself because it cannot evaluate authority, answers 503 and sends nothing (a failed RBAC read is still refused, with the 404). Service-scoped API tokens are refused 403 on both actions, as before. The retention-paused frame is gated by the fleet read check and shows only the devices the operator may see; its Re-enable and Purge buttons still appear only for a holder of a global grant, so a management-group-scoped operator purges through `POST /api/v1/echo/retention-paused/purge`, while Re-enable has no REST route: the dashboard shows them no Re-enable button even though the re-enable POST itself admits them.
