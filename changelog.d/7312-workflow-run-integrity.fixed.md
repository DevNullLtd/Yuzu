- **A workflow run is finalized when a dispatch throws, and is reported a success only when every step reached an agent.** A throw out of a workflow step used to leave the execution `running` forever and the transports could answer it as a retryable fault; the execution is now closed `failed` with its remaining steps `skipped`, the twins answer `500` (MCP `-32603`) `dispatch_exception` with no retry hint and name the run and the count of sends accepted, and a step refused at send time (definition changed, approval or targeting no longer admits the caller) is failed at once instead of being retried. The final status write is retried for up to 10 seconds with a back-off, and a lost commit acknowledgement on a run's admission is resolved with `pg_xact_status` instead of being reported as a failed start; if the status write still fails the row stays `running` and `yuzu_server_workflow_finalize_failed_total` moves. A run used to be labelled `success` whenever any step reached an agent; it is `success` now only when the engine recorded it `completed`, no step was refused at send time and every step's final attempt reached its agents, otherwise it is `partial`, `failed` or `aborted`. The shutdown drain now waits for a workflow run that holds its stream lease but has not reached the engine yet (one still in prepare), retry delays can be cut short by a shutdown instead of holding it for the whole delay, and the agent id list stored on a run row is deduplicated and capped at 1000 distinct ids and 131,072 bytes on every route (a marker with the count of distinct ids and a SHA-256 of the distinct list replaces the rest) so a looped run over unknown ids cannot grow the row without limit.
