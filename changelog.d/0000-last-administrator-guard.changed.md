- **Breaking: the last administrator can no longer be deleted or demoted.** Deleting (deactivating) or demoting the last member of a protected administrator population is now refused: the active local `role='admin'` accounts (with RBAC enforcement on or off) and, with enforcement on, the accounts that hold the `Administrator` role grant. `DELETE /api/settings/users/{username}` and `POST /api/settings/users/{username}/role` answer `409` with a toast (audit `last_administrator_blocked`); SCIM deactivation, delete, `active:false` and group-derived demotion answer `409` with `scimType` `mutability` (audit `scim.user.last_administrator_refused`); both are counted on `yuzu_server_rbac_last_admin_guard_refused_total{transport="dashboard"|"scim"}`. Linked credentials are still revoked before a delete, so when the refusal comes after the early check the `409` says the credentials were revoked and the account remains active; an IdP that retries a `409` is not stopped by it. This is a recovery rule, not a proof anyone can sign in. SCIM provisioning now refuses a username that already holds an `Administrator` grant or whose deactivated record has an elevated role, and a failed create/revive undo is guarded and escalated (`scim.user.compensation_failed`). Replicas running an older build do not enforce the guard, so drain them during a rolling upgrade; a server with an authentication database but no RBAC store refuses to start. See `docs/user-manual/rbac.md`.
