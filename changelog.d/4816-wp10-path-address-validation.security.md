- **Breaking: webhook and offload-target destinations in the link-local, cloud-metadata, unspecified, multicast and reserved address classes are refused, and several agent plugins refuse network and device paths and non-public destinations.** This hardens specific sinks reported by the 2026-11-17 security scan; it is not a general SSRF fix. *Server:* `POST /api/webhooks`, `POST /api/v1/offload-targets` and MCP `create_offload_target` refuse such a host, including numeric spellings (`2852039166`, `0xa9fea9fe`, `0`), audited `denied` / `destination_refused`; delivery resolves a name once through its own resolver pool, vets every answer, tries the vetted addresses in turn (only while no connection was made) and declines a delivery (`destination_refused`, `destination_unresolved`, `destination_resolver_busy`), counted in `yuzu_server_{webhook,offload}_delivery_refused_total{cause}` (not in `_failed_total`) and audited as `webhook.delivery.declined` / `offload_target.delivery.declined`. A stored target that points at such an address does not deliver. Loopback and private ranges are NOT refused (opt-in policy: #4816, #3870, open). The `content_dist` stage URL, `netprobe`, `network_actions`, `wol`, the `firewall` probe target, analytics, health check, NVD and directory sync have no destination guard in this build and are tracked with #4816 and #3870. *Agent (enforced by the agent's own plugin code; the server does not enforce it):* `ioc.check` and `disk_space.free` refuse UNC, device and reserved-DOS-name paths and non-fixed Windows drives, and POSIX paths on or symlinked into a mount of a listed network type (unlisted FUSE and overlays over a network mount included; no operator override: a network-rooted `/` is refused by `disk_space`); `ioc` opens POSIX paths component by component with no symlink followed and Windows handle-relative with no reparse point, reports every unexamined path in a `coverage` row (a clean device reads `complete`), hashes only regular files of at most 512 MiB (never `/proc`, `/sys`, `/dev`) and caps 64 paths and 256 hashes; `http_client.download` refuses a network/device destination, accepts only 2xx, requires a complete body (Content-Length, chunked or `expected_hash`), verifies, then replaces the destination atomically; `http_client` resolves once, requires every answer to be public and connects to a vetted address. **Linux `processes` and `procfetch` do not judge network mounts** (they hash through `/proc/<pid>/exe`, regular files only, capped, on a bounded helper), Windows and macOS `processes` and macOS `procfetch` refuse network and device image paths, Windows `procfetch` opens handle-relative, and Linux/macOS `filesystem` have no network-mount check (Windows `filesystem` is lexical). `windows_updates.patch_connectivity` caps caller targets at 16 and refuses loopback, link-local/metadata, multicast and reserved resolved addresses (RFC 1918 allowed). `ioc`, `processes`, `procfetch` and `disk_space` do the filesystem work on a bounded helper so a stalled mount cannot hold a command-pool worker (the helper itself can stay blocked). A Windows junction or directory symlink to a share is a residual for `filesystem`, `disk_space` and the download destination. `procfetch` returns an empty hash, never the SHA-1 of a truncated read. The `disk_space.free` `path` and the pre-flight `volume` refuse a leading double separator server-side. The Windows code paths were compiled with MSVC on Windows; they have not been run end to end.
