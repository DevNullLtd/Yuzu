- **Breaking: webhook and offload-target destinations in the link-local, cloud-metadata, unspecified, multicast and reserved address classes are refused, and several agent plugins refuse network and device paths and non-public destinations.** This hardens specific sinks reported by the 2026-11-17 security scan; it is not a general SSRF fix. *Server:* `POST /api/webhooks`, `POST /api/v1/offload-targets` and MCP `create_offload_target` refuse such a host, including numeric spellings (`2852039166`, `0xa9fea9fe`, `0`), audited `denied` / `destination_refused`; delivery resolves a name once through its own resolver pool, vets every answer, tries the vetted addresses in turn (it moves on only when the connect failed or the connect timed out, because nothing was sent; after a connection was made a read or write error ends the delivery with no second POST) and declines a delivery (`destination_refused`, `destination_unresolved`, `destination_resolver_busy`), counted in `yuzu_server_{webhook,offload}_delivery_refused_total{cause}` (not in `_failed_total`) and audited as `webhook.delivery.declined` / `offload_target.delivery.declined`. A stored target that points at such an address does not deliver. Loopback and private ranges are NOT refused (opt-in policy: #4816, #3870, open). The `content_dist` stage URL, `netprobe`, `network_actions`, `wol`, the `firewall` probe target, analytics, health check, NVD and directory sync have no destination guard in this build and are tracked with #4816 and #3870. *Agent (enforced by the agent's own plugin code; the server does not enforce it):* `ioc.check` and `disk_space.free` refuse UNC, device and reserved-DOS-name paths and non-fixed Windows drives, and POSIX paths on or symlinked into a mount of a listed network type (unlisted FUSE and overlays over a network mount included; no operator override: a network-rooted `/` is refused by `disk_space`); `ioc` opens POSIX paths component by component with no symlink followed and Windows handle-relative with no reparse point, reports every unexamined path in a `coverage` row (a clean device reads `complete`), hashes only regular files of at most 512 MiB (never `/proc`, `/sys`, `/dev`) and caps 64 paths and 256 hashes; `http_client.download` refuses a network/device destination, accepts only 2xx, requires a complete body (Content-Length, chunked or `expected_hash`), verifies, then replaces the destination atomically; `http_client` resolves once, requires every answer to be public and connects to a vetted address. **Linux `processes` and `procfetch` do not judge network mounts** (they hash through `/proc/<pid>/exe`, regular files only, capped, on a bounded helper; a hash that timed out or was not started reads `hash_unavailable:timeout` or `hash_unavailable:skipped`, at most two stuck helpers per dispatch), Windows and macOS `processes` and macOS `procfetch` refuse network and device image paths on a bounded helper (a hash that timed out or was not started reads `hash_unavailable:timeout` or `skipped` there too; a refused image is an empty hash), Windows `procfetch` opens handle-relative with no helper and reads `hash_unavailable:not_examined`, `unreadable` or `not_regular` in its `sha1` column, and Linux/macOS `filesystem` have no network-mount check (Windows `filesystem` is lexical). `windows_updates.patch_connectivity` with caller `targets` needs `Infrastructure:Read` (default targets keep `SoftwareDeployment:Read`; enforced at send, when a schedule carrying `targets` fires and when its queued command is delivered, and refused for a background dispatch with no operator; the pre-dispatch dry run does not see parameters, so those routes need both grants for a call with `targets`; a parameter key with a control byte, NUL or invalid UTF-8, or a value with a NUL, is refused `400` `param_key_invalid`), and caps caller targets at 16 and refuses loopback, link-local/metadata, multicast and reserved resolved addresses (RFC 1918 allowed). **The agent command pool now reserves one worker for protective actions (the closed `firewall` containment set and `__guard__.push_rules`; ADR-2005), so ordinary commands stalled on a filesystem or resolver cannot occupy the last worker; that the protective action's own blocking calls are independent of the stall is asserted, not verified, the lane does not cover pool teardown (a dropped stream drains every queued task, stagger sleeps included, before the agent reconnects; #8247), and the heartbeat reports `yuzu.command_pool_busy` and `yuzu.command_pool_queued`.** `ioc.check`, Linux/macOS `processes` and `procfetch`, Windows/macOS `processes`, `disk_space` and the name lookup of `windows_updates.patch_connectivity` do their blocking work on a bounded helper thread, so a stalled mount holds a helper (up to 64 per plugin) instead of a command-pool worker; `filesystem` (Linux/macOS), the `http_client` name lookup and Windows `procfetch` are NOT helper-bounded and can pin an ordinary worker, a helper can itself stay blocked in the kernel (the unload drain barrier is tracked as #8204). `windows_updates.patch_connectivity` clamps its name lookup and its connect to what is left of one 60 s dispatch budget, so a dispatch ends by about 60 s, but it still holds a command worker for that long. A Windows junction or directory symlink to a share is a residual for `filesystem`, `disk_space` and the download destination (tracked as #8208). `procfetch` returns an empty hash, never the SHA-1 of a truncated read. `ioc.check` rows carry a string in the `matched` position: `true` or `false`, or a state word on a `coverage` row. The `disk_space.free` `path` and the pre-flight `volume` refuse a leading double separator server-side. Windows hunks were compiled with MSVC (cl.exe) on a Windows host and the path-policy exerciser was run; no Windows unit tests were run. The macOS code paths were syntax-checked only; they have not been built or run on macOS. `http_client.download` stores exactly the bytes received (a gzip body is stored compressed) and a destination name of about 235 characters or more fails.
