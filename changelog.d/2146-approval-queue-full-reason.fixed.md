- **A full approval queue is now reported as such instead of as a retryable store failure.** When the shared pending-approval queue (1000 rows across every principal) is full, `POST /api/v1/instructions/{id}/execute`, the MCP `execute_instruction_definition` tool and the MCP approval-ticket mint of every approval-gated tool used to answer `approval_submit_failed` with `retry_after_ms` 5000, although only a human reviewer deciding a pending approval, or the 7-day expiry, frees a slot, so a retry loop could never succeed. They now answer `503` (REST) or `-32603` (MCP) `approval_queue_full` with `retry_after_ms` null and a remediation naming the reviewer, and the new fourth value of `yuzu_server_approval_submit_refused_total{reason}` (pre-seeded to `0`) counts it, so a saturated queue is separable from a storage fault; `approval_submit_failed` now means only a genuine store fault. The MCP ticket mint now also counts its refusals on that metric (previously only its cap refusal was counted).
