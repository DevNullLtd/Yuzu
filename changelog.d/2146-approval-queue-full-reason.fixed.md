- **A full approval queue is now reported as such by the MCP approval-ticket mint instead of as a retryable store failure.** When the shared pending-approval queue (1000 rows across every principal) is full, the supervised-tier ticket mint of every approval-gated tool used to answer `-32603` "failed to create approval request" with `retry_after_ms` 5000, although only a human reviewer deciding a pending approval, or the 7-day expiry, frees a slot, so a retry loop could never succeed. It now answers `-32603` with `error.data.reason` `approval_queue_full`, `retry_after_ms` null and a remediation naming the reviewer, writes a `denied` audit row (`reason=approval_queue_full correlation_id=<id>`), and counts it on the new `yuzu_server_approval_submit_refused_total{reason}` family; `approval_submit_failed` now means only a genuine store fault and keeps `retry_after_ms` 5000. Every refusal of the mint now carries the same `reason` token and `correlation_id` in `error.data` and in its audit row, and `audit_persisted:false` when the row was lost.
