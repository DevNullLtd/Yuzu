- **A service-scoped API token now sees only executions that touched an agent in its service scope (#5557).** The token used to see every execution its minting account had dispatched, including executions on agents outside its service scope. On every execution read surface (REST v1, the legacy routes, the dashboard fragments, the event streams and the MCP tools) it now sees an execution once an agent in its service scope has a status row for it, and a service scope with no tagged agent lists nothing. An integration that dispatches with another credential and polls with the service-scoped token gets not found until the first in-scope agent replies, so poll no faster than about once every 5 seconds and stop after a timeout: each not-found answer writes a `denied` audit row. MCP `list_executions` for such a token now also lists other principals' executions that touched its agents. Every execution the token can see names its dispatching operator in `dispatched_by`, which can be an account other than the one that minted the token. Known limits, tracked as follow-ups: an open event stream keeps the scope it attached with (#7815), and the number of events withheld from a stream can be inferred from its event ids (#7816). See "a service-scoped credential's execution visibility is limited to its service scope" in `docs/user-manual/upgrading.md`.
