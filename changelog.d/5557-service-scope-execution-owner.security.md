- **A service-scoped credential's execution visibility is limited to its service scope (#5557).** A service-scoped API token used to be shown every execution its minting account had dispatched, including executions on agents outside the token's service scope (id, definition, status and timing; the counts were already projected), because the "the caller dispatched it" rule compared against the minting account. That rule no longer applies to a service-scoped token on any execution read surface (`GET /api/v1/executions` and its detail, children and events routes, the legacy `/api/executions*` routes, the executions fragments and `GET /sse/executions/{id}`, and the MCP `get_execution_status`, `get_execution_children` and `list_executions` tools). The token now sees an execution only once an agent in its service scope has a status row for it; before that the execution reads as not found, and a service scope with no tagged agent lists nothing. Behaviour changes: a token no longer lists its minting account's other executions, an integration that dispatches with another credential and polls with the service-scoped token gets not found until the first in-scope agent replies, and MCP `list_executions` for a service-scoped token now also lists other principals' executions that touched its agents. The real dispatch attribution and audit identity are unchanged, and no other caller class changes. Two list gates (`require_fleet_read` and `require_list_read`) also refuse to give a service-scoped session unrestricted authority: a service-scoped engine session, which minting already forbids and so only a corrupted credential row can be, is refused with `403` before any store read, and a defect that would have admitted one unrestricted is refused with a non-retryable `500`. Both refusals are audited and counted in the new `yuzu_server_authz_service_scope_unrestricted_refused_total{gate,site}` counter (present at 0 from boot; no alert rule ships for it). The user manual's upgrade note corrects the earlier advice that a service-scoped token could rely on a streamed dispatch and `execution_id` polling: it cannot dispatch through `execute_instruction`, and it reads an execution by id only once an in-scope agent has a status row.
