- **Breaking: this build is a HARD CUTOVER with no upgrade path, no rolling or mixed-version window and no rollback (#6079).** The `auth` v3 migration seeds nothing, so an enrolled account that reads factor generation `0` (only a database an earlier build wrote holds one) and is refused `503` (audit `reason=mfa_proof_unavailable`; sticky: `retry_after_ms` is `null`, meaning no retry hint; every refusal of the central step-up check now carries the `error.retry_after_ms` key, `5000` for a failed enrolment-status or stored-proof read and `null` otherwise, so a client that retries on `503` must stop on `null`) on the 41 step-up routes (the 39 ordinary rows, approve and reject among them, and the 2 factor-credential routes; Settings self-disable and recovery-code regeneration are two of them) and on the 3 JIT-elevation routes (they probe the same factor state), until `yuzu-server --mfa-reset <user>` clears its factor (under `--mfa-enforcement=required`, or `admin-only` for an administrator, the user enrols again at next sign-in). An administrator API token passes the 39 ordinary rows at the central check but is refused `403` on the 2 factor-credential routes and cannot approve or reject, and an administrator at generation `0` cannot mint one while the window is above 0. The 39 ordinary rows refuse only while `--mfa-step-up-window-secs` is above 0 (at 0 they pass without reading the store); approve and reject, the 2 factor-credential routes and the elevation routes refuse regardless. The build supports a fresh database only (docs/user-manual/upgrading.md, "Deployment contract"): there is no carry-over procedure for an earlier build's database, and a reset (`yuzu-server --mfa-reset <user>`, from a host shell with the Postgres DSN and the keys directory) is the repair for an account that reads generation `0`, not an upgrade step. A reset clears a non-administrator's factor too, and a non-administrator cannot enrol itself under `--mfa-enforcement=optional` or `admin-only`, so it stays refused on approvals and JIT elevation until an administrator enrols it (or a `required` window runs). Under `--auth-mode=sso-only`, resetting the `--break-glass-user` account makes the next `sso-only` start refuse to boot until it is enrolled again under a restart with `--auth-mode=standard`. **Action required:** a non-admin cannot enrol itself under `--mfa-enforcement=optional` or `admin-only`, and the seeded `Operator` role holds `Approval:Approve`, so, with RBAC enforcement on, every non-admin approver (and any un-enrolled administrator) is refused until an administrator enrols it (with enforcement off, the shipped default, a non-admin is refused `403` "admin role required" before the MFA gate), through an enrolment sign-in window or by promoting the account long enough to enrol and then demoting it; both are in `docs/ops-runbooks/auth-db-recovery.md`, "Enrolling a non-admin approver". Endpoint agents need no change.

- **The approver rule counts only a proof bound to the factor enrolled now (#6079).** The approver rule (the "approving or rejecting needs an enrolled MFA factor" entry of the 0.15.0 release has the matrix of refusals, the window and the audit detail) now requires a local proof's recorded factor generation to equal the account's current one, so disabling MFA and enrolling again replaces the factor and earlier proofs stop counting; the refusal is the usual step-up `401`. When the approver rule's own read fails the answer is `503` with `retry_after_ms`, except for three persistent causes that no retry clears (the auth-store binding trigger observed not in force, the session store's rebind guard latched not in force, and an enrolled account whose factor generation is not positive), which are a `503` with no retry hint until an operator repairs the triggers (and restarts the server) or the account's MFA state; every such `503` is counted as `yuzu_auth_secret_unavailable_total{route="approval"}` (the stored-proof case also increments `yuzu_auth_session_store_degrade_total{op="validate"}`). Tickets decided earlier gain no retroactive assurance, and the `attempted` and `success` audit rows written from this version carry `detail` `approver_assurance:enrolled_fresh_mfa` as the cutover marker. Two follow-ups are named and not part of this change: real OIDC re-authentication at approval time (`auth_time` with `max_age`), and self-service MFA enrolment for non-admin approvers.

- **MFA proofs are bound to the factor they were earned with (#6079).** A local proof now records the account's factor generation (a database-owned random value that changes on every enrolment or clear and is never reissued in practice, so a restored `auth` schema cannot make a later re-enrolment match an earlier proof; `auth` schema v3 and `session_store` schema v3 add it with two triggers) and the database instant at which the code was checked, and the central step-up check, JIT elevation and the approver rule all require the generation to equal the account's current one. `POST /api/settings/mfa/recovery-codes` and `POST /api/settings/mfa/disable` now accept only a local session (API-token, MCP-token, SSO and engine callers get `403`), keep a ceiling of 300 seconds even with `--mfa-step-up-window-secs=0`, and answer `409` with nothing written if the factor changed after the check admitted the request. New `reason=` tokens on `mfa.step_up.required` rows: `mfa_proof_missing`, `proof_factor_unbound`, `proof_factor_mismatch`, `mfa_proof_unavailable`, `mfa_binding_unenforced` and `factor_credential_requires_local_session`; a Settings factor race is recorded as `reason=factor_changed expected_gen=<n>`. A code that `POST /login/mfa/stepup` accepted but could not leave a bound proof for is an `mfa.step_up.failed` row whose `detail` is `verification_future_dated`, `factor_changed_during_step_up`, `step_up_proof_invalid` or `step_up_proof_store_error` (the same two conditions on a sign-in are `cause=verification_future_dated` and `cause=factor_changed` on a failed `auth.login`), and the answer is the uniform `401` except `step_up_proof_store_error`: a valid code the session store could not record is a `503` ("Your code was accepted but could not be recorded. Wait for the next code and try again.") with no `retry_after_ms`, because the code is spent and a retry with it is a `401` replay. The session store's rebind guard failing reaches a local session as `mfa_proof_unavailable` (SSO sessions are unaffected), not `mfa_binding_unenforced`, so a SIEM rule for this condition must key on both tokens. New metrics: `yuzu_auth_mfa_binding_enforcement_ok{store}`, `yuzu_auth_mfa_stamp_denied_total{reason}`, `yuzu_auth_mfa_verification_future_dated_total`, and `yuzu_auth_mfa_factor_changed_total{route}`, a new `route="mfa_binding"` value on `yuzu_auth_secret_unavailable_total`, and `yuzu_auth_role_recheck_post_mint_denied_total` now carries a `reason` label (a `sum()` over it is unchanged). Clearing the factor (Settings Disable or `yuzu-server --mfa-reset`) changes the generation through the same trigger, so every earlier proof stops counting. A server whose database lacks either trigger refuses to start (only the one-shots `--mfa-reset` and `--break-glass-arm` open their bootstrap `AuthDB` without that refusal and print a loud warning instead, so they stay usable for recovery; `--mfa-reset` also opens the session store it uses to end sessions past a missing rebind guard, with a warning; the serving process has no bypass), and `yuzu_auth_mfa_binding_enforcement_ok{store}` with the `YuzuMfaBindingNotEnforced` alert report a trigger found not in force while running (the alert ships in `docs/prometheus/yuzu-alerts.yml`; see `docs/ops-runbooks/auth-db-recovery.md`, "MFA binding enforcement failed"). See `docs/user-manual/upgrading.md` and `docs/user-manual/instructions.md` "Who can approve".
