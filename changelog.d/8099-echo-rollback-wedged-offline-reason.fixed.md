- **An Echo database closed at run time after a failed rollback is now reported as storage offline with reason `rollback_wedged`, and the Echo actions that answered as if nothing were wrong are refused.** Such an agent stops all Echo collection and retention until it restarts, and until now nothing outside `echo status` said so. The agent now publishes the `yuzu.plugin.echo.storage_offline` heartbeat tag with the value `rollback_wedged` at its next slow collect tick, `echo status` ends with `storage_state|offline|rollback_wedged` (it was a bare `storage_state|offline`, so automation that matches that exact line must accept the reason suffix), the `yuzu_fleet_echo_storage_offline{reason}` gauge gains a `rollback_wedged` series, and the existing `YuzuEchoStorageOffline` alert and runbook cover it; the `/echo` Capture-sources frame and the `/device` page already show the `echo status` error line. While the database is closed, `collect_fast`, `collect_slow`, `rollup`, `configure` and `fleet_snapshot` now fail with the same `error|Echo storage is offline` line as `echo status`: they used to answer an empty success, a fleet snapshot that read the process and tcp sources as paused by an operator, or (for a `usage_enabled=true` re-assert) `status|ok` with nothing written. `echo sql` keeps reading the historical data, and `echo query` and `echo export` keep failing with `error|database not open`. This reason is not retried: only an agent restart recovers it. The tag is published through the agent's plugin key-value store, which sits on the same volume as the Echo database, so on a full volume (the likeliest cause of the failed rollback) it may not publish and no alert fires; `echo status` and the agent log still report the state.
