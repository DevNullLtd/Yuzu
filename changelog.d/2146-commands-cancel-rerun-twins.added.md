- **`POST /api/v1/commands`, `POST /api/v1/executions/{id}/cancel` and `.../rerun`, and the MCP tools `cancel_execution` and `record_execution_rerun`.** `POST /api/v1/commands` is the REST v1 twin of `POST /api/command` and of the MCP `execute_instruction`: it applies the same targeting-shape check, Destructive and Forensics gates and management-group confinement, creates an execution row and returns its `execution_id`, writes a `requested` audit row before anything is sent and refuses with `503` (nothing dispatched) when that row cannot be stored, and answers a command that reaches no agent as a typed error (`invalid_scope`, `quarantined`, `plugin_not_found`, `kill_switched_os`, `containment_unreadable`, `route_unreadable`, `os_gate_unreadable`, `no_agents_reached`) with an honest `retry_after_ms`. A dispatch that throws part-way answers `500` `dispatch_exception` with no retry hint (agents may already hold the command) and leaves its execution row `running` rather than cancelled: when the server had confirmed sending to at least one agent it stores that count as the row's targeted count (the `failure` audit row carries `agents_sent=<n>`, a lower bound), so those agents' results complete the row, and otherwise the stuck-execution sweep closes the row if no agent ever answers; `cancel_execution` closes it at once. A store that throws while the execution row is created answers `503` `execution_record_unavailable` (retryable, nothing dispatched). The four cancel and rerun twins (REST and MCP) share one admit, audit, change, audit sequence (the legacy routes are untouched and keep their own handlers): cancel only marks the tracker record cancelled and rerun only creates a `pending` record linked through `rerun_of`; neither sends anything to a device (the rerun body says `dispatched_to_devices: false`). Each publishes the same platform event as its legacy route once, on success. When the `denied` or `failure` row of a refused cancel or rerun cannot be stored, the REST routes add `Sec-Audit-Failed: true` and the MCP tools add `error.data.audit_persisted: false` to the refusal, without changing its status, code or message. `cancel_execution` is the one tool on a closed approval-exempt list (`kApprovalExemptTools` in `mcp_policy.hpp`): a supervised-tier MCP token needs no approval ticket for it, because it only marks a tracker record cancelled, starts no work and stops nothing on a device, and it still writes an `attempted` audit row first. The exemption is MCP only: `POST /api/v1/executions/{id}/cancel` still refuses a supervised-tier token with `403`, and `record_execution_rerun` stays approval-gated at that tier. `POST /api/v1/commands` has its own `commands` body-cap class (4 MiB, body must be measurable in advance), so a chunked or length-less body is refused `411`, stricter than the legacy `POST /api/command`. The audit log gains the result values `requested` and `pending` on these verbs (other verbs already write them), `metrics.md` documents two new counters, `yuzu_server_approval_submit_refused_total` and `yuzu_server_event_emit_failed_total`, and a dispatch that throws is counted on `yuzu_server_dispatch_fanout_throw_total{route="command_v1",phase="dispatch"}`.
