- **Reinstalling or upgrading the Windows agent no longer locks the agent out of its update trust bundle.** Agent installers from 0.14.0-rc1 to rc5 gave every file already in `%ProgramData%\Yuzu\agent-certs`, such as an operator-provisioned `update-trust-bundle.pem`, an empty permission list, and still reported success. SYSTEM, and so the agent, could then no longer read the bundle, so every OTA update was refused (`yuzu_agent_ota_signature_refused_total` rises, and the agent logs `signature verification FAILED (untrusted chain)`). 0.13.0 is not affected. To repair an affected endpoint, run, elevated:

  `icacls "C:\ProgramData\Yuzu\agent-certs\*" /reset /L /C /Q`

  This resets the files inside the folder, never the folder itself, whose own permissions must stay as they are; run it only after checking the folder holds nothing but files. Then run the verification step in *OTA update binary signing* (`docs/user-manual/server-admin.md`), which also corrects the same mistake in that page's manual procedure. Installing this version repairs the folder too, but any installer run rewrites the service's binary path, so read the security note about update-signing flags first. The installer's check now compares the permissions exactly, so a file nobody can read, a deny entry or an inherit-only entry stops the install instead of passing. The installer also no longer takes over a folder it did not secure. If `agent-certs` already exists, it must already be secured (as earlier installers left it), otherwise the install stops: a folder a local user created first could hold their own trust bundle. Nothing it runs on the folder is recursive any more: the folder may hold only files, and the install stops, naming the item, if the folder or anything in it is a junction, symbolic link or subdirectory. Setup also no longer fails when the installing account's profile path contains a typographic apostrophe. Found on Windows Server 2022. (#5196)
