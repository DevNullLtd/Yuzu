- **Breaking: `yuzu_echo_source_purge_total` and `yuzu_echo_source_reenable_total` carry a `surface` label and one shared `result` set, and dashboard audit rows end in a correlation id.** Both counters now have the labels `result` and `surface` (`dashboard` or `rest`; the purge on both, the re-enable on `dashboard` only). The label is `dashboard` where #2536 proposed `fragment`, because that is what the page is called everywhere else. The dashboard fragments and the REST purge write the same closed `result` set: `success`, `agent_not_connected`, `invalid_input`, `denied`, `scope_violation`, `rate_limited` (dashboard only), `infra_unavailable` (the scoped gate or the dispatch function is unwired, or the gate answered `503` itself, counted `denied` before), `audit_unavailable`, `store_unavailable` (a failed authorization read; both surfaces) and the six dispatch-chokepoint refusal reasons. Every series exists from boot at 0, and the unlabelled `{result}` series no longer move: dashboards and alerts that select `result` alone must name or sum over `surface`. The REST purge's status, body and audit rows are unchanged except one detail: when the recheck after its `requested` row is refused because an authorization read failed, the `failure` row reads `store_unavailable store=<mgmt_group_store|rbac_store> device=<id> source=<src> cid=<id>` instead of `permission_revoked ...`. Every `detail` the dashboard writes from the `attempted` row on (`echo.source.reenable`, `echo.source.purge`, `group.create_from_results`, and the console's `command.dispatch`) now ends in the same request-scoped ` cid=<id>` (` correlation_id=<id>` on `command.dispatch`), so an outcome pairs with its attempt; a SIEM rule matching one of those details exactly must match its prefix.
