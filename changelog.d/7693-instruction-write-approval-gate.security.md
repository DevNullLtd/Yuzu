- **Breaking: a supervised-tier MCP token now needs an approval ticket for `InstructionDefinition:Write` and `ProductPack:Write`, so it gets 403 on the REST routes that gate on them (#2146).** An unticketed write could set a definition's `approval_mode` from `always` to `auto`, or repoint its `plugin` and `action`, after which an existing schedule or an operator-tier run needed no human; a product pack install could create such a definition too. The gate is keyed on the permission pair, so it also applies to the legacy `POST /api/instructions`, `PUT /api/instructions/{id}`, `POST /api/instructions/import` and `POST /api/instructions/yaml` routes, to `POST`, `PUT` and `DELETE /api/v1/definitions/{id}/response-templates`, and to `POST /api/product-packs` (audit action `auth.approval_required`, result `denied`). The ticket flow exists only on `/mcp/v1/`, and only the definition authoring tools take a ticket: the response-templates writes and the pack install have no MCP tool, so a `supervised` token cannot do them at all and must use a credential without an MCP tier or a browser session. Callers with no MCP tier are unaffected. `InstructionSet:Write` is not gated, `InstructionDefinition:Read` is unchanged, and `Delete` was already ticketed at that tier. What to look for, what to do and the rollback note are in `docs/user-manual/upgrading.md` ("a supervised-tier MCP token needs an approval ticket for InstructionDefinition:Write and ProductPack:Write").
