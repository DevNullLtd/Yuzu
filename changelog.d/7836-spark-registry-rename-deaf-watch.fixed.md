- **A Registry spark watch now notices a renamed parent key instead of staying silently deaf (Windows, #5719 item 5, #7836).** The watch held a notify handle that followed the renamed key, so it kept reporting Healthy and never saw a change at the watched path. An idle, healthy watch is now verified every 5 s on the mechanism's existing probe lane (no new long-lived thread; one short-lived worker per watched key per check): the registered path is re-opened, and a path that no longer names a key reports the watch faulted (`registry watch key renamed or replaced`), owes a resync fire, and re-opens the path on the ordinary retry (30 s, doubling on repeated failure to a 300 s cap). Detection is sampled, about 5 s in production by design (plus the sweep wake, the probe latency and, when the shared 16-slot probe lane refuses a check, the admission backoff of up to 30 s) and not measured. A verification that cannot decide is counted and does not fault the watch. Not covered (accepted residuals, tracked in #7877): a parent renamed away and a key re-created at the original path before the next sample, a rename away and back inside one interval, a verification that could not decide (it keeps the old handle, so a rename it saw is missed until the next one that decides), a renamed shelter ancestor of an Ancestor-mode watch (never verified, including one re-established after a verdict), a persistently access-denied verification open (the watch stays unverified), the HKCR merged view, and a registry open that hangs while holding one of the 16 shared probe-lane slots. The re-open can raise object-access audit events on a key that carries an auditing SACL and adds one short-lived worker per watched key per check (unmeasured; the runtime off switch tracked in #7876 will cover it for the File and Registry mechanisms, until then `--spark-disable`, a boot-time flag that restarts the agent). No Registry spark is armed in production today (`prefer_spark_` is false), so this is visible only on rig-flipped agents.
