- **A Registry spark watch now notices a renamed parent key instead of staying silently deaf (Windows, #5719 item 5, #7836).** The watch held a notify handle that followed the renamed key, so it kept reporting Healthy and never saw a change at the watched path. An idle, healthy watch is now verified every 5 s on the mechanism's existing probe lane (no new thread): the registered path is re-opened, and a path that no longer names a key reports the watch faulted (`registry watch key renamed or replaced`), owes a resync fire, and re-opens the path on the ordinary retry (30 s, doubling on repeated failure to a 300 s cap). Detection is sampled, about 5 s in production by design and not measured. A verification that cannot decide is counted and does not fault the watch. Not covered: a parent renamed away and a key re-created at the original path before the next sample, a rename away and back inside one interval, a renamed shelter ancestor of an Ancestor-mode watch, and a persistently access-denied verification open (the watch stays unverified). The re-open can raise object-access audit events on a key that carries an auditing SACL and adds one short-lived worker per watched key per check (unmeasured; the runtime off switch tracked in #7876 will cover it, until then `--spark-disable`). No Registry spark is armed in production today (`prefer_spark_` is false), so this is visible only on rig-flipped agents.
