- **The execution visualization route, the dashboard results fragment's unfiltered read and the TAR retention-paused scan page read their responses through the byte-aware fetch, and report a cut (#4644).**
  Each read up to 10,000 rows through the unbounded `ResponseStore::query()` (every output is cut to 2 MiB of raw bytes at ingest, apart from a terminal frame's `error_detail`), which materialised the whole result while holding a lease on the shared Postgres pool. They now use the same SQL-side 50 MiB payload cap as the export routes (`query_bounded`; the visualization route pushes its management-group scope into the query, but the dashboard results fragment and the scan page apply scope after the fetch, as before, so their cut is made on the fleet-wide set and can be reported even when every dropped row was outside the caller's scope), and a cut is never silent because a chart or a table built from a cut read is a wrong picture, not a smaller one. The dashboard chart adapter (`/static/yuzu-charts.js`) now shows a "Partial result" notice in the chart's card, naming the row cap or the 50 MiB cap, on every page that shows the chart deck. `GET /api/v1/executions/{id}/visualization` adds `result_truncated_by_cap: true` and `truncation_cause` (`row_cap` or `byte_cap`) to its payload, and its existing `rows_capped` is now exact (it also fired on a read of exactly 10,000 rows); the dashboard results fragment shows a "truncated" notice in its result summary; the retention-paused scan page shows a "Partial result" banner and its REST/MCP JSON gains a `result_truncated_by_cap` boolean (always present, `false` when uncut) beside `store_degraded`, which is also `true` on a cut scan so a client that predates the new field still sees an incomplete result (test `result_truncated_by_cap` first to tell a cut from a failed read). The dashboard results fragment's filtered branch (it reads by response id), the plain list routes and the internal reads (the fleet visualization collect poll, the deployment and pre-flight polls, a bundle execution's result read) are not changed here.
