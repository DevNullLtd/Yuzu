- **Breaking — a management-group-confined operator holding a scoped Inventory grant is now refused the issued-certificate list.** `GET /api/v1/ca/issued` without a filter, the MCP tool `list_issued_certs` without filter arguments, and the issued-certificate list in the Settings certificate panel returned every certificate's subject, SAN and issuing identity to any caller holding `Security:Read`, including such a confined one (the seeded Viewer role holds `Security:Read`). They now apply the check the filtered form already used: that caller gets `403` (MCP: permission denied) with no permission named, and the panel withholds only the list (a note in its place; the CA details, the root and CRL downloads and the import form are still shown, and a revoke or import no longer leaves a blank panel). An access check that reports itself unavailable is `503` with `retry_after_ms: 5000`. **What did not change:** RBAC-off installs (the default) are unchanged; a `Security:Read` holder with no `Inventory:Read` grant at all is not confined and is served the list (removing a scoped grant does not confine a caller, and granting a global `Inventory:Read` removes the confinement); and a read failure partway through the access check **fails open**, serving the list, on the unfiltered list, the filtered list and the `/crypto` drill (tracked by an issue (issue number to be added when filed)). Both forms are now audited `crypto.ca.certificates.view` (target `inventory`): a `success` row per page ending `standing=available|refused`, a `denied` row for a refusal and a `failure` row when the access check or the store is unavailable. The Settings panel itself is still not audited.
