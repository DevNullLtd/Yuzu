- **Breaking: an access-review attestation must name the scope of the grant (#6969).** `POST /api/v1/access-reviews/{id}/attestations` and the MCP `record_attestation` tool now require `scope`, either `fleet` or `management_group`. For `fleet`, `scope_group_id` is absent or empty; for `management_group` it is required, a nonempty string of at most 256 bytes without a NUL byte (the management-group id limit). A request that omits `scope`, or sends a `scope_group_id` that contradicts it, is refused with `400` (REST) or invalid params (MCP), writes no audit row and records nothing; the message ends `reload the page so it sends the scope (a page opened before this field existed sends none); API callers must send scope`. Update every client, and every attest request you queued or saved, to send `scope` (and `scope_group_id` for a management group), copied from the attestation row; reload any Settings or Access page opened before the server restart, whose Attest and Flag buttons answer `400` until then. Each attestation row in `GET /api/v1/access-reviews/{id}` and `get_access_review` now carries `scope`, `scope_group_id` and `scope_group_name` (every row is fleet-wide in this build), both campaign tables show a Scope column, and the `access_review.attested` / `access_review.flagged` audit detail gains ` scope=fleet` or ` scope=management_group scope_group_id=<id>` after `role=<role>`; audit rows exported from an earlier build have no `scope=` token. The access-review store moves to schema v4, which adds `scope_group_id` to both attestation tables and their primary keys and drops the column default, so an older build's INSERT that names only the four earlier key columns fails on a v4 database; do not run an older build against it, the runner only warns. The migration is one transaction under `ACCESS EXCLUSIVE` locks on both tables: start one replica first and wait for `PgMigrationRunner: access_review_store migrated to v4`, because a second replica that starts meanwhile can fail waiting for the runner's lock and refuse to start. This build supports a fresh database only: it describes no upgrade, mixed-build operation or rollback. See `docs/user-manual/upgrading.md`.
