- **A locked `kv_store.db` no longer pushes the agent's stage-by-stage shutdown past its 20-second deadline in the cases measured (6.03 seconds largest; see the limits below, including that each already-queued writer adds about 1 second) (#5604).** Each shutdown write used to wait the full 5 seconds for the lock and the shutdown makes several in a row, so the agent's own shutdown watchdog could end it (exit code 4, no log line) and a Guardian baseline capture that was still waiting to be written was lost. During shutdown the wait is now 1 second, and lowering it also cuts a write that is already waiting. Measured with the store locked throughout (Linux, one run per point except the journal rows, which were run two and sixteen times): shutdowns that took 21 to 29 seconds on earlier revisions of this code (those revisions were not re-run on the final code) took 2.0 to 6.03 seconds on the final code, on a row of real writes and on a row that emulates one of the writes; the real-write journal row varied between 4.0 and 6.0 seconds from run to run. A stalled disk write is not a lock wait and can still reach the watchdog, and SQLite's own internal retries are not covered by the 1-second wait (measured up to about 2.3 seconds against a 1-second budget on Linux, phasing dependent). Every other writer already queued on the store when the shutdown begins adds about 1 second (9.0 seconds with three extra writers, measured on Linux, one run). The Spark baseline and lifecycle-journal benefits apply only once Spark detection is enabled (it is off in every released agent today); the shorter shutdown wait itself is in effect now.
