- **Decommissioning a device now also erases its presence row.** `DELETE /api/v1/sle/agents/{id}` fans out to a seventh store, `offline_endpoint`, and deletes the device's `endpoint_state` row: its last-known hostname, OS, agent version, architecture and heartbeat times. Until now the row was removed only on a graceful disconnect, which a decommissioned agent never sends, so it stayed in the database indefinitely. The response's `stores` map gains an `offline_endpoint` entry and `deleted` now counts up to 7 where it counted 6; if that delete cannot complete (for example the database is unavailable) the entry is `failed` and the request returns `500`; re-issue the DELETE. Erasure is point-in-time and does not unenroll the agent: a still-enrolled agent re-creates the row on its next heartbeat, so stop the agent first (revoke its certificate, and for a gateway-connected agent also disconnect it there, #5578) and then issue the DELETE. Other replicas may serve the old row for up to the 3 s presence cache, and `/viz/fleet` for up to 60 s. During a rolling upgrade, a DELETE served by a not-yet-upgraded replica returns `200` without erasing the row; a response with no `offline_endpoint` key did not erase it, so re-issue the DELETE once every replica is upgraded. (#5682)
