- **A second Guardian agent log line per full push, `Guardian: full_sync rebuilt N rule(s) ...`, is added but inactive in production (#5719).** Every production agent (`prefer_spark` off) logs `Guardian: full_sync rebuilt 0 rule(s) (rebuild attempted): path=legacy first_attach=0 ...`, and `rebuilt 0` there does not mean nothing was rebuilt: on `path=legacy` every carried rule is still stopped and re-armed on each full push. The line counts the rules the Spark path rebuilt instead of skipping, under eleven reasons (`first_attach`, `content_changed`, `key_busy`, `faulted_key`, `dead_key`, `health_unknown`, `subscription_replaced`, `unknown_episode`, `baseline_empty`, `baseline_differs`, `other`). Each rule gets one reason; for a committed rule a health reason outranks a changed-content one, but a changed rule that still has its own arm in flight reports `content_changed`. `first_attach` and `content_changed` are counts only; every other group is followed by `ids=[...]` only when its count is above zero, all groups share one cap of 64 ids / 2048 bytes, and `more=M` counts the ids left off. The count includes rebuilds that may still fail afterwards. Three in-process counters on the Spark runtime (`health_probe_failures`, `sweep_snapshot_failures`, `sweep_health_query_failures`) count key-health failures that were previously swallowed; they are read by tests only, not exported on the heartbeat or `/metrics`, and read zero in production. The line is covered by unit tests on fake mechanisms and has not been observed on a flipped fleet. The user manual's "Reading the rebuild line (#5719)" table explains each token, and the upgrading guide's Guardian full_sync log-lines entry and the Spark flip gate's precondition (b) describe it.
