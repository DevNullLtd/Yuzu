- **Breaking: workflow execution is capped per principal, and the legacy `POST /api/workflows/{id}/execute` ends differently.** Details and the rollback note are in `docs/user-manual/upgrading.md` ("workflow execution is capped per principal and idempotent on a client key"). The legacy route (the one behind the dashboard's Run now button) keeps its request and its `202`, but: it shares the new admission step, so a principal with 2 workflow runs already in progress gets `429` with `Retry-After: 5`, and every caller gets `503` with `Retry-After: 5` while the server shuts down (a legacy caller that ran more than 2 at once was unbounded before); a run is bounded to 60 seconds from the moment the request is taken, after which no dispatch attempt starts, the remaining steps are skipped and the execution is closed `failed`, while the answer is still `202` with `status: running` and `GET /api/workflow-executions/{id}` shows the real state; a step whose dispatch throws now closes the execution `failed` (its remaining steps `skipped`) and the request answers the server's generic `500` with an empty body, where it used to leave the execution `running`; and a step refused at send time by the targeting gate is recorded failed at once and no longer retried. The `workflow_engine` schema moves to v3 (`workflow_executions` gains `principal`, `idempotency_key`, `request_fingerprint` and `correlation_id`, a CHECK, and the partial unique index `idx_wf_exec_idem`); there is no supported rollback to a build without it, only a restore of this build's own backup into a fresh deployment. MCP clients that call `execute_workflow` must now send a unique `idempotency_key` per intended run.
