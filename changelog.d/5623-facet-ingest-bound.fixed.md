- **One over-long value in a command's output no longer makes the response lose all of its facets.** A facet value over 2048 bytes is now left out of that response's facets (excluded, never truncated), and the response row, its output and every other facet still persist; before, the single value made the whole facet insert fail and the facet filter, dropdowns and group-from-results could not find that response at all. When a response has more than 5,000 distinct facets, the 5,000 kept are now chosen in a fixed order (most lines first, then column, then value) instead of whichever the server held first, so the choice is repeatable. A new counter, `yuzu_server_response_facets_dropped_total{reason}` (`value_too_long`, `cap`, `batch_failed`), counts the facets that did not persist; no alert rule ships for it. A value over 2048 bytes in a newly ingested response is no longer indexed (this includes values from 2049 bytes to about 2.6 KB that older servers indexed), so a facet filter or group count for it shows nothing or "0 agents"; the results page now shows a static hint when an active filter value is longer than 2048 bytes, so that empty result is not mistaken for "no agent has this value" (rows stored by an older server stay readable until retention removes them); the REST and MCP agent-count previews, the create-group form and a direct group-from-results submit still answer 0 or 422 with no such hint. Server-only, no schema, configuration, agent or gateway step (#5623).
