- **Breaking — agent-bundle build now verifies the release's cosign signature.** `scripts/build-agent-bundle.sh` (and the `docker-publish-agent-bundle` job) previously described `SHA256SUMS` as signed but never checked the signature, and accepted a file whose hash appeared on any manifest line. It now runs `cosign verify-blob` against the exact, tag-bound `release.yml` identity before reading the manifest, requires each download to match its own manifest line, and refuses to build otherwise. For operators who run it by hand: `cosign` v2.6.2 or later is now required (no skip flag; verified with v2.6.2, v3.0.5 and v3.1.3); `--version` is validated strictly; new flags `--signer-repo owner/repo` (prints a `[!!]` warning when it differs from the era table) and `--verify-only`; releases with only the legacy `SHA256SUMS.bundle` (v0.7.x) or with no signature file (v0.8.0-rc0 to v0.10.0) are refused. Each run now stages in its own temporary directory under `deploy/docker/`. The image ships `UPSTREAM-SHA256SUMS.sigstore` so the manifest can be re-verified later. Each installer is now chosen by the requested version (a pre-release such as v0.13.0-rc6 also carries earlier rc installers, which were silently bundled before); none or several matching is an error. `release.yml` also verifies its own `SHA256SUMS` signature before the GitHub Release is created. The published `cosign verify` commands in the docs, the release skills and the release notes of future releases now use an exact tag-bound identity instead of a wildcard; the release notes already published for v0.11.0 to v0.15.0 still show the old wildcard command, so use `docs/user-manual/release-verification.md` instead. The bundle READMEs, the docs and the reference compose file no longer claim the Windows or macOS agent is Authenticode-signed, signed or notarized: neither is code-signed today (#239), and the bundle README now says that the image signature, not its sha256 files, is what authenticates the extracted payload.
