- **Breaking:** stored responses of Forensics-tier plugins (`app_usage`, `browser_inventory`, `execution_artifacts`, `privacy_permissions`, `remote_access_audit`) are now served only to callers holding `Forensics:Read` in addition to `Response:Read` (#4990). The tier applies on the stored-response read paths of REST, MCP and the dashboard (including the executions drawer and the hardware result poll) and in the server's own consumers of those rows: bundle collation, result-set membership, policy checks (such a check scores `unknown`), the live output stream, and the failure text kept in execution records, which is reduced to a short machine token or `forensics_error`. Other readers see the rows as absent, with counts, caps and filter options computed over the rows they may read, so an empty result no longer implies that no data exists; a read whose authority cannot be determined is refused with a retryable error instead of a partial result (`yuzu_server_forensics_tier_withheld_total`, alert `YuzuForensicsTierUnresolved`). Callers that held only `Response:Read` (the Viewer, Operator, PlatformEngineer and ITServiceOwner roles, and every non-administrator session while RBAC is off) no longer receive them; assign the new `ForensicsAnalyst` role to those who need them. A read that serves such rows also writes a `response.forensics.read` audit row. Upgrade every server replica; see "Behaviour change: stored responses of Forensics-tier plugins need `Forensics:Read`" in the upgrade guide for who is affected, the rolling-upgrade and rollback notes, and the known limits.
