- **Breaking — `firewall.quarantine` is refused on a device whose control endpoint is one of its own addresses.** `firewall.quarantine` now answers `refused|self_host` when the agent's server or gateway address is loopback, unspecified or any address the host answers to, and `refused|own_addresses_unreadable` when the host's own addresses cannot be read (permanent where the agent cannot open `AF_NETLINK`: allow it for the agent), because containing it would cut the agent off from the server that has to release it. Every apply that is not `repair=1` is checked, whoever sent it (an operator's dispatch, the server's reconciler, an MCP re-apply), an apply to an already-contained device included; not checked are the 60-second repair, the boot re-apply, `release` and `quarantine_allow`, so a stored containment is still re-applied and is released wherever the agent can elevate (on the packaged Linux unit only a forced end ends the record). A refusal changes nothing: no leg is built, no record is stored, and an existing record and its containment are left as they were; the refusal is in the agent log and the command's stored reply, and there is no override. So the token alone does not say whether the device is contained: a device that held no containment stays uncontained and its record never confirms until an operator ends it with `DELETE /api/v1/quarantine/{agent_id}` (with `?force=true` on the packaged Linux unit); one that was already contained stays contained (the repair and the boot re-apply keep the stored containment, and the server's re-apply is refused there); `firewall.quarantine_status` says which. On a device whose record is active, a refusal carries `note|allow_set_unchanged_use_quarantine_allow=1` when the request's exceptions differ as a set from those in force (the same rule and text as a retry that is not refused), so a never-confirmed server record stays unconfirmed; with equal exceptions there is no note. A single-host stack (agent and server on one machine) cannot apply a containment; a server in a container or VM on the same host, reached at a bridge address, is not seen as the host's own.
- **A macOS agent that runs unprivileged now says why a pf read is unknown.** `state` and `rules` add `error|appfirewall:...` and `error|pf:...` rows (`not_run`, `timeout`, `truncated` or `exit:<n>`) beside their `unknown` rows, so `pf|unknown` and `ruleset|unknown` come with the row for the read that did not complete (a read that completed but whose text is not recognised is `unknown` alone), and a global-state read that did not complete is `state|unknown` whatever its partial text said. Every such host sees up to three extra rows on `state` and two on `rules`.
- **The firewall containment ceremony has a remote mode.** `scripts/test/instructions_firewall_containment.py --remote` runs the round trip with the script on the server's host and the agent on another machine, bound by `--agent-hostname` (typed by the operator, and not one of this machine's names) and `--i-have-console-access-to-the-agent`; `instructions-tests.sh --target-agent-hostname <name> --console-access-to-agent` runs it (#8366). A one-host run ends `refused|self_host` (exit 2) by design; only that refusal exits 2, and `own_addresses_unreadable` exits 1 with the generic `NOT released` message. The run lock now tells a lock file it could not open, a lock call that failed and a lock another run holds apart (#8046); a refused dispatch ends `dispatch refused` (exit 1) instead of `RELEASE NOT CONFIRMED` (a release refused after an apply went out can still exit 3); a status read that sits RUNNING and unchanged ends early; `--record <path>` writes a 0600 JSON pass or fail record on every exit path of a run to a file it creates, and refuses a path that already exists rather than overwrite it (#7860); and a plain http dashboard at a non-loopback address is warned about, because the login crosses the network unencrypted. `install-agent-user.sh --dry-run` reports the helper directory verdict and exits as the real run would.
