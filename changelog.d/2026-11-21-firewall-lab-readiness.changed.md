- **Breaking — a device is never contained when its own control endpoint is one of its own addresses.** `firewall.quarantine` now answers `refused|self_host` when the agent's server or gateway address is loopback, unspecified or any address the host answers to, and `refused|own_addresses_unreadable` when the host's own addresses cannot be read (permanent where the agent cannot open `AF_NETLINK`: allow it for the agent), because containing it would cut the agent off from the server that has to release it. Every apply is checked, whoever sent it (an operator's dispatch, the server's reconciler, an MCP re-apply); not checked are an apply when the record the plugin keeps on the device is already active, the repair, the boot re-apply, `release` and `quarantine_allow`, so a stored containment is still re-applied and is released wherever the agent can elevate (on the packaged Linux unit only a forced end ends the record). A refused apply changes nothing on the device and stores no record there; the refusal is in the agent log and the command's stored reply, and there is no override. The record of a refused device stays unconfirmed until an operator ends it with `DELETE /api/v1/quarantine/{agent_id}` (with `?force=true` on the packaged Linux unit). A single-host stack (agent and server on one machine) cannot apply a containment; a server in a container or VM on the same host, reached at a bridge address, is not seen as the host's own.
- **A macOS agent that runs unprivileged now says why a pf read is unknown.** `state` and `rules` add `error|appfirewall:...` and `error|pf:...` rows (`not_run`, `timeout`, `truncated` or `exit:<n>`) beside their `unknown` rows, so `pf|unknown` and `ruleset|unknown` come with the row for the read that did not complete (a read that completed but whose text is not recognised is `unknown` alone), and a global-state read that did not complete is `state|unknown` whatever its partial text said. Every such host sees up to three extra rows on `state` and two on `rules`.
- **The firewall containment ceremony has a remote mode.** `scripts/test/instructions_firewall_containment.py --remote` runs the round trip with the script on the server's host and the agent on another machine, bound by `--agent-hostname` (typed by the operator, and not one of this machine's names) and `--i-have-console-access-to-the-agent`; `instructions-tests.sh --target-agent-hostname <name> --console-access-to-agent` runs it (#8366). A one-host run ends `refused|self_host` (exit 2) by design; only that refusal exits 2, and `own_addresses_unreadable` exits 1 with the generic `NOT released` message. The run lock now tells a lock file it could not open, a lock call that failed and a lock another run holds apart (#8046); a refused dispatch ends `dispatch refused` (exit 1) instead of `RELEASE NOT CONFIRMED` (a release refused after an apply went out can still exit 3); a status read that sits RUNNING and unchanged ends early; `--record <path>` writes a 0600 JSON pass or fail record on every exit path of a run to a file it creates, and refuses a path that already exists rather than overwrite it (#7860); and a plain http dashboard at a non-loopback address is warned about, because the login crosses the network unencrypted. `install-agent-user.sh --dry-run` reports the helper directory verdict and exits as the real run would.
