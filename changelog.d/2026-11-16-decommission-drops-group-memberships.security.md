- **Decommissioning a device now removes it from every management group.** `DELETE /api/v1/sle/agents/{id}` gains a tenth cascade store, `management_group_memberships` (the response's `stores` map gains that key and `deleted` reaches 10 when every store is configured). Before, the agent id stayed a member of every group it had been in; because decommission does not unenrol the device, the same id was accepted again on its next registration and was back inside those groups' scope (visible to the group's operators, targeted by `group:` dispatch). Now the id leaves every group, static and dynamic and root alike. Decommission still does not unenrol: the same id can reconnect, and its next registration attempts to add it back to the All Devices group only, not the other groups it was in; un-enrolling is a separate planned change. The removal is a point in time (an operator add, or a dynamic or `Service:` group created later from the tags decommission leaves in place, can put the id back in a group). A decommissioned device that is still connected belongs to no group until it registers again: group-targeted compliance policies, group-scoped Guardian, dispatch and collection-settings reach stop covering it until it is added back to its groups, and with RBAC enforcement off the dispatch, execute-console and Echo paths that read group visibility directly answer "no visible target" for it. The groups the device left are recorded, best effort, in the `sle.agent.decommission` outcome audit row (`management_group_memberships.groups=<n>:<ids>`). `Decommission:Delete` is the authority for this removal, including from groups the caller could not otherwise write (a service-scoped token admitted for a device in its service is an example); the gate is unchanged. No schema change. See the Upgrading guide.
