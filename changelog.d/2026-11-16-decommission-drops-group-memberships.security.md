- **Decommissioning a device now removes it from every management group.** `DELETE /api/v1/sle/agents/{id}` gains a tenth cascade store, `management_group_memberships` (the response's `stores` map gains that key and `deleted` reaches 10 when every store is configured). Before, the agent id stayed a member of every group it had been in; because decommission does not unenrol the device, the same id was accepted again on its next registration and was back inside those groups' scope (visible to the group's operators, targeted by `group:` dispatch). Now the id leaves every group, static and dynamic and root alike. Decommission still does not unenrol: the same id can reconnect, and its next registration attempts to add it back to the All Devices group only, not the other groups it was in; un-enrolling is a separate tracked change. The removal is a point in time (an operator add, or a dynamic or `Service:` group created later from the tags decommission leaves in place, can put the id back in a group). With RBAC enforcement off, a decommissioned device that is still connected belongs to no group, so the dispatch, execute-console and Echo paths that read group visibility directly answer "no visible target" for it until it registers again (the main device lists are unaffected); the same goes for group-targeted compliance policies and group-scoped Guardian and dispatch reach, which stop covering a returning device until it is added back to its groups. `Decommission:Delete` is the authority for this removal, including from groups the caller could not otherwise write (a service-scoped token admitted for a device in its service is an example); the gate is unchanged. No schema change. See the Upgrading guide.
