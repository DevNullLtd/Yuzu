- **The gateway-upstream service now requires an authorized gateway peer, and the server refuses to start without one.** The service (`--gateway-upstream`) authenticated callers only by membership of the install CA, or by the network boundary on a plaintext listener, and because it is registered on the one gRPC server that also listens for agents it was reachable on the agent and management ports too: on a default-certificate install a caller with no client certificate could reach it on the agent port, and any holder of a CA-issued client certificate (an agent leaf included) could reach it elsewhere. Every call is now refused with `UNAUTHENTICATED` unless the caller's TLS-authenticated leaf certificate lists `serverAuth`, has a public key whose SHA-256 (over the SubjectPublicKeyInfo) is pinned, and is inside its validity window; the check applies on every port the service is served on. Pins are fixed at boot (`--gateway-peer-pin`, `--gateway-peer-pin-file`, env `YUZU_GATEWAY_PEER_PINS` / `YUZU_GATEWAY_PEER_PIN_FILE`); on the generated default certificates the server pins its own `default-gateway.pem` automatically. **Breaking:** with your own certificates the server exits at boot until you supply a pin (this includes a Linux package install with its own certificates, because the shipped systemd unit passes `--gateway-upstream` unconditionally even if you run no gateway: the RPM restarts the service on upgrade, so it fails at once, and the deb only enables it, so it fails at the next restart; pin, or drop `--gateway-upstream` in a drop-in, before upgrading; the RPM `%pre` and the deb `preinst` print an advisory warning during the upgrade when `/etc/yuzu/yuzu-server.env` or a unit override shows that configuration, and never fail or change the upgrade); a plaintext (`--no-tls`) rig must pass `--insecure-gateway-peer` (env `YUZU_INSECURE_GATEWAY_PEER=1`), which disables the check on every port, is refused together with a pin, and is reported by a boot error line, a `server.gateway_peer_authz_disabled` audit row and `yuzu_server_gateway_peer_authz_mode`. Changing or withdrawing a pin is a server restart (a rolling restart with the old and new pins together for HA); there is no pin reload and no revocation check on this path. After a refusal window the runbook depends on where the cause was: for a server-side cause (a pin or an acknowledgement) restart the serving replicas and do not restart the gateways first (only on a gateway that has the #1197 consumer, #5383, does it then recover through its replay path), and verify three separate things (registration counts with `sum(yuzu_gw_agents_current) - sum(yuzu_agents_connected{job="yuzu-server"})`, placement through the raw notify error and drop counters, and a read-only command to a sample agent that returns a result), because agreeing counts alone do not prove placement; for a gateway-side cause (a certificate that expired or was renewed, a rotated key) the gateway presents its current files only when it redialled, which a server restart forces, so first check whether it already has and restart that gateway node, one at a time, only if denials continue and its agents can take the disconnect (agents without the #5183 fix, in no release yet, stay wedged after one); a same-key renewal needs no server restart, and a redial can present the previous certificate for about 2 minutes after the files change. For placement loss, restart the agent service on the unreachable agents first. The validity check runs on every call, so a gateway certificate that expires on an open connection is refused until the gateway redials: renew before `notAfter`, inside a maintenance window, and check whether the gateway has already redialled. Refusals are counted in `yuzu_server_gateway_peer_denied_total{rpc,reason}`, authenticated peers also write a bounded `session.gateway_peer_denied` audit row, and five alert rules ship (three on the server's metrics, including a critical one for the gateway's own heartbeat being refused, and two on the gateway's metrics, for upstream status 16 and for upstream TLS handshake failures). The Docker reference gateway compose now mounts only the public CA certificate into the agent container (a one-shot `ca-export` service fills a `ca-public` volume) so an agent cannot read the gateway key the pin authorizes; recreate the whole stack to pick it up. Remove the new flags before rolling a binary back (an older binary rejects an unknown flag but ignores an unknown environment variable). The Windows installer takes `/GATEWAY_PEER_PIN_FILE=<cert.pem>` or `/GATEWAY_PEER_PIN=<64 hex>` (mutually exclusive, stored as `certs\gateway-peer-pin`; the wizard has no pin page), `/GATEWAY /NOTLS` now passes `--insecure-gateway-peer` and is refused together with a pin parameter, and a silent `/NOTLS` clears any gRPC certificate parameters. See "Gateway upstream peer authorization" in `docs/user-manual/server-admin.md` and the breaking-change section of `docs/user-manual/upgrading.md`.
