- **The MCP approval-ticket mint's per-principal pending-approval cap now refuses when the approval store cannot be read, instead of admitting the caller, and no longer counts expired tickets.** The ticket mint of every approval-gated tool bounds one principal's share of the shared approval queue with a soft bound of about 25 pending approvals (the count is read and then the approval submitted, so concurrent requests from one principal can briefly exceed it). It read the principal's pending count with a call that returned `0` on a pool timeout or a failed query, so a struggling approval store admitted every principal at once. An unreadable count now refuses the call with `-32603` `approval_unavailable` and `retry_after_ms` 5000, creates no ticket, writes a `failure` audit row and is counted on `yuzu_server_approval_submit_refused_total{reason="approval_unavailable"}`. The count also no longer includes pending rows older than the 7-day approval window that the lazy expiry sweep (which runs only when something submits) had not yet marked expired, so a principal holding stale rows is not locked out of every approval-gated tool. The count spans every approval origin. `POST /api/v1/instructions/{id}/execute` and the MCP tool `execute_instruction_definition` apply the same bound with the same fail-closed behaviour (`503` on REST).
