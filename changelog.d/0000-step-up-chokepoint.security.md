- **Breaking: MFA step-up is enforced by one central check on 33 named high-risk routes, and it now runs before the route's own authorization.** A fresh MFA proof is required on 33 named high-risk routes (the 31 that already required one, plus `POST /api/settings/mfa/recovery-codes` and `POST /api/settings/mfa/disable`, which are newly gated); the three JIT-elevation routes keep their own handler gate, and other mutating routes and all MCP tools are not MFA-step-up gated in this release. The check runs before the route's own authorization and same-site (CSRF) checks, so a session with a stale or missing proof receives the `401` step-up envelope instead of that route's `403`; refusals are audited with `stage=pre_authz` and carry an `X-Correlation-Id` header equal to the body's `correlation_id`. A server with no wired authentication store answers `503` on these routes for every caller class; otherwise engine principals receive `403` on every step-up-gated route regardless of grants (audit `reason=engine_principal_denied`), without a store read. An unreadable store answers `503` to local sessions; API-token and MCP-token callers pass the proof check. The server now exits with status `1` at boot if a mutating route has no step-up classification, which can only happen on a fork or custom build (under a restart policy it is a restart loop; roll back to recover). The Guardian guard update and delete buttons now show the refusal as a toast. New metric `yuzu_auth_mfa_step_up_gate_total` and alerts `YuzuStepUpGateUnavailable` and `YuzuStepUpWindowDisabled`; see [Upgrading](docs/user-manual/upgrading.md).
