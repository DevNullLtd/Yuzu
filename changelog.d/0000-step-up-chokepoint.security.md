- **Breaking: MFA step-up is enforced by one central check on 36 named high-risk routes, and it now runs before the route's own authorization.** A fresh MFA proof is required on these 36 routes (25 already required one in the last release, nine more were gated in their handlers earlier in this release cycle, and `POST /api/settings/mfa/recovery-codes` and `POST /api/settings/mfa/disable` are newly gated by this change) for MFA-enrolled local accounts and OIDC sessions per `--mfa-enforcement`; un-enrolled accounts and API-token and MCP-token callers pass the proof check. The three JIT-elevation routes keep their own handler gate; other mutating routes and all MCP tools are not step-up gated in this release. The check runs after the body cap (an over-cap body is still `413`) and before the route's own authorization and same-site (CSRF) checks, so a session with a stale or missing proof receives the `401` step-up envelope instead of that route's `403`. Refusals are audited as `mfa.step_up.required` with `result=error`: a stale or absent proof has the detail `user=<name> age_secs=<n> window_secs=<n> cid=<id> stage=pre_authz` (`age_secs=-1` with no proof), and every other refusal `user=<name> reason=<token> cid=<id> stage=pre_authz`, where `cid` equals the `X-Correlation-Id` response header and the body's `correlation_id`; the JIT-elevation handlers' own gate writes the same fields without `cid=` or `stage=`. A server with no wired authentication store answers `503` on these routes for every caller class, and an unreadable store answers `503` to local sessions. Engine principals receive `403` on every one of the 36 routes regardless of grants, once their credential resolves (during a database outage it cannot, and the request is answered `401` `unauthorized`), and the denial reads no MFA store: the denial is recorded as `mfa.step_up.required` (`reason=engine_principal_denied`), and the per-route handler row (`result=denied`, detail `engine_session_denied`) and body text `engine principals cannot access this endpoint` are no longer produced there, so SIEM rules keyed on them must be updated. SAML sessions cannot satisfy step-up in this release (`403`, unless `--mfa-step-up-window-secs` is `0` or less, which skips the SAML refusal and lets them pass): the remediation says to use an existing untiered, unscoped API token where the route accepts one, or ask an administrator. API clients are told to step up through the `401` envelope, but the Settings MFA panel cannot yet prompt: once the proof is older than the window (default 300 s), Regenerate and Disable show only a toast and the operator must sign in again. An administrator who has just enrolled is covered inside the window, for the confirming session only, because enrolment confirmation records a proof (audited as `step_up_proof=stamped` or `not_stamped` on `mfa.enroll.verified`). The server now exits with status `1` at boot if a mutating route has no step-up classification, which can only happen on a fork or custom build (under a restart policy it is a restart loop, and the gRPC agent port accepts connections for about five seconds of each eleven-to-twelve-second cycle before the process exits; roll back to recover). A refused htmx request on a dashboard or `/api/v1/` route (never MCP) now carries an error toast; the Guardian page's Edit and Delete controls are `fetch`-based dialogs instead, which prompt for the code on a stale proof and show the server's message for a `403` or `503`. New metric `yuzu_auth_mfa_step_up_gate_total` and alerts `YuzuStepUpGateUnavailable` and `YuzuStepUpWindowDisabled` (rolling back removes the counter and the window gauge, so both alerts go silent); see [Upgrading](docs/user-manual/upgrading.md). A request that the step-up check has passed keeps the principal it passed: a later credential resolution in the same request that would land on a different principal yields no session, and the route answers its ordinary no-session response.
