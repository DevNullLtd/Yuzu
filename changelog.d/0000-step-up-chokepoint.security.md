- **Breaking: MFA step-up is enforced by one central check on 33 named high-risk routes, and it now runs before the route's own authorization.** A fresh MFA proof is required on 33 named high-risk routes (the 31 that already required one, plus `POST /api/settings/mfa/recovery-codes` and `POST /api/settings/mfa/disable`, which are newly gated) for MFA-enrolled local accounts and OIDC sessions per `--mfa-enforcement`; un-enrolled accounts and API-token and MCP-token callers pass the proof check, and engine principals are denied. The three JIT-elevation routes keep their own handler gate, and other mutating routes and all MCP tools are not MFA-step-up gated in this release. The check runs before the route's own authorization and same-site (CSRF) checks, so a session with a stale or missing proof receives the `401` step-up envelope instead of that route's `403`. Refusals are audited as `mfa.step_up.required` with `result=error` and a detail of the form `user=<name> reason=<token> cid=<id> stage=pre_authz`, where `cid` equals the `X-Correlation-Id` response header and the body's `correlation_id`. A server with no wired authentication store answers `503` on these routes for every caller class. Otherwise engine principals receive `403` on every one of the 33 routes regardless of grants, without a store read: the denial is recorded as `mfa.step_up.required` (`result=error`, `reason=engine_principal_denied`), and the per-route handler denial row (`result=denied`, detail `engine_session_denied`) and the older body text `engine principals cannot access this endpoint` are no longer produced on these routes, so SIEM rules keyed on them must be updated. SAML sessions cannot satisfy step-up in this release (`403`); use an API token or ask an administrator. An unreadable store answers `503` to local sessions; API-token and MCP-token callers pass the proof check. API clients and the Console are prompted for a code when a proof is stale, but the Settings MFA panel cannot yet prompt: once the proof is older than `--mfa-step-up-window-secs`, the Regenerate and Disable buttons show a toast and the operator must sign in again (an administrator who has just enrolled is covered, because enrolment confirmation now records a fresh proof for the session). The server now exits with status `1` at boot if a mutating route has no step-up classification, which can only happen on a fork or custom build (under a restart policy it is a restart loop; roll back to recover). The Guardian guard update and delete buttons now show the refusal as a toast. New metric `yuzu_auth_mfa_step_up_gate_total` and alerts `YuzuStepUpGateUnavailable` and `YuzuStepUpWindowDisabled` (rolling back removes the counter and the window gauge, so both alerts go silent); see [Upgrading](docs/user-manual/upgrading.md).
