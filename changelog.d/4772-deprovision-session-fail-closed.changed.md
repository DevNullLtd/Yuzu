- **Breaking — a deprovision whose durable session delete does not persist is now a `500` and changes nothing, not a clean success (#4772).** This covers SCIM `PATCH`/`PUT` with `active:false`, SCIM `DELETE` of an active resource and the dashboard user delete (`DELETE /api/settings/users/{username}`). They already answered `500` when the API-token revoke did not persist; they now answer `500` when the cookie-session delete did not persist either, or when both did not (the SCIM body names the failed leg: `failed to revoke API tokens`, `failed to revoke sessions` or `failed to revoke API tokens and sessions for one or more linked identities`; the dashboard says the same, with a `try again` suffix and an error toast). The account stays active and the SCIM resource and identity links are untouched, so a retry once the session store recovers completes the deprovision. The audit row is `partial` (`scim.user.deactivated`, `scim.user.deleted`, `user.delete`) and its detail carries `api_tokens_db_error=true` and/or `sessions_db_error=true`. Before this change the result of the session delete was dropped at this point. For the local username a later session wipe inside the account removal repeated the delete and failed closed, so a silent success needed both deletes to fail; for a linked `oidc:` or `saml:` principal that later wipe covers only the SCIM slug, so this was the only session delete and a failure was silent: the federated session could survive and be rehydrated by another replica or after a restart. Connectors that treat `5xx` as a hard failure, and runbooks that expect a deprovision to complete while the session store is degraded, need attention; there is no break-glass, so wait for `YuzuSessionStoreDegraded` to clear and re-run the deprovision. SCIM `POST /Users` with `active:false` is not in this list for the session leg: its token leg still fails closed (`500`, audit `partial`) and the IdP's retry meets `409` because the account already exists, so reconcile with `GET` and `PATCH active:false`; a failed session delete there is recorded as `sessions_db_error=true session_leg_backstopped=true`, and the call succeeds only if the account removal's own session wipe persisted. Details in `docs/user-manual/upgrading.md` and `docs/user-manual/scim-provisioning.md`.
