- **Breaking: numeric query parameters are parsed strictly across the REST routes that read `limit`, `since`, `until`, `offset`, `index`, `machines_max` or `window` (#4644).**
  The execution-statistics routes, the executions lists, `GET /api/v1/audit` and `GET /api/audit`, `GET /api/analytics/recent`, the instruction, product-pack, workflow, policy and policy-fragment lists, the patch lists, the software-inventory list, the fleet-topology `machines_max` and the app-performance compare `window` read their numbers with `std::stoi`/`std::stoll` (or `strtol`), so `?limit=100abc` was read as `100` and `?since=junk` on the statistics routes meant `0`, "from the beginning". A value that is not one whole base-10 integer now returns `400` (a malformed `limit` on `/api/analytics/recent` and the patch lists, and a malformed `window`, used to be ignored). The shared primitive is `server/core/src/query_int_parse.hpp`. On MCP, `query_audit_log` and the app-performance compare tool answer `-32602` for a `since`, `until`, `limit` or `window` that is not a JSON integer or does not fit a signed 64-bit value (`18446744073709551615` wrapped to `-1`, an unbounded window), and the lenient integer readers now saturate instead of wrapping, so an oversized `limit` reaches the tool's own ceiling instead of `0`. The same strictness covers the dashboard fragments' `page`/`per_page`, the software inventory, DEX perf, network quality, hardware and CA-issued lists, the notification, webhook and offload delivery lists, the pre-flight run list, the hardware sync poll's `await_since`, the TAR process-tree `node` and the `GET /api/v1/events` `?since` cursor (on the query-parameter routes a present-but-empty value is malformed, `GET /api/v1/audit` `limit` included; a malformed `Last-Event-ID` header on `/api/v1/events` and the workflow stream is served live only, nothing replayed and never the whole buffer, and `-1` and `5abc` are never accepted as cursors; the verify fragment's `window` is refused with its usual `200` note). Four admin forms no longer silently save a different value than the one typed: a malformed DEX blast-radius threshold is a `400` that saves nothing, a mistyped enrollment-token `max_uses`/`ttl_hours` (`0x5` read as `0`, meaning unlimited or never-expiring) is a `400` plus an error toast, a mistyped or negative API-token `ttl_hours` is refused with the form's usual `200` feedback span and mints nothing, a negative enrollment `ttl_hours` is refused (it computed `0`, never expires; only an empty field or a value that parses to a literal `0` means unlimited or no expiry, and `/batch` defaults an empty `max_uses` to `1`), and a malformed OTA `rollout_pct` is a `400` instead of `100`. Not changed here, and not an exhaustive list: the live-snapshot `n` attempt counters, and values parsed from stored rows, agent output or server configuration. Three MCP tools whose integer arguments the saturating reader would otherwise turn from a refusal into an accepted value are strict and bounded instead: `create_offload_target` `batch_size` must be 1 to 10000 (the declared schema range, now enforced), `mint_upload_grant` `declared_max_size` must be a JSON integer that fits a signed 64-bit value, and `create_guardian_rule` `version` must be 1 to 2147483647, each answering `-32602` otherwise. `since` and `until` are now presence-tracked on every epoch-bound surface, not only the response routes: a negative `since`, and an `until` of `0` or below, are refused (`400`, or `-32602` on MCP) on the legacy `GET /api/audit` and MCP `query_audit_log`; a negative `since` on REST `/api/v1/execution-statistics/agents` and `/definitions` and their MCP twins; `to=0` on `GET /api/v1/audit/auth-sample`; and `until` of `0` or below, or a non-integer bound, in the JSON body of `POST /api/v1/inventory/query` and `POST /api/inventory/query` (a mistyped bound there made the body read throw). Each used to read `-3600` or `until=0` as no bound and returned the whole log, statistics set or inventory. Omit the parameter for no bound; `since=0` is accepted and matches the same rows as omitting it. `0` and omitting the parameter still mean no bound. `GET /api/v1/audit` takes no `since`/`until`, so it is unchanged. The new `GET /api/v1/execution-statistics/agents` handler also answers `503` instead of throwing when its fleet-read seam is unwired. The two bounded MCP arguments are enforced at their stores too, so the REST twins cannot bypass them: `POST /api/v1/offload-targets` rejects a `batch_size` above 10000 (the per-target buffer flushes only at that size), `POST /api/v1/guaranteed-state/rules` rejects a `version` outside 1 to 2147483647, and a rule update (REST `409`, MCP `-32602`) is refused when the stored version is already at 2147483647, instead of overflowing the signed increment. Numeric path ids matched by a `(\d+)` route pattern (notification read/dismiss, the webhook routes and the auto-approve rule index) now answer `404` for an id that does not fit a signed 64-bit integer, where they threw and answered `500`. A negative hardware `offset`/`limit` is refused (it was clamped to `0`), `GET /api/v1/events` parses `?since` before it writes its success audit row, and the OTA `rollout_pct` is parsed by one helper shared by the upload and rollout routes. A present but empty `limit=` is now a `400` on the two patch lists as well (they used to read it as the default page).
