- **Breaking: numeric query parameters are parsed strictly across the REST routes that read `limit`, `since`, `until`, `offset`, `index`, `machines_max` or `window` (#4644).**
  A value that is not one whole base-10 integer is now `400` where it used to be read as something else: `?limit=100abc` was `100`, `?since=junk` on the statistics routes meant "from the beginning", and a malformed `limit` on `/api/analytics/recent` and the patch lists, or `window` on app-performance compare, was ignored. This covers about thirty routes: the statistics, executions, audit, analytics, definition, policy, patch, inventory, topology, DEX, network, Guaranteed State events, result-set, notification, webhook, delivery, CA, hardware and pre-flight lists, the dashboard fragments' paging, and the `GET /api/v1/events` `?since` cursor (the REST API reference lists them). On the query-parameter routes a present but empty value is malformed; a malformed `Last-Event-ID` header on the event streams is served live only, never replayed. On the result-set list and members routes an integer outside the page range still falls back to the default page size.
  On MCP, `query_audit_log` and the app-performance compare tool answer `-32602` for a bound or limit that is not a JSON integer or does not fit a signed 64-bit value (`18446744073709551615` used to wrap to `-1`), and `mint_engine_credential` does the same for a `ttl_days` of the wrong type (nothing is minted). The per-agent and per-definition statistics tools answer `-32602` for a `limit` below 1 (it became 50; their REST twins still map `0` or a negative to 50). Other integer arguments saturate instead of wrapping, except `create_offload_target` `batch_size` (1 to 10000), `mint_upload_grant` `declared_max_size` (a signed 64-bit integer) and `create_guardian_rule` `version` (1 to 2147483647), which are enforced and answer `-32602`. The two ranges also hold on the REST twins and in the stores: `POST /api/v1/offload-targets` reads `batch_size` as a 64-bit value, rejects anything outside 1 to 10000 with no wrap, and answers `400` for a float, string, boolean or null (a float used to be truncated), `POST /api/v1/guaranteed-state/rules` rejects a `version` outside the range, and a rule update is refused (`409` on REST, `-32602` on MCP) when the stored version is already 2147483647 or above.
  Also refused now, each used to be accepted or clamped: a negative `limit` or `offset` on `GET /api/notifications`; a negative `limit` on the patch lists and on the legacy `GET /api/policy-fragments` and `GET /api/policies` (it reached Postgres and answered `503`); a malformed or negative `min_gib`, or a malformed `window`, on the pre-flight run form; a negative hardware `offset` or `limit`; and a negative `since`, or an `until` or `to` of `0` or below, on the epoch-bounded reads (legacy `GET /api/audit`, MCP `query_audit_log`, the execution-statistics routes, `GET /api/v1/audit/auth-sample`, and the `POST /api/v1/inventory/query` and `POST /api/inventory/query` bodies, where a non-integer bound is also `400`). Those bounds had read as no bound and returned the whole log, statistics set or inventory. Omit the parameter for no bound; `since=0` is accepted.
  Admin forms no longer save a different value than the one typed: a malformed DEX blast-radius threshold, enrollment-token `max_uses`/`ttl_hours` (`0x5` read as `0`, unlimited or never-expiring) or OTA `rollout_pct` is `400`, a mistyped or negative API-token `ttl_hours` is refused with the form's usual `200` feedback span, and a negative enrollment `ttl_hours` is refused. **Behaviour change:** on the OTA rollout change route, an empty `rollout_pct` or one above `100` is now `400` (it used to mean `100`), a negative one still clamps to `0`, and the upload route is unchanged. A numeric path id that does not fit a signed 64-bit integer is `404`, where it was `500`. Not covered: the `n` retry-attempt counter on the live-snapshot polls, and values parsed from stored rows, agent output or server configuration.
