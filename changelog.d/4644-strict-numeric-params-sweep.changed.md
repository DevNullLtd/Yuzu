- **Breaking: numeric query parameters are parsed strictly across the REST routes that read `limit`, `since`, `until`, `offset`, `index`, `machines_max` or `window` (#4644).**
  The execution-statistics routes, the executions lists, `GET /api/v1/audit` and `GET /api/audit`, `GET /api/analytics/recent`, the instruction, product-pack, workflow, policy and policy-fragment lists, the patch lists, the software-inventory list, the fleet-topology `machines_max` and the app-performance compare `window` read their numbers with `std::stoi`/`std::stoll` (or `strtol`), so `?limit=100abc` was read as `100` and `?since=junk` on the statistics routes meant `0`, "from the beginning". A value that is not one whole base-10 integer now returns `400` (a malformed `limit` on `/api/analytics/recent` and the patch lists, and a malformed `window`, used to be ignored). The shared primitive is `server/core/src/query_int_parse.hpp`. On MCP, `query_audit_log` and the app-performance compare tool answer `-32602` for a `since`, `until`, `limit` or `window` that is not a JSON integer or does not fit a signed 64-bit value (`18446744073709551615` wrapped to `-1`, an unbounded window), and the lenient integer readers now saturate instead of wrapping, so an oversized `limit` reaches the tool's own ceiling instead of `0`. The same strictness covers the dashboard fragments' `page`/`per_page`, the software inventory, DEX perf, network quality, hardware and CA-issued lists, the notification, webhook and offload delivery lists, the pre-flight run list, the hardware sync poll's `await_since`, the TAR process-tree `node` and the event streams' `?since` cursor (a present-but-empty value is malformed; a malformed `Last-Event-ID` header still means no replay, but `-1` and `5abc` are no longer accepted as cursors; the verify fragment's `window` is refused with its usual `200` note). Four admin forms no longer silently save a different value than the one typed: a malformed DEX blast-radius threshold is a `400` that saves nothing, a mistyped enrollment-token `max_uses`/`ttl_hours` or API-token `ttl_hours` (`0x5` read as `0`, meaning unlimited or never-expiring) is a `400`, and a malformed OTA `rollout_pct` is a `400` instead of `100`. Not changed here, and not an exhaustive list: the live-snapshot `n` attempt counters, numeric path segments matched by a `(\\d+)` route pattern, and values parsed from stored rows, agent output or server configuration. Three MCP tools whose integer arguments the saturating reader would otherwise turn from a refusal into an accepted value are strict and bounded instead: `create_offload_target` `batch_size` must be 1 to 10000 (the declared schema range, now enforced), `mint_upload_grant` `declared_max_size` must be a JSON integer that fits a signed 64-bit value, and `create_guardian_rule` `version` must be 1 to 2147483647, each answering `-32602` otherwise. A negative `since` or `until` is now refused (`400`, or `-32602` on MCP) on the legacy `GET /api/audit`, MCP `query_audit_log` and REST `/api/v1/execution-statistics/definitions` as well, matching the response routes and the per-agent statistics route: the store applies a bound only above zero, so `-3600` used to mean no bound and returned the whole log or statistics set. `0` and omitting the parameter still mean no bound. `GET /api/v1/audit` takes no `since`/`until`, so it is unchanged. The new `GET /api/v1/execution-statistics/agents` handler also answers `503` instead of throwing when its fleet-read seam is unwired. The two bounded MCP arguments are enforced at their stores too, so the REST twins cannot bypass them: `POST /api/v1/offload-targets` rejects a `batch_size` above 10000 (the per-target buffer flushes only at that size), `POST /api/v1/guaranteed-state/rules` rejects a `version` outside 1 to 2147483647, and a rule update (REST `409`, MCP `-32602`) is refused when the stored version is already at 2147483647, instead of overflowing the signed increment.
