- **The firewall plugin's `state` and `rules` reads answer on macOS accounts that are not root.** Each pf read (`pfctl -s info`, `-s Anchors`, `-s rules`) now runs as `sudo -n -- /sbin/pfctl -s <word>` on the installer's exact read-only sudoers lines, and directly when the agent is root, so the `_yuzu` account reads `pf|enabled` or `pf|disabled`, the anchors, the pf rule rows and the true `ruleset|<n>` instead of `pf|unknown`. An account with neither root nor the lines still reads `pf|unknown`, `ruleset|unknown` and the `error|pf:...:exit:1` rows, never a false-safe value; on a non-root agent `exit:1` means sudo refused the grant or `pfctl` failed (stderr is dropped, so the two read alike).
- **The firewall plugin's Windows `rules` read never returns a default for a property it could not read.** Each rule's name, enabled flag, direction, action and profile mask is read with its own HRESULT and used only when that read returned `S_OK`; a refused or failed property (and `S_FALSE`, which used to read an action as `block`) now shows `unknown` in that field instead of an empty name, `disabled`, `block` or profile `0`, one `error|rule_property:<rules>:0x<hresult>` row says how many rule rows are affected, and a rule the enumerator returned but whose object could not be obtained is an all-`unknown` row that still counts instead of being dropped. The `enabled` and `profiles` columns of `security.firewall.rules` can now read `unknown`. The privilege model no longer claims the Windows reads "need no elevation": they were measured elevated, the shipped identity is LocalSystem, and the least-privilege identity stays with #1442.
- **The packaged Linux agent reads the firewall's state and rules.** Under `NoNewPrivileges=true` with one capability the agent could read neither the nftables ruleset nor the legacy iptables tables, so `state` and `rules` read `unknown` there. firewalld answers first only when its read was complete: the packaged account has no polkit rule and is refused firewalld's `getServices`, so a packaged agent on a firewalld host now answers `backend|nftables` with the nft rule count instead of `backend|firewalld`, `state|running`, `ruleset|unknown`, and a firewalld that was read only in part is held, its own rows written only when no read shows an active ruleset. After the netlink dump, the plugin now reads a root-owned systemd socket (`/run/yuzu-fw-snapshot.sock`), which runs one fixed read-only script per connection and takes no input: `nft -a list ruleset`, and each address family's legacy save tool under its own name (`iptables-legacy-save`, `ip6tables-legacy-save`, which list every instantiated table; a family with no such tool reads the kernel's own table list), cut at 4 MiB. The pure parsers frame the reply strictly and fail closed. Each of the three sections is read or unread: a failed, unrecognised or absent section is unread and reads `unknown` with its own `error|` row, and `inactive` is answered only when all three sections were read and none shows content, in two snapshots taken one after the other; a rule count is written whenever all three were read. A host whose nft command is not installed reads `error|nftables:snapshot:absent`, never `inactive`. The new rows are `error|snapshot:<token>`, `error|nftables:snapshot:failed`, `error|nftables:snapshot:absent`, `error|nftables:unrecognised_output`, `error|iptables:snapshot:failed`, `error|iptables:snapshot:absent`, `error|ip6tables:snapshot:failed`, `error|ip6tables:snapshot:absent` and `error|ip6tables:unrecognised_output`; the table-dump row of a refused netlink read is now written only when the snapshot does not answer. A worst-case walk of every rung is about 25 seconds.
- **A Linux host the installer provisioned reads the firewall's state and rules through the root helper's `snapshot` word.** With no packaged socket, a non-root agent that is not under `NoNewPrivileges` runs `sudo -n -- /usr/local/sbin/yuzu-fw-helper snapshot` (a sudoers line the account already has) and feeds the listing to the same parser and decision as the socket's reply, instead of reading `unknown`. Only a complete run that exited 0 is parsed; a host without the helper file makes no sudo call and says nothing, and a sudo that refuses, or a helper that times out, is clipped or fails, reads `error|snapshot:helper:<token>`.
