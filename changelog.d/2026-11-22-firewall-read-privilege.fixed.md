- **The firewall plugin's `state` and `rules` reads answer on macOS accounts that are not root.** Each pf read (`pfctl -s info`, `-s Anchors`, `-s rules`) now runs as `sudo -n -- /sbin/pfctl -s <word>` on the installer's exact read-only sudoers lines, and directly when the agent is root, so the `_yuzu` account reads `pf|enabled` or `pf|disabled`, the anchors, the pf rule rows and the true `ruleset|<n>` instead of `pf|unknown`. An account with neither root nor the lines still reads `pf|unknown`, `ruleset|unknown` and the `error|pf:...:exit:1` rows, never a false-safe value; on a non-root agent `exit:1` means sudo refused the grant or `pfctl` failed (stderr is dropped, so the two read alike).
- **The firewall plugin's Windows `rules` read never returns a default for a property it could not read.** Each rule's name, enabled flag, direction, action and profile mask is read with its own HRESULT and used only when that read returned `S_OK`; a refused or failed property (and `S_FALSE`, which used to read an action as `block`) now shows `unknown` in that field instead of an empty name, `disabled`, `block` or profile `0`, one `error|rule_property:<rules>:0x<hresult>` row says how many rule rows are affected, and a rule the enumerator returned but whose object could not be obtained is an all-`unknown` row that still counts instead of being dropped. The `enabled` and `profiles` columns of `security.firewall.rules` can now read `unknown`. The privilege model no longer claims the Windows reads "need no elevation": they were measured elevated, the shipped identity is LocalSystem, and the least-privilege identity stays with #1442.
