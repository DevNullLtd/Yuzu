- **The plain-HTTP port answers the four health probes when HTTPS is on.** `GET /livez`, `/readyz`, `/health` and `/api/health` on the redirect port (8080 by default) are now served directly, in cleartext, to GET and HEAD requests, instead of answering `301`; every other request on that port still redirects. A monitor that expected the `301`, or followed it to TLS, now sees `200` (or `503`) and must repoint to `https://…:8443/readyz` or `yuzu-server --healthcheck`; a Kubernetes `httpGet` probe on this port keeps working but now reads the plain port's own answer (`503` only while the HTTPS listener is not bound or has exited): the kubelet used to follow the `301` to TLS, so a wedged HTTPS listener failed the probe, and a probe with a custom `Host` header never followed and now sees real `503`s; for TLS-listener liveness use `httpGet` with `scheme: HTTPS` on 8443 or the `exec` probe. The HTTP port never resolves a session (`/health` always returns the unauthenticated shape) and answers `503` while the HTTPS listener is not bound. Responses on that port (the `301`s, `400`s and probe answers) now count in `yuzu_http_requests_total` with their own method and status labels, so `rate()` totals and the 5xx error ratio include them. They carry the same security headers as the HTTPS port minus HSTS and the CSP `upgrade-insecure-requests` directive, the port's worker pool is fixed-size, and shutdown waits at most 15 s for its thread. The counter's `method` label is limited to the accepted HTTP methods (`GET`, `HEAD`, `POST`, `PUT`, `DELETE`, `CONNECT`, `OPTIONS`, `TRACE`, `PATCH`, `PRI`); any other request-line token is reported as `UNKNOWN`, so existing dashboards and `YuzuHighErrorRate` are unchanged. `--no-https-redirect` removes the listener.
