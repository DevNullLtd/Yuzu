- **The hardware plugin now reads chassis, baseboard, swap and the machine id on Windows, and fills the CPU and DIMM identity columns.** `chassis` and `baseboard` decode the SMBIOS table (chassis type, serial and asset tag; board vendor, product and serial), `swap` reads the page files (`Win32_PageFileUsage`, with the configured maximum from `Win32_PageFileSetting` as the total when there is one), and `machine_id` ships only an HMAC-SHA256 of the registry `MachineGuid` under a fixed public label, so it is stable across agent reinstalls (not across an OS re-image, which regenerates the identifier, and identical on cloned images that were not generalised) but is not secret from a party that already holds the raw id. `processors` rows gain the socket designation and stepping, and `memory` rows the DIMM manufacturer, part number and serial. Each estate action reports a typed status (`ok`, `constrained`, `permission_denied` or `unavailable`, with a named reason); firmware filler such as `To Be Filled By O.E.M.` is written `-` and the section stays supported, while a table that could not be fully read is reported `constrained`. The reads were measured working under a non-administrator service account; a host that refuses one reports `permission_denied` for that section. Linux and macOS still answer the `<os>:planned` status row. These values are stored in the device record and returned by the on-demand `hardware` instructions (`Inventory:Read`); they are not yet shown on the Hardware pages or returned by the REST or MCP device-record endpoints. Each Windows device sends one changed daily report after its agent is built and enrolled. Chassis, board and DIMM serial numbers and the asset tag are now collected; by owner ruling they are device identifiers, not personal data.
