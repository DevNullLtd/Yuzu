- **Enrollment tokens and the pending-agent approval queue are now PostgreSQL-authoritative, shared across every server replica**, instead of living in per-replica `enrollment-tokens.cfg` / `pending-agents.cfg` files (HA WS-6 6.2, ADR-2002). Token consumption and agent enrollment happen in a single guarded transaction, so a `max_uses`-limited token is honoured correctly even when two enroll requests race across different replicas or separate server processes. A pre-6.2 install's `.cfg` files are imported automatically, exactly once, at the first 6.2+ boot — verified against a stored content fingerprint so a later mismatched file is refused rather than silently merged — then renamed aside and never read again.
- **`--generate-tokens` now requires a reachable Postgres auth store** (`--postgres-dsn`/`YUZU_POSTGRES_DSN`) — it mints straight into the same `auth.enrollment_tokens` table the running server reads, so the pre-6.2 file-only mode is gone; the CLI refuses with the same message style as `--mfa-reset` when the store is absent or unreachable.
- **Rolling upgrade to 6.2+ with more than one replica: stop every pre-6.2 replica before starting the first 6.2+ one.** The one-time `.cfg` import runs on whichever replica boots first and stamps a content-fingerprint marker; a second pre-6.2 replica started afterwards contributes no new state, and its own `.cfg` files are skipped or, if they differ, refused (never merged). See [Upgrading](../docs/user-manual/upgrading.md#pre-upgrade-checklist) for the full checklist and the fingerprint-mismatch recovery steps.
- **`DELETE /api/settings/pending-agents/{id}` now returns `409`** if the target row is no longer `pending` (already `approved` or `denied`) — removal only succeeds against a genuinely pending row, closing a gap where removing an already-decided row could silently reverse that admin decision with no audit trail.
