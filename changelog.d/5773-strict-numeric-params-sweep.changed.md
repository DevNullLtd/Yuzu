- **Breaking: numeric query parameters are parsed strictly across the REST routes that read `limit`, `since`, `until`, `offset`, `index`, `machines_max` or `window` (#4644).**
  A value that is not one whole base-10 integer is now `400` where it used to be read as something else: `?limit=100abc` was `100`, `?since=junk` on the statistics routes meant "from the beginning", and a malformed `limit` on `/api/analytics/recent` and the patch lists, or `window` on app-performance compare, was ignored. This covers about thirty routes: the statistics, executions, audit, analytics, definition, policy, patch, inventory, topology, DEX, network, Guaranteed State events, result-set, notification, webhook, delivery, CA, hardware and pre-flight lists, the dashboard fragments' paging, and the `GET /api/v1/events` `?since` cursor (the REST API reference lists them). On the query-parameter routes a present but empty value is malformed, except `limit` on the software list and catalogue routes and fragments, where an empty `limit=` means the default (the three software dashboard fragments answer `200` with a note for a malformed `limit`, not `400`); a malformed `Last-Event-ID` header on the event streams is served live only, never replayed. On the result-set list and members routes an integer outside the page range still falls back to the default page size.
  On MCP, `query_audit_log` and the app-performance compare tool answer `-32602` for a bound or limit that is not a JSON integer or does not fit a signed 64-bit value (`18446744073709551615` used to wrap to `-1`), and `mint_engine_credential` does the same for a `ttl_days` of the wrong type (nothing is minted). The per-agent and per-definition statistics tools answer `-32602` for a `limit` below 1 (it became 50), and their REST twins now answer `400` for it too. Other integer arguments saturate instead of wrapping (`list_issued_certs` `limit` and `offset` included; a non-integer, or an unsigned value above the signed 64-bit range, there is `-32602`; the REST twin `GET /api/v1/ca/issued` answers `400` for any value outside the 32-bit range, where MCP clamps), except `create_offload_target` `batch_size` (1 to 10000), `mint_upload_grant` `declared_max_size` (a signed 64-bit integer) and `create_guardian_rule` `version` (1 to 2147483647), which are enforced and answer `-32602`. The two ranges also hold on the REST twins and in the stores: `POST /api/v1/offload-targets` reads `batch_size` as a 64-bit value, rejects anything outside 1 to 10000 with no wrap, and answers `400` for a float, string, boolean or null (a float used to be truncated), `POST /api/v1/guaranteed-state/rules` rejects a `version` outside the range, and a rule update is refused (`409` on REST, `-32602` on MCP) when the stored version is already 2147483647 or above. On REST, the `limit` in the `POST /api/v1/inventory/query` and `POST /api/inventory/query` bodies is read as a 64-bit value (4294967297 used to wrap to 1 and return one row) and is `400` when below 1 or not an integer, and the `ttl_days` of `POST /api/v1/engine-principals/{id}/credentials` is `400` unless it is a JSON integer from 1 to 90 when present (a string used to throw and a float was truncated). That mint route also answers `400` for a malformed or non-object body instead of minting the default 90-day credential; an empty body still defaults to 90.
  Also refused now, each used to be accepted or clamped: a negative `limit` or `offset` on `GET /api/notifications`; a negative `limit` on the patch lists (the store answered an empty `200`) and on the legacy `GET /api/policy-fragments` and `GET /api/policies` (it reached Postgres and answered `503`); a malformed or negative `min_gib`, or a malformed `window`, on the pre-flight run form; a negative hardware `offset` or `limit`; and a negative `since`, or an `until` or `to` of `0` or below, on the epoch-bounded reads (legacy `GET /api/audit`, `GET /api/v1/audit`, MCP `query_audit_log`, the execution-statistics routes, `GET /api/v1/audit/auth-sample`, and the `POST /api/v1/inventory/query` and `POST /api/inventory/query` bodies, where a non-integer bound is also `400`). Those bounds had read as no bound and returned the whole log, statistics set or inventory. Omit the parameter for no bound; `since=0` is accepted.
  Admin forms no longer save a different value than the one typed: a malformed DEX blast-radius threshold, enrollment-token `max_uses`/`ttl_hours` (`0x5` read as `0`, unlimited or never-expiring) or OTA `rollout_pct` is `400`, a mistyped or negative API-token `ttl_hours` is refused with the form's usual `200` feedback span, and a negative enrollment `ttl_hours` is refused. **Behaviour change:** on the OTA rollout change route, an empty `rollout_pct` or one above `100` is now `400` (it used to mean `100`), a negative one still clamps to `0`, and the upload route is unchanged. A numeric path id that does not fit a signed 64-bit integer is `404`, where it was `500`. Not covered: the `n` retry-attempt counter on the live-snapshot polls, and values parsed from stored rows, agent output or server configuration.
  Security-gating numbers in JSON request bodies are strict too: `expires_at` on `POST /api/v1/tokens` (`-1` or a value above 9223372036854775807 minted a token that never expires; now `400`, `0` or omitted still means never expires), `overlap_secs` on the human and engine-principal rotate routes (a truncated or non-object body used to rotate with the 7-day default), `version` on `POST /api/v1/guaranteed-state/rules`, and `ttl_secs` on `POST /api/v1/upload-grants` (a wrong type, `0` or a negative value used to mint the 900 s maximum). The enrollment-token batch route now honours JSON numbers as well as numeric strings for `count`, `max_uses` and `ttl_hours` (a JSON number was ignored, so the documented example minted single-use tokens that never expired) and answers `400` for a float, boolean, `null`, overflow or malformed body.
  The MCP twins are strict on the same security-gating arguments (`-32602`, nothing created): `issue_code_signing_cert` `validity_days` (1 to 730; `4294967297` wrapped to a 1-day certificate), `mint_upload_grant` `ttl_secs` (at least 1), `create_api_token` `expires_at` (`0` or a future epoch; a negative value minted a token that never expires) and `activate_platform_license` `seat_count`/`expires_at` (at least 0; both licence surfaces are dormant until the `LicenseStore` is wired, ADR-0048). A wrong-typed `enabled`, `full_sync` or `include_revoked` boolean on the Guardian rule, `push_guardian_rules` and engine-principal tools is `-32602` instead of a bare `500`, `create_offload_target` neutralises the name it writes to audit rows, and `query_inventory` advertises its `limit` bounds (1 to 1000, still clamping).
  Also strict, `400` and nothing created or changed: `POST /api/schedules` `interval_minutes` (1 to 35791394), `day_of_week` (0 to 6) and `day_of_month` (1 to 28) (`4294967297` minutes became an every-minute schedule), `POST /api/schedules/{id}/enable` `enabled` (a boolean, the integer `0` or `1` or the exact string `"true"` or `"false"`, and an empty or whitespace-only body still enables; `{"enabled":0}` used to arm the schedule, and any other string is now refused), `POST /api/command` `stagger` and `delay` (0 to 300, the agent-side cap; a float, string or `null` dispatched a delayed command immediately, and a value above 300 ran after 300 seconds without telling the caller), a result-set matcher on `from-instruction-result` and its MCP twin (`n` an integer of at least 1; a `matcher` that is present but not an object, or a `kind` that is not a string, used to be dropped so every responder qualified; a malformed stored `n` or `kind`, or an `n` below 1, threw in the maintenance tick every 2 seconds or admitted everyone and now matches no device), the pre-flight `app_min`, `app_max` and `os_min` thresholds (dotted-decimal with an optional `-beta` suffix; a malformed one read as version 0 and passed every device), and `POST /api/v1/license` `seat_count` and `expires_at` (integers of at least 0, like the MCP twin; dormant until the `LicenseStore` is wired, ADR-0048). A numeric `conditions[].value` on `POST /api/v1/inventory/evaluate`, `POST /api/v1/result-sets/from-inventory-query` and the MCP `create_result_set_from_inventory_query` is accepted with a comparison operator and compared as a number against the raw stored value under all six operators (exact for integers and for integer against a decimal, a stored numeric string counting as a number, so `==` 5 matches a stored `5` or `"5.0"`; a stored value that is not a number, such as `"5 GB"` or `"N/A"`, no longer satisfies `>`, `>=`, `<` or `<=`, where it was read as 5 or compared as text; a boolean with `==`/`!=`; under `>`, `>=`, `<`, `<=` a string operand that is a plain decimal number such as `"4"` or `"2e-7"` compares exactly against a stored number or fully numeric string (a stored integer within int64/uint64, including an integer-valued exponent spelling that fits (such as `"564141138995e7"`), and a stored decimal with a fraction of at most 15 significant digits and a magnitude below 2^53 compare exactly; any other stored decimal, one of more digits or a non-integer at or above 2^53, or a stored negative integer below `-9223372036854775808`, is compared as the nearest double), so the MCP tool, whose schema declares `value` as a string, gets it too; a stored string that merely starts with a number, such as a dotted version `"1.2.3"` or `"5 GB"`, has its leading number read and compared the same way there, and any other stored value never matches, where a JSON number operand never matches a non-numeric stored string; use `version_gte`/`version_lte` for dotted versions, while `==`/`!=` with a string stay an exact text compare and a non-numeric string operand keeps its old ordering; every JSON float (anything written with a decimal point or exponent, such as `5.0`, `1e3` or `5.5`, or an integer outside `-9223372036854775808` to `18446744073709551615`, which arrives as a float) is refused because its original text is lost once parsed, while JSON integers are exact, so send a decimal as a string under `>`, `>=`, `<`, `<=`, which is accepted as a whole number within int64/uint64 (digits or an integer-valued exponent form such as `"1e16"`, read exactly) or with at most 15 significant digits, a magnitude below 2^53, a value that is zero or at least the smallest normal double, and a value within the range of a double (a longer or subnormal decimal is rounded by a double and a comparison against a stored integer could flip; a plain-decimal string such as `"1e400"` is refused instead of ordering lexically; `==`/`!=` with a string stay a text compare): write a whole number as an integer up to 18446744073709551615 or as digits, and a string such as `"9007199254740993.0"` reads as that exact integer; a non-integer at or above 2^53 such as `"9007199254740992.5"` is refused) and any other type, or a non-string `plugin`/`field`/`op`, is `400` (`-32602`): it used to become the empty string, and `>` then selected every device that had the field. A result-set matcher whose `column`, `op` or `value` is present but not a string (or `value_set` not an array) is refused at admission and matches no device when stored, instead of qualifying every responder. The DEX `window` on `GET /api/v1/dex/signals`, `/dex/scope`, `/dex/signals/{obs_type}` and the MCP `list_dex_signals`, `get_dex_signal_scope`, `get_dex_signal_detail`, `get_dex_device_score` must be `24h`, `7d`, `30d` or `all` (only an omitted value keeps `7d`; an empty value is refused too): `90d`, `junk`, an empty value or (on the MCP tools) a non-string such as `30` or `null` used to be answered with 7 days. A schedule row stored with an `interval_minutes` above 35791394 now advances (the advance SQL multiplied in 32 bits and failed with SQLSTATE 22003, so the row re-fired on every poller tick), and `ScheduleEngine::create_schedule` refuses that interval for non-route callers.
