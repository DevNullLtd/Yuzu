- **Agent plugins: reentrant libc lookups, resolver-cache leaks and scan cost.** The `tags` plugin guards its in-memory tag map with a mutex, so concurrent dispatch-pool commands cannot corrupt it. `users.group_members` / `users.local_admins` and `filesystem.get_acl` use the reentrant `getgrnam_r` / `getpwuid_r` / `getgrgid_r` and copy results at once, instead of reading libc's shared static buffers; `users` now reports a failed group lookup as a degraded (CONSTRAINED) result rather than a silently shorter admin list. On Windows, `network_config.dns_cache` and `ioc.check` free the resolver-cache list that `DnsGetCacheDataTable` returns (one RAII owner, `win_dns_cache_table.hpp`, whose walk never frees a node or name twice) and bound the walk; `ioc.check` reports an unreadable cache as CONSTRAINED instead of "Not in DNS cache". The e-mail redaction scan used by `browser_inventory` is bounded: a value over 1 KiB containing an `@` is treated as an address (over-match is the safe direction) instead of rescanning per `@`. The race fixes are checked in CI by a source-text gate that forbids the non-reentrant calls in these plugins; the concurrency tests only exercise the code in plain builds, and regression detection for the races themselves is the nightly ThreadSanitizer job.
- **`filesystem` regex search and replace have a 64 KiB subject SIZE limit; it is not a safety bound.** The standard library's regex executor recurses per matched character and, on libstdc++, overflowed the worker stack (crashing the agent) in testing: g++ -O2 first crashed at 24 KiB for `(a|b)*c` and 48 KiB for `a*b`, and -O0 at 12 KiB and 24 KiB, on an 8 MiB stack (thresholds depend on the pattern and compiler flags; an independent probe saw -O0 crash at 16 and 32 KiB); and at 4 to 8 KiB on a 1 MiB stack (-O0). A line well under the limit can still crash the agent, and the nested-quantifier check remains a heuristic that misses alternation patterns (`(a|a)+$`). A linear-time engine (RE2) is the real fix and is not done; issue #3866 stays open.
