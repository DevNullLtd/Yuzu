- **`GET /api/v1/config`, `PUT /api/v1/config/{param}` and the MCP tools `get_runtime_config` and `set_runtime_config`.** The runtime-configuration API now has v1 REST and MCP twins of the legacy `GET /api/config` and `PUT /api/config/{key}`. All of them share one implementation, so the per-key caller rule from the administrator-only key fix, the value checks and the `config.update` audit rows (`denied`, or `attempted` then `success` or `failure`) are the same on every surface. The v1 routes answer in the A4 envelope. `PUT /api/v1/config/{param}` needs a fresh MFA step-up proof for an MFA-enrolled local or OIDC cookie session, and, like `set_runtime_config`, answers an `effect` field (`immediate`, `deferred` or `stored_only`) because `applied: true` only means the value was stored: the retention windows, `auto_approve_enabled`, `plugin_signing_required` and the `oidc_*` keys are `stored_only`. An MCP-tier token can write only the five keys that are not administrator-only (`heartbeat_timeout`, `response_retention_days`, `guardian_event_retention_days`, `auto_approve_enabled`, `log_level`); the rest answer a permission error with a `denied` audit row (`dex_score_policy` answers invalid params).
