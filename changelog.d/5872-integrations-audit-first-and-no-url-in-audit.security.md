- **Webhook and offload-target audit rows no longer store the destination URL, and the Integrations page's writes are audit-first and same-site.** A destination URL is a bearer secret in practice (Slack-style hooks), but `offload_target.create`/`.delete` and `webhook.create`/`.delete` wrote it into the audit detail, readable by any role holding `AuditLog:Read`. The rows now carry `url=<scheme>://<host>[:<port>] url_fp=<12 hex of the URL's SHA-256>`: enough to say where data went and to match a candidate URL, not enough to use it. Rows written by earlier builds keep the full URL and should be treated like a credential. Webhook create and delete, offload-target create and delete (REST and MCP), directory sync, the group-mapping save and `POST /api/settings/mcp` now write a `result=attempted` audit row first and refuse with `503` and `Sec-Audit-Failed: true` when it cannot be stored, so no change happens without a row (ADR-0033 section 9). The same browser writes (not MCP) refuse a cookie session whose `Origin`/`Referer` names another site or is absent with `403` (`csrf.denied`); token callers are unaffected. A group-mapping save is now validated as a whole before anything is stored, so one malformed entry no longer leaves the earlier pairs written with no audit row, and the strict `POST /api/settings/mcp` refusal carries the standard error envelope and `X-Correlation-Id`. A webhook or offload URL with a query but no path (`https://hooks.example?token=x`) now delivers to the host instead of treating the query as part of it.
