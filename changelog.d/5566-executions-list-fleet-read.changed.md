- **The dashboard executions list and MCP `summarize_working_set` (`kind=execution`) now use the management-group-aware fleet-read gate that `GET /api/v1/executions` uses.** This is hardening plus an admission change, not a fix for a reachable leak. On `GET /fragments/executions`, a group-scoped-only operator gets a confined view (scope applied in SQL before the row limit) where they got `403`; a service-scoped token gets one too when RBAC enforcement is on and the tag store is reachable, and sees executions only through in-scope agents, never through the owner rule. `summarize_working_set` keeps its `Infrastructure:Read` first gate, so a group-scoped-only operator is still refused there. With RBAC off (the shipped default) both surfaces stay unconfined for every authenticated non-service, non-engine caller whose tier allows it (an engine principal is refused with `403` with RBAC off). The gate now answers a retryable `503` when the RBAC or management-group store is not open, for every caller except a JIT-elevated non-service session and, for the management-group store, an engine principal. `GET /api/v1/executions` keeps its real `403`/`503`; on the dashboard fragment the gate still audits the refusal but the response is replaced with an HTTP `200` note (`data-degraded="gate"` for a `503`, `data-denied="true"` for a `403`, `401` unchanged), as are the fragment's own failure notes (`data-degraded="tracker|unavailable"`), so the panel no longer sticks on "Loading...". A monitor that treats `200` as healthy, or watches the fragment's HTTP status, will not see these; use the `auth.fleet_read_required` audit rows and, for the ceiling case, `yuzu_server_rbac_read_degrade_total`. For `summarize_working_set`, a confined caller's absent or out-of-scope execution id is audited `result=denied`, and a NUL byte in those ids is rejected. The ids in these audit details are neutralised and capped at 128 bytes. The `ITServiceOwner` ceiling on this gate was applied by PR #5546. See Upgrading.
