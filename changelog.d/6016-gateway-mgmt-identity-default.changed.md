- **If you use bring-your-own certificates, `--no-default-certs`, a server given its own `--cert`/`--key`, or a corporate or other CA that lets a requester choose a URI SAN, set `{mgmt_peer_auth_mode, pin}` and keep your pin BEFORE you take the new reference gateway configs (#6016, release N+1; breaking).** The shipped configs (`gateway/config/sys.config.prod`, `deploy/docker/reference-gateway-sys.config`) now set `{mgmt_peer_auth_mode, identity}` with no pin, so a default-certificate install needs no gateway action at a server key renewal. A certificate without the identity is refused `no_uri_san` (`YuzuGatewayMgmtAuthRejected` fires, and `YuzuGatewayMgmtIdentityOutage` (critical) once the gateway has admitted nothing for five minutes); under a corporate CA the identity is `yuzu://<hash of that CA's certificate>/server`, a value anyone can compute, so any certificate that CA issues with that URI would be admitted. An unset mode is still `pin` (the boot logs a WARN), so a `sys.config` of your own is unchanged. Upgrade the server first and confirm `yuzu_server_identity_uri_present` is 1; on compose, upgrade the server alone with `--no-deps`, then change the gateway image and config together in one restart, one gateway first (only if its agents can take the disconnect, because agents without the #5183 fix stay wedged). A `cacertfile` that is a bundle, or is empty, truncated or missing, refuses the gateway's boot (`no_mgmt_peer_identity`). Trust: a holder of the CA key alone can mint the identity; revoking the server certificate in the CA does NOT remove its access (a serial in `mgmt_peer_denied` plus a gateway restart does); a gateway binary from before #6016 refuses the pin-less config, so restore your pins before rolling back. See "Behaviour change: the shipped gateway configs admit the server by its identity" in the upgrade guide and "Authorizing the server by its identity" in the gateway guide.
