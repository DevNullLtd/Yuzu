- **Breaking — a store fault at SCIM bearer validation or on a User or Group lookup is now a retryable `503`, not a `401` or `404` (#6835).** During a PostgreSQL outage every SCIM verb used to answer `401` (the token check could not read the store) or `404`/`409`/an empty list/"no duplicate" (a lookup could not), which an IdP may read as a credential failure or "resource gone". Yuzu now answers `503` with `Retry-After: 2` for the token check, every `GET`/`PUT`/`PATCH`/`DELETE` of `/Users/{id}` and `/Groups/{id}`, the `POST` and Group-rename duplicate checks and the `userName eq`/`displayName eq` filters. A missing or wrong token is still `401`, a missing resource `404`, a duplicate `409`. A mutating request's lookup fault (`POST`, `PUT`, `PATCH`, `DELETE`) is audited under its own verb (`scim.user.provisioned` / `updated` / `deleted`, `scim.group.created` / `updated` / `deleted`) as `failure` with detail `store_unavailable: lookup (<site>)`, best effort because the audit store is usually the same database that just failed; `GET /Users/{id}`, `GET /Groups/{id}`, the list filters and the bearer-token `503` write no audit row (a row per polled `GET` would trip `YuzuScimAuditWriteFailures`). The trail is an `ERROR` log line (naming the target id; the bearer line throttled to one per minute) and `yuzu_scim_guard_store_unavailable_total`, whose `guard` label gains `bearer` and `resource`. `YuzuScimGuardStoreUnavailable` covers them, but the rule fires only when Prometheus manages to scrape `/metrics`, which a remote scrape may not during a full outage (it resolves its token against Postgres); `YuzuServerPostgresUnreachable` and `YuzuPgConnectFailing` need a working scrape too, so they are not an honest backstop for a total outage: that is the job of the `/readyz` probe and an operator-defined `up == 0` alert (none ships), and the SCIM alert then fires after recovery or at once for a partial fault. In a full outage the audit store is down as well, so no audit row can be written for the `503`, and `YuzuScimAuditWriteFailures` can fire for a request that changed nothing when a failure row is lost. `scim.auth.denied` and `yuzu_scim_auth_failures_total` no longer fire for an outage: re-check SIEM rules on them, and rules on the mutating verbs above with result `failure` now also match outages, so key them on the `store_unavailable` detail. Group "membership unavailable" `503`s now carry `Retry-After: 2`. Configure the connector to retry `5xx`, but do not assume a vendor does: none of the vendor pages cited in the SCIM guide describes the vendor's behaviour on a `503` from a SCIM server, and the research did not exhaust each vendor's support knowledge base (Okta documents only `429`; the only HTTP status the Entra quarantine page names is a `404` where `200` is expected, as a quarantine cause; in the pages read OneLogin documents no handling of `401`, `429`, `503` or `Retry-After` during provisioning and mentions `404` only for the initial connection check and deleted users), so test against a simulated outage in a non-production tenant. **Still not covered:** the unfiltered `GET /Users`/`GET /Groups` (`list()`/`count()` fail open, #2481: an unfiltered list can answer an empty `200` while a filtered one answers `503`), the `POST` create reads including the concurrent-create re-read and `find_by_external_id` (#6837: a fault there falls through to the later `500`), the tombstone-role `500` and failed post-commit re-read `500` in the revive path, post-mutation re-fetches (`500`), no reconciliation sweep (#6838), the #5214 state and a concurrent revive race (#6946). `POST /Groups` creates the group row before resolving members, so a "membership unavailable" `503` now rolls the empty group back (`ScimStore::delete_group`) first and the retry normally creates the group (`201`); if the rollback itself cannot run because the store is still failing, the empty group remains, the audit row says `could NOT be rolled back` and the retry meets `409` `displayName already exists` until it is removed. **This supersedes the sentence in the already-merged fragment `changelog.d/6842-get-user-role-store-error.security.md` that says a full database outage "still returns `401` at SCIM bearer validation" and is "Tracked in #6835 (SCIM outage answers 401/404)": #6835 closes that gap, the full-outage answer is now `503`.** See `docs/user-manual/scim-provisioning.md` "SCIM failure-mode matrix".
