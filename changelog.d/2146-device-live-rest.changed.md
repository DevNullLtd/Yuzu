- **Breaking - `POST /api/v1/dex/devices/{id}/live` answers each zero-reach cause by name, shares one limit with the new MCP tool `get_device_live`, answers only a finished device answer, gives a store fault, an over-large or empty answer and a shutdown their own statuses, and counts outcomes by word.** A send that reaches no agent used to be one retryable `503`; it now answers `409` `quarantined`, `422` `plugin_not_found` and `403` `kill_switched_os` (permanent, no `retry_after_ms`), and a retryable `503` with `error.reason` `no_agents_reached`, `containment_unreadable`, `route_unreadable` or `os_gate_unreadable` and `retry_after_ms` 5000; a `failure` audit row follows the `requested` row. The in-flight limit is now 2 per principal and 4 in all (it was 4 server-wide), fixed with no flag and counted per server process (N replicas allow N x 4), taken from the shared held-open budget with the MCP tool and the confirmation wait of `DELETE /api/v1/quarantine/{agent_id}` (which skips the wait when no slot is free: a plain call answers `202`, a forced call ends the record and answers `200` with `device_confirmed:false`); over it the route answers `429` with `Retry-After: 2`, and a live read can now also be refused with `429` `global_stream_cap` when the server's whole held-open capacity (`--max-sse-streams`) is full, and counts in `yuzu_http_held_open_responses` and so in `YuzuHeldOpenUtilisationHigh`. The poll now answers only after the device has finished: output without a final row inside the budget is discarded and answered `504` `incomplete` (the one exception is an answer already over the size cap, which REST refuses at once as `502` `output_too_large` and the MCP tool cuts and flags `truncated` at once) with `retry_after_ms` 25000 for a quick kind (the poll's own wall deadline, by which its first run has finished) or 120000 for `processes`, whose first run can hash for up to 120 seconds (it used to be returned as a complete `200`; `timeout` keeps 3000, or 120000 for kind `processes`, whose run can hash for up to 120 seconds), chunked output is joined with a newline in stored order (the route used to keep the last non-empty chunk; rows from other devices were already skipped and a failure row already won), a device that finishes with nothing usable answers `502` `device_error` (it was `200`), a joined answer over 4 MiB, more than 20000 process rows or more than 64 stored rows answers `502` `output_too_large` (unless a stored failure or an `error|` first chunk decides it, as `device_failed` or `device_error`), and a response store that cannot be read answers `503` `response store read degraded` (`store_degraded`, `retry_after_ms` 2000) where it used to answer `504`. Known limit: a chunk the server failed to store cannot be detected, so a `200` can still be a complete-looking answer with a hole in it (a response-store ingest property that affects every reader of stored results; see the REST and MCP references). A permission store that cannot be read at the second permission check answers a retryable `503` `gate_unreadable` and is recorded as such, not as a revocation. A server that is shutting down refuses a new live read with `503` `shutting_down` (no `retry_after_ms`; the MCP tool answers `-32015`, and the quarantine release confirmation skips its wait), abandons a read in progress when the server closes, and its shutdown now waits for live reads within the existing 30 second cap. An audit sink that throws on the `requested` row now answers `503` with `Sec-Audit-Failed: true` instead of an httplib `500`. `yuzu_server_live_requests_total` is now `{surface, kind, outcome}` and `outcome` is a closed set of 31 words (`ok`, `over_budget_principal`, `shutting_down`, `incomplete`, `gate_unreadable` and so on) instead of the HTTP status, with every one of its 186 series created at 0 at boot: a rule that selects `outcome="429"` or any other status matches nothing after the upgrade and raises no error; select `outcome=~"over_budget_.*"` for shed load. The gauge `yuzu_server_live_inflight` is renamed `yuzu_server_live_in_flight` and now includes the MCP tool and the quarantine release confirmation (ceiling 4); the dashboard **Get live info** path is outside the gauge and the limits. Restart all replicas together and do not mix builds, so one rule window never mixes the old and the new outcome values.
