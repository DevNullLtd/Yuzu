- **One approval now runs at most one scheduled occurrence, whatever the server clocks say (#6096).** An approval ticket's submission time was stamped from the submitting server's own clock and compared with the schedule's own run stamps to decide that an approved ticket was already spent, so a clock step or skew between submitting and firing could re-fire an occurrence (extra runs for up to 7 days) or let a skewed server pin the global pending-approval cap. Submission time is now database time like every other approval stamp, and a scheduled ticket is marked used (a guarded `consumed_at` transition scoped to the tickets that tick observed, backed by a clock-free check of the command outbox, which records which ticket each scheduled run used) when its occurrence is queued, so no clock comparison decides it. The schema upgrade marks every outstanding approved or rejected scheduled ticket as used once, so a schedule that was waiting on an approval already given asks again; see `docs/user-manual/upgrading.md`.
