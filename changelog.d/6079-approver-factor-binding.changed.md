- **Breaking: this build is a HARD CUTOVER with no upgrade path, no rolling or mixed-version window and no rollback (#6079).** The `auth` v3 migration seeds nothing, so an account that was already enrolled reads factor generation `0` and is refused `503` (audit `reason=mfa_proof_unavailable`; sticky, no `retry_after_ms`) on the 37 step-up routes (the 35 ordinary rows, approve and reject among them, and the 2 factor-credential routes; Settings self-disable and recovery-code regeneration are two of them) and on the 3 JIT-elevation routes (they probe the same factor state), until `yuzu-server --mfa-reset <user>` clears its factor (under `--mfa-enforcement=required`, or `admin-only` for an administrator, the user enrols again at next sign-in). An administrator API token passes the 35 ordinary rows at the central check but is refused `403` on the 2 factor-credential routes and cannot approve or reject, and an administrator at generation `0` cannot mint one while the window is above 0, so mint it before the cutover. The 35 ordinary rows refuse only while `--mfa-step-up-window-secs` is above 0 (at 0 they pass without reading the store); approve and reject, the 2 factor-credential routes and the elevation routes refuse regardless. The carry-over procedure for an existing deployment (not an upgrade path; `docs/user-manual/upgrading.md`): on the previous build list the enrolled accounts with `SELECT username FROM auth.users WHERE mfa_enrolled_at IS NOT NULL;` (`mfa_factor_gen` does not exist until this build's migration) and record the `auth` and `session_store` rows of `public.schema_meta`; stop every server replica; back up the `auth` and `session_store` schemas with `pg_dump`, with the keys directory as a pair; run `yuzu-server --mfa-reset <user>` on the host for each enrolled operator (it applies both migrations itself, so it can run before any replica starts, and it needs a host shell, the Postgres DSN and the keys directory, so an affected user cannot recover on their own) or start the new build and reset the accounts listed by `SELECT username FROM auth.users WHERE mfa_enrolled_at IS NOT NULL AND mfa_factor_gen <= 0;`. Under `--auth-mode=sso-only`, resetting the `--break-glass-user` account makes the next `sso-only` start refuse to boot until it is enrolled again under a restart with `--auth-mode=standard`; reset it in that order or leave it for a planned window (see the upgrade notes). Restoring the backup is the only way back and is a restore of the previous build's data, not a rollback: `pg_restore --clean --if-exists` does not work over the migrated schemas, so drop the `auth` and `session_store` schemas with `CASCADE`, run `pg_restore` without `--clean`, and set the two `public.schema_meta` rows back to the recorded versions (the upgrade notes have the exact sequence). Starting with empty `auth` and `session_store` schemas instead is an operator choice for a deployment with no enrolled operators; it discards local accounts, passwords, MFA enrolments and sessions. **Action required:** a non-admin cannot enrol itself under `--mfa-enforcement=optional` or `admin-only`, and the seeded `Operator` role holds `Approval:Approve`, so, with RBAC enforcement on, every non-admin approver (and any un-enrolled administrator) is refused until an administrator enrols it (with enforcement off, the shipped default, a non-admin is refused `403` "admin role required" before the MFA gate), through an enrolment sign-in window or by promoting the account long enough to enrol and then demoting it; both are in `docs/ops-runbooks/auth-db-recovery.md`, "Enrolling a non-admin approver". Endpoint agents need no change.

- **The approver rule counts only a proof bound to the factor enrolled now (#6079).** The approver rule (the "approving or rejecting needs an enrolled MFA factor" entry of this release has the matrix of refusals, the window and the audit detail) now requires a local proof's recorded factor generation to equal the account's current one, so disabling MFA and enrolling again replaces the factor and earlier proofs stop counting; the refusal is the usual step-up `401`. When the approver rule's own read fails the answer is `503` with `retry_after_ms`, except for three persistent causes that no retry clears (the auth-store binding trigger observed not in force, the session store's rebind guard latched not in force, and an enrolled account whose factor generation is not positive), which are a `503` with no retry hint until an operator repairs the triggers (and restarts the server) or the account's MFA state; every such `503` is counted as `yuzu_auth_secret_unavailable_total{route="approval"}` (the stored-proof case also increments `yuzu_auth_session_store_degrade_total{op="validate"}`). Tickets decided earlier gain no retroactive assurance, and the `attempted` and `success` audit rows written from this version carry `detail` `approver_assurance:enrolled_fresh_mfa` as the cutover marker. Two follow-ups are named and not part of this change: real OIDC re-authentication at approval time (`auth_time` with `max_age`), and self-service MFA enrolment for non-admin approvers.

- **MFA proofs are bound to the factor they were earned with, and an MFA clear is one transaction (#6079).** A local proof now records the account's factor generation (a database-owned counter that advances on every enrolment or clear; `auth` schema v3 and `session_store` schema v2 add it with two triggers) and the database instant at which the code was checked, and the central step-up check, JIT elevation and the approver rule all require the generation to equal the account's current one. `POST /api/settings/mfa/recovery-codes` and `POST /api/settings/mfa/disable` now accept only a local session (API-token, MCP-token, SSO and engine callers get `403`), keep a ceiling of 300 seconds even with `--mfa-step-up-window-secs=0`, and answer `409` with nothing written if the factor changed after the check admitted the request. New `reason=` tokens on `mfa.step_up.required` rows: `mfa_proof_missing`, `proof_factor_unbound`, `proof_factor_mismatch`, `mfa_proof_unavailable`, `mfa_binding_unenforced` and `factor_credential_requires_local_session`; a Settings factor race is recorded as `reason=factor_changed expected_gen=<n>`. A code that `POST /login/mfa/stepup` accepted but could not leave a bound proof for is an `mfa.step_up.failed` row whose `detail` is `verification_future_dated`, `factor_changed_during_step_up`, `step_up_proof_invalid` or `step_up_proof_store_error` (the same two conditions on a sign-in are `cause=verification_future_dated` and `cause=factor_changed` on a failed `auth.login`), and the answer is the uniform `401` except `step_up_proof_store_error`: a valid code the session store could not record is a `503` ("Your code was accepted but could not be recorded. Wait for the next code and try again.") with no `retry_after_ms`, because the code is spent and a retry with it is a `401` replay. The session store's rebind guard failing reaches a local session as `mfa_proof_unavailable` (SSO sessions are unaffected), not `mfa_binding_unenforced`, so a SIEM rule for this condition must key on both tokens. New metrics: `yuzu_auth_mfa_binding_enforcement_ok{store}`, `yuzu_auth_mfa_stamp_denied_total{reason}`, `yuzu_auth_mfa_verification_future_dated_total`, `yuzu_auth_mfa_factor_changed_total{route}` and `yuzu_auth_mfa_disable_total{result}` (one increment per Settings Disable outcome that reached the owner's commit; `--mfa-reset` has no counter), a new `route="mfa_binding"` value on `yuzu_auth_secret_unavailable_total`, and `yuzu_auth_role_recheck_post_mint_denied_total` now carries a `reason` label (a `sum()` over it is unchanged). `yuzu-server --mfa-reset` and Disable in Settings now clear the factor, the recovery codes, every session of the account (the caller's included) and write the audit row in ONE database transaction (`MfaDisableOwner`), recording `sessions_ended=<n>`; any failure, the audit INSERT included, rolls everything back, so there is no `attempted` row and no `partial` result, the Settings Disable is fail-closed on its audit row (a failure now answers HTTP `200` with an inline error fragment rather than `503`), and `--mfa-reset` exits `1` with "nothing was changed" and applies the `session_store` migrations first; the one exception is a connection lost at COMMIT, where the transaction may have committed (the `--mfa-reset` message says to check the account's MFA status and the `mfa.reset.breakglass` audit row before re-running, and Settings can then hold both an `error` and an `ok` audit row for one clear); neither ends API tokens. `POST /api/settings/mfa/init` and `/verify` now re-confirm the session against its durable row before acting (a session another replica's clear already deleted gets `401` with an empty body, and an unreadable store gets the "MFA backend unavailable" fragment), and reactivating an account (`AuthManager::reactivate_user`, including SCIM) now ends its sessions first and leaves it inactive, answering SCIM `500` so the IdP retries, if that wipe fails. A server whose database lacks either trigger refuses to start (only the one-shots `--mfa-reset` and `--break-glass-arm` open their bootstrap `AuthDB`, and only that, without that refusal and print a loud warning instead, so they stay usable for recovery; the session store has no bypass), and `yuzu_auth_mfa_binding_enforcement_ok{store}` with the `YuzuMfaBindingNotEnforced` alert report a trigger found not in force while running (the alert ships in `docs/prometheus/yuzu-alerts.yml`; see `docs/ops-runbooks/auth-db-recovery.md`, "MFA binding enforcement failed"). See `docs/user-manual/upgrading.md` and `docs/user-manual/instructions.md` "Who can approve".
