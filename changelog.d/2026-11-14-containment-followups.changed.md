- **Breaking — firewall containment and `services.set_start_mode` go through root-owned helpers; re-run the installer on every Linux and macOS host.** `scripts/install-agent-user.sh` writes two helpers (`root:root` 0755 in `/usr/local/sbin` on Linux, `root:wheel` 0755 in `/Library/PrivilegedHelperTools` on macOS) and the sudoers file names each with no argument and no wildcard: `yuzu-fw-helper` and `yuzu-svc-helper`. No sudoers line takes an argument wildcard. On Linux the sudoers file keeps only the two fixed `nft` commands that delete and list the plugin's table beside the helpers, and no longer grants `iptables`, `ip6tables`, an `nft` that takes a file name, or `systemctl`. The firewall plugin loads its nftables ruleset through `yuzu-fw-helper` (`nft load <staged file>`: it checks every line of the file against the ruleset the plugin generates and gives `nft` a ruleset it rebuilt, on standard input, with no temporary file) and runs its iptables fallback through it (nine fixed shapes, every token checked). On macOS the same helper loads the pf anchor (`pf load <staged file>`, checked the same way against the anchor ruleset the plugin generates), and the sudoers file no longer grants `pfctl -f` or `pfctl -X` with a wildcard: `pfctl -X <token>` is pinned to 1 to 24 digits, one bracket class per digit. `services.set_start_mode` runs `systemctl enable|disable|mask|unmask` (Linux) or `launchctl enable|disable` (macOS) through `yuzu-svc-helper`, which checks the unit or label name (1 to 256 letters, digits and `- _ . @`); the macOS sudoers file has no `launchctl bootstrap` or `bootout` and no `security` entry (`certificates.delete` runs as the agent's own identity, root under the shipped LaunchDaemon). Until the installer has been re-run, sudo refuses the helpers: `quarantine` fails on Linux (`nft_load_failed` on an nft host, `iptables_list_failed` on an iptables-only host) and on macOS (`pf_load_failed`, the enable reference taken for the attempt is still given back), and `services.set_start_mode` fails on a non-root agent, each with sudo's own message in the detail. An agent that runs as root runs the tools itself and needs neither the sudoers file nor the helpers. The installer writes the sudoers file only when both helpers were installed in that run: when a helper's directory is not owned by root, or other users can write to it, it removes `/etc/sudoers.d/yuzu-agent`, says so and exits non-zero, and a non-root agent has no sudo grants until the directory is corrected and the installer is re-run (`--check` reports it). The packaged systemd unit is unaffected (it has no sudo path).
- **The `202` response of `DELETE /api/v1/quarantine/{agent_id}` has a documented schema,** and the whitelist limit of 512 characters is named in the `400`.
- **`GET /api/v1/quarantine?include=release_owed` and MCP `list_quarantined_devices` with `include=release_owed`.** The records an operator ended by force whose device has not yet confirmed a release are listed after the active ones with `status: "release_owed"` and the keys `released_at` and `release_owed_since`. Without the option the body is unchanged. Any other `include` value is a `400` (`-32602` on MCP).
- **`quarantine.enable` success rows carry `record_id=<id>`**, on REST and on the MCP `quarantine_device` tool (created and already-recorded paths), so they join to the later `quarantine.disable` and `quarantine.reapply` rows for the same record.
- **New reconciler signals.** `yuzu_server_quarantine_reapply_total` gains `result="drift"` (a record that read confirmed no longer does, counted apart from `unconfirmed`), the gauge `yuzu_server_quarantine_reconciler_last_tick_unixtime` records when a tick last finished, and two alerts follow: `YuzuQuarantineDriftRepeated` (three drifts in an hour) and `YuzuQuarantineReconcilerStalled` (no tick finished for about ten minutes, five minutes stale held for five, while the release and unconfirmed gauges stay frozen).
- **Status replies the reconciler reads are kept 24 hours,** not the default retention, unless they changed what the server holds about the device (they ended a record, cleared an owed release, first confirmed containment, or showed drift). A server set to keep responses forever (`--response-retention-days 0`) keeps them like every other response.
- **Schema v5** adds `apply_gen` and `apply_claimed_at` to `quarantine_store.quarantine_records`. The reconciler's owed-release bookkeeping stays in memory, so a server restart sends one more release and writes the `forced_release_*` rows again.
