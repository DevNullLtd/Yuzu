- **Breaking - Echo reads are roll-up only on the server: a stored result set over a raw capture table is refused.** Creating a result set from a query over a `$<Source>_Live` name or a `<source>_live` table (`from-echo-query`, `from-instruction-result` with an `echo.sql` definition, and the MCP twins), and re-evaluating such a set, formerly answered 201 or 202 and now answers 400 (MCP `-32602`) with `RESULT_SET_REEVAL_STALE_SOURCE`; nothing is dispatched and no audit row is written. Move such queries to the hourly tier (`$<Source>_Hourly`); see Upgrading. The canned Echo queries (recent processes, TCP by process, listening ports, service changes, user sessions, process tree, ARP, DNS, mapped drives) now read the hourly tier, so they return counts per hour rather than individual events and no longer carry a pid. `GET /api/v1/settings/data-retention` drops the `live` tier from `echo.tiers`, adds `budget_dependent` to every tier row (true for `hourly`, the tier a device over its byte budget trims first) and adds `echo.db_budget_bytes` (the 250 MiB default). Result sets now report `agents_failed` and `partial`: an answering agent whose query failed (or whose answer lacks the matcher's column) and never produced a matching row is counted instead of silently left out; agents that never answered are not counted, and a set with more than 100,000 stored answers is marked failed rather than filled as partial. The Device page and the Echo retention-paused list read a source's row count from `<src>_rows`; an agent that sends only the older `<src>_live_rows` shows a dash, not its raw-row figure.
