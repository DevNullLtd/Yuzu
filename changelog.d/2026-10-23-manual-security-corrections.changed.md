- **`--jit-oidc-amr-elevation` works and is on by default.** The server administration page said the flag had no observable effect and that OIDC sessions could not use just-in-time admin elevation. An OIDC session whose identity provider attested multi-factor sign-in (the `amr` claim) can satisfy the second factor for `POST /api/v1/elevate` without local TOTP enrollment. A single-factor OIDC session is always refused. Run with `--no-jit-oidc-amr-elevation` to stop OIDC sessions from elevating at all.
- **An expired upload grant that was never redeemed can still be revoked.** The manual listed "expired" among the states that cannot be revoked. Revoke acts on any grant that is still minted, whether or not its expiry has passed, so use it to clear a stale grant.
- **The audit log writes the `access_review.*` actions.** The audit log page said the `access_review.*` family had no rows of its own in its table, which a reader could take to mean the routes do not audit. The export, list, campaign open, get, attest, flag and close routes each write a row (`access_review.exported`, `access_review.list`, `access_review.campaign_opened`, `access_review.get`, `access_review.attested`, `access_review.flagged`, `access_review.closed`).
- **The fleet visualisation `413` text names a flag that does not exist.** The page tells the operator to raise `--viz-machines-max`. No such server flag exists. Call the REST route directly with a larger `machines_max` query parameter (default `5000`, ceiling `100000`).
- **Revoking an engine credential with `DELETE /api/v1/tokens/{token_id}` needs the administrator role.** The engine principal guides sent operators there without saying so. An engine credential belongs to the engine principal, so a caller who is not an administrator gets `404 token not found`, the same answer as for an unknown id, and only the audit log records the denial.
- **The idle session timeout is off by default.** The enterprise readiness page listed the inactivity timeout as not built. It is built as `--session-inactivity-secs` (`YUZU_SESSION_INACTIVITY_SECS`), and the default `0` disables it, so it protects only the servers where an operator sets it.
- **The OpenAPI document names the session cookie correctly.** `cookieAuth` now names the real cookie, `yuzu_session`, and the top-level `security` lists the bearer token, the `X-Yuzu-Token` header and the session cookie as alternatives rather than as one combined requirement. A client generated from the old document that required all three would send credentials the server does not need. The guaranteed-state rule schema now says `spec_json` is the authoritative form and `yaml_source` is a rendering of it, and an event's `guard_category` may be empty.
