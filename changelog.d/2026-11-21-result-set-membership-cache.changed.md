- Repeated scope previews and evaluations reuse materialized result-set membership within a bounded (16 MiB) per-server cache; ownership, expiry and readiness are still read live on every use. **Behaviour change:** an unpinned result set past its TTL is now refused as a `from_result_set:` scope (`404`) from the moment it expires, not only after the GC sweep deletes it, and using it no longer extends it; pin a set that a schedule or other recurring job targets. Result-set store migrations v6 (`result_sets.membership_generation`) and v7 (triggers on `result_set_members` that re-stamp it on any out-of-band member write) run at boot with no operator action, except that a PostgreSQL `temp_file_limit`, if set, must allow at least 12 MB for a 100,000-member set (see `docs/user-manual/upgrading.md`); after a restore or repair that bypasses triggers, restart every server (see `docs/user-manual/server-admin.md`, "Result-set membership after a restore or repair"). A server that opens with those triggers disabled or altered logs an error and serves result-set membership uncached. The result-set GC sweep now also bounds each pass by member rows (5,000,000, at least one set), so a large expired backlog drains over several passes instead of exceeding the statement timeout and retrying the same sets on every pass.
