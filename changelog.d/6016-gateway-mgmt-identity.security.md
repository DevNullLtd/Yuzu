- **Trust model of the management hop, in the identity modes (#6016, ADR-2004).** A pin required the server's private key; the identity requires a certificate the issuing CA signed with the server URI, so a holder of the CA key alone can command the fleet through a gateway in `identity` or `identity_or_pin` mode, which a pin did not allow. The identity trusts the issuing CA's issuance policy: the install CA mints it only onto the built-in server leaf, but a bring-your-own corporate CA that lets a requester choose a URI SAN with serverAuth would let that requester obtain it, so do not enable the identity there (stay in `pin`, which is not affected); an identity over a `cacertfile` that is not demonstrably exactly one readable certificate refuses boot unless the mode is `identity` with a pin. In the default deployment the CA key and server key are both `0600` files in one certificate directory on the server host, so little changes; a deployment that guards the CA key separately should stay in `pin`, or use `identity` with a pin (which requires both). Withdrawing an identity-mode server certificate is a serial in `mgmt_peer_denied`, read at gateway boot (a change needs a gateway restart, which disconnects the node's agents), until the CRL-fed follow-up lands; rolling the gateway back to a pre-#6016 binary silently drops the deny-list.
