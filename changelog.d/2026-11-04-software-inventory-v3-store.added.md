- **Server side of the sectioned installed-software report (blob contract v3), with install type, scope and location stored per row.** The `installed_software` ingest seam now recognises a v3 blob by its header and applies it one section at a time: a `full` section replaces only its own collector's rows, a status-only section (`constrained`, `timeout`, `oversize`, `not_collected`, `disabled`) records the status and leaves the rows alone, and a section that breaks the grammar is refused and asked for again by name (`installed_software:<facet>` in `need_full`) while the other sections of the same report still apply. The first v3 report from a device removes every row its v2 reports left. A `delta` or `component_inventory` section is parsed and answered with a per-section request for a full resend; applying them arrives with a later change, so nothing is lost. The v2 path is unchanged, and no shipped agent sends v3 yet. A record holding a NUL byte, or a final record cut off before its terminator, refuses its section (the other sections still apply). Schema v10 gives `installed_software` the `install_type`, `install_scope`, `install_location`, `identity_key`, `instance_key` and `purl` columns (`purl` is a server-composed Package URL, indexed, empty for a row from a v2 report and for an ecosystem with no registered type) and adds a per-device `software_facet_state` table; a row from a v2 report keeps `install_location` and `purl` empty until its device's first v3 report. The index builds take `ACCESS EXCLUSIVE` on `installed_software`, which is immediate on the empty table of a fresh deployment (see `docs/user-manual/upgrading.md`). Section outcomes are counted in the new `yuzu_inventory_section_ingest_total{facet,outcome}`; `YuzuInventorySectionIngestRefused` warns on `rejected` sections and `YuzuInventorySectionDeltaUnsupported` only informs on deltas the server cannot apply yet.
