- **Bulk device-CI read: `GET /api/v1/hardware-ci` and the MCP tool `list_hardware_ci_records`.** Pages through the stored hardware CI records of every device (the scalar CI block plus the stored `content_hash` and `blob_version`, no sections), 100 per page by default (the MCP tool defaults to 20) and 1000 at most, for a daily pull into an external CMDB without one call per device. Rows are ordered by the byte value of `agent_id`, so a database collation change cannot make the read skip or miss a device (the byte order comes from the comparison spelled in the query, not from the index). A new index on that byte order, created at server start, makes each page an index scan (writes to the device CI table wait about half a second per million devices while it builds). A duplicate row that a write admitted through a stale primary key would be served twice (the write side is a later control), and writes and every other keyset read still follow the database collation. It reads the stored CI table, not the 30-day roster, so a device offline for longer still appears while its record exists. Read-only; needs `Inventory:Read`; each served page is audited fail-closed as `inventory.devices.ci` and sent with `Cache-Control: no-store`. A present-but-empty `agent_id` is a `400`. A complete walk is not a snapshot, so confirm a device with `?agent_id=<id>` before retiring it. A caller with global read pages through any number of devices; a caller confined to a scope of more than 10000 devices is refused with a clear error unless it passes `agent_id`.
