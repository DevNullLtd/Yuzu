- **Breaking — management-group create, add-member and remove-member are refused with 503 while the audit store is unavailable (#7074, ADR-0033 §9).** Creating a group (REST `POST /api/v1/management-groups`, the MCP tool `create_management_group` and the Settings form) and adding or removing a member (REST add and remove, MCP add) used to act first and audit afterwards, so during an audit-store outage they changed state with no audit row. Each now stores a `result=attempted` row before the change; if it cannot be stored the request is refused (`503` with `Sec-Audit-Failed: true` on REST and Settings, a retryable internal error on MCP) and nothing is created, added or removed. A request refused before any write (permission, an invalid body or argument, an unknown parent, an unknown group on add member) writes no `attempted` row. The session and the permission are checked again after the `attempted` row, and the outcome row is a `success` or a `failure` with a fixed `detail` (`name_conflict`, `store_error`, `validation_refused`, `group_not_found`, `session_revoked`, `permission_revoked`). A lost outcome row never rolls the change back. At the supervised MCP tier the one-time approval is consumed before the `attempted` row, so a call refused for audit reasons has already used its approval and a retry at that tier needs a new approval. A name, parent id or agent id over 256 bytes or holding a control character is now refused before any `attempted` row (a control byte or invalid UTF-8 in an agent id still writes a `denied` row with `detail=invalid_agent_id`, on REST and on MCP), and a parent group that cannot be read is a retryable store fault rather than `parent group not found`. Management-group creation, listed as not covered in #3619, is now audit-first; group update, delete and role assignment remain audit-after-commit. See "Upgrading" and the audit log reference.
