- **Breaking: management-group create, add-member and remove-member are refused with 503 while the audit store is unavailable (#7074, ADR-0033 §9).** Creating a group (REST `POST /api/v1/management-groups`, the MCP tool `create_management_group` and the Settings form) and adding or removing a member (REST add and remove, MCP add) used to act first and audit afterwards, so during an audit-store outage they changed state with no audit row. Each now stores a `result=attempted` row before the change; if it cannot be stored the request is refused (`503` with `Sec-Audit-Failed: true` on REST and Settings, a retryable internal error on MCP) and nothing is created, added or removed. A request refused before any write (permission, an invalid body or argument, an unknown parent, an unknown group on add member) writes no `attempted` row. The session and the permission are checked again after the `attempted` row, and the outcome row is a `success` or a `failure` whose `detail` is `<token> <key>`: a fixed token (`name_conflict`, `store_error`, `validation_refused`, `group_not_found`, `session_revoked`, `permission_revoked`; none holds a space) and the same key the `attempted` row carries (the group name for create, the agent id for add and remove member), so read the first space-delimited word as the token. A lost outcome row never rolls the change back. At the supervised MCP tier the one-time approval is consumed before the `attempted` row, so a call refused for audit reasons has already used its approval and a retry at that tier needs a new approval. A name, parent id or agent id over 256 bytes or holding a control character is now refused before any `attempted` row (a control byte or invalid UTF-8 in an agent id still writes a `denied` row with `detail=invalid_agent_id`, on REST and on MCP), and a parent group that cannot be read is a retryable store fault rather than `parent group not found`. Management-group creation, listed as not covered in #3619, is now audit-first; group update, group delete, role assignment and unassignment and the Settings group delete are audited after the change (the Settings delete records principal `unknown` when no session is resolved), and `ensure_service_management_group` writes no `management_group.*` row, so none of those is refused during an audit outage. Rules that read `management_group.*` rows now also see `result=attempted` rows, so key on the outcome row; MCP `create_management_group` failure rows change (`target_id` is empty and `detail` is a fixed token followed by the group name), and REST and Settings create now write failure rows. The add-member and remove-member failure rows (REST) and the MCP add-member `management_group.add_member` failure row carried a bare `detail=store_error` and are now `store_error <agent id>`, so a SIEM rule that matches `detail` exactly stops matching: match on the first word or a prefix. See "Upgrading" and the audit log reference.
