- **A PostgreSQL collation mismatch now pauses device-CI writes and refuses the bulk CI read.**
  Each replica keeps a gate set from its last conclusive collation check: trusted (the versions match, or the check does not apply), mismatch, or unproven (no conclusive check since the server started). A failed check does not clear a mismatch.
  While the gate reads mismatch, agent ingest of the device-CI source is refused before the blob is parsed and the agent is told to resend in full on its existing backoff (no wire change), so `ci.last_seen` stops advancing for every device until the repair; the refusals are counted as `yuzu_inventory_ingest_total{source="device_ci",outcome="deferred"}` and the new `yuzu_device_ci_writes_deferred_total{op="ingest"|"delete"}`, with one WARN log line when a replica first refuses and one INFO line when writes resume.
  A decommission does not attempt the device-CI removal: `DELETE /api/v1/sle/agents/{id}` answers `500` with `details.write_paused` and `retry_after_ms` 60000 while the other stores are still erased, so re-issue it only after the repair; the device's CI row stays stored until then, so keep a worklist of the devices decommissioned during the pause.
  While the gate is mismatch or unproven, `GET /api/v1/hardware-ci` and the MCP tool `list_hardware_ci_records` answer a retryable `503` (`retry_after_ms` 60000, `Retry-After: 60`, no override flag) and write an `inventory.devices.ci` failure audit row; the per-device CI reads (`GET /api/v1/hardware/{id}`, `get_hardware_ci`, the CI columns of `GET /api/v1/hardware`, the device pages) show the CI part as degraded, and the single-device form `GET /api/v1/hardware-ci?agent_id=<id>` is refused too. After a refusal restart the walk from the first page instead of resuming the old cursor, and compare with your copy.
  A new alert `YuzuDeviceCiWritesPaused` ships in `docs/prometheus/yuzu-alerts.yml` and fires only when that file is loaded.
  Writes and reads resume by themselves, with no restart, within about a minute of the repair (reindex first, then `ALTER DATABASE ... REFRESH COLLATION VERSION` only after the reindex has finished and no invalid index remains, because the refresh now also reopens writes and reads; deduplicate first if a unique reindex fails on duplicate rows), and the agents catch up over their backoff. A check that finds the versions equal while an invalid index exists in the schema `device_inventory_store` (typically a failed `REINDEX ... CONCURRENTLY`) holds the gate: it never pauses writes by itself.
  Unproven is not always transient: when the database records a collation version while the host reports none, or the catalog read is refused, the gate stays unproven, the bulk read stays refused and writes are not paused, with no override flag; the exits are in the server-admin note. Before the first start of a deployment, run the `SELECT` in the upgrading note: a database that is already drifted changes from silent corruption to a paused ingest and a refused CMDB pull until it is repaired.
  Not covered: other stores' text-keyed unique indexes (for example `endpoint_state`) and agent registration are not gated; drift that begins while the server runs is seen up to about an hour later, per replica; a write that passed the check just before the gate flipped is not stopped; rows duplicated before the pause are not repaired by it; behind a load balancer the replicas decide independently (a write can land on a replica still reading trusted); the resend burst on resume has no server-side limit.
  See the PostgreSQL collation version note in `server-admin.md`.
