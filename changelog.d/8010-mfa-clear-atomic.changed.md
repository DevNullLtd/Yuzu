- **Breaking: an API-token or cookie-less caller can no longer confirm an MFA enrolment, and clearing a second factor is one transaction with new audit outcomes (#6079, #8010).** `POST /api/settings/mfa/verify` now needs a signed-in browser session whose stored session row exists: an API-token caller, or any request with no session cookie, is refused `401` (`This action needs a signed-in browser session. Nothing was enrolled.`) and a cookie with no stored row is refused `401` (`Your session is no longer valid. Nothing was enrolled; sign in again.`), both audited `mfa.enroll.failed` with detail `session_not_durable`; an unreadable session store is `503` with `Retry-After: 5` and detail `session_store_unavailable`. API tokens used to enrol (recorded `step_up_proof=not_stamped`); they must now confirm from a browser session. Nothing is enrolled on a refusal and the pending secret is untouched: sign in again, press Set up (it shows the same secret) and enter a current code from the same authenticator entry. SIEM rules that count `mfa.enroll.failed` as wrong-code attempts must filter on the detail. The Settings **Disable two-factor** button and `yuzu-server --mfa-reset` now clear the factor, delete the account's recovery codes, end every durable session of the account and write the outcome audit row in one database transaction (`MfaDisableOwner`). The `attempted` intent row is still written first and still fails closed. The `partial` outcome and the `sessions_ended=failed` detail no longer exist for `mfa.disabled` and `mfa.reset.breakglass`: a clear whose sessions cannot be ended rolls back and leaves the factor enrolled. A store fault or a vanished account on Settings is `503` with `Retry-After: 5` and an `error` row with detail `disable failed`; an outcome row the transaction cannot store is `503` with `Sec-Audit-Failed: true`, changes nothing and leaves only the `attempted` row. Settings and `--mfa-reset` no longer call `invalidate_user` and are no longer counted on `yuzu_auth_session_store_degrade_total{op="invalidate_user"}`. `--mfa-reset` writes `success` with `sessions_ended=<n>` or `error`, and every `error` says nothing was changed (the outcome row's detail ends `(os_identity=<account>)`, in which a `{` or `}` in the OS identity is written as `_` on the `success` row only); the old `state unknown` detail and stderr line are gone, and a refusal now also prints a pointer to the runbook's direct-SQL fallback. An `attempted` row with no outcome row now means the clear did not commit, apart from a connection lost exactly at COMMIT. SIEM rules keyed on `result IN ('partial','error')` should key on `result = 'error'`; rows written by 0.15.x builds can still carry `partial` and `sessions_ended=failed`, so keep those values in queries over retained history.
