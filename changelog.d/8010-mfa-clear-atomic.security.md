- **A second-factor clear can no longer leave sessions live or lose its audit row (#6079 PR 2c, #8010).** The factor clear, the deletion of the account's recovery codes, the deletion of every durable session of the account and the outcome audit row are now one database transaction for both the Settings disable and `yuzu-server --mfa-reset` (`MfaDisableOwner`, in the same ADR-0012 cross-store owner family as the credential-change owner, with the same lock order). This closes the earlier residual in which a failed session delete, or a process killed between the two commits, left the factor cleared with sessions made under it still live, and in which the outcome row could be lost after the clear. The intent row stays first and fail-closed. Limits: a database connection lost exactly at COMMIT can leave the outcome unknown to the caller (the transaction may have committed, and if it did all of it landed); the transaction is correct only while the auth, session and audit stores share one Postgres database, as they do today; API tokens are not ended; an in-flight sign-in can still mint a session the delete did not cover. The Settings enrolment confirm now refuses to commit the factor unless the caller's session is a valid stored session, so an enrolment cannot commit on a session that has already ended; a session that ends between that check and the commit still leaves the account enrolled with `step_up_proof=not_stamped`. Closes #8010: the session validate-cache epoch now also advances on the in-place edits of a cached entry that the cache listed as racy on this replica, the MFA-proof edits (the drop of a cached proof, the post-stamp re-derive and the durable stamp) and the elevation clears (`revoke_elevation`, `revoke_user_elevations`), so a validation held across one of them is served to its one request but not cached; this closes the two-commit window and the cached-proof and elevation stale-copy races on this replica.
