- **A second-factor clear can no longer leave sessions live or lose its audit row (#6079 PR 2c, #8010).** The factor clear, the deletion of the account's recovery codes, the deletion of every durable session of the account and the outcome audit row are now one database transaction for both the Settings disable and `yuzu-server --mfa-reset` (`MfaDisableOwner`, in the same ADR-0012 cross-store owner family as the credential-change owner, with the same lock order: the `auth.users` row, the session rows, the audit INSERT, the session write-generation row last). This closes the earlier residual in which a failed session delete, or a process killed between the two commits, left the factor cleared with sessions made under it still live, and in which the outcome row could be lost after the clear. The intent row stays first and fail-closed. Limits: a database connection lost exactly at COMMIT can leave the outcome unknown to the caller (the transaction may have committed, and if it did all of it landed), so the error text still asks the operator to check the account; the transaction is correct only while the auth, session and audit stores share one Postgres database, as they do today; API tokens are not ended. The Settings enrolment confirm now refuses to commit the factor unless the caller's session is a valid stored session (`401` `session_not_durable`, or `503` `session_store_unavailable`), so an enrolment cannot commit on a session that has already ended; the check runs just before the commit and outside the account's row lock, so a session that ends in that instant still leaves the account enrolled with `step_up_proof=not_stamped`. Closes #8010: the session validate-cache epoch now also advances on an in-place MFA proof edit on this replica (a step-up stamp, its post-stamp re-derive and a cleared proof, whether or not the entry is cached), so a validation held across a stamp or a clear is served to its one request but not cached; this is cache-coherence hardening and no wrong outcome was reachable.
