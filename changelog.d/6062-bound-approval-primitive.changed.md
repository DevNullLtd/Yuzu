- **Breaking: the `guardian.` instruction-definition id prefix is now reserved, beside `mcp.` (#6062).** Creating, importing or YAML-saving a definition whose id starts `guardian.` is refused (case-sensitive, exact prefix), and boot auto-import skips one. A definition that already has such an id keeps executing, but it cannot be re-imported, and the dashboard YAML editor refuses to save it if the document declares `metadata.id`. No shipped content uses the prefix. Before upgrading, run the read-only check and rename anything it lists (see the `guardian.` entry in the Server Administration upgrade notes and the Upgrading guide).
- **Approval store groundwork for bound approvals (#6062, four-eyes MVP PR2); no operator-facing feature creates a bound ticket yet.** Approvals schema migration v2 adds three default-empty columns (`request_json`, `request_digest`, `excluded_roots`), and `ApprovalManager::consume_ticket` now requires the caller to declare the surface it redeems for, so a caller that declares none, or a ticket with no recorded origin, always refuses. What is live today: the MCP approval recall declares `mcp`, and a recall refused by its pre-consume precondition (every approval-gated MCP recall now supplies one that checks the ticket still matches the recalled tool and arguments, and `confirm_engine_rotation` also checks the rotation state) is now counted in `yuzu_approval_precondition_denied_total{origin}` and audited as `approval.precondition_denied`, in addition to its existing `mcp.*` denied row; add the new action to any SIEM audit-action allow-list. What is not live: nothing calls `submit_bound`, so no ticket carries a frozen request or a list of barred reviewers, the `guardian_deploy` origin cannot be minted, and there is no Guardian deploy approval gate (that arrives with #6063 and stays off until #6066). Rollback to the previous build is not supported once a bound ticket exists; see the Upgrading guide.
- **Approval redemption re-checks the stored ticket and refuses a row that moved (#6062).** Every MCP recall of an approval-gated tool now re-checks an approved, unconsumed ticket before spending it: a ticket whose reviewer is the submitter or an excluded root, that records no reviewer, whose excluded roots are unreadable, or whose stored request no longer matches its digest is refused, as the same "approval already used" response a replay gets (audited as `refused: foreign_origin`; the cause is in the server log). The consuming statement is also pinned to the row it examined, so a ticket whose row was rewritten between the check and the spend is refused (audited as `refused: not_consumable`); a no-op rewrite or a VACUUM FULL or CLUSTER at that moment causes a false refusal that a retry clears, whereas after a concurrent spend or a real edit the retry is refused again. Approving always records a distinct reviewer, so ordinary operation never triggers the integrity refusal.
