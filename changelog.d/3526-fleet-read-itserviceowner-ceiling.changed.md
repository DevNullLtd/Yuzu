- **Breaking for service-scoped tokens: `GET /api/v1/enrollment/pending-agents` and `GET /api/v1/upload-grants` now answer `403`.** Two chokepoints let a service-scoped token reach more than the `ITServiceOwner` role allows (found while working #3526). (1) `require_fleet_read` now applies the `ITServiceOwner` authority ceiling that `require_permission` already applied, through one shared helper: a service-scoped token is refused (`403`, "service-scoped token does not grant <securable>:<operation> (the ITServiceOwner role does not hold it)", no `permission` field, audit `auth.fleet_read_required` / `denied`) unless that role itself holds the pair, whatever its minter holds. `ITServiceOwner` does not hold `Enrollment:Read` (deliberately not granted), so `GET /api/v1/enrollment/pending-agents` no longer returns the minter's pending-agent view narrowed to the token's tagged agents. (2) `GET /api/v1/upload-grants` evaluated only its minter's username, so a service-scoped token inherited its minter's `UploadGrant:Read` view (every grant, for a minter holding a global grant); it is now refused (`403`, no `permission` field, audit `upload_grant.list.access_denied`), as the MCP tool `list_upload_grants` already did. **Remediation for both:** use a non-service token (Administrator-minted for the enrollment route); for enrollment automation that is an Administrator-grade credential replacing a confined one, and there is no narrower option today because `Enrollment:Read` is Administrator-only by default and custom-role authoring is not reachable through REST, MCP or the dashboard yet. With the seeded defaults nothing else changes for `Execution`, `Response`, `Inventory`, `Infrastructure`, `Policy`, `GuaranteedState` and `Workflow:Read`; the ceiling also applies wherever a seeded `ITServiceOwner` permission is absent, but no REST, MCP or CLI surface removes one today, and a direct database `DELETE` of a seeded row is re-seeded at the next boot unless the pair is recorded in `revoked_seed_defaults`. A FAILED permission read answers a retryable `503` with `retry_after_ms` 5000 (and bumps `yuzu_server_rbac_read_degrade_total`) on the fleet-read gate, while `require_permission` and `require_scoped_permission` keep answering `403` for the same failure. The ceiling read goes through the RBAC authz circuit breaker with a 250 ms acquire budget (an open breaker is counted under `pool_acquire_timeout`; the sibling gates' ceiling read, which was not breaker-gated and waited up to the pool's 500 ms saturated-pool clamp, now uses the same budget and breaker); a read that is already admitted can still wait up to the pool's `lock_timeout` (10 s default) or `statement_timeout` (30 s default). `kServiceScopeGlobalSafe` is not widened.
