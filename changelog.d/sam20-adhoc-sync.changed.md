- **Breaking - on-demand software sync: a whole group or the whole fleet needs `confirm`, the 500-device limit is replaced by pacing, and the cooldown is per group.** `POST /api/v1/hardware/sync` and the MCP tool `sync_hardware_software` refuse a `group:<id>` or `__all__` scope with `400` unless the request carries `"confirm": true`; `__all__` also needs the global `ManagementGroup:Write` grant on top of an unfiltered `Execution:Execute`. The Software page's **Whole fleet** choice and the tool's group and fleet forms answer `400` naming the confirmation until they send it; a single device and a scope expression are unchanged. There is no device ceiling: the agents are asked to report inside `delay_max_s` seconds (at most 86,400) under one budget of 50 reports per second per server process, `429` with `Retry-After` when that budget is in use and `413` when a run cannot be spread inside 86,400 seconds. `delay_max_s` and `estimated_completion_at` are estimates: the budget bounds what the server asks for, not the rate reports arrive at. A repeat of a run still spreading joins it (`202`, `joined: true`, nothing sent); the gap between runs of one group, scope expression or the fleet is 600 seconds by default (`--inventory-sync-cooldown`, 0-86400) instead of 60 seconds per operator, and runs of different groups no longer exclude each other. The `202` gains `execution_id`, `delay_max_s`, `estimated_completion_at`, `skipped_fresh` and `joined`, the request gains `last_synced_before`, the whole-fleet audit row is `software_estate.sync.fleet_wide`, and the new `GET /api/v1/hardware/sync/{execution_id}` reports how a run is going. New metric `yuzu_server_software_sync_runs_total{result}`.
