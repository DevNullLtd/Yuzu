- **Gateway heartbeat batches now report their latency and bound how long they wait on a failing presence store** (#5686). A new histogram, `yuzu_server_gateway_batch_heartbeat_duration_seconds{outcome="ok"|"degraded"}`, records how long the server takes to handle each gateway `BatchHeartbeat`; `degraded` marks a batch in which the session directory read, the lease renewal or a presence write hit a Postgres problem. When the agent presence store fails during a batch (for example a saturated connection pool), later entries in that batch no longer each wait up to 250 ms for a connection: their presence write is skipped, except for probes (the entry right after the first failure is attempted and the spacing doubles on each further consecutive failure), so under total saturation (every attempt fails) a batch of N makes at most about `floor(log2 N)+1` attempts, each waiting at most its 250 ms pool acquire (not once, and not N times; an attempt stalled on a row lock is bounded by the pool `lock_timeout` instead); under partial brownout a success resets the spacing, so waits can exceed that count (a strictly alternating failure pattern can still approach about N/2 failed waits, about 41 s at N=330, still half of the old N). Skipped writes are counted in the new `yuzu_server_agent_presence_upsert_skipped_total`, with one rate-limited warning; `yuzu_server_agent_presence_store_failed_total{op="upsert"}` now counts the attempts actually made (about `floor(log2 N)+1` at most per saturated gateway batch, not one per entry), so per-entry rate queries on it under-report during saturation. Those heartbeats are still acknowledged and their route leases still renewed, and once the presence store recovers (a later probe in the same batch or the next batch then refreshes the row) the presence row is current again. Limit: during a long presence brownout, other replicas' scope evaluation can be narrower while rows are unrefreshed (rows age out after 90 s by default). Direct (non-gateway) heartbeats are unchanged. No alert ships for it; see `docs/user-manual/metrics.md`.
