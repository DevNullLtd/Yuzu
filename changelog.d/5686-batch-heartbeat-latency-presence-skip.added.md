- **Gateway heartbeat batches now report their latency and bound how long they wait on a failing presence store** (#5686). A new histogram, `yuzu_server_gateway_batch_heartbeat_duration_seconds{outcome="ok"|"degraded"}`, records how long the server takes to handle each gateway `BatchHeartbeat`; `degraded` marks a batch in which the session directory read, the lease renewal or a presence write hit a Postgres problem. When the agent presence store fails during a batch (for example a saturated connection pool), later entries in that batch no longer each wait up to 250 ms for a connection: their presence write is skipped, except for exponentially spaced probes, so under total saturation (every attempt fails) a batch of N waits at most about `ceil(log2 N)+1` times 250 ms (not once, and not N times); under partial brownout a success resets the spacing. Skipped writes are counted in the new `yuzu_server_agent_presence_upsert_skipped_total`, with one rate-limited warning. Those heartbeats are still acknowledged and their route leases still renewed, and once the presence store recovers (a later probe in the same batch or the next batch then refreshes the row) the presence row is current again. Limit: during a long presence brownout, other replicas' scope evaluation can be narrower while rows are unrefreshed (rows age out after 90 s). Direct (non-gateway) heartbeats are unchanged. No alert ships for it; see `docs/user-manual/metrics.md`.
