- **Breaking - `PUT /api/config/{key}` applies the same caller rule as the Settings routes for seven administrator-only keys.** For `plugin_signing_required`, `dex_alert_routing`, `dex_blast_min_devices`, `dex_blast_window_seconds`, `dex_blast_cooldown_seconds`, `dex_cohort_export_key` and `audit_retention_days`, the callers that newly get `403` are a supervised-tier MCP token (even one minted by an administrator) and, with RBAC on, a non-administrator role that holds `Infrastructure:Write`; the `remediation` points to the Settings page or an administrator API token that is not MCP-tier. A temporary elevation still counts as administrator, as on the Settings routes, and a service-scoped token was and remains refused earlier by the permission gate (`auth.permission_required`). The new refusal comes before the runtime-config store is opened and before the body is parsed, stores nothing, and is audited as `config.update` with result `denied` (`token_session_admin_setting_blocked` or `admin_role_required_setting_blocked`) and no preceding `attempted` row; the Settings routes audit the equivalent denial as `auth.admin_required`. The `oidc_*` keys keep their rule and now also refuse a service-scoped token. `audit_retention_days` has no Settings route; it joins the class by maintainer ruling because it sets how long audit events are kept, so write it with an administrator account through `PUT /api/config/audit_retention_days`. Every other key, including `response_retention_days`, `guardian_event_retention_days`, `log_level` and `heartbeat_timeout`, is unchanged and stays writable under `Infrastructure:Write`. Before this change these seven keys could be written with `Infrastructure:Write` alone, so review their stored values (`GET /api/config`, then the `config.update` audit rows). Replaying the whole `GET /api/config` `overrides` map with a non-administrator token stops at the first administrator-only key. See [Upgrading](docs/user-manual/upgrading.md).
