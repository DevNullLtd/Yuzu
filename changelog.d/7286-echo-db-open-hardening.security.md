- **Echo opens `echo.db` more defensively, and a planted `echo.db` no longer blocks a Windows upgrade.** A database that another connection holds past the five-second busy timeout is reported busy and left where it is: Echo refuses to load and the next agent start retries, where before the integrity check read the lock as corruption and moved a healthy `echo.db` aside, resetting the device's history and per-source pause state. A symbolic link (on Windows, any reparse point such as a junction) at `echo.db`, `echo.db-wal`, `echo.db-shm` or `echo.db-journal` is refused before anything is opened, moved or secured. The quarantine of a corrupt `echo.db` and of a corrupt `command_dedup.db` is now one shared routine that never overwrites an earlier quarantine: it needs a filesystem with hard links (NTFS, ReFS, ext4, xfs and APFS all have them) and otherwise leaves the file in place and fails closed, and a `-wal`, `-shm` or `-journal` file that cannot be renamed is copied into the quarantine set before the original is removed. On Windows, when the upgrade finds a foreign-owned `echo.db` beside the legitimate `tar.db`, or a foreign-owned `echo.db-wal` (or `-shm`, `-journal`) beside the legitimate `tar.db-wal`, it now moves that file aside to `echo.db.planted-<epoch>` (a sidecar to `echo.db-wal.planted-<epoch>`) and adopts `tar.db`, instead of failing closed on every start until an operator intervenes; an owner it cannot read moves nothing, and an owner-verified `echo.db-wal` from an interrupted adoption is never carried away. A planted read-only or held-open `-wal`, `-shm` or `-journal` is now deleted through a handle with POSIX delete semantics. The connection used while `echo.db` is opened is now closed by an owner object on every error path.
