- **Echo opens `echo.db` more defensively, and a planted `echo.db` no longer blocks a Windows upgrade.** A database that another connection holds past the five-second busy timeout is reported busy and left where it is: Echo refuses to load and the next agent start retries, where before the integrity check read the lock as corruption and moved a healthy `echo.db` aside, resetting the device's history and per-source pause state. Only an explicit integrity failure (a failed integrity result, a corrupt page or a file that is not a database) moves a file aside now: any other failure to read it, such as an I/O error, a permission fault or a full disk, is refused with `echo.db could not be checked` and quarantines nothing. A symbolic link (on Windows, any reparse point such as a junction) at `echo.db`, `echo.db-wal`, `echo.db-shm` or `echo.db-journal` is refused before anything is opened, moved or secured; the check repeats before the reopen that follows a quarantine, and on Linux and macOS Echo's own two connections (the main one and the read-only query connection) are opened without following a link, so a link swapped in after the check is refused by SQLite itself. On Windows a quarantined set keeps the protected access list, including, best effort and logged, a sidecar that had to be copied rather than renamed; a name in that set that is owned by another account or carries a second hard link is left as it is and logged, never re-secured. The quarantine of a corrupt `echo.db` and of a corrupt `command_dedup.db` is now one shared routine that never overwrites an earlier quarantine: it needs a filesystem with hard links (NTFS, ReFS, ext4, xfs and APFS all have them) and otherwise leaves the file in place and fails closed: Echo refuses to load, and the command-dedup store, which used to fall back to a plain rename, now runs degraded (`yuzu.dedup_degraded`=1, no replay protection) until the data directory is on a filesystem with hard links. On Linux and macOS the move is bound to the regular file Echo opened for the check (its identity is read at the name right after the open): a link swapped in at `echo.db`, or a different file placed there, before the move is left where it is, nothing is moved or re-secured through it and Echo refuses to load; if the name was replaced only after the claim was taken, the judged file stays under its `echo.db.corrupt-<epoch>` name, the file now at `echo.db` is left in place and Echo still refuses to load, and the next start judges that file. Short of the two instants the shared routine records (between the open and the identity read, and between the last re-check and the drop of the original name, which POSIX can only drop by name) and two planted-link cases it records (a hard link already at the name is judged as its target, and a name in the quarantine set swapped for a hard link has that file's mode tightened). A link at a sidecar name (a dangling one too) travels into the quarantine set as a link when it can be renamed and is never resolved or re-secured through, and one that cannot be renamed is removed and not kept. On Windows no such identity is read, so only the no-follow regular-file checks bind the move (a database SQLite has open cannot lose its name there, as SQLite holds it without delete sharing; a link swapped in between the name check and the open is not caught there either; neither is verified on a Windows host yet). The command-dedup store passes no identity to the shared routine, which then binds the move to the file at the name at the moment of the claim. A `-wal`, `-shm` or `-journal` file that cannot be renamed is copied into the quarantine set before the original is removed; one that is a link and cannot be renamed is removed and not kept. On Windows, when the upgrade finds a foreign-owned `echo.db` beside the legitimate `tar.db`, or a foreign-owned `echo.db-wal` (or `-shm`, `-journal`) beside the legitimate `tar.db-wal`, it now moves that file aside to `echo.db.planted-<epoch>` (a sidecar to `echo.db-wal.planted-<epoch>`) and adopts `tar.db`, instead of failing closed on every start until an operator intervenes; an owner it cannot read moves nothing, and an owner-verified `echo.db-wal` from an interrupted adoption is never carried away. On Windows a planted read-only or held-open `-wal`, `-shm` or `-journal` is now deleted through a handle with POSIX delete semantics.
