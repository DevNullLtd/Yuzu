- **In a gateway-fronted deployment (`--gateway-upstream`), the route directory now enforces at most one non-NULL route row per session id by a database unique index.** Two agents racing to adopt the same unheld session id could both succeed, leaving two directory rows with one id (observed at 22% of racing pairs over gRPC). `GatewayRouteStore` migration v5 adds a unique index on `agent_routes(session_id)` (tombstoned rows excluded): the loser of the race is now refused (`FAILED_PRECONDITION` on a `ProxyRegister` replay, counted under `yuzu_server_gateway_route_desync_total{outcome="session_held_by_other_agent"}`), and a `NotifyStreamStatus` CONNECTED that presents an id another agent holds is refused with the placement unpublished (`op="announce_connected"`, a `gateway.session_held_by_other_agent` audit row, and `YuzuGatewaySessionHeldByOtherAgent` now covers both ops) when the presenting agent has no directory row; an agent that still has a row, including a tombstone, is not covered (its CONNECTED lands as `session_mismatch` and does not unpublish). The tombstoned-victim window is NOT closed (#6339) and the safe-to-scale gate is unchanged: run one server replica. The migration runs once at the first start of this version, takes an exclusive lock on `agent_routes` (about 2.4 s at one million rows), tombstones every row of any group that already shared a session id and reports the count as `yuzu_server_gateway_route_session_dedup_total`; the server will not start if the 30 s lock wait expires, so fix the blocker and restart. See the upgrading guide.
