- **`/crypto` dashboard: fleet cryptographic-library inventory.** A new **Posture > Crypto** page shows which cryptographic libraries (OpenSSL, LibreSSL, BoringSSL, GnuTLS, NSS, Mbed TLS, wolfSSL, Libgcrypt, libsodium, Nettle, Botan, Bouncy Castle) are installed across the fleet, with the number of distinct devices per family, a per-version breakdown and a device drill-down. It reads the existing daily installed-software inventory and matches package names against a curated, versioned table (`table_version` in every response); no agent change and nothing new is collected. The evidence is package-level only: statically linked, vendored and OS-bundled copies are not visible, and an empty result means "no matching package rows in the caller's visible inventory", not that a library is absent. Yuzu reports presence and versions and does not judge them. Requires `Inventory:Read`; management-group-confined and service-scoped callers see counts over their visible devices only (service-scoped tokens are refused with 403 until RBAC enforcement is on). The same data is available as `GET /api/v1/crypto/libraries` and `GET /api/v1/crypto/libraries/devices` and as the MCP tools `get_crypto_libraries` and `list_crypto_library_devices`. Every read is audited (`crypto.libraries.view`, `crypto.libraries.devices`, set-and-proceed), and a degraded inventory store is a `503` with `retry_after_ms`, never an empty list. Responses say where the package names came from (`names_source` `catalogue` or `live`, and `names_as_of`); a device-drill cursor is bound to that source, so a walk that crosses a catalogue refresh is refused with a `400` and restarts. Each server process runs at most two `/crypto` store reads at once; a read over that bound is refused at once with a retryable `503`. See `docs/user-manual/crypto.md`.
