- **`BatchHeartbeatResponse` now reports the sessions the server does not hold (#1197; the server lists the sessions it does not know, and the gateway consumes this list, see the gateway heartbeat reconcile entry).** The gateway upstream `BatchHeartbeat` reply gains `unknown_session_ids` (distinct session ids in the batch that this server replica has no in-memory record of, at most 4096, each at most 64 bytes) and `unknown_session_ids_truncated`. The gateway-side replay that consumes them ships in the same release (see the 1197-gateway-heartbeat-reconcile fragment); the rest of this entry describes a gateway or server that does not yet include it, so after a server-only restart `/health` `agents.online` can still stay 0 while the server logs `BatchHeartbeat: unknown session` and `0/1 acked` at debug level (the default-level signals are a server WARN `GatewayRouteStore renew_leases guard rejected the write (outcome=unknown_session ...)` and the `yuzu_server_gateway_route_desync_total{op="renew_leases",outcome="unknown_session"}` counter rising); the gateway manual section "What happens when the server restarts" describes what was observed on one local rig. Old gateways ignore the new fields and old servers leave them empty, so no upgrade ordering is required. A new `yuzu_server_gateway_route_desync_total{op="batch_heartbeat",outcome="malformed_session_id"}` series counts over-length session id entries the server does not hold (expected to stay at zero, no alert); such entries are no longer counted under `renew_leases`/`unknown_session`. The gateway manual's `BatchHeartbeat` interval default is corrected to 1000 ms (`heartbeat_batch_interval_ms`; it previously said 10 seconds).
