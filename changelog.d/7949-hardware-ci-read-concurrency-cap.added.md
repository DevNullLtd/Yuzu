- **The bulk device-CI read now has a per-replica concurrency cap, so a burst of bulk pages can no longer starve permission checks and audit writes.** `GET /api/v1/hardware-ci` and the MCP tool `list_hardware_ci_records` each hold one pooled PostgreSQL connection for the whole page read, and a burst of them could take every connection of the pool they share with authorization and the access-audit write, which then failed their bounded acquires. A new flag `--hardware-ci-read-concurrency` (`YUZU_HARDWARE_CI_READ_CONCURRENCY`) limits how many bulk reads run at once on a replica; unset, it is `min(2, max(1, pool/4))` of `--postgres-pool-size` and is logged at boot, and an explicit value outside 1 to 8 or above half the pool (at least 1) refuses boot. A read that finds every slot taken waits up to 500 ms and is then refused: REST answers `503` with `retry_after_ms` 2000 and `Retry-After: 2`, MCP a retryable error with the same hint, nothing is read, and no `inventory.devices.ci` audit row is written (MCP writes only its generic `mcp.list_hardware_ci_records` row). The new counter `yuzu_hardware_ci_read_busy_total{surface="rest"|"mcp"}` counts each refusal, and a read that names an `agent_id` takes no slot. Read one page at a time. While the audit store is down the same cap bounds the wasted work, since each read still runs and its page is discarded: at most the cap many such reads hold connections at once per replica. That is a concurrency bound only, retries are not rate limited, and the ceiling across replicas is the cap times the replica count. See `server-admin.md` and `metrics.md`.
