- **The pool connections that bulk device-CI page reads hold are now bounded by a per-replica cap (`--hardware-ci-read-concurrency`); over the cap a read gets a retryable `503`.** `GET /api/v1/hardware-ci` and the MCP tool `list_hardware_ci_records` each hold one pooled PostgreSQL connection for the whole page read, and a burst of them could take every connection of the pool they share with authorization and the access-audit write, which then failed their bounded acquires. A new flag `--hardware-ci-read-concurrency` (`YUZU_HARDWARE_CI_READ_CONCURRENCY`) limits how many bulk reads run at once on a replica; unset, it is `min(2, max(1, pool/4))` of `--postgres-pool-size` and is logged at boot, and an explicit value outside 1 to 8 is rejected at argument parsing while one above half the pool (at least 1) refuses boot. A read that finds every slot taken waits up to 500 ms and is then refused: REST answers `503` with `retry_after_ms` 2000 and `Retry-After: 2`, MCP a retryable error with the same hint, nothing is read, and no `inventory.devices.ci` audit row is written (MCP writes only its generic `mcp.list_hardware_ci_records` row). The new counter `yuzu_hardware_ci_read_busy_total{surface="rest"|"mcp"}` counts each refusal. Point reads that name an `agent_id`, other stores, and a single caller that holds every slot are not covered, and the cap is not a reserve: authorization and audit writes can still be refused if other traffic exhausts the pool. Read one page at a time. While the audit store is down the cap bounds the read load, since each read still runs and its page is discarded (at most the cap many per replica at once, retries not rate limited, ceiling across replicas the cap times the replica count); it does not stop audit writes themselves from using the pool. See `server-admin.md` and `metrics.md`.
