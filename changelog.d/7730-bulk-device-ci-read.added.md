- **Bulk device-CI read: `GET /api/v1/hardware-ci` and the MCP tool `list_hardware_ci_records`.** Pages through the stored hardware CI records of every device (the scalar CI block plus the stored `content_hash` and `blob_version`, no sections), 100 per page by default (the MCP tool defaults to 20) and 1000 at most, for a daily pull into an external CMDB without one call per device. Rows are ordered by the byte value of `agent_id`, so a database collation change cannot make the read skip or miss a device (the byte order comes from the comparison spelled in the query, not from the index). A new index on that byte order, created at server start, makes an index scan available for each page (writes to the device CI table wait about half a second per million devices while it builds). Writes, decommission and the per-device reads still go through the primary key and follow the database collation, so after an unrepaired collation change the read can serve duplicate or divergent records and still serve decommissioned devices, and per-device reads can report a stored device as missing (the write pause is a later control); every other keyset read follows the collation too. It reads the stored CI table, not the 30-day roster, so a device offline for longer still appears while its record exists. Read-only; needs `Inventory:Read`; each served page is audited fail-closed as `inventory.devices.ci` and sent with `Cache-Control: no-store`. A present-but-empty `agent_id` is a `400`. A complete walk is not a snapshot, so confirm a device with `?agent_id=<id>` before acting on its absence, and retire a configuration item only through your own decommission process (`GET /api/v1/devices/{id}` answers only for a device with a live session). A caller with global read pages through any number of devices; a caller confined to a scope of more than 10000 devices is refused with a clear error unless it passes `agent_id`.
