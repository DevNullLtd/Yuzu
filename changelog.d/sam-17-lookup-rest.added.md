- **One REST call answers "how many installs, on which devices, last polled when, in what state" for an application or a component.** `GET /api/v1/inventory/software` rows gain `hostname`, `last_seen`, `status` (`current`, `unconfirmed` or `disabled`, derived from the row's collection facet; an unconfirmed row is never proof of absence), `last_confirmed_at`, `install_type`, `install_scope`, `install_location` and `instance_key`, and the route gains `match=exact|prefix|contains`, `version_min` / `version_max` (inclusive, under the catalogue's version comparator) and `status` filters. A new `GET /api/v1/inventory/software/components` serves the component inventory the same way (audit verbs `inventory.components.view` and `inventory.components.export`). A `totals` block, `{installs, devices}` (components: `{instances, devices, devices_unconfirmed}`) with the rollup epoch `as_of`, is served to an unfiltered caller for an exact name; a management-group-confined caller gets its rows with `totals: null` and `totals_omitted: "scope"` (null means not shown, never zero). `installs` counts install rows and `devices` distinct devices. The components rows carry `component_last_confirmed_at`; a version range is resolved against the live distinct versions, so a version first reported since the last refresh is inside it. A component rollup (refreshed hourly with the catalogue rollup, metrics `yuzu_inventory_component_rollup_*`) backs the component totals.
