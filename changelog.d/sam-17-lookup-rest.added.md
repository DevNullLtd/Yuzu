- **One REST call answers "how many installs, on which devices, last polled when, in what state" for an application (REST only; the MCP `query_installed_software` tool keeps its 14 fields until its twin follows).** `GET /api/v1/inventory/software` rows gain `hostname`, `last_seen`, `status` (`current`, `unconfirmed` or `disabled`, derived from the row's collection facet; an unconfirmed row is never proof of absence), `last_confirmed_at`, `install_type`, `install_scope`, `install_location` and `instance_key`, and the route gains `match=exact|prefix|contains`, `version_min` / `version_max` (inclusive, under the catalogue's version comparator) and `status` filters. A `totals` block, `{installs, devices}` with the rollup epoch `as_of`, is served to an unfiltered caller for an exact name; a management-group-confined caller gets its rows with `totals: null` and `totals_omitted: "scope"` (null means not shown, never zero). `installs` counts install rows and `devices` distinct devices. A version range is resolved against the live distinct versions within the caller's scope, so a version first reported since the last refresh is inside it. The totals of a name lookup without a version filter come from the hourly catalogue rollup, so on a fleet above the catalogue ceiling (about 6,000 endpoints, about 4,700 for Windows endpoints that also report MSI products) they read `totals_omitted: "building"` permanently until the rollup is made incremental; add a version filter (`version_min=0`) to get a live figure, and rows and exports are live regardless. The route `GET /api/v1/inventory/software/components` is also added for the same question about components found inside applications (audit verbs `inventory.components.view` and `inventory.components.export`; totals `{instances, devices, devices_unconfirmed, as_of}` backed by a new component rollup, metrics `yuzu_inventory_component_rollup_*`), but no agent reports components until the component producer ships, so it answers an empty page today.
