- **Breaking: the released `DELETE /api/instructions/{id}` and `DELETE /api/product-packs/{id}` now refuse a definition that is still referenced.** A definition that a schedule, a live workflow or a policy fragment still names was previously deleted out from under them. `DELETE /api/instructions/{id}` now answers `409` listing the referrers (nothing deleted; one `instruction.delete` row, `denied` / `referenced`), and `503` when the reference check cannot be answered or the definition cannot be read first. `DELETE /api/product-packs/{id}` runs the same check for every InstructionDefinition item the pack carries before it deletes any item (the pack's own workflows are not counted, nor are its own policy fragments unless a policy still uses one, which survives the uninstall, is counted and has the policy named in the `409`) and answers `409` or `503` the same way, so a refusal never leaves a half-uninstalled pack (a database failure part-way through the deletes still can: the pack stays listed and a retry of the same `DELETE` finishes it, and a failed delete of one of the pack's own policy fragments now stops the uninstall with a `503` instead of being logged and the pack removed). A pack item that names a definition that no longer exists is still checked, so a schedule left dangling by an older build blocks the uninstall until it is removed. The check is advisory, not transactional. The Instructions page shows the refusal of its Delete button as an error toast. A `PUT /api/instructions/{id}` that sets a present `plugin` to an empty string on a row whose plugin is set is refused `400`. Installed product packs that contain a deleted definition do not block it: the `instruction.delete` success row (legacy, v1 and MCP) ends with `packs=<id>,...` (at most 5, then `,+N`). **Breaking for clients that round-trip a whole definition:** the legacy `PUT /api/instructions/{id}` (and the dashboard editor) now clears a stored `yaml_source` when the edit changes `name`, `description`, `version`, `type`, `plugin`, `action` or `approval_mode`, so a later YAML round trip cannot revert the edit; the audit row records which of them changed and the size and SHA-256 of the cleared text. The legacy import also stores the authenticated caller as `created_by` and ignores the document's own value, as the v1 and MCP twins do. The dashboard `POST /api/instructions`, `POST /api/instructions/yaml` (a create), `PUT /api/instructions/{id}` (only for a `plugin` or `action` it changes) and `POST /api/instructions/validate-yaml` now refuse a `plugin` or `action` over 128 characters or outside `A-Za-z0-9._-`, as the v1 twins do; this supersedes the statement in the twins entry that the legacy dashboard routes apply no field bounds. The legacy `PUT /api/instructions/{id}` success audit row records a change of `plugin`, `action`, `approval_mode` or `enabled` as `old -> new`, the dashboard YAML save does the same for `plugin`, `action`, `approval_mode` and `concurrency_mode`, and a legacy delete success row carries the deleted definition's dispatch tuple. On the legacy `PUT /api/instructions/{id}`, restating the stored action in another case is no longer an edit: it keeps the stored spelling and the stored YAML, and the audit detail records no action change (the v1 and MCP updates still lowercase the action and clear the stored YAML on such a restate).
