- **Breaking - access-review attestations require the reviewer to differ from the subject of the grant, and every decision is kept (#4752).** `POST /api/v1/access-reviews/{id}/attestations` and the MCP tool `record_attestation` now refuse a decision (`403`; permission-denied on MCP, with the message `the reviewer must differ from the subject of this grant; ask another reviewer to record this decision`) when the grant is a `user` grant for the reviewer's own account, an engine principal the reviewer owns, or a group the reviewer belongs to (a reviewer who owned the engine principal when the campaign opened is still refused after an ownership transfer, because the store compares the owner frozen into the grant; the way out is another reviewer, or a new campaign, which freezes the current owner). The engine and group checks are read just before the write and fail closed (`503`) when they cannot be answered; group membership is read from Yuzu's stored membership, which an identity provider updates only when that member next signs in interactively (a long-lived API or MCP token can outlast it). A later decision no longer replaces an earlier one: each is appended to the new `access_review_attestation_history` table (access-review store schema v3), a grant keeps at most 100 decisions (the 100th is final: the next is refused with `400`, and the refusal now says to open a new campaign to review the grant again; closing the old one is a separate choice that leaves every undecided grant pending), `GET /api/v1/access-reviews/{id}` and `get_access_review` return `decision_seq` and a `history` of at most the latest 100 entries per grant (every entry except the latest shows at most its first 64 characters of justification, flagged by `justification_truncated`; the full text stays in the database), and a successful call answers `{recorded, decision_seq, previous_decision}`. `principal_id` and `role_name` are limited to 1024 bytes (as is `principal_type`) and `justification` to 4096 bytes. A store fault while recording a decision is now answered `503` (an internal error on MCP) with a fixed message and `retry_after_ms` 5000 instead of database text, and attest and close now give up on a row lock after 3 seconds with that retryable `503` (nothing is committed on that path). The attestation audit rows (`access_review.attested`, `access_review.flagged`) now carry the campaign id alone as `target_id` and the grant in `detail` (` principal_type=... principal_id=... role=...`, after `decision=... previous=... seq=... sod=pass` on success or a `sod_*` token with `result=denied` on a refusal); a SIEM rule keyed on the earlier `<campaign_id>:<principal_type>:<principal_id>:<role_name>` target must be re-keyed, and an archived SIEM export from an earlier deployment holds the old shape, so match both if you search across archives. The schema v3 migration refuses a database that holds a `user` grant decided by its own subject, so the server will not start on it: deploy into a fresh database. The history read assumes a UTF8 database (`SHOW server_encoding;` must answer `UTF8`) and builds its whole response in memory: a worst-case campaign of 1000 grants with 100 decisions each measured 32 MB to 105 MB on the wire and a server peak of about 331 MB to 779 MB in one test on one Linux host, so set a server memory limit (see `docs/auth-architecture.md`). The OpenAPI responses of the open, attest and close routes now document the `Sec-Audit-Failed` header, the output schemas of `open_access_review`, `record_attestation` and `close_access_review` declare the optional `audit_persisted` flag, the campaign id path parameters carry their length and character pattern, and the Settings campaign panel shows "No campaign with that id." for a malformed or unknown id instead of the store's internal error text, and shows the refusal message instead of "[object Object]" when a write is refused; the Settings panel hides Attest and Flag on the reviewer's own user grant and disables the buttons while a request is in flight, and both dashboard pages name the decision a new one replaced. The `created_at_ms`, `decided_at_ms` and `closed_at_ms` values now come from the database clock (the write transaction's start time) rather than each replica's system clock (rows imported or restored from an earlier build keep their old stamps; audit rows are still stamped from the server's own clock). A campaign `title` is now limited to 256 bytes (a longer one is refused with `400`, invalid-params on MCP), and a `justification` that is present and not a string is refused with `400` (invalid-params on MCP) instead of being recorded as empty.
