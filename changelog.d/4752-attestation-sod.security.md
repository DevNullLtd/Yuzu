- **Breaking - access-review attestations require the reviewer to differ from the subject of the grant, and every decision is kept (#4752).** `POST /api/v1/access-reviews/{id}/attestations` and the MCP tool `record_attestation` now refuse a decision (`403`; permission-denied on MCP, with the message `the reviewer must differ from the subject of this grant; ask another reviewer to record this decision`) when the grant is a `user` grant for the reviewer's own account, an engine principal the reviewer owns, or a group the reviewer belongs to. The engine and group checks are read just before the write and fail closed (`503`) when they cannot be answered; group membership is read from Yuzu's stored membership, which an identity provider updates only when that member next signs in interactively (a long-lived API or MCP token can outlast it). A later decision no longer replaces an earlier one: each is appended to the new `access_review_attestation_history` table (access-review store schema v3), a grant keeps at most 100 decisions (the 100th is final: the next is refused with `400`, and the grant can be reviewed again only by closing the campaign and opening a new one), `GET /api/v1/access-reviews/{id}` and `get_access_review` return `decision_seq` and a `history` of at most the latest 100 entries per grant (every entry except the latest shows at most its first 64 characters of justification, flagged by `justification_truncated`; the full text stays in the database), and a successful call answers `{recorded, decision_seq, previous_decision}`. `principal_id` and `role_name` are limited to 1024 bytes (as is `principal_type`) and `justification` to 4096 bytes. A store fault while recording a decision is now answered `503` (an internal error on MCP) with a fixed message and `retry_after_ms` 5000 instead of database text. The attestation audit rows (`access_review.attested`, `access_review.flagged`) now carry the campaign id alone as `target_id` and the grant in `detail` (` principal_type=... principal_id=... role=...`, after `decision=... previous=... seq=... sod=pass` on success or a `sod_*` token with `result=denied` on a refusal); a SIEM rule keyed on the earlier `<campaign_id>:<principal_type>:<principal_id>:<role_name>` target must be re-keyed, and rows written before the upgrade keep the old shape. The schema v3 migration refuses a database that holds a `user` grant decided by its own subject, so the server will not start on it: deploy into a fresh database. The history read assumes a UTF8 database (`SHOW server_encoding;` must answer `UTF8`) and builds its whole response in memory: a worst-case campaign of 1000 grants with 100 decisions each measured 32 MB to 105 MB on the wire and a server peak of about 331 MB to 779 MB in one test on one Linux host, so set a server memory limit (see `docs/auth-architecture.md`).
