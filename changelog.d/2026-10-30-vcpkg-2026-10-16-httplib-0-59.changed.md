- vcpkg baseline bumped to the 2026.10.16 release (cpp-httplib 0.37.1 to 0.59.0, gRPC 1.81.1, OpenSSL 3.6.5, libpq 18.4 and related ports). This includes a glibc `getaddrinfo_a` use-after-free fix in cpp-httplib (upstream #2431, fixed from 0.43.2). Meson now passes the tree's own `protoc` to the gRPC and protobuf CMake probes (needed for trees installed for a non-host triplet). On Windows, meson now also accepts zlib 1.3.2's `z.lib`/`zd.lib` names and no longer requires `libpgcommon.lib`/`libpgport.lib`, which libpq 18 does not install.
- **cpp-httplib 0.59 changes what the server's HTTP front end accepts and sends.** Operators who run a proxy, load balancer or WAF in front of the server should read the upgrading guide (`docs/user-manual/upgrading.md`). Request framing is stricter: a request with a `Content-Length` that is not a single valid decimal number (including one above 2^64-1), two `Content-Length` headers with different values, a non-zero `Content-Length` together with any `Transfer-Encoding`, or a `Transfer-Encoding` whose final coding is not `chunked` is answered `400` with the connection closed before any Yuzu handler runs, so no Yuzu log line, audit row or body-cap metric records it. A request path longer than 256 bytes (`CPPHTTPLIB_REGEX_ROUTE_PATH_MAX_LENGTH`) no longer matches a regex route and answers `404`; this affects the `(.+)` id-in-path routes (for example a very long user name or agent id in the path). The plain-HTTP redirect listener's `301` now closes the connection. A response that leaves a declared request body unread now closes the connection (`Connection: close`); clients that pool connections will reconnect more often after such a response, and a client or proxy that is still sending a large request body when the response is written may see a connection reset instead of the response (an idempotent client should retry as it would for any reset). When a request header is sent twice (including `Cookie` and `Authorization`), the server now reads the first occurrence on every platform (on 0.37.1 the Linux server read the last occurrence, the line a proxy appends; the earlier behaviour on other platforms was not checked), and response headers go out in insertion order. An explicit `Content-Encoding: identity` is now admitted instead of being answered with a bare `415`.
- **The agent `http_client` and `content_dist` plugins are stricter about responses.** A response with two `Content-Length` headers of different values, or (for a body-bearing response) a non-zero `Content-Length` together with `Transfer-Encoding`, now fails: `get` and `head` report `connection failed`, `download` (and a `content_dist` download) reports `download failed: HTTP connection error`, and a `content_dist` upload reports `failed to open upload session (HTTP 0)`. The `head` action returns the response headers in the order the server sent them; before this change the order was unspecified (hash order, differing by platform).
- **Name resolution on Linux can hold an outbound request longer after a timeout.** The `getaddrinfo_a` fix applies to glibc builds only (the macOS and Windows resolver paths are unchanged). On Linux a timed-out lookup now waits for the resolver itself (cpp-httplib estimates about 30 seconds with default resolver settings) before the request fails, so an outbound request to an unresolvable name can take about that long beyond its connect timeout. This includes the server's OIDC discovery and JWKS fetches (OIDC sign-in, Test Connection) and the webhook and offload delivery pools; see the upgrading guide.
