- **`device.filesystem.find_by_hash` is bounded and never follows symlinks (#5624).** The walk used to fork one `sha256sum`/`shasum` per file with no deadline, cap or cancel, so a large tree (the Instructions gate pointed it at a busy `/tmp` or `/etc`) ran past the 30-second poll. It now stops after 20 seconds, 50,000 directory entries or 4 GiB hashed, and after 100 matches, and when anything was skipped or the walk stopped early it writes one trailing `truncated|<reason>|visited=N|hashed=N|skipped_...=N` row and reports `CONSTRAINED` / `PARTIAL` when a bound tripped, an entry could not be read, or a network mount was skipped; a run that skipped nothing writes the same rows as before. Symlinks and junctions are counted and never entered, and a file that is not a regular file is never opened: the open refuses a symlink in any path component on macOS and on Linux 5.6 or later, and in the final component on older Linux kernels and on Windows. Subtrees on network mounts (NFS, SMB and the other types the plugin already refuses elsewhere) are skipped before anything under them is read, on Linux, macOS and Windows. Linux and macOS hash in-process instead of running `sha256sum`/`shasum` per file, empty files are now hashed, and `max_depth` no longer miscounts when the search root is `/`. `device.filesystem.find_by_hash` is now at version 0.4.0 and declares the result columns `row_kind`, `path` and `size`. The Instructions gate searches a private per-run directory seeded with known files instead of the shared temp directory. Result-set column matchers on a key-value plugin's declared columns (such as `filesystem`) now split each row to the declared width, so a matcher over `row_kind`, `path` or `size` can match; before, such a definition's matchers never matched any row.
