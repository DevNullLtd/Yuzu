- **`POST /api/v1/instructions/{id}/execute` and the MCP tool `execute_instruction_definition`.** The stored-definition execute route now has v1 REST and MCP twins that share one pipeline: the definition's stored `parameter_schema` is checked first (a violation queues no approval and dispatches nothing), a Destructive or Forensics action requires explicit, visibility-confined `agent_ids`, and the definition's own `approval_mode` decides whether the call dispatches or answers `pending_approval`. That decision is independent of the MCP tier: an operator-tier token's auto-approval and a supervised token's consumed ticket never satisfy a non-auto definition, and a supervised call whose definition needs approval mints no tier ticket. Unlike the legacy route, the audit row is written before dispatch and a failure to store it refuses the call (`503`, nothing dispatched), every row of one call ends with the same `correlation_id=` as the response's `X-Correlation-Id` header and error body, an unknown definition or an unparseable or too-deeply-nested body leaves a `denied` row, and zero-agents-reached answers a typed `reason` (`invalid_scope`, `quarantined`, `plugin_not_found`, `kill_switched_os`, `containment_unreadable`, `route_unreadable`, `os_gate_unreadable`, `no_agents_reached`) with an honest `retry_after_ms`. The existing MCP `execute_instruction` is unchanged: it remains a raw `plugin.action` call.
