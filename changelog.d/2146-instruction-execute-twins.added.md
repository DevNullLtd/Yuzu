- **`POST /api/v1/instructions/{id}/execute` and the MCP tool `execute_instruction_definition`.** The stored-definition execute route now has v1 REST and MCP twins that share one pipeline: the definition's stored `parameter_schema` is checked first (a violation queues no approval and dispatches nothing), a Destructive or Forensics action requires explicit, visibility-confined `agent_ids`, and the definition's own `approval_mode` decides whether the call dispatches or answers `pending_approval`. That decision is independent of the MCP tier: an operator-tier token's auto-approval and a supervised token's consumed ticket never satisfy a non-auto definition, and a supervised call whose definition needs approval mints no tier ticket. Unlike the legacy route, the audit row is written before dispatch and a failure to store it refuses the call (`503`, nothing dispatched), every row the shared pipeline writes for one call ends with the same `correlation_id=` as the response's `X-Correlation-Id` header and error body (the legacy route's rows carry none), an unknown definition or an unparseable or too-deeply-nested body leaves a `denied` row, and zero-agents-reached answers a typed `reason` (`invalid_scope`, `quarantined`, `plugin_not_found`, `kill_switched_os`, `containment_unreadable`, `route_unreadable`, `os_gate_unreadable`, `no_agents_reached`) with an honest `retry_after_ms`. Creating an approval is bounded per principal by a soft bound of about 25 pending approvals (the count is read and then the approval submitted, so concurrent requests can briefly exceed it; the legacy route does not apply it) and every refusal fails closed and is counted on `yuzu_server_approval_submit_refused_total{reason}`: `429` (MCP `-32004`) `approval_cap_reached` at the bound, `503` (MCP `-32603`) `approval_queue_full` with `retry_after_ms` null when the shared 1000-row queue is full, `503` (MCP `-32603`) `approval_unavailable` when no approval manager is wired or the pending count cannot be read (retryable only for the unreadable count), and `500` (MCP `-32603`) `approval_submit_failed` for a store fault. A dispatch that throws part-way answers `500` `dispatch_exception` (MCP `-32603`) with no retry hint and leaves its execution row `running`, recording the count of sends accepted by the send path so those agents' results complete it, as on `POST /api/v1/commands`; the response names the row and the count as typed fields (`error.execution_id`, always present for this refusal and empty when no row exists, and `error.agents_sent`, a lower bound present only when at least one send was accepted by the send path; `error.data.*` on MCP), the `failure` audit row carries `agents_sent=<n>` whenever a send was accepted by the send path, even if the count could not be stored, and the remediation says when the server will not close the row by itself and that `cancel_execution` does. A definition id holding a control character (a byte below `0x20` or equal to `0x7F`, NUL included) or not valid UTF-8 (reachable on REST) is refused `400` (MCP `-32602`) `invalid_definition_id` with a `denied` row and no retry hint before the definition is looked up, because the store binds the id as a C string and `foo\0xyz` would otherwise resolve `foo` while the audit row recorded another string, and invalid UTF-8 would reach Postgres and read as a retryable `503`; the legacy route is unchanged. The definition id written to audit rows and logs is cut to 128 bytes on a character boundary, with `...` appended. On MCP the supervised-tier pre-mint probe runs after the `Execution:Execute` permission check. The existing MCP `execute_instruction` is unchanged: it remains a raw `plugin.action` call.
