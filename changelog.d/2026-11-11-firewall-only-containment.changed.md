- **Breaking — `DELETE /api/v1/quarantine/{agent_id}` now releases the device and ends the record only on the device's word.** It sends `firewall.release` as the caller and waits up to 5 seconds for the reply: `200` with `state: "released"` when the device answers `status|inactive`, `202` with `state: "releasing"` otherwise (device offline, no reply, a refusal, a partial release). A releasing record stays listed and keeps the dispatch refusal until the device confirms, and the reconciler finishes the release when the device is reachable. `DELETE ...?force=true` ends the record without the device's confirmation for a device that will not return or cannot finish a release (`200` with `forced: true`, `device_confirmed: false` and a message that the device may still be contained); it does not release the device, the server then stops refusing commands to it, and the reconciler sends the release it owes once per reconnect and once per server start. The flag takes `true` or `false` only (any other value is a `400`), needs the same authority as a release, and is REST only. A record ends in those two ways only: a device that reads `inactive` while its record is active is treated as drift and re-applied, never as an end.
- **Quarantine whitelists are bare IPv4 or IPv6 addresses, at most 32.** `POST /api/v1/quarantine` and the MCP `quarantine_device` tool now refuse ports, prefix lengths, IPv4-mapped forms and leading-zero octets, which the firewall plugin's exception grammar cannot express; each address is sent as an outbound and an inbound exception. The MCP tool's created and already-recorded paths both dispatch the stored row; on a record whose release is in progress it answers `-32602` ("a release is in progress for this device") and dispatches nothing.
- **The containment reconciler re-verifies and re-applies.** A confirmed record is re-read every 5 minutes and a status that no longer confirms is drift: one audit row, then a re-apply. The CONFIRMED audit row is written once per transition. A record reads `releasing` while a requested release is unconfirmed. Schema v4 adds two columns and one partial index to `quarantine_store.quarantine_records`.
- **A new record on a device that is already contained is not confirmed when the device kept other exceptions.** `firewall.quarantine` to a contained device keeps the exceptions in force; when the request's exceptions differ from them (as a set) the reply says so. For a record that was never confirmed the reconciler then writes one `quarantine.reapply` failure row (`allow_set_not_applied`), reads no status, leaves the record unconfirmed and `YuzuQuarantineEndpointUnconfirmed` fires. The new whitelist is not applied until the device is released and quarantined again.
- **A forced end's owed release is sent again when the device was busy.** A `busy` answer means the device did not run the release, so the reconciler waits an escalating backoff and sends it again in the same session (at most one release per 15 minutes) instead of giving up for the session. Until the device confirms the owed release, it lifts whatever containment the device holds, including one applied directly with `firewall.quarantine`.
- **Definition ids are `security.firewall.*`, and the macOS sudoers grant is narrowed.** The four containment definitions are in `content/definitions/firewall.yaml`; `scripts/install-agent-user.sh` no longer grants a bare `/sbin/pfctl` or the iptables save and restore helpers.
- **New alert `YuzuQuarantineReleasePending` and gauges.** The alert fires after 15 minutes for a connected device whose release has not completed, and names the forced end as the way out. New gauges `yuzu_server_quarantine_release_pending{reachability}` and `yuzu_server_quarantine_forced_release_owed{reachability}`; `yuzu_server_quarantine_reapply_total` gains `release_sent` and `released`. The Hardware Actions lens no longer lists the four containment actions while the containment UI is off.
