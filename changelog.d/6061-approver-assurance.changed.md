- **Breaking: approving or rejecting an approval request now needs an interactive session and a fresh MFA step-up; MCP can no longer approve (#6061).** `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject`, the dashboard Approvals page and the MCP tools `approve_request` / `reject_request` now require an interactive cookie session (local or OIDC), a fresh MFA step-up, a human principal and not an engine principal; the reviewer-is-not-the-submitter rule is unchanged. API-token and MCP bearer sessions are refused with a typed `403` (A4 envelope, message `approver_assurance_required:<reason>`). A cookie-session `POST` must also carry a same-site `Origin` (or `Referer`) or it is refused with `403`. The MCP transport is not an approval surface (it runs no MFA step-up), so `approve_request` / `reject_request` now always return the typed refusal, whatever credential the caller used (an exception recorded in ADR-1005's exception ledger, entry 2026-10-18: human review is a human-session act); the tools stay registered and listing pending approvals through MCP is unchanged. **Automation that approved over MCP or with an API token will fail, and SAML users cannot approve while MFA step-up is on** (SAML sessions can never pass step-up, #4935). "Fresh MFA step-up" is the existing step-up gate, which can only ask for a factor the account has: a local account that never enrolled in MFA, an OIDC session whose identity provider asserted no `amr` proof under the default `--mfa-enforcement=optional`, and any session when `--mfa-step-up-window-secs=0` all pass it, so approval is not guaranteed to be backed by a second factor. A requirement that the approver holds an enrolled factor is tracked in #6079. With `--mfa-step-up-window-secs=0` the assurance drops to an interactive session only; review every `approval.approve` audit row with `result=success` if you run that way (each decision also writes a `result=attempted` row first, so count only the outcome rows). Also: an unresolvable session now fails closed with `503` and the ticket stays pending, where it used to record the reviewer `unknown` (#4128); the approval attempt is audited before the decision is applied, and approve/reject return `503` with nothing changed when that audit row cannot be written (#5823); the MCP tier/permission mapping for the two tools is `Approval:Approve` (it was `Approval:Write`, #3151); an approved ticket not used within 7 days of its review is refused at consume, and no longer fires from a schedule, even if no new submit has swept expiry (`reviewed_at`, `consumed_at` and the expiry cutoffs now come from the database clock; `submitted_at`, and the schedule stamps `ScheduleRunner` compares it with, still come from the submitting server's own clock, so keep every server NTP-synchronised: when the server that submitted a ticket and the one that advances a recurring schedule disagree about the time, an approved ticket can be used for an extra occurrence or be ignored and re-requested, and a submitter clock far behind or ahead of the database changes how long its pending tickets live; all tracked in #6096); and the Approvals page shows Approve and Reject only to a session that can use them. Before upgrading, search the audit log for token and MCP approvers, and note the rollback and mixed-version behaviour: both are in `docs/user-manual/upgrading.md`. See `docs/user-manual/instructions.md` "Who can approve".
