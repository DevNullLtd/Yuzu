- **Breaking: approving or rejecting an approval request now needs an interactive session and a fresh MFA step-up (which #6079 tightens to an enrolled factor with a fresh proof); MCP can no longer approve (#6061).** `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject`, the dashboard Approvals page and the MCP tools `approve_request` / `reject_request` now require an interactive cookie session (local or OIDC), a fresh MFA step-up, a human principal and not an engine principal; the reviewer-is-not-the-submitter rule is unchanged. API-token and MCP bearer sessions are refused with a typed `403` (A4 envelope, message `approver_assurance_required:<reason>`). A cookie-session `POST` must also carry a same-site `Origin` (or `Referer`) or it is refused with `403`. The MCP transport is not an approval surface (it runs no MFA step-up), so `approve_request` / `reject_request` now always return the typed refusal, whatever credential the caller used (unless read-only mode, a service-scoped token or the tier check refuses first with `-32004`/`-32003`) (an exception recorded in ADR-1005's exception ledger, entry 2026-10-18: human review is a human-session act); the tools stay registered and listing pending approvals through MCP is unchanged. **Automation that approved over MCP or with an API token will fail, and SAML users cannot approve** (SAML sessions can never pass step-up, #4935; a SAML-only deployment has no working approver path until that is decided, tracked in #6098). The MFA requirement is tightened by the #6079 entry, which replaces the generic step-up gate with an enrolled factor and a fresh proof in every `--mfa-enforcement` mode; read that entry for the MFA rules and the action required before upgrading. Before #6079, with `--mfa-step-up-window-secs=0` the assurance dropped to an interactive session only; review every `approval.approve` audit row with `result=success` if you run that way (each decision also writes a `result=attempted` row first, so count the outcome rows, and check every `attempted` row that has no outcome row, comparing counts per `target_id`, because only the `attempted` row is fail-closed and an outcome row is best effort). Also: an unresolvable session now fails closed with `503` and the ticket stays pending, where it used to record the reviewer `unknown` (#4128); the approval attempt is audited before the decision is applied, and approve/reject return `503` with nothing changed when that audit row cannot be written (#5823); the MCP tier/permission mapping for the two tools is `Approval:Approve` (it was `Approval:Write`, #3151); an approved ticket not used within 7 days of its review is refused at consume, and no longer fires from a schedule, even if no new submit has swept expiry (`submitted_at`, `reviewed_at`, `consumed_at` and the expiry cutoffs now all come from the database clock, so server clock skew no longer changes ticket lifetimes); and the Approvals page shows Approve and Reject only to an interactive human session that holds `Approval:Approve` (a hint only: a SAML session is shown them and the route still refuses it), and the Instructions-tab Approvals buttons now show a message, or the code prompt, when a decision is refused. Before upgrading, search the audit log for token and MCP approvers, and note the rollback and mixed-version behaviour: both are in `docs/user-manual/upgrading.md`. See `docs/user-manual/instructions.md` "Who can approve".
