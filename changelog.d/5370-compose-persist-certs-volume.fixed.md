- **The shipped Docker Compose files keep the server's CA and secrets key on a volume, so recreating the server container no longer stops it from starting.** The server keeps its internal CA, default certificates and secrets key-encryption key (KEK) in `/etc/yuzu/certs`. Since 0.14.0 the KEK is also registered in Postgres. `deploy/docker/docker-compose.yml` (the README quickstart) and `docker-compose.uat.yml` kept only `/var/lib/yuzu` on a volume, so an image upgrade, `docker compose down` then `up`, or `--force-recreate` deleted the key files. The server then refused to start with `kek_unresolvable`, and the secrets sealed under that key (TOTP enrolments among them) and the CA root were lost with them. Those composes, `docker-compose.full-uat.yml`, `docker-compose.viz-uat.yml`, `docker-compose.demo.yml` and the `/test` upgrade-test compose now mount a `server-certs` volume on `/etc/yuzu/certs`. The path does not move, so CA key paths recorded in Postgres stay valid. The chiselled server image now creates `/etc/yuzu/certs` owned by the server user. The demo stack adds a one-shot `server-certs-init` service so it also works on older chiselled images. The `/test` upgrade gate also recreates the upgraded server and checks that it comes back on the same keys. **Before switching an existing 0.14.0 stack to the new compose file, copy `/etc/yuzu/certs` out of the old container**: `docs/user-manual/upgrading.md` gives the commands, and what can still be recovered if the files are already gone.
