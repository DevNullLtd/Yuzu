- **Action required before upgrading from 0.14.0 on Docker Compose: copy `/etc/yuzu/certs` out of the running server container first (Upgrading → "Docker Compose: copy `/etc/yuzu/certs` out of the server container before you recreate it").** Affected: a 0.14.0 Docker Compose stack whose server has no volume on `/etc/yuzu/certs` while Postgres has one — `deploy/docker/docker-compose.yml` (the README quickstart), `docker-compose.uat.yml`, `docker-compose.full-uat.yml`, `docker-compose.viz-uat.yml`, `docker-compose.demo.yml` used with `--keep`, any compose copied from them, and Compose Wizard output from before 0.14.1 in Plaintext mode or with 'Persist generated certs' unticked. Not affected: `docker-compose.reference.yml` and `docker-compose.reference-gateway.yml` (their `certs` volume). The server keeps its internal CA, default certificates and secrets key-encryption key (KEK) in `/etc/yuzu/certs`, and since 0.14.0 the KEK is also registered in Postgres. In those stacks an image upgrade, `docker compose down` then `up`, or `--force-recreate` deleted the key files, and the server then refused to start with `kek_unresolvable`. Those composes, the `/test` upgrade-test compose and the Compose Wizard's Default and Plaintext output now mount a `server-certs` volume on `/etc/yuzu/certs` (the wizard's "Persist generated certs" option is now always on). The path does not move, so CA key paths recorded in Postgres stay valid. The chiselled server image now creates `/etc/yuzu/certs` owned by the server user, and the demo stack adds a one-shot `server-certs-init` service so it also works on older chiselled images. The upgrade guide gives a checked copy-out recipe, the diagnostics to run before anything destructive (a lost volume line or the wrong file owner gives the same error), a rollback that keeps the keys, and what can still be saved if the files are already gone. The `/test` upgrade gate also recreates the upgraded server and checks that it comes back on the same keys. (#5370)
