- **Action required before upgrading from 0.14.0 on Docker Compose: copy `/etc/yuzu/certs` out of the running server container first (Upgrading → "Docker Compose: copy `/etc/yuzu/certs` out of the server container before you recreate it").** Affected: a 0.14.0 Docker Compose stack whose server has no named volume on `/etc/yuzu/certs` while Postgres has one — `deploy/docker/docker-compose.yml` (the README quickstart), `docker-compose.uat.yml`, `docker-compose.full-uat.yml`, `docker-compose.viz-uat.yml`, `docker-compose.demo.yml` used with `--keep`, any compose copied from them, and Compose Wizard output from before 0.14.1 in Plaintext mode, with 'Persist generated certs' unticked, or with named volumes off and an external Postgres. Not affected: `docker-compose.reference.yml` and `docker-compose.reference-gateway.yml` (their `certs` volume). The server keeps its internal CA, default certificates and secrets key-encryption key (KEK) in `/etc/yuzu/certs`, and since 0.14.0 the KEK is also registered in Postgres. In those stacks an image upgrade, `docker compose down` then `up`, or `--force-recreate` deleted the key files, and the server then refused to start with `kek_unresolvable`. Those composes and the `/test` upgrade-test compose now mount a `server-certs` volume on `/etc/yuzu/certs`. The Compose Wizard's Default and Plaintext output always mount a volume there too (its "Persist generated certs" option is now always on): the named `server-certs` volume when named volumes are on or Postgres is external, otherwise an anonymous volume that is discarded together with the database's anonymous volume. The wizard's Operator-certs mode still mounts `./certs` read-only, so the server cannot write its KEK and stops at first boot with `provider_failure` (#5420). The path does not move, so CA key paths recorded in Postgres stay valid. The chiselled server image now creates `/etc/yuzu/certs` owned by the server user, and the demo stack adds a one-shot `server-certs-init` service so it also works on older chiselled images. The upgrade guide gives a checked copy-out recipe, the diagnostics to run before anything destructive (a lost volume line, the wrong file owner, or keys left on a dangling anonymous volume give the same error), a rollback that keeps the keys, and what can still be saved if the files are already gone. The `/test` upgrade gate also recreates the upgraded server and checks that it comes back on the same keys. (#5370)
