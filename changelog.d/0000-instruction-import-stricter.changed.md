- **Breaking: the instruction import is stricter, on the legacy `POST /api/instructions/import` as well as the new v1 twin (#2146).** A field of the wrong JSON type is refused `400` naming the field, which now includes `gather_ttl_seconds` and `response_ttl_days` given as a float (`300.0`) or `null`; both are range-checked (1 to 86400 and 1 to 3650), where a larger integer was previously narrowed and stored as a negative number. The operator import also bounds `name` (128 characters), `version` (64), `description` (16384 bytes) and `instruction_set_id` (128), and so do the v1 and MCP YAML routes for the YAML `description`, requires a non-empty `plugin` and `action` to be at most 128 characters of `A-Za-z0-9._-`, and lowercases `action`. The boot-time seed shares the type and range checks but not the name, version, set id and identifier bounds. The `updated_at` of a definition is now a monotonic version token rather than exactly the epoch second of the last write (the `instruction_store` schema moves to v4 with one additive column), a present empty `plugin` is refused on create and update over REST v1 and MCP, and a `DELETE /api/v1/instructions/{id}` of a definition that a schedule, a live workflow or a policy fragment still names is refused `409`. No create path accepts `.` or `..` as a new definition id. A NUL byte in `parameter_schema`, `result_schema`, `concurrency_mode`, `visualization_spec` or `response_templates_spec` is refused `400` naming the field on create, import and update.
