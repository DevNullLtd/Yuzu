- **Breaking: approving or rejecting an approval request now requires an enrolled MFA factor with a fresh proof, in every `--mfa-enforcement` mode (#6079).** `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject` and the dashboard Approvals page now run the central step-up check first and then a stricter approver rule of their own, because the central check passes an account that has no factor. A local account must have an enrolled TOTP factor and a proof no older than the approver window that does not predate its current enrolment (disabling MFA and enrolling again invalidates older proofs). An OIDC session qualifies when the identity provider issued an ID token with an MFA-method `amr` within the window; the MFA itself may predate the token, because the provider can reuse its own session, and no second factor is presented again at approval time. A SAML session is refused (#4935). The approver window is `min(--mfa-step-up-window-secs, 300)` seconds (a hard ceiling, measured on the database clock against the session's stored proof with no suspend or skew allowance, so a paused host cannot extend it), and 300 when that setting is `0` or negative, so `--mfa-step-up-window-secs=0` no longer lowers approval assurance and no longer admits a SAML approver. Break-glass accounts get no exemption and the reviewer must still differ from the submitter.

  A refused caller gets `403` with message `approver_assurance_required:<reason>`, but not every reason is typed in every configuration. `mfa_not_enrolled` is typed at every window. With the step-up window above `0` the central check answers first for a stale proof, a SAML session, an engine principal and a deleted or deactivated account, with its generic `401` or `403` and an `mfa.step_up.required` row with `stage=pre_authz`; so `saml_mfa_unsupported` is typed only with `--mfa-step-up-window-secs=0`, `account_unavailable` only with that setting or when the account is removed between the central check's read and the approver rule's, and `mfa_proof_missing` is typed at the default window only when `--mfa-enforcement` does not protect the role (under `required`, or `admin-only` for an administrator, an OIDC session with no MFA `amr` gets the central `401` step-up). The ticket-specific `approver_assurance:mfa_proof_stale` row appears only for a proof that predates the enrolment or that falls between the central whole-second test and the approver millisecond ceiling. When the approver rule's own read fails (an unreadable stored session proof, or an MFA-store fault at its own read) the answer is `503` with `retry_after_ms`, counted as `yuzu_auth_secret_unavailable_total{route="approval"}` (the stored-proof case also increments `yuzu_auth_session_store_degrade_total{op="validate"}`); with step-up on, an unreadable local MFA store is answered first by the central check, `503` without `retry_after_ms`, counted as `route="mfa_stepup"` and `yuzu_auth_mfa_step_up_gate_total{outcome="unavailable"}`. A path id that is empty, longer than 128 characters or holds anything other than letters, digits, `_` and `-` is now refused before the store is asked, with `400` and an A4 envelope (`error` is an object, message `approval not found`) and one `denied` audit row with `target_id=invalid-id` and `detail=invalid_approval_id`; an unknown id that passes that check still gets the store's older `{"error":"..."}` string shape, so a client that parses the body should handle both. The `user=` value in the `detail` of every `mfa.step_up.required` audit row, whether written by the central step-up check or from inside a handler, is now neutralised: a space, `=`, `,`, DEL or control byte in the account name is written as `_`, so a SIEM rule that matches that field on a name containing those characters must match the neutralised form.

  **Action required before upgrading:** on a default install (RBAC enforcement off, `--mfa-enforcement=optional`) the only approvers are administrators and none is enrolled, so every approver is refused until it enrols itself in Settings; another administrator cannot enrol it. Once RBAC enforcement is on, the seeded `Operator` role holds `Approval:Approve` and a non-admin cannot enrol itself under `optional` or `admin-only`, so every non-admin approver is refused until an administrator enrols it, through an enrolment sign-in window or by promoting the account long enough to enrol and then demoting it; both are in `docs/ops-runbooks/auth-db-recovery.md`, "Enrolling a non-admin approver". With RBAC enforcement off, a non-admin is refused `403` "admin role required" before the MFA gate. A SAML-only deployment has no approver path (#6098). **Mixed versions:** the control is active only while every replica serving `/api/approvals/*` runs the new version. Rolling those replicas first shortens the exposure window; the gap closes only when approval traffic reaches upgraded replicas only (pin or drain approvals), and stop-all, upgrade, start-all is the default recommendation. Running more than one server replica is unsupported today (the safe-to-scale gate). Rolling back is a security-policy downgrade; tickets decided earlier gain no retroactive assurance, and the `attempted` and `success` audit rows written from this version carry `detail` `approver_assurance:enrolled_fresh_mfa` as the cutover marker; endpoint agents need no change. Two follow-ups are named and not part of this change: real OIDC re-authentication at approval time (`auth_time` with `max_age`), and self-service MFA enrolment for non-admin approvers. See `docs/user-manual/upgrading.md` and `docs/user-manual/instructions.md` "Who can approve".
- **`yuzu-server --mfa-reset` and the Settings "Disable two-factor" now end the account's sessions (#6079).** `--mfa-reset` deletes the account's durable sessions after clearing the factor and records `sessions_ended=<n>` in its audit row. When it cannot end them it now exits non-zero with `error: MFA cleared but the account's sessions were not ended` and records `result=partial` with `sessions_ended=failed`; automation that runs `--mfa-reset` and treats exit `0` as success must handle that and end the sessions by hand (`DELETE /api/v1/sessions?username=<name>`). Disabling MFA in Settings ends every session of the account, the caller's included, so the user is signed out and signs in again, unless the account had no verified factor (cancelling an unfinished enrolment ends none). Neither path ends API tokens. The clear and the session delete are two separate commits: if the Settings session delete fails the audit row is `mfa.disabled` `partial` and an administrator must end the sessions, since the page has no retry control; if the clear itself fails the sessions are still ended, because the clear may have committed with its acknowledgement lost, and the page says the state is unknown when they could not be ended either.
- **A factor clear is now audited in two phases (#6079).** Both `yuzu-server --mfa-reset` (`mfa.reset.breakglass`) and the Settings disable (`mfa.disabled`) write a `result=attempted` intent row before they touch the factor, and the row fails closed: if the audit store does not accept it, `--mfa-reset` prints `error: audit store did not accept the intent row; nothing was changed` and exits `1`, and Settings answers `503` with `Sec-Audit-Failed: true`, with nothing cleared. The outcome row follows (`success` or `ok`, `partial`, or `error` when the clear itself failed and its state is unknown). An `attempted` row with no outcome row marks a clear that was requested but whose result is unknown, for example because the process died after the clear; `docs/ops-runbooks/auth-db-recovery.md` has a query that lists them. A SIEM rule that counts these rows once per clear now sees two, ordered by the audit `id`.
