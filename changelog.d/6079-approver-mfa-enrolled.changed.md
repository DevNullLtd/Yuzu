- **Breaking: approving or rejecting an approval request now requires an enrolled MFA factor with a fresh proof, in every `--mfa-enforcement` mode (#6079).** `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject` and the dashboard Approvals page no longer use the generic step-up gate, which passed an account that had no factor to ask for. A local account must have an enrolled TOTP factor and a proof no older than the approver window that does not predate its current enrolment (disabling MFA and enrolling again invalidates older proofs); an OIDC session needs the identity provider to have asserted an MFA-method `amr` on an ID token issued within the window, which means recent provider-side MFA and not a second factor presented again at approval time; a SAML session is refused (#4935). A refused caller gets `403` with message `approver_assurance_required:<reason>` where `<reason>` is `mfa_not_enrolled`, `mfa_proof_missing`, `account_unavailable` (the session's account was deleted or deactivated) or `saml_mfa_unsupported` (a stale proof is the usual step-up `401`, audited with `approver_assurance:mfa_proof_stale`), and an unreadable MFA store, or an unreadable stored session proof, answers `503` with `retry_after_ms` and increments `yuzu_auth_secret_unavailable_total{route="approval"}` (the stored-proof case also increments `yuzu_auth_session_store_degrade_total{op="validate"}`). A path id that is empty, longer than 128 characters or holds anything other than letters, digits, `_` and `-` is now refused before the store is asked, with `400` and an A4 envelope (`error` is an object, message `approval not found`) and one `denied` audit row with `target_id=invalid-id` and `detail=invalid_approval_id`; an unknown id that passes that check still gets the store's older `{"error":"..."}` string shape, so a client that parses the body should handle both. The `user=` value in the `detail` of the `mfa.step_up.required` audit row, written by the shared step-up challenge that every step-up-gated endpoint uses, is now neutralised: a space, `=`, `,` or control byte in the account name is written as `_`, so a SIEM rule that matches that field on a name containing those characters must match the neutralised form. The approver window is `min(--mfa-step-up-window-secs, 300)` seconds (a hard ceiling, measured on the database clock against the session's stored proof with no suspend or skew allowance, so a paused host cannot extend it), and 300 when that setting is `0` or negative, so `--mfa-step-up-window-secs=0` no longer lowers approval assurance and no longer admits a SAML approver. Break-glass accounts get no exemption and the reviewer must still differ from the submitter. **Action required before upgrading:** a non-admin cannot enrol itself under `--mfa-enforcement=optional` or `admin-only`, and the seeded `Operator` role holds `Approval:Approve`, so, with RBAC enforcement on, every non-admin approver (and any un-enrolled administrator) is refused until an administrator enrols it (with enforcement off, the shipped default, a non-admin is refused `403` "admin role required" before the MFA gate), through an enrolment sign-in window or by promoting the account long enough to enrol and then demoting it; both are in `docs/ops-runbooks/auth-db-recovery.md`, "Enrolling a non-admin approver". **Mixed versions:** the control is active only while every replica serving `/api/approvals/*` runs the new version, so roll those replicas first or drain approvals; rolling back is a security-policy downgrade; tickets decided earlier gain no retroactive assurance, and the `attempted` and `success` audit rows written from this version carry `detail` `approver_assurance:enrolled_fresh_mfa` as the cutover marker; endpoint agents need no change. Two follow-ups are named and not part of this change: real OIDC re-authentication at approval time (`auth_time` with `max_age`), and self-service MFA enrolment for non-admin approvers (`yuzu-server --mfa-reset` now ends the account's sessions and records `sessions_ended` in its audit row, and disabling MFA in Settings ends the account's other sessions). See `docs/user-manual/upgrading.md` and `docs/user-manual/instructions.md` "Who can approve".
