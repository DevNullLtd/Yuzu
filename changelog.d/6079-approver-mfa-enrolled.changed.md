- **Breaking: approving or rejecting an approval request now requires an enrolled MFA factor with a fresh proof, in every `--mfa-enforcement` mode (#6079).** `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject` and the dashboard Approvals page now run the central step-up check first and then a stricter approver rule of their own, because the central check passes an account that has no factor. A local account must have an enrolled TOTP factor and a proof no older than the approver window that does not predate its current enrolment (disabling MFA and enrolling again invalidates older proofs); an OIDC session needs the identity provider to have asserted an MFA-method `amr` on an ID token issued within the window, which means recent provider-side MFA and not a second factor presented again at approval time; a SAML session is refused (#4935). Once the central check has passed (or with the window at `0`), a refused caller gets `403` with message `approver_assurance_required:<reason>` where `<reason>` is `mfa_not_enrolled`, `mfa_proof_missing`, `account_unavailable` (the session's account was deleted or deactivated) or `saml_mfa_unsupported`; with step-up on, a stale proof, a SAML session or an engine principal is normally answered first by the central check with its generic `401` or `403` and an `mfa.step_up.required` row with `stage=pre_authz` (the typed `saml_mfa_unsupported` appears only with `--mfa-step-up-window-secs=0`, an OIDC session with no MFA `amr` under `required`, or `admin-only` for an administrator, gets the central `401` step-up, and the ticket-specific `approver_assurance:mfa_proof_stale` row appears only for a proof that predates the enrolment or that falls between the central whole-second test and the approver millisecond ceiling). When the approver rule's own read fails (an unreadable stored session proof, or an MFA-store fault at its own read) the answer is `503` with `retry_after_ms`, counted as `yuzu_auth_secret_unavailable_total{route="approval"}` (the stored-proof case also increments `yuzu_auth_session_store_degrade_total{op="validate"}`); with step-up on, an unreadable local MFA store is answered first by the central check, `503` without `retry_after_ms`, counted as `route="mfa_stepup"` and `yuzu_auth_mfa_step_up_gate_total{outcome="unavailable"}`. A path id that is empty, longer than 128 characters or holds anything other than letters, digits, `_` and `-` is now refused before the store is asked, with `400` and an A4 envelope (`error` is an object, message `approval not found`) and one `denied` audit row with `target_id=invalid-id` and `detail=invalid_approval_id`; an unknown id that passes that check still gets the store's older `{"error":"..."}` string shape, so a client that parses the body should handle both. The `user=` value in the `detail` of every `mfa.step_up.required` audit row, whether written by the central step-up check or from inside a handler, is now neutralised: a space, `=`, `,`, DEL or control byte in the account name is written as `_`, so a SIEM rule that matches that field on a name containing those characters must match the neutralised form. The approver window is `min(--mfa-step-up-window-secs, 300)` seconds (a hard ceiling, measured on the database clock against the session's stored proof with no suspend or skew allowance, so a paused host cannot extend it), and 300 when that setting is `0` or negative, so `--mfa-step-up-window-secs=0` no longer lowers approval assurance and no longer admits a SAML approver. Break-glass accounts get no exemption and the reviewer must still differ from the submitter. **Action required before upgrading:** a non-admin cannot enrol itself under `--mfa-enforcement=optional` or `admin-only`, and the seeded `Operator` role holds `Approval:Approve`, so, with RBAC enforcement on, every non-admin approver (and any un-enrolled administrator) is refused until an administrator enrols it (with enforcement off, the shipped default, a non-admin is refused `403` "admin role required" before the MFA gate), through an enrolment sign-in window or by promoting the account long enough to enrol and then demoting it; both are in `docs/ops-runbooks/auth-db-recovery.md`, "Enrolling a non-admin approver". **Mixed versions:** the control is active only while every replica serving `/api/approvals/*` runs the new version, so roll those replicas first or drain approvals; rolling back is a security-policy downgrade; tickets decided earlier gain no retroactive assurance, and the `attempted` and `success` audit rows written from this version carry `detail` `approver_assurance:enrolled_fresh_mfa` as the cutover marker; endpoint agents need no change. Two follow-ups are named and not part of this change: real OIDC re-authentication at approval time (`auth_time` with `max_age`), and self-service MFA enrolment for non-admin approvers (`yuzu-server --mfa-reset` now ends the account's sessions and records `sessions_ended` in its audit row, exiting non-zero and recording `sessions_ended=failed` when the sessions could not be ended; disabling MFA in Settings ends every session of the account, the caller's included, unless the account had no verified factor (cancelling an unfinished enrolment ends none); neither ends API tokens, the clear and the session delete are two separate commits, and if the Settings session delete fails the audit row is `mfa.disabled` `partial` and an administrator must end the sessions, since the page has no retry control; if the clear itself fails the sessions are still ended and the page says the state is unknown when they could not be ended either; the Settings audit write is best effort). See `docs/user-manual/upgrading.md` and `docs/user-manual/instructions.md` "Who can approve".
