- **Breaking: approving or rejecting an approval request now requires an enrolled MFA factor with a fresh proof, in every `--mfa-enforcement` mode (#6079).** `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject` and the dashboard Approvals page no longer use the generic step-up gate, which passed an account that had no factor to ask for. A local account must have an enrolled TOTP factor and a proof no older than the approver window that does not predate its current enrolment (disabling MFA and enrolling again invalidates older proofs); an OIDC session needs the identity provider to have asserted an MFA-method `amr` on an ID token issued within the window, which means recent provider-side MFA and not a second factor presented again at approval time; a SAML session is refused (#4935). A refused caller gets `403` with message `approver_assurance_required:<reason>` where `<reason>` is `mfa_not_enrolled`, `mfa_proof_missing` or `saml_mfa_unsupported` (a stale proof is the usual step-up `401`, audited with `approver_assurance:mfa_proof_stale`), and an unreadable MFA store answers `503` with `retry_after_ms` and increments `yuzu_auth_secret_unavailable_total{route="approval"}`. The approver window is `min(--mfa-step-up-window-secs, 300)` seconds, and 300 when that setting is `0` or negative, so `--mfa-step-up-window-secs=0` no longer lowers approval assurance and no longer admits a SAML approver. Break-glass accounts get no exemption and the reviewer must still differ from the submitter. **Action required before upgrading:** a non-admin cannot enrol itself under `--mfa-enforcement=optional` or `admin-only`, and the seeded `Operator` role holds `Approval:Approve`, so every non-admin approver (and any un-enrolled administrator) is refused until an administrator enrols it, through an enrolment sign-in window or by promoting the account long enough to enrol and then demoting it; both are in `docs/ops-runbooks/auth-db-recovery.md`, "Enrolling a non-admin approver". **Mixed versions:** the control is active only while every replica serving `/api/approvals/*` runs the new version, so roll those replicas first or drain approvals; rolling back is a security-policy downgrade; tickets decided earlier gain no retroactive assurance; endpoint agents need no change. Two follow-ups are named and not part of this change: real OIDC re-authentication at approval time (`auth_time` with `max_age`), and self-service MFA enrolment for non-admin approvers (ending an account's existing sessions when its MFA is disabled or reset is a further follow-up). See `docs/user-manual/upgrading.md` and `docs/user-manual/instructions.md` "Who can approve".
