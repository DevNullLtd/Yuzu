- **A supported, audited way to raise the Guardian policy generation.** `POST /api/v1/guaranteed-state/policy-generation/raise` and the MCP tool `raise_guardian_policy_generation` set the server's policy generation to a target from `1` to `9007199254740991`, in one atomic step that never lowers it, so a server whose counter fell below what its agents hold (a restored database, a rebuilt Postgres) can recover without editing the database by hand. The caller must be a durable administrator and must send `acknowledge_rule_set_replaced: true`, because the heartbeat reconcile then converges every agent behind the new value to the rule set the server holds at that moment. The REST route needs MFA step-up for a cookie session and refuses service-scoped and MCP-tier bearer tokens; the MCP tool needs the supervised tier and an approval. The response reports `previous_generation`, `generation`, `raised`, `rules`, `deployed_baselines` and `ceiling`; a target at or below the current value changes nothing and returns `raised: false`. Each call writes an `attempted` audit row before anything changes and an outcome row after, both under `guaranteed_state.policy_generation.raise`, and is counted in `yuzu_server_guardian_policy_generation_raise_total{transport,result}`. The route has its own 1 KiB pre-auth body cap (`guardian_policy_generation`). The manual database statement in "Restoring the policy generation" is now a last resort.
