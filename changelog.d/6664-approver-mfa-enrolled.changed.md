- **Breaking: approving or rejecting an approval request now requires an enrolled MFA factor with a fresh proof, in every `--mfa-enforcement` mode (#6079).**

  **Action required before upgrading** (the full checklist is in `docs/user-manual/upgrading.md`):

  - On a default install every approver is refused until it enrols itself; another administrator cannot enrol it.
  - Administrators enrol in Settings, Security and sign-in, Two-factor sign-in.
  - Non-admin approvers need the runbook path, `docs/ops-runbooks/auth-db-recovery.md` "Enrolling a non-admin approver".
  - A SAML-only deployment has no approver path (#6098).
  - Mixed-version running and rollback are security-policy downgrades; see the upgrade notes.

  `POST /api/approvals/{id}/approve`, `POST /api/approvals/{id}/reject` and the dashboard Approvals page now run the central step-up check first and then a stricter approver rule of their own, because the central check passes an account that has no factor. A local account must have an enrolled TOTP factor and a proof no older than the approver window that does not predate its current enrolment. An OIDC session qualifies when the identity provider issued an ID token with an MFA-method `amr` within the window; no second factor is presented again at approval time. A SAML session is refused (#4935). The approver window is `min(--mfa-step-up-window-secs, 300)` seconds, and 300 when that setting is `0` or negative, measured on the database clock with no suspend or skew allowance, so `--mfa-step-up-window-secs=0` no longer lowers approval assurance and no longer admits a SAML approver. Break-glass accounts get no exemption and the reviewer must still differ from the submitter. The `attempted` and `success` audit rows of a decision carry `detail` `approver_assurance:enrolled_fresh_mfa` as the cutover marker.

  A refused caller gets `403` with message `approver_assurance_required:<reason>`. `mfa_not_enrolled` is typed at every window; the other reasons are typed only in some configurations, because with the step-up window above `0` the central check answers first with its generic `401` or `403`. The full matrix is in `docs/user-manual/authentication.md`, "Approver MFA requirement".

- **Approver refusal answers and audit detail (#6079).**

  When the approver rule's own read fails (an unreadable stored session proof, or an MFA-store fault at its own read) the answer is `503` with `retry_after_ms` 5000, counted as `yuzu_auth_secret_unavailable_total{route="approval"}`. With step-up on, an unreadable local MFA store is answered first by the central check: `503` with no `retry_after_ms` key, counted as `route="mfa_stepup"` and `yuzu_auth_mfa_step_up_gate_total{outcome="unavailable"}`.

  An OIDC approver whose stored MFA proof is dated after the database clock (the replica that took the sign-in ran ahead of the database clock) is refused `503` with `retry_after_ms` null and audit `detail` `approver_assurance:mfa_proof_clock_skew`, and is not counted in `route="approval"`; it needs a clock-synchronisation fix, not a retry. It is reached only when the central check does not answer first (default optional enforcement, `admin-only` for a non-administrator, or step-up window `0`); afterwards the approver gets `403` `mfa_proof_missing`, whose remediation always ends by asking the administrator to check clock synchronisation.

  A path id that is empty, longer than 128 characters or holds anything other than letters, digits, `_` and `-` is refused before the store is asked, with `400`, an A4 envelope (message `approval not found`) and one `denied` row (`target_id=invalid-id`, `detail=invalid_approval_id`). An unknown id that passes that check still gets the store's older `{"error":"..."}` string shape, so a client that parses the body should handle both.

  The `user=` value in the `detail` of every `mfa.step_up.required` audit row is now neutralised: a space, `=`, `,`, DEL or control byte in the account name is written as `_`, so a SIEM rule that matches that field must match the neutralised form.

  The dashboard approve dialog and Approvals tab now show the A4 message and remediation of a `503` together to the approver instead of a generic message.

- **`yuzu-server --mfa-reset` and the Settings "Disable two-factor" now end the account's sessions (#6079).** `--mfa-reset` deletes the account's durable sessions after clearing the factor and records `sessions_ended=<n>` in its audit row. When it cannot end them it exits non-zero with `error: MFA cleared but the account's sessions were not ended` and records `result=partial` with `sessions_ended=failed`; automation that treats exit `0` as success must handle that and end the sessions by hand (`DELETE /api/v1/sessions?username=<name>`). Disabling MFA in Settings ends every session of the account, the caller's included, unless the account had no verified factor (cancelling an unfinished enrolment ends none). Neither path ends API tokens. The clear and the session delete are two separate commits: if the Settings session delete fails the audit row is `mfa.disabled` `partial` and an administrator must end the sessions, since the page has no retry control; if the Settings clear itself fails the sessions are still ended, because the clear may have committed with its acknowledgement lost. The CLI differs: after a failed clear it ends no session and exits `1`, so re-run `--mfa-reset` (it clears again and ends the account's sessions without an admin session) or, with an administrator session, check `auth.users.mfa_enrolled_at` and end the sessions by hand if it is null.
- **A factor clear is now audited in two phases (#6079).** Both `yuzu-server --mfa-reset` (`mfa.reset.breakglass`) and the Settings disable (`mfa.disabled`) write a `result=attempted` intent row before they touch the factor, and the row fails closed: if the audit store does not accept it, `--mfa-reset` prints `error: audit store did not accept the intent row; nothing was changed` and exits `1`, and Settings answers `503` with `Sec-Audit-Failed: true` and `Retry-After: 5` (the message "Audit store unavailable; MFA was not changed." is shown as a toast on both Settings pages and in the Two-factor panel of Security and sign-in), with nothing cleared. The outcome row follows (`success` or `ok`, `partial`, or `error` when the clear itself failed and its state is unknown). An `attempted` row with no outcome row marks a clear that was requested but whose result is unknown; `docs/ops-runbooks/auth-db-recovery.md` has a query that lists them and a second query for outcome rows that ended `error` or `partial`. A SIEM rule that counts these rows once per clear now sees two, ordered by the audit `id`, and a failure rule written as `result <> 'success'` must exclude `attempted` and `detail LIKE 'blocked:%'` rows (key it on `result IN ('partial','error')`).
