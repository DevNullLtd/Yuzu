- **A File spark watch now notices a renamed or replaced parent directory instead of staying silently deaf (Windows, #5719 item 5).** The watch held a handle that followed the renamed directory, so it kept reporting Healthy and never saw a change at the watched path. An idle watch now re-opens its directory path every 5 s and compares the directory identity with the one its handle was opened on; a different directory, or a path that names nothing, reports the watch faulted (`file watch parent directory renamed or replaced`) and re-discovers the path. Detection is sampled: a renamed or replaced parent directory is noticed at the next 5 s sample (nothing is promised between samples), verified on local NTFS only. The watch then stays faulted until its retry: on the ordinary drain route the first retry is 30 s and doubles on repeated failure, up to 300 s; if a pass throws while the lost path drains, recovery uses a 50 ms backoff instead (still bounded by the 30 s admission cap). A watch whose check cannot decide 3 checks in a row is also reported faulted (`file watch parent directory unverifiable`). Consecutive losses with no successful check between them back off from 30 s to the 300 s cap, and due checks wait for a free verification slot (least recently checked first; a wait of more than 3 intervals is counted and warned once) instead of being refused and retried every 50 ms. Not covered: an ancestor shelter whose own parent is renamed, filesystems that give no file id (reported on one FAT32 volume to go undetected), and detection between samples. No File spark is armed in production today (`prefer_spark_` is false), so this is visible only on rig-flipped agents.
