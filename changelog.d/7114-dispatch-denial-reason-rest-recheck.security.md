- **A dispatch the server refuses for authorization reasons is now reported and audited as that refusal, and the audit-first REST dispatch routes listed below decide their permission again after their writes.** The Echo dashboard re-enable and purge actions used to report a command refused at the dispatch chokepoint (for example `approval_required` for a non-admin operator re-enabling a source) as `agent_not_connected`, in the audit row, the response and the `yuzu_echo_source_reenable_total` / `yuzu_echo_source_purge_total` counters. They now answer `403` (or `500` when the server's own command is not in the catalogue), audit `dispatch_denied reason=<token>`, and count the refusal under its own `result` value. The dashboard execute console, the Echo SQL console and the Echo fleet scan answer `Not permitted: <token>` (and audit `reason=dispatch_denied`) instead of `No agents connected`. `POST /api/v1/commands` and `POST /api/v1/instructions/{id}/execute` report the same refusal as `403` with reason `dispatch_denied`, the MCP tool `execute_instruction_definition` and the workflow surfaces as status `dispatch_denied`, instead of `no_agents_reached`. `POST /api/v1/commands`, the instruction-execute twins, `POST /api/v1/echo/retention-paused/purge`, `POST /api/v1/dex/devices/{id}/live` and `POST /api/v1/hardware/{id}/sync` write a row before they dispatch; they now check the caller's permission again after their last own write (the audit row, and the execution row where one is created) and before the dispatch is built; `POST /api/v1/commands`, `POST /api/v1/dex/devices/{id}/live`, the REST instruction twin and the MCP tool `execute_instruction_definition` also resolve the credentials again and derive the dispatched caller from that resolution (a role demoted during the writes is seen), and the hardware sync route repeats only its per-device gate (its dispatch is the server's own). A permission withdrawn in that window (an expired elevation, a revoked role, and on the instruction-execute twins the administrator standing a `role-gated` definition requires) now sends nothing, closes the row (a `failure` audit row `permission_revoked`, and the execution row cancelled) and answers `403` (MCP: permission denied), where before the command was sent under the permission held when the request arrived; on `POST /api/v1/commands` and the instruction-execute twins (REST and MCP) a recheck that itself throws (a store fault) is treated the same way, so the rows it follows are closed. `POST /api/v1/dex/devices/{id}/live` also reports a command the dispatch chokepoint refuses as `403` (or `500` for a server catalogue fault) with the audit detail `dispatch_denied reason=<token>`, instead of a retryable `503` device offline. The dispatch chokepoint's own provenance-record write, between its authorization and the send, is not decided again by these surfaces; it is a known limit of the dispatch chokepoint. The `kind` label of `yuzu_server_live_requests_total` is now only `uptime`, `processes` or `unknown`. Audit trail: see the `echo.source.reenable`, `echo.source.purge` and result-vocabulary entries in the audit log reference.
