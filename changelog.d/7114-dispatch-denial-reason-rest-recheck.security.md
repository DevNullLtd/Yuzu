- **A dispatch the server refuses for authorization reasons is now reported and audited as that refusal, and the REST dispatch surfaces decide their permission again after their audit-first row.** The Echo dashboard re-enable and purge actions used to report a command refused at the dispatch chokepoint (for example `approval_required` for a non-admin operator re-enabling a source) as `agent_not_connected`, in the audit row, the response and the `yuzu_echo_source_reenable_total` / `yuzu_echo_source_purge_total` counters. They now answer `403` (or `500` when the server's own command is not in the catalogue), audit `dispatch_denied reason=<token>`, and count the refusal under its own `result` value. `POST /api/v1/commands` and `POST /api/v1/instructions/{id}/execute` report the same refusal as `403` with reason `dispatch_denied`, and the MCP tool `execute_instruction_definition` as status `dispatch_denied`, instead of `no_agents_reached`. The stored row of `POST /api/v1/commands`, the instruction-execute twins and `POST /api/v1/echo/retention-paused/purge` is written before dispatch; they now check the caller's permission again after it, and re-derive the caller from the current grants and visible set. A permission withdrawn while the row was being written (an expired elevation, a revoked role) now dispatches nothing and writes a `failure` row `permission_revoked`, answered `403` (MCP: permission denied), where before the command was sent under the permission held when the request arrived. Audit trail: see the `echo.source.reenable`, `echo.source.purge` and result-vocabulary entries in the audit log reference.
