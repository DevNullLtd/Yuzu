- **Breaking — a dispatch the server refuses for authorization reasons is reported and audited as that refusal on the surfaces named here, instead of as "no agents connected" (#7114).** The Echo dashboard re-enable and purge actions used to report a command refused at the dispatch chokepoint (for example `approval_required` for a non-admin operator re-enabling a source) as `agent_not_connected`, in the audit row, the response and the `yuzu_echo_source_reenable_total` / `yuzu_echo_source_purge_total` counters. They now answer `403` (or `500` when the server's own command is not in the catalogue), audit `dispatch_denied reason=<token>`, and count the refusal under its own `result` value. The dashboard execute console, the Echo SQL console and the Echo fleet scan answer `Not permitted: <token>` (and audit `reason=dispatch_denied`) instead of `No agents connected`. `POST /api/v1/commands` and `POST /api/v1/instructions/{id}/execute` report the same refusal as `403` with reason `dispatch_denied`, `POST /api/v1/dex/devices/{id}/live` as `403` (or `500` for a server catalogue fault) with the audit detail `dispatch_denied reason=<token>` instead of a retryable `503` device offline, and the MCP tool `execute_instruction_definition` and the workflow surfaces as status `dispatch_denied` (a workflow step whose zero-reach cause is permanent is no longer retried), instead of `no_agents_reached`. Other dispatch surfaces (`POST /api/command`, MCP `execute_instruction`, the legacy `POST /api/instructions/{id}/execute` and `POST /api/workflows/{id}/execute`, the Echo capture-source and DEX device fragments, the device page's live-info fragments, the result-set producers) still report such a refusal as no agents reached. The `kind` label of `yuzu_server_live_requests_total` is now only `uptime`, `processes` or `unknown`. Audit trail: see the `echo.source.reenable`, `echo.source.purge` and result-vocabulary entries in the audit log reference; migration notes in the upgrading guide.
- **Breaking — the audit-first dispatch routes decide the caller's permission again after their writes, and a permission withdrawn in that window sends nothing (#7110).** `POST /api/v1/commands`, the instruction-execute twins (REST `POST /api/v1/instructions/{id}/execute` and MCP `execute_instruction_definition`), `POST /api/v1/echo/retention-paused/purge`, `POST /api/v1/dex/devices/{id}/live` and `POST /api/v1/hardware/{id}/sync` write a row before they dispatch; they now check the caller's permission again after their last own write (the audit row, and the execution row where one is created) and before the dispatch is built. `POST /api/v1/commands`, `POST /api/v1/echo/retention-paused/purge`, `POST /api/v1/dex/devices/{id}/live`, the REST instruction twin and the MCP tool also resolve the credentials again and derive the dispatched caller from that resolution (a role demoted during the writes is seen); the hardware sync route repeats only its per-device gate (its dispatch is the server's own). The legacy `POST /api/instructions/{id}/execute` decides its route gate and the definition's approval mode again on the caller it derives after its execution row. A permission withdrawn in that window (an expired elevation, a revoked role, and on the instruction-execute routes the administrator standing a `role-gated` definition requires) now sends nothing, closes the row (a `failure` audit row `permission_revoked`, `denied` on the legacy route, and the execution row cancelled) and answers `403` (MCP: permission denied), where before the command was sent under the permission held when the request arrived; on `POST /api/v1/commands`, the instruction-execute twins and the legacy `POST /api/instructions/{id}/execute` a recheck that itself throws (a store fault) is treated the same way (`gate=exception` on the row), so the rows it follows are closed. On the purge, DEX live and hardware sync routes a lost `failure` row is flagged `Sec-Audit-Failed: true` on the `403`.
- **Not decided again after their writes:** `POST /api/command` and MCP `execute_instruction` (one permission decision, before their writes), the fleet-wide hardware sync (a server-run job) and each step of a workflow run (run as the caller admitted at entry). The dispatch chokepoint's own provenance-record write, between its authorization and the send, is not decided again by any of these surfaces; it is a known limit of the dispatch chokepoint. On the purge, DEX live and hardware sync routes the recheck has no catch: a store fault inside it answers a generic `500` and leaves the `requested` row without an outcome row.
