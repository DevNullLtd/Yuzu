- **The agent now stamps the Guardian events that feed per-rule status with an ordering pair, (`boot_epoch`, `emit_seq`), so a server can order verdicts independently of timestamp skew; the epoch still derives from the agent clock at boot, and the pair is agent-asserted and not authenticated.** `GuaranteedStateEvent` gains `boot_epoch` and `emit_seq` (fields 24 and 25), assigned when the agent decides the event's queue order, on both the legacy and the Spark emit paths. `boot_epoch` is claimed once at agent boot from a persisted counter and the boot time; `emit_seq` increases within a boot. A server that compares the pair orders by it; one that does not ignores it and keeps ordering by the timestamp. Events replayed from the lifecycle journal, DEX observations, and events from an agent whose epoch claim failed carry no pair (0/0) and are ordered by the timestamp. Only one agent process per data directory claims an epoch: a second one started on the same `--data-dir` logs `instance_lock_not_held` and sends unordered events. The cases where epochs can repeat or regress are listed under Known limits in the Guardian design document, section 7.1. No operator action is needed for a routine upgrade; the procedure for recovering from a lost or regressed epoch will be described with the server change. The change is additive and wire-compatible in both directions. (#5690, #5674)
