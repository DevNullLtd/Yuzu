- **`registry` 2.1.0: per-user hive writes and a declarative `apply` with a returned undo manifest.** `set_user_value` and `delete_user_value` write or delete one value in a user's hive, resolving the profile as `get_user_value` does: through the live `HKEY_USERS\<SID>` hive when the user is logged in, otherwise through the offline `NTUSER.DAT` behind the shared hive-file guard, under the offline-hive lock, with the same typed, read-back-verified write as `set_value` and a `RegFlushKey` before the unload (a flush that fails fails the write). A hive loaded after an offline write returned is reported as a warning; the audit row names `hive=HKU` and the profile's `sid`. `apply` runs a plan of up to 256 `HKLM` `set_value` / `delete_value` / `create_key` / `delete_key` items: a dry run by default, one checked handle per distinct key, one verdict function for the dry run and the real run, refusal before any mutation of an item whose previous value this plugin could not write back or whose key path or value name a row could not spell exactly (`unsupported_old_type`, `unrepresentable_name`), and an undo manifest in the reply (the previous value of each item, the values of each deleted key) bounded by one 512 KiB budget, with `undo_complete` in the summary row; nothing is persisted on the endpoint. A plan is refused whole when two items depend on each other (`dependent_items`). Each plan item is audited as its own `registry.write` row. Three new definitions: `windows.registry.set_user_value`, `windows.registry.delete_user_value` and `windows.registry.apply`.
