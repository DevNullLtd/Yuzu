- **Breaking, fresh deployment only: the Guardian compliance census chooses its verdict by an ordering key and says when it cannot be sure (#5690).** The census row for an (agent, rule) pair used to keep the verdict with the latest whole-second timestamp text, so a clock step or two verdicts in one second could leave a stale "compliant". It now keeps the verdict with the greatest `(key, ingest_seq)`, where the key is the agent's event time limited to the server's receipt plus 300 seconds and ties break by the order the server stored the events in. A verdict that is refused, whose time is unusable or capped, or whose order disagrees with its arrival marks the row `order_uncertain`; an event whose census write fails is stored with `projection_pending` and a redelivery repairs it. Both flags appear on the per-guard agent drilldown and the per-device guards read, and `uncertain_rules` on the fleet and per-agent rollups, on REST and the MCP twins. The Guardian overview shows "Compliant, ordering uncertain" instead of "All compliant", the device Guardian tile is not shown as clean over an uncertain or pending guard, and the compliance captions no longer say "as of last check-in". Pending events are exempt from retention, `delete_rule` retires a rule's pending events in the same transaction, and the new gauge `yuzu_server_guardian_census_pending_events` counts them. `guaranteed_state_store` schema v4 adds the columns and indexes; its migration rewrites the events table under an ACCESS EXCLUSIVE lock and needs free disk of one full copy, so stop every replica first (see "Behaviour change: the Guardian compliance census orders by an event key" in `docs/user-manual/upgrading.md`). Census rows written before v4 are not backfilled, and an event with no `rule_id` is now refused at ingest instead of being stored (counted on `yuzu_server_guardian_events_rejected_total`). Projection outcomes are counted on `yuzu_server_guardian_census_projection_total`. The device-compliance read does not yet report ordering uncertainty.
