- **The gateway now sends a stream-status notice again when the server answers that it did not record it.** The server answers `NotifyStreamStatus` with `acknowledged=false` when it cannot record a session (its route store could not be read, the session is unknown, superseded or bound to another cluster); the gateway used to treat that answer as delivered, so an agent whose `CONNECTED` was refused stayed unknown to the server (an independent test: a server refusing every `CONNECTED` for 60 s left 500 of 500 agents unknown 5 minutes later). A refused notice is now held and sent again with decorrelated-jitter backoff (1 s, up to 60 s): a `CONNECTED` while the gateway holds the session, a `DISCONNECTED` for up to 120 s; a newer notice for the session cancels the resend. Refusals neither open nor reset the upstream circuit breaker, and resends use at most half of the notification lane so new notices are never held up. New metrics `yuzu_gw_upstream_notify_unacknowledged_total{event}`, `yuzu_gw_upstream_notify_unacked_keys` and `yuzu_gw_upstream_notify_unacked_ended_total{outcome}`, a new `reason="unacknowledged"` on `yuzu_gw_upstream_notify_lost_total`, the settings `notify_unacked_retry_base_ms`, `notify_unacked_retry_max_ms` and `notify_unacked_disconnected_window_ms`, and the alert `YuzuGatewayNotifyUnacknowledged` (refused notices still waiting after 10 minutes; it names the server log lines and the route-store checks to make).
