- **A full approval queue is now reported as such by the MCP approval-ticket mint instead of as a retryable store failure.** When the shared pending-approval queue (1000 rows across every principal) is full, the supervised-tier ticket mint of every approval-gated tool used to answer `-32603` "failed to create approval request" with `retry_after_ms` 5000, although only a human reviewer deciding a pending approval, or the 7-day expiry, frees a slot, so a retry loop could never succeed. It now answers `-32603` with `error.data.reason` `approval_queue_full`, `retry_after_ms` null and a remediation naming the reviewer, writes a `denied` audit row (`reason=approval_queue_full correlation_id=<id>`), and counts it on the new `yuzu_server_approval_submit_refused_total{reason}` family; `approval_submit_failed` now means only a genuine store fault and keeps `retry_after_ms` 5000. The four refusals of the mint that follow its generic unwired-approval-manager check (an unreadable pending count, the per-principal cap, a full queue and a store fault) now carry the same `reason` token and `correlation_id` in `error.data` and in their audit rows, and `audit_persisted:false` when the row was lost. That generic arm, which answers when no approval manager is wired at all (a degraded or test server; production always wires one), is not covered: it still answers `-32004` with no `reason`, no `correlation_id` in its audit row and no counter, a known gap deferred to a follow-up issue.
