- **Published container images carry current packages, `yuzu-postgres` moves to PostgreSQL 18.6, and a release refuses to push an image with a fixable CRITICAL vulnerability that its scanner can see (WP15/S9).** `yuzu-postgres` (and `yuzu-postgres-ha`, built on it) moves from 18.4 to 18.6, which carries the server security fixes released after 18.4 (there was no 18.5). Deploy it on a fresh data volume, as this release's deployment contract requires (`docs/user-manual/upgrading.md`); it stays on Debian bookworm, so a database it initialises records collation version `2.36`, and the image build fails if an update would move libc6 off glibc 2.36 or ICU off 72. The server, gateway and postgres images now upgrade their distribution packages at build time, on a fresh base digest, and a package index that cannot be fetched (an unreachable security pocket) fails the build instead of shipping an unpatched image (`apt-get update --error-on=any`; Alpine's `apk upgrade` already refused). `yuzu-postgres` keeps its PostgreSQL packages at the pinned minor, so no release build takes a PostgreSQL fix (only a base bump does); the build log names each held package that has a newer version available. Every published image, the three chisel variants and the agent bundle included, is scanned by `scripts/ci/image-vuln-gate.sh` (pinned, checksum-verified Trivy, local Docker daemon only, by image ID) before `release.yml` pushes it, and the pushed digest's layers are checked against the scanned image's before it is signed. The gate fails on a CRITICAL with a fix that `.trivyignore.yaml` does not accept (a release honours an entry only when it names one concrete file path or one package at one version, states why, expires at most 92 days out and records its approver, approval date and approving pull request; Trivy reads only a validated copy of the entries in force), on a vulnerability DB older than 72 hours or not downloaded by that run (it is pinned by registry digest, which every report records; the DB is not signed by its publisher, so an altered DB is not detected), on an image whose OS release has no advisory data in that DB (end of life, Debian testing/sid, Alpine edge), and on an image whose OS packages the scanner cannot see, unless that image is listed, with an approval and an expiry, as not covered. Four images are listed and their OS packages ship unscanned: the three chisel images and the agent bundle, which are built from chisel slices with no package database. The gate also does not see PostgreSQL itself (PGDG packages have no advisories it matches), the gateway's Erlang/OTP runtime or statically linked code. Each release carries the gate's reports for its six images (`trivy-yuzu-*.{json,txt,gate.txt}`, inside `SHA256SUMS`: Trivy version, DB digest and date, image ID, coverage, advisory check, result); the agent bundle's report is attached to the release afterwards with its own signed checksum list. A refused image's report is kept too (90-day workflow artifact). The pre-release QA scan covers all seven images and fails on the same conditions, except that it honours (and reports) an acceptance whose approval is still pending. Point-in-time counts, measured 2026-11-17 with Trivy 0.70.0 and its DB of 2026-11-17 13:00 UTC (unique CVEs, CRITICAL/HIGH, the v0.15.0 images against this build's): server 3/77 to 0/25 (no fixable left), postgres 7/71 to 4/61 (the remaining fixable ones are all in the upstream image's `gosu`, whose one CRITICAL is accepted as unreachable once its approval is recorded). No figure is given for the gateway or the chisel images: Trivy sees neither OTP nor the chisel images' packages, so its count for them says nothing. The chiselled gateway's builder moves to OTP 28.5.0.8, which grype shows clears 1 CRITICAL and 22 HIGH OTP CVEs that the v0.15.0 image carried; the Alpine gateway stays on OTP 28.5.0.2 (#6740).
