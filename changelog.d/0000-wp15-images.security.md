- **Published container images carry current packages, `yuzu-postgres` moves to PostgreSQL 18.6, and a release refuses to push an image with a fixable CRITICAL vulnerability that its scanner can see, which excludes the operating-system packages of four images (WP15/S9).** `yuzu-postgres` (and `yuzu-postgres-ha`, built on it) moves from 18.4 to 18.6, which carries the server security fixes released after 18.4 (there was no 18.5). Deploy it on a fresh data volume, as this release's deployment contract requires (`docs/user-manual/upgrading.md`); it stays on Debian bookworm, so a database it initialises records collation version `2.36`, and the image build fails if an update would move libc6 off glibc 2.36 or ICU off 72. The server, gateway and postgres images now upgrade their distribution packages at build time, on a fresh base digest, and a package index that cannot be fetched (an unreachable security pocket) fails the build instead of shipping an unpatched image (`apt-get update --error-on=any`; Alpine's `apk upgrade` already refused). `yuzu-postgres` keeps its PostgreSQL packages at the pinned minor, so no release build takes a PostgreSQL fix (only a base bump does); the build log names each held package that has a newer version available. Every published image goes through `scripts/ci/image-vuln-gate.sh` (pinned, checksum-verified Trivy, local Docker daemon only, by image ID) before `release.yml` pushes it, but for four of them, `yuzu-server-chisel`, `yuzu-gateway-chisel`, `yuzu-agent-chisel` and `yuzu-agent-bundle-chisel`, that run checks no operating-system package (below), so passing it says nothing about their OS packages; the pushed digest's layers are checked against the scanned image's before it is signed. The gate fails on a CRITICAL with a fix that `.trivyignore.yaml` does not accept (a release honours an entry only when it is scoped to one file path inside the image, with a `/`, no wildcard and not a scanner result name such as `Python`, or to one package at one version, states why, expires at most 92 days out, and carries an approver, an approval date and a pull-request reference that are not `pending`; those three fields are checked for format only, not verified against GitHub, so the control is review of the change that adds the entry; Trivy reads only a validated copy of the entries in force), on a vulnerability DB older than 72 hours or not downloaded by that run (it is pinned by registry digest, which every report records; the DB is not signed by its publisher, so an altered DB is not detected), on an image whose OS release, as Trivy identifies it, the gate cannot show that DB has advisories for (end of life, a distribution other than Debian, Ubuntu or Alpine, a pre-release or non-numeric version such as Alpine `_alpha`/`_rc`, Debian `~rc`, testing/sid or Alpine edge, or a test scan of that release that matches nothing), and on an image whose OS packages the scanner cannot see, unless that image is listed as not covered, with an expiry and approval fields that are not `pending` (checked for format only, like an acceptance's). Those four images are listed and their OS packages ship unscanned: they are built from chisel slices with no package database. The gate also does not see PostgreSQL itself (PGDG packages have no advisories it matches), the gateway's Erlang/OTP runtime or statically linked code. Each release carries the gate's reports for its six images (`trivy-yuzu-*.attempt-<N>.{json,txt,gate.txt}`, inside `SHA256SUMS`: run attempt, Trivy version, DB digest and date, image ID, coverage, advisory check, result); the agent bundle's report is attached to the release afterwards with its own signed checksum list, never replacing a completed asset (an interrupted upload is replaced), and only when it agrees with the bundle job's record of the digest that attempt pushed (or of no push), because the highest attempt on the release is not necessarily the published bundle image. Reports are named by the workflow run attempt, so when a refused job is re-run the refused attempt's report stays beside the passing one, in the workflow artifacts and, once the release is created, in the release; a scan cancelled by SIGINT or SIGTERM (a cancelled run or a job timeout, including the runner's second signal) writes a `gate: FAIL: cancelled` report, and the gate stops itself with a report when its 25-minute time budget runs out; a refusal never followed by a release is kept only as a 90-day workflow artifact. On a stable tag, `:latest` and `:X.Y` move as each image is pushed, before the GitHub Release exists (`docs/user-manual/release-verification.md`). The pre-release QA scan covers all seven images and fails on the same conditions, except that it honours (and reports) an acceptance whose approval is still pending. Point-in-time counts, measured 2026-11-17 with Trivy 0.70.0 and its DB of 2026-11-17 13:00 UTC (unique CVEs, CRITICAL/HIGH, the v0.15.0 images against this build's): server 3/77 to 0/25 (no fixable left), postgres 7/71 to 4/61 (the remaining fixable ones are all in the upstream image's `gosu`, whose one CRITICAL is accepted as unreachable once its approval is recorded). No figure is given for the gateway or the chisel images: Trivy sees neither OTP nor the chisel images' packages, so its count for them says nothing. The chiselled gateway's builder moves to OTP 28.5.0.8, which grype shows clears 1 CRITICAL and 22 HIGH OTP CVEs that the v0.15.0 image carried; the Alpine gateway stays on OTP 28.5.0.2 (#6740).
