- **New Linux-only `runtime_posture` action on the `virtualization` plugin: which container runtimes (docker, podman, containerd) are on this device, how they are configured, and which containers run with risky settings.** Off by default: with no endpoint configured the agent never opens a socket and reports only what a `stat` of the standard runtime sockets, config files and data roots shows, plus an allow-listed set of posture keys from `/etc/docker/daemon.json`. An operator opts in per host by setting `YUZU_AGENT_RUNTIME_ENDPOINT` (or `--runtime-endpoint`) to a read-only unix socket they provide in front of the runtime, in `/etc/yuzu-agent/yuzu-agent.env` or a unit drop-in; the packaged unit is unchanged and the agent never joins the `docker` group. Over that endpoint the agent sends only four fixed `GET` requests (version, info, container list, per-container inspect) under a 20 s deadline, and refuses the four default runtime sockets as an endpoint (by path and by inode) with a typed `endpoint_refused` row. Container rows carry name, image, state, privileged flag, network mode and whether a runtime socket is mounted into the container; environment, command line, labels, ports and other mounts are never read. Endpoint and runtime outcomes are typed (`unset`, `endpoint_refused`, `permission_denied`, `unreachable`, `not_http`, `ok`; `not_detected`, `detected`, `served`), and a failed read makes the result `constrained` instead of an empty success. containerd is detected by presence only. Securable `Security`, operation `Read`, no approval gate. macOS and Windows answer one `unsupported` status row. The design and the privilege change are in `docs/virtualization-runtime-posture-design.md` and `docs/agent-privilege-model.md`.
