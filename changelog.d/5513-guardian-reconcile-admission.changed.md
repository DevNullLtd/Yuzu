- **Guardian heartbeat reconcile is now admission-controlled per server replica, and a degraded tag or property store now aborts it (behaviour change).** A reconcile the replica declines to admit (its time budget is empty, its per-second admission ceiling is reached, or 256 pushes are already in flight) is shed: no push, no audit row, and the agent's 25 s slot is not consumed, so the agent retries on its next heartbeat. Sheds are counted by `yuzu_server_guardian_reconciles_total{result="shed"}`, and the new `yuzu_server_guardian_reconcile_duration_seconds` histogram plus the per-replica gauges `yuzu_server_guardian_reconcile_in_flight`, `yuzu_server_guardian_reconcile_budget_balance_ms` (negative is debt) and `yuzu_server_guardian_reconcile_claims` are the sizing and saturation inputs. Three new per-replica flags set the budget: `--guardian-reconcile-budget-ms-per-s` (default 500), `--guardian-reconcile-burst-ms` (default 1000) and `--guardian-reconcile-max-per-s` (default 1000); the defaults are provisional starting values, not derived from fleet measurement. The per-agent limit is unchanged: an agent is re-pushed at most once per 25 s, because a claim younger than 25 s is kept even when the agent reports the current generation in between. The policy generation that decides admission is read through a 2 s cache, an admitted push re-reads it fresh and sends nothing if the fresh value is not ahead of the agent, rule sets are held per generation, and scope membership is evaluated for the one agent instead of across the fleet. **Behaviour change:** if the tag or property store cannot be read while evaluating a rule's scope, the reconcile now aborts (`result="degraded"` and an `ABORTED` audit row, nothing sent) where it previously treated the agent as out of scope and pushed a narrowed rule set that disarmed the rule. This removes the reconcile path's O(fleet) cost and makes it shed-safe, but it does not by itself make the server handle 500,000 agents: per-heartbeat Postgres writes, gateway forwarding, the policy-bump fan-out (unbudgeted and synchronous), audit volume and cluster-wide (rather than per-replica) budgets remain separate follow-ups. A committed rule create, update or delete now invalidates the generation and rule-set caches on the replica that took it, whether or not its generation bump succeeded, so on the replica that took the edit, apart from the instants around the hook, a failed bump does not leave a stale rule set served to a newly reporting agent; a Baseline update, delete or deployed create, a policy-generation raise that increased the stored value, and every push the replica fans out (an explicit push included) drop them the same way; and a reconcile already running on that replica when any of these happens sends nothing (counted by the new `yuzu_server_guardian_reconcile_invalidated_total`, not as `degraded`; an `ABORTED` audit row is written) and is retried from a fresh load.
