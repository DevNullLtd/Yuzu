- **A Registry spark watch now notices a parent renamed away with the watched path re-created, and a path re-pointed to another key, when the opt-in check is enabled (Windows, #7877 item 31).** Before this change the check re-opened the registered path and, when the open succeeded, took the key as healthy without comparing it with the key the watch holds, so an administrator who renamed the parent and re-created the path left the watch reporting Healthy and deaf. Each check now also reads the held handle's canonical name (through a duplicate of the handle, taken under the sweeper's lock; the name is never logged) and compares it with the name recorded when the handle was committed, whether or not the fresh open succeeds, so a re-created path that the agent can no longer open is caught too; and it compares the fresh open's name with the held handle's. A mismatch faults the watch with `registry watch key moved from its path` or `registry watch path re-pointed to another key`, owes a resync fire, and re-opens the path on the ordinary retry (30 s, doubling to a 300 s cap); a held handle whose hive was unloaded faults with `registry watch hive unloaded`. The first compare runs only for a watch whose commit recorded a name. A name that cannot be read, or a held key that has been deleted, leaves the verdict undecided and does not fault the watch. A watch whose parent is renamed and replaced by a registry link at the old name is expected to fault once and recover at the retry, as is a watch whose ancestor is renamed by case only and an `HKCR` watch when a per-user class key appears over the machine one; the `HKCR` case was driven on a rig (2026-11-25, one fault then recovery onto the per-user key), the link-replacement and case-only cases were not observed. The check stays OFF by default and is enabled at boot with `--spark-registry-path-verify-interval` (env `YUZU_AGENT_SPARK_REGISTRY_PATH_VERIFY_INTERVAL`); the Spark detection layer is not live in production (`prefer_spark_` is false), so this is visible only on rig-flipped agents. Not covered: a parent renamed away and back inside one interval; on the 2026-11-25 Windows rig the name read through `HKCR` was measured to be the underlying hive key's canonical name (for example `\REGISTRY\USER\<SID>_Classes\...` for a per-user class key), and a registry link re-pointed to another target was driven on the rig and gave one fault followed by recovery onto the new target; the other #7877 residuals stand. The duplicate adds no Security-log events under Registry auditing alone; with the Handle Manipulation audit subcategory also enabled on a key whose SACL audits all access, each check adds two (one 4690 and one 4658).
