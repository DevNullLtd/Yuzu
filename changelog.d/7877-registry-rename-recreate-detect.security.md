- **A Registry spark watch now notices a parent renamed away with the watched path re-created, and a path re-pointed to another key, when the opt-in check is enabled (Windows, #7877 item 31).** Before this change the check re-opened the registered path and, when the open succeeded, took the key as healthy without comparing it with the key the watch holds, so an administrator who renamed the parent and re-created the path left the watch reporting Healthy and deaf. Each check now also reads the held handle's canonical name (through a duplicate of the handle, taken under the sweeper's lock; the name is never logged) and compares it with the name recorded when the watch was established, whether or not the fresh open succeeds, so a re-created path that the agent can no longer open is caught too, and it compares the fresh open's name with the held handle's. A mismatch faults the watch with `registry watch key moved from its path` or `registry watch path re-pointed to another key`, owes a resync fire, and re-opens the path on the ordinary retry (30 s, doubling to a 300 s cap); a held handle whose hive was unloaded faults with `registry watch hive unloaded`. The first compare runs only for a watch whose establishment recorded a name. A key name too long for the first read buffer (a deeply nested path of long names) is read through a retry, and a name past 64 KiB counts as changed against a recorded one; a watch is only established or re-established when a second read of the key's name agrees with the first, so a rename landing between the open and the first read is retried and never recorded. Both are closed in this change. A name that cannot be read, or a held key that has been deleted, leaves the check undecided and does not fault the watch: the agent log then says once per watch that the check could not decide and the watch is not protected until a check decides. Verified on a rig (2026-11-26, one fault then recovery onto the new key): an `HKCR` watch when a per-user class key appears over the machine one, and a registry link re-pointed to another target. A watch whose parent is renamed and replaced by a link at the old name, and a watch whose ancestor is renamed by case only, are expected to fault once and recover at the retry; those two were not observed. The check stays OFF by default and is enabled at boot with `--spark-registry-path-verify-interval` (env `YUZU_AGENT_SPARK_REGISTRY_PATH_VERIFY_INTERVAL`); the Spark detection layer is not live in production (`prefer_spark_` is false), so this is visible only on rig-flipped agents. Not covered (owner decisions: Dave, no independent adjudicator, 2026-11-26; register in `docs/spark-flip-gate.md`): a parent renamed away and back inside one interval; an undecided check, which keeps the old handle and which an administrator can force to persist (a link or a per-user class key pointing the path at a key that denies this agent a notify right while the held key has not moved), closed by #7877 item 32; a verification phase that is predictable, so a decoy can be placed between two checks (jitter deferred); an Ancestor-mode watch is never checked; the other #7877 residuals stand. This supersedes the "Not covered" clause of `changelog.d/8016-spark-registry-rename-deaf-watch.fixed.md` for a parent renamed away and the path re-created. Audit load, measured once on one key whose SACL audits all access for Everyone (one check: 1 event with Registry auditing alone, 6 with the Handle Manipulation subcategory also on; 1,440 versus 8,640 events a day at 60 s; real SACLs and many keys not measured); every establishment and re-arm also opens the key a second time for the name confirmation (one more event, four with Handle Manipulation on).
