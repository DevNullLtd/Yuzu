- **Gateway: an agent registration no longer gets slower as the gateway fills up, and a slow registry no longer holds up every other agent's connection.** For each registration the gateway's registry made about 71 synchronous `pg` calls for an agent with a full plugin set (one per plugin, plus `all_agents` and `{agent, Id}`), all inside that one process. Each call also cost time in proportion to the number of agents already in the group. Measured in one node on a development machine, a registration took 2.9 ms at 5,000 agents and 12.9 ms at 25,000, and a mass disconnect of 25,000 agents took 357 s. The registry now makes no `pg` call: about 4 µs per registration at both sizes, and 0.06 s for the same mass disconnect. The per-plugin and `all_agents` groups had no reader and are gone; the agent process joins its own `{agent, Id}` group, which a node reads to find an agent held by another gateway node. Removing an agent no longer walks every agent's monitor, so N disconnects cost the registry O(N) work, not O(N²). The agent process now registers after its `init/1` has returned, so the single agent supervisor never waits for the registry. The Subscribe handler still waits for the outcome and refuses with the same `UNAVAILABLE` (`session_limit`) as before. A refused registration now exits normally and writes no crash report, so a burst of refusals no longer floods the log.
