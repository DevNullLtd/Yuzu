- **Adding a management-group member records whether the agent id is an enrolled device in the audit row, and a REST create store fault is now a `503` (#7074, #6967).** An agent id the server has not enrolled is still added. The `management_group.add_member` success audit row's `detail` changes from the bare agent id to `<agent_id> agent_known=<1|0|unreadable>` (`1` when the server holds an enrolment record for the id, any status; `0` when it holds none; `unreadable` when the lookup could not be made); read the last space-delimited token as the flag, because the id is caller text. Nothing about enrolment status is returned in the REST response of `POST /api/v1/management-groups/{id}/members` or the MCP result of `add_management_group_member`. `POST /api/v1/management-groups` now answers a fault of the group store `503` with a fixed message and a retry hint instead of `400` with the store's own error text (a validation refusal and a name conflict stay `400`), and the Settings form escapes the refusal text it shows. `audit_persisted:false` on `create_management_group` now means only that the closing outcome row was lost.
