- **Release SBOMs now describe each shipped file, not the build workspace.** Every
  binary archive (not the Compose Wizard zip), `.deb`, `.rpm`, Windows installer and
  macOS `.pkg` gets its own CycloneDX and SPDX SBOM, named after the file
  (`yuzu-agent_X.Y.Z_amd64.cdx.json`, `YuzuAgentSetup-X.Y.Z.spdx.json`; the four
  archive SBOMs keep their names). The release unpacks the file, scans only that, and
  adds the vcpkg libraries its C++ binaries are built with from the installed vcpkg
  tree: the real version, licence, a `pkg:github` or `pkg:generic` purl and, where NVD
  has one, a CPE. The Windows installer is not unpacked: its SBOM lists the files the
  Inno Setup compiler's own manifest says it packed (`OutputManifestFile`), each read
  from the build directory and checked against the SHA-256 the compiler recorded, and
  listed at its path in the build directory, not where it is installed. The release's
  Windows job fails if that manifest is not in the format Inno Setup 6.7.3 writes
  (another compiler version can change it) or a listed file is missing, lies outside
  the build directory or does not match. The gateway's SBOMs list its Erlang/OTP release, with
  `pkg:hex` purls for Hex packages. Each SBOM records its file's SHA-256. Earlier SBOMs
  scanned the whole checkout: v0.15.0's Linux SBOM had 40,853 components, mostly the
  vcpkg ports catalogue, and none of the libraries that ship (it named OpenSSL 1.1.1t
  and 3.0.2 and libpq 16.9; the release ships OpenSSL 3.6.5 and libpq 18.4). Measured
  locally: 16 (agent `.deb`) to 22 (server and Linux archive) vcpkg libraries, and 18
  Erlang applications plus ERTS for the gateway. The release now fails before the
  GitHub Release is created (the images are already pushed by then) if a package has
  no SBOM, an SBOM belongs to no file of the release, records another file's hash, has
  more than 400 entries, or lists a path under `vcpkg/`, `vcpkg_installed/`,
  `build-*/`, `_build/`, `_build_*/`, `site/`, `tests/`, `.git/` or `.github/`, or if
  an image SBOM that should be marked incomplete is not. Each `yuzu:sbom:` note appears
  once, and the release check refuses an SBOM carrying a second copy of a note it
  reads. The image SBOMs now use the
  same syft (v1.57.2). Not listed yet, though the file holds it: code vendored into
  the source tree and compiled into `yuzu-server` (qrcodegen, and the web assets it
  embeds: htmx, ECharts, three.js, Cytoscape, IBM Plex fonts), the Windows installer's
  own InnoSetup runtime with the licence text, icon and installer script it embeds,
  and what the gateway's Erlang emulator (`beam.smp`) vendors
  and links in (PCRE2, asmjit, zstd, Ryu, OpenSSL's MD5). An SBOM whose file or image
  holds something it does not list is marked incomplete (CycloneDX
  `aggregate: incomplete`, SPDX `CONTAINS NOASSERTION`) and names why in its
  `yuzu:sbom:incomplete-reasons` note (a CycloneDX property; in SPDX, a line of the
  described package's comment, under the same key), by tokens from a closed, documented
  set: every SBOM of a file holding `yuzu-server`, the installer's, every gateway SBOM,
  and the six release image SBOMs (an image scan cannot see the statically linked
  vcpkg libraries or what the Erlang emulator vendors, and `yuzu-postgres` builds
  pgvector from source).
  Scanners such as grype report no finding for the marker: read it yourself.
  Libraries the binaries load from the operating system at run time are not in the
  file and are not listed. See `docs/user-manual/release-verification.md` section 5
  and the upgrade note in `docs/user-manual/upgrading.md`.
