- **Breaking -- `registry` 2.0.0 changes the behaviour of existing actions, and a write under `HKLM\SYSTEM\CurrentControlSet` now fails.** Registry links are refused (`key_is_link`), not followed as 1.0.0 did, and `CurrentControlSet` is a link: write under `HKLM\SYSTEM\ControlSet001` (or the numbered set `Select\Current` names). `set_value` now validates its `type` and numeric text instead of storing every non-`REG_DWORD` type as `REG_SZ`, and its errors are tokens (`access_denied`, `key_not_found`, `invalid_data`, ...) rather than sentences (`0x10`, `-1`, `12abc` and a lowercase `reg_dword` now fail where 1.0.0 wrote 0 or `REG_SZ`); `delete_value` answers tokens too and both limit the key path to 255 bytes and 32 components. `delete_key` reports a key that has subkeys as `key_has_subkeys` and on success appends four rows (`counted_keys`, `counted_values`, `dry_run`, `capped`) after `status|ok`. A creating write whose first key component is missing directly under the hive root is now refused `root_level_create`; registry 1.0.0 created it. The read actions (`get_value`, `enumerate_keys`, `enumerate_values`, `get_user_value`) map `|`, CR and LF in registry data to `_`. Upgrade agents to registry 2.0.0 before using the new value types or `data_hex`: an agent still running registry 1.x writes an EMPTY `REG_SZ` over the value for a `data_hex`-only `set_value` and answers `status|ok`, stores `REG_QWORD`, `REG_MULTI_SZ`, `REG_EXPAND_SZ` and `REG_BINARY` values as `REG_SZ` text and reports `status|ok`; the server does not gate dispatch on a plugin version. Agents at v0.14.1 or earlier never stamp the dispatched action and mint no `registry.write` rows, silently; the minimum agent version is the first release that contains the audit binding of #6294.
