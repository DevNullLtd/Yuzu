- **Engine credential `rotate` and `confirm`, and `DELETE /api/v1/engine-principals/{id}`, now tell clients when a `503` is safe to retry.** A `503` from a store that is not open, or from a store failure that left the work unfinished, carries `Retry-After: 2` and `retry_after_ms: 2000`. For `DELETE` that covers every `503` except one: the `503` for an audit row that could not be saved after the revoke committed carries no hint. When the identity revoke reports nothing done, the route now reads the principal again: if a concurrent `DELETE` already revoked it, the answer is the idempotent `200`; if it is still active, the answer is a `503` with the hint. The failure audit row for an identity revoke that failed after the credentials were revoked now records `credentials_revoked=<N>`, and a repeat of that call reports `credentials_revoked: 0`, because the credentials were already revoked. The old failure detail `store_unavailable` (written when the identity revoke reported nothing done) is gone on both surfaces; it is now `revoke matched no active row but the principal is still active; credentials_revoked=<N>`, or the matching "no longer found" or "re-read failed" text, so a rule that matches the old literal needs updating. The MCP tool `revoke_engine_principal` now matches the REST route on the failure rows and the race: the failure audit row carries the count, and a concurrent revoke answers success. Its normal success row still differs: REST records the count, MCP records the `reason`. That `detail` is now the `reason` with spaces, `=`, `,` and control bytes replaced by `_`, and a concurrent-revoke row appends `; reason=<sanitised reason>`; the REST success row's `superseded_by=` value is sanitised the same way, so match the race row on its `credentials_revoked=<N>; revoked_by_concurrent_request` prefix. The `revoke_engine_principal` tool's retryable errors already carried `retry_after_ms: 5000`. The MCP tool `confirm_engine_rotation` now sends `retry_after_ms: 5000` on retryable errors, as `rotate_engine_credential` does, and none on terminal ones. Clients should cap their retries and read the principal when a `503` persists: the empty-read answers on `rotate` and `confirm` (no active credential, no in-flight rotation) also carry the hint, and a revoked principal gives them every time.
- **A malformed engine rotation pair is now a terminal answer, and `rotate` refuses stale rotation metadata.** `confirm` on two active credentials that are not a linked rotation pair answers `409` on REST and `kInvalidParams` on MCP instead of a retryable `503`, because no retry can repair it. The `yuzu_engine_principal_confirm_total` series for it moves from `transient` to `conflict`, so a persistent malformed pair shows there (and, on the REST confirm route, in a warning log line; on MCP, in the failure audit row). `rotate` on a sole active credential that still carries rotation metadata (for example after its predecessor was revoked out of band) answers `409` on REST and `kInvalidParams` on MCP `rotate_engine_credential` instead of minting a second successor; read the principal and inspect the credential, and never re-rotate it. This is a behaviour change, not breaking for a well-formed principal, and there is no schema or state change, but it is worth a look for any integration that treats `503` as "retry".
- The served OpenAPI document now names every outcome the quarantine, engine-principal revoke and credential rotate and confirm, session revoke, upload-grant mint, `POST /elevate` and v2 plugin-policy routes can return: both quarantine 403 refusals and the audit-unavailable 503, the six revoke 503 causes and which ones carry a retry hint, the rotate `400` for a non-engine credential and `409` for stale rotation metadata, the sessions 500 and 503, the two missing upload-grant 400 causes, every `/elevate` refusal (a SAML session cannot elevate in this release), and the plugin-policy permission (granted to Administrator by default, not Administrator-only). The user manual was brought into line: the rotate and confirm error tables, the audit log rows for revoke, rotate and confirm, the confirm metric, the upgrade notes and the `confirm_engine_rotation` tool entry.
