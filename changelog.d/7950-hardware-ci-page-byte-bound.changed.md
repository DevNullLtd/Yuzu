- **A bulk device-CI page can now end early at a byte budget, which bounds the size of one response page (REST about 4 MiB, MCP about 3 MiB of body, additive `page_bytes_capped`), not the rows the server reads or holds per request.** `GET /api/v1/hardware-ci` cuts a page when its device rows reach about 4 MiB of JSON and `list_hardware_ci_records` when they reach 1 MiB (the MCP result carries the payload twice, so its body can reach about 3 MiB); both are fixed limits, not flags. A page always holds at least one device and a row is never truncated. When the budget, not `limit`, ended the page, the response carries the additive `page_bytes_capped: true` (absent otherwise), `next_cursor` names the last device served, and the access-audit detail ends ` byte_capped=1`; a page the budget does not touch is unchanged. Clients must follow `next_cursor` until it is empty and must not treat a page shorter than `limit` as the last one. The byte budget limits the response only, not the read: `limit=1000` still reads and holds 1001 rows from the store before the page is cut.
