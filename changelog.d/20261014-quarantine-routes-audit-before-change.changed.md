- **Quarantining or releasing a device now writes its audit record first and refuses if it cannot.** `POST` and `DELETE /api/v1/quarantine` write a `quarantine.enable` / `quarantine.disable` row with `result=attempt` before they change anything and answer `503` with `Sec-Audit-Failed: true`, leaving containment unchanged, if that row cannot be written; `success` then means the change was applied, and a lost outcome row is flagged with the same header. Each of these requests now leaves two audit rows (`attempt`, then `success` or `failure`). `GET /api/v1/quarantine` makes one `Security:Read` list-gate decision per request instead of one permission check per record, so the second `503` message `"authorization check unavailable — try again"` no longer occurs. Removing a device's stored data from the Hardware page also flags a lost outcome audit row with `Sec-Audit-Failed`.
