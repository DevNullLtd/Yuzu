- **A File spark watch now notices a renamed or replaced parent directory instead of staying silently deaf (Windows, #5719 item 5).** The watch held a handle that followed the renamed directory, so it kept reporting Healthy and never saw a change at the watched path. No shipped agent arms spark watches (`prefer_spark_` is false); the behaviour is visible only on rig-flipped agents. An idle watch now re-opens its directory path every 5 s and compares the directory identity with the one its handle was opened on; a different directory, or a path that names nothing, reports the watch faulted (`file watch parent directory renamed or replaced`) and re-discovers the path. Detection is sampled: a renamed or replaced parent directory is noticed at the next 5 s sample, at up to a few hundred watched directories (beyond that the lag grows with the directory count, see docs/spark-flip-gate.md, cost item), and nothing is promised between samples, verified on local NTFS only, in author-reported rig runs that are not part of CI. The watch then stays faulted until its retry: on the ordinary drain route the first retry is 30 s and doubles on repeated failure, up to 300 s; if a pass throws while the lost path drains, recovery uses a 50 ms backoff instead (still bounded by the 30 s admission cap). A watch whose check cannot decide 3 checks in a row is also reported faulted (`file watch parent directory unverifiable`). Repeated losses with no successful check, failed re-establishment or shelter commit between them back off from 30 s to the 300 s cap (a replace loop faster than the 5 s check can still leave the watch blind for up to 300 s per cycle), and due checks wait for a free verification slot (least recently checked first; a wait of at least 3 intervals is counted and warned once per episode). Not covered: an ancestor shelter whose own parent is renamed, filesystems that give no file id (an author-reported run on one FAT32 volume went undetected), and detection between samples.
