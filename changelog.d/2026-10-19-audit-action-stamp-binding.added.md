- **Groundwork, dormant until the `registry` plugin emits `audit|` lines: plugin output can be audited per action. The agent stamps `CommandResponse.action`, and the server mints `registry.write` audit rows from a `registry` plugin's `audit|` lines.** The agent stamps the dispatched action (the existing proto field 8, about 10 bytes per frame) on every plugin-output frame and on the terminal frame of every executed plugin command. The server turns the `audit|` lines a `registry` command streams from its mutating actions (`set_value`, `delete_value`, `delete_key`) into `registry.write` audit rows carrying the old and new values, `principal=agent:<agent_id>` and the `command_id`, which links each row to the dispatching operator's audit row where one exists. A row is minted only when the stamped action is one of those three, the plugin is `registry` (matched ASCII-case-insensitively) and the `command_id` is exactly what the server mints (`registry-` plus 16 or 32 lowercase hex digits); a read action never mints one, and an agent that predates the stamp mints none, so during a mixed-fleet rollout only upgraded agents are audited. At most 300 lines of 4,096 bytes per frame are recorded and a frame past that is logged once, each agent is budgeted to 600 rows per 60 seconds, and everything not recorded is counted by `yuzu_server_registry_audit_dropped_total{reason}`. The rows are written before the execution advances. A failed audit write ends that frame's rows, is logged and moves `yuzu_server_audit_emit_failed_total`; the direct session also gets the gRPC audit-failed trailer once per stream (the gateway path logs it). No `registry` plugin build emits `audit|` lines yet, so no rows are written and nothing else changes. See `docs/user-manual/audit-log.md` (`registry.write`).
