- **Linux software inventory reads the dpkg and rpm databases in-process instead of running `dpkg-query` and `rpm -qa`.** The `installed_apps` plugin now reads the dpkg status file and the rpm database itself, read-only and bounded (20 seconds, 50,000 packages or dpkg stanzas, fixed byte limits, and 8 MiB of retained text across the rpm headers): rpm sqlite (Fedora, RHEL 9 and later), ndb (SUSE) and Berkeley DB hash (RHEL 8 measured, little- and big-endian; RHEL 7 was not captured) are all supported. This plugin runs no `dpkg-query` or `rpm` process (`pacman` and `apk` are unchanged, and other plugins still run their own tools). The rows, the wire format and the section hash are unchanged on every host measured, so nothing is resent on upgrade except hosts that carry a tab, pipe or newline inside a maintainer or vendor, whose rows are sent once more with the full value instead of the truncated one.
  What else is different:
  - A host whose packages live only in `/var/lib/dpkg/status.d/` (minimal images with no shell, which `dpkg-query` never read; each package is a control file with no `Status` field, read as installed) now reports them as new install rows, and a host with a healthy status file and one unparseable regular file in `status.d` is now degraded (`dpkg_status_d:corrupt`; remove the file or give it a leading dot).
  - The package manager is chosen by its database file rather than its binary. A dpkg status with no installed package (empty, or only config-files and half-installed states) falls through to rpm, and an rpm database that holds no package falls through to `pacman` (and, for `list_inventory`, `apk`).
  - A dpkg `Status` is accepted only as dpkg writes it (dpkg's own words, lowercase, one space between them): a status file hand-edited to mixed case or repeated blanks, which `dpkg-query` read, is now `dpkg_status:corrupt` until dpkg next rewrites it.
  - A symlinked status file, `status.d` directory or rpm database file is refused (`symlink_refused`) where the tools followed the link. A symlinked rpm directory is skipped, never followed; when a database file sits behind such a link in a directory this reader did not read, the read is `rpmdb:symlink_refused` rather than an empty list (the current Fedora, RHEL and SUSE layout is unaffected).
  - While an rpm transaction is running on a host that keeps an ndb or Berkeley DB database, or while a dpkg update journal is pending (a file named with digits only in `/var/lib/dpkg/updates`, left by a dpkg run in progress or an interrupted one; clear it with `dpkg --configure -a` when no dpkg run is in progress, or by hand on an rpm host that carries a stale dpkg tree), the read answers `locked` with no rows and the server keeps its stored rows, where `rpm -qa` read between the writer's steps and `dpkg-query` printed the merged view.
  - An rpm sqlite database without its WAL sidecars is readable by an unprivileged account (measured on one AlmaLinux 9 image, where `rpm -qa` failed).
  - A failed read is a degraded collection with a named reason (`installed_apps:<source>:<cause>`, for example `rpm_sqlite:locked`) in the agent log, the `list`/`query` error row and the result's provenance, with no rows and the server keeping its stored ones. A damaged database record fails the whole read rather than publishing a shorter list.
