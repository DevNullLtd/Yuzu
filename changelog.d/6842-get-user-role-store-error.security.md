- **Breaking — a user-store outage on Settings user create / role change and on SCIM `active:false` is now a retryable `503` with its own audit reason (#4068).** `AuthManager::get_user_role()` now returns `std::expected<Role, GetUserRoleError>` (`NotFound` / `DbError`) instead of a bare `nullopt`, so callers can tell a missing user from a store error. Narrows one CC6.8 gap: SCIM `PUT`/`PATCH` `active:false` on a resource whose mirror already reads inactive used to take the "already deprovisioned" no-op (a `200`) when the AuthDB lookup failed, leaving a possibly-live account reported as deprovisioned; it now answers `503` + `Retry-After: 2` and the IdP's retry completes the deactivation. The Settings role-change route answers `503` with audit `failure` / `store_unavailable` instead of `404` / `denied` / `user_not_found` (SIEM rules keyed on the old pair no longer see outages), the create-user duplicate check answers `503` instead of carrying on with an unanswered lookup. Legacy API-token session synthesis still floors to `Role::user` on a store error, and `yuzu_auth_get_user_role_store_error_total` is unchanged but now counts every caller. **This does not make deprovisioning outage-proof:** a full database outage still returns `401` at SCIM bearer validation, deactivating a resource whose mirror reads active can still return `404` on a store error, there is no reconciliation sweep (the IdP owns the retry), and `DELETE` of an already-inactive mirror does not repair a live account. Tracked in #6835 (SCIM outage answers 401/404), #6836 (`deactivate()` provenance 404), #6837 (remaining store-error-as-absent sites) and #6838 (no reconciliation; DELETE repair). See `docs/user-manual/scim-provisioning.md`, "When the user store cannot answer a deactivation".
