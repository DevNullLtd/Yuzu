## How it works

`state` and `rules` are reads. `state` answers "is the host firewall on, and which firewall answered"; `rules` lists what the same source exposes. Every parse is a pure function in `firewall_parsers.hpp`, and every subprocess is a literal argv run through the bounded runner with a fixed 5 second deadline, with no shell command line; the one program so run that is itself a shell script is the installer's root helper (rung 3, registered in the spawn-sink manifest).

- **Windows.** The `INetFwPolicy2` COM interface is called in process. `state` asks each of the Domain, Private and Public profiles whether `FirewallEnabled` is set and adds the true total rule count (`INetFwRules` count). `rules` enumerates `INetFwRules` and stops after 100 rules with a `truncated|true` marker row. Each rule's name, enabled flag, direction, action and profile mask are read separately and a value is used only when its own read returned `S_OK` (an `S_FALSE` is a failure here, as everywhere in this plugin): a property that could not be read shows `unknown` in its field, never a default such as `disabled`, `block` or profile `0`, and a rule the enumerator returned but whose object could not be obtained is an all-`unknown` row that still counts.
- **macOS.** Two separate firewalls are read. The Application Firewall is primary, because it is the firewall a Mac administrator means: `socketfilterfw --getglobalstate` gives `state|`, plus `mode|block_all` when block-all is set, and `socketfilterfw --listapps` gives the per-app allow or block list. The pf packet filter, off by default and unrelated to the Application Firewall, is secondary: `pfctl -s info` gives the `pf|` row, and `pfctl -s Anchors` and `pfctl -s rules` give the anchor names, the raw pf rule lines and the rule count. Each pf read opens `/dev/pf`, so it runs as `sudo -n -- /sbin/pfctl -s <word>` on the installer's exact read-only grant (the argv is unchanged when the agent is root). Every one of those reads is published only when the command ran, did not time out, was not truncated and exited zero; a read that did not complete never contributes a row built from its text. Each such failure is named by an `error|` row (see Reading the macOS error rows below), so an agent that has neither root nor the grant (sudo refuses and exits 1) reads as `pf|unknown`, `ruleset|unknown` and the rows that say why, never as a firewall that is off or has no rules. A global-state read that did not complete is `state|unknown` whatever its partial text said.
- **Linux.** A fixed ladder stops at the first source that answers: firewalld over sd-bus (only in builds with libsystemd; otherwise this rung is skipped; it answers first only when its read was complete, the zones and every zone's services, and a partial read is held, see below), then nftables over `NETLINK_NETFILTER` dumps, then the root snapshot broker (below), then `ufw status numbered`, then `iptables -S`, else `backend|none`. The nftables leg checks that each dump reply came from the kernel (`nl_pid == 0`) and splits its 5 second deadline across three dumps (table, then chain, then rule, with cumulative cut-offs at 1, 2.5 and 5 seconds). It also compares the ruleset generation the kernel stamps on each dump (the big-endian `res_id` of the `nfgenmsg` header): a commit that lands between two dumps moves it, so three dumps that are individually clean but disagree are not trusted as one picture (`generation:changed`). A chain or rule dump that is torn, or a moved generation, is churn and gets one more look: the three dumps run again on fresh sockets inside the same overall 5 second deadline, only when at least 2 seconds of it remain, and the second pass is the answer. A failed table dump ends the probe with no re-read, and a timeout, an error or an oversized dump gets no second look. An empty ruleset dumps no data message at all, so it has no generation and never reads as a change. The snapshot rung has its own 5 second deadline, so a run that walks every rung takes about 25 seconds in the worst case.

The packaged Linux unit (`NoNewPrivileges=true`, one capability) can read neither the nftables ruleset nor the legacy iptables tables, and `sudo` cannot elevate under it, so, once firewalld has not answered completely and the netlink dump has failed, the plugin reads the root snapshot broker: it connects to `/run/yuzu-fw-snapshot.sock` (a systemd socket unit owned by root, group `yuzu-agent`, mode `0660`), sends nothing and reads to end of stream. Each connection starts a root service that runs one fixed read-only script (ADR-3007) with no input: `nft -a list ruleset` for nf_tables, and each address family's legacy save tool under its own name (`iptables-legacy-save` and `ip6tables-legacy-save`, no argument), which lists every instantiated table and, for the tables the kernel lists, loads no module and takes no lock; the whole reply is cut at 4 MiB (4194304 bytes, the same number as the netlink leg's cap; the two bound different encodings, the text listing and the netlink dump, so a ruleset can fit one and not the other). A family with no legacy save tool reads the kernel's own list of its tables instead (the section is `[tables]` and then the names). The alternatives-selected `iptables` is never run: on an nft-backed host it is the shim, which lists nothing the nft section does not. The agent spawns no process for the read (rung 1) and treats the reply as untrusted text: the three headed sections and the closing `== end` line must all be there, or the read is `error|snapshot:empty`, `truncated` or `malformed`; on the first read the ladder then goes on, and on the second read of a pair the answer is `unknown` (below). The decision is made over three disjoint rulesets, each READ or UNREAD. The nf_tables section is READ when its text parses; each legacy section is READ when it is a save listing in the shape the parser knows (empty output with exit 0 is a family that holds no table) or `[tables]` with no name after it. A section is UNREAD when its tool failed (`[failed]`), was not installed (`[absent]`, the nft section only), printed text the parser does not know, or is `[tables]` followed by a name (tables exist that nothing listed). The answer: `active` when any READ section has content (an nft rule or a base chain whose policy is not accept, a legacy rule, a user-defined chain or a policy other than ACCEPT); otherwise `unknown` when any section is UNREAD, with one error row per unread section (`error|nftables:snapshot:failed`, `error|nftables:snapshot:absent`, `error|iptables:snapshot:failed`, `error|iptables:snapshot:absent`, `error|<tool>:unrecognised_output` and the `ip6tables` forms); and `inactive` with `ruleset|0`. `inactive` is answered only when all three sections were read and none shows content, in two snapshots taken one after the other; a rule count is written whenever all three sections of the answering snapshot were read and the netlink read did not turn the state to unknown. The second snapshot is taken only when the first reads `inactive`, and its answer is the answer (`inactive` confirmed, `active`, or `unknown` with its error rows). A second snapshot that cannot be taken or framed, that finds no transport (`error|snapshot:gone`) or that declines is `unknown` with the row that says why and no count, and the read ends there, without the `ufw` and `iptables -S` rungs, which read less than the snapshot. A host that reads `inactive` makes two broker reads (two helper runs on an installer-provisioned host) per `state` or `rules`, and both snapshots share the client's one 5 second deadline: a host on which they do not fit reads `error|snapshot:timeout` (`error|snapshot:helper:timeout` through the helper) and `unknown`, never `inactive`. The rule count is the nft rules plus the `-A` rules of both legacy families; otherwise `ruleset|unknown`. `backend|iptables` is written when a legacy section has content and nft has none, else `backend|nftables`. A legacy row is `rule|[ip6|][<table>|]<kind>|<chain>|<spec>`: `<table>` is one of `nat`, `mangle`, `raw`, `security` (the `filter` table writes none) and `<kind>` is `policy`, `new_chain`, `append` or `unknown`, so the second field is one of nine fixed words and never `nftables` or `firewalld`, which the other backends' rows carry there (`rule|raw|append|PREROUTING|...`, `rule|ip6|mangle|policy|...`). The save parser accepts a subset of what `iptables-save` writes: the five kernel table names, each once, and every chain and append line with its double quotes closed; anything else is `error|iptables:unrecognised_output` (or the `ip6tables` form) and no row. A host with no `nft` command cannot have nf_tables read: with no content in any section that was read the rung declines, writes only `error|nftables:snapshot:absent` (and the other unread sections' rows) and the ladder goes on, so the host reads as a host without the broker does and never `inactive`; with legacy content it answers `active` with `ruleset|unknown` and that error row. `ufw` hosts are reported through these nftables or iptables rows, because the snapshot has no `ufw` section. The root agent's direct `iptables -S` leg reads whichever iptables the alternatives select and lists the filter table only (#8614), so on the same host its rows and count can differ from the broker's in the label, the tables read and the count; the broker's reads are the ones that list every instantiated legacy table. When the netlink dump fails before any table is seen (for `rules`, also when tables were seen and their chain or rule dump was not trusted: the `rules` legs have no clamp) and the snapshot rung does not answer (no transport, or a first read that failed or declined), `ufw` and `iptables -S` answer unclamped, as they do on a host without the broker: for a root agent they can read `inactive`, or for `rules` a list and a count without the rules they do not list (#8638), while the packaged account is refused both and reads `unknown`. A host without the broker has no socket file. If the agent is also not root and not under `NoNewPrivileges` and the helper file is there (a host the installer provisioned), the rung reads the same listing from the root helper's `snapshot` word through `sudo -n --` instead (the same strict framing and the same decision; rung 3 at that one site, `firewall/try_snapshot#1` in the spawn-sink manifest). A host with no helper file makes no sudo call and says nothing, and the ladder goes on; a sudo that refuses (exit 1), or a helper that timed out, was clipped or failed, is `error|snapshot:helper:<token>`. A non-root agent that is not under `NoNewPrivileges`, has the helper file and no sudo grant makes one refused `sudo -n` attempt per `state` or `rules` read, which reads `error|snapshot:helper:exit:1`. Whether the refusal is logged is the host's sudo: measured on Rocky 9.9 (sudo 1.9.17p2) one audit-log record per attempt (`USER_CMD`, `res=failed`) and no syslog line, and on Ubuntu 26.04 (sudo-rs 0.2.13) no line naming the helper command under the journal identifier `sudo`, the only log searched there. The helper has no connection limit: the agent's command pool (4 to 32 workers) bounds how many helper runs are in flight, and the runner caps each run's output at 8 MiB.

A firewalld that answered `getActiveZones` but whose `getServices` was refused, failed, did not decode or ran out of the 5 second budget is held, not answered: it says that firewalld runs, not what filters. Measured on Rocky 9.9 (aarch64, SELinux enforcing, firewalld running) as the packaged account, which has no polkit rule: `getActiveZones` answers and `getServices` is refused. While firewalld is held the nftables rung answers only a ruleset that shows content, and the snapshot rung only an `active` answer (any other snapshot answer writes just its `error|` rows, so a refusal is still reported); a held answer is therefore replaced only by a complete read that shows an active ruleset, never by `inactive` or `unknown`. When no read does, the plugin writes firewalld's own rows after the deferred table-dump row (`backend|firewalld`, `state|running`, `ruleset|unknown`; for `rules` the services that were read, then `ruleset|unknown`), and `ufw` and `iptables` are not asked. A firewalld host whose read was complete answers at once. The reason is that firewalld can run on its iptables backend, where the nf_tables ruleset an agent reads can be empty: an `inactive` there would be false.

The honest-status rule holds on every leg: empty, truncated or unrecognised output parses to `unknown` (state) or no rows (rules), never to a false-safe "disabled" or an invented rule. If nftables' table dump succeeds but a later chain or rule dump fails, the leg writes a `fallthrough|nftables:<dump>:<reason>` row for EACH failed dump (both reasons, not just the first) and continues to `ufw` then `iptables`, with their verdicts clamped so a downstream "disabled" cannot contradict tables already seen. Output from `ufw` or `iptables` that completed but is not in the shape the parser knows is not read as "no rules": the state and the count read `unknown`, with `error|ufw:unrecognised_output` or `error|iptables:unrecognised_output`, and the rule rows already parsed are still written.

### Device containment

Four more actions contain a host and lift the containment again: `quarantine`, `release`, `quarantine_status` and `quarantine_allow`. All of them run through one OS-neutral core (`firewall_quarantine_parsers.hpp`) that decides everything and is unit-tested on every host; the plugin only wires an OS mechanism to it. Windows, Linux and macOS are implemented; the macOS design is in `docs/quarantine-macos-pf-anchor-design.md`. Three limits are part of the contract. **Linux is constrained on the packaged systemd unit**: it runs as `yuzu-agent` with `NoNewPrivileges=true` and no sudoers grant, so `sudo` cannot elevate and every mutating action (`quarantine`, `release`, `quarantine_allow`) is refused up front, `refused|privilege_unavailable`, before any record is written; the privilege path is a later change. **A time limit (`ttl_seconds`) ends the containment unattended, with two limits of its own** (caveat 2): its expiry release is logged on the agent (`firewall: release -> inactive ttl_expired=1`), and a device-reported time limit never ends a server-applied record: the server reads that `inactive` answer as drift and contains the host again (a host that refuses the apply is not contained again: its re-apply is refused), so after a limit passes check `quarantine_status`; and it is measured on the host's wall clock while the quarantine blocks NTP, so a clock stepped back means it never fires and one stepped forward releases early. **A host that is its own server refuses new containment** (the next section): `quarantine` answers `refused|self_host` before the privilege check and changes nothing, so a host that was already contained stays contained, and a packaged Linux unit whose server is the host itself answers that, not `privilege_unavailable`.

- **What stays reachable.** Loopback, the agent's own control channel (the address the agent is connected through when the quarantine is applied, which the agent daemon publishes from the stream the server answered on, plus every address the server name resolved to at agent start on the server's port; the host being contained never chooses which address survives, and neither the plugin nor the host resolves a name at quarantine time), DHCP (UDP 67 and 68; on Windows scoped to the DHCP client service, as Windows' own DHCP rules are), DNS to the host's configured resolvers (at most eight, port 53), IPv6 neighbour discovery, and any operator exceptions. Nothing else is reachable and nothing that existed before is: Linux has no "established" accept, so a connection that predates the quarantine is cut unless an allowance matches it. DHCPv6 (UDP 546 and 547) and multicast listener discovery are not allowed on any OS, and Windows disables its built-in rules for both, so a host that depends on stateful DHCPv6 loses its address when the lease expires. The containment covers the host's own IP traffic and the traffic the host routes; **L2-bridged guests (without `br_netfilter`), macvlan and ipvlan containers and Hyper-V external-switch guests never reach the hooks it uses and are not contained.**
- **A host that is its own server refuses new containment.** Every `firewall.quarantine` apply that is not `repair=1` is checked, whoever sent it (an operator's dispatch, the server's reconciler, an MCP re-apply) and an apply to an already-contained device included: the control endpoints (the live peer and every address the server name resolved to at agent start) are compared with every address the host answers to, loopback and link-local included, and the answer is `refused|self_host` when one is an own address or is loopback or unspecified, because the server it must keep reaching would be the host itself, so the apply could not be released from outside. A read of the host's own addresses that fails refuses too (`refused|own_addresses_unreadable`), because an unknown is not "not this host"; that read fails for good where the agent cannot open `AF_NETLINK` (a unit or seccomp profile that denies it), so every checked apply is refused there until the agent is allowed it, and the agent log names the errno. A loopback or unspecified control address is refused whatever that read returned. A refusal changes nothing: no leg is built, no record is stored, and an existing record and its containment are left as they were; there is no override. So the token alone does not say whether the device is contained. A device that held no containment stays uncontained and its record never confirms. A device that was already contained stays contained: the repair and the boot re-apply keep the stored containment, and the server's re-apply is refused there. A time limit set on the device (by a `firewall.quarantine` dispatch outside the quarantine routes; a server apply carries none) still ends that containment, and the server cannot then contain it again. `quarantine_status` says which. The check runs before the privilege check, so a packaged Linux unit whose server is the host itself (the unit's default) answers `self_host`, not `privilege_unavailable`. Not checked: the 60-second repair, the boot re-apply, `release` and `quarantine_allow`, so a stored containment is still re-applied and is released wherever the agent can elevate (on the packaged Linux unit only an operator's forced end ends the record, see Caveats 5); `release` and the console steps still lift a containment on a device that refuses. The refusal is in the agent log (`firewall: quarantine -> refused:self_host`) and in the command's stored reply (the `status|refused|<token>` row). The server keeps re-dispatching to a device that refuses, so on a device that held no containment a record that was never confirmed stays unconfirmed until an operator deletes it. On a device whose own record (the one the plugin keeps on the device) is active, a refusal carries `note|allow_set_unchanged_use_quarantine_allow=1` when the request's exceptions differ as a set from those in force (the same rule and text as a retry that is not refused), so a never-confirmed server record then stays unconfirmed (`allow_set_not_applied`); with equal exceptions there is no note and the status read confirms. Do not release and quarantine again to change the whitelist on such a device: the release lifts the containment and the new quarantine is refused, so the device ends uncontained; use `quarantine_allow`. A single-host stack (the agent and the server on one machine) therefore cannot apply a containment.
- **Windows.** A Windows Firewall rule group named `Yuzu Firewall Quarantine` holds one allowance rule per entry, and every profile's default action is set to block, inbound and outbound. An Allow rule beats a profile-default block, so every other enabled rule is disabled for the duration, its name written to the plugin's storage before the first one is touched, and re-enabled on release. The pre-quarantine default actions are captured once and restored; a default the profile had no local value for (read from the local policy store, `HKLM\SYSTEM\CurrentControlSet\Services\SharedAccess\Parameters\FirewallPolicy\<Domain|Standard|Public>Profile`, because `INetFwPolicy2` reports only the effective action) is restored by first writing the OS default through the firewall API (inbound block, outbound allow, so the running service is correct at once) and then deleting the local value, so a host that relied on the OS default stays unpinned; a default action set locally while a quarantine is active is overwritten on release (the captured snapshot wins); a local value that cannot be read refuses the apply (`prior_policy_unreadable`), and a delete that fails counts as a restore failure. A release widens first and removes the allowance rules last: a default action that will not restore, or a captured image that exists but cannot be read (an old format or a malformed one: `note|prior_policy_unreadable=1`), leaves the allowances in place and the release incomplete (`partial|release_failed:release_incomplete`); only a confirmed absence of the image falls back to the OS default, so the host is never left blocking with no allowance; the record stays `releasing` and the next release or agent start retries. A rule the policy store refuses to disable (typically one delivered by Group Policy) is counted, and the result is `partial`, never `active`. A stock rule is remembered by every property that tells two rules apart (name, direction, profile, protocol, local and remote ports, program, service and action: Windows ships rules that share a name and differ by profile, one on and one off, and an administrator's copy can differ by a single port), so a release switches back on what the quarantine switched off and nothing else, bar the one guess described next. A listed rule that someone edited during the quarantine (its program, ports, service or action changed, so its key no longer matches) is found by name, direction and profile instead, but only when two things hold: when the quarantine switched it off, no other rule, on or off, carried that name, direction and profile (the stored list records this for each rule), and exactly one rule in total, switched on or off, carries them at release. If that rule is switched off it is switched on: that is a guess, so the reply says so (`note|rules_reenabled_by_identity=<n>`). If it is already on (a retry after that guess, or the edited rule switched back on by hand) it is accounted for and the reply says so (`note|rules_accounted_enabled=<n>`). In every other case nothing is switched on for it (a second rule of the same name, direction and profile may have been off before the quarantine, and a rule that was renamed, or moved to another direction or profile, would otherwise leave that second rule looking like it) and the release completes as `partial|rules_unmatched` with `note|rules_unmatched=<n>`, up to 8 names go to the agent log and the record is erased (an unmatched rule is never a reason to keep retrying). A host where Group Policy or MDM controls ANY of the three profiles is refused (`refused|gpo_override:<Profile>`, naming the first controlled profile) before anything is touched: the quarantine writes a default block on every profile, and Microsoft documents that a rule or default written locally takes no effect where Group Policy controls the firewall, so a containment would be a lie there. Each profile's Group Policy store (`HKLM\SOFTWARE\Policies\Microsoft\WindowsFirewall\<Profile>Profile`) and its MDM store (the Firewall CSP's `HKLM\SYSTEM\CurrentControlSet\Services\SharedAccess\Parameters\FirewallPolicy\Mdm\<Profile>Profile`; the path is taken from the CSP's documented storage and is not yet confirmed on a host) are read, because `INetFwPolicy2::LocalPolicyModifyState` describes the current profile only and a laptop on its Private network would otherwise be contained while its Domain profile is policy-controlled. A profile counts as controlled when `AllowLocalPolicyMerge` is present and 0 (the quarantine's allowances would not merge, so the host would be block and block with no allowance) or when `DefaultInboundAction` or `DefaultOutboundAction` is present, whatever its value (a policy-set default makes the quarantine's default block, and its restore, inert), so **a host whose policy itself sets block and block is refused too**. The two stores are folded per profile: a definite override in either one controls the profile, even beside a store that could not be read; otherwise an unreadable store leaves the profile unreadable. A missing key or value is no policy; a store that cannot be read is refused as `firewall_state_unreadable:<Profile>`, never guessed. The `LocalPolicyModifyState` reading (`GP_OVERRIDE`) stays as a second signal and, on its own, refuses with the bare `gpo_override`. A policy that arrives after the quarantine reads `degraded|gpo_override` on every status (with `note|firewall_profile=<Profile>` when the store named one; never `partial` or `active`), an update fails whole (`update_failed|gpo_override:<Profile>`), and the self-check does not retry it, because a re-apply would write the same ineffective values. A rule that Group Policy will not let release switch back on is its policy's, not the containment's: it is a `note|rules_not_reenabled=<n>` on a completed release. A default action that will not restore keeps the release incomplete and names its profile (`note|policy_restore_failed=<Profile>`). A captured image that never parses (a corrupted store; no older format ever shipped) keeps every retry incomplete with the allowances in place; until the break-glass release lands, recovery is manual on the host: remove the `Yuzu Firewall Quarantine` rule group and set each profile's default actions back (for example `Set-NetFirewallProfile -DefaultInboundAction NotConfigured -DefaultOutboundAction NotConfigured`). A profile whose firewall is switched off makes every rule and the default block inert, so the apply refuses (`refused|firewall_disabled:<Profile>`, or `firewall_state_unreadable:<Profile>` when the switch cannot be read) before anything is touched, and the status reads `degraded|firewall_disabled` with `note|firewall_profile=<Profile>` naming the profile; the plugin never switches a firewall on, because that switch is often policy-managed and is not the plugin's to undo. A previous generation's rule that would not delete during an update is a live allowance the record no longer lists, so it is counted, persisted and reported `partial|stale_rules_left` until a later update removes it.
- **Linux.** With `/usr/sbin/nft` present, the plugin loads its own `inet yuzu_quarantine` table in a single nft transaction (a non-root agent has the root-owned helper load it with `nft load`; an agent that runs as root runs `nft -f` itself): input, output and forward base chains at policy drop plus the allowances, replacing the previous generation atomically, so a failed load leaves the old table in force. The chains are stateless: a TCP allowance's reply path refuses a bare SYN (`tcp flags & (syn|ack) != syn`, two positive `--tcp-flags` rules on iptables), so a peer cannot open a new connection from its service port, but **a UDP allowance admits datagrams from the peer's service port to any local port**, because the design has no connection tracking on purpose. Release is one `delete table`, and a table is treated as already gone only when nft itself says so (`Error: ... No such file or directory`), never on the text of `sudo` or the dynamic loader. Without nft it builds a new `yuzu-fwq-<generation>` chain in iptables and ip6tables (INPUT, OUTPUT and FORWARD jump to it), inserts the new jumps, then removes the old generation, so both exist during the swap and an update only ever tightens; the status requires our jump to be the FIRST rule of INPUT, OUTPUT and FORWARD (a Docker restart re-inserts its own FORWARD jump ahead of ours, which reads `degraded|policy_not_blocking` until a retried `quarantine` repairs it). IPv6 is judged from two facts, the `ip6tables` binary and the host's IPv6 stack: a host with a stack (or one whose stack cannot be read) and no `ip6tables` is refused (`refused|ip6tables_missing`, `refused|ipv6_stack_unknown`) rather than contained over IPv4 only, and only a host that has IPv6 switched off is contained over IPv4 alone. The apply plan, including every exception on both address families, runs under a 60 second deadline and the verification gets 10 seconds more; the undo of a failed initial apply gets a fresh 60 seconds, so a failed apply takes up to about 130 seconds. A boot-time re-apply is bounded by the first two.
- **macOS.** The plugin never loads or rewrites the main pf ruleset. It loads its own sub-anchor `com.apple/000.yuzu_quarantine` with `pfctl -a ... -f` (a non-root agent has the root-owned helper's `pf load` action run it; see Privileges below), which Apple's own `anchor "com.apple/*"` line already evaluates; the `000.` prefix makes it sort ahead of Apple's `200.AirDrop` and `250.ApplicationFirewall` anchors, because pf evaluates sub-anchors in name order and a `quick` pass in an earlier one would win. The anchor opts out of NAT and redirection (`no nat all`, `no rdr all`), passes loopback and the allowances, and ends in `block drop quick all`. The control channel is stateless in both directions, so the one `pfctl -F states` that follows the load (pf passes a packet that matches a state without looking at any rule, so established connections would otherwise survive) cannot disturb the stream the agent's reply travels on. pf is switched on with `pfctl -E`, which returns a reference token the plugin records at once; release empties its own anchor (`-F rules`, `-F nat`, never `-F all`) and releases that token. If another actor switches pf off (`pfctl -d`) the status reads `degraded|pf_disabled` and the next `quarantine` or agent start releases the dead token and takes a fresh one. Two further statuses mean a re-apply cannot help and say so: a main ruleset with no `anchor "com.apple/*" all` line (`anchor_not_referenced`, which also fails an apply before anything is loaded) and an anchor that sorts ahead of ours (`anchor_not_first`, `partial` on apply). An empty anchor (`policy_not_blocking`) is repaired by the next `quarantine`. The staged ruleset path may contain a space (the packaged data directory is `/Library/Application Support/Yuzu`) and is checked against the staging directory before `pfctl -E` takes a reference.
- **Verify after applying.** The agent connects to the live control address, the one the agent daemon is connected through right now (it must succeed; `note|control_proved=live`), or, at agent start when no Register has happened yet, to a listed control endpoint (`note|control_proved=listed`), and to the optional `probe_target`, an IP literal that answered before the change and must now time out; a probe target that an operator exception already admits is refused before anything changes (`refused|probe_target_covered_by_exception`). `active` means the proof STARTS with `verified`: any proof that failed (the control channel did not answer, the probe target was still reachable) reads `active_unproven` in every later status, a no-op update and the TTL tick. A refused connection after the change means the packet got through, so it counts as reachable. A failed initial apply writes the phase `releasing` first, then removes its own rules, then the record, and reports `rolled_back`, so a crash or a failed record delete at any point is finished by the next start and never re-applies the containment that just failed its check; with no probe target the result is `active_unproven`.
- **Generations and phases.** The record `quarantine.state` in the plugin's storage is written, with phase `applying`, before any change to the host, and the action refuses (`refused|state_not_persisted`) when it cannot be written. It then moves to `active`, or `releasing` during a release. A `quarantine_allow` update writes the next generation first, applies it as an update, and on failure puts the previous generation's record back (`update_failed|<reason>`); rollback to nothing exists only for the first apply. Two `update_failed` answers do NOT mean the previous generation is in force: `update_failed|revert_failed:<reason>` (the new generation failed verification and the revert failed too) leaves the NEW generation in force with its record `applying`, and `update_failed|commit_unknown` (a tool committed and then overran its five-second budget, so the kernel may hold either set) leaves the candidate record `applying`; in both the next retried `quarantine` or agent start converges the full set. A retried `quarantine` over an incomplete (`applying`) record takes the request's `probe_target` (proven reachable first) in place of the stored one. A `quarantine` retried on an active record never rewrites its stored allow set or expiry, except to admit the agent's live control peer when the stored set lacks it (`note|control_live_peer=<ip:port>`, or `note|control_live_peer_over_cap=1` when the set is full; see Self-check), and answers what `quarantine_status` would unless a re-apply can repair the gap (it then re-applies the stored set and adds `note|repaired=1`); a `ttl_seconds` it carries is answered with `note|ttl_unchanged_release_then_quarantine=1`.
- **At agent start.** `init()` finishes an interrupted release, and re-applies a stored containment the host no longer enforces (a reboot, a release by hand, pf switched off) as a generation update; a re-apply that fails puts the record back as it was, so for an `active` record `quarantine_status` reports what the host does, `degraded` with a reason such as `firewall_disabled`, `gpo_override`, `policy_not_blocking`, `pf_disabled`, `anchor_not_referenced` or `os_unreadable`. A record that was already `applying` stays so and reads `partial|operation_in_progress`, and `note|state_restore_failed=1` means the put-back itself could not be saved, so the record is left `applying` and reads the same way. A record whose initial apply never completed (no proof was ever recorded) is NOT promoted to `active` when the control channel does not answer at start: it stays `applying` (`note|control_unreachable_unproven=1`) until a retried `quarantine` converges and verifies it. It never rolls back and never releases because the server is unreachable. A host whose control set stopped matching the server (a re-addressed server, a wrong set) is lifted by a `release` dispatch that reaches it, by a configured time limit (`ttl_seconds`) running out (the `release if_ttl_expired=1` tick, or the release at start when the limit lapsed while the agent was down), or by the later break-glass. Without a time limit there is no local release in this release, a containment removed by hand is re-applied at the next start while the record is `active`, and the exit is **not** bounded. A store that cannot answer (SQLite busy, a closed handle) reads as `degraded|state_unreadable` and changes nothing: it is never read as "no record". A time limit that lapsed while the agent was down is released at start (`note|ttl_expired=1`), not re-applied. A time limit is enforced by an interval trigger (`firewall.quarantine.ttl`, every 30 seconds) that runs `release` with `if_ttl_expired=1`: a no-op until the limit passes (a lapsed limit always releases: nothing defers it), and a trigger that cannot be registered is residue (`partial|ttl_unregistered`) until a later registration succeeds. An expiry release leaves one agent log line; the server's own record of a containment it applied is described in the first paragraph above.
- **Self-check.** While a record exists, an agent-local interval trigger (`firewall.quarantine.repair`, every 60 seconds) dispatches `quarantine` with `repair=1`, which the plugin routes to a repair path (a bare periodic `quarantine` would start a containment with no record and converge an in-progress one every minute). The trigger's dispatch carries `repair=1` and nothing else: the plugin cannot tell it from an operator's dispatch, so a `repair=1` that also names `ttl_seconds`, `exceptions` or `probe_target` is refused (`refused|repair_with_containment_parameters`, no record, no repair) instead of answering `inactive` to an operator who meant to contain. It takes the same mutation gate as every mutating action (`busy`, it never waits behind another), reads the host once (a COM enumeration on Windows, one `sudo nft list table` on Linux, a few `sudo pfctl -s` reads on macOS) and acts only on an `active` record whose live read says the host stopped enforcing it in a way a re-apply fixes (a flushed table, restored profile defaults, pf switched off): it re-applies the STORED allow set through the same converge a retried `quarantine` uses, plus the address the agent is connected through when the stored set lacks it (a server re-addressed since the quarantine: the address the agent daemon publishes from the authenticated stream, never one the host chose). That is the agent-side twin of the server's stored-whitelist-only re-dispatch rule, not an exception to it: the server reconciler and a retried device quarantine still re-dispatch the stored set alone, and the agent admits the live address the way it does when it first builds the set, from the authenticated stream and never from the caller or the host. It shows as `note|control_live_peer=<ip:port>`, or `note|control_live_peer_over_cap=1` when the set is already full and the address is left out. The repair also adds `note|repaired=1` and counts it on the record (`note|repairs=<n>` and `note|last_repair_at=<epoch>` on every later status). The count is every time the host was found no longer enforcing the stored set and re-applied, whichever dispatch found it: the self-check, or a retried `quarantine` that converged the same record. It never acts on a store that cannot answer (`degraded|state_unreadable`), never converges a record that is `applying` or `releasing` (`note|repair_skipped=1`), never re-applies what a re-apply cannot fix (a switched-off Windows profile, a profile Group Policy controls, a dangling pf anchor: reported, not retried every minute). Every repair, and every tick that finds the host degraded, is one line in the agent log (`firewall: repair -> active repair_tick=1 repaired=1 repairs=1`); a healthy tick and a gap the record already reports are silent. A repair trigger that cannot be registered is residue (`partial|repair_unregistered`) until a later registration succeeds. The tick's own reply is not sent to the server. A repair that fails verification is kept, not reverted (`active_unproven`, the failed proof as the `verify` row, one apply and no second flush): the next tick finds the host enforcing and does not repeat it. Another tool that keeps re-inserting its own jump ahead of ours makes the Linux iptables leg re-apply on every tick; a bound on that is tracked in #7670.

| Action | Parameters | Reply rows |
|---|---|---|
| `quarantine` | `probe_target` (`ip:port` or `[v6]:port`, a literal; optional), `ttl_seconds` (60 to 2,592,000, optional), `exceptions` (comma-separated, optional), `repair=1` (the self-check's own dispatch; it takes no other parameter, and one that also carries `ttl_seconds`, `exceptions` or `probe_target` is refused `repair_with_containment_parameters`) | `status\|<token>[\|<reason>]`, `verify\|control=<ok\|fail>\|probe=<blocked\|reachable\|refused\|unproven>`, `allow\|<kind>\|<value>`, `rolled_back\|<reason>`, `refused\|<reason>`, `note\|<k>=<v>` |
| `release` | `if_ttl_expired=1` (optional; the time-limit tick, a no-op until the TTL has passed) | the same rows |
| `quarantine_status` | none | the same rows, read from the record and the live host; never takes the mutation gate |
| `quarantine_allow` | `op` (`add` or `remove`), `exceptions` (required) | the same rows |

An exception is `addr[/prefix][:port][/tcp\|udp][/in\|out]`, with a v6 address bracketed when it carries a port. Without a protocol it covers TCP and UDP, without a direction it is outbound, without a port it covers every port; the port is the service port (the remote port outbound, the local port inbound). At most 64 exceptions exist across every add; a removal never removes loopback, the control channel, a resolver or DHCP. The mutating actions run one at a time (`status|busy` after two seconds).

### What you can decide with it

| Question | Action | Windows | macOS | Linux |
|---|---|---|---|---|
| Is the host firewall on? | `state` | Three `profile\|` rows, each `enabled`, `disabled` or `unknown`. Only Windows Firewall's own switches are read. | `state\|` is the Application Firewall only (`enabled`, `disabled`, `unknown`); pf is the separate `pf\|` row | `state\|` is `running` (firewalld), `active`/`inactive` (nftables, ufw, iptables) or `unknown` |
| Which firewall answered? | `state` or `rules` | Always Windows Firewall | `backend\|appfirewall` | `backend\|` names the first source that answered, which is not necessarily the tool an administrator uses (rules managed by another tool but held in nftables report `nftables`) |
| What is it enforcing? | `rules` | The first 100 rules: name, enabled, direction, allow or block, profile bitmask. No ports, programs or addresses. | `app\|` rows (per-app allow or block, no root needed); pf `rule\|` lines, anchors and a count (root only) | firewalld: services per active zone. nftables: base-chain hook and policy plus one handle row per rule. ufw: numbered rules. iptables: the `-S` entries. |
| Is a particular port open? | neither | No: rows omit ports, and the list is capped | No: pf lines are raw text and the per-app list is not port-based | Not reliably: firewalld lists services only, and nftables handle rows carry no match detail |

How to read the answers:

- `unknown` and `ruleset|unknown` mean the read did not complete (refused, timed out, truncated or unrecognised). They never mean "off" or "empty"; a cleanly read empty ruleset reports `ruleset|0`.
- `active` from nftables or iptables means there is at least one rule or a base-chain policy other than accept (for iptables, a user-defined chain also counts). A container runtime's own rules make a host `active`, so it is not evidence of a restrictive policy; `inactive` is reported only on a complete read.
- On Windows `enabled` says a profile's firewall switch is on, not what its default inbound action is, and on macOS an Application Firewall `enabled` does not imply pf is filtering.
- A fleet roll-up that counts `state` values should count `unknown` separately, since it hides both permission failures and absent tools.

This is the whole Linux decision. The table-dump row of a refused netlink read (`error|nftables:table:eperm`) is written only when the snapshot rung does not answer: that read saw no table, so an answer of the rung rests on the snapshot alone, its `unknown` carries the rung's own `error|` rows for what it could not read, and the refused netlink read beside them would name a read the answer does not rest on. A netlink read that saw a table holds nothing back: its rows (`fallthrough|nftables:<dump>:<reason>`, or `error|nftables:table:<reason>` when the table dump of a second pass failed) are written at once, because the snapshot rung then turns an empty listing to `unknown` on the strength of that read and writes no `error|` row of its own for it. A firewalld answer that was read only in part is written after that row and before `ufw`, when neither the nftables rung nor the snapshot rung showed an active ruleset. A refused read does not stop the ladder early except at the last rung: `ufw` falls through on any failure, while a failed `iptables -S` is final and reports `backend|iptables` with `unknown`. `backend|none` appears when no nftables table was read and neither `/usr/sbin/ufw` (exit 0) nor `/usr/sbin/iptables` (ran) answered. A host with `iptables` therefore ends at `backend|iptables`, but a host with only `ufw` whose `ufw status` fails (for example when not run as root) ends at `none`.

The macOS plugin keeps the two firewalls apart: the Application Firewall answers without privilege, while every pf read opens `/dev/pf` and needs root, so it runs through the installer's exact `sudo -n -- /sbin/pfctl` read-only lines (direct when root); an account with neither still returns the Application Firewall answer plus `pf|unknown` and `ruleset|unknown`. Each rows-publishing read is gated on a clean exit, so a partial read yields no rows rather than a partial list, and an `error|` row says which read it was (see Reading the macOS error rows).

### Reading the Linux error and fallthrough rows

| Row | Meaning |
|---|---|
| `error\|nftables:socket:eperm` | The netlink socket could not be opened or bound and the kernel answered `EPERM` or `EACCES`, typically a seccomp profile or AppArmor. A unit that denies the address family (systemd `RestrictAddressFamilies=`) answers `EAFNOSUPPORT` instead, which reads as a kernel with no nftables and writes no row; it also makes `own_addresses_unreadable` permanent (see Device containment) |
| `error\|nftables:<table or chain or rule>:eperm` | The socket opened but the kernel refused the dump; grant `CAP_NET_ADMIN` or use firewalld |
| `error\|nftables:<dump>:timeout` | A dump did not finish in its budget, usually a long nft transaction holding the table lock |
| `error\|nftables:<dump>:foreign_flood` | Another local process is writing to the same netlink family and drowning out the agent's replies |
| `error\|nftables:<dump>:errno:undecoded` | The kernel's error reply could not be decoded; treat as an undiagnosed refusal, not errno 0 |
| `error\|nftables:<dump>:truncated`, `oversized` or `io_error` | The dump exceeded the read buffer, exceeded the 4 MiB cap, or hit a socket failure; the ladder still falls through rather than report a clipped count |
| `error\|fd_exhausted` | `EMFILE` or `ENFILE` on the nftables socket |
| `fallthrough\|nftables:<dump>:torn` | The kernel flagged the dump as interrupted by a concurrent ruleset change; the ladder continues |
| `fallthrough\|nftables:generation:changed` | The table, chain and rule dumps each ended cleanly but did not carry the same ruleset generation: a commit landed between two of them. Written after the one re-run saw it again, or at once when under 2 seconds of the budget remained for a re-run; the ladder continues |
| `fallthrough\|nftables:<dump>:torn_persistent`, `error\|nftables:<dump>:torn_persistent` | Churn (torn, or a moved generation) ended three probes in a row: the ruleset is rewritten continuously, not once by a passing collision |
| `error\|ufw:unrecognised_output`, `error\|iptables:unrecognised_output` | The tool ran and finished, but its output is not in the shape the parser knows (a drifted `ufw` table, an `iptables -S` dump with no policy line or an unknown line; the snapshot's legacy sections write the same rows for a save listing the parser does not know). The state and the count read `unknown`; rows already parsed are still written. For `iptables -S`, a `#` comment line and blank lines never cause this (`ufw` output with a `#` line is not recognised) |

Which row kind carries a reason depends on the dump. A failed table dump (including `torn`) writes `error|nftables:table:<reason>`. A failed chain or rule dump, after the table dump succeeded and any re-run, writes `fallthrough|nftables:chain:<reason>` or `fallthrough|nftables:rule:<reason>` with any of the reasons above, one row for each dump that failed (a chain timeout and an oversized rule dump are two rows); two clean dumps that disagree on the generation write `fallthrough|nftables:generation:changed` (or `torn_persistent`) instead. The `error|nftables:chain|rule|generation:<reason>` form appears only on the terminal `unknown` result, again one per failed dump. A socket that could not be opened writes its `error|fd_exhausted` or `error|nftables:socket:eperm` row once per probe, ahead of any fallthrough row, however many of the dumps hit it.

An `error|nftables:table:<reason>` row can appear next to a later successful `backend|ufw` or `backend|iptables`: it is written before those rungs run, once the snapshot rung has not answered (or the moment the dump fails, when the read had already seen a table, and then it can also stand before a snapshot answer). Only a terminal `unknown` after it means no backend could answer.

### Reading the Linux snapshot rows

| Row | Meaning |
|---|---|
| `error\|snapshot:connect:eacces` | The socket exists but the agent account is not in its group (`yuzu-agent`) |
| `error\|snapshot:connect:refused` | A socket file exists and nothing is listening on it. Measured on Rocky 9.9 (systemd 252): `systemctl mask --now yuzu-fw-snapshot.socket` alone leaves the file and reads this; stop the socket and then mask it, or remove the stale file |
| `error\|snapshot:connect:busy` | `EAGAIN` from the non-blocking `connect`: the socket's listen backlog is full; the read is not retried. A connection over `MaxConnections` is not this row: systemd accepts it and closes it at once, and it reads as `empty` |
| `error\|snapshot:connect:errno:<n>` | Any other `connect(2)` failure |
| `error\|snapshot:peer_not_root` | The socket was not created by root (its peer credentials say so), so none of it was read |
| `error\|snapshot:timeout`, `error\|snapshot:io_error`, `error\|snapshot:oversized` | The 5 second deadline passed, the socket call failed, or more than 4 MiB came back |
| `error\|snapshot:empty` | The broker accepted the connection and sent no byte (its service could not start, or the connection limit was reached) |
| `error\|snapshot:truncated`, `error\|snapshot:malformed` | The reply has no end line (the listing was cut at 4 MiB, or the stream ended early), or it is not the three headed sections in order |
| `error\|snapshot:gone` | The first snapshot of the read was `inactive` and the second found no transport: no socket file and no usable installer helper (on a packaged host the socket was stopped, removed or failed between the two reads; on an installer-provisioned host the helper file was removed or is no longer executable). The answer is `unknown` with no count, never `inactive` |
| `error\|snapshot:helper:<token>` | The installer helper's `snapshot` word, run through `sudo -n --`, did not complete: `timeout`, `truncated` (the output was clipped), `not_run`, or `exit:<n>`, the status sudo or the helper exited with (`exit:1` is a sudo that refused). A host with no helper file makes no sudo call and writes no row |
| `error\|nftables:snapshot:failed` | The nftables listing exited non-zero. The nf_tables ruleset was not read: the state reads `unknown` unless a legacy section that was read shows content |
| `error\|nftables:snapshot:absent` | The `nft` command is not installed, so the nf_tables ruleset was not read. It is never evidence of an empty ruleset: with no content in any section that was read the snapshot rung declines and writes only this row (and the rows of the other unread sections), and the ladder goes on; with legacy content the answer is `active` with `ruleset\|unknown` |
| `error\|nftables:unrecognised_output` | The nftables listing is not text this parser fully understands. `state\|unknown`, `ruleset\|unknown` |
| `error\|iptables:snapshot:failed`, `error\|ip6tables:snapshot:failed` | That legacy save tool exited non-zero, or `/proc/net` could not be stat'ed (the section is then `[failed]` and no tool is run); the family was not read and cannot read `inactive` |
| `error\|iptables:snapshot:absent`, `error\|ip6tables:snapshot:absent` | The family has no legacy save tool and the kernel's own list of its tables names at least one table: tables exist that nothing listed, so the family was not read. No count, never `inactive` |
| `error\|iptables:unrecognised_output`, `error\|ip6tables:unrecognised_output` | The legacy save listing completed in a shape the parser does not know |
| `rule\|ip6\|<kind>\|<chain>\|<spec>` | An IPv6 entry of a legacy `filter` table. The second field of a legacy row is one of nine fixed words (`ip6`, the four tables below, the four kinds `policy`, `new_chain`, `append`, `unknown`), never another backend's word |
| `rule\|<table>\|<kind>\|<chain>\|<spec>`, `rule\|ip6\|<table>\|<kind>\|<chain>\|<spec>` | An entry of a legacy table other than `filter` (`nat`, `mangle`, `raw`, `security`, the only other table names the parser admits): the table's name stands before the kind. The tables and the kinds are two closed sets of fixed words, so neither can take another backend's row (`rule\|nftables\|...`, `rule\|firewalld\|...`) |

A legacy section holds the output of the family's legacy save tool, `iptables-legacy-save` or `ip6tables-legacy-save`, run with no argument: every instantiated table as `*<table>`, `:<chain> <policy> [<packets>:<bytes>]` lines, `-A` lines and `COMMIT`, between two comment lines that carry the date. The parser accepts a subset of that shape: a table is one of `filter`, `nat`, `mangle`, `raw`, `security`, each once, and every chain and append line closes its double quotes (a newline inside a rule comment leaves its line open, so the listing is unread); anything else reads `error|<tool>:unrecognised_output`. Only what stands between double quotes is covered: a field outside them (an interface, chain or target name) is taken as it stands, so an unpaired double quote there leaves the line open and the listing is unread on every read until the name changes, and a newline there reads as a line break, which can add a line (a row and a count) and never removes one. A tool that exits 0 and prints nothing is a family that holds no table. The script makes two decisions before any tool runs, from host state: when `/proc/net` cannot be stat'ed the section is `[failed]` and no tool is run (a save tool reads a missing table list as no table); and when the family has no save tool the section is `[tables]` followed by the kernel's own list of that family's tables, one name per line, read with `head -c 4096` (`ip_tables_names` for IPv4, `ip6_tables_names` for IPv6; the file is there exactly while the family's core kernel module is loaded). `[tables]` alone is a family that holds no table, a name after it is tables nothing listed, and a list that cannot be read is `[failed]`. A list file that cannot be stat'ed is read as no table behind the `/proc/net` check, which rules out every cause at directory level; that residual, with legacy `arptables` and `ebtables` tables, which no read of this plugin lists, is outside what `inactive` says (ADR-3007 clause 6). `[tables]` is honoured only as the first line of a legacy section; in the nft section or anywhere else it is ordinary text, which reads `error|<tool>:unrecognised_output`. Counters on the chain lines are parsed and never read. On Ubuntu 26.04 `/usr/sbin/iptables-legacy-save` and `/usr/sbin/ip6tables-legacy-save` exist; Rocky 8.10 ships no legacy binary. Whether `/proc/net/ip_tables_names` exists on a stock EL host is not measured.

A socket file that is absent (no package, or a socket that was stopped and then masked) says nothing: the rung tries the installer helper's `snapshot` word where that applies and otherwise declines, and the ladder goes on. A host that opted out therefore answers from the ladder without the snapshot rung, after the error rows of the reads it was refused (`error|nftables:table:eperm`): a firewalld host with firewalld's own rows (`backend|firewalld`, `state|running`, `ruleset|unknown`), another host with `state|unknown` and `ruleset|unknown` from `ufw` or `iptables` (`backend|none` when neither ran). A host with no helper file makes no sudo call and writes no `error|snapshot:` row either. A sudo that refuses the helper (exit 1) is a failed read of a provisioned transport: `error|snapshot:helper:exit:1`. On a packaged host with no socket file the read answers as a host that opted out does (above): the refused netlink read's row, then firewalld's own rows or `unknown`, and no row that names the snapshot. The file is gone when the socket was stopped, was masked before it ever started, or has failed (`systemctl status yuzu-fw-snapshot.socket`; `systemctl reset-failed yuzu-fw-snapshot.socket` and `systemctl start yuzu-fw-snapshot.socket`; `journalctl -u 'yuzu-fw-snapshot@*'` shows each instance). A socket fails when systemd's activation limit is passed, more than 200 connections inside 2 seconds with those refused at `MaxConnections` counted (measured on Rocky 9.9, systemd 252: `Result=trigger-limit-hit` and the socket file removed; on Ubuntu 26.04, systemd 259, 600 connections at once did not fail it). A `state` or `rules` read makes at most two connections.

### Reading the macOS error rows

| Row | Meaning |
|---|---|
| `error\|appfirewall:globalstate:<token>` | `socketfilterfw --getglobalstate` did not complete; the `state\|` row above it reads `unknown` and no `mode\|block_all` row is written. A read that completed but whose text is not recognised is `state\|unknown` alone, with no error row |
| `error\|appfirewall:listapps:<token>` | `socketfilterfw --listapps` did not complete; no `app\|` rows are written |
| `error\|pf:info:<token>` | `pfctl -s info` did not complete, typically because the agent has neither root nor the sudo grant (`exit:1`; see the note below this table); the `pf\|` row reads `unknown`. `pf\|unknown` comes with this row when the read did not complete, and alone when it completed but said neither `Status: Enabled` nor `Status: Disabled` |

| `error\|pf:rules:<token>` | `pfctl -s rules` did not complete; no `rule\|` rows are written and the count reads `ruleset\|unknown`. `ruleset\|unknown` appears if and only if this row does |

`<token>` is `not_run` (the tool never started), `timeout`, `truncated` (its output was clipped) or `exit:<n>` (it ran and exited non-zero). A timeout outranks a clipped output, which outranks an exit code. Each error row sits right after the row it explains, or where the rows it replaces would have been.

On a non-root agent, `exit:1` on a pf read means sudo refused the grant (the account has no `/sbin/pfctl -s <word>` line) or `pfctl` itself failed: the two look the same because stderr is dropped by design, and the row grammar does not tell them apart. `install-agent-user.sh --check` reports a sudoers file that lacks a line.

### Where the data goes

- **Instruction result only.** Rows land in the ResponseStore (90-day default retention), queryable at `/api/responses/{id}`; `security.firewall.state` aggregates by `state` and drives the fleet pie "Firewall profile state across the fleet" (profile rows, labelled by value).
- **Not consumed by** daily-sync inventory, the Echo warehouse, DEX, or metrics. Both definitions carry a gather TTL (120 s and 300 s) but no schedule; they run when dispatched.
- **Sensitivity.** `rules` rows name installed applications on the host (Windows rule display names are application names — an installed-software inventory by another route; macOS `rules` rows carry the same kind of disclosure via unprivileged per-app allow/block entries, `app|<path>|...`, naming installed executables by absolute path) and, on Linux, the host's network policy; on macOS, both `state` and `rules` rows may also carry pf anchor names, which can identify installed network/security software (VPN clients, security tools) or local pf policy structure — `state` is otherwise limited to the device id.
- **MCP / REST.** Discover: `discover_plugins` (summary) → `yuzu://plugin-docs` (this page as data) → `discover_instructions` / `get_definition("security.firewall.state")`. Run: `execute_instruction {definition_id, parameters}`. Read: `/api/responses/{id}`.
- **Containment state.** `quarantine.state` (the phase, generation, allow set, probe target, TTL, the iptables generation, the counts of Windows rules the policy store would not disable or would not delete, the macOS flag for a failed pf state flush, the flags for a time-limit or repair trigger that could not be registered, how many times and when the self-check re-applied the host, and on macOS the pf enable token with the boot it belongs to; a key a newer build wrote is skipped on read, so a downgrade still reads the record) lives in the plugin's SQLite key-value storage on the endpoint, as do the Windows restore images `win.prior_firewall_policy` and `win.disabled_rules` (the latter holds one line per rule, `<flag>|name|direction|profiles|protocol|action|local ports|remote ports|program|service`, under a `v=3` header; the flag is `1` when no other rule, on or off, carried that name, direction and profile when the rule was disabled, and `0` otherwise). The ruleset a privileged tool loads is staged for the length of that call in `<agent.data_dir>/firewall-staging` (0700, files 0600) and removed afterwards. None of it leaves the endpoint except as reply rows.
- **Containment sensitivity.** `allow|` and `note|` rows name the control-channel addresses, the host's DNS resolvers, the operator's exception addresses and the probe target, which together describe the network the device sits in. The Windows disabled-rule list holds rule display names (installed application names) but is kept on the endpoint and never echoed.
- **Siblings:** `rdp_control` (toggles the Remote Desktop rule group through `INetFwPolicy2`), `network_config`.

## Caveats and known gaps

1. **The read actions' row shape and coverage are limited.** The server clamps `state` and `rules` to two fields, so a `profile|Domain|enabled` row reaches the dashboard as key `profile`, value `Domain|enabled` (#626). Windows `rules` stop at 100 (the `truncated|true` row appears only when a genuine 101st rule exists; `state` reports the true total) and omit ports, programs and addresses. macOS pf reads need root and no capture has used root, so the samples show the unprivileged answer (`pf|unknown` with its `error|pf:` rows); the Application Firewall `state|` and `app|` rows are unaffected. The firewalld leg has never run against a live firewalld and lists services only, and the unprivileged nftables denial path is reasoned from the code, not measured. The Linux snapshot broker has its own limits: a listing over its 4 MiB cut reads `error|snapshot:truncated` and `unknown`, never a shorter ruleset (the root netlink dump has the same number as its cap, for a different encoding, so a ruleset can fit one and not the other); iptables older than 1.8 has no `iptables-legacy-save` name, so on such a host the family reads `unknown` when legacy tables exist; `/usr/sbin/iptables-legacy-save` and `/usr/sbin/ip6tables-legacy-save` exist on Ubuntu 26.04 and Rocky 8.10 ships no legacy binary, and whether `/proc/net/ip_tables_names` exists on a stock EL host is not measured; two reads can make the kernel load a module, both measured on Ubuntu 26.04 (ADR-3007 clause 3): an nft read on a host where nf_tables is not loaded makes the kernel load nf_tables, and a legacy save tool that asks for a table whose module is not loaded makes the kernel load that module (an empty table), which the broker's reads reach only when a table is removed while a read is under way; neither can be avoided: skipping nft needs proof that nf_tables is absent, which a kernel that builds it in does not give, and nothing the script can test closes the time between the kernel's list and the tool's request; a host with no `nft` command has nf_tables read through nothing, so the rung declines and the ladder's own `unknown` follows or, with legacy content, it answers `active` with no count, and the real fix is the package depending on `nftables` or a compiled netlink reader; `inactive` is answered only when all three sections were read and none shows content, in two snapshots taken one after the other; a rule count is written whenever all three sections of the answering snapshot were read and the netlink read did not turn the state to unknown. Legacy `arptables` and `ebtables` tables, which no read of this plugin lists, are outside that answer, as is a family whose table list cannot be stat'ed while `/proc/net/dev` can (read as no table), and rules that move between rulesets more than once inside one read can be missed (the count of an `active` answer is one pass of three reads); `IPAddressDeny=any` in the broker's service unit takes effect only on hosts with the unified cgroup hierarchy (defence in depth: the address-family list is what bounds its sockets, and it is parsed and not enforced on Rocky 8.10); and the agent account can read the whole ruleset through it.
2. **A containment is only as proven as its probe.** Without a `probe_target` the block is reported `active_unproven`: the agent can show the control channel works, not that anything else is blocked. The resolvers are read on the host being contained, at quarantine time (the same trust window #3429 closed for the server address), bounded to eight and to port 53, and listed in the reply (recorded in the stored response). The boot-time re-apply cannot roll back on an unreachable server, so an allow set that stopped matching the server's address strands the host until a `release` dispatch reaches it, a configured `ttl_seconds` limit runs out, or the later break-glass lifts it. The control set follows the address the agent is connected through at quarantine time; a server re-addressed AFTER the containment still strands the host (its new address is blocked before the agent can learn it), and a `quarantine_allow` then answers `update_failed|control_unreachable` while the live peer is outside the stored set. The self-check re-apply admits the live peer itself (`note|control_live_peer=<ip:port>`) and, if the proof still fails, keeps what it applied as `active_unproven` rather than reverting. Without a `ttl_seconds` limit there is no local release. **A time limit rides the host wall clock while NTP is blocked**: a clock stepped back means it never fires (`note|clock_before_apply=1` on the status says so) and one stepped forward releases early. **An expiry release is logged on the agent** (`firewall: release -> inactive ttl_expired=1`) **and the server learns of it only from a status read**: a device-reported time limit never ends a server-applied record, so the server reads that `inactive` answer as drift and contains the host again (a host that refuses the apply is not contained again: its re-apply is refused); after a limit passes an operator should still check `quarantine_status` (the owner's decision is to keep the time limit and document these two limits; tracked in #7436). The resolvers are read once, at apply: a host whose DHCP or roaming changes them loses DNS until the next `quarantine_allow` or re-apply, and a server given as a hostname cannot re-resolve.
3. **Windows containment has known edges.** Rules the policy store refuses to disable (Group Policy or MDM) stay enabled, so on a hardened domain host the result may never read `active`. A Windows Firewall profile switched off refuses containment (`firewall_disabled:<Profile>`): enable it by policy first, the plugin does not switch it on. A stale-generation rule that will not delete leaves the result `partial|stale_rules_left`. Rule names are not unique in Windows Firewall, so each rule is remembered by every property that tells two apart (name, direction, profile, protocol, ports, program, service, action); two rules identical in all of them are indistinguishable, and a disabled one of the pair is re-enabled with its twin on release (when both were enabled and one is edited during the quarantine, the untouched one comes back with the key, the edited one stays off and the release reports nothing: a rule left off is never more open than before); two rules that differ only in their addresses, interface types or edge traversal (none of which is in the key) share a key and are re-enabled together. A rule edited during the quarantine changes its key, and the release then falls back to name, direction and profile only for a rule that was the only carrier of them (on or off) when the quarantine switched it off, which the stored list records per rule, and only when exactly one rule in total carries them at release: switched off, it is switched on (`rules_reenabled_by_identity`); already on, it is accounted for (`rules_accounted_enabled`). Nothing is switched on for a rule that shared its name, direction and profile with another when it was disabled (so a rename, or a direction or profile edit, of a rule that had a same-named sibling off before the quarantine can never make that sibling look like it), for one with more than one carrier at release (the edited rule beside an untouched twin), or when the only carrier is already claimed by another listed rule; the release reports `partial|rules_unmatched`, so the fallback never switches on a rule that was off before the quarantine, outside the one case below. One case cannot be told apart: a listed rule that was the only carrier of its name, direction and profile when it was disabled and then LEFT that identity during the quarantine (deleted, renamed, or moved to another direction or profile), beside exactly one rule that ENTERED that identity during the quarantine (created, or renamed or re-profiled into it). The entering rule reads as an edit of the listed one: if it is off it is switched on (`rules_reenabled_by_identity`), although it may have been off before the quarantine under another name; if it is on it is accounted for. It is disclosed, not fixed. A host where Group Policy or MDM controls any of the three profiles is refused (`gpo_override:<Profile>`): a rule or default written locally takes no effect there, so the plugin contains nothing and changes nothing; if the policy arrives mid-quarantine the status reads `degraded|gpo_override`. A host whose policy itself sets block and block is refused as well (a policy-set default action marks the profile controlled whatever its value). A Group Policy refresh during the quarantine can re-enable rules; the status read does not detect it. COM calls cannot be cancelled from a plugin (#1391), so the enumeration, the disable loop, the release and the status read check the operation deadline between calls (every 256 rules, every 64 removals) and give up with `deadline_exceeded`; **a single COM call that never returns (a stopped firewall service) is not bounded.**
4. **Linux and macOS containment cut more than the agent's traffic, and every OS is open before the agent starts.** On Linux the input, output and forward chains are at policy drop and the rules are stateless, so established connections that no allowance matches are cut, and a router host loses its clients' traffic through the forward chain; guests that never traverse the IP hooks (L2-bridged VMs without `br_netfilter`, macvlan and ipvlan containers) are not contained at all, and neither are Hyper-V external-switch guests on Windows. IPv6 neighbour discovery is newly allowed so an IPv6 control channel can work. On an iptables-only host the IPv6 stack is read from `/proc/net/if_inet6` and `disable_ipv6`; a stack that cannot be read counts as unknown, never as absent, so a host that may route IPv6 and has no `ip6tables` is refused instead of contained over IPv4 only. Unprivileged agents have no `CAP_NET_ADMIN`, so `quarantine_status` normally reads the table through `sudo nft list table` rather than netlink. On macOS the apply flushes the whole pf state table once (and each `quarantine_allow` update again), so connections the allow set does not cover are cut and **release does not restore them**: `Reversible` in the capability catalogue means the rules and the enable state, not every connection, and the comparison that holds after a release is the main ruleset (`pfctl -s rules`), the `Status:` line and the reference count, not `pfctl -s info` as a whole. macOS DHCP leaves only to the broadcast address (a unicast lease renewal is not allowed; rebinding falls back to broadcast) and its inbound reply direction stays open. A sibling anchor inserted later that sorts ahead of ours, or a `pass quick` rule before the anchor line in a customer's `/etc/pf.conf`, defeats the macOS containment; the first reads `degraded|anchor_not_first`, the second is only caught by the probe. A crash between `pfctl -E` and the record write leaks one pf enable reference until reboot (visible as `note|pf_references=<n>`). macOS resolvers come from `/etc/resolv.conf`, so per-interface scoped resolvers are not read, and the `-s References` and `-a com.apple -s Anchors` output layouts are not yet confirmed on a live host (they only add notes or a degraded reason). Allowing DNS to the configured resolvers also allows DNS tunnelling through them, on every OS. Finally, nothing persists a containment at OS level: between boot and the agent's start the host is uncontained, and a host whose agent fails to start stays so.
5. **The four containment actions are the protective set, and the server drives them.** They are in the closed protective set that no enablement gate may refuse (`common/include/yuzu/protective_actions.hpp`): a kill switch, a per-OS withhold, a plugin-presence filter or a degraded plugin-config read never refuses `quarantine`, `release`, `quarantine_status` or `quarantine_allow`, so none of those gates keeps a contained host from being released or repaired remotely. The host itself can: a Linux host on the packaged systemd unit refuses every mutating containment action (`privilege_unavailable`), so its record stays unconfirmed or releasing until the installer's sudoers grant is available to it. A containment is released wherever the agent can elevate; on the packaged Linux unit `release` is refused too, so only an operator's forced end (`DELETE ...?force=true`) ends the record, and it does not release the device. The server's containment gate exempts the same four, so a degraded quarantine store never blocks them either. A plugin-level `firewall` kill-switch row still gates the ordinary `state` and `rules` actions. The self-host check compares addresses only: a server that runs in a container or a VM on the same host and is reached at a bridge address (for example `172.17.0.2` behind `docker0`) is not one of the host's own addresses, so that host can still be contained and the server reaches it only through the allow set. NAT, floating and port-forwarded addresses are not seen either. Such a host has `forward` at policy drop with no rules, so forwarded traffic is dropped and the server's published ports vanish for the whole fleet while the containment stands; a server apply carries no time limit, and the 60 second repair puts back a table removed by hand. A host that runs the server while its agent reaches a remote gateway or VIP passes the check the same way, and its new inbound connections are dropped. The exits are `DELETE /api/v1/quarantine/{agent_id}` while the API is reachable, otherwise console recovery (the steps are in `docs/user-manual/security-hardening.md`, "A device that is its own server refuses new containment"). The server keeps the record: the MCP tool dispatches `quarantine` and a record created over REST is applied by the reconciler; the reconciler re-applies the stored allow set (as `exceptions`), reads `quarantine_status` to confirm and to re-verify every five minutes, and ends a record only on the device's `inactive` after a `release`, or by an operator's forced end, which does not release the device. This build neither removes nor detects firewall rules or Windows rule names left on a host by an earlier build.
