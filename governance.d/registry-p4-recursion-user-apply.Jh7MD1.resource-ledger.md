# Resource Ledger -- registry 2.1.0 (recursive delete_key, per-user hive writes, declarative apply)

Range described: `430bc85a2..3475ee75c` (branch `feat/registry-p4-recursion-user-apply`, the governance r1 fix round included), plus the PR review-round fixes `1c0ed1175..2810cbd3f` made after the dev merge `5e105eacf` (rows 5, 5a, 6, 7, 11 and table 2 below were amended for them; no new resource kind). This is a DELTA ledger over `governance.d/registry-pr3-typed-writes.Xt7Qpa.resource-ledger.md` (the base fragment) and `governance.d/registry-pr3-hardening.qfUWmU.resource-ledger.md` (its first delta). It restates only the rows this change adds or modifies. **Base rows 2-8 and 10 are unchanged in kind** (row 1 `Owned`, row 2 `Opened`, row 10 the creating walk's `made` stack and rollback keep their contracts; the two changes to them are listed below as rows 1 and 2 of this fragment). Symbols are cited by file and function; line numbers move with every edit.

## Summary

The plugin still owns one kind of production resource: an open registry key handle. This change adds four new ways to hold one: a stack of handles during a recursive walk, a per-plan cache of checked handles, a one-shot create-access probe handle, and a write through a mounted per-user hive (which brings the existing mount, privilege, lock and flush machinery onto a write path). It adds bounded in-memory structures that live for one `apply` call (the undo budget, the retained values of the item in hand, the dry-run create simulation) and one `nlohmann::json` document per plan parse; `apply` writes its rows through a sink (`LineSink`) as each item concludes instead of holding them. The shared hive-file guard (`agents/shared/win_hive_file_guard.hpp`, `win_hive_file_probe.hpp`) reads one more fact from a handle it already holds (the leaf's link count) and acquires nothing new. No fd, SOCKET, `FILE*`, SQLite, OpenSSL, BCrypt, thread, callback, subprocess or timer is added in production C++. The server side adds no owner (catalogue rows, the six-action binding array, enablement units and comments only).

The test side adds Windows-only owners: salted temp directories, LocalAlloc'd security descriptors and SIDs, offline hive mounts, privilege scopes, a synthetic HKLM `ProfileList` row and a deny-ACE restorer. Every one is RAII-owned; the one manual close the first draft of this change had (governance CS-3) is now an `Owned` guard (row 12).

## Items checked and not applicable

- **`RegDeleteTreeW`:** not used in production (it follows links); appears only in test cleanup.
- **Threads, callbacks, subprocesses, timeouts:** none added. `apply` and the recursive walk have no wall-clock deadline; work is bounded by `kMaxPlanItems` (256), `kMaxTreeNodes` (10,000) and `kMaxTreeDepth` (600) (governance P1 records the plan-wide aggregate).
- **Server:** `kRegistryMutatingActions` (`std::array<..., 6>`), the catalogue rows and `kUnitOs` (`std::array<..., 236>`) are compile-checked sizes; no store, lock, pool lease or thread.
- **Ownership-type changes:** none (no `unique_ptr` / `shared_ptr` change).

## Accepted risks

Residuals this change ships knowingly; each is stated in the README and the user manual.

- **`apply` is not transactional.** `continue_on_error=false` stops at the first refused or failed item; the undo manifest in the reply is the way back (owner decision, grill).
- **The undo manifest is a capture-time snapshot of values only** (governance SG-2, UP-1: the key's security descriptor, class and volatility are not captured; capture is a follow-up issue).
- **The base fragment's B3 (secret values in `old=`/`new=` hex) now extends to the undo manifest, the `apply` plan and the per-user write parameters** (governance D-1, CO-4: disclosed in this change in the README "Sensitivity" bullet and audit grammar, `docs/user-manual/audit-log.md`, the enterprise-readiness register row and the routed security-posture row).
