# Resource Ledger -- Echo registry source, offline (unloaded) per-user hive reads

Scope: the registry source now baselines and diffs the curated per-user roots of profiles whose hive is not loaded, by mounting the hive file through the shared guarded ladder (`yuzu::win::with_user_hive`: default-on hive-file guard, the process-wide offline-hive lock, SeBackup/SeRestore scope, live arm wins if the user logged in meanwhile). This ledger covers only what the change adds or alters; the registry source's key-watch, ETW and cursor owners are in `echo-registry-live-source.KttYnZ.resource-ledger.md` and `echo-registry-live-etw-attribution.ztWpFV.resource-ledger.md`, and the hive-mount residuals this change shares with the mapped-drive walk are accepted in `5291-hive-file-guard-default.gTuSZf.resource-ledger.md`. Files: `agents/plugins/echo/src/echo_registry_source.cpp` (`read_offline_hive_bounded`, `discover_offline_profiles`, `collect()`), `echo_registry_parsers.hpp`, `echo_hive_mount_gate.hpp`, `echo_mapdrive_collector.cpp`.

## Summary

No new handle type, thread type, subprocess or temp file. The change adds one detached bounded worker per offline hive mount (the same `bounded_call_ex` shape the mapped-drive walk already owns), reuses that walk's in-flight counter and module pin (moved to a shared header so there is one counter per plugin DLL), opens up to five subtree roots from the one mounted hive root with RAII `RegKey` owners, and adds two persisted fields to the existing `echo_cursor` row.

## Accepted residuals

- **A stuck `RegLoadKeyW` holds the process-wide offline-hive lock and SeBackup/SeRestore for as long as it hangs.** The caller waits at most 30 s and halts further mounts, but the detached worker cannot be cancelled; every other `with_user_hive` caller queues behind it. The module pin and the shared in-flight gate stop a later mount from either source from piling on. Same acceptance as the mapped-drive walk (`5291-hive-file-guard-default.gTuSZf.resource-ledger.md`), now shared with it.
- **Tick cost and fairness.** The loaded roots (HKLM and the loaded hives) are read first and keep the whole 10 s snapshot budget as before; the offline hives take what is left, deferred hives first and then the hive read longest ago (sid as the tie-break), so a queue of logged-off profiles can never starve a loaded root, and a notified loaded root is read in the tick that sees it. At about one mount per budget second the tail of a long list is deferred to later ticks (visible as `registry_offline_roots_deferred`) and there is no guarantee that every hive is read within the hour: that depends on the budget the loaded reads leave and on the cost of each mount. One tick can still overrun by one 30 s mount bound. The mount cost on a real host is not yet measured (tracked in the issue drafts). `registry_offline_roots_deferred` is 0 on a small host, non-zero for part of every hour on a large one, and never 0 above roughly 120 hives at an assumed second per mount.
- **Shutdown waits out a pass.** `shutdown()` takes `collect_mu_` before it stops the source, and `collect()` runs under that lock for the whole pass, so `stop()` never runs mid-pass in the plugin host and a pass is not interruptible: a shutdown waits for its queued offline mounts (each bounded at 30 s) against the agent's 20 s shutdown guard, and a mount can still be live at the hard-exit. Moving the offline mounts out from under `collect_mu_` is tracked in the issue drafts.
- **A closed mount gate (a failed module pin, or a worker abandoned on a timeout that is still running) pauses every offline read** and is silent per hive (not-attempted, retried next tick); it is logged once per open -> closed transition, and `registry_offline_roots_deferred` shows the backlog.
- **Profile-list walks.** `ProfileList` is walked on every tick while the last walk was incomplete or an entry has no path yet, and also on every tick on a host with NO logged-off profile (the cursor list is empty); otherwise only on the hourly tick or an HKU name-watch mark. A host with more entries than the walk's 512-entry cap is incomplete on every walk: the profiles the walk reaches are discovered (an incomplete walk adds but never removes), the rest are not, and `registry_offline_discovery_incomplete` stays `1`. A walk that would remove a known profile, or one that was loaded last tick, or would fill or change a known profile's path, is confirmed by one more walk in the same tick: the profile goes only when both complete walks omit it (a profile either walk lists is kept), and a path first learned or changed is taken only when both walks list the SAME path (otherwise its previous entry stands, a pathless one staying pathless and deferred), because the enumeration is index-driven and a concurrent change can skip a healthy profile, or its `.bak` sibling so that a temporary profile's folder is listed alone; the root-cause stability check inside `enumerate_profile_list` (a shared header) is a follow-up. A `<sid>.bak` record counts as proof that its base sid exists and is never mounted under the `.bak` name; virtual service SIDs (`S-1-5-80/82/83/90/96-`) and the well-known system SIDs (`S-1-5-18/19/20`) are never offline profiles, and one whose hive unloads leaves scope silently. The path that a profile's record lists beside its `<sid>.bak` leftover (a temporary profile) is never mounted: a profile with a known path keeps being read from that path, while one with no path (a known entry still pathless, which `registry_offline_roots_deferred` counts, or a sid first seen beside a stale leftover, which nothing reports) is not read while the leftover exists. Because an incomplete walk never removes scope, a profile deleted from a host past the 512-entry cap is never dropped.
- **Roaming and redirected profiles are never read.** The guard refuses UNC and non-fixed paths; the result is one `gap:unreadable` row PER ROOT (up to five per hive; five times the number of such profiles at the transition) naming the token, and an hourly re-attempt. After a restart the settled offline hives are not re-mounted (the restart reconcile is for loaded roots); a hive refused at its first sight waits for the hour like any refused hive.
- **A hive whose read keeps hitting the budget (`Capped`) is mounted again on the next tick** and every tick while it stays Capped (a first Capped read is never trusted as a baseline). The curated offline subtrees are small, so this usually means the mount landed near the deadline; but a hive with more than 32 child keys that deny read access, or a root past the 20000-key or 50000-value caps, stays Capped for good and costs one mount on every tick, and one extra baseline write on every tick as well when its first read was the capped one (only a fresh capped offline root is re-marked unbaselined); the cost is one mount per tick, not per root.
- **Racing a logon.** The exclusive hive load holds the profile's `NTUSER.DAT` for the span of one mount (expected to be short but not measured, up to the 30 s wait bound plus the worker's remaining time on a hang). A user who logs on, or a scheduled task / service that loads the same profile, in that span can fail to load it and be given a temporary profile; the live arm of the ladder wins only when the hive is already loaded at the start. This is the residual the mapped-drive walk already accepted (`5291-hive-file-guard-default.gTuSZf.resource-ledger.md`) at a one-shot cadence; here it recurs hourly for every logged-off profile. `RefCount > 0` is already covered by HKU membership, and no cheap reliable pre-check of `State` exists; measuring the hold on a real host and a pre-load share probe are tracked in the issue drafts.
- **Privilege.** SeBackupPrivilege and SeRestorePrivilege are enabled for the span of each mount, on the hourly tick for each unloaded profile in scope, on first sight of a newly found profile, a re-baseline or re-enable and a never-read hive, and on every tick for a capped, deferred or retried hive (`PrivilegeScope`, restored on exit), where the mapped-drive backfill did so once. Documented in the Echo README and `docs/agent-privilege-model.md`.
- **Data exposure.** The values under the five curated roots of OTHER, logged-off users are stored unmasked, exactly as for loaded hives: in `echo_state` baselines (uncapped in count, at most 512 bytes of text per value), in `$Registry_Live` (row-count retention) and, for the `[sid, ProfileImagePath]` list, in the cursor row; all are readable through `echo.sql` by `Infrastructure:Read` holders and erased by `echo.purge_source` on the paused `registry` source. Offline rows fall under `$Registry_Live`'s 500000-row default retention; the cursor `offline` list is not capped in number and persists until the purge or the profile leaves scope.
- **No per-mount audit record.** A successful mount leaves no row or log line; the latest `read_end` and status per root in `echo_cursor` are the only trace (stated in the Echo README and `docs/agent-privilege-model.md`). A failed unload is logged each time (info) and alerted once (warn).
- **The Windows shell is exercised only by the `[windows]` live cases.** `read_offline_hive_bounded` and `discover_offline_profiles` cannot be compiled or run off Windows; the `registry live:` cases cover them and SKIP, naming the reason, when the runner's token cannot save or load a hive, so a green suite on a non-elevated runner is not evidence for the shell. The portable core (the due rule, the lifecycle over an injected reader, and `classify_offline_discovery`, the pure classification of a profile-list walk) runs on every OS; only the gathering of Win32 facts is shell code.
