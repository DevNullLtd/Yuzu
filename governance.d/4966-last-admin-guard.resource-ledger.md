## Summary verdict

Production: no new fd, `FILE*`, SOCKET, `sqlite3*`/`sqlite3_stmt*`, OpenSSL object, BCrypt handle, allocated C string, subprocess, temp path, mapped library, callback context or thread. The owned
resources are pooled Postgres connection leases, transactions and the row locks taken inside them (all RAII through `PgPool::Lease`, `PgTxn`, `PgResult`), one process-lifetime function-local
static (`RefusalLogThrottle`, bounded, mutex-guarded), the two pre-existing process-wide Group mutexes (`kRecomputeMu`, `kGroupMutationMu`), and plain value members and locals (the lifecycle lock
timeout; the recompute loop's tallies and its capped name lists). The one owner WITHOUT an RAII owner is the manual unwire `set_rbac_store(nullptr)` in `stop()` paired with the borrowed
`RbacStore*` it clears. Further borrowed raw pointers are RECORDED and are non-owning by design: `AuthManager::metrics_` (R3), `DeprovisionCtx`'s three pointers (R4), the captured
`analytics_store` (P16) and the `named` out-pointer of the recompute (R6). Nothing else in production C++ is released by hand.

Tests: raw libpq usage is confined to RAII wrappers (`PgPool::Lease`, `pg::PgConn`, `pg::PgResult`). Every test thread is owned by `yuzu::test::Workers` (join on scope exit, release callback first);
the only `std::thread` ADDED by this range is the `std::vector<std::thread>` inside `Workers` itself (checked by grep over the added lines of `tests/unit/`: no bare `std::thread`,
`std::jthread` or `std::async` appears in any added test line). Every fault injection is an RAII `SqlFault` (idempotent noexcept repair in the destructor). Three gaps recorded earlier (F1, F2 and F5) are fixed; F3 and F4 remain listed in
"Recorded, not fixed", with F6 and F7 (accepted as they are); none is a leak in production code.

## Recorded, not fixed

- **F1 (tests): FIXED in the PR-A fix round. `PrincipalLockGate::release()` could throw from a destructor.** It is called from `~PrincipalLockGate()` (implicitly `noexcept`) and as a `Workers` pre-join callback, and builds a `std::vector<std::string>` argument for `exec_params`, so a `bad_alloc` there would have terminated. The unlock is now wrapped in `try/catch (...)` with a stderr line (`test_principal_lock_gate.hpp:128-148`), the same shape as `HeldLocks::rollback()` and `SqlFault::repair()`.

- **F2 (tests): FIXED in the PR-A fix round. The burst case could hang if thread creation threw between the two `add` calls.** The `Workers` callback is now `[&] { go = true; }` (T16), so `~Workers` releases the spinning threads before it joins them.

- **F3 (production): `NamedMembers::add` does not cap a name's length.** `log_token` replaces bytes but does not shorten; the 20-name cap bounds the COUNT. The names come from stored SCIM usernames (validated to <= 64 bytes when the account is created) or from `scim_id:<hex id>`, so the audit detail stays small in practice, but that bound is upstream of this struct.
- **F4 (production): the `RefusalLogThrottle` table is shared by two key families** (refusal keys by username, pre-check keys by `precheck:` prefix) under one 1024-key cap, so many distinct pre-check usernames can demote refusal log lines to debug while the table is full of live keys. The audit rows and counters are unaffected.

- **F5 (production): FIXED in fix round 2. The breadcrumb (R15) used to do up to 20 sequential `get_by_scim_id` reads (each up to the 1500 ms `kReadTimeout`, `scim_store.cpp:32,374-380`, so up to 30 s) inside the per-process Group lock before the first demotion.** It now performs no store read; what remains is O(N) `unordered_set` work over at most 5000 members, which the exact removed-member count needs, plus one log write and flush.

- **F6 (production): `recompute_members` has no `try`/`catch` around its loop.** A `bad_alloc` inside it escapes the handler and the request answers `500` with the membership write already committed; the signature is the mid-recompute row of the crash table (the breadcrumb and partial per-member rows, no summary row). Accepted, no change.

- **F7 (production): a demotion that meets an account deactivated concurrently lands in the `Failed` class.** Every `UpdateRoleOutcome` other than `Updated` and `LastAdministratorRefused` takes the failure arm (`scim_routes.cpp:1198-1247`), so a `NotFound` or `InactivePromotionRefused` answer can raise a critical `scim.user.role_demotion_incomplete` event for an account that holds nothing. It over-reports and is harmless. Accepted, no change.

## Manual cleanup in NEW C++ (reported, not papered over)

- **M1 (production, new but conventional): `auth_mgr_.set_rbac_store(nullptr)` at `server.cpp:10436`** is a manual unwire with no RAII owner (P12). It mirrors the existing `set_credential_change_owner(nullptr)` / `set_auth_db(nullptr)`
  clears and is required because the borrowing `AuthManager` is owned by `main.cpp` and outlives `ServerImpl`. It is not guarded against being skipped; the boot self-check and `lifecycle_guard_unwired`
  fail closed on a MISSING store, not on a DANGLING one. This is the only owning resource without an RAII owner; the borrowed raw pointers are non-owning (P12 `RbacStore*`, R3 `AuthManager::metrics_`,
  R4 `DeprovisionCtx`, P16 `analytics_store`, R6 `named`).
- No other manual `new`/`delete`, `PQfinish`, `PQclear`, `PQexec("ROLLBACK")`, `unlock`, `close` or `free` was added in production C++ by this range (a grep over the added lines found none; the
  `unlock()` calls in `auth.cpp` are the existing `std::unique_lock` pattern). Every new transaction goes through `PgPool::with_txn_for`, so the rollback lives in the existing `PgTxn` RAII guard.

## Ownership notes

- There is no new ownership of a `PGconn*` anywhere in production: the two owner write methods and `AuthDB` either let `PgPool::run_in_txn` own the lease (P1, P2, P8) or hold a local `PgPool::Lease`
  (P3, P9, P10). The `auth_db_sql_helpers.hpp` helpers (P7) are deliberately ownership-free and take a borrowed connection.
- `deactivate_account` / `set_local_role` never nest a second acquire inside their transaction lambda, and neither does any helper they call. `lifecycle_failure_text` calls `pool.last_error()` (a short
  `mu_` take inside the pool) only AFTER `with_txn_for` has returned, i.e. with no lease or lock held.
- The unassign guard's counted-set lock statement (`lock_authenticatable_admin_grants`) changed shape (`ORDER BY` added); it still returns the locked ids and holds the locks until the caller's
  COMMIT / ROLLBACK, as before.
- Not determined: no ASan, UBSan or TSan run has been performed on this range, and no test was run for this ledger. In particular the concurrency-sensitive rows (P13, R6, R7, R9, T2, T16) rest on
  reading the code and on the lock order stated in the source comments, not on a sanitizer result.
