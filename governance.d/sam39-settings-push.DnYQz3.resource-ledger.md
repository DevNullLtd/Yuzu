# Resource Ledger: sam39-settings-push

Every owning boundary the C++ in `0e6a58722..HEAD` (feat/sam-39-settings-push) acquires: on the server the `CollectionSettingsPusher` and its wiring in `server.cpp` and `HeartbeatIngestion`; on the agent the `__sync__.settings` apply path (`collection_settings_agent.hpp`, `agent.cpp`, `SyncScheduler`, the `installed_software` source). No fd, HANDLE, SOCKET, `FILE*`, `sqlite3*`, OpenSSL object, allocated C string, temporary path, subprocess, thread or `dlopen` is acquired, and no new thread exists. The only `std::async` in the range is the lock probe in `tests/unit/server/test_collection_settings_push.cpp`, waited on with a bounded `wait_for`.

## Decision lines

- **No thread, no job, no timer.** Delivery is driven only by heartbeats: the hook runs synchronously on the heartbeat thread under the shared lock, as the quarantine hook does. One heartbeat per 60 s refreshes the snapshot (single flight, each read bounded by the store's acquire timeout, a failed refresh retried after the TTL). A failed membership read is not retried for any agent for 60 s, so a degraded pool costs one acquire timeout per gap, not one per heartbeat.
- **State is memory only on the server.** Every map is rebuilt from heartbeats after a restart; a lost memo costs one membership read and at most one re-send.
- **Only the plugin-wide kill switch is carried.** The pusher reads `PluginConfigStore::get_kill_switch(plugin, "")` for each collector, the same call the effective-settings route makes, so a switch set for one operating system or one action does not reach the document.
- **No version guard.** The agent compares versions and the server and agents are deployed in that order; neither end carries handling for a peer that predates the contract.
