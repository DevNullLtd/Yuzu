# Resource Ledger: sam35-wave3-mcp-twins

Every owning boundary the C++ in `0e6a58722..HEAD` (feat/sam-35-wave3-mcp) acquires: the MCP server's read context and collection-settings dependencies, the two transport-neutral API TUs (`software_read_api.cpp`, `software_collection_settings_api.cpp`) the REST routes and the nine MCP twins now both call, and their wiring in `server.cpp`. No new fd, HANDLE, SOCKET, `FILE*`, OpenSSL object, allocated C string, temporary path, subprocess, thread, mutex or background job, and no new store read: the route bodies moved into the two API TUs, and the MCP handlers call the same functions on the same stores.

## Decision lines

- **MCP handlers run on the same httplib web thread as REST.** The tool handlers are registered on `*web_server_` by `McpServer::register_routes`, so the SAM-33 and SAM-34 teardown argument (web server stopped, web thread joined, then the stores reset) covers them unchanged. The two API TUs hold no state of their own.
- **The write is ticketed at the supervised tier and denied to service-scoped tokens.** `set_software_collection_settings` is `(ManagementGroup, Write)`: the operator and read-only tiers are refused ahead of the handler, the supervised tier needs an approval ticket, and the three group-settings tools carry the default `denied` service-scope class, so a service-scoped token is refused structurally. The handler then re-checks the grant twice through the probe, writes the `requested` audit row fail-closed, and audits the outcome.
- **The step-up row mirrors the REST exemption.** `set_software_collection_settings` is `exempt` in `step_up_mcp_policy.hpp`, as `PUT .../collection-settings/{group_id}` is in `kStepUpPolicy` (operational data, owner decision at SAM-34); the MCP ladder is the stricter of the two because of the approval ticket and the audit-ahead row.
