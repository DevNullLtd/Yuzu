Notes:

- Floor adjudication, recorded for the ledger: the `fs::remove(side_dest)` of the injected-copy and Windows path is a single `error_code` compensating filesystem call on a name this call created, guarded by the free-name check, `copy_ran`, the `file_exists` exclusion and a no-follow regular-file check. It acquires no held descriptor or handle, so there is no resource object to wrap and an RAII guard would add a branch, not a release; it matches the existing by-name removals in the same function (the claim release, `fs::remove(side, rm)`). Both the security and the cpp-safety review of this run ruled it not a manual-cleanup policy floor independently; recorded as adjudicated by the governance-agent reviewers, not by the change author. The same holds for the removal in the POSIX descriptor copy (`std::filesystem::remove(to, partial.removal)` in `copy_sidecar_by_descriptor`, run only when this call's `O_EXCL` create succeeded and a later read or write failed, after the destination descriptor has closed): the security reviewer proposed it as a floor candidate and the cpp-safety reviewer of governance gate 3 round 2, who is neither the change author nor the proposer, ruled it not a floor.
- By-name residual (accepted, in the banner): the free-name check, the copy and the removal are by name with no identity check between them. A writer of the agent's data directory who puts a link, an empty directory or a file at the name inside that gap can, on Windows or through an injected copy, have the copy write through a non-exclusive library copy, and on every platform have the removal act on what is there by name. It needs write access to the data directory. On POSIX the descriptor copy closes the source side and the destination create (R12 to R14); the by-name removal of a partial copy remains. On Windows `copy_file` still follows a link at its source, so the source side stays a by-name residual there (same class, same write access). A throw from `copy_file` or a throwing test seam between the check and the removal leaves the partial behind (unchanged from before the change; no production path throws).
- No lock-order or thread change: no mutex, thread, timer or callback context is added in production.

- Descriptor copy on top of the governance r1 fix round (POSIX only; Windows keeps `fs::copy_file` and its behaviour): the default sidecar copy now opens two descriptors, R12 (source, `O_NOFOLLOW`) and R13 (destination, `O_EXCL`), both owned by `yuzu::shared::ScopedFile` and closed on every path, and R14 removes the destination it created when a later step fails. This supersedes the earlier statement on this ledger that no descriptor is opened by this code, and replaces by-name residuals on the source side of the copy and on the destination create. The `FsOps::copy` seam is unchanged in signature and meaning: when set, it replaces the whole default and the earlier removal path (guarded by the free-name check, `copy_ran`, the `file_exists` exclusion and a no-follow regular-file check) still applies to it.
- Lifetime and lock order: no thread, mutex, timer or callback context is added; the descriptors and the buffer live inside one function call and nothing outlives it. The destination file is fsynced before the original sidecar is dropped (a failed flush is reported in the note and does not stop the drop); the containing directory is not separately fsynced, so after a power loss the new directory entry is not guaranteed, and the guarantee is limited to a process crash between the two steps, which leaves the sidecar in the set or at its live name, never neither.
- Governance r2 fix round (POSIX descriptor copy): a failed fsync no longer removes the finished copy. `PartialCopy` gains `unsynced` and `sync_error`, the copy retries an interrupted fsync, the caller's success note says the flush failed, and `fsync_fn` is a test seam beside `write_fn`. No resource is added: the same two descriptors (R12, R13), the same single by-name removal (R14), now reached only for a failed read or write.
- Temporary-name copy (POSIX): the default copy no longer creates the file at its quarantine name. It writes a temporary (`<name>.partial-<pid>-<n>`, R13) and publishes it with `link(2)` (R13), removing the temporary after a failed step (R14) or after the link; no descriptor, thread or lock is added, and `link(2)` adds no filesystem requirement (the claim of the database file already needs hard links and fails closed without them). The stray temporary left by a crash is the one new thing that can outlive a call; it is outside the name grammar, so the prune and every reader ignore it.
