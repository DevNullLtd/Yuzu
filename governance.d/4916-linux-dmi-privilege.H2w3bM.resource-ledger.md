# Packaged Linux agent: ambient CAP_DAC_READ_SEARCH, child clearing and DMI snapshot — Resource Ledger (governance Gate 1)

The production-code ledger for the one C++ change in this branch, `clear_child_capabilities()` and its call at the top of `main()` in `agents/core/src/main.cpp` (Linux only). The other C++ edits (`hardware_plugin.cpp` and the three plugin capability-descriptor note strings) change comments and string literals only. The shell helper, the unit and the CI script are not C++; they are listed last for completeness because they create and remove paths.

## Resource Ledger (C++)
- No new or modified fd, HANDLE, SOCKET, `FILE*`, sqlite3 handle or statement, OpenSSL or BCrypt object, allocated C string, mapped library, temp-file path, subprocess, shell string, callback context or thread, in production or test code. No manual cleanup is added or changed.
- `clear_child_capabilities()` (file-static, `noexcept`, `#ifdef __linux__`): its only objects are a `__user_cap_header_struct` and a `__user_cap_data_struct[2]`, both zero-initialised stack values with automatic storage, trivially destructible. Their addresses are passed to `SYS_capget` and `SYS_capset` and used only for the duration of each call (the kernel copies them in and out); nothing keeps a pointer past the call.
- `prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_CLEAR_ALL)`, `SYS_capget` and `SYS_capset` acquire no resource. They change the calling thread's own capability sets and return an integer status. `EINVAL` from the ambient call (a kernel without ambient support) is treated as nothing to clear; any other failure returns `std::nullopt`.
- Return value: `std::optional<std::uint64_t>` by value, holding the effective mask. In `main()` it is a local `const` value read once after the version banner by the `spdlog::info` call; no reference or view to it escapes.
- Failure path: `nullopt` makes `main()` write one line to stderr with `std::fputs` and return `EXIT_FAILURE` as its first statement, before `CLI::App`, the logger, any plugin, any thread or any other resource exists, so there is nothing to unwind. The agent never runs with the capability still inheritable.
- Thread ownership: capability sets are per thread and a new thread inherits its creator's sets, so the call is the first statement of `main()` and no thread has been created yet. A thread started by a library's static initialiser before `main()` would keep its own sets; the per-thread `CapInh`/`CapAmb` assertion over `/proc/<pid>/task/*` in `scripts/test/agent-unit-capcheck.sh` is the regression guard. In-process plugin code could re-raise inheritable or ambient capabilities; plugins are trusted code that already holds the effective set, and this is documented in the code and in `docs/user-manual/upgrading.md`.
- Exception paths: none. The function is `noexcept` and calls no throwing function. Platforms other than Linux compile none of it.

## Not C++, listed for completeness
- `deploy/systemd/yuzu-agent-dmi-snapshot.sh` creates `dmi.tmp` (and publishes `dmi` by one `mv -T`) in the agent-writable state directory as the service account via `runuser`, never as root. On any failure it removes `dmi.tmp` and `dmi` as that account and exits 0; an interruption leaves at most `dmi.tmp`, which the unit's `ExecStartPre=-/bin/rm -rf` and the helper's own first step remove at the next start. Root only reads the sources.
- `scripts/test/agent-unit-capcheck.sh` stages into `/run/<unique id>` and `/var/lib/<unique id>*` and removes them, its units and drop-ins in an `EXIT` trap. It creates the `yuzu-agent` account if missing and deliberately never removes it, because removing it would race concurrent jobs on the shared host.

## Independent ownership proof
Static proof by cpp-safety (Gate 3) at `701a038fc`: stack structs only, no fd, thread, handle or allocation, and a fail-closed exit before any resource exists. security-guardian (Gate 2) independently checked that the clear is the first statement of `main()` with no earlier thread, and that the helper never writes into the agent-writable directory as root. Dynamic: the capability check under the real unit on a Linux host (systemd 259) asserts the main process holds exactly `0x4` in `CapEff`/`CapPrm`/`CapBnd` and that every thread has `CapInh` and `CapAmb` of zero. The sanitizer jobs add no coverage here because the function allocates nothing.
