# Resource Ledger: facet value bound, deterministic facet cap, dropped-facets counter (#5623)

Covers `origin/dev..HEAD` on `fix/5623-facet-value-bound`.

No fd, HANDLE, SOCKET, `FILE*`, OpenSSL object, BCrypt handle, allocated C string, mapped library, temp path, subprocess or thread is added in production code. There is no `new`, `delete`, `malloc` or manual cleanup in the added C++. The libpq connection, `PgResult` objects and the SAVEPOINT are the existing ones in `ResponseStore::store`; no new libpq call site is added.

| resource | owner | acquired | released | transfer / failure cleanup |
|---|---|---|---|---|
| `facets` (`std::unordered_map<int, std::unordered_map<std::string,int>>`) in `ResponseStore::store` | the `store` call frame | built from every field of every output line | end of the facet block | frame-local; owns its strings (a by-value map) but no OS resource; peak bounded by `kMaxIngestBytes`; it copies EVERY distinct value, including a value over `kMaxFacetValueBytes`, because the length filter runs afterwards while `flat` is built (so the exclusion count is of distinct pairs). Peak ingest memory is therefore bounded by the ingest byte cap as before, not by the facet bound; this change does not raise it |
| `flat` (`std::vector<std::tuple<int,std::string,int>>`) in `ResponseStore::store` | the `store` call frame | built from the `facets` map | end of the facet block | unchanged ownership; values longer than `kMaxFacetValueBytes` are skipped while building it (not copied INTO `flat`; they are already in `facets`), so its size is bounded by the same distinct-facet count as before; `std::partial_sort` runs in place only when `flat` exceeds the cap, O(n log cap) time and no allocation of its own |
| `yuzu_server_response_facets_dropped_total{reason}` counter series | `yuzu::MetricsRegistry` (owned by `ServerImpl`, pointer held by `ResponseStore` as before) | `seed_response_facet_metrics` at startup, and on first use per reason | registry destruction | the three reason labels are fixed constants (bounded cardinality); `note_facets_dropped` is a no-op when `metrics_` is null and when the count is zero; no label is built from response content |
| `yuzu_server_response_facet_filter_refused_total{surface}` counter series | `yuzu::MetricsRegistry` (owned by `ServerImpl`) | `seed_response_facet_metrics` at startup (and `note_facet_filter_refused` on first use of a surface) | registry destruction | static const metric name plus three fixed `surface` labels (`dashboard`, `rest`, `mcp`; bounded cardinality); no new resource; `note_facet_filter_refused` is a no-op on a null registry; no label is built from request content |
| non-owning `yuzu::MetricsRegistry*` captured in the REST agent-count-preview lambda (`rest_api_v1.cpp`), held as `DashboardRoutes::metrics_` and passed to the MCP server | the lambda / `DashboardRoutes` / `McpServer` (borrowers only; `ServerImpl::metrics_` owns the registry) | at route registration from `ServerImpl` | with the holder | no ownership transfer; lifetime: `ServerImpl::metrics_` is declared before every holder (`rest_api_v1_`, `mcp_server_`, `dashboard_routes_`), so members destruct in reverse order and the holders go first; same precedent as the sibling counters already captured this way (for example `yuzu_server_response_param_rejected_total`) |
| test code | stack objects and the existing PG fixtures (`YUZU_REQUIRE_PG_DB` family) | per test | per test scope | no raw owning pointers, no new thread-owning code, no temp paths or fixed ports |

Platform notes: no `#ifdef` added; the constant is a plain `std::size_t`; the comparator is a captureless lambda over `std::get`. The three facet-drop deltas are plain `std::size_t` locals filled inside the transaction callback and published with `note_facets_dropped` only after `with_txn_for` has returned success, outside the callback (an aborted or failed transaction publishes none, so a facet counter only ever describes a stored response). The series are pre-seeded at startup, so publishing finds an existing counter; `store()` has no try/catch, so an exception from the registry would propagate after the commit, which is the same as the other post-transaction `note_ingest_dropped` call. Behaviour that is intentionally unchanged: the 5000 facet cap value, the ingest byte cap, the schema and indexes.
