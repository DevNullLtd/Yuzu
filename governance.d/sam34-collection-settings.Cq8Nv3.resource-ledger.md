## Decision lines

- **No `ON CONFLICT DO UPDATE`.** A row lock on a row that does not exist locks nothing, so DO UPDATE would silently overwrite the winner of a concurrent create. Create is `DO NOTHING RETURNING` and replace is `FOR UPDATE` plus a version compare, so a stale writer gets a conflict carrying the current document.
- **Authority fails closed and distinguishes outage from refusal.** The global probe is the RBAC-unavailable-aware twin: a 503 from it ends the request. The group fallback reads the ancestors and the principal's assignments with the two degrade-distinguishable reads (`get_ancestor_ids`, `get_assignments_for_principal`); either failing is a 503, never a 403 or an admit. Service-scoped, MCP-tier and engine sessions are excluded from the fallback because the MCP tier belt lives inside the permission gate only.
- **Access-control table (routed concern: security-guardian).** New REST routes: `GET .../collection-settings`, `GET`/`PUT .../collection-settings/{group_id}`, `GET .../hosts/{agent_id}/collection-settings`. The one mutating route is classified in `kStepUpPolicy` (exempt, operational data) and has a pre-auth body cap row (16 KiB). The root group and a priority change need the global `ManagementGroup:Write` grant.
- **History is count-bounded (newest 200 per group), trimmed in the write transaction, with no wall-clock cutoff;** the disposition is recorded in `docs/clock-guarded-retention.md`.
- **The quiet probe's row for a token caller (audit sequence, recorded).** `group_authority` checks the global grant through `probe_permission_unavailable_aware`, which withholds its `auth.permission_required` denial row only for an interactive cookie session. No probe in `AuthRoutes` withholds that row for an API-token or engine caller, and adding one would change the auth gate's audit contract, so this change does not. A plain API token admitted through the `ITServiceOwner` fallback therefore leaves a `denied` `auth.permission_required` row followed by the `software_estate.collection_settings.update` `requested` and outcome rows for the same request; `docs/user-manual/audit-log.md` states the sequence. A refused per-group GET writes its own `software_estate.collection_settings.read` `denied` row so a cookie session's refusal is on the record.
