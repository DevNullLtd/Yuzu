## Decision lines

- **No `ON CONFLICT DO UPDATE`.** A row lock on a row that does not exist locks nothing, so DO UPDATE would silently overwrite the winner of a concurrent create. Create is `DO NOTHING RETURNING` and replace is `FOR UPDATE` plus a version compare, so a stale writer gets a conflict carrying the current document.
- **Authority is the `ManagementGroup` gate only, and fails closed.** Settings are managed by fleet administrators: the PUT needs the global `ManagementGroup:Write` grant (the administrator role while RBAC enforcement is off, the default); the per-group GET and the list take the standard `ManagementGroup:Read` gate, which is the global grant while RBAC enforcement is on and admits any signed-in non-service-scoped session while it is off, the same as the sibling management-group routes; this build has no group-scoped delegation (owner ruling at governance r1). The per-group GET and the PUT use the RBAC-unavailable-aware probe: a 503 from it ends the request, a refusal is the route's own audited 403. The list (`perm_fn`) and the host route (`scoped_perm_fn`) keep the shared deny-on-degrade gate (ADR-0041): an RBAC read that cannot be completed is a 403 there. The PUT probes the grant a second time immediately ahead of `store->put`, behind the `requested` audit row; the settings transaction cannot join the RBAC tables, so a revoke landing during the store call is ordered behind the write (accepted by the owner ruling).
- **Access-control table (routed concern: security-guardian).** New REST routes: `GET .../collection-settings`, `GET`/`PUT .../collection-settings/{group_id}`, `GET .../hosts/{agent_id}/collection-settings`. The one mutating route is classified in `kStepUpPolicy` (exempt, operational data) and has a pre-auth body cap row (16 KiB). Every write needs the global `ManagementGroup:Write` grant (the administrator role while RBAC enforcement is off).
- **History is count-bounded (newest 200 per group), trimmed in the write transaction, with no wall-clock cutoff;** the disposition is recorded in `docs/clock-guarded-retention.md`. `settings` rows are permanent by design.
- **The quiet probe's row for a token caller (audit sequence, recorded).** `probe_permission_unavailable_aware` withholds its `auth.permission_required` denial row only for an interactive cookie session. An API-token or engine caller without the global grant therefore leaves that `denied` row followed by this route's own `denied` row; an admitted caller leaves none. `docs/user-manual/audit-log.md` states the sequence. A refused per-group GET writes its own `software_estate.collection_settings.read` `denied` row so a cookie session's refusal is on the record.
