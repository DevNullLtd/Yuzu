# Resource Ledger -- TAR registry source, writer attribution (the Kernel-Registry ETW leg)

Range described: `b59a2f70d..125170317` (branch `feat/tar-registry-live-etw-attribution`). Symbols are cited by file and function; the tree is C++23 and every line moves with an edit. This ledger covers only what this change adds or alters; the key-watch owners it builds on (registry key handles, event handles, the watcher thread and the dirty table's `first` stamp) are described in `tar-registry-live-source.KttYnZ.resource-ledger.md`, and rows 15 and 16 below state what this change does to them. Files read at `125170317` (the follow-on commit `5f11df0df` only wraps the session-death warn in a `try/catch` and corrects one comment, and adds no resource): `agents/plugins/tar/src/tar_registry_source.cpp`, `tar_registry_source.hpp`, `tar_registry_parsers.hpp`, `tar_win_process_name.hpp`, and `tar_db.cpp` (`purge_source`).

## Summary

The change adds one system-wide kernel ETW session (write-only mask `0x4300`), its consumer handle and worker thread, an in-memory event buffer, a pid-to-image cache, one short-lived process handle per lookup, and one new kind of persisted content (held candidates and loss epochs in the existing `tar_cursor` row). Every handle is owned by an RAII type from the moment it is acquired; there is no manual `CloseHandle`, `CloseTrace`, `ControlTraceW` STOP or `join` outside an owner's `reset()` or `WinEtw::teardown_locked()`. Teardown has one ordered home: `teardown_locked()` runs CloseTrace, then joins the worker, then stops the session. The `ProcessTrace` callback and the worker body are contained by `try/catch(...)`, so no exception crosses the ETW C frame. There is no subprocess, no stored callback beyond the `RegistryReader` hooks A1 already owns, and no temp file in production code. One resource cannot be bounded by the agent: a kernel ETW session outlives a crashed process. That residual is listed below and is not hidden.

## Items checked and not applicable

- **Subprocess:** none. No `CreateProcess`, `popen` or `system` anywhere in the change.
- **Stored callbacks:** none beyond the `RegistryReader` `std::function` hooks, which capture shared owners by value; the ETW callback is a static function pointer, not a stored closure.
- **Temp paths in production code:** none. Temp files exist only in tests (row 14).
- **Ownership-type changes to existing types:** none; `ScopedWinHandle` replaces the module consumer's local `HandleGuard`, and the handle is still RAII.
- **Timeout and bound derivations:** the settle interval is 5 s (`kEtwSettle100ns`); the notify window slack is 1 s (`kEtwWindowSlack100ns`); the pid-reuse clock slack is 100 ms; the pid-cache flush is 5 minutes; caps are 65536 buffered events, 65536 cached pids, 64 loss epochs, 16383 + 1 characters per decoded value name. The `ProcessTrace` wait has no timeout by design (it ends on `CloseTrace`), so the join is bounded by one wake-up; the ETW session flushes every second (`FlushTimer = 1`).
- **Resource picture after the governance r2 fix round:** the only code changes are the worker-thread death warn (row 4) and the kernel-loss epoch end stamp (row 10), neither of which adds an owner, handle, thread, allocation lifetime or persisted field; rows 1-3, 5-9 and 11-16 were re-checked against the code and are unchanged.
- **Schema:** none. The `actor_pid` / `actor_image` columns existed; no migration.

## Accepted residuals

- **A crashed or killed agent leaks its session until reboot or until a same-pid restart.** A session is a kernel object that outlives its process; `start()` stops a stale session of the SAME pid by name and retries once, but a restarted agent usually has a different pid and a different name. The comment in `WinEtw::start()` states the leak; a dead-pid sweep over all three TAR ETW sessions belongs in one shared helper and is deferred (follow-up to be filed after the PR is raised). The shipped manual (Health) and the implementer doc now carry the operator cleanup line (`logman query -ets` to list `YuzuTar*` sessions, `logman stop <name> -ets` to remove a leaked one). The `ponytail:` comment on `r.start` records the related no-restart ceiling for a session that dies after start, not the sweep.
- **The system allows 64 concurrent ETW sessions.** At the limit `StartTraceW` returns `ERROR_NO_SYSTEM_RESOURCES`; the source degrades to the key watch (`registry_capture_method=notify`, rows `attr:off`), the Win32 code is logged, and a source that starts at the limit is not retried until the agent restarts (tracked with the existing session-restart issue).
- **A starved consumer can deliver an event late.** An event delivered more than the settle interval after its window closed, with no counted loss (a starved consumer thread, suspend and resume), can leave one unrelated pid as the only candidate. Documented in the banner, the manual and the implementer doc; the settle interval is a heuristic, not a delivery-progress check.
- **Uncached empty lookups cost.** Events from a pid whose image lookup returns empty (protected, exited, or created after the event) repeat `OpenProcess` and `GetProcessTimes` per event on the consumer thread. Bounded by the event rate and the buffer cap; it is the price of naming a reused pid's new holder at its own first event.
- **Attribution can be forced to ambiguous.** Events carry no key name, so any local process writing a same-name, same-type, same-size value inside a window forces `attr:ambiguous`; the contract then names nobody. The pid in the event header cannot be forged.
- **A root that was once Complete and then stays Capped or Unreadable, or is simply idle between hourly reads, keeps pinning the retention floor** at its stale `window_base`; at a host-wide write rate of about 65536 / (age of that read) per second the buffer evicts every tick. The manual (Health) and the implementer doc now state this ceiling and the operator cues (`registry_etw_dropped` rising, `registry_roots_unreadable` / `registry_roots_capped`). Marked (`gap:loss` and `attr:degraded` every tick), never silent; no volume guard (owner ruling); a follow-up will be filed after the PR is raised.
- **Native Windows proof is pending.** The ETW legs were compiled for syntax only (mingw) and exercised on macOS through the injected seams; the elevated `[registry][windows]` cases and the provider keyword bits are confirmed on kingsley in gate 4 and recorded in the PR body.
- **Unmasked values** in the held candidates are the owner's ruling and are stated plainly in the shipped manual and the implementer doc.
