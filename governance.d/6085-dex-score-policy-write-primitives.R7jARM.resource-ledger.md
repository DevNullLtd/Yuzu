# Score-policy write primitives Resource Ledger (governance Gate 1)

The production-code ledger for the conditional-write and conditional-delete methods on `RuntimeConfigStore`, the `version` field of the stored score-policy document and the serialised commit-then-install path of `DexScorePolicyProvider`, kept here so the ownership analysis is retrievable with the change. Range `7d23da86b64f442e7c316e313b4f75ad182e72b9..e7386602e` (reviewed), files `server/core/src/runtime_config_store.{hpp,cpp}`, `server/core/src/dex_score_policy_json.hpp`, `server/core/src/dex_score_policy_provider.hpp`, and the tests `tests/unit/server/test_runtime_config_store.cpp`, `test_dex_score_policy_json.cpp` and `test_dex_score_policy_provider.cpp`. No route, tool, fragment, audit row or permission is added; nothing in the product calls the new methods yet.

## Resource Ledger (C++)
- Pooled connection lease for `RuntimeConfigStore::compare_and_set` and `compare_and_remove`: owner = a function-local `pg::PgPool::Lease` (move-only; its destructor returns the connection through `reset()`), acquired with `pool_.try_acquire_for(kWriteTimeout)` after every caller-input gate (open, allow-listed key, non-secret key, per-key validation, representable `expected`) so a refused call never takes a lease; an empty lease returns before any SQL; the lease is released on every return and, after the governance round, before the in-process live effect of a winning write. Failure cleanup: the failed-statement and stale paths return through the same RAII owner.
- `pg::PgResult` of the single conditional statement in each method: owner = the move-only `PgResult` wrapper (`PQclear` in its destructor), declared after the lease so it is cleared before the connection returns to the pool; the borrowed `PQntuples` read happens while the result is in scope and distinguishes a zero-row (stale) result from a failed one (a null or non-tuples result is a prefixed store failure, never stale).
- Bound parameters: every value is passed through `pg::exec_params`, which copies the `std::string` parameters into a local array before the call, so each `c_str()` stays valid for the call and nothing outlives it. `key` is allow-listed, `value` and `updated_by` pass through `sanitize_pg_text`, and `expected` is bound exactly: an `expected` that `sanitize_pg_text` would change (NUL or invalid UTF-8) is refused before any lease, so no NUL can reach a C-string bind.
- `DexScorePolicyProvider::write` locking: a new `std::timed_mutex writer_mu_` held across the caller-supplied commit callable and the install, taken with `std::unique_lock` (deferred) and `try_lock_for(writer_wait_)`, then the existing `std::mutex mu_` for the install through `std::lock_guard`. Lock order is `writer_mu_` then `mu_` and never the reverse; `current()`, `apply_locked`, `read_and_resolve` and `ClearRefreshing` never touch `writer_mu_`. Both locks are RAII and released on every exit, including a throwing commit (caught and returned as a typed failure). The wait for `writer_mu_` is bounded (default 2000 ms, typed `WriterBusy`, the commit never invoked); the HOLD lasts as long as the commit, which is the store call above and is bounded by the lease wait and the pool's server-side statement and lock timeouts, but NOT hard-bounded against a frozen database backend (the repository measured 101 seconds at the containment-read note in `server.cpp`) or against a connection string that supplies its own `options`. Consequences: one stalled commit holds the writer lock, its calling thread and one pool connection per process; every other writer fails fast after the wait; readers never take the lock; the 5 s and 60 s read bounds are unchanged.
- `generation_` (uint64) and the cached policy: every access is under `mu_`; a successful in-flight read that predates an install is discarded by the generation check, a failed one still goes through the stale-cap path; the generation is bumped after the install call returns so a bump implies an install.
- `std::function` commit callable: taken by const reference and called synchronously; not stored. Re-entering `write()` from the commit is documented as undefined behaviour (non-recursive mutex); calling `current()` from the commit is safe.
- Exceptions: a throw from the commit is caught (`std::exception` and `...`) and returned as `CommitFailed`; nothing is installed on any typed failure. An allocation-class throw from the install tail is not caught (it would escape with the change committed); the caller must treat an exception from `write()` as commit-state unknown.
- Tests (harness only): every `std::thread` and `std::async` in the new cases is joined or waited on every exit path, with each future declared before the scope guard that releases the parked writer; `ParkedRead`, `ParkedCommit` and `ParkedClock` guard their promise with an exchange so it is set at most once; no `REQUIRE` or `CHECK` runs off the main thread; the row-lock cases join before asserting and drive a second connection owned by RAII wrappers.
- No new fd/HANDLE/SOCKET/`FILE*`/sqlite handle/OpenSSL or BCrypt object/mapped library/temp-file path/subprocess/shell string/`system`/`popen` in production or test code, no new thread in production code, and no cast over a lifetime: the one narrowing is a clamped unsigned-to-signed conversion of a parsed version number.

## Independent ownership proof
Both proofs are static code reads at `e7386602e`, each with no blocking finding. The governance round that followed changed comments, test hygiene, the clock-sampling order inside `write()` and the lease release point in `compare_and_set`; those were verified by rebuild, the suites listed below and mutation probes, and re-read by a fresh-context reviewer, not by a second full proof.

- security-guardian (Gate 2): proved the gate order refuses a secret or unknown key before any lease and that the new SQL touches only the plain `runtime_config` table; walked every other writer of `runtime_config` and found no path that writes the policy key; showed `representable_expected` is true exactly when a text could ever have been stored; ran scratch probes for hostile document keys (control characters, bidi, deep nesting) and for versions at and above 2^63.
- cpp-safety (Gate 3): proved the two leases have one owner and one release path with checked failure cleanup; proved the lock order is acyclic and every access to the cached state is under `mu_`; checked every exit of `write()` for lock release; checked test thread and future teardown; reproduced a hang-on-regression in two tests with a scratch model (fixed in the governance round and re-verified by a mutation probe that now fails fast).
- Sanitizer coverage: the per-pull-request `ci.yml` has no sanitizer leg. The nightly `sanitize-tsan` and `sanitize-asan` jobs run the server suites with a Postgres service, so the new concurrency cases run under both; TSan is the relevant one (a new mutex, a generation protocol and several multi-thread cases). The `std::timed_mutex` with a bounded `try_lock_for` already has production precedent under the same legs.
