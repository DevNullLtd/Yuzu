## Scope

When the gateway's upstream client could not send a `NotifyStreamStatus` call at once (10 already in flight, or the circuit breaker open), it dropped the `CONNECTED` or `DISCONNECTED` notification. A dropped `CONNECTED` left an agent that the server had acknowledged but could not dispatch to. The change replaces both drop sites with a bounded, memory-only pending store (key: agent id, session id, stream home id; cap `notify_pending_max`, default 10000) and a first-in-first-out drain of at most 10 workers, keeps one worker slot free while a registration replay is active, and uses one held notification as the probe of a half open breaker (delivery of a probe notification is therefore at least once). It adds the gauges `yuzu_gw_upstream_notify_pending` and `yuzu_gw_upstream_notify_inflight`, the counter `yuzu_gw_upstream_notify_coalesced_total`, and retires the `circuit_open` value of `yuzu_gw_upstream_notify_dropped_total` (closed set `at_capacity` and `unknown`). After the governance run it also sanitises the agent-supplied peer address (a value that is not valid UTF-8 becomes `invalid`; a longer one is cut to 255 bytes at a character boundary) where it is read and again at admission. After the Gate 8 re-review it also makes a local encode exception (the request never left the gateway) neither a success nor a failure of the circuit breaker, evicts a held notification that cannot be encoded instead of requeueing it, converts `cluster_id` with the unicode conversion and refuses to start when it cannot be represented, and validates `circuit_breaker_reset_timeout_ms` and `circuit_breaker_max_reset_timeout_ms`. After the Gate 8 re-review of fix round 2 it also bounds the agent id at the gateway edge (an empty or over-256-byte id is refused locally, no upstream call), stops counting the server statuses that mean the request was wrong against the breaker, refuses to send a request over 4194304 bytes, interprets the `cluster_id` environment text in the VM's native name encoding, rate-limits the warnings a refused or malformed registration can trigger, counts a local encode failure under `code="encode"`, applies `log_text` to the remaining agent-controlled log text, and range-checks `circuit_breaker_failure_threshold` and raises the reset timeout floor to 100 ms. Behaviour and operating guidance: `docs/user-manual/gateway.md` "Stream Status Notification" and the runbook rows; upgrade note: `docs/user-manual/upgrading.md`; design note: `docs/adr/2002-high-availability-architecture.md` section 7c, update 2026-10-06.

This record covers one core replica and one gateway node. No multi-replica run exists.

## Rig configuration and what the instruments can show

OBSERVED setup, identical for every run: loopback, one shared 32 core host with other sessions running on it, a debug-built C++ server, PostgreSQL in a container with `fsync` off, a release-built gateway on one node, debug log level on gateway and server, a fresh database, server data directory and gateway for every run. Agents were either real `yuzu-agent` processes with the default plugin set (68 plugins) or a load generator (`asim`) that sends a synthetic `Register` of the same serialized size (about 9 KB), holds a `Subscribe` stream open without answering commands, and sends a heartbeat every 30 s. The captured request template of earlier rigs no longer existed, so the size is matched but the content is synthetic. TLS runs used the server's default per-install certificates with a private certificate directory and the dashboard on plain HTTP.

Instruments, and what each cannot show:

- Prometheus scrapes once per second: they cannot see a burst shorter than a second (the pending gauge was 0 in every scrape of every cold wave although a faster sampler saw hundreds of held keys).
- A 100 ms sampler of the two gauges, the upstream process mailbox and memory over a persistent Erlang node: samples, not event-level maxima.
- A temporary telemetry and trace handler loaded into the gateway (event-level log of `put`, `take`, circuit state, RPC results and the key of each notification): this has an observer effect and is the only evidence for "exactly one probe", "first in first out" and the per-key take counts. The gateway debug log has no line for a successful notification, and the 100 ms sampler cannot resolve a 2 ms event.
- A route oracle: the server's `agent_routes` table classified as routable (session set, placed, lease valid), never announced (session set, no placement) or tombstoned (no session), polled about every 1.5 s, plus the server's own online count.
- Freezing the server with `SIGSTOP`: requests already written into the frozen server's socket buffer are executed when it resumes, so a freeze alone cannot show a lost request (see the worker loss rows).

## Cost investigation (R6)

Whether the TLS and plaintext differences seen above are TLS costs was measured with alternating pairs, all OBSERVED on the debug-built rig:

- The server CPU gap between two steady-state runs (14.7 % against 7.9 % of a core) was not TLS: the server's boot-time vulnerability-data sync alone burned 9.2 to 10.0 % of a core for the first 3 to 5 minutes in both modes, and ran faster in one run than the other. With that sync off, six alternating pairs showed no consistent sign (plaintext 5.3, 8.4, 6.2 %; TLS 7.4, 8.3, 6.1 %).
- The gateway cost of TLS: about +1.6 ms of scheduler time per handshake (1000 handshakes: +1.6 core seconds), 3 more processes per connection, a peak VM memory +46 to +96 MB for 1000 connections (all freed after teardown), +0.5 to +1.2 points of a core in steady state.
- The +0.15 to +0.2 s on 1000 registrations is the per-call time of the serialised `ProxyRegister` over the single upstream connection (+0.15 to +0.21 ms per call, 1.77 to 1.78 ms against 1.93 to 1.99 ms mean); about 0.06 ms of that is Erlang TLS work and about 0.13 ms lies outside the gateway's processes and was not separated.
- The agent's roughly 6 s start delay is not TLS and not the gateway: it is 3 sequential 2 s timeouts of the cloud identity probes that run before the first `Register`, identical in both modes, on a host that does not answer the link-local metadata address.

## Residuals and follow-ups

Residuals carried by the change (INFERRED from the code unless a run is cited; the manual's Known limits is the authoritative list):

- A notification for a new key is lost, and counted, when the store is full; the key of a half open probe that is out counts toward the cap. One notification lost after admission (a failed or killed ordinary worker, a gateway stop) is lost and not counted; a lost `DISCONNECTED` leaves the agent online in the server's registry and its route row routable until the lease expires (OBSERVED).
- The head held notification is the breaker probe. A notification that fails in the gateway's own encoder is evicted with a warning when it is the half open probe and does not move the breaker (UP-1, the poison head, is closed for a local encode exception since round 2; the earlier statement that this closed the whole class was an overclaim, see N1; the registration routes that fed the breaker were already present at the base commit). A notification that the server answers with an error status every time would still fail the probe and be requeued (INFERRED from the code; not known to occur, and not searched for on the server).
- A successful probe proves only the notification path (UP-2): a server whose registration path fails can still accept the probe, so the breaker can cycle at the base interval.
- `circuit_breaker_reset_timeout_ms` and `circuit_breaker_max_reset_timeout_ms` were not validated (0 or 1 with the server down would make the probe and its WARN a hot loop, UP-3); round 2 checked both against 1 to 3600000 ms and round 3 raised the floor to 100 ms. `circuit_breaker_failure_threshold` was read raw (0 opened the breaker on the first failure); round 3 checks it against 1 to 1000, and keeps the effective maximum reset timeout at or above the base. A probe from an earlier generation still out delays the next probe (UP-4, covered by design and tests). With the breaker closed and a server that blackholes traffic, the backlog drains into 5 s calls and is lost uncounted, scaling with the backlog (UP-6).
- A crash of the upstream process loses the held store, and old workers can briefly overlap new ones (UP-8). A cold wave near 15,000 agents reaches the 30 s caller timeout of `ProxyRegister`, and late registrations execute for abandoned callers (UP-9, extrapolated). A very large cap with a long-open breaker and large entries grows memory and mailbox (UP-10). UP-11 (a stored empty stream home admits any value in the stale `DISCONNECTED` fence) was examined and is resolved as refuted for current code: one `stream_home_id` is minted per `yuzu_gw_agent` process and a reannounce reuses it, a session is bound to one agent process, and the server states that no concurrent producer exists for one session (refuted on independent adjudication by security-guardian and architect). A future same-session re-home would have to revisit it. The replay reserve holds one slot for the whole drip (UP-12); held entries have no age bound (UP-13); a raising telemetry handler detaches the single metrics handler, a pre-existing class (UP-14); a TLS failure on the first probe drives the breaker (UP-16).
- Pre-existing and not caused by this change, and not to be overstated in any assurance statement (OBSERVED, R7): the server's upstream port admits any certificate that chains to the run's authority at the TLS layer, including the server's own certificate, so the gateway identity is not pinned there (the management listener pins; the gRPC layer of the upstream port was not probed), and TLS 1.3 is not offered on the agent edge (a TLS 1.3 client was refused with a protocol-version alert). No statement should say the gateway identity is pinned on the upstream port.
- Round 3 residuals (INFERRED from the code and unit tests): a request-fault answer never moves the breaker in either direction, so a half open breaker that receives only such answers or local failures stays half open until a real RPC or probe decides (the same as for a local encode failure); the probe handling for a request-fault status is defence in depth, because the server cannot return one for `NotifyStreamStatus` today; on a node whose VM native name encoding is UTF-8, non-UTF-8 bytes in `YUZU_GW_CLUSTER_ID` are read by the VM as latin1 characters and become a valid but different name (a latin1 node, which the shipped images are, refuses them); the agent-controlled text sites left unwrapped in `log_text` are the backpressure line that names a command id (it comes from the dispatching server or operator, not from the agent), `~p` prints of a reason term (which escape control characters; the server text inside them is cut by `log_text` where it is printed), and lines that name no agent text (every logger call in the gateway source was re-checked, but that re-check missed the debug line at `yuzu_gw_agent.erl:344`, "ignoring stale upstream_reannounced", which printed a raw agent id; it is a raw agent-id site wrapped in `log_text` in round 4, together with two other survivors); the test script hazard noted under "Automated results".
- Pre-existing and not caused by this change, found in round 4 (INFERRED from the code, not run on a rig): a replayed stored `Register` that the server refuses with a request-fault status other than 9 (3, 5, 6 or 11) leaves the agent attached to the gateway without a server placement, and only 9 disconnects it. The `Subscribe` path can emit warnings without a limit and is reachable by an unauthenticated peer. The guardian worker logs one warning per failure without a limit.
- Pre-existing and not caused by this change: the agent edge accepts only NPN and every failed handshake on the edge or management listeners ends in an acceptor error report (a scanner produces error lines); the one gateway upstream process serialises every `ProxyRegister`, so enrolment of a large wave takes seconds.

## Caveats

- The rig notes and raw logs behind this record are local files, not committed artifacts. This document is a summary of them. The run labels used by those notes (a, b, c, d, e, w, f, R1 to R7, T0, G1 to G3, UP-n) are not defined elsewhere in the repository.
- Debug-built server, debug log level, a shared host with other load (the one load average that fell from about 40 to about 1.5 during the cost investigation shows how noisy it was), PostgreSQL with `fsync` off, loopback only: absolute times and CPU figures are not capacity numbers, and comparisons are within the same session.
- Simulated agents answer no commands, send no inventory and use a synthetic request of the right size; only the 30 real agent runs exercise commands.
- The event-level evidence comes from a temporary tracer with an observer effect; the 100 ms figures are samples.
- Post-rig commits are not rig-run (see "Tested SHAs"). The hashes before and after the rebase onto dev differ for the same changes.
- Server-side counters for duplicate deliveries rise (`session_mismatch`, `unknown_session`) when a held `DISCONNECTED` is delivered more than once or after a server restart; that is expected and not an alarm.
