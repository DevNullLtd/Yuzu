## Scope

When the gateway's upstream client could not send a `NotifyStreamStatus` call at once (10 already in flight, or the circuit breaker open), it dropped the `CONNECTED` or `DISCONNECTED` notification. A dropped `CONNECTED` left an agent that the server had acknowledged but could not dispatch to. The change replaces both drop sites with a bounded, memory-only pending store (key: agent id, session id, stream home id; cap `notify_pending_max`, default 10000) and a first-in-first-out drain of at most 10 workers, keeps one worker slot free while a registration replay is active, and uses one held notification as the probe of a half open breaker (delivery of a probe notification is therefore at least once). It adds the gauges `yuzu_gw_upstream_notify_pending` and `yuzu_gw_upstream_notify_inflight`, the counter `yuzu_gw_upstream_notify_coalesced_total`, and retires the `circuit_open` value of `yuzu_gw_upstream_notify_dropped_total` (closed set `at_capacity` and `unknown`). After the governance run it also sanitises the agent-supplied peer address (a value that is not valid UTF-8 becomes `invalid`; a longer one is cut to 255 bytes at a character boundary) where it is read and again at admission. After the Gate 8 re-review it also makes a local encode exception (the request never left the gateway) neither a success nor a failure of the circuit breaker, evicts a held notification that cannot be encoded instead of requeueing it, converts `cluster_id` with the unicode conversion and refuses to start when it cannot be represented, and validates `circuit_breaker_reset_timeout_ms` and `circuit_breaker_max_reset_timeout_ms`. Behaviour and operating guidance: `docs/user-manual/gateway.md` "Stream Status Notification" and the runbook rows; upgrade note: `docs/user-manual/upgrading.md`; design note: `docs/adr/2002-high-availability-architecture.md` section 7c, update 2026-10-06.

This record covers one core replica and one gateway node. No multi-replica run exists.

## Rig configuration and what the instruments can show

OBSERVED setup, identical for every run: loopback, one shared 32 core host with other sessions running on it, a debug-built C++ server, PostgreSQL in a container with `fsync` off, a release-built gateway on one node, debug log level on gateway and server, a fresh database, server data directory and gateway for every run. Agents were either real `yuzu-agent` processes with the default plugin set (68 plugins) or a load generator (`asim`) that sends a synthetic `Register` of the same serialized size (about 9 KB), holds a `Subscribe` stream open without answering commands, and sends a heartbeat every 30 s. The captured request template of earlier rigs no longer existed, so the size is matched but the content is synthetic. TLS runs used the server's default per-install certificates with a private certificate directory and the dashboard on plain HTTP.

Instruments, and what each cannot show:

- Prometheus scrapes once per second: they cannot see a burst shorter than a second (the pending gauge was 0 in every scrape of every cold wave although a faster sampler saw hundreds of held keys).
- A 100 ms sampler of the two gauges, the upstream process mailbox and memory over a persistent Erlang node: samples, not event-level maxima.
- A temporary telemetry and trace handler loaded into the gateway (event-level log of `put`, `take`, circuit state, RPC results and the key of each notification): this has an observer effect and is the only evidence for "exactly one probe", "first in first out" and the per-key take counts. The gateway debug log has no line for a successful notification, and the 100 ms sampler cannot resolve a 2 ms event.
- A route oracle: the server's `agent_routes` table classified as routable (session set, placed, lease valid), never announced (session set, no placement) or tombstoned (no session), polled about every 1.5 s, plus the server's own online count.
- Freezing the server with `SIGSTOP`: requests already written into the frozen server's socket buffer are executed when it resumes, so a freeze alone cannot show a lost request (see the worker loss rows).

## Cost investigation (R6)

Whether the TLS and plaintext differences seen above are TLS costs was measured with alternating pairs, all OBSERVED on the debug-built rig:

- The server CPU gap between two steady-state runs (14.7 % against 7.9 % of a core) was not TLS: the server's boot-time vulnerability-data sync alone burned 9.2 to 10.0 % of a core for the first 3 to 5 minutes in both modes, and ran faster in one run than the other. With that sync off, six alternating pairs showed no consistent sign (plaintext 5.3, 8.4, 6.2 %; TLS 7.4, 8.3, 6.1 %).
- The gateway cost of TLS: about +1.6 ms of scheduler time per handshake (1000 handshakes: +1.6 core seconds), 3 more processes per connection, a peak VM memory +46 to +96 MB for 1000 connections (all freed after teardown), +0.5 to +1.2 points of a core in steady state.
- The +0.15 to +0.2 s on 1000 registrations is the per-call time of the serialised `ProxyRegister` over the single upstream connection (+0.15 to +0.21 ms per call, 1.77 to 1.78 ms against 1.93 to 1.99 ms mean); about 0.06 ms of that is Erlang TLS work and about 0.13 ms lies outside the gateway's processes and was not separated.
- The agent's roughly 6 s start delay is not TLS and not the gateway: it is 3 sequential 2 s timeouts of the cloud identity probes that run before the first `Register`, identical in both modes, on a host that does not answer the link-local metadata address.

- The HIGH finding (UP-1), verified before the fix: `gateway_pb:encode_msg` of a `StreamStatusNotification` whose `peer_addr` is not valid UTF-8 raises an error. The peer address is the agent-supplied `:authority` header and was not validated. A notification that fails on its own payload is retried as the half open probe: the probe fails within microseconds, the breaker reopens with a doubled backoff and the notification goes back to the head, so every later notification stays held, `ProxyRegister` and `ProxyInventory` answer `circuit_open` against a healthy server, an agent reconnect does not help, and only a gateway restart does. Reachable by a caller with an accepted registration, with the breaker open and the notification at the head (INFERRED from the code, verified for the encoder; not run on a rig). Fixed by sanitising and capping the peer address at admission, with a red test first (a poison head must not stop a good notification from probing and closing the breaker, and an all-poison queue must drain). The class remains a standing invariant (see the manual's Known limits). The round-1 sanitiser closed the peer address route only. The round-2 closure below closes the general class: a local encode exception never feeds the circuit breaker, and a held notification that cannot be encoded is evicted with a warning instead of being requeued (see the next bullet).
- Gate 8 re-review of the fix round (11 agents; no regression in the round-1 fix, two further findings of the same class): (1) security F1, derived CRITICAL (I5(a)+(c), E1) and PRE-EXISTING at the base `f79ba8d13`, not introduced by this change: a `Register` whose `RegisterRequest` carries a text field that is not valid UTF-8 is decoded without validation, the gateway re-encodes it for the upstream `ProxyRegister` call, the encoder raises inside `do_rpc`, and `do_rpc` turned that into an ordinary RPC failure that counted against the circuit breaker, so enough of them opened the breaker and it refused `ProxyRegister` and `ProxyInventory` until its backoff ended. An unauthenticated peer could trigger it. The problem pre-dates this change and affects released builds, which is why the security changelog fragment recommends an upgrade. A scratch eunit run reproduced the effect and a good registration was then answered `circuit_open` (a unit test, not run on a rig). Fixed in this change. (2) unhappy-path F1, derived HIGH: the `cluster_id` stamped on every notification was built with `list_to_binary` from the environment or `sys.config`, so a configured name with a character above 127 under a UTF-8 locale (for example one containing a u-umlaut) produced bytes that are not valid UTF-8, every notification failed the encoder, and with a notification as the half open probe the breaker could never close. Fixed in this change. Both are closed by one mechanism: a local marshalling or encoding exception (the request never left the gateway) is not a server verdict and feeds the breaker neither as a success nor as a failure (see the Mutation checks section for the tests). The other Gate 8 findings were LOW or NICE: the sanitised peer address kept its whole header block alive (a 255 byte value taken from a 5 MiB parent referenced 5,242,880 bytes; it is now copied), agent-controlled text in log lines (now logged through `log_text`, with one WARN naming the agent and the original size when the edge replaces a peer address), the unvalidated reset timeout, test gaps and documentation corrections; all were handled in fix round 2.

## Residuals and follow-ups

Residuals carried by the change (INFERRED from the code unless a run is cited; the manual's Known limits is the authoritative list):

- A notification for a new key is lost, and counted, when the store is full; the key of a half open probe that is out counts toward the cap. One notification lost after admission (a failed or killed ordinary worker, a gateway stop) is lost and not counted; a lost `DISCONNECTED` leaves the agent online in the server's registry and its route row routable until the lease expires (OBSERVED).
- The head held notification is the breaker probe. A notification that fails in the gateway's own encoder is now evicted with a warning and does not move the breaker (UP-1 closed as a class in round 2; the registration route that fed the breaker was already present at the base commit). A notification that the server answers with an error status every time would still fail the probe and be requeued (INFERRED from the code; not known to occur, and not searched for on the server).
- A successful probe proves only the notification path (UP-2): a server whose registration path fails can still accept the probe, so the breaker can cycle at the base interval.
- `circuit_breaker_reset_timeout_ms` and `circuit_breaker_max_reset_timeout_ms` were not validated (0 or 1 with the server down would make the probe and its WARN a hot loop, UP-3); round 2 checks both against 1 to 3600000 ms. `circuit_breaker_failure_threshold` is still read raw (0 would open the breaker on the first failure). A probe from an earlier generation still out delays the next probe (UP-4, covered by design and tests). With the breaker closed and a server that blackholes traffic, the backlog drains into 5 s calls and is lost uncounted, scaling with the backlog (UP-6).
- A crash of the upstream process loses the held store, and old workers can briefly overlap new ones (UP-8). A cold wave near 15,000 agents reaches the 30 s caller timeout of `ProxyRegister`, and late registrations execute for abandoned callers (UP-9, extrapolated). A very large cap with a long-open breaker and large entries grows memory and mailbox (UP-10). A stored empty stream home admits any value in the stale `DISCONNECTED` fence (UP-11, speculative, bounded by the verdict heal, and a same-session re-home does not exist today). The replay reserve holds one slot for the whole drip (UP-12); held entries have no age bound (UP-13); a raising telemetry handler detaches the single metrics handler, a pre-existing class (UP-14); a TLS failure on the first probe drives the breaker (UP-16).
- Pre-existing and not caused by this change, and not to be overstated in any assurance statement (OBSERVED, R7): the server's upstream port admits any certificate that chains to the run's authority at the TLS layer, including the server's own certificate, so the gateway identity is not pinned there (the management listener pins; the gRPC layer of the upstream port was not probed), and TLS 1.3 is not offered on the agent edge (a TLS 1.3 client was refused with a protocol-version alert). No statement should say the gateway identity is pinned on the upstream port.
- Pre-existing and not caused by this change: the agent edge accepts only NPN and every failed handshake on the edge or management listeners ends in an acceptor error report (a scanner produces error lines); the one gateway upstream process serialises every `ProxyRegister`, so enrolment of a large wave takes seconds.

Follow-ups (no issue numbers yet; the owner files them):

1. Retry or breaker feedback for an ordinary notification worker that fails (error-class discrimination, so a locally failing head is evicted without feeding the breaker, and the standing test for that class, were done in fix round 2).
2. Alerts: pending stuck, in flight saturated, admission loss at `at_capacity`, the `unknown` tripwire, breaker flapping (needs a circuit state gauge and pre-seeding of `circuit_transitions_total` and `rpc_errors_total`), and the poison head signature.
3. Validate `circuit_breaker_failure_threshold` (the reset timeouts were validated in fix round 2).
4. A server test with two overlapping `NotifyStreamStatus` handlers for one session.
5. A probe that also proves the registration path (UP-2).
6. Capacity: the synchronous RPCs inside the upstream process, a 15,000 agent wave, and large held entries.
7. Seed the `unknown` series of `verdict_dropped` and `buffer_dropped`.
8. Agent start-up: the cloud identity probes cost 6 s on a host that does not answer the metadata address; the default boot-time vulnerability-data sync costs about 10 % of a core for minutes on a small server.
9. Enrolment: serialise or parallelise the certificate-signing `Register` path.
10. A head-age gauge and a probe failure reason in the log for support.
11. The NPN-only edge and the acceptor error report on failed handshakes.
12. Replay and chaos scenarios for the cases above (probe collisions at fleet scale, repeated server restarts with a held store, large held entries).

## Caveats

- The rig notes and raw logs behind this record are local files, not committed artifacts. This document is a summary of them. The run labels used by those notes (a, b, c, d, e, w, f, R1 to R7, T0, G1 to G3, UP-n) are not defined elsewhere in the repository.
- Debug-built server, debug log level, a shared host with other load (the one load average that fell from about 40 to about 1.5 during the cost investigation shows how noisy it was), PostgreSQL with `fsync` off, loopback only: absolute times and CPU figures are not capacity numbers, and comparisons are within the same session.
- Simulated agents answer no commands, send no inventory and use a synthetic request of the right size; only the 30 real agent runs exercise commands.
- The event-level evidence comes from a temporary tracer with an observer effect; the 100 ms figures are samples.
- Post-rig commits are not rig-run (see "Tested SHAs"). The hashes before and after the rebase onto dev differ for the same changes.
- Server-side counters for duplicate deliveries rise (`session_mismatch`, `unknown_session`) when a held `DISCONNECTED` is delivered more than once or after a server restart; that is expected and not an alarm.
