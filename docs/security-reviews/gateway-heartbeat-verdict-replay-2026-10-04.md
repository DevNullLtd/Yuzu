- **Date:** 2026-10-04
- **Change:** branch `feat/1197-gateway-heartbeat-reconcile` (issue #1197; builds on the server-side verdict recorded in `changelog.d/1197-batch-heartbeat-unknown-sessions.changed.md`)
- **Component:** Erlang gateway (`gateway/apps/yuzu_gw`): `yuzu_gw_heartbeat_buffer`, `yuzu_gw_upstream`, `yuzu_gw_registry`, `yuzu_gw_telemetry`. No proto or agent change; the only server change is a comment in the `BatchHeartbeat` handler.
- **Reviewed by:** `/governance` (security, SRE, architecture and gateway, documentation, consistency, enterprise-readiness, compliance and quality-engineering roles). Outcome in plain words: the first run found one derived-HIGH documentation finding (the side effects of replaying a session the server already knows). The re-review of the fix round found two further derived-HIGH items (upgrade-day guidance that omitted the wedge of released agents, and crash report redaction that covered the state but not the mailbox) and a number of MEDIUM and LOW items. All of them are addressed in this PR as documented here and in the Known limits of the gateway manual; the crash report mailbox residual was disclosed at that point, and a later round narrows it with a logger filter (see the later code commits and "Not tested" below). The re-review of the open-items round then found two derived-HIGH items (a caller-side leak of the registration request through the exit reason of the calling gRPC handler process, and the crash report of the per-agent process, which stored the request and had no redaction) and a MEDIUM stale metric HELP text (it did not say that `queue_full` also covers the upstream mailbox backlog). All three are addressed in this PR. The re-review of the buffer rewrite then found the following, all fixed in this PR and verified by probes in scratch copies of the code against a fake server, not by rig runs: an oversized heartbeat that wedged the flush (found by three reviewers), two more call sites that logged the registration request in a crash report (a Register while the registry process is down, and a Subscribe while the agent supervisor is down), invalid UTF-8 in a status tag crashing the buffer process (an existing defect, not introduced by this change), an exit that escaped the RPC crashing the buffer with a state dump, a garbage collect call that did nothing, and mailbox growth during a long drain. The re-review of that fix round then found the following, all fixed in this PR and checked by eunit, dialyzer, Common Test and scratch probes against a fake upstream, not by rig runs: (1) screening that dropped a whole heartbeat for invalid or oversized status tags would have stopped lease renewal for a session that sends such tags on every heartbeat (fixed: the heartbeat is kept and only its tags are dropped or repaired); (2) a `SendCommand` with a negative timeout crashed the command router, and its crash report printed the command request including its parameters (OBSERVED by a review probe with the real application and a marker value, not on a rig; fixed: the timeout is clamped to 1 to 3600 seconds, the router and the heartbeat buffer are covered by the crash report filter, and the router has a counts-only crash status); (3) one connection holding many pending sessions with large snapshots could push the other agents' snapshots out of a full heartbeat buffer while the upstream was not draining (OBSERVED by a review probe against the real application with a fake upstream; it did not reproduce with a healthy upstream; not a rig run; fixed with a per-connection session cap); (4) a crash of the heartbeat buffer would have printed fleet status tags (reported by the review, covered by the same filter change). The post-rig code changes of that round are listed in the paragraph under "Tested SHAs".
- **Reading this record:** it summarises local rig runs and local review notes. Nothing here is a CI result. Every figure is as recorded in those notes; where a statement was inferred from the code rather than observed it says so.

## Scope

After a server-only restart the server answers every `BatchHeartbeat` with the session ids it does not hold. The gateway now validates that list, resolves the ids against the sessions it still holds, and replays exactly those through the existing registration-replay drip: one pending entry per agent, a per-session guard window, a cap on verdict appends, and the circuit breaker in front of every replay `ProxyRegister`. Behaviour and operating guidance: `docs/user-manual/gateway.md` "What happens when the server restarts"; design note: `docs/adr/2002-high-availability-architecture.md` section 7c, update 2026-10-04.

This record covers one core replica. No multi-replica run exists; the multi-replica statement is read from the code.

A last round of post-rig code changes, NOT rig-run (checked by eunit, dialyzer, Common Test and scratch probes against a fake upstream only), adds: (a) heartbeat screening degrades instead of dropping: invalid UTF-8 in a status tag is repaired with replacement characters (counted under `heartbeat_invalid`, the heartbeat is kept), and a heartbeat with more than 512 status tags, or tags larger than a request chunk, loses all of its status tags and is kept (counted under `heartbeat_oversize`); (b) the command router clamps `timeout_seconds` to 1 to 3600 (a non-positive or missing value uses the router's default), the router and the heartbeat buffer join the crash report filter's covered processes (now five: upstream, agent, registry, router, heartbeat buffer), the router has a counts-only crash status, and a management API `SendCommand` while the router is unavailable answers `UNAVAILABLE` (it answered `INTERNAL`) with one rate-limited warning; ## Stuck heartbeat batch (agent with the TAR plugin)

OBSERVED on a rig, after the runs above, with real agents running their default plugin set (so with the TAR plugin), one core replica, debug builds, at `848709698`. The earlier runs R1 to R6 used an agent without the TAR plugin, so their heartbeats were small and did not meet this. A heartbeat from an agent with the TAR plugin carried a `fleet_snapshot_json` of 200 to 815 KB (observed byte sizes on this busy rig host; about 700 KB each in the 30 agent run). The server's gRPC receive limit is 4,194,304 bytes.

| Run | Scenario | Result |
|---|---|---|
| E2x, the unplanned long outage | 1 agent, server down 15.6 minutes (a local port collision kept it from restarting; not planned) | the gateway circuit breaker opened (6 open and 6 half_open transitions, 909 `econnrefused` batch errors) and its own recovery replay (`trigger="breaker"`) ran 36 s after the server was healthy again, but every later `BatchHeartbeat` failed with `Received message larger than max (24805137 vs. 4194304)` and never drained (31 heartbeats buffered, the retained batch grew by about 0.8 MB per buffered heartbeat). The server's route row was reaped (`reap_total{ok}` 3) and stayed gone while `online` stayed 1 from the server's in-memory session. Recovery came only from restarting the gateway (the buffer is in memory) |
| E2a | 1 agent, planned 300 s server outage (restart at 302 s) | FAIL. At T0 the buffer held 10 heartbeats, 7,067,350 bytes. After T0 every `BatchHeartbeat` failed with `Received message larger than max (N vs. 4194304)`. `agents.online` stayed 0 for the whole 420 s deadline plus 91 s of further observation, `/api/command` returned 503 `no agent connected`, the route row was tombstoned, there was no verdict and no replay (the replay counters did not change) and the agent never reconnected |
| E3c | 30 agents, 10 s server outage | FAIL. The first flush after T0 was 28 heartbeats, 20,035,889 bytes, and was rejected. `agents.online` stayed 0 for the 200 s deadline plus 61 s, all 30 route rows expired, no verdict, no replay |

With the TAR plugin removed, the heartbeat `fleet_snapshot_json` was 0 bytes (observed) and the runs E2b, E2c, E3a and E3b recovered (see "Runs on the code before the buffer change"). The TAR header comment says realistic hosts emit 50 to 500 KB per snapshot, so 6 to 80 buffered heartbeats would pass 4 MiB (arithmetic, not run); a run with a real host's size distribution, or with smaller snapshots, was not done.

Cause (OBSERVED from the failing log line, plus the buffer's design): the heartbeat buffer retained heartbeats on a failed flush capped by count only (10000), with no byte bound, so the retained batch passed the server's gRPC receive limit of 4194304 bytes and could never be sent. This is existing buffer behaviour, not introduced by the replay change, and it disabled the recovery the replay provides.

Change (code, in this branch): the buffer keeps one entry per session (a newer heartbeat replaces the fields of the older one, except that the newest non-empty `fleet_snapshot_json` is kept); a flush is split into chunks of at most about 3 MiB (estimated), oldest first, the verdict of each successful chunk is consumed, and a failed chunk and the unsent ones stay buffered; `max_heartbeat_buffer_bytes` (default 67108864, valid 1048576 to 1073741824, otherwise the default with a WARN naming the key) bounds the retained buffer, dropping snapshots oldest first and then whole sessions oldest first; a single heartbeat over 3 MiB is sent without its snapshot; `max_heartbeat_buffer` now counts sessions. New counters: `yuzu_gw_heartbeat_buffer_dropped_total{reason}` and `yuzu_gw_heartbeat_coalesced_total`. Consequences: the server's `yuzu_heartbeats_received_total{via="gateway"}` under-counts while a backlog is coalesced, and an agent's topology snapshot can be one agent snapshot cycle older after an eviction (INFERRED). The server's receive limit of 4 MiB is unchanged and not raised.

## Obligations from the server-side verdict's governance ledger

The server-side change recorded six obligations for the gateway consumer (finding `F-prc-obligations`, in `governance.d/1197-batch-heartbeat-unknown-sessions.1sz0KG.jsonl`). The ledger records only that they were linked to #1197 (disposition `linked-to-#1197`), with no rationale. The reasons below were RECONSTRUCTED from the code at the branch tip by the author of this change; they are not recovered from a stored decision. Status per obligation:

1. **Replay only ids seen in at least two batches (the two-batch rule).** Not adopted. Reason (reconstructed): the replay already re-checks local liveness when an id is queued and again immediately before every send, a per-agent pending entry and the guard window bound repeats, and a second batch would only add up to one heartbeat interval of latency.
2. **Check local liveness at replay time (no ghost resurrection).** Met by `yuzu_gw_registry:entries_for_sessions/1` at queue time, which requires the agent row to agree with the session index, and by `lookup_local_session/1` immediately before each send.
3. **Dedupe against the replay queue and reuse the drip pacing.** Met by one pending entry per agent (an already queued agent is skipped), the per-session guard window, and the verdict entries feeding the existing drip with its spacing.
4. **Suppress replays while the directory is unavailable and exclude them from breaker accounting.** Two halves. Suppression is approximated, not met: a verdict that arrives while the breaker is open is dropped, but an open breaker only approximates "the directory is unavailable", and a verdict that arrives half open is queued on purpose, because its first replay is the probe (`yuzu_gw_upstream.erl`, `replay_verdict` and `enqueue_sessions`). Excluding replays from breaker accounting is not adopted. Reason (reconstructed): a replay that the server answers with `UNAVAILABLE` must still count toward the circuit breaker, so a failing server can open it (see "Replay failures feed the shared circuit breaker" in the gateway manual).
5. **A "verdict ever seen" gauge for version skew.** Not adopted. Reason (reconstructed): skew is a no-op in both directions by design (an old server never sends the fields, an old gateway ignores them), and `yuzu_gw_registration_replay_triggered_total{trigger="heartbeat"}` and `yuzu_gw_registration_replay_total` show whether replays are being sent.
6. **Sanitise ids before logging in Erlang.** Met for the ids the server lists: the verdict path logs counts only, never ids. The pre-existing DEBUG line `Registration replay: re-proxied <agent> (adopted session <id>)` still logs the session id the server returned, unsanitised (INFERRED from the code; this change did not touch that line).
