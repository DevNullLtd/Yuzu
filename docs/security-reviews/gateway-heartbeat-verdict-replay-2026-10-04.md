## Scope

After a server-only restart the server answers every `BatchHeartbeat` with the session ids it does not hold. The gateway now validates that list, resolves the ids against the sessions it still holds, and replays exactly those through the existing registration-replay drip: one pending entry per agent, a per-session guard window, a cap on verdict appends, and the circuit breaker in front of every replay `ProxyRegister`. Behaviour and operating guidance: `docs/user-manual/gateway.md` "What happens when the server restarts"; design note: `docs/adr/2002-high-availability-architecture.md` section 7c, update 2026-10-04.

This record covers one core replica. No multi-replica run exists; the multi-replica statement is read from the code.

They add: the `consume_verdict` map guard and `listed_ids` in the heartbeat buffer; the cast-boundary cap and type check of `replay_sessions` (`bound_session_ids`, `replay_verdict`); control byte replacement in `reject_reason_for_log`; the HELP text correction of the truncated counter; and, in the second fix round, redaction of the reason and the log in `format_status`, an exception wrap of the RPC bodies, a non-map reply guard at the replay arm and in the agent service register, and C1 control byte replacement (the other logged server text, the gRPC message of a failed RPC, now goes through the same cut and replacement). A further round of post-rig code changes adds four more: `registration_replay_spacing_ms` is validated like the other two replay keys (default 20, valid 0 to 60000, otherwise the default with one warning naming the key); `heartbeat_batch_interval_ms` is validated (default 1000, valid 100 to 60000, otherwise the default with one warning naming the key) and the heartbeat buffer skips casting a verdict to the upstream client while that client's mailbox holds more than 100 messages, counting those ids as `yuzu_gw_heartbeat_verdict_dropped_total{reason="queue_full"}` with one debug line; the truncated-verdict warning is rate limited to one per 60 s per heartbeat buffer process (the limit resets when that process restarts; the counter still counts every occurrence, and the warning text ends with `suppressed N`); and a logger primary filter, `yuzu_gw_crash_redact`, installed at application start, redacts the crash report and the supervisor `child_terminated` report of the upstream client (the process mailbox becomes a count, and the exception and reason keep no argument lists). A last round of post-rig code changes, also not rig-run, adds: (a) `yuzu_gw_upstream:proxy_register/1` and `proxy_inventory/1` catch an exit of their call to the upstream client (a crash, the 30 s timeout, or the process not running during a restart) and return `{error, upstream_unavailable}`, never logging the exit reason (which carries the registration request) and logging one caller-side warning that names only the kind (`noproc`, `timeout` or `other`); (b) the per-agent process `yuzu_gw_agent`, which holds its stored registration request, now has a `format_status` that redacts it, and the crash report filter `yuzu_gw_crash_redact` also covers the reports of `yuzu_gw_agent` processes; (c) the HELP text of `yuzu_gw_heartbeat_verdict_dropped_total` now says that `queue_full` also covers the upstream mailbox backlog; and a shared redaction helper module used by both `format_status` callbacks and the filter. Two behaviour changes come with them: an exception inside the upstream client's own RPC calls used to crash the process and reset the circuit breaker; it is now a counted failed RPC (telemetry code `exception`, one WARN with the exception class and a redacted reason); and a verdict is no longer cast while the upstream client's mailbox is over 100 messages, so the `queue_full` reason now covers a full replay queue or an upstream message backlog. A final round of post-rig code changes, also not rig-run, adds: (a) the exit wrapper `yuzu_gw_safe_call` is now used at three call sites, `yuzu_gw_upstream:proxy_register/1`, `proxy_inventory/1` and `yuzu_gw_registry:register_agent/7` (a third site that carries a registration request); the callers get `{error, upstream_unavailable}` or `{error, registry_unavailable}`, the per-agent process init stops with the fixed reason `registry_unavailable`, and the wrapper's warning is limited to one per second per called process and names only the class (`noproc`, `timeout` or `other`); (b) `format_status` exists for the registry as well, and the crash report filter `yuzu_gw_crash_redact` now covers three processes (`yuzu_gw_upstream`, `yuzu_gw_agent`, `yuzu_gw_registry`), including the `gen_statem` terminate report of a per-agent process and the supervisor reports that carry a reason; (c) the application env key `upstream_call_timeout_ms` (default 30000), a test seam that also works as a setting; (d) the HELP text of `yuzu_gw_heartbeat_verdict_dropped_total` now names both causes of `queue_full`; and (e) one bounded env_int helper shared by the upstream client and the heartbeat buffer. They validate inputs and harden logging, and they were checked by eunit and dialyzer only.

## Stuck heartbeat batch (agent with the TAR plugin)

OBSERVED on a rig, after the runs above, with one real agent running its default plugin set (so with the TAR plugin), one core replica, debug builds, at `848709698`. The earlier runs R1 to R6 used an agent without the TAR plugin, so their heartbeats were small and did not meet this. A heartbeat from an agent with the TAR plugin can carry a `fleet_snapshot_json` of 200 to 800 KB (this rig host, busy).

| Run | Scenario | Result |
|---|---|---|
| unplanned long outage | server down 15.6 minutes (a local port collision kept it from restarting; not planned) | the gateway circuit breaker opened and its own recovery replay ran 36 s after the server was healthy again, but every later `BatchHeartbeat` failed with `Received message larger than max (24805137 vs. 4194304)` and never drained (the retained batch grew by about 0.8 MB per buffered heartbeat). The server's route row was reaped, and recovery came only from restarting the gateway |
| E2a | planned 300 s server outage | FAIL. After T0 every `BatchHeartbeat` failed with `Received message larger than max (N vs. 4194304)`. `agents.online` stayed 0 for the whole 420 s deadline plus 91 s of further observation, `/api/command` returned 503 `no agent connected`, the route row was tombstoned, there was no verdict and no replay (the replay counters did not change) and the agent never reconnected |

Cause (OBSERVED from the failing log line, plus the buffer's design): the heartbeat buffer retained heartbeats on a failed flush capped by count only (10000), with no byte bound, so the retained batch passed the server's gRPC receive limit of 4194304 bytes and could never be sent. This is existing buffer behaviour, not introduced by the replay change, and it disabled the recovery the replay provides.

Change (code, in this branch): the buffer keeps one entry per session (a newer heartbeat replaces the fields of the older one, except that the newest non-empty `fleet_snapshot_json` is kept); a flush is split into chunks of at most about 3 MiB (estimated), oldest first, the verdict of each successful chunk is consumed, and a failed chunk and the unsent ones stay buffered; `max_heartbeat_buffer_bytes` (default 67108864, valid 1048576 to 1073741824, otherwise the default with a WARN naming the key) bounds the retained buffer, dropping snapshots oldest first and then whole sessions oldest first; a single heartbeat over 3 MiB is sent without its snapshot; `max_heartbeat_buffer` now counts sessions. New counters: `yuzu_gw_heartbeat_buffer_dropped_total{reason}` and `yuzu_gw_heartbeat_coalesced_total`. Consequences: the server's `yuzu_heartbeats_received_total{via="gateway"}` under-counts while a backlog is coalesced, and an agent's topology snapshot can be one agent snapshot cycle older after an eviction (INFERRED). The server's receive limit of 4 MiB is unchanged and not raised.

Post-fix rig run: pending (not run yet; fill in the scenario, the commit it ran on, the outage length, the snapshot size seen and the recovery time here). Until this line carries numbers, that the change closes the stuck batch is INFERRED from the design, not observed.

## Obligations from the server-side verdict's governance ledger

The server-side change recorded six obligations for the gateway consumer (finding `F-prc-obligations`, in `governance.d/1197-batch-heartbeat-unknown-sessions.1sz0KG.jsonl`). The ledger records only that they were linked to #1197 (disposition `linked-to-#1197`), with no rationale. The reasons below were RECONSTRUCTED from the code at the branch tip by the author of this change; they are not recovered from a stored decision. Status per obligation:

1. **Replay only ids seen in at least two batches (the two-batch rule).** Not adopted. Reason (reconstructed): the replay already re-checks local liveness when an id is queued and again immediately before every send, a per-agent pending entry and the guard window bound repeats, and a second batch would only add up to one heartbeat interval of latency.
2. **Check local liveness at replay time (no ghost resurrection).** Met by `yuzu_gw_registry:entries_for_sessions/1` at queue time, which requires the agent row to agree with the session index, and by `lookup_local_session/1` immediately before each send.
3. **Dedupe against the replay queue and reuse the drip pacing.** Met by one pending entry per agent (an already queued agent is skipped), the per-session guard window, and the verdict entries feeding the existing drip with its spacing.
4. **Suppress replays while the directory is unavailable and exclude them from breaker accounting.** Two halves. Suppression is approximated, not met: a verdict that arrives while the breaker is open is dropped, but an open breaker only approximates "the directory is unavailable", and a verdict that arrives half open is queued on purpose, because its first replay is the probe (`yuzu_gw_upstream.erl`, `replay_verdict` and `enqueue_sessions`). Excluding replays from breaker accounting is not adopted. Reason (reconstructed): a replay that the server answers with `UNAVAILABLE` must still count toward the circuit breaker, so a failing server can open it (see "Replay failures feed the shared circuit breaker" in the gateway manual).
5. **A "verdict ever seen" gauge for version skew.** Not adopted. Reason (reconstructed): skew is a no-op in both directions by design (an old server never sends the fields, an old gateway ignores them), and `yuzu_gw_registration_replay_triggered_total{trigger="heartbeat"}` and `yuzu_gw_registration_replay_total` show whether replays are being sent.
6. **Sanitise ids before logging in Erlang.** Met for the ids the server lists: the verdict path logs counts only, never ids. The pre-existing DEBUG line `Registration replay: re-proxied <agent> (adopted session <id>)` still logs the session id the server returned, unsanitised (INFERRED from the code; this change did not touch that line).

OBSERVED before these fixes, by a security reviewer running the real application with a real gRPC client: the request reached the log through the exit reason of the calling handler process for three triggers (an upstream crash with a call queued, a 30 s stall with no crash, the restart gap), and through the crash report of a forced per-agent process crash. Not rig-tested by this record: no crash of either process was provoked on a rig by the author of this change. Not covered: use of the modules outside the application (no filter is installed there), a report shape the filter does not recognise, hot-loading the code into a running node (not a supported deployment path for the gateway), and any other process holding a registration request. The earlier stand-in probe (OTP 28.4.2) result stays as the history of the first measurement (see "Known limits" in the gateway manual).
- The heartbeat buffer change (one entry per session, chunked flush, byte cap) on a rig: the post-fix run with a TAR plugin agent is pending (see "Post-fix rig run:" above). Also not tested: more than one agent with large snapshots, a backlog that reaches `max_heartbeat_buffer_bytes` on a rig, and the `snapshot_oversize` path with a real agent.
- Known limits of the buffer change: (1) the agent's snapshot size is not bounded here. The agent proto comment says 5 to 20 KB typically, 200 to 800 KB was observed on one busy host, and the server accepts up to 2 MiB (`kPushedSnapshotMaxBytes`, read from the code). A smaller snapshot on the agent side is a follow-up for the agent side (no issue number yet). (2) The server does not configure its gRPC maximum receive size explicitly (INFERRED from a search of the server and gateway sources for the setting; not run), so the roughly 3 MiB chunk relies on the library default of 4194304 bytes staying as it is. (3) `flush_sync`'s 5 s shutdown wait may be exceeded by a shutdown flush that needs several chunks (INFERRED from the code; not run); what is still buffered is then lost with the process.
