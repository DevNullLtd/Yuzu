# 4003 — CAVM v20 adoption on Yuzu's reachability graph

> **Implementation status (2026-09-07 ADR reconciliation):** Accepted — deferred, not started. Zero crown-jewel/trust-zone/AMAPC/chain-centrality implementation in `server/core/src` (the only "crown jewel" hits are unrelated CA-root-key comments in `ca_store.hpp`/`key_provider.hpp`/`server.cpp`). Deferred, not withdrawn: re-homes into a use-case engine under ADR-1005 Phase 7 (not started, #4099); NOT grandfathered — faces ADR-1005 Decision 2 at implementation.

> Records how Yuzu adopts the CAVM v20 whitepaper (Andy Younie, July 2026 — an external design document, not tracked in this repo) into the reachability-graph architecture ADR-0002/0005 already committed, and into the observed-reachability MVP trade-off ADR-4002 already accepted. CAVM v20 is a substantially more complete graph-theoretic prioritization framework (formal metrics, an operational stability layer, remediation batching, speculative scoring) than anything scoped when 4001/4002 landed. This ADR decides what's adopted now, what's deferred, and — critically — how CAVM's own default graph model (coarser, asset-level, no existing integration) maps onto Yuzu's *already more precise* service-level graph, rather than adopting CAVM's model wholesale and discarding what Yuzu already has.

## Context

ADR-4002 (2026-07-01) committed Yuzu to observed reachability as a deliberate, eyes-open lower-bound MVP substrate for CAVM-style scoring. It did not decide *how much* of CAVM's actual algorithmic machinery Yuzu adopts, because CAVM's own specification hadn't reached this level of formality yet. The v20 whitepaper now provides: chain centrality, crown-jewel reachability, chained risk, and an attacker-prior component composing into a per-vulnerability composite priority score (CPS); average minimum attack path complexity (AMAPC) as a board-level resilience metric; exploitation utility classification (EUC) as a per-instance attacker-state-transition taxonomy; a gate model for protecting scheduled remediation from rescore churn (landed separately in ADR-4004); speculative scoring; and remediation batching.

Two things make this reconciliation non-trivial rather than a straight port:

1. **CAVM's default graph model is coarser than Yuzu's own.** The whitepaper's node schema (Annex B.1) is asset-level, with privilege-state expansion applied uniformly (Annex B.3 Stage 7 — every node duplicated into `@none/@user/@admin/@system` variants). ADR-0002 already rejected a flat host-only graph for the same reason CAVM's own reasoning would predict — *"cannot express 'the CVE is on the SSH service that is actually exposed' vs 'a CVE on a library nothing listens on'"* — and already commits CVE/value attachment to the **service** node tier, not the host. Adopting CAVM's coarser default would be a regression against Yuzu's own committed architecture, not an upgrade.
2. **CONTEXT.md already has committed vocabulary CAVM's whitepaper doesn't know about.** `Asset value (Crown jewel)`, `Trust zone`, `Entry point`, `Attack path`, and `Chokepoint` are all pre-existing, ratified glossary terms (authored against ADR-0002/0005) that overlap heavily with CAVM's crown-jewel/breach-point/AMAPC/chokepoint concepts — in most cases more precisely than CAVM's own defaults. This ADR reconciles CAVM's formal algorithms against *that* vocabulary, not the other way around.

## Decision

### 1. Staged adoption, not the full v20 framework

Adopted now, on data Yuzu already ingests, no new external integration required:

- **Chain centrality** (unweighted — Decision 5), **crown-jewel reachability**, **chained risk**, and **AMAPC** — the whitepaper's four core graph metrics.
  - **`best_path_through(v)`** — the shared building block for the next two: the lowest-complexity exploit path from any entry point that passes through node `v` to *any* crown jewel (ties broken arbitrarily but deterministically, e.g. lowest `crown_jewel` id). Both metrics below evaluate the *same* path for the same node, not independently-chosen ones.
  - **Crown-jewel reachability** — `max over cj in crown_jewels of 1/(1 + path_complexity(shortest path from v to cj))` (CAVM Annex C.2, restated in-repo). **Higher is closer/riskier** — inverted from raw complexity on purpose, so it composes correctly with CPS's positive weight below. `0` means "no path to any crown jewel found" (including the empty-`crown_jewels`-set case, since `max` over an empty sequence is conventionally 0 here) — a genuinely neutral floor under this polarity, not a misleading one. Distinct from chain centrality (which rewards sitting *on the path* between entry points and crown jewels, not proximity to one).
  - **Chained risk** — `product(epss_score(e) for e in best_path_through(v)) * max_cvss(best_path_through(v)) / 10.0`, floored at `0.01` so a viable chain never scores exactly zero (CAVM Annex C.3, restated in-repo). Already normalized to roughly `[0.01, 1.0]` by the `/10.0` term — captures that a chain is only as loud as its worst finding, discounted by how likely the whole chain is to be walked, not diluted by averaging.
  - (All three defined here because the whitepaper is external/untracked — this is their first in-repo specification, not a restatement of something already citable.)
- **The composite priority score (CPS)** — the per-vulnerability ranking a remediation queue is actually ordered by, computed in-repo as (weights per the whitepaper's Annex C.5, restated here since the whitepaper itself isn't tracked): `CPS = 0.30·centrality + 0.25·crown_jewel_reachability + 0.25·chained_risk + 0.20·attacker_prior`. All four components are scaled to roughly `[0,1]` before weighting (chain centrality is a fraction by construction; crown-jewel reachability and chained risk are inverted/normalized above; `attacker_prior` is an EPSS probability), so the weights mean what they say — no term dominates purely from unit mismatch. `attacker_prior(cve) = epss_score(cve)` for an internet-facing node, or `min(1.0, epss_score(cve) * ttp_prior_multiplier)` for an internal one (`ttp_prior_multiplier` ranges 1.0 with no CTI to 3.0 for a strong TTP match — CAVM Annex C.5, restated in-repo). It degrades gracefully to the internet-facing formula (EPSS-only, multiplier pinned at 1.0) with no CTI, which the module already ingests, so CPS is fully computable without the CTI dependency below.
- **EUC** (exploitation utility classification) — Decision 4.

**Degenerate case, no crown jewels declared yet (a fresh deployment, or before an operator has used Decision 6's mechanism):** `crown_jewel_reachability` is `0` for every node under the inverted-polarity formula above (a true, non-misleading floor — "no crown jewel to be close to," consistent with its own semantics, unlike a naive raw-complexity `0` would be); chain centrality is likewise `0` for every node (nothing to be *between*). `chained_risk` shares this fate for the same reason: it evaluates over `best_path_through(v)`, which is empty whenever no crown jewel exists to route toward, so it floors to the same `0.01` CAVM's own formula already reserves for "a viable chain that shouldn't read as exactly zero" — reused here for "no chain exists to evaluate," a second, honestly-named use of the same floor value rather than a separate undefined case. AMAPC (min over an empty crown-jewel set) is **undefined**, reported as `N/A`, never `0` — a `0` would misleadingly read as "zero attack-path complexity," the opposite of the intended "nothing has been assessed yet" meaning; AMAPC and `crown_jewel_reachability`/`chained_risk` deliberately use different degenerate-case conventions because they answer different questions (AMAPC reports "how hard is the easiest path" only over jewels that exist; the other two report "how close/risky is this node," where "no jewel exists" is honestly a floor, not an undefined value). **CPS in this state is really just `attacker_prior` plus a fixed, near-zero offset from the floored `chained_risk`** — not a genuine two-term combination — so the dashboard/API surface consuming CPS (ADR-4001) must flag this as degraded (e.g. "crown-jewel-aware scoring not yet available"), not present a full-looking score silently missing three of its four components' real signal.

**Store unavailable is not the same as empty (Gate 6 sre finding).** The degenerate-case floors above apply only when the `AssetValue`/`TrustZone` store is up and genuinely holds no declarations — never when a read against it fails (store down, corrupted, connection lost). Per this codebase's own precedent (the software-inventory `list_inventory` route returns 503 rather than letting a store outage alias to "installed nowhere," `rest_api_v1.cpp`), Decision 6's REST/MCP surface must return 503 on store unavailability, and `attack_path_engine`'s in-process consumption must carry an explicit degraded flag distinct from this section's legitimate `0`/`N/A` floors. Falling through to the empty-declaration path on a store error would present a false, fully-scored-looking "no crown jewels" CPS — a fabricated all-clear indistinguishable from the genuine case, the same failure class the software-inventory precedent exists to prevent. This pairs with Decision 6's `/readyz`/`/healthz` commitment below — same store-down event, two required surfaces.

Named future work, explicitly not blocking this ADR or M1–M5 of the vulnerability-management module:

- **Value-weighted chain centrality** — Decision 5 ships unweighted centrality now. Crown-jewel membership is binary by definition (a crown jewel *is* the ceiling — see Decision 5), so there's no gradient to weight *within* that set; a future differentiator, if one is ever needed, more plausibly comes from widening the algorithmic target set to include graded tiers (`high`/`standard`, Decision 6) with real per-tier weights, not from a continuous value inside `crown-jewel` itself. Not scoped now.
- **CTI/TTP-weighted `attacker_prior`** — no threat-intel ingestion source exists in Yuzu today; `attacker_prior` runs EPSS-only until one does.
- **SOC/EDR/SIEM-integration-dependent gate triggers** (SOC anomaly detection, MOAK-class+KEV combo) — ADR-4004's `gate_state` ships with only the triggers sourced from data already flowing (KEV addition, EPSS threshold breach, EPSS week-on-week spike, published PoC).
- **Speculative scoring's AI-assisted-scan-status input** — this is a source-code SAST-class capability (Constantine-class tooling), unrelated to package/CVE correlation; a different capability Yuzu doesn't have, not a near-term extension of this module.
- **Remediation batching / co-location sequencing** — maps cleanly onto the existing `/auto` Deploy machinery (`DeploymentRunStore`) as a future consumer, but isn't built now.
- **Crown-jewel Stage 3/4 automation** (CMDB enrichment, automated crown-jewel detection from data-flow/auth-log analysis) — Decision 6 below builds Stage 1/2 (manual, operator-declared) only.

### 2. CAVM's path algorithms run directly on ADR-0002's service-level graph — no asset-level collapse

Chain centrality, crown-jewel reachability, chained risk, min-path-complexity (AMAPC), and CPS all operate on the graph exactly as ADR-0002 defines it: host nodes and service nodes (`host, port, protocol, owning process`), CVE/value attached at the service, two edge classes (network reachability, local-IPC). This is *more* precise than CAVM's own asset-level default, not a simplification of it — it already targets the "which running service actually exposes the vulnerable package" precision CAVM's whitepaper doesn't natively have.

**Known, honestly-flagged gap, not solved by this decision:** the process-to-package correlation ("does this specific listening service actually load this specific vulnerable library") isn't collected today. ADR-0002 already designs CVE-to-service attachment on the assumption this exists; the collector that makes it true doesn't yet. This ADR doesn't fix that — it's a named dependency for whichever milestone lands the component-inventory-to-process correlation.

### 3. Privilege escalation — a bounded ladder on the host tier, not the service tier

CAVM's Stage 7 privilege-state expansion (`@none/@user/@admin/@system` per node) is adopted, but scoped to ADR-0002's **host** node tier only, not applied per-service. This keeps duplication bounded at 4 states per host rather than 4 states × every service on it.

**Every F(oothold)/LM (lateral movement)/PE (privilege escalation) exploit edge bridges to `host@<privilege_postcondition>`, not only PE-classified findings.** CAVM's own edge schema (Annex B.2) already carries `privilege_precondition`/`privilege_postcondition` on every exploit edge, not just PE ones — a foothold RCE with postcondition `user` lands the attacker at `host@user`, not merely at the compromised service. PE edges are the special case that need no new service compromise at all: a pure `host@<precondition> → host@<postcondition>` transition using whatever's already been reached, generalizing ADR-0002's existing "setuid/sudo hop" local-IPC edge kind. Any local-IPC or network edge whose exploit precondition requires a given host privilege level is only traversable once that `host@<state>` node has been reached earlier in the same path walk — structural ordering by construction, no runtime precondition check needed, the same trick CAVM's own Stage 7 relies on.

**Privilege states are cumulative, not independent flags.** `host@admin` satisfies any precondition gated on `host@user` (the ladder is ordered `none < user < admin < system`) — an edge requiring `host@user` is traversable from `host@admin` too, not only from an exact `host@user` match. Without this, a real path is invisible to the walk whenever an attacker reaches a *higher* state than an edge's stated precondition through a different route than the one that defined it — a false "no path" on a genuinely-reachable target. **Named modeling limitation:** this assumes the ladder's four states form a strict total order where a higher tier's capability set is a strict superset of every lower tier's. Real OS/network access control is sometimes non-nested (group-scoped sudo grants, service-account-specific ACLs) — a `host@admin` compromise doesn't always grant literally everything a narrower `host@user`-gated edge requires. The model accepts this simplification deliberately (matching CAVM's own `@none/@user/@admin/@system` ladder, Annex B.3 Stage 7); it is a coarsening, not a correctness bug, and it errs toward *more* traversable paths rather than fewer, which is the safe direction for a security-prioritization tool to be wrong in (a missed path is a false sense of security; an extra one is, at worst, over-caution).

**DA (data access) edges are excluded from this bridge by default.** CAVM's own EUC definition for DA gives its postcondition as "access to data on or accessible from the target," not genuine execution presence on the host — a leaked config file is not a landed session. Bridging a bare DA edge to `host@<postcondition>` would let downstream PE/LM edges become wrongly traversable off a data leak that never actually put the attacker on the box. Where leaked data (e.g. credentials) genuinely grants presence, that's modeled as a separate F or LM edge using that data, not as the DA edge itself touching the host-state ladder.

**The bridge is a zero-cost annotation, not a second weighted hop.** An exploit edge's destination is `(service, host-state)` jointly — the same edge, not an additional edge with its own `edge_complexity`. Charging a second hop's worth of complexity for host-state arrival would inflate AMAPC and distort centrality for no real reason: the attacker didn't do extra work by also holding host-level privilege, that's a side-effect of the exploit they already paid for.

This is a narrow, per-node, exploit-sequencing device only. It is explicitly **not** the cross-host identity/account/ACL graph ADR-0002 already declared out of scope ("no identity/account nodes... the BloodHound space we do not enter") — that non-goal stands unchanged; this ladder never models group membership, credential relationships, or domain trust, only "what privilege level has an attacker reached on this one host via exploitation."

### 4. EUC computed at graph-construction time, as an edge attribute — never persisted separately

EUC depends jointly on a finding, the network position it's approached from, and the privilege state its edge's precondition requires — genuinely per-edge, not per-finding or per-node. **It is static per edge once the edge exists** (fixed by the edge's own endpoints and precondition, not something that varies by which path a later walk happens to take through it) — it is computed once, by `attack_path_engine`, during the same pass that already builds the reachability→exploit-edge graph, living in the same in-memory, TTL-evicting structure `FleetTopologyStore` already uses (rebuilt daily with incremental updates), never a finding-store column and never a standalone refreshed SQL table, and never recomputed per-traversal during a centrality/AMAPC walk. Precomputing it independently of graph construction (e.g. for every theoretical edge across the whole fleet up front) would still be wasteful — it's computed alongside each edge as that edge is built, not ahead of or separate from that pass.

### 5. Chokepoint ranking adopts CAVM's chain-centrality mechanism, unweighted — amends CONTEXT.md and `docs/vuln-scan-engine-design.md`, not classical betweenness

CONTEXT.md's `Chokepoint` entry currently ranks by defender ROI (`crown-jewel value × path probability`, summed over every path a removal would break), explicitly *not* by generic graph centrality. `docs/vuln-scan-engine-design.md` §5.2 rejected "Brandes betweenness" more specifically, for two stated reasons: computational cost (O(V·E), a real concern at the 1.2M-host/HSBC-scale target per ADR-0005's Context) and semantic correctness ("wrong (weights all-pairs equally)," §5.2's own words). **Neither objection applies to CAVM's chain centrality as actually specified, and this decision does not reopen either rejection:**

- **Not all-pairs.** CAVM's algorithm is `for source in breach_points: for target in crown_jewels:` — already scoped to the declared entry-point/crown-jewel surface (ADR-0005's own "sources/sinks are the declared surface" bounding principle), never a graph-wide all-pairs computation. The "weights all-pairs equally" objection was never applicable to it.
- **Not O(V·E).** Computed as a Dijkstra-class shortest-path search per breach-point source, bounded by the declared surface — the same complexity shape as ADR-0005's attack-path scoring (detailed at implementation level in `docs/vuln-scan-engine-design.md` §5.1), not a separate graph-wide pass. It requires its own shortest-path computation over the graph *as extended by Decision 3's host-state nodes* — that graph differs from §5.1's plain service-level one, so this is not literally "free reuse" of already-computed output, but it is the same bounded, declared-surface-scoped complexity shape §5.1 already established, not a new algorithm class.

**Decision: adopt CAVM's chain centrality exactly as specified — unweighted, crediting only the single least-complex path per `(entry point, crown jewel)` pair** (`entry point` is Yuzu's term for CAVM's `breach_point` — Decision 6 maps the two; "least complex" is mathematically equivalent to "most probable," CAVM's own Annex I.3):

```
paths = all_shortest_paths(G, entry_point, crown_jewel, weight='edge_complexity')
# ties for the SINGLE minimum-complexity route only — not a top-k set.
# A path with strictly higher complexity than the minimum earns zero credit,
# even if it's a real, viable secondary route. This is CAVM's own accepted
# design (the rational-attacker model takes the easiest route, full stop),
# not an approximation this ADR introduces.
for path in paths:
    for node in path[1:-1]:
        centrality[node] += 1.0 / (len(paths) * len(breach_points) * len(crown_jewels))
```

Value-weighting is explicitly NOT adopted now — see Decision 1's future-work list for why (crown-jewel membership is binary by definition; there's no gradient within the set to weight by). This is still a real, deliberate change from the old defender-ROI formula: it credits a node for sitting on the easiest route to *any number* of crown jewels, not just its single highest-value target, and it drops the "sum every viable path" behavior in favor of "only the easiest route counts" — both `CONTEXT.md`'s `Chokepoint` entry and `docs/vuln-scan-engine-design.md` §5.2 are amended accordingly.

**Empty declared-surface handling.** If `crown_jewels` or `breach_points` is empty (nothing declared yet, e.g. a fresh deployment), the loop body never executes — every node's centrality is 0, the chokepoint ranking is empty, not an error. This is the correct behavior (there is genuinely nothing to rank yet), and the dashboard/API surface consuming this output (ADR-4001) must render "no crown jewels/entry points declared yet" rather than a bare empty list that reads as "no chokepoints exist." As with Decision 1's degenerate case, this floor applies only when the store is genuinely empty — a store-unavailable read must never alias to this same empty-ranking output; see Decision 1's store-unavailable-vs-empty distinction above.

**Host-state ladder nodes (Decision 3) are excluded from centrality/chokepoint output.** A `host@<state>` node can sit on a path (per Decision 3's bridging), but it isn't a remediable target — there's nothing to patch or isolate about a privilege-state annotation, only about the service whose exploit granted it. Centrality accumulates per-node exactly as specified above (the formula is unchanged); the exclusion is a *display-time* filter on the ranked list, not an accumulation-time rule — no separate edge-keyed ledger is introduced. **Attribution rule:** whenever a `host@<state>` node would appear in the ranked output, its accumulated credit is instead attributed to the *nearest preceding service-sourced edge* on this path (walking back past any host-state-to-host-state PE edges, which by Decision 3's own definition have no service source at all — "no new service compromise") — not to every service that happens to also touch that host-state node from other paths, which would double-count. **Consecutive PE hops on the same host correctly collapse to that host's single entry service** — e.g. `host@user → host@admin → host@system` via two PE edges in a row both attribute to whichever F/LM edge first landed the attacker on that host, because that is the one actual remediable action underlying the whole chain; there is nothing to separately patch about the second PE step, only about the entry point that made the host reachable at all. A *fresh* F/LM hop onto a **different** host starts a new attribution chain from that host's own entry service — attribution never crosses a host boundary.

**Resolved (2026-07-16):** Tr3kkR authored the original `Chokepoint`/`Attack path` entries; asked directly, he confirmed excluding centrality wasn't a deliberate design call against it — it simply wasn't considered when the entry was written. No reason to preserve the exclusion surfaced, so adopting centrality at all stands without qualification (the unweighted-vs-value-weighted question above is a separate, later-discovered issue, not part of what was confirmed with him).

### 6. Crown-jewel and breach-point (trust-zone) declaration — a dedicated mechanism, not tags

CONTEXT.md's `Asset value (Crown jewel)` and `Trust zone` entries are already committed, and both are already explicit, non-tag-derived axes: `Asset value` states it directly ("operator-declared... orthogonal to tags, management groups, and scope"); `Trust zone` is declared CIDR/site tiers, stated as "orthogonal to Management Group... and to Scope" (tags aren't mentioned there, but the entry never derives zones from tags either — declared ranges only). Neither has any implementation today (verified: no `crown_jewel`/`trust_zone` symbol exists anywhere in `server/core/src/`). This ADR builds them as designed, rather than retrofitting the general tag system:

**ADR-1005 mechanism-vs-engine call.** The execution plan (item iv's "Likewise" clause, appended to that item's main ADR-4002-non-absorption ruling) explicitly parks this exact class of decision, requiring a fresh boundary call rather than silent inheritance: "asset criticality plausibly has many consumers and may be mechanism, but that is a governance classification, not an inheritance." Made here, explicitly: crown-jewel/trust-zone **declaration** (the raw operator-asserted fact — is this node valuable, what trust zone is it in) is **mechanism** — a fleet-fact store analogous to tags and management groups, both already core-resident, both already classified as mechanism. It is not itself a domain interpretation. What consumes it (`attack_path_engine`'s scoring — chain centrality, AMAPC, CPS) is separately, and already, classified as **engine territory** — ADR-4001's own absorption note names `attack_path_engine` as "domain scoring in code — ADR-1005 Decision 2 engine territory" (ADR-4001), the same "baked into code... engine territory" characterization ADR-1005's own tiebreaker paragraph uses for this class of component — licensed only under the interim grandfather. So the store this decision builds stays core under the same reasoning as tags/management groups; the algorithms consuming it remain grandfathered-interim per ADR-4001/ADR-1005, unchanged by this ADR.

- **Value** is a 3-tier operator-declared axis (`crown-jewel` / `high` / `standard`) carried by the **service** (matching CONTEXT.md's existing "value is carried by the service... a host's effective value is the maximum of the values of the services/instances it carries"). `crown-jewel` is the axis's top tier and the only value CAVM's centrality/AMAPC/CPS algorithms treat as crown-jewel-set membership; `high`/`standard` are manual operator context only, feeding nothing algorithmically yet. **The `crown_jewels` target set for Decision 5's algorithms is therefore always service nodes** — value is declared at the service tier, never the host tier, so a path-walk's target is the specific crown-jewel-tagged service, not its owning host (which may carry other, non-crown-jewel services too; targeting the host would over-credit unrelated services on the same box). `host@<state>` nodes (Decision 3) are never targets — only intermediate/source waypoints. A continuous `mission_criticality` float (CAVM Annex B.1) and inheritance from Yuzu's existing `service` tag/ownership model are named future work, arriving with a CMDB integration that doesn't exist yet.
- **Breach points map onto CONTEXT.md's already-committed `Trust zone` + `Entry point` machinery**, not a new CAVM-shaped `breach-exposure` category. An operator declares ordered trust tiers (CIDR/site, e.g. `internet < partner-extranet < branch-campus < datacenter`); `Entry point` is *derived* — any service exposed across a trust-zone boundary — rather than separately tagged per device. This is a direct, cleaner mapping of CAVM's three breach-point categories (internet-facing / user-reachable / third-party ≈ services exposed from the internet / a low-trust staff-branch zone / a partner-extranet zone respectively), already more precise than CAVM's manual three-category tag because it derives from the trust-zone topology rather than requiring per-device manual classification. **Known, honestly-flagged gap, not solved by this decision:** trust-zone *declaration* has no implementation today, and neither does the entry-point *derivation* computation that reads it against the reachability graph (comparing each service's trust zone to the zones it's reachable from) — this decision specifies the shape, it doesn't build the computation, same as Decision 2's process-to-package correlation gap.
- **RBAC:** new dedicated securables `AssetValue` and `TrustZone` (not `Tag:Write`), each with `:Write` and `:Read` operations.
  - **`:Write`** — seeded onto `Administrator` only, matching the precedent this codebase already uses for consequential write access on this exact module lineage (`Vulnerability` CRUD is Administrator-only per ADR-4001; `rbac_store.cpp`'s Operator seed is curated per-securable, never a blanket grant, and reserves security-sensitive write access — e.g. `ApiToken` — for narrow dedicated roles or Administrator). Crown-jewel/trust-zone declarations drive CPS/AMAPC/chokepoint ranking end-to-end, so a wrong declaration has real downstream consequence — the same bar `Vulnerability` CRUD is already held to.
  - **`:Read`** — seeded to `Administrator`, `Operator`, `PlatformEngineer` — **matching `Vulnerability:Read`'s actual precedent exactly** (ADR-4001 line 66 seeds Operator/PlatformEngineer, Administrator via CRUD; an earlier draft of this bullet added `Viewer` and mis-cited this same precedent as covering it — corrected). `Viewer` is deliberately excluded: declared crown-jewel/trust-zone metadata is attacker-reconnaissance-grade ("which of our assets matter most, and where our defended perimeter is") in a way ordinary operational dashboard data isn't, so the lowest-privilege read-only role doesn't get it by default — extend to `Viewer` later only with its own independent risk justification, not as an assumed consequence of this decision.
  - **Confinement:** the `?tier=` list read (below) is a fan-out read over services fleet-wide and **must route through the `authorize_list_read` admit-then-filter chokepoint (ADR-0017)**, not a bare `require_permission` check — a group-confined operator's result set is filtered to services whose owning device is within their management-group scope, fail-closed on any confinement-evaluation error, matching the standing invariant CLAUDE.md states for every list/fan-out read of per-agent-adjacent data. The single-service lookup (`GET /api/v1/asset-value/{service_id}`) is a per-record scope check, not a fan-out — same effective outcome (confined operators can't read outside their scope) but via the simpler "does the caller's scope cover this one record" pattern, not the list chokepoint. `GET /api/v1/trust-zones` is **not** confinement-scoped — declared trust tiers are fleet-wide topology configuration (analogous to `tag-categories`, not per-device data), so every `TrustZone:Read`-holding principal sees the same full list regardless of management-group membership; say so explicitly rather than leaving the two routes' confinement posture ambiguous by omission.
  - **Audit:** `:Write` emits `asset_value.set` / `trust_zone.set` — corrected from an earlier `.write` draft, which cited `vuln.refresh.dispatch` (a dispatch/trigger action) as precedent when the actual shipped convention for "declare/set an entity's value" is a domain verb like `tag.set`, or `.create`/`.update`/`.delete` for CRUD-shaped entities (`guaranteed_state.rule.create`, `management_group.create`, per `docs/user-manual/audit-log.md`) — `.set` is the correct match for a single-path declare-this-value operation, fired on every successful write. The `detail` field must capture the prior tier/zone alongside the new one (before→after, not new-value-only) — this data's own stated risk bar (¶ above: "a wrong declaration has real downstream consequence") makes a *downgrade* (crown-jewel → standard, or a `PUT /trust-zones` perimeter replacement that narrows coverage) the highest-value forensic event, and new-value-only audit rows can't distinguish a downgrade from a promotion after the fact (Gate 6 compliance finding). **`:Read`'s single-lookup is not separately audited** (declared value/zone metadata isn't behavioral-PII-tier — unlike `device.live.*`, which routes through `emit_behavioral_audit` — so it follows the same convention as other non-PII REST read endpoints, which aren't individually audited); this is a named residual-risk trade-off, not a closed question — a caller with `AssetValue:Read` can loop the single-lookup route across known `service_id`s and reconstruct the full crown-jewel set while emitting zero `tier_list_read` rows, so an auditor sampling logs can reliably answer "who ran the bulk `?tier=` query" but not "who has fully enumerated the crown-jewel set by other means" (Gate 6 compliance finding; left open rather than resolved here, consistent with this ADR's honest-gap discipline). **The `?tier=` bulk list read emits its own dedicated `asset_value.tier_list_read` audit verb**, distinct from the confinement chokepoint above — per CLAUDE.md's standing "accountability is a separate control from authorization" principle (the same reasoning that gives per-agent findings reads their own dedicated audit verb beyond `authorize_list_read` alone): confinement determines *what* a caller can see, the audit verb records *that* a caller enumerated the org's crown-jewel set, which is forensically relevant even when properly authorized.
  - **Health-check coverage:** the `AssetValue`/`TrustZone` store joins the `/readyz`/`/healthz` `stores_ok` conjunction (`server.cpp`), matching every born-on-Postgres store since ADR-0012 — omitting it would let `/healthz` report healthy while this store is degraded, the exact HC-1-class gap that conjunction exists to prevent (Gate 6 sre finding).
  - Fully reconfigurable via Yuzu's existing granular RBAC `role_permissions` model with zero new mechanism required.
- **REST + MCP surface, committed now (not deferred), covering both read and write:**
  - `GET /api/v1/asset-value/{service_id}` — single-service lookup (path param, not query param — avoids the ambiguous combined-query-param shape an earlier draft had). `404` for a service that doesn't exist *or* that the caller's confinement scope excludes (the same code and body in both cases — the documented 404-vs-403 anti-enumeration convention, so a confined operator can't distinguish "doesn't exist" from "exists but not yours"). `200` with an explicit `null`/absent `tier` field for a service that exists, is visible, but has no declared value — untagged is a valid state, not an error.
  - `GET /api/v1/asset-value?tier={crown-jewel|high|standard}` — list by tier, confinement-filtered per above, paginated per this codebase's existing list conventions (`limit`/`offset` params, `total`/`start`/`page_size` response envelope), capped at **1000** — this codebase has no single uniform ceiling (existing list routes split between 1000 and 500 by data shape/sensitivity), so this decision names the value explicitly rather than leaving "the standard ceiling" ambiguous for the implementer: 1000 matches the closest analog, the software-inventory fleet-wide enumeration cap (Gate 6 sre finding).
  - `PUT /api/v1/asset-value/{service_id}` — declare/update a service's value tier (`:Write`).
  - `GET /api/v1/trust-zones` — the full ordered tier/CIDR-site declaration list, unconfined (see above), small enough not to need pagination.
  - `PUT /api/v1/trust-zones` — replace the full ordered trust-zone declaration (`:Write`) — a small, whole-list config object, not incrementally patched. **No concurrency control** (no `If-Match`/ETag precedent exists anywhere in `rest_api_v1.cpp` for write paths, only read caching) — two admins racing an edit silently clobber each other; acceptable for a rarely-edited config object, named here rather than left undiscovered (Gate 6 enterprise-readiness finding).
  - All five carry the standard A4 error envelope and register in `/api/v1/openapi.json` (A2 discoverability). MCP twins: `get_asset_value`, `list_assets_by_value_tier`, `set_asset_value`, `list_trust_zones`, `set_trust_zones` — enumerable via `tools/list` (A3), all `readonly` tier except the two `set_*` writes, each with a decision-grade description, a bounded input schema, and a typed output schema mirroring its REST twin's response body verbatim (no MCP-specific reshaping) per the A5 agentic-context contract. This satisfies ADR-1005 Decision 4's twin mandate directly rather than deferring it to a tracked exception — the store this decision builds has no reason to ship surface-less on either read or write.
  - **Distinct from derived CPS/AMAPC visibility.** This RBAC/REST/MCP surface gates the *raw declaration* (is service X crown-jewel, what trust zone is it in) — it does not gate `attack_path_engine`'s consumption of that same data to compute chain centrality/AMAPC/CPS, which reads the store in-process as a grandfathered-interim engine component (per this Decision's opening paragraph) and sits outside this boundary entirely. Dashboard-rendered CPS/AMAPC visibility is gated by `Vulnerability:Read` (ADR-4001), a separate securable — not automatically implied by holding `AssetValue:Read`/`TrustZone:Read`.

## Considered and rejected

- **CAVM's own asset-level node model with uniform privilege-state expansion.** Rejected — coarser than what ADR-0002 already commits to, and would discard the service-level precision that's the entire reason ADR-0002 rejected a flat host graph in the first place.
- **Value-weighted chain centrality (an earlier draft of this ADR).** Considered and reverted: the formula required a numeric gradient *within* the crown-jewel set, but crown-jewel membership is binary by definition (a crown jewel is the ceiling of the value axis, not a graded position on it — Decision 6) — every member shares one value, so the weight term cancels algebraically and the formula silently collapses to unweighted centrality while claiming otherwise. Caught by three independent Gate 4 governance reviews (happy-path, unhappy-path, architect) before this ADR shipped. CAVM's literal unweighted default is adopted instead (Decision 5); a real gradient, if ever needed, more plausibly comes from widening the target set to graded tiers, not from weighting within `crown-jewel`.
- **Folding crown-jewel/breach-point declaration into the general tag system.** Considered mid-design (a `criticality`/`breach-exposure` tag-category pair), then rejected on discovering CONTEXT.md already commits both concepts as explicitly non-tag-based, and neither is implemented yet — no reason to retrofit tags over building what was already designed.
- **Adopting the full v20 framework in one pass.** Rejected per the whitepaper's own maturity-gradient argument and Yuzu's existing "don't block core matching on CAVM" posture (§7 of the vulnerability-management module's own design work) — CTI, SOC integration, speculative scoring's AI-input, and remediation batching all carry real external dependencies Yuzu doesn't have yet.
- **Classical (Brandes) all-pairs betweenness centrality.** Still rejected, for the exact reasons `docs/vuln-scan-engine-design.md` §5.2 already gave (O(V·E) at 1.2M-host scale; "wrong (weights all-pairs equally)"). This ADR does not reopen that rejection — CAVM's chain centrality as actually specified was never that algorithm (Decision 5 above), so there was no live tension to resolve, only a documentation gap where ADR-0005/the engine-design doc weren't cross-referenced against this ADR's arrival (and an earlier hardening-round pass misattributed the engine-design doc's own section numbers and quotes to ADR-0005 directly — fixed here).
- **Yen's top-k paths as the credit-accumulation set for centrality (an earlier draft of this ADR).** Reverted in favor of CAVM's literal `all_shortest_paths` semantics (ties for the single minimum-complexity route only) — the ADR previously claimed both "single lowest-complexity path" and a top-k-based `paths` variable simultaneously, a self-contradiction that would have let two implementers build materially different, incompatible algorithms from the same text.

## Consequences

**Gained:**
- A materially more complete graph-scoring model (CPS + AMAPC + unweighted chain centrality + EUC) than ADR-4001/4002 originally scoped, built without regressing any of ADR-0002's existing precision.
- CONTEXT.md's pre-existing crown-jewel/trust-zone/entry-point vocabulary turns out to already be a better fit for CAVM's breach-point/crown-jewel concepts than CAVM's own defaults — validated, not replaced.
- Confirmed, not just asserted, that chain centrality is tractable at the 1.2M-host/HSBC-scale target ADR-0005's Context sets — the same bounded, declared-surface-scoped shape as ADR-0005's own algorithm, and both `docs/vuln-scan-engine-design.md` and `CONTEXT.md` now cross-reference this ADR instead of silently describing a superseded formula.
- The `AssetValue`/`TrustZone` store-vs-engine split makes an explicit ADR-1005 mechanism call this codebase's own execution plan required but hadn't yet made (Decision 6).
- Decision 6 ships with a committed REST+MCP surface (read and write), management-group confinement on the fan-out read, and named audit verbs from the start, rather than a capability landing surface-less pending a future exception — satisfying ADR-1005 Decision 4's twin mandate directly.
- In-repo definitions now exist for crown-jewel reachability, chained risk, and CPS's actual weights — previously citable only via the external, untracked whitepaper.

**Costs / open items:**
- The process-to-package correlation collector (which service actually loads which vulnerable component) still doesn't exist — EUC and service-level CVE attachment both assume it; this ADR names the gap, doesn't close it.
- The crown-jewel/trust-zone declaration mechanism (store, RBAC, REST+MCP surface, audit, dashboard surface) *and* the entry-point derivation computation that reads trust zones against the reachability graph are both specified here but not yet built — CONTEXT.md described the shape years before any implementation landed, and this ADR is the first to schedule the actual build.
- CTI, SOC-driven gate triggers, speculative scoring's AI-scan input, remediation batching, and value-weighted centrality all remain named, undated future work — none has a committed milestone.
- Several failure-mode gaps flagged by Gate 4 unhappy-path review are named but not solved here, consistent with this ADR's own honest-gap discipline: the mechanism that turns a DA (data-leak) finding into a genuine F/LM edge when the leaked data grants real presence is unspecified (Decision 3); AMAPC does not distinguish "no path exists" from "no path within the depth bound" (a real path beyond the ~5-hop cutoff reads identically to a genuinely unreachable target); `FleetTopologyStore`'s daily-rebuild swap atomicity against a concurrent dashboard read is assumed, not guaranteed, once EUC context is added to what a rebuild changes.
- **Corrected (Gate 6 enterprise-readiness finding):** an earlier draft of this bullet claimed the new RBAC securables have no upgrade-migration path for an already-populated `rbac.db`. That's overstated — `rbac_store.cpp`'s `seed_defaults()` runs unconditionally on every boot via `INSERT OR IGNORE`, so `Administrator` picks up `:Write`/`:Read` automatically on upgrade via its existing generic grant loop, and `Operator`/`PlatformEngineer` pick up `:Read` via the dedicated seed lines the implementer adds — the same mechanism the `SoftwareLicensing` precedent already documents ("an upgrade inserts the new type fresh"). Residual implementer note, not a gap: the generic `Administrator` loop will also over-grant inert `Execute`/`Delete`/`Approve` no-ops on the new securable types, harmless but worth a one-line comment when built.
- **`Viewer`'s exclusion from `:Read` needs to reach the compliance-questionnaire / role-mapping documentation at ship time** (Gate 6 enterprise-readiness finding) — a customer's SOC 2 auditor typically maps to `Viewer`, and crown-jewel/trust-zone classification is often exactly what such an auditor legitimately needs to see. The exclusion's risk rationale (Decision 6) is sound and stands, but it should be a documented, discoverable answer for a pilot customer, not something discovered mid-pilot.
- **`GET /api/v1/trust-zones` being fleet-wide and unconfined understates real exposure for a multi-BU/MSP deployment** (Gate 6 enterprise-readiness finding), distinct from the confinement point already made in Decision 6: declared trust-zone CIDRs describe real internal network topology, and a management-group-confined operator scoped to one business unit would see every other business unit's zone declarations too. Defensible for a single-tenant fleet (Decision 6's stated rationale); worth flagging explicitly for multi-tenant/MSP pilot onboarding rather than leaving the "analogous to tag-categories" framing to imply the exposure is smaller than it is.
- **Audit-log documentation registration.** `asset_value.set`, `trust_zone.set`, and `asset_value.tier_list_read` need to be added to `docs/user-manual/audit-log.md` (the canonical audit-verb registry) and any SIEM/evidence-collection rule set at implementation time — named here so it isn't dropped between this ADR and the build (Gate 6 compliance finding).
- **A dedicated state gauge** (e.g. `yuzu_crown_jewels_declared_total`, precedent: `yuzu_nvd_total_cves` per `docs/observability-conventions.md`) would let an operator/alert distinguish "zero crown jewels declared" from "store degraded" at a glance, complementing the 503/degraded-flag mechanism above rather than replacing it — named future work, not required for this ADR (Gate 6 sre finding).
