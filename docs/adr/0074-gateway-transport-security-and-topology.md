## Context

### What runs today

| Hop | Today | Gap |
|---|---|---|
| Agent to server, direct | Mutual TLS. The agent presents its CA-issued leaf (`yuzu://<ca-fingerprint>/agent/<id>`, about a year, renewed at two thirds). Under the generated default certificates the port asks for a certificate but does not require one, so an unenrolled agent can bootstrap; the application enforces the rest. With operator-supplied certificates the port requires one (`server/core/src/grpc_tls_credentials.cpp`, `server.cpp`). | Only single-server installs use it. ADR-2002 section 2 makes the gateway mandatory in HA. |
| Agent to gateway (`:50051`) | One-way TLS (PKI PR5c). The gateway proves itself; it does not check the agent's certificate. The agent proves itself with its enrollment token, and heartbeats are bound to its Subscribe connection. | No transport identity for the agent at the edge that will face the internet. The enrollment token is presented only at first enrollment: the agent removes its token file once a registration is accepted (`agents/core/src/agent.cpp`), so after that an approved agent's `ProxyRegister` carries no per-agent secret. Revoking a gateway-proxied agent does not cut it off (`docs/auth-architecture.md`, "Gateway-proxied agents: revocation scope"). |
| Gateway to server (`:50055`) | Mutual TLS. The server admits the gateway by an SPKI pin fixed at boot. | Pins are per pair and do not scale to many gateways and many servers. No revocation. |
| Server to gateway management (`:50063`) | Strict mutual TLS. SPKI pin, or (opt-in, #6016) the server's URI SAN `yuzu://<install>/server` (the install id is derived from the CA fingerprint). | No CRL; a manual serial deny-list (`mgmt_peer_denied`) read at boot. Pins again. |

So gateway and server already authenticate each other in both directions. The missing link is the agent at the gateway.

### Why it matters now

- **Scale.** ADR-0069 sets 1.2 million agents and 100,000 per gateway.
- **SaaS.** Gateways will face the internet. A compromised or impersonated gateway must not be able to act as an agent.
- **Customers' PKI.** Most target customers already deploy a machine identity certificate (on Windows, in the certificate store behind CNG, often non-exportable or in the TPM). The direction of travel is SPIFFE/SPIRE for workload identity and RATS for attestation.
- **Topology.** The product needs agents that know several gateways, gateways that can be drained for maintenance, and gateways that use several servers writing to replicated Postgres (ADR-2002 section 7g).

### Measurements behind the transport choice (rocky9, 2026-10-28)

These come from branch `perf/gateway-idle-mem-ktls` (a kTLS handover NIF) and are not yet in the repository. Wave 0 commits the measurements the waves gate on to the repository, as an artefact, before they gate anything.

| Measure | OTP `ssl` | kTLS NIF |
|---|---|---|
| OS anonymous memory per idle agent (100 Windows agents, TLS 1.2) | 85.0 KB | 48.1 KB |
| Processes per agent | 6 | 3 |
| Handshakes per second, 4 cores | about 2,500 to 3,000 | about 6,000 to 6,600 |
| Memory per connection during a 30,000-handshake storm | 34.3 KiB | 8.4 KiB |

The kTLS NIF was fuzzed for 91.2 million executions (92% line coverage, one bug found and fixed) and ran clean under ASan inside the BEAM. It can verify no peer certificate today.

## Decision

### D1. Gateway and server: CA trust, then identity, then revocation

All three, in this order:

1. **Trust our CA, not per-pair pins.** Gateways and servers admit each other by a certificate chaining to the install CA (or the customer's intermediate, D4). SPKI pins stay as an optional extra, not the default.
2. **Identity in the certificate.** Every certificate carries a URI SAN that names the role and the instance (D3). Each side checks the role it expects: a gateway is not a server, and an agent is neither.
3. **Revocation.** Every hop checks the revocation list (D7).

### D2. The agent edge: a separate enrollment port, and a strict main port

- **Main port.** It requires a valid client certificate at the TLS layer. A connection without one never reaches application code.
- **Enrollment port.** It accepts connections without a certificate, and the only thing it serves is enrollment. It has its own rate limit and connection cap at all times. The port is certless and faces the internet, so its cap must not be holdable by clients that never enroll: wave 2 must show that per-source limits (or an equivalent) keep it usable, and set a recovery target for a mass re-enrollment after an outage longer than a day.
- **Clean break.** This ships as a breaking change in the next release, with no fallback to the single-port behaviour. There are no production customers at the time of writing (2026-10-30); wave 2 re-checks this before it merges, and if a pilot runs agents through a gateway the upgrade note becomes a merge gate.
- **A routed-concern rule changes with it.** `.claude/routed-concerns-access-control.md` (the PKI row) forbids an `auth_fun` on the `:50051` agent listener, because it would reject every certless peer and stop agent bootstrap fleet-wide. That rule exists because today one port does both jobs. The change that splits the ports must amend the row in the same PR, with `security-guardian`: certless bootstrap moves to the enrollment port, which must never require a certificate.
- **Open: the direct port.** Whether the direct agent-to-server port of single-server installs gets the same split into an enrollment port and a strict main port. Wave 2 decides.

### D3. Identities are SPIFFE IDs

The URI SAN takes the SPIFFE form, `spiffe://<trust-domain>/<role>/<name>`. Examples: `spiffe://<trust-domain>/agent/<agent_id>`, `.../gateway/<name>`, `.../server/<name>`.

- **The trust domain (decided 2026-10-29)** is a random UUID generated once at install. The operator may set their own name at install time only; it never changes afterwards. It is not derived from the CA fingerprint: rotating the CA, or importing a customer intermediate (D4), would then rename every identity in the fleet. The SPIFFE standard itself advises a random name such as a UUID when no operator chooses one.
- **One URI SAN per certificate.** The SPIFFE X.509 standard says a verifier must reject a certificate with more than one. So the existing `yuzu://<ca-fingerprint>/agent/<id>` and `yuzu://<ca-fingerprint>/server` URIs cannot sit beside the new ones in one certificate. The migration is: verifiers accept either form for a window, then issuance flips to `spiffe://`. The CA alone chooses the SAN; a requester never does (`sign_agent_csr` already ignores the CSR's subject and SAN).
- **The role comes from the SPIFFE path, never from the EKU.** The same standard says that when a leaf carries an EKU it must list both `serverAuth` and `clientAuth`. So every leaf carries both, and the EKU no longer tells a gateway from a server or an agent. The management port's existing `serverAuth` check still passes; it simply stops being a role check.
- A SPIRE server can later replace the issuer without changing what the main port checks.

### D4. Who issues the main-port certificate

- **Yuzu issues it**, always, as a short-lived certificate with a SPIFFE ID (D6).
- **The customer's machine certificate is an enrollment credential only.** On the enrollment port the agent proves it holds the machine certificate by signing a server challenge through the platform key store (Windows CNG, macOS Keychain, Linux file or PKCS#11). That signature is application-layer, so a non-exportable or TPM-held key works. It does not need gRPC to hold the private key.
  - This matters because gRPC 1.76 (the vcpkg pin) takes the client key as PEM and has no public private-key signing hook. So the machine certificate cannot be presented on the main port as it stands.
- **The enrollment token stays a supported credential** for machines without a machine certificate.
- **Customer PKI as the root of trust:** a customer may import an intermediate CA signed by their own root, and Yuzu issues from it. Customer-issued main-port certificates (the customer's CA issuing to agents directly) are not offered at first, and the design must not rule them out.
- **Default:** a customer who brings nothing gets the Yuzu-generated root.
- **Later:** TPM or RATS evidence is added at the enrollment step.

### D5. Agent identity reaches the server end to end

The gateway checks the agent's certificate, but the server does not trust the gateway's word alone. The owner chose this so that a compromised internet-facing gateway can drop or delay traffic but cannot impersonate an agent, or forge or alter what passes between agent and server.

**Decided on 2026-10-29.** Three kinds of signature, together:

1. **Per session.** The agent signs a server-issued challenge at the start of every session with its own key. The server verifies the signature against the certificate it issued, and refuses a revoked or mismatched agent.
2. **Every command** is signed by the server that issues it, with that server's own CA-issued key (its SPIFFE ID, `.../server/<name>`). The agent verifies it whichever server sent it and whichever gateway carried it.
3. **Every result** is signed by the agent. **The gateway list and drain suggestions** (D9, D11) are server-signed in the same way.

Each signature is over the whole message: for a command, the plugin, action and parameters; for a result, its status and payload; for the gateway list, the list itself. Each also binds the agent id, the command or execution id, the signer's identity and an expiry. The per-session signature covers the server's challenge. How an agent learns that a server's signing key is revoked is not yet designed; wave 2 decides.

A replayed command is a duplicate to ADR-2002 WS-0's durable command idempotency only while WS-0's terminal ring still holds it (a bounded ring, `kMaxDedupRows` in `command_dedup_store.hpp`), and only while the agent's dedup store is healthy: a degraded store fails open by design (`docs/command-dedup.md`). The ring is bounded by count, not by time, and evicts in claim order, not signing order, so no fixed expiry is guaranteed to stay inside it. Wave 2 must design and test a replay bar that still holds after a row is evicted, after the store is recreated, and when the agent's clock is skewed, using only times the server signs; this ADR does not choose the mechanism. While the store is degraded, wave 2 must either refuse signed commands outside the protective set or record that residual; a protective action is never refused because the store is degraded (below). The protective set (`common/include/yuzu/protective_actions.hpp`) passes every enablement gate, but `quarantine`, `unquarantine` and `whitelist` each change a device's containment or allow-list, so a replay of any of them can loosen containment; and no `__guard__` dispatch takes the dedup claim, even with a healthy store, so its only replay bar is the expiry. Wave 2 must give these actions a replay bar that does not depend on the dedup store; only `status` needs none. **That bar may refuse `quarantine`, `unquarantine`, `whitelist` or a `__guard__` dispatch only for a proven replay, never because a store is degraded (decided by Nathan Dornbrook on 2026-10-30).** A store that is degraded, unreadable or recreated, or a check that could not complete, is never proof; what counts as proof is wave 2's design, but proof must be decidable on the agent from server-signed data alone, so that nothing an on-path gateway can block or delay is needed to establish it (otherwise a gateway could make every replay unprovable, and so executed). A protective action whose replay cannot be proven executes within its signed expiry (Accepted risks). This is the single exception to the rule that no enablement gate may refuse a protective action (see Rules this design re-opens). If the agent refuses a containment action, the server's quarantine record must not show a state the device is not in: today the server's release of a quarantine record does not depend on any agent answer (`release_device`, called from the REST release route). The expiry also bounds how long a gateway can hold a command back. Liveness heartbeats stay unsigned.

Why signed messages rather than a key agreed per session with a MAC on every message: any server may send a command straight to the gateway that holds the agent (D12), and a drained agent delivers its result through another gateway, in another session, possibly to another server (D11, D12). A signed message survives both unchanged; a per-session key would have to be shared between servers, which is a new secret store. A signed result kept in Postgres is also evidence anyone can check later from the agent's key, which a MAC is not. The survey below found the same rule elsewhere: a relay that must read, store and forward messages (TUF mirrors, Tailscale's Tailnet Lock key distribution) uses signed messages; a relay that moves opaque bytes (WireGuard through Tailscale's DERP relays, SSH through Teleport's proxy) uses a per-session key.

**What D5 deliberately does not give, stated plainly:**
- **Confidentiality from the gateway.** The gateway still reads commands and results in plaintext. Hiding them would need encryption to the agent's key, a separate decision for SaaS.
- **Honest heartbeats.** A compromised gateway can report a dead agent as alive. The lie lasts until the next signed result or the next session start.

**To measure in wave 2:** the agent's cost of signing each result, and the server's verification rate, at the result rate of the 5,000-agent rig, alongside D14's handshake budget.

### D6. Certificate lifetimes and revocation

- **Agent certificates** last 24 hours and are renewed at half-life. At 100,000 agents per gateway, renewing every 12 hours, that is about 2.3 renewals per second per gateway.
- **Expired certificates.** An agent whose certificate expired (a server outage longer than a day, or a laptop off over a weekend) cannot use the main port and must go back through the enrollment port. The agent decides that its certificate has expired from its own leaf's notAfter (against a time it can trust, see Open questions), never from a TLS alert: a gateway holding a stale CRL also refuses it, and treating that refusal as expiry would send the whole fleet to the enrollment port while the CA is stalled. Wave 2's chaos tests must show that a stale gateway CRL causes no re-enrollment. Wave 1 must decide whether a recently expired certificate may renew there on its own key, and wave 2 must measure a mass re-enrollment after an outage. Prior art for renewing on its own key: Teleport's bound-keypair joining, where a bot whose certificates lapsed signs a server challenge with its bound private key, a generation counter refuses a cloned credential, and automatic recoveries are capped.
- **Gateway and server certificates** last 7 days, on the same revocation list.
- **Revocation scope, not yet settled.** With renewal at half-life an agent holds two valid leaves for about 12 hours, so revoking one serial leaves the other valid. Today's block on re-issuing to a revoked agent (`server.cpp`) lasts until the revoked certificate's notAfter, so with 24-hour certificates it lapses within a day instead of about a year. And with CRL pruning (D7) plus renewal on an expired certificate's own key, a revoked and expired agent is on neither list. Wave 1 must state the revocation scope (every live serial of an identity) and what blocks re-issuance (the append-only revoked set and the agent DENY, never the published CRL).
- These replace today's one-year agent leaf and the server and gateway leaves sized to the CA's life.

### D7. Revocation at a gateway that keeps no state of its own

- The gateway pulls the revocation list from the server every 60 seconds and refuses revoked agents at the handshake. That stops a revoked agent before it costs a session, memory and an upstream call.
- It keeps the last good list if a pull fails, and fails closed (refuses new agent handshakes) after 15 minutes without a good pull, or sooner if the held CRL's nextUpdate passes first. A good pull returns a CRL signed within the last 15 minutes (by its thisUpdate) whose nextUpdate is still in the future: a pull that only returns the same list again, because the signer has stalled, is not one, whatever the list's nextUpdate. Fail-closed state, CRL age, their alerts and readiness all follow the same rule, so a stalled signer is seen even while pulls succeed.
- **The gateway's own hop must survive a stale list.** D1.3's revocation check on the gateway-to-server hop, combined with a stale CRL, could lock a gateway out of the server it needs for a fresh list. Wave 1 must show that a gateway with a stale list can still fetch a fresh one without skipping revocation for anything else: for example, an exemption limited to the CRL-pull call, which carries no commands, with the fetched CRL verified against the CA's signature before use, and accepted only if its CRL number is not lower than the highest the gateway has seen (and, if equal, it is the same list) and its nextUpdate is still in the future, so a replayed older CRL is refused. Restoring `ca_store` from a backup must neither lower the CRL number, or every gateway would refuse every new list, nor re-use a number for a different list; wave 1 tests a restore. The 15-minute fail-closed refuses new agent handshakes only.
- **Under several servers (D12),** the server that owns an agent's stream must learn of a revocation made on another server. How is not yet designed; wave 5 decides.
- The server ends a revoked agent's live session immediately.
- **The window a revoked agent still has, stated plainly:** up to one poll (60 s) when everything is up; about two minutes across a Postgres failover (D13's 60 s plus a poll), provided the revocation survives the failover (D13's requirement for revocation); up to 15 minutes when the gateway can reach no server, which is the fail-closed bound. The server's own check at session start (D5) closes it earlier whenever the server is reachable.
- **Two 15-minute clocks coincide:** the CRL's fail-closed bound and the gateway's CONNECTED resend, which slows after 15 minutes of refusals (`notify_unacked_slow_after_ms`). An outage of 20 to 30 minutes with revocation on must be tested.
- The list is the CRL `CaStore::publish_next_crl` already publishes (ADR-2002 section 8).
- **CRL signing becomes a 15-minute dependency, and it is decoupled from the standby (decided by Nathan Dornbrook on 2026-10-30).** A 15-minute nextUpdate (see the test below) means the server must re-sign the CRL at least every 15 minutes, so CRL freshness then depends on the CA key, the leader and a write to the primary. Today the CRL carries a 7-day nextUpdate and is re-published about every 6 days, from a leader-gated tick (`crl_publisher.cpp`, `server.cpp`). Losing a standby, or a Postgres failover, must not make gateways fail closed: CRL signing never waits for a standby to confirm, whatever durability wave 1 gives revocation and issuance (D13), and whichever profile the operator chose, strict mode (`YUZU_PG_SYNC_STRICT=true`) included. A primary that stays unreachable past the bound, with no failover, still fails gateways closed; that is the 15-minute bound working as designed. Wave 1 designs the decoupling, and its chaos tests show a CRL signed and pulled within the bound with every standby lost, and across a failover; wave 6 repeats the standby-loss test with strict mode on. Open for wave 1: a server that checks gateway certificates against a stale list would drop its gateway connections and their live sessions too; wave 1 decides whether servers check the `ca_issued` revoked set instead of the published list.
- **The CRL number never goes backwards or repeats across a failover (decided 2026-10-30).** With asynchronous replication (D13) a failover can lose the `ca_crl_versions` rows of lists already published, so the promoted primary's next number could be one a gateway already holds, or lower. Gateways keep the highest CRL number they have seen and accept no list below it, nor a different list under the same number. The signer must therefore issue, after a failover, a number above any number published before it, or every gateway would refuse every new list and fail closed, which the decoupling above forbids. Wave 1 designs how the signer gets past the lost numbers (for example, a number derived from time, or gateways reporting the highest number they hold) and tests it on a failover that loses published rows. Both examples carry a hazard wave 1 must close: a number a gateway reports is untrusted input to a fleet-wide counter (one gateway reporting the largest number RFC 5280 allows would leave no number above it, and every gateway would fail closed), so wave 1 authenticates the reporter and bounds how far one report can move the signer; a number derived from time goes backwards if the promoted primary's clock is behind, so it must stay above the last published number under clock skew, which wave 1 tests. A clock that is ahead is the worse case: one signed list with an outlier number raises every gateway's highest number, and every later list is refused. Wave 1 bounds how far one list can move a gateway's number, or gives operators an authenticated, audited way to reset it, and tests a forward clock step followed by its correction. Wave 1 also states whether a gateway's highest number survives a gateway restart: if it is held only in memory, a restarted gateway accepts any older list signed within the last 15 minutes whose nextUpdate is still in the future (the good-pull rule above); keeping it across a restart needs a writable gateway state volume, which the shipped gateway deployments do not have, and is state no server can rebuild, which conflict 5 does not yet allow (Open questions); so wave 1 tests a restart followed by a replayed older list, and either the older list is refused or the window is recorded in Accepted risks.
- **Expired entries leave the CRL (decided 2026-10-29).** The published CRL drops a revoked certificate only after it has appeared on one scheduled CRL issued after its notAfter, as RFC 5280 allows. The revoked rows in `ca_issued` stay append-only, exactly as today: only the published list shrinks, never the table. With 24-hour agent certificates the list then only holds certificates revoked in about the last day. Even 1% of 1.2 million agents revoked in one day is about 12,000 entries, roughly 0.45 MB, so no delta or Bloom-filter form is needed. A mass revocation (every agent behind a compromised gateway, a fleet-wide re-key) is handled by rotating the issuing intermediate, not by growing the list. A default install has no issuing intermediate: it signs leaves from the Yuzu root, and Yuzu never signs CA intermediates itself (`docs/pki-architecture.md`). So in a default install a mass revocation is a root rotation, unless wave 1 adds an issuing intermediate under the root. Wave 1 decides.
- **A routed-concern rule changes with it, in wave 1, not now.** The PKI row in `.claude/routed-concerns-access-control.md` says each CRL is a superset of the last. Pruning by expiry breaks that wording, though not the append-only table under it. ADR-2002 section 8 says the same (each CRL is a superset of the one before it), and wave 1 amends that sentence too. Pruning also breaks the count-based CRL freshness self-heal: `has_unpublished_revocations` (`ca_store.cpp`) compares the latest CRL's revoked count with the revoked rows, so wave 1 must re-key it to the non-expired revoked set in the same change. The wave-1 change that prunes the CRL amends the row in the same PR, with `security-guardian`.
- **To test in wave 1:** if the CRL's nextUpdate is set 15 minutes ahead, OpenSSL itself refuses a stale list, so the 15-minute fail-closed bound becomes a property of the signed CRL, the same on both TLS paths at the agent edge (the gateway's own pull is the exception above).
- **Customer intermediates (D4):** checking every level of the chain needs a CRL from the customer's root for the intermediate, which Yuzu cannot produce. Either the leaf alone is checked, or the customer supplies their root's CRL; wave 1 decides.

### D8. kTLS is the default at the agent edge; OTP `ssl` is the fallback

The reasons are the measurements above, and that nginx and HAProxy run the same design: OpenSSL's TLS state machine and X.509 code in their own process, then (where enabled) kernel record encryption. **Neither makes kTLS a default (verified 2026-10-29).** nginx offers it as an opt-in since 1.21.4 (2021), through `ssl_conf_command Options KTLS`. HAProxy offers it as an experimental option since 3.3 (2025), through `ktls on`, refused unless the configuration also sets `expose-experimental-directives`. Our default is therefore a stronger position than either, but only if the requirements below are met; they are what make it acceptable. HAProxy, like the gateway, is one multi-threaded process, so a memory-safety bug there also costs every connection; nginx isolates it to one worker.

**TLS version.** TLS 1.2 sends the client certificate in the clear, so on an internet-facing gateway a passive observer reads every agent's SPIFFE ID. That argues for TLS 1.3 on the main port. A TLS 1.3 peer can send KeyUpdate to change keys mid-connection. Under kTLS the kernel must install the new receive key, and only newer kernels can (the rekey support is documented for Linux 6.14). Rocky 9's 5.14 cannot: there a KeyUpdate ends the connection (item K2 of BigColin's review, 2026-10; no Yuzu agent stack was seen to send one). If wave 2 chooses TLS 1.3 it needs two things:
- **A KeyUpdate policy:** refuse it and close the connection, or require a kernel with rekey support on gateway hosts, or keep the receive side in user space.
- **A KeyUpdate rate limit** whatever the policy, because each KeyUpdate costs CPU. HAProxy added one (100 per second per connection by default) to stop a KeyUpdate flood; the lesson applies with or without kTLS.

Because memory safety is vital, these are requirements, not options:
- a pinned OpenSSL version, with its security advisories tracked and acted on;
- continuous fuzzing of our C code in CI, plus an ASan build exercised by the test suite. These apply to gateway C from the trim NIF onward, not from wave 2. CI compiles the trim NIF and eunit loads it, but no CI job fuzzes gateway C or builds it with ASan today (the NIF's build script ignores sanitizer flags). Wave 0 adds an ASan run for the trim NIF, which takes no input and so has nothing to fuzz; continuous fuzzing starts with the kTLS NIF in wave 2;
- one shared test suite proving the kTLS and OTP `ssl` paths accept and refuse exactly the same certificates (chain, SAN, EKU, expiry, revocation);
- security review of the C code before it ships enabled.

The difference from nginx is recorded: nginx runs handshakes in worker processes, so a crash costs one worker. Our handshake runs inside the Erlang VM, so a crash costs the gateway. Whether to move handshakes out of the VM later is an open item (see Open questions).

**Where the agent-certificate checks run (decided by Nathan on 2026-10-28):**
- **In C:** OpenSSL checks the chain and the revocation list during the handshake. The NIF sets `SSL_VERIFY_PEER` with fail-if-no-peer-certificate, the CA store (Yuzu root or customer intermediate) and the CRL. A bad chain or a revoked certificate is refused before the handshake completes. Our C stays small: configuring OpenSSL and handing the verified peer certificate to Erlang.
- **In Erlang:** the gateway checks the SPIFFE identity and the EKU of the verified certificate just after the handshake, before any gRPC request is served. Identity rules will change as SPIFFE and customer intermediates arrive, so they live where they are easy to change and test.
- **The same split on the fallback path:** OTP `ssl` checks chain and CRL, and the same Erlang identity check runs. The shared accept/refuse suite covers both.

The kTLS branch (`perf/gateway-idle-mem-ktls`, not on `dev`) currently refuses `ktls` together with `verify_peer`; that refusal goes away.

### D9. Discovery and choosing a gateway

- **"Use DNS" is a design principle.** An agent finds its first gateway by DNS.
- **After first contact,** the server gives the agent the current gateway list, with weights and draining state. The agent caches it on disk for the next start.
- **Choosing:** weighted random choice, with the weight from measured round-trip time, so the nearest gateway in time weighs most and agents do not all pile onto one. Jittered back-off between attempts. Failover down the list.
- **Draining gateways** have weight zero.
- No region or site field in the first version: latency weighting covers it. The weight function stays pluggable, because round-trip time does not see a LAN boundary (a per-campus site gateway, for example).
- **When every cached entry fails** (all drained or dead), the agent goes back to DNS. The cached list carries an expiry; to be set in wave 4, preferably per entry by the server, as Teleport's proxies do.
- **Any gateway list that reaches the agent through a gateway is signed by the server** (D5), and the agent refuses one that is not. Otherwise a compromised gateway could steer agents to endpoints of its choosing. Those could not impersonate the server, but they could hold agents captive.

### D10. How gateways know about one another

- **Inside a corporate network:** gateways may form an Erlang cluster (the existing `yuzu_gw_cluster_discovery` and per-agent `pg` lookup; there is no hash ring, #4556). The cluster's own connections run over TLS (`inet_tls_dist`) with CA-issued certificates. Membership in an Erlang cluster is full control of every member. D1.2's role check applies: distribution admits only gateway identities carrying the cluster's id, with chain and CRL checked. Under D3 agent leaves carry both `serverAuth` and `clientAuth` and chain to the same CA, so a chain-only check would admit an agent leaf to the cluster.
- **New in wave 4:** TLS distribution with CA-issued certificates (today distribution is plaintext, and the cookie is its only authentication); distribution off by default on an internet-facing gateway (today cluster formation is tried by default everywhere); and a `cluster_id` mismatch check at join, which guards against misconfiguration only, because admission is the distribution certificate.
- **Outside, including every internet-facing gateway:** gateways never talk to each other. They coordinate only through the server. Erlang clustering is off by default for an internet-facing gateway.
- **Either way,** every gateway reports health, load and draining state to the server, because the server owns the gateway list agents receive (D9).

### D11. Draining a gateway

1. **The order:** an operator issues it through the dashboard, REST API or MCP, RBAC-gated and audited, reaching the gateway through the server (or through the cluster). Automation uses the same API.
2. **What agents receive (decided 2026-10-29):** the gateway sets its weight to zero. Each agent first receives, on its own stream, a short suggested list of other gateways signed by the server (D5). Then the gateway sends an HTTP/2 GOAWAY in two phases: a first one that stops new streams, and a final one after a jittered delay. The GOAWAY carries nothing in its debug data: RFC 9113 says that data is for diagnostics only, and the agent's gRPC stack does not hand it to the application. The agent reconnects by its normal weighted choice. Cowboy already sends a two-phase GOAWAY when a listener shuts down; the per-connection trigger, the batches and the jitter are new.
3. **Pace:** the two-phase GOAWAY goes out in staggered, jittered batches over an operator-set window, 10 minutes by default, so no other gateway takes a storm. The gateway exits when empty or at a hard deadline.
4. **Commands in flight:** the agent reconnects elsewhere and delivers the result there. The server must accept a result for a command it sent through a different gateway. The durable command idempotency of ADR-2002 WS-0 and the execution ids carry it. **This is new code on both sides.** Today a gateway drops a response for a command it did not dispatch (the orphaned-response path in `yuzu_gw_agent`); it must forward it upstream instead. And nothing re-drives an operator command whose result was lost on the drained stream (the command outbox covers scheduled runs only), so wave 4 builds the re-drive, with WS-0 replaying the stored outcome.
5. **The enrollment port** stops accepting new connections at the start of the drain window.

### D12. Several servers

1. **All servers active.** Singleton jobs run on the elected leader of ADR-2002 sections 3 and 6.
2. **Each gateway connects to every server** (ADR-2002 section 7g). Each agent's stream goes to one server, chosen by consistent hashing on `agent_id`. When a server is lost or drained, only its agents move.
3. **Reaching an agent:** Postgres records which gateway holds which agent (`agent_routes`). Any server sends a command straight to that gateway's management port. **This is new server code.** As of `origin/dev@fbd8b5409`, `AgentRegistry::send_to` (`server/core/src/agent_registry.cpp`) returns false for an agent not in that server's own memory, so a dispatch handled by a server that does not own the agent reaches nobody. With N gateways each connected to M servers, the upstream permit model (#6057) must also be re-derived. The result returns through the server that owns the agent's stream and lands in Postgres. The gateway part is new too: today a result returns on the dispatching server's SendCommand stream.
4. **Gateways find servers by DNS.**
5. **Draining a server:** it stops taking new agent streams, and its agents are rehashed onto the others in staggered batches.

### D13. Postgres

- **Replication: asynchronous by default (decided by Nathan Dornbrook on 2026-10-30; conflict 8).** An earlier draft of this decision required one synchronous standby that never degrades to the primary alone; that rule is dropped. Many enterprise data-centre pairs are more than 2 ms apart, and a commit that waits for a standby in the other data centre on every write is too slow there. No commit waits for a standby by default. ADR-2002 section 11's synchronous profiles stay available as an operator's choice. The shipped Patroni profile is unchanged until wave 6 changes its default (conflict 8).
- **RPO zero for acknowledged writes is no longer a target.** A failover can lose every write the old primary acknowledged but had not yet sent to the standby that is promoted. How much is lost depends on replication lag at the moment of failure; wave 6 measures it, and this ADR sets no bound on it. A failover tool may cap it: the shipped Patroni rig refuses to promote a standby more than 1 MiB behind (`maximum_lag_on_failover`, `patroni-entrypoint.sh`), which bounds the loss but can leave no standby to promote, so write downtime then has no bound. Wave 6 sets that cap deliberately, as the trade between the loss and the 60-second target, and tests a failover in which every standby lags past it.
- **What a failover can lose, and what each store must meet.** For each store below, the named wave must design how its loss is prevented or made harmless, and prove it on a failover that loses acknowledged writes. These are requirements; the mechanisms are not decided.
  - **Revocation** (the revoked rows of `ca_issued`). Lost means a revoked certificate becomes valid again. Requirement (wave 1): a revocation the server has acknowledged, or that any published CRL has carried, survives a failover, and no CRL is signed that omits an unexpired revocation an earlier published CRL carried. Gateways run no superset check of their own, so a later list that drops such a revocation would make the certificate valid again. Wave 1 may meet this by making the revocation write wait for a standby (not the CRL re-signing, which never waits, D7), or by recovering published revocations from somewhere other than the primary; either way it states what a revoke does while every standby is lost.
  - **Issuance** (the issued rows of `ca_issued`). Lost means a certificate is in use that the database does not know, so it cannot be revoked by serial. Requirement (wave 1): every issued certificate can still be revoked after a failover.
  - **CRL number** (`ca_crl_versions`). Lost means a number is re-used or goes backwards, so gateways refuse the next list, or a gateway that has restarted or is new accepts a stale one. Requirement (wave 1): neither happens (D7).
  - **Audit rows.** Lost means a gap in the audit evidence. Requirement (wave 6, with `compliance-officer`): state whether an acknowledged audit row must survive a failover, and how.
  - **Access revocations and containment** (operator sessions and logouts, API token revocation, SCIM, OIDC and SAML deprovision, user deactivation, RBAC unassignment, and `QuarantineStore` records and allow-lists). Lost means a revoked session or token, or a deprovisioned operator, works again; or a contained device is treated as dispatchable, or an older allow-list is pushed again by the stored-containment re-dispatch. Requirement (wave 6): an acknowledged revocation or quarantine change survives a failover, or its loss fails closed. This one may not be recorded as accepted.
  - **Agent routes.** Lost means a stale route. Requirement (wave 6): routes are rebuilt from live connections (the reconcile, #5649) as agents reconnect, and a lost route row never leaves an agent unreachable once it has reconnected.
  - **Command outbox and dispatch.** Lost means a command is driven again or not at all. Requirement (wave 6): a command whose dispatch row is lost is shown to the operator as not done, never as done; a command driven again is a duplicate to the agent only within WS-0's ring and while its store is healthy (D5), so the re-drive must stay within that.
  - **Leader epoch** (`leader_epoch_seq` and `leader_state` in the `leader_elector` schema). Lost means an epoch is issued twice, so a new leader and a paused former leader both pass the epoch fence and a fenced claim can be made twice (ADR-2002 section 6). Requirement (wave 6): no epoch is ever issued twice across a failover. This one may not be recorded as accepted.
  - **RBAC write generation** (`rbac_meta.write_generation` in the `rbac_store` schema). Lost means the generation goes backwards, and a server that saw the lost value ignores later grant changes, so it serves a revoked grant while every refresh succeeds. Requirement (wave 6): no server ignores a grant change made after a failover. This one may not be recorded as accepted.
  - **Event outbox** (`event_outbox`, and its role as the schedule runner's spent-ticket record). Lost means a server polling forward from its last-seen position skips new events with no visible gap (the poller's position is a transaction-id horizon the promoted primary can issue again), an event id names two events, or a spent approval ticket can be spent again. Requirement (wave 6): no event is skipped and no event id names two events across a failover, and a lost spent-ticket row never lets an approval run twice. This one may not be recorded as accepted.
  - **Execute-once claims** (`DeploymentRunStore`'s `claim_for_exec`, and the policy remediation claim). Lost means a mutating step runs twice: a reclaimed deployment step is sent under a new command id, which WS-0's dedup does not absorb. Requirement (wave 6): a lost claim never causes a second execution of a mutating step. This one may not be recorded as accepted.
  - **Every other store.** Requirement (wave 6): list what a failover can lose there, and either close it or record it as accepted.
- **The leading candidate for revocation, issuance and possibly audit, not a decision:** per-transaction synchronous commit, where only those transactions wait for a standby (Postgres `SET LOCAL synchronous_commit`) and every other write stays asynchronous. These writes are rare, so the extra round trip costs little. It works only where a standby is named as synchronous: on the shipped `async` profile (`synchronous_mode: false`, so `synchronous_standby_names` is empty) the setting waits for the local flush only, and gives no durability. If it is chosen, "asynchronous by default" is delivered as Patroni's synchronous mode (which also limits promotion to the synchronous set) with a cluster-wide `synchronous_commit = local`, not as the `async` profile. Choosing it means wave 1 must also state what such a transaction does while no standby is reachable (wait, which holds up revocation, or proceed, which re-opens the loss; Patroni without strict mode clears the synchronous standby list when every standby is lost, so a wait silently becomes proceed). A synchronous wait that is cancelled leaves the transaction committed locally but not replicated, so wave 1 must not publish a revocation in that state. CRL signing must not wait on a standby either way (D7).
- **Failover:** Yuzu depends on no particular HA tool. It reaches Postgres by one DNS name, or a multi-host DSN, with `target_session_attrs=read-write`. Patroni is the documented on-premises reference; a managed service is the SaaS choice. Whatever HA tool is used must not break the per-store requirements above.
- **Targets:** write downtime under 60 seconds per failover. This is a target, unmeasured until wave 6. While Postgres is unreachable, servers fail closed for writes. **That is not true of every store today:** `ResponseStore` logs a failed store under pool pressure and drops the response (BigColin's test run RR7, 2026-10-28, at 5,000 agents: one of seven runs lost 1,989 of 4,941 responses with the default pool of 16). A synchronous standby, where an operator chooses one, lengthens every commit and makes that likelier. This decision therefore includes a concrete change: bounded retry, or an explicit error, for response storage, and a pool size measured with the default asynchronous replication and with a synchronous standby.
- **Reads:** no reads from standbys in the first version.
- **Leadership** is re-elected after every failover, and every singleton job must tolerate that.
- **Several servers need more than this ADR.** Multi-server operation (D12, wave 5) also requires ADR-2002's safe-to-scale gate (`docs/ha-delivery-matrix.md`, including #6528 and #6535). Wave 5's rig does not lift it.

### D14. The gateway budget

This replaces the 8 KiB-per-connection goal set on 2026-10-26.

These are targets, not yet evidence. On merged `dev` the gateway holds about 320 to 470 KB per agent at 5,000 agents (Nathan's 5,000-agent suite; BigColin RR7, RSS). The 48.1 KB above is the kTLS branch at 100 agents with one-way TLS. Wave 0 measures a common baseline at 5,000 and 10,000 agents, with one method (OS anonymous memory plus kernel, after settling, TLS on), on merged `dev` and on the kTLS branch, before the CI check becomes a gate.

- **Goal, per box:** one gateway on 8 cores and 16 GB holds 100,000 idle agents with mutual TLS. It must stay inside:
  - memory under 8 GB;
  - idle CPU under 2 cores;
  - a full reconnect of all 100,000 agents within 60 seconds (about 1,700 handshakes per second, plus the D5 signature checks). RR7 registered about 290 agents per second against the about 1,700 needed; the likely bottleneck is the server's Register path (and the D5 verification, whose CPU cost is not yet budgeted), not the handshake;
  - memory back within 5% of its pre-storm level within 2 minutes.
- **CI regression check, per agent:** 64 KiB per idle agent, all-in including the kernel's per-connection memory. The check is measured with the ADR-0073 heartbeat (liveness only, no fleet snapshot), so until ADR-0073 lands it does not measure the heartbeat that ships.

The memory measures in this ADR's companion change (on `dev` since commit 857ac374e) are: a garbage collection of the large processes after an agent-count drop, plus a second pass 30 seconds later; and a periodic `malloc_trim(0)` through a small NIF. The periodic trim runs every 5 minutes by default (`trim_interval_ms`; 0 turns it off). Only the trim after an agent-count drop was measured; the periodic trim was not. The trim acts on glibc only, and does nothing on the default musl image. `+MMmcs 0` and `MALLOC_ARENA_MAX=2` are not in it: they are deferred to the hibernation work, because they gave no measurable memory gain and had a measured idle-CPU cost.

`malloc_trim` is a glibc feature. It acts on the chiselled Ubuntu image (`Dockerfile.gateway.chisel`), where it was measured. The default image (`Dockerfile.gateway`) is Alpine with musl, and musl has no `malloc_trim`. musl's allocator returns freed memory differently, and that is not yet measured. The glibc builders (the chisel builder, CI, and the Meson-driven gateway build on Linux) already compile the trim NIF (`gateway/apps/yuzu_gw/rebar.config`, `c_src/build_mem_trim_nif.sh`). Only the Alpine builder in `Dockerfile.gateway` has no C toolchain; the kTLS NIF must add one there (`build-base`, `openssl-dev`, `linux-headers`), and its rebar pre_hook must match musl targets too, because the trim NIF's `-linux-gnu-` filter skips Alpine. Both NIFs are Linux-only: Windows and macOS gateway builds skip them. kTLS itself does not need glibc. Checked on 2026-10-28: the NIF builds without warnings against musl in `erlang:28-alpine` (with `openssl-dev` and `linux-headers`) and loads in the BEAM there. What kTLS needs is the host kernel's `tls` module, because a container shares the host's kernel and cannot load modules itself.

### Rules this design re-opens

Several standing rules, and one earlier ADR, say the opposite of a decision above. Until the named wave amends each one, with `security-guardian`, the current rule stands and code must follow it.

- **No `auth_fun` on the `:50051` agent listener** (the PKI row of `.claude/routed-concerns-access-control.md`; D2). It is also enforced in code: the gateway refuses to boot with `auth_fun_on_agent_listener` (`yuzu_grpc_listener.erl`), and the manual's stage 3 in `docs/user-manual/gateway.md` ("Moving the agent edge to mutual TLS") says the same. The enrollment port also needs a per-listener method allow-list, which the layer does not have: new code. **Wave 2.**
- **Each CRL is a superset of the last** (the PKI row; D7). **Wave 1.**
- **The protective set passes every enablement gate, a degraded store included** (clause (3) of the quarantine row in `.claude/routed-concerns.md`; D5). A replay bar that can refuse `quarantine`, `unquarantine`, `whitelist` or a `__guard__` dispatch narrows it. Decided on 2026-10-30: the narrowing is allowed only for a proven replay, never because a store is degraded, and it is the single exception to the rule (D5). The row's clause (3) is amended to say so in wave 2, with `security-guardian`. **Wave 2.**
- **The leader epoch only ever increases** (clause (1) of the fenced leader election row in `.claude/routed-concerns-access-control.md`; D13): asynchronous replication can lose an epoch advance in a failover, so the fence holds only once wave 6 meets D13's requirement for the leader epoch. **Wave 6.**
- **Command dedup retention is a clock-free ring** (the durable command idempotency row; `docs/command-dedup.md`; D5), if wave 2's replay bar adds time to ring retention. **Wave 2.**
- **The gateway-upstream peer row,** clause (2) (CA membership never substitutes for the pin) and clause (3) (pins fixed at boot, no revocation read, and re-opening them means re-opening `docs/security-reviews/gateway-peer-authz-minimal-2026-10-07.md`). Also clause (4): `gateway_peer_resolution.*` refuses to boot with operator certificates and no pin, or with zero loadable pins, and D1's CA trust without pins is exactly that configuration. D1 re-opens all three. **Wave 1.**
- **The mgmt-plane peer row and ADR-2004:** clause (2), one byte-exact identity `yuzu://<install>/server`, against D3's window that accepts both forms and its per-instance `.../server/<name>`; clause (3), an unset `mgmt_peer_auth_mode` is always `pin`, against D1's optional pins; clause (4), `identity_over_ca_bundle` refuses a CA file that is not exactly one certificate (unless the mode is `identity` and a pin is configured), which a customer intermediate plus its root (D4) is; and the identity derived from the CA fingerprint, against D3's UUID trust domain. **Wave 1.**
- **Alternatives ADR-2004 rejected and this ADR takes up:** short-lived server certificates (rejected there because the server never renews its leaf and client credentials have no hot reload), and CRL checks at the handshake only on the long-lived management connection. So wave 1 must add credential hot reload on server and gateway, and the teardown of a live connection whose peer certificate is revoked.

## Conflicts this ADR creates, to resolve in wave 0

1. **Cluster affinity against free gateway choice. Decided on 2026-10-29: affinity is dropped.** #4669 made an agent's home cluster sticky (`agent_routes.home_cluster_id`), so another cluster cannot claim and answer for it. D9 and D11 move agents between gateways freely, possibly across clusters. From wave 4 the choice of gateway is free, and affinity is no longer an admission rule, nor kept as a preference.
   - **The risk this carries, stated plainly:** until D5 lands in wave 2, a compromised gateway that holds a valid gateway certificate can claim any agent's route. D5's per-session signature and signed commands and results close it only if the route write (`agent_routes`, written today on the gateway's CONNECTED notification and asserted by the gateway) changes only after the server has verified that session's agent signature. Wave 2 makes it so. D5 does not stop a gateway that holds the agent from reading command payloads (a D5 non-goal).
   - **The #4669 admission check is removed no later than wave 4.** Whether it goes earlier, before D5 lands in wave 2 (while the route-claim risk is open), is for the owner at sign-off.
2. **D5's scope. Decided on 2026-10-29:** signed commands, signed results and a signed gateway list, on top of the per-session signature (see D5).
3. **#5649. Still open: a proof obligation for wave 5.** D12 point 2 chooses stickiness on the gateway side (one owning server per agent). Wave 5 must show the reconcile correct when that owner changes (server loss or drain).
4. **ADR-0073's budget text. Done:** ADR-0073 is in PR #6704 and was revised there to cite D14 instead of the 8 KiB goal, and to re-cite the gateway after the merge of PR #5695.
5. **"The gateway adds no state." Decided on 2026-10-29:** both this ADR and ADR-0073 say instead that the gateway keeps **no per-agent state beyond the connection**. Fleet-level state that any gateway could rebuild is allowed: the cached CRL, the drain flag, the cached gateway list, and cluster membership. ADR-0073's part is done: PR #6704 uses this wording. Today's gateway already keeps two kinds of per-agent state beyond the connection: per-agent `pg` groups across cluster members, and the DISCONNECTED resend window after a connection ends. Wave 4 keeps each as rebuildable state or changes it.
6. **Erlang clusters and the server's `cluster_id`. Decided on 2026-10-29: one Erlang cluster is one `cluster_id`.** The server already routes by a `cluster_id` per gateway session (ADR-2002 WS-4 4.3). Every member of a cluster (D10) is configured with the same id. Wave 4 adds a mismatch check at join, which guards against misconfiguration only: admission is the distribution certificate.
7. **The design target.** ADR-0069 records 100,000 agents per gateway. Dave has been steering to a solid 5,000 per gateway now, nothing that blocks 50,000 and beyond, and 500,000 as the long-term horizon. **Decided by Nathan on 2026-10-28** (Dave to see): waves 1 to 5 must pass at 5,000 agents on both rigs, with nothing that blocks 50,000; wave 6 tests failover under a 5,000-agent load; wave 7 is the 100,000-agent per-box budget (D14); 500,000 stays the long-term horizon, outside this programme.
8. **D13 against ADR-2002 section 11. Decided by Nathan Dornbrook on 2026-10-30: asynchronous replication is the default, and D13's one synchronous standby that never degrades is dropped.** Section 11 specified one primary plus two synchronous standbys (`ANY 1`), failing closed when both are lost. WS-7 measured that this strict mode blocks writes for minutes after a single failover, so the shipped Patroni default is the `quorum3` profile without strict mode (`YUZU_PG_DURABILITY` defaults to `quorum3` and `YUZU_PG_SYNC_STRICT` to false in `deploy/docker/ha-postgres/patroni-entrypoint.sh`): non-strict synchronous replication, where every commit waits for one standby while any standby is up and replication degrades to asynchronous only when every standby is lost. The decided default is asynchronous: no commit waits for a standby. The reason: many enterprise data-centre pairs are more than 2 ms apart, too far for a standby wait on every commit. RPO zero for acknowledged writes is no longer a target; what a failover can lose is accepted (Accepted risks), and each store's loss must meet the requirement D13 sets for it in wave 1 or wave 6. ADR-2002 sections 11 and 13 carry a dated update to match. Wave 6 changes the shipped profile's default on the existing Patroni rig (`deploy/docker/docker-compose.ha-postgres.yml`), not a new one; until then the shipped default is unchanged.

## Audit and evidence

The waves add audit records or metrics for: certificate issuance, renewal and revocation; CRL publication and gateway pulls; handshake refusals by reason; entry into and exit from fail-closed; enrollment by machine certificate; D5 signature refusals; the drain lifecycle (order, abort, completion); and changes to the gateway list the server signs. Each wave must add the audit verbs, metrics and alerts it introduces to its Done-when before it closes; the cells below do not list them yet. Measured: the Register rate with mutual TLS and the per-session signature, and a mass re-enrollment after a simulated outage. | The shared suite passes on both TLS paths; 100 real Windows agents (rig100) enroll and connect with mutual TLS. Chaos: a mass re-enrollment under a flood on the enrollment port; a replayed signed command; a revoked agent refused within 60 s, within about 2 minutes across a Postgres failover (on the existing Patroni rig), and within 15 minutes with no server reachable; a revoked agent whose connection stayed up through a partition is cut off within one poll of the heal; a gateway's CONNECTED notification for an agent without a verified session signature changes no route; a certificate-less client is refused on the main port; a bad session signature, an unsigned or tampered command and a result with a bad agent signature are each refused. |
| 3 | The server, before agents move: an agent seen on two gateways at once must not lose its route (RR7: about 50 of 5,000 lost in 8 of 8 forced-move runs); response storage must not drop under pool pressure; the in-memory registry must not lag the Postgres routes after a restart. Accepted by Nathan on 2026-10-28 from the BigColin review. | The RR7 forced-move, pool-pressure and post-restart cells pass with no loss, on BigColin's rig and ours. |
| 4 | Topology: DNS discovery; the server-pushed gateway list, server-signed, and the server-signed drain suggestion (D5); latency weighting; gateway drain (GOAWAY batches, enrollment port closed at the start); Erlang clustering on or off by deployment, over TLS distribution with CA-issued certificates, with a `cluster_id` mismatch check at join (misconfiguration only); forwarding results for commands another gateway dispatched, and the re-drive of an operator command whose result was lost (D11). | A drain moves every agent to other gateways within the window, with no lost command result. An agent refuses an unsigned or wrongly signed gateway list; a node with a different `cluster_id`, or without a CA-issued certificate, cannot join. Chaos: through a drained or killed gateway, each result is stored once per execution id, and no command runs twice while WS-0's ring holds it and its store is healthy. |
| 5 | Several servers: consistent hashing of agents to servers; the agent-to-gateway table; results through a different gateway; server drain; the ADR-2002 leader election wired in. | Two or more servers serve one fleet; one is killed and one is drained without losing an acknowledged result. Chaos: through a drained or killed server, each result is stored once per execution id, and no command runs twice while WS-0's ring holds it and its store is healthy. |
| 6 | Postgres: on the existing Patroni rig (`deploy/docker/docker-compose.ha-postgres.yml`), make asynchronous replication the shipped default (conflict 8); the D13 requirements for audit, agent routes, access revocations and containment, the RBAC write generation, the event outbox, execute-once claims, the command outbox and every other store; failover tests. | Failover takes under 60 seconds of write downtime, under load, and the loss window is measured. The default changes in both `patroni-entrypoint.sh` and `docker-compose.ha-postgres.yml`; `docs/user-manual/ha-postgres.md` and `docs/user-manual/upgrading.md` say that an existing cluster keeps the profile it was created with until changed with `patronictl edit-config`, and that a new install wanting a synchronous standby must set `YUZU_PG_DURABILITY` itself; a `changelog.d/` fragment records the change. Each D13 requirement for this wave is proven on a failover that loses acknowledged writes. Chaos: every standby is lost for more than 15 minutes, and writes and gateways carry on (D7); a failover promotes a standby that is behind the primary, and no revoked certificate becomes valid again, no issued certificate becomes unrevocable, no CRL number is re-used or goes backwards, no leader epoch is issued twice, no RBAC grant change is ignored, no event is skipped, and no mutating step runs twice. |
| 7 | The 100,000-agent run: the gateway on an 8-core, 16 GB allocation, load from Ngai-Syoon and the other test machines. | The D14 budget is met, or the gap is measured and explained. |

## Obligations the waves carry

Each line is something the named wave must state, decide or test. None is decided here.

**Wave 0**
- A committed script defines the D14 measurement method.

**Wave 1**
- The renewal port and the credential a renewal presents.
- Renewal of gateway and server leaves, with credential hot reload on both.
- Renewal jitter, so renewals do not bunch.
- What an agent whose certificate lapsed, and that has no machine certificate, uses to return.
- The clock-skew tolerance on every certificate and CRL check.
- How the trust-domain UUID is stored, backed up, and shared between servers.
- How a gateway's CRL pull is authenticated.
- The enterprise prerequisites for importing a customer intermediate.

**Wave 2**
- The enrollment sequence: the CSR; which trust anchors admit a machine certificate; the challenge, single-use and with an expiry; and how an unenrolled agent trusts the gateway.
- How agents find an open enrollment port.
- The gateway closes an agent's connection when the server ends a revoked session.
- `forwarded_for` cannot work on a strict main port, and PROXY protocol must be parsed before the kTLS handshake.
- The privacy classification of `agent_id`, as an input to the TLS version choice (D8).
- The signed-result evidence window. As designed, a signed result can be checked only while both the response (kept 90 days by default) and the signing certificate's `ca_issued` record are kept; whether evidence must outlive that is open.
- How agents already running behind a gateway get the wave-2 agent binary, and who confirms the pilot check before wave 2 merges. The wave 2 PR description records who confirmed it, on its merge date.

**Wave 4**
- Refusing to drain the last gateway.
- What aborting or extending a drain does to agents already moved.
- Operator surfaces for gateway drain and server drain: REST and MCP, with a dashboard twin, a securable, a step-up row and audit, plus read access to the gateway list (ADR-1005).

**Wave 5**
- The source of ring membership and its hysteresis.
- Re-attestation when an agent's owning server changes.

**Observability and readiness (waves 1 to 5, each for what it adds)**
- Metrics for CRL age, fail-closed state, refusals by reason, CA signing rate, enrollment-port saturation, certificate-expiry horizons, drain progress and ring membership. A gateway or server certificate renewal that keeps failing pages, as does a gateway or server certificate with less than a quarter of its lifetime left; the expiry horizons themselves, and agent certificate expiry, are a dashboard. These replace the existing day-band rules for gateway and server certificates (`YuzuCertificateExpir*`, `YuzuGatewayCertificateExpir*`, warning from 30 days), which would fire without end on a 7-day certificate. Each page names the responder's action.
- Alerts from wave 1: entry into fail-closed pages, and so does a gateway CRL nearing the 15-minute fail-closed bound, because someone must restore the gateway's path to a server or the CRL signer. A condition seen on many gateways at once (a stalled signer) pages once for the fleet, not once per gateway.
- Readiness: a fail-closed or draining gateway is not ready for new agents but stays live. Until wave 4 decides whether a fail-closed gateway gets weight zero, readiness is the only steer: a load balancer stops sending agents to it, but a gateway found by DNS still draws agents, which are refused and retry.

## Survey of comparable projects (2026-10-29)

Wave 0 compared this design with open-source systems that answer the same questions. Only public, open-source sources are cited here; findings about commercial endpoint platforms were gathered too, and inform the decisions, but are not named. Versions as seen on 2026-10-29.

| Question | What the projects do | What it means here |
|---|---|---|
| Identity format and trust domain (D3) | [SPIFFE](https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE-ID.md): the operator chooses the trust domain; an automatically generated one should be random, such as a UUID. [X.509 SVIDs](https://github.com/spiffe/spiffe/blob/main/standards/X509-SVID.md) carry exactly one URI SAN, and a leaf's EKU, when present, lists both `serverAuth` and `clientAuth`. [Envoy's SPIFFE validator](https://github.com/envoyproxy/envoy/blob/main/api/envoy/extensions/transport_sockets/tls/v3/tls_spiffe_validator_config.proto) picks the trust bundle by the presented trust domain. | A random install UUID; one SAN, so the `yuzu://` migration accepts both forms for a window; role from the path, not the EKU. |
| Bootstrap with an existing machine certificate (D2, D4) | [SPIRE](https://github.com/spiffe/spire/blob/main/doc/plugin_server_nodeattestor_x509pop.md)'s `x509pop` node attestor checks that a pre-provisioned certificate chains to a trusted CA and issues a signature challenge for proof of possession; `tpm_devid` does the same for a TPM. None of the projects found puts certificate-less bootstrap on its own port; nginx's equivalent of today's single port is `ssl_verify_client optional`. | D4 has direct prior art. Bound keypair is the model for a recently expired renewal. |

## Alternatives considered

- **One port that asks for a certificate but does not require one, at the agent edge.** This is what direct agent-to-server connections use. Rejected: every request needs a "did this connection present a certificate?" check, and one missed check is a hole. A separate port gives a guarantee the TLS layer enforces.
- **The customer's machine certificate on the main port.** Rejected for now. It ties certificate lifetimes, naming and revocation to the customer's PKI, needs a second path for customers without one, and runs into gRPC's PEM-only client key.
- **The gateway vouches for the agent, and the server trusts it.** Rejected: an internet-facing gateway that is compromised could impersonate every agent behind it.
- **Gateway-held per-agent state, or a gateway mesh across the internet.** Rejected: membership in an Erlang cluster is full control of every member, and per-agent state at the gateway breaks free gateway choice. Fleet-level state any gateway could rebuild is allowed (conflict 5).
- **A per-session key between agent and server, with a MAC on every message, for D5.** Rejected: it does not survive a command sent by another server or a result redelivered through another gateway, and it proves nothing to a third party (D5).
- **The suggested-gateway list inside the GOAWAY frame, for D11.** Rejected: GOAWAY debug data carries no meaning by RFC 9113, and the agent's gRPC stack does not expose it.
- **OTP `ssl` as the default.** Rejected by the owner, on the measured memory and handshake rate. It is kept as the fallback and as the reference the shared test suite compares against.

## Consequences

- The release that ships wave 2 breaks every existing agent-to-gateway deployment: new port, new certificates, agents re-enroll. This is acceptable only because there are no production customers at the time of writing (2026-10-30); wave 2 re-checks this before it merges, and if a pilot runs agents through a gateway the upgrade note becomes a merge gate.
- Wave 2 ships with an upgrade section in `docs/user-manual/upgrading.md` (the new enrollment port and its firewall rule; the upgrade order server, then gateway, then agents; re-enrollment and its prerequisites; roll-forward), a changelog fragment marked Breaking, and an update to `docs/user-manual/gateway.md`'s "Moving the agent edge to mutual TLS".
- The CA signs far more often: each agent renews every 12 hours instead of about every eight months. At 1.2 million agents that is about 28 signatures per second, around the clock, before any mass re-enrollment. Its signing path, its `ca_issued` table and its CRL size must be measured before wave 2, not after.
- The gateway gains C code that faces the internet. The fuzzing, ASan and advisory-tracking requirements in D8 are permanent.
- `docs/pki-architecture.md`, `docs/user-manual/gateway.md`, the reference composes and other compose files, the compose wizard, the agent and gateway installers, the gateway `sys.config` files and the environment examples all change with waves 1, 2, 4, 5 and 6.

## Open questions

Resolved in wave 0 (2026-10-29): the SPIFFE trust domain (D3), D5's scope, and whether the CRL needs a delta or Bloom-filtered form (it does not with 24-hour leaves; D7). Resolved on 2026-10-30: replication is asynchronous by default (D13, conflict 8), CRL signing is decoupled from the standby (D7), and the replay bar may refuse a protective action only for a proven replay (D5).

- **For wave 2:** whether to move kTLS handshakes out of the Erlang VM, so a memory-safety bug costs only the handshakes in flight rather than the gateway. No project surveyed runs a process per handshake; the form to measure is a small pool of handshake OS processes that hand the established socket and its kTLS state back to the gateway.
- **For wave 1:** checking a customer intermediate's revocation: the leaf only, or the customer's root CRL as well (D7).
- **For wave 2:** the TLS version on the main port and, if TLS 1.3, the KeyUpdate policy (D8).
- The ephemeral-port limit on load generators for wave 7: one source address to one gateway port gives about 16,000 connections on macOS defaults.
- **For wave 2:** whether the direct agent-to-server port of single-server installs gets the same enrollment and main port split (D2).
- **For wave 1:** whether a default install gains an issuing intermediate under the Yuzu root, so a mass revocation is not a root rotation (D7).
- **For wave 1:** whether servers check gateway certificates against the `ca_issued` revoked set rather than the published CRL (D7).
- **For wave 1:** whether a recently expired agent certificate may renew at the enrollment port on its own key (D6).
- **No wave named yet:** the wave in which verifiers stop accepting `yuzu://` URIs (D3).
- **For wave 1:** whether automated CRL re-signing and certificate renewal fail closed on audit failure (Audit and evidence).
- **For wave 2:** how an agent whose clock is far off learns that its own certificate has expired, since it ignores TLS alerts for that decision (D6).
- **For wave 2:** how an agent learns that a server's signing key is revoked (D5).
- **For wave 5:** how the server that owns an agent's stream learns of a revocation made on another server (D7, D12).
- **For sign-off:** whether a gateway may keep its highest CRL number across a restart, which is fleet-level state no server can rebuild and so outside what conflict 5 allows (D7).
- **For sign-off:** whether a replayed protective action that cannot be proven a replay may execute within its expiry (the Accepted risks row), or whether the two actions that loosen containment, `unquarantine` and `whitelist`, are treated differently from `quarantine` and `__guard__` (D5).
- **For sign-off:** whether the #4669 cluster-affinity admission check is removed before wave 2, while the route-claim risk is open, or with wave 4 (conflict 1).
- **For wave 4:** whether a fail-closed gateway gets weight zero in the gateway list (D7, D9).
- **No wave named yet:** #5578's R-6, per-gateway `agent_id` scoping.
