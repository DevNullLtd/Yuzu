## Context

### What runs today

| Hop | Today | Gap |
|---|---|---|
| Agent to server, direct | Mutual TLS. The agent presents its CA-issued leaf (`yuzu://<ca-fingerprint>/agent/<id>`, about a year, renewed at two thirds). Under the generated default certificates the port asks for a certificate but does not require one, so an unenrolled agent can bootstrap; the application enforces the rest. With operator-supplied certificates the port requires one (`server/core/src/grpc_tls_credentials.cpp`, `server.cpp`). | Only single-server installs use it. ADR-2002 section 2 makes the gateway mandatory in HA. |
| Agent to gateway (`:50051`) | One-way TLS (PKI PR5c). The gateway proves itself; it does not check the agent's certificate. The agent proves itself with its enrollment token, and heartbeats are bound to its Subscribe connection. | No transport identity for the agent at the edge that will face the internet. The enrollment token is presented only at first enrollment: the agent removes its token file once a registration is accepted (`agents/core/src/agent.cpp`), so after that an approved agent's `ProxyRegister` carries no per-agent secret. Revoking a gateway-proxied agent does not cut it off (`docs/auth-architecture.md`, "Gateway-proxied agents: revocation scope"). |
| Gateway to server (`:50055`) | Mutual TLS. The server admits the gateway by an SPKI pin fixed at boot. | Pins are per pair and do not scale to many gateways and many servers. No revocation. |
| Server to gateway management (`:50063`) | Strict mutual TLS. SPKI pin, or (opt-in, #6016) the server's URI SAN `yuzu://<install>/server` (the install id is derived from the CA fingerprint). | No CRL; a manual serial deny-list (`mgmt_peer_denied`) read at boot. Pins again. |

So gateway and server already authenticate each other in both directions. The missing link is the agent at the gateway.

### Why it matters now

- **Scale.** ADR-0069 sets 1.2 million agents and 100,000 per gateway.
- **SaaS.** Gateways will face the internet. A compromised or impersonated gateway must not be able to act as an agent.
- **Customers' PKI.** Most target customers already deploy a machine identity certificate (on Windows, in the certificate store behind CNG, often non-exportable or in the TPM). The direction of travel is SPIFFE/SPIRE for workload identity and RATS for attestation.
- **Topology.** The product needs agents that know several gateways, gateways that can be drained for maintenance, and gateways that use several servers writing to replicated Postgres (ADR-2002 section 7g).

### Measurements behind the transport choice (rocky9, 2026-10-28)

These come from branch `perf/gateway-idle-mem-ktls` (a kTLS handover NIF) and are not yet in the repository. Wave 0 commits the measurements the waves gate on to the repository, as an artefact, before they gate anything.

| Measure | OTP `ssl` | kTLS NIF |
|---|---|---|
| OS anonymous memory per idle agent (100 Windows agents, TLS 1.2) | 85.0 KB | 48.1 KB |
| Processes per agent | 6 | 3 |
| Handshakes per second, 4 cores | about 2,500 to 3,000 | about 6,000 to 6,600 |
| Memory per connection during a 30,000-handshake storm | 34.3 KiB | 8.4 KiB |
| Memory left after the storm, automatic reclaim | about +30 MiB | about +17 MiB |

The kTLS NIF was fuzzed for 91.2 million executions (92% line coverage, one bug found and fixed) and ran clean under ASan inside the BEAM. It can verify no peer certificate today.

## Decision

### D1. Gateway and server: CA trust, then identity, then revocation

All three, in this order:

1. **Trust our CA, not per-pair pins.** Gateways and servers admit each other by a certificate chaining to the install CA (or the customer's intermediate, D4). SPKI pins stay as an optional extra, not the default.
2. **Identity in the certificate.** Every certificate carries a URI SAN that names the role and the instance (D3). Each side checks the role it expects: a gateway is not a server, and an agent is neither.
3. **Revocation.** Every hop checks the revocation list (D7).

### D2. The agent edge: a separate enrollment port, and a strict main port

- **Main port.** It requires a valid client certificate at the TLS layer. A connection without one never reaches application code.
- **Enrollment port.** It accepts connections without a certificate, and the only thing it serves is enrollment. It has its own rate limit and connection cap at all times. The port is certless and faces the internet, so its cap must not be holdable by clients that never enroll: wave 2 must show that per-source limits (or an equivalent) keep it usable, and set a recovery target for a mass re-enrollment after an outage longer than a day.
- **Clean break.** This ships as a breaking change in the next release, with no fallback to the single-port behaviour. There are no production customers at the time of writing (2026-10-30). Before wave 2 merges, Nathan Dornbrook confirms that no pilot runs agents behind a gateway, and the wave 2 PR records it (decided by Nathan Dornbrook on 2026-10-30); if a pilot does, the upgrade note becomes a merge gate.
- **A routed-concern rule changes with it.** `.claude/routed-concerns-access-control.md` (the PKI row) forbids an `auth_fun` on the `:50051` agent listener, because it would reject every certless peer and stop agent bootstrap fleet-wide. That rule exists because today one port does both jobs. The change that splits the ports must amend the row in the same PR, with `security-guardian`: certless bootstrap moves to the enrollment port, which must never require a certificate.
- **Open: the direct port.** Whether the direct agent-to-server port of single-server installs gets the same split into an enrollment port and a strict main port. Wave 2 decides.

### D3. Identities are SPIFFE IDs

The URI SAN takes the SPIFFE form, `spiffe://<trust-domain>/<role>/<name>`. Examples: `spiffe://<trust-domain>/agent/<agent_id>`, `.../gateway/<name>`, `.../server/<name>`.

- **The trust domain (decided 2026-10-29)** is a random UUID generated once at install. The operator may set their own name at install time only; it never changes afterwards, except by a documented migration. It is not derived from the CA fingerprint: rotating the CA, or importing a customer intermediate (D4), would then rename every identity in the fleet. The SPIFFE standard itself advises a random name such as a UUID when no operator chooses one.
- **How an install sets its own trust domain (decided by Nathan Dornbrook on 2026-10-30):** an environment variable, with a matching Compose Wizard field, read only at first boot and locked afterwards. A different value at a later start stops startup with a clear error; an unset variable at a later start uses the stored domain. Changing the domain is the documented migration, never a setting. The value must match the SPIFFE trust-domain grammar (lowercase letters, digits, `.`, `-` and `_`); any other value stops first boot.
- **One URI SAN per certificate.** The SPIFFE X.509 standard says a verifier must reject a certificate with more than one. So the existing `yuzu://<ca-fingerprint>/agent/<id>` and `yuzu://<ca-fingerprint>/server` URIs cannot sit beside the new ones in one certificate. The migration is: verifiers accept either form for a window, then issuance flips to `spiffe://`. **The window ends at wave 2 (decided by Nathan Dornbrook on 2026-10-30):** from wave 2, verifiers accept only the SPIFFE form. Before wave 2 merges, a check shows that no server certificate, gateway certificate or management-port pin still uses `yuzu://`. An agent leaf issued before wave 1 still carries `yuzu://` for up to a year; wave 2's re-enrollment (Consequences) replaces it, and the upgrade section says so. The CA alone chooses the SAN; a requester never does (`sign_agent_csr` already ignores the CSR's subject and SAN).
- **The role comes from the SPIFFE path, never from the EKU.** The same standard says that when a leaf carries an EKU it must list both `serverAuth` and `clientAuth`. So every leaf carries both, and the EKU no longer tells a gateway from a server or an agent. The management port's existing `serverAuth` check still passes; it simply stops being a role check.
- A SPIRE server can later replace the issuer without changing what the main port checks.

### D4. Who issues the main-port certificate

- **Yuzu issues it**, always, as a short-lived certificate with a SPIFFE ID (D6).
- **The customer's machine certificate is an enrollment credential only.** On the enrollment port the agent proves it holds the machine certificate by signing a server challenge through the platform key store (Windows CNG, macOS Keychain, Linux file or PKCS#11). That signature is application-layer, so a non-exportable or TPM-held key works. It does not need gRPC to hold the private key.
  - This matters because gRPC 1.76 (the vcpkg pin) takes the client key as PEM and has no public private-key signing hook. So the machine certificate cannot be presented on the main port as it stands.
- **The enrollment token stays a supported credential** for machines without a machine certificate.
- **Customer PKI as the root of trust:** a customer may import an intermediate CA signed by their own root, and Yuzu issues from it. Customer-issued main-port certificates (the customer's CA issuing to agents directly) are not offered at first, and the design must not rule them out.
- **Default:** a customer who brings nothing gets a Yuzu-generated root and issuing intermediate (below).
- **An issuing intermediate in the default install (decided by Nathan Dornbrook on 2026-10-30).** The default install creates a root and an issuing intermediate at first boot, and only the intermediate signs leaves. The root may be kept offline or in an HSM. Wave 1 states the default intermediate's lifetime and how it is renewed, the schedule of the root's CRL, and what an operator who keeps the root offline must do for both. No HSM `KeyProvider` exists today (`FileKeyProvider` only); wave 1 states whether it adds one.
- **Key custody.** The issuing intermediate's key and the root's key must never sit on a volume, host or container a gateway can read. Today the reference gateway rig mounts the `certs` volume, CA key included (mode 0600, owned by the server's user), into the gateway container; wave 1 states where both keys live, and where the secrets KEK that shares that volume lives. Until no gateway can read the issuing key, a gateway compromised to container root can sign certificates, and the limit D10 puts on a compromised gateway (it controls only its own domain) does not hold.
- **Intermediate renewal under a customer's root (subordinate mode) is automated (decided by Nathan Dornbrook on 2026-10-30).** Yuzu requests renewal from the corporate CA through a standard enrollment protocol (EST, ACME or SCEP, whichever the CA supports). The fallback is a manual CSR and an escalating alert. The old and new intermediates are both trusted during an overlap. No leaf outlives its issuing intermediate: issuance moves to the new intermediate at least one leaf lifetime (7 days) before the old one's notAfter. Wave 1 states the renewal lead time against that, and what happens if no renewal completes in time.
- **Later:** TPM or RATS evidence is added at the enrollment step.

### D5. Agent identity reaches the server end to end

The gateway checks the agent's certificate, but the server does not trust the gateway's word alone. The owner chose this so that a compromised internet-facing gateway can drop or delay traffic but cannot impersonate an agent, or forge or alter what passes between agent and server.

**Decided on 2026-10-29.** Three kinds of signature, together:

1. **Per session.** The agent signs a server-issued challenge at the start of every session with its own key. The server verifies the signature against the certificate it issued, and refuses a revoked or mismatched agent.
2. **Every command** is signed by the server that issues it, with that server's own CA-issued key (its SPIFFE ID, `.../server/<name>`). The agent verifies it whichever server sent it and whichever gateway carried it.
3. **Every result** is signed by the agent. **The gateway list and drain suggestions** (D9, D11) are server-signed in the same way.

**Decided for ADR-0073 by Nathan Dornbrook on 2026-10-30, and binding here:** after a reattach the server sends a signed challenge, and the agent must answer it before its route is published or any command is routed to it, so a reattach never bypasses the per-session signature; and the agent signs its StatusTags deltas and its topology report, and the server rejects any that a gateway has altered (ADR-0073, PR #6704).

Each signature is over the whole message: for a command, the plugin, action and parameters; for a result, its status and payload; for the gateway list, the list itself. Each also binds the agent id, the command or execution id, the signer's identity and an expiry. The per-session signature covers the server's challenge.

**A server's signing key is revoked by the ban list only (decided by Nathan Dornbrook on 2026-10-30).** Server signing keys keep their normal lifetime (7 days, D6) and are not shortened. A revoked server key goes on the CRL; agents receive the CRL with their server-signed gateway list, and servers share it through `ca_store`. Wave 2 must make sure that a gateway list signed by a stolen key cannot bring back a CRL from before that key's revocation: the agent judges a CRL by the CA's signature and its number, never by the list that carries it. Wave 2 states whether the agent keeps its highest CRL number per issuer across a restart, and what freshness rule it applies to a CRL that arrives with a gateway list; a rule that resets on restart needs its own Accepted-risks row. The server-signed gateway list ships in wave 4 (D9); whether agents receive it, and so the CRL, from wave 2 is open (Open questions), and until they do a stolen server key is bounded only by its 7-day certificate lifetime. Wave 2 also states how soon after a server-key revocation the new CRL reaches every connected agent. The CRL reaches an agent through the gateway that holds it, so that gateway can withhold it. A stolen server key therefore stays usable until it is revoked and that revocation reaches the agents; for the agents of a gateway that withholds the CRL, until the key's certificate expires. That bound holds only if a key cannot extend its own life: wave 2 must ensure that no signed time decides the expiry of the key that signed it, and that a signed time never moves an agent's estimate of the time backwards (Accepted risks).

A replayed command is a duplicate to ADR-2002 WS-0's durable command idempotency only while WS-0's terminal ring still holds it (a bounded ring, `kMaxDedupRows` in `command_dedup_store.hpp`), and only while the agent's dedup store is healthy: a degraded store fails open by design (`docs/command-dedup.md`). The ring is bounded by count, not by time, and evicts in claim order, not signing order, so no fixed expiry is guaranteed to stay inside it. Wave 2 must design and test a replay bar that still holds after a row is evicted, after the store is recreated, and when the agent's clock is skewed, using only times the server signs; this ADR does not choose the mechanism. While the store is degraded, wave 2 must either refuse signed commands outside the protective set or record that residual; a protective action is never refused because the store is degraded (below). The protective set (`common/include/yuzu/protective_actions.hpp`) passes every enablement gate, but `quarantine`, `unquarantine` and `whitelist` each change a device's containment or allow-list, so a replay of any of them can loosen containment; and no `__guard__` dispatch takes the dedup claim, even with a healthy store, so the dedup store gives it no replay bar; its signed expiry acts as one (below). Wave 2 must give these actions a replay bar that does not depend on the dedup store; only `status` needs none. **That bar may refuse `quarantine`, `unquarantine`, `whitelist` or a `__guard__` dispatch only for a proven replay, never because a store is degraded (decided by Nathan Dornbrook on 2026-10-30).** A store that is degraded, unreadable or recreated, or a check that could not complete, is never proof; what counts as proof is wave 2's design, but proof may rest only on server-signed data and on agent-local state that wave 2 shows is healthy (never the degraded or recreated dedup store), so that nothing an on-path gateway can block or delay is needed to establish it (otherwise a gateway could make every replay unprovable, and so executed). Remembering a prior receipt needs agent-local state; server-signed data alone can show only that a command is superseded or stale (for example, through a signed per-device containment generation). **A signed expiry counts as proof of replay (decided by Nathan Dornbrook on 2026-10-30):** it may refuse all four protective actions (`quarantine`, `unquarantine`, `whitelist`, `__guard__`), and all four are treated alike. Expiry is judged against server-signed time, as the replay bar above already requires, never against a device clock that has not been checked. D6 sets the rule: the agent uses its own clock only when the OS reports NTP-synchronised and that clock agrees with the server-signed time; otherwise it uses the latest server-signed time, advanced by the time elapsed since it arrived, which a gateway can neither replay nor freeze. Accepted consequence: a device whose clock is badly wrong may refuse a genuine lockdown (Accepted risks). A protective action whose replay cannot be proven, inside its validity window, executes (accepted by Nathan Dornbrook on 2026-10-30; Accepted risks); wave 2 sets the expiry length, longer than the clock-skew tolerance and the delivery delays the design creates (a drain window, D11; a re-drive, wave 4). A re-drive re-signs the command with a fresh expiry rather than resending an expired one, and only while it is still the device's latest protective action of its kind (for example, by a signed per-device containment generation); a superseded one is dropped and shown to the operator as superseded. This is the single exception to the rule that no enablement gate may refuse a protective action (see Rules this design re-opens). If the agent refuses a containment action, the server's quarantine record must not show a state the device is not in: today the server's release of a quarantine record does not depend on any agent answer (`release_device`, called from the REST release route). The expiry also bounds how long a gateway can hold back a command, a protective action included. Liveness heartbeats stay unsigned.

Why signed messages rather than a key agreed per session with a MAC on every message: any server may send a command straight to the gateway that holds the agent (D12), and a drained agent delivers its result through another gateway, in another session, possibly to another server (D11, D12). A signed message survives both unchanged; a per-session key would have to be shared between servers, which is a new secret store. A signed result kept in Postgres is also evidence anyone can check later from the agent's key, which a MAC is not. The survey below found the same rule elsewhere: a relay that must read, store and forward messages (TUF mirrors, Tailscale's Tailnet Lock key distribution) uses signed messages; a relay that moves opaque bytes (WireGuard through Tailscale's DERP relays, SSH through Teleport's proxy) uses a per-session key.

**What D5 deliberately does not give, stated plainly:**
- **Confidentiality from the gateway.** The gateway still reads commands and results in plaintext. Hiding them would need encryption to the agent's key, a separate decision for SaaS.
- **Honest heartbeats.** A compromised gateway can report a dead agent as alive. The lie lasts until the next signed result or the next session start.

**Signed-result evidence window (decided by Nathan Dornbrook on 2026-10-30): a fixed 13 months,** one SOC 2 audit year plus a month. Within that window the response, the signing certificate's `ca_issued` record, and the certificate of the intermediate that issued it (kept after any D4 renewal or rotation) are all kept, so a signature and its certificate's chain can still be checked, whatever the response retention setting (90 days by default). Longer retention is by export to the customer's archive. Every result is signed (D5.3), so this keeps every response for 13 months whatever shorter retention an operator sets, Forensics rows and the registry plugin's `old=`/`new=` values included. Wave 2 states the export's permission (the same Forensics tier as reading the stored rows), the audit row it writes (who exported which range) and an integrity check that shows the archive is complete. The response pruner is a wall-clock bulk delete, so it follows the clock-guarded retention row, and it keeps what a signed result inside the window needs (its response, its `ca_issued` record, its issuing intermediate's certificate, and the CRL versions that show its revocation status when it was signed).

**To measure in wave 2:** the agent's cost of signing each result, and the server's verification rate, at the result rate of the 5,000-agent rig, alongside D14's handshake budget.

### D6. Certificate lifetimes and revocation

- **Agent certificates** last 24 hours and are renewed at half-life. At 100,000 agents per gateway, renewing every 12 hours, that is about 2.3 renewals per second per gateway.
- **Expired certificates.** An agent whose certificate expired (a server outage longer than a day, or a laptop off over a weekend) cannot use the main port and must go back through the enrollment port. The agent decides that its certificate has expired from its own leaf's notAfter (judged by the agent's clock rule below), never from a TLS alert: a gateway holding a stale CRL also refuses it, and treating that refusal as expiry would send the whole fleet to the enrollment port while the CA is stalled. Wave 2's chaos tests must show that a stale gateway CRL causes no re-enrollment. **A recently expired certificate may renew there on its own key for 30 days after its notAfter (decided by Nathan Dornbrook on 2026-10-30),** and only if the append-only revoked set and the agent DENY show no revocation. After 30 days the agent must re-enroll with an enrollment token or a machine certificate. Wave 2 must measure a mass re-enrollment after an outage. Prior art for renewing on its own key: Teleport's bound-keypair joining, where a bot whose certificates lapsed signs a server challenge with its bound private key, a generation counter refuses a cloned credential, and automatic recoveries are capped.
- **Gateway and server certificates** last 7 days, on the same revocation list.
- **Revocation scope, not yet settled.** With renewal at half-life an agent holds two valid leaves for about 12 hours, so revoking one serial leaves the other valid. Today's block on re-issuing to a revoked agent (`server.cpp`) lasts until the revoked certificate's notAfter, so with 24-hour certificates it lapses within a day instead of about a year. And with CRL pruning (D7) plus renewal on an expired certificate's own key, a revoked and expired agent is on neither list. Wave 1 must state the revocation scope (every live serial of an identity) and what blocks re-issuance (the append-only revoked set and the agent DENY, never the published CRL). A revoke and a renewal of the same identity must not interleave so that the renewal escapes: a certificate issued while that identity's revoke commits is covered by it (for example, revoke and issuance take one per-identity lock, and issuance re-checks the revoked set and the DENY inside its own transaction). Wave 1 tests a revoke racing a half-life renewal; wave 2 tests one racing a renewal on an expired certificate's own key.
- These replace today's one-year agent leaf and the server and gateway leaves sized to the CA's life.
- **The agent's clock (decided by Nathan Dornbrook on 2026-10-30):** the agent trusts the server's signed time, and also checks that the OS has an accurate NTP service. This is the wave-2 requirement that follows from that decision, to be confirmed in wave 2:
  - every session, and every answer on the enrollment port, carries a server-signed time;
  - the agent also reads the OS time-sync state, through a direct interface before a subprocess (ADR-3002's acquisition ladder; for example the kernel's synchronisation status through `adjtimex` on Linux, or the W32Time status on Windows); any subprocess it runs needs a row in `docs/agent-spawn-sink-manifest.md`, and a probe only reads the state (`sntp`, for example, sends its own NTP queries);
  - when the OS reports NTP-synchronised and the agent's clock agrees with the signed time within a tolerance, the agent uses its own clock;
  - when NTP is unsynchronised or absent, or the two disagree beyond the tolerance, the agent judges expiry (its certificate's, and a signed message's, D5) against the latest server-signed time, advanced as the next sub-bullet requires, and reports a clock-skew or NTP health signal to the server, which operators can see.
  - whatever wave 2 confirms, a gateway must not be able to replay an old signed time or freeze it by forwarding no newer one, or the expiry no longer bounds how long a gateway can hold back a command (D5). For example: the signed time answers a nonce the agent chose, and the agent adds the time elapsed since it received it on a clock that keeps running through sleep (`CLOCK_BOOTTIME` or the platform's equivalent, which on Windows is not `QueryUnbiasedInterruptTime`), also through a VM pause or snapshot restore, or the agent fetches a fresh signed time after one. An agent with an untrusted clock that the main port refuses fetches a fresh signed time from the enrollment port before it decides its certificate has expired.
  - a server's clock can be wrong too. Because a signed time never moves an estimate backwards (D5), agents that followed a server with a fast clock would stay ahead after it is corrected, refuse genuine protective actions as expired, and decide their certificates have expired. Wave 2 bounds how far signed time can move an agent's estimate ahead of its elapsed-time projection in total, not only per message: a bound per signed time still lets a server that stays fast, or a stolen server key, walk agents forward one step at a time. Its chaos tests hold a server's clock forward for many signing intervals, then correct it.

### D7. Revocation at a gateway that keeps no state of its own

- The gateway pulls the revocation list from the server every 60 seconds and refuses revoked agents at the handshake. That stops a revoked agent before it costs a session, memory and an upstream call. Session resumption would skip that check, so the main port issues no resumable sessions, or revalidates against the CRL on resumption; wave 2 states which, on both TLS paths, and tests that a revoked agent cannot resume.
- It keeps the last good list if a pull fails, and fails closed (refuses new agent handshakes) after 15 minutes without a good pull, or sooner if the held CRL's nextUpdate passes first. A good pull returns a CRL signed within the last 15 minutes (by its thisUpdate) whose nextUpdate is still in the future: a pull that only returns the same list again, because the signer has stalled, is not one, whatever the list's nextUpdate. Fail-closed state, CRL age, their alerts and readiness all follow the same rule, so a stalled signer is seen even while pulls succeed.
- **The gateway's own hop must survive a stale list.** D1.3's revocation check on the gateway-to-server hop, combined with a stale CRL, could lock a gateway out of the server it needs for a fresh list. Wave 1 must show that a gateway with a stale list can still fetch a fresh one without skipping revocation for anything else: for example, an exemption limited to the CRL-pull call, which carries no commands, with the fetched CRL verified against the CA's signature before use, and accepted only if its CRL number is not lower than the highest the gateway has seen from that issuer (and, if equal, it is the same list) and its nextUpdate is still in the future, so a replayed older CRL is refused. Restoring `ca_store` from a backup must neither lower the CRL number, or every gateway would refuse every new list, nor re-use a number for a different list; wave 1 tests a restore. The 15-minute fail-closed refuses new agent handshakes. Because D10's distribution links check the same CRL, and OTP `ssl` refuses a certificate whose CRL is past its nextUpdate, it also refuses new gateway-to-gateway links: a cluster that loses a link during a CA outage longer than 15 minutes cannot re-form it until a fresh list arrives. Wave 4 states whether distribution links fail closed, or are exempted from the CRL's freshness only, still checked against the last good list and never exempted from revocation as the CRL pull is, and tests a link reconnect during such an outage.
- **Under several servers (D12),** the server that owns an agent's stream must learn of a revocation made on another server. How is not yet designed; wave 5 decides.
- The server ends a revoked agent's live session immediately.
- **The window a revoked agent still has, stated plainly:** up to one poll (60 s) when everything is up; about two minutes across a Postgres failover (D13's 60 s plus a poll), provided the revocation survives the failover (D13's requirement for revocation; a revocation the standby never confirmed is shown to the operator as not done, so they can re-issue it); up to 15 minutes when the gateway can reach no server, which is the fail-closed bound. The server's own check at session start (D5) closes it earlier whenever the server is reachable.
- **Two 15-minute clocks coincide:** the CRL's fail-closed bound and the gateway's CONNECTED resend, which slows after 15 minutes of refusals (`notify_unacked_slow_after_ms`). An outage of 20 to 30 minutes with revocation on must be tested.
- The list is the CRL `CaStore::publish_next_crl` already publishes (ADR-2002 section 8).
- **CRL signing becomes a 15-minute dependency, and it is decoupled from the standby (decided by Nathan Dornbrook on 2026-10-30).** A 15-minute nextUpdate (see the test below) means the server must re-sign the CRL at least every 15 minutes, so CRL freshness then depends on the CA key, the leader and a write to the primary. The signer re-signs with margin inside the nextUpdate, so a missed tick or a slow pull does not reach the bound, and each re-sign takes a new CRL number; wave 1 sets the period and the retention of `ca_crl_versions` rows at that rate. The period is chosen against failover time, plus the 60-second pull, plus the clock-skew tolerance between gateway and signer (wave 1 states that tolerance, since a good pull is judged by thisUpdate on the gateway's clock; a gateway whose own clock is off by more than the tolerance, in either direction, therefore fails closed while the signer is healthy, its fail-closed alert names the clock, and wave 1's chaos tests skew one gateway's clock both ways), with immediate retry on a failed tick. The server exports the age of its newest published CRL, and a ticket-level alert on that age fires before the gateway page does. Leadership is part of the dependency: a server becomes leader only by writing a new leader epoch (`leader_elector.cpp`), and the CRL tick runs only on the leader, so CRL re-signing must not depend on a leader-epoch write that waits for a standby. Waves 1 and 6 resolve this together with D13's leader-epoch requirement (for example, the CRL publish runs without the leader gate, since `publish_next_crl`'s table lock already serialises signers, or the epoch scheme does not wait). The first example, if chosen, re-opens clause (3) of the fenced leader election row and the CRL job's classification in `background_jobs.hpp`, and has every replica re-sign, so wave 1 sizes `ca_crl_versions` retention for that rate. Today the CRL carries a 7-day nextUpdate and is re-published about every 6 days, from a leader-gated tick (`crl_publisher.cpp`, `server.cpp`). Losing a standby, or a Postgres failover, must not make gateways fail closed: CRL signing never waits for a standby to confirm, whatever durability wave 1 gives revocation and issuance (D13), and whichever profile the operator chose, strict mode (`YUZU_PG_SYNC_STRICT=true`) included; under strict mode that means the CRL publish and any audit write it needs commit without waiting for a standby (for example with `SET LOCAL synchronous_commit = local`), and the leader-epoch write is resolved under D13's leader-epoch requirement, which a local-only epoch commit does not meet. A primary that stays unreachable past the bound, with no failover, still fails gateways closed; that is the 15-minute bound working as designed. Wave 1 designs the decoupling, and its chaos tests show a CRL signed and pulled within the bound with every standby lost, and across a failover; wave 6 repeats the standby-loss test with strict mode on. Open for wave 1: a server that checks gateway certificates against a stale list would drop its gateway connections and their live sessions too; wave 1 decides whether servers check the `ca_issued` revoked set instead of the published list.
- **The CRL number never goes backwards or repeats across a failover, and gateways stay stateless (decided by Nathan Dornbrook on 2026-10-30).** With asynchronous replication (D13) a failover can lose the `ca_crl_versions` rows of lists already published, so a number counted on from those rows could repeat one a gateway already holds, or go lower. Servers therefore derive the CRL number from the signing time, so it never repeats or goes back after a failover. Gateways keep, for each CRL issuer (the root's CRL over intermediates, and the CRL of each issuing intermediate over leaves, two of them during a D4 overlap; an issuer is its name together with its key, the CRL's authority key identifier, so an old and a new intermediate under one name keep separate numbers, and wave 1 tests an overlap where both sign in the same second), the highest CRL number they have seen from that issuer, in memory only, and accept no list from that issuer below it, nor a different list under the same number; RFC 5280 numbers CRLs per issuer. In memory means for the life of the gateway's node, not of the process that pulls: a crash and supervisor restart of that process is not a gateway restart and must not reset the number. A gateway that restarts trusts the first CRL it fetches from an issuing intermediate, provided that fetch is a good pull (above); a gateway that restarts while no good pull is possible starts fail-closed, without the 15 minutes its held list gave it, so restarting gateways during a CA outage takes them out of service (the runbook says so, and wave 1 tests a restart during a stalled signer); wave 1 sets the matching rule for the root's CRL, whose schedule is not 15 minutes. Gateways keep no state across a restart (conflict 5 is unchanged). Wave 1 designs the derivation and tests it on a failover that loses published rows. A number derived from time goes backwards if the server that signs next has a clock behind the one that signed last, so wave 1 keeps it above the last published number within the clock-skew tolerance, and tests it under skew. A clock that is ahead is the worse case: one signed list with an outlier number raises every gateway's highest number, and every later list is refused until that gateway restarts. Wave 1 bounds how far one list can move a gateway's number (for example, a gateway refuses a list whose thisUpdate is ahead of its own clock by more than the clock-skew tolerance, so an outlier never becomes its highest number), and tests a forward clock step on the signer followed by its correction. If wave 1 leaves a gateway restart as the recovery, that outage gets its own Accepted-risks row. The restart rule leaves a window, recorded in Accepted risks: a restarted gateway accepts any older list signed within the last 15 minutes whose nextUpdate is still in the future (the good-pull rule above).
- **Expired entries leave the CRL (decided 2026-10-29).** The published CRL drops a revoked certificate only after it has appeared on one scheduled CRL issued after its notAfter, as RFC 5280 allows. The revoked rows in `ca_issued` stay append-only, exactly as today: only the published list shrinks, never the table. With 24-hour agent certificates the list then only holds certificates revoked in about the last day. Even 1% of 1.2 million agents revoked in one day is about 12,000 entries, roughly 0.45 MB, so no delta or Bloom-filter form is needed. A mass revocation (every agent behind a compromised gateway, a fleet-wide re-key) is handled by rotating the issuing intermediate, not by growing the list. Today a default install has no issuing intermediate: it signs leaves from the Yuzu root, and Yuzu never signs CA intermediates itself (`docs/pki-architecture.md`). From wave 1 the default install has one (D4, decided by Nathan Dornbrook on 2026-10-30), so a mass revocation there is an intermediate rotation too, not a root rotation. A rotation cuts off the old intermediate's leaves only once verifiers stop trusting it: the root signs a CRL that revokes the old intermediate, or every verifier drops it from its trust; until then those leaves stay valid to their notAfter (24 hours for agents, 7 days for gateways and servers). Short of every verifier dropping it from its trust, that root-signed CRL is the only way to revoke a compromised intermediate key. Wave 1 decides how a root kept offline or in an HSM issues that CRL and on what schedule (its nextUpdate cannot be 15 minutes), and whether gateways, servers and agents check the intermediate level of the chain, together with the customer-intermediate question below. If they do, a root CRL past its nextUpdate refuses every leaf of every hop at once, so wave 1 states what a lapsed root CRL does, adds an escalating alert on the root CRL's age that gives the operator of an offline root days rather than minutes, and lets the root CRL lapse in its chaos tests.
- **A routed-concern rule changes with it, in wave 1, not now.** The PKI row in `.claude/routed-concerns-access-control.md` says each CRL is a superset of the last. Pruning by expiry breaks that wording, though not the append-only table under it. ADR-2002 section 8 says the same (each CRL is a superset of the one before it), and wave 1 amends that sentence too. Pruning also breaks the count-based CRL freshness self-heal: `has_unpublished_revocations` (`ca_store.cpp`) compares the latest CRL's revoked count with the revoked rows, so wave 1 must re-key it to the non-expired revoked set in the same change. The wave-1 change that prunes the CRL amends the row in the same PR, with `security-guardian`.
- **To test in wave 1:** if the CRL's nextUpdate is set 15 minutes ahead, OpenSSL itself refuses a stale list (at the leaf level; the intermediate level follows the root CRL's schedule), so the 15-minute fail-closed bound becomes a property of the signed CRL, the same on both TLS paths at the agent edge (the gateway's own pull is the exception above).
- **Customer intermediates (D4):** checking every level of the chain needs a CRL from the customer's root for the intermediate, which Yuzu cannot produce. Either the leaf alone is checked, or the customer supplies their root's CRL; wave 1 decides.

### D8. kTLS is the default at the agent edge; OTP `ssl` is the fallback

The reasons are the measurements above, and that nginx and HAProxy run the same design: OpenSSL's TLS state machine and X.509 code in their own process, then (where enabled) kernel record encryption. **Neither makes kTLS a default (verified 2026-10-29).** nginx offers it as an opt-in since 1.21.4 (2021), through `ssl_conf_command Options KTLS`. HAProxy offers it as an experimental option since 3.3 (2025), through `ktls on`, refused unless the configuration also sets `expose-experimental-directives`. Our default is therefore a stronger position than either, but only if the requirements below are met; they are what make it acceptable. HAProxy, like the gateway, is one multi-threaded process, so a memory-safety bug there also costs every connection; nginx isolates it to one worker.

**TLS version (decided by Nathan Dornbrook on 2026-10-30).** `agent_id` is personal data (a GDPR online identifier). That makes four more things wave requirements: wave 1 inventories where `agent_id` is written (log lines, metric labels, audit rows, the SPIFFE SAN in `ca_issued`, responses), and no metric label or unbounded log field carries it; each store holding it states its retention basis, including why a revoked `ca_issued` row is kept indefinitely and what erasure means for a decommissioned device; the manual's privacy and data-retention pages say it is personal data; and the audit and export verbs D5 and D7 add do not put it in free-text fields. TLS 1.2 sends the client certificate in the clear, so on an internet-facing gateway a passive observer reads every agent's SPIFFE ID, and so its `agent_id`. Internet-facing gateways (the zone, D10) therefore require TLS 1.3 on the main port, so the client certificate is never sent in the clear. Internal gateways may still allow TLS 1.2. Until wave 4 puts the zone in the gateway certificate (D10), wave 2 states where a gateway's zone comes from. The requirement holds on both TLS paths: the OTP `ssl` fallback on an internet-facing main port also requires TLS 1.3. Both paths are pinned to TLS 1.2 today (`yuzu_grpc_listener:ssl_opts/1` sets `{versions, ['tlsv1.2']}` with TLS 1.2-only options that OTP refuses on a TLS 1.3-only listener, the kTLS branch's NIF builds one-version contexts, and the shipped `sys.config` files pin the upstream client to TLS 1.2), so wave 2 makes the version a per-listener setting. D14's figures were measured on TLS 1.2; wave 2 re-measures them on TLS 1.3 before they gate an internet-facing gateway. A TLS 1.3 peer can send KeyUpdate to change keys mid-connection. Under kTLS the kernel must install the new receive key, and only newer kernels can (the rekey support is documented for Linux 6.14). Rocky 9's 5.14 cannot: there a KeyUpdate ends the connection (item K2 of BigColin's review, 2026-10; no Yuzu agent stack was seen to send one). Wave 2 handles that limit, and needs two things:
- **A KeyUpdate policy:** refuse it and close the connection, or require a kernel with rekey support on gateway hosts, or keep the receive side in user space.
- **A KeyUpdate rate limit** whatever the policy, because each KeyUpdate costs CPU. HAProxy added one (100 per second per connection by default) to stop a KeyUpdate flood; the lesson applies with or without kTLS. On the OTP `ssl` fallback path neither the policy nor the limit is available: OTP answers every peer KeyUpdate itself, with no option to refuse or count it (`tls_gen_connection_1_3`, OTP 28.4). Wave 2 must either provide one there or record that the fallback has none as an Accepted-risks row the owner accepts by name.

Because memory safety is vital, these are requirements, not options:
- a pinned OpenSSL version, with its security advisories tracked and acted on;
- continuous fuzzing of our C code in CI, plus an ASan build exercised by the test suite. These apply to gateway C from the trim NIF onward, not from wave 2. CI compiles the trim NIF and eunit loads it, but no CI job fuzzes gateway C or builds it with ASan today (the NIF's build script ignores sanitizer flags). Wave 0 adds an ASan run for the trim NIF, which takes no input and so has nothing to fuzz; continuous fuzzing starts with the kTLS NIF in wave 2;
- one shared test suite proving the kTLS and OTP `ssl` paths accept and refuse exactly the same certificates (chain, SAN, EKU, expiry, revocation);
- security review of the C code before it ships enabled.

The difference from nginx is recorded: nginx runs handshakes in worker processes, so a crash costs one worker. Our handshake runs inside the Erlang VM, so a crash costs the gateway. Whether to move handshakes out of the VM later is an open item (see Open questions).

**Where the agent-certificate checks run (decided by Nathan on 2026-10-28):**
- **In C:** OpenSSL checks the chain and the revocation list during the handshake. The NIF sets `SSL_VERIFY_PEER` with fail-if-no-peer-certificate, the CA store (Yuzu root or customer intermediate) and the CRL. A bad chain or a revoked certificate is refused before the handshake completes. Our C stays small: configuring OpenSSL and handing the verified peer certificate to Erlang.
- **In Erlang:** the gateway checks the SPIFFE identity and the EKU of the verified certificate just after the handshake, before any gRPC request is served. Identity rules will change as SPIFFE and customer intermediates arrive, so they live where they are easy to change and test.
- **The same split on the fallback path:** OTP `ssl` checks chain and CRL, and the same Erlang identity check runs. The shared accept/refuse suite covers both.

The kTLS branch (`perf/gateway-idle-mem-ktls`, not on `dev`) currently refuses `ktls` together with `verify_peer`; that refusal goes away.

### D9. Discovery and choosing a gateway

- **"Use DNS" is a design principle.** An agent finds its first gateway by DNS.
- **After first contact,** the server gives the agent the current gateway list, with weights and draining state. The agent caches it on disk for the next start.
- **Choosing:** weighted random choice, with the weight from measured round-trip time, so the nearest gateway in time weighs most and agents do not all pile onto one. Jittered back-off between attempts. Failover down the list.
- **Draining gateways** have weight zero.
- **A fail-closed gateway** (D7) has weight zero until it has a fresh CRL, then returns to its measured weight in the next server-signed list (decided by Nathan Dornbrook on 2026-10-30; wave 4). Wave 4 states how soon after recovery the list is re-signed and pushed, and adds hysteresis so a flapping gateway does not re-sign and push the list fleet-wide on every change. If every gateway is at weight zero, agents still try them all. Wave 4 states how the server learns that a gateway has failed closed, including for one that reaches no server. When the CRL returns, every gateway leaves fail-closed together; wave 4 states the agents' back-off cap and so the recovery time, and tests the recovery as well as the outage, including the enrollment-port load from agents fetching a signed time (D6).
- No region or site field in the first version: latency weighting covers it. The weight function stays pluggable, because round-trip time does not see a LAN boundary (a per-campus site gateway, for example).
- **When every cached entry fails** (all drained or dead), the agent goes back to DNS. The cached list carries an expiry; to be set in wave 4, preferably per entry by the server, as Teleport's proxies do.
- **Any gateway list that reaches the agent through a gateway is signed by the server** (D5), and the agent refuses one that is not. Otherwise a compromised gateway could steer agents to endpoints of its choosing. Those could not impersonate the server, but they could hold agents captive.

### D10. How gateways know about one another

- **Within one communication domain (below):** gateways may form an Erlang cluster (the existing `yuzu_gw_cluster_discovery` and per-agent `pg` lookup; there is no hash ring, #4556). The cluster's own connections run over TLS (`inet_tls_dist`) with CA-issued certificates. Membership in an Erlang cluster is full control of every member. D1.2's role check applies: distribution admits only gateway identities of its own communication domain (the zone and organisation in the certificate, below), with chain and CRL checked. Under D3 agent leaves carry both `serverAuth` and `clientAuth` and chain to the same CA, so a chain-only check would admit an agent leaf to the cluster.
- **Bounded communication domains (decided by Nathan Dornbrook on 2026-10-30).** A domain is a zone (internet-facing or internal) together with one organisation (tenant). Gateway-to-gateway links stay inside one domain and never cross a domain boundary: an internet-facing gateway may link with the internet-facing gateways of the same organisation, but never with an internal gateway, and never with the internet-facing gateways of another organisation. This keeps ADR-2002 section 7's rule that a cluster does not span trust zones, and adds the organisation as a second boundary. Section 7 also says a cluster must not span a WAN (one per region); whether one domain's internet-facing gateways in different regions may form one cluster is open (Open questions). Because membership in an Erlang cluster is full control of every member, a compromised gateway controls every gateway in its domain, and no gateway outside it through the cluster; until wave 2 it can still claim agents of any domain or organisation through the server (conflict 1).
- **Link identity (decided by Nathan Dornbrook on 2026-10-30; delivered in wave 4).** Gateways link by mutual TLS, and each gateway certificate names its zone and its organisation (for example in the SPIFFE path, D3). Every link checks both, and is refused on any mismatch. OTP checks a distribution peer's certificate only when the link is set up, so wave 4 also disconnects every live link to a member whose certificate is revoked or has expired (once the CRL lists it, or at its notAfter), and tests it; wave 1's credential hot reload covers the distribution certificate too. Yuzu has no organisation or tenant concept today: one install has one CA and one trust domain (D3), and "tenant" in the code means an identity provider's tenant. Wave 4 defines what an organisation is, where the server records it, and how it appears in the certificate alongside D3's `<role>/<name>` path. The CA takes a gateway's zone and organisation from the server's record of that gateway, never from the request, and a renewal keeps them; wave 4 states how that record is set. A change to it takes effect only by revoking every live certificate of that gateway (a renewal leaves two, and a live link may have been set up with the older one) and issuing one under the new domain. Wave 1's block on re-issuing to a revoked identity and its revoke/issue interlock must not refuse or revoke that new certificate, so wave 4 states how a domain move differs from a compromise revoke (for example, the domain is part of the identity). Once the CRL lists those serials, the moved gateway keeps no live link into its old domain (the revoked-member disconnect above). Erlang distribution runs over that mutual TLS and admits a peer by that identity; OTP's handshake still checks the shared cookie, which is no longer the admission control. The gateway already refuses to boot on the shipped default cookie, an empty one, or one shorter than 32 characters (`check_distribution_cookie`, #659, #4555), unless `YUZU_GW_ALLOW_DEFAULT_COOKIE=1` is set for dev and CI, and wave 4 keeps that refusal.
- **New in wave 4:** TLS distribution with CA-issued certificates naming zone and organisation (today distribution is plaintext, and the cookie is its only authentication; node names are IP literals, `yuzu_gw@<ip>` from `gateway-entrypoint.sh`, and OTP's TLS distribution checks the dialled peer's certificate against that host by default, so wave 4 either puts the address in the certificate or replaces the host check with the identity check); the domain check on every link; and a `cluster_id` mismatch check at join, which guards against misconfiguration only, because admission is the distribution certificate.
- **Across domains,** gateways coordinate only through the server.
- **Either way,** every gateway reports health, load, draining and CRL (fail-closed) state to the server, because the server owns the gateway list agents receive (D9).

### D11. Draining a gateway

1. **The order:** an operator issues it through the dashboard, REST API or MCP, RBAC-gated and audited, reaching the gateway through the server (or through the cluster). Automation uses the same API.
2. **What agents receive (decided 2026-10-29):** the gateway sets its weight to zero. Each agent first receives, on its own stream, a short suggested list of other gateways signed by the server (D5). Then the gateway sends an HTTP/2 GOAWAY in two phases: a first one that stops new streams, and a final one after a jittered delay. The GOAWAY carries nothing in its debug data: RFC 9113 says that data is for diagnostics only, and the agent's gRPC stack does not hand it to the application. The agent reconnects by its normal weighted choice. Cowboy already sends a two-phase GOAWAY when a listener shuts down; the per-connection trigger, the batches and the jitter are new.
3. **Pace:** the two-phase GOAWAY goes out in staggered, jittered batches over an operator-set window, 10 minutes by default, so no other gateway takes a storm. The gateway exits when empty or at a hard deadline.
4. **Commands in flight:** the agent reconnects elsewhere and delivers the result there. The server must accept a result for a command it sent through a different gateway. The durable command idempotency of ADR-2002 WS-0 and the execution ids carry it. **This is new code on both sides.** Today a gateway drops a response for a command it did not dispatch (the orphaned-response path in `yuzu_gw_agent`); it must forward it upstream instead. And nothing re-drives an operator command whose result was lost on the drained stream (the command outbox covers scheduled runs only), so wave 4 builds the re-drive, with WS-0 replaying the stored outcome.
5. **The enrollment port** stops accepting new connections at the start of the drain window.
6. **Drain and stop (decided by Nathan Dornbrook on 2026-10-30; wave 4).** A drain is an explicit step before a stop, an API or MCP call, and the stop waits for it. A bare stop runs a fast drain that fits the platform's stop grace; wave 4 makes sure a fast drain never pushes its peers above D14's reconnect rate, even under a short grace (for example by leaving the remaining agents to their ordinary jittered back-off). Today the shipped Compose files, the files the Compose Wizard generates and the systemd unit give a gateway 40 seconds to stop (`stop_grace_period: 40s`, `TimeoutStopSec=40`, sized to the planned stop's 20-second `shutdown_flush_budget_ms`; the server has 210 seconds). Wave 4 raises the gateway's stop grace in the shipped Compose files and the files the Compose Wizard generates to 11 minutes (whether the systemd unit follows is open, Open questions), and any Kubernetes manifests Yuzu ships will use 11 minutes too (none ship today). A fast drain with no other gateway to move agents to ends at once instead of waiting out the grace (every shipped Compose file but the cluster reference runs one gateway). Wave 4 reconciles the drain with `shutdown_flush_budget_ms` (default 20 seconds, at most 10 minutes).

### D12. Several servers

1. **All servers active.** Singleton jobs run on the elected leader of ADR-2002 sections 3 and 6.
2. **Each gateway connects to every server** (ADR-2002 section 7g). Each agent's stream goes to one server, chosen by consistent hashing on `agent_id`. When a server is lost or drained, only its agents move.
3. **Reaching an agent:** Postgres records which gateway holds which agent (`agent_routes`). Any server sends a command straight to that gateway's management port. **This is new server code.** As of `origin/dev@fbd8b5409`, `AgentRegistry::send_to` (`server/core/src/agent_registry.cpp`) returns false for an agent not in that server's own memory, so a dispatch handled by a server that does not own the agent reaches nobody. With N gateways each connected to M servers, the upstream permit model (#6057) must also be re-derived. The result returns through the server that owns the agent's stream and lands in Postgres. The gateway part is new too: today a result returns on the dispatching server's SendCommand stream.
4. **Gateways find servers by DNS.**
5. **Draining a server:** it stops taking new agent streams, and its agents are rehashed onto the others in staggered batches.

### D13. Postgres

- **Replication: asynchronous by default (decided by Nathan Dornbrook on 2026-10-30; conflict 8).** An earlier draft of this decision required one synchronous standby that never degrades to the primary alone; that rule is dropped. Many enterprise data-centre pairs are more than 2 ms apart, and a commit that waits for a standby in the other data centre on every write is too slow there. No commit waits for a standby by default, except a transaction D13's per-store requirements below make wait. ADR-2002 section 11's synchronous profiles stay available as an operator's choice. An operator who chooses `quorum3` or `sync2` keeps RPO zero only while a synchronous standby is up; in exchange every commit waits one round trip to that standby, `quorum3` without strict mode silently falls back to asynchronous when every standby is lost, `sync2` stalls every write when its one standby is lost, and strict mode blocks writes for longer after a failover. `docs/user-manual/ha-postgres.md` states these trade-offs next to the profile table from wave 6. The shipped Patroni profile is unchanged until wave 6 changes its default (conflict 8).
- **RPO zero for acknowledged writes is no longer a target.** A failover can lose every write the old primary acknowledged but had not yet sent to the standby that is promoted. How much is lost depends on replication lag at the moment of failure; wave 6 measures it, and this ADR sets no bound on it. A failover tool may cap it: the shipped Patroni rig refuses to promote a standby more than 1 MiB behind (`maximum_lag_on_failover`, `patroni-entrypoint.sh`), which bounds the loss but can leave no standby to promote, so write downtime then has no bound. Wave 6 sets that cap deliberately, as the trade between the loss and the 60-second target, and tests a failover in which every standby lags past it. The cap also decides fleet admission: with no standby promoted the primary stays unreachable, and after 15 minutes every gateway fails closed (D7).
- **What a failover can lose, and what each store must meet.** For each store below, the named wave must design how its loss is prevented or made harmless, and prove it on a failover that loses acknowledged writes. These are requirements; the mechanisms are not decided.
  - **Revocation** (the revoked rows of `ca_issued`). Lost means a revoked certificate becomes valid again. Requirement (wave 1): a revocation the server has acknowledged, or that any published CRL has carried, survives a failover, and no CRL is signed that omits an unexpired revocation an earlier published CRL carried. Gateways run no superset check of their own, so a later list that drops such a revocation would make the certificate valid again. Wave 1 may meet this by making the revocation write wait for a standby (not the CRL re-signing, which never waits, D7), or by recovering published revocations from somewhere other than the primary; either way it states what a revoke does while every standby is lost. A revocation the standby has not confirmed is shown to the operator as not done, so the operator can re-issue it (decided by Nathan Dornbrook on 2026-10-30).
  - **Issuance** (the issued rows of `ca_issued`). Lost means a certificate is in use that the database does not know, so it cannot be revoked by serial. Requirement (wave 1): every issued certificate can still be revoked after a failover.
  - **CRL number** (`ca_crl_versions`). Lost means a number counted on from these rows is re-used or goes backwards, so gateways refuse the next list. Requirement (wave 1): the number is derived from the signing time, so a lost row neither re-uses nor lowers it, and a gateway that has restarted or is new trusts its first good pull of an issuing intermediate's CRL (the root's CRL: wave 1, D7) (D7, decided by Nathan Dornbrook on 2026-10-30; Accepted risks).
  - **Audit rows.** Lost means a gap in the audit evidence. Requirement (wave 6, with `compliance-officer`): state whether an acknowledged audit row must survive a failover, and how. Whatever the general answer, the audit row for a revocation, an issuance, an access revocation or a quarantine change commits in the same transaction as the act, or with the same or stronger durability: an act that survives a failover must not lose the record of who did it and when.
  - **Access revocations and containment** (operator sessions and logouts, API token revocation, SCIM, OIDC and SAML deprovision, user deactivation, RBAC unassignment, and `QuarantineStore` records and allow-lists). Lost means a revoked session or token, or a deprovisioned operator, works again; or a contained device is treated as dispatchable, or an older allow-list is pushed again by the stored-containment re-dispatch. Requirement (wave 6): an acknowledged revocation or quarantine change survives a failover, or its loss fails closed (for example, every session and token older than the replication lag must authenticate again); wave 6 defines what failing closed means for each. This one may not be recorded as accepted.
  - **Agent routes.** Lost means a stale route. Requirement (wave 6): routes are rebuilt from live connections (the reconcile, #5649) as agents reconnect, and a lost route row never leaves an agent unreachable once it has reconnected.
  - **Command outbox and dispatch.** Lost means a command is driven again or not at all. Requirement (wave 6): a command whose dispatch row is lost is shown to the operator as not done, never as done; a command driven again is a duplicate to the agent only within WS-0's ring and while its store is healthy (D5), so the re-drive must stay within that; a protective action, which the ring may not cover (`__guard__` never takes the claim), is bounded by supersession instead (D5).
  - **Leader epoch** (`leader_epoch_seq` and `leader_state` in the `leader_elector` schema). Lost means an epoch is issued twice, so a new leader and a paused former leader both pass the epoch fence and a fenced claim can be made twice (ADR-2002 section 6). Requirement (wave 6): no epoch is ever issued twice across a failover. This one may not be recorded as accepted.
  - **RBAC write generation** (`rbac_meta.write_generation` in the `rbac_store` schema). Lost means the generation goes backwards, and a server that saw the lost value ignores later grant changes, so it serves a revoked grant while every refresh succeeds. Requirement (wave 6): no server ignores a grant change made after a failover. This one may not be recorded as accepted.
  - **Event outbox** (`event_outbox`, and its role as the schedule runner's spent-ticket record). Lost means a server polling forward from its last-seen position skips new events with no visible gap (the poller's position is a transaction-id horizon the promoted primary can issue again), an event id names two events, or a spent approval ticket can be spent again. Requirement (wave 6): no event is skipped and no event id names two events across a failover, and a lost spent-ticket row never lets an approval run twice. This one may not be recorded as accepted.
  - **Execute-once claims** (`DeploymentRunStore`'s `claim_for_exec`, and the policy remediation claim). Lost means a mutating step runs twice: a reclaimed deployment step is sent under a new command id, which WS-0's dedup does not absorb. Requirement (wave 6): a lost claim never causes a second execution of a mutating step. This one may not be recorded as accepted.
  - **Restores.** A restore from backup rewinds every store above further than a failover does. Every requirement above holds for a restore as well as a failover; waves 1 and 6 each write the post-restore runbook for their stores (for example: re-apply revocations made after the backup, and force sessions and tokens to authenticate again). A CRL number derived from the signing time (D7) is already past every published number after a restore, provided the signer's clock is within the tolerance; the runbook covers a signer whose clock is not.
  - **Every other store.** Requirement (wave 6): list what a failover can lose there, and either close it or record it as accepted.
- **The leading candidate for revocation, issuance and possibly audit, not a decision:** per-transaction synchronous commit, where only those transactions wait for a standby (Postgres `SET LOCAL synchronous_commit`) and every other write stays asynchronous. Each such transaction then takes one round trip to the standby. Revocations are rare, so that costs little; issuance is not rare (about 28 signatures per second at 1.2 million agents, see Consequences), so wave 1 measures the cost on the signing path before choosing it. It works only where a standby is named as synchronous: on the shipped `async` profile (`synchronous_mode: false`, so `synchronous_standby_names` is empty) the setting waits for the local flush only, and gives no durability. If it is chosen, "asynchronous by default" is delivered as Patroni's synchronous mode (which also limits promotion to the synchronous set) with a cluster-wide `synchronous_commit = local`, not as the `async` profile. Choosing it means wave 1 must also state what such a transaction does while no standby is reachable (wait, which holds up revocation, or proceed, which re-opens the loss; Patroni without strict mode clears the synchronous standby list when every standby is lost, so a wait silently becomes proceed). A synchronous wait that ends early leaves the transaction committed locally but not replicated, and Postgres still reports the commit to the client as successful, with only a warning. Wave 1 must treat such a commit as not durable: it neither acknowledges the revoke nor publishes it until replication is confirmed, and the CRL publisher, not only the revoke handler, excludes a revocation whose replication is unconfirmed (`publish_next_crl` reads every committed revoked row). That covers every way a wait ends early: the pool's `statement_timeout` (30 s by default, `pg_pool.hpp`), a terminated backend, a client disconnect, the synchronous standby list being cleared, and a primary restart during the wait. CRL signing must not wait on a standby either way (D7).
- **Failover:** Yuzu depends on no particular HA tool. It reaches Postgres by one DNS name, or a multi-host DSN, with `target_session_attrs=read-write`. Patroni is the documented on-premises reference; a managed service is the SaaS choice. Whatever HA tool is used must not break the per-store requirements above.
- **Targets:** write downtime under 60 seconds per failover. This is a target, unmeasured until wave 6. While Postgres is unreachable, servers fail closed for writes. **That is not true of every store today:** `ResponseStore` logs a failed store under pool pressure and drops the response (BigColin's test run RR7, 2026-10-28, at 5,000 agents: one of seven runs lost 1,989 of 4,941 responses with the default pool of 16). A synchronous standby, where an operator chooses one, lengthens every commit and makes that likelier. This decision therefore includes a concrete change: bounded retry, or an explicit error, for response storage, and a pool size measured with the default asynchronous replication and with a synchronous standby.
- **Reads:** no reads from standbys in the first version.
- **Leadership** is re-elected after every failover, and every singleton job must tolerate that.
- **Several servers need more than this ADR.** Multi-server operation (D12, wave 5) also requires ADR-2002's safe-to-scale gate (`docs/ha-delivery-matrix.md`, including #6528 and #6535). Wave 5's rig does not lift it.

### D14. The gateway budget

This replaces the 8 KiB-per-connection goal set on 2026-10-26.

These are targets, not yet evidence. On merged `dev` the gateway holds about 320 to 470 KB per agent at 5,000 agents (Nathan's 5,000-agent suite; BigColin RR7, RSS). The 48.1 KB above is the kTLS branch at 100 agents with one-way TLS. Wave 0 measures a common baseline at 5,000 and 10,000 agents, with one method (OS anonymous memory plus kernel, after settling, TLS on), on merged `dev` and on the kTLS branch, before the CI check becomes a gate.

- **Goal, per box:** one gateway on 8 cores and 16 GB holds 100,000 idle agents with mutual TLS. It must stay inside:
  - memory under 8 GB;
  - idle CPU under 2 cores;
  - a full reconnect of all 100,000 agents within 60 seconds (about 1,700 handshakes per second, plus the D5 signature checks). RR7 registered about 290 agents per second against the about 1,700 needed; the likely bottleneck is the server's Register path (and the D5 verification, whose CPU cost is not yet budgeted), not the handshake;
  - memory back within 5% of its pre-storm level within 2 minutes.
- **CI regression check, per agent:** 64 KiB per idle agent, all-in including the kernel's per-connection memory. The check is measured with the ADR-0073 heartbeat (liveness only, no fleet snapshot), so until ADR-0073 lands it does not measure the heartbeat that ships.

The memory measures in this ADR's companion change (on `dev` since commit 857ac374e) are: a garbage collection of the large processes after an agent-count drop, plus a second pass 30 seconds later; and a periodic `malloc_trim(0)` through a small NIF. The periodic trim runs every 5 minutes by default (`trim_interval_ms`; 0 turns it off). Only the trim after an agent-count drop was measured; the periodic trim was not. The trim acts on glibc only, and does nothing on the default musl image. `+MMmcs 0` and `MALLOC_ARENA_MAX=2` are not in it: they are deferred to the hibernation work, because they gave no measurable memory gain and had a measured idle-CPU cost.

`malloc_trim` is a glibc feature. It acts on the chiselled Ubuntu image (`Dockerfile.gateway.chisel`), where it was measured. The default image (`Dockerfile.gateway`) is Alpine with musl, and musl has no `malloc_trim`. musl's allocator returns freed memory differently, and that is not yet measured. The glibc builders (the chisel builder, CI, and the Meson-driven gateway build on Linux) already compile the trim NIF (`gateway/apps/yuzu_gw/rebar.config`, `c_src/build_mem_trim_nif.sh`). Only the Alpine builder in `Dockerfile.gateway` has no C toolchain; the kTLS NIF must add one there (`build-base`, `openssl-dev`, `linux-headers`), and its rebar pre_hook must match musl targets too, because the trim NIF's `-linux-gnu-` filter skips Alpine. Both NIFs are Linux-only: Windows and macOS gateway builds skip them. kTLS itself does not need glibc. Checked on 2026-10-28: the NIF builds without warnings against musl in `erlang:28-alpine` (with `openssl-dev` and `linux-headers`) and loads in the BEAM there. What kTLS needs is the host kernel's `tls` module, because a container shares the host's kernel and cannot load modules itself.

### Rules this design re-opens

Several standing rules, and one earlier ADR, say the opposite of a decision above. Until the named wave amends each one, with `security-guardian`, the current rule stands and code must follow it.

- **No `auth_fun` on the `:50051` agent listener** (the PKI row of `.claude/routed-concerns-access-control.md`; D2). It is also enforced in code: the gateway refuses to boot with `auth_fun_on_agent_listener` (`yuzu_grpc_listener.erl`), and the manual's stage 3 in `docs/user-manual/gateway.md` ("Moving the agent edge to mutual TLS") says the same. The enrollment port also needs a per-listener method allow-list, which the layer does not have: new code. **Wave 2.**
- **Each CRL is a superset of the last** (the PKI row; D7). **Wave 1.**
- **`CaStore::publish_next_crl` is the single CRL publisher, numbering `MAX(version)+1` with no gaps** (the PKI row; ADR-2002 section 8, update of 2026-09-23). D7's number derived from the signing time leaves gaps, and D4 and D7 add a second CRL issuer (the root's CRL over intermediates) that `ca_crl_versions`' single `version` key does not model. The derivation stays inside `publish_next_crl`'s table lock, per issuer, never in a second path, so two replicas cannot sign two lists under one number. Wave 1 states how a root CRL signed outside the server (an offline or HSM root) is recorded through that same path, never through a second one. **Wave 1.**
- **The protective set passes every enablement gate, a degraded store included** (clause (3) of the quarantine row in `.claude/routed-concerns.md`; D5). A replay bar that can refuse `quarantine`, `unquarantine`, `whitelist` or a `__guard__` dispatch narrows it. Decided on 2026-10-30: the narrowing is allowed only for a proven replay, never because a store is degraded, and it is the single exception to the rule (D5). A signed expiry counts as proof (decided by Nathan Dornbrook on 2026-10-30, D5). The row's clause (3) is amended to say so in wave 2, with `security-guardian`. **Wave 2.**
- **Rows whose guarantee holds across a failover only once D13's requirement for that store is met** (D13): clauses (1) and (3) of the fenced leader election row and clause (8) of the RBAC administration row (`.claude/routed-concerns-access-control.md`); the `/auto` Deploy row's execute-once and clause (1) of the quarantine row (`.claude/routed-concerns.md`); the PKI row's append-only revoked set and serial-scoped revoke. The rows stand as written; asynchronous replication can lose the state each rests on. The wave that meets the requirement re-verifies each one, with `security-guardian`. **Waves 1 and 6.**
- **Command dedup retention is a clock-free ring, and a store failure is a deliberate fail-open** (the durable command idempotency row; invariant 7 of `docs/command-dedup.md`; D5): the first if wave 2's replay bar adds time to ring retention, the second if wave 2 refuses signed commands outside the protective set while the store is degraded. **Wave 2.**
- **The gateway-upstream peer row,** clause (2) (CA membership never substitutes for the pin) and clause (3) (pins fixed at boot, no revocation read, and re-opening them means re-opening `docs/security-reviews/gateway-peer-authz-minimal-2026-10-07.md`). Also clause (4): `gateway_peer_resolution.*` refuses to boot with operator certificates and no pin, or with zero loadable pins, and D1's CA trust without pins is exactly that configuration. D1 re-opens all three. **Wave 1.**
- **The mgmt-plane peer row and ADR-2004:** clause (2), one byte-exact identity `yuzu://<install>/server`, against D3's window that accepts both forms and its per-instance `.../server/<name>`; clause (3), an unset `mgmt_peer_auth_mode` is always `pin`, against D1's optional pins; clause (4), `identity_over_ca_bundle` refuses a CA file that is not exactly one certificate (unless the mode is `identity` and a pin is configured), which a customer intermediate plus its root, the default install's root plus issuing intermediate, and an old and a new intermediate during a renewal overlap (D4) each is; and the identity derived from the CA fingerprint, against D3's UUID trust domain. **Wave 1**; the `yuzu://` form is then dropped in wave 2 (D3).
- **Yuzu never signs CA intermediates itself** (`docs/pki-architecture.md`, Subordinate-CA). D4's issuing intermediate in the default install is one that Yuzu signs under its own root, at first boot (`default_certs.{hpp,cpp}`, under the PKI row). **Wave 1.**
- **The issuing key never changes** (`docs/pki-architecture.md`, Subordinate-CA). An intermediate rotation (D7) changes it, and so does a subordinate-mode renewal (D4) that changes the key. **Wave 1.**
- **`ca_store` holds the root key's `key_ref` only, and the root key stays behind `KeyProvider`** (the PKI row). Today `ca_store.ca_root` is one row (`CHECK (id = 1)`) that `set_root` overwrites, holding the issuing certificate and its `key_ref`, and `CaMode` is either a self-signed `Builtin` root or an enterprise-signed `Subordinate` intermediate. D4 needs a root and a Yuzu-signed issuing intermediate side by side, and two trusted intermediates during a renewal overlap; D5's 13-month window keeps every superseded intermediate's certificate, which an overwrite loses; and ADR-2002 section 8's shared key custody (every replica holds the CA key and must resolve it before it is ready) applies to the issuing key only once the root may be offline or in an HSM. **Wave 1.**
- **Mutations fail closed on audit failure** (the headless-platform row of `.claude/routed-concerns-access-control.md`; ADR-1005). Narrowed for routine CRL re-signs (Audit and evidence). **Wave 1.**
- **The registry write rows' risk acceptance assumes responses are kept 90 days by default** (clause (3) of both `registry` rows, `.claude/routed-concerns-security-posture.md`). D5's 13-month window keeps those responses, secrets included, for 13 months. The owner re-accepts the rows with the longer window, or wave 2 keeps the evidence another way; until then the row in Accepted risks is not yet accepted. **Wave 2.**
- **Gateway key custody** (the gateway-upstream peer row of `.claude/routed-concerns-security-posture.md` allows the key-bearing certificate volume into the gateway container). The CA's issuing and root keys must not be readable there (D4). **Wave 1.**
- **Alternatives ADR-2004 rejected and this ADR takes up:** short-lived server certificates (rejected there because the server never renews its leaf and client credentials have no hot reload), and CRL checks at the handshake only on the long-lived management connection. So wave 1 must add credential hot reload on server and gateway, and the teardown of a live connection whose peer certificate is revoked.

## Conflicts this ADR creates, to resolve in wave 0

1. **Cluster affinity against free gateway choice. Decided on 2026-10-29: affinity is dropped.** #4669 made an agent's home cluster sticky (`agent_routes.home_cluster_id`), so another cluster cannot claim and answer for it. D9 and D11 move agents between gateways freely, possibly across clusters. The #4669 admission check is to be removed now, ahead of D5 and wave 4 (below); the choice of gateway is free from wave 4, and affinity is neither an admission rule nor kept as a preference.
   - **The risk this carries, stated plainly:** until D5 lands in wave 2, a compromised gateway that holds a valid gateway certificate can claim any agent's route. D5's per-session signature and signed commands and results close it only if the route write (`agent_routes`, written today on the gateway's CONNECTED notification and asserted by the gateway) changes only after the server has verified that session's agent signature. Wave 2 makes it so. D5 does not stop a gateway that holds the agent from reading command payloads (a D5 non-goal).
   - **Affinity is dropped now (decided by Nathan Dornbrook on 2026-10-30, re-confirming the decision of 2026-10-29).** Removing the #4669 admission check does not wait for D5 or for wave 4, and Nathan accepts the route-claim gap by name until wave 2 (Accepted risks).
2. **D5's scope. Decided on 2026-10-29:** signed commands, signed results and a signed gateway list, on top of the per-session signature (see D5).
3. **#5649. Still open: a proof obligation for wave 5.** D12 point 2 chooses stickiness on the gateway side (one owning server per agent). Wave 5 must show the reconcile correct when that owner changes (server loss or drain).
4. **ADR-0073's budget text. Done:** ADR-0073 is in PR #6704 and was revised there to cite D14 instead of the 8 KiB goal, and to re-cite the gateway after the merge of PR #5695.
5. **"The gateway adds no state." Decided on 2026-10-29:** both this ADR and ADR-0073 say instead that the gateway keeps **no per-agent state beyond the connection**. Fleet-level state that any gateway could rebuild is allowed: the cached CRL and the highest CRL number seen from each issuer (in memory only, D7), the drain flag, the cached gateway list, and cluster membership. ADR-0073's part is done: PR #6704 uses this wording. Today's gateway already keeps two kinds of per-agent state beyond the connection: per-agent `pg` groups across cluster members, and the DISCONNECTED resend window after a connection ends. Wave 4 keeps each as rebuildable state or changes it.
6. **Erlang clusters and the server's `cluster_id`. Decided on 2026-10-29: one Erlang cluster is one `cluster_id`.** The server already routes by a `cluster_id` per gateway session (ADR-2002 WS-4 4.3). Every member of a cluster (D10) is configured with the same id. Wave 4 adds a mismatch check at join, which guards against misconfiguration only: admission is the distribution certificate.
7. **The design target.** ADR-0069 records 100,000 agents per gateway. Dave has been steering to a solid 5,000 per gateway now, nothing that blocks 50,000 and beyond, and 500,000 as the long-term horizon. **Decided by Nathan on 2026-10-28** (Dave to see): waves 1 to 5 must pass at 5,000 agents on both rigs, with nothing that blocks 50,000; wave 6 tests failover under a 5,000-agent load; wave 7 is the 100,000-agent per-box budget (D14); 500,000 stays the long-term horizon, outside this programme.
8. **D13 against ADR-2002 section 11. Decided by Nathan Dornbrook on 2026-10-30: asynchronous replication is the default, and D13's one synchronous standby that never degrades is dropped.** Section 11 specified one primary plus two synchronous standbys (`ANY 1`), failing closed when both are lost. WS-7 measured that this strict mode blocks writes for minutes after a single failover, so the shipped Patroni default is the `quorum3` profile without strict mode (`YUZU_PG_DURABILITY` defaults to `quorum3` and `YUZU_PG_SYNC_STRICT` to false in `deploy/docker/ha-postgres/patroni-entrypoint.sh`): non-strict synchronous replication, where every commit waits for one standby while any standby is up and replication degrades to asynchronous only when every standby is lost. The decided default is asynchronous: no commit waits for a standby, except a transaction D13's per-store requirements make wait. The reason: many enterprise data-centre pairs are more than 2 ms apart, too far for a standby wait on every commit. RPO zero for acknowledged writes is no longer a target; what a failover can lose is accepted (Accepted risks), and each store's loss must meet the requirement D13 sets for it in wave 1 or wave 6. ADR-2002 sections 11 and 13 carry a dated update to match. Wave 6 changes the shipped profile's default on the existing Patroni rig (`deploy/docker/docker-compose.ha-postgres.yml`), not a new one; until then the shipped default is unchanged.

## Audit and evidence

The waves add audit records or metrics for: certificate issuance, renewal and revocation; CRL publication and gateway pulls; handshake refusals by reason; entry into and exit from fail-closed; enrollment by machine certificate; D5 signature refusals; the drain lifecycle (order, abort, completion); and changes to the gateway list the server signs. Each wave must add the audit verbs, metrics and alerts it introduces to its Done-when before it closes; the cells below do not list them yet. Audit records go to the existing audit log, with its retention (365 days by default) and its `AuditLog:Read` gate. D5's 13-month window does not extend audit retention: for the last month of the window a kept result's signature and chain can be checked but the audit rows around it may already be pruned. Wave 2 decides, with `compliance-officer`, whether the audit verbs D5 and D7 add are kept at least 13 months, or this gap is recorded as accepted. Issuance records and CRL versions stay in `ca_store`, where a revoked row is never deleted. Mutations fail closed on audit failure (ADR-1005), with one exception, decided by Nathan Dornbrook on 2026-10-30: a routine automated CRL re-sign continues when its audit write fails. Its audit rows are buffered and written later, and the failure pages. A new revocation still fails closed on audit failure: the revoke is refused and shown to the operator as not done, so while audit writes fail no new revocation can be made, and anything that can break audit writes can delay a revocation (the failure pages).

Today's revoke commits the revocation before its audit row (`revoke_core`, `ca_routes.cpp`); from wave 1 the revocation's audit row commits in the same transaction as the revocation (D13's audit requirement, applied to revocation in wave 1). A routine re-sign is the scheduled tick, never the publish that follows an operator's revoke; it publishes only revocations already committed with their audit row, so the exception cannot carry an unaudited revocation, and it never holds back a committed one.

So audit availability is not a 15-minute dependency of CRL freshness (D7). Wave 1 designs the buffer: where it is held, its bound, and what a server restart does to it. Whatever bound it sets, buffered rows are never lost silently: an overflow, or a restart (a crash included) or leader change with rows buffered, leaves a durable record of what was lost (how many rows, over what time) and pages. The record is not written by the failing path: it is derived at the next start or leader change, by reconciling the durable `ca_crl_versions` rows against the audit rows that exist, or the buffer is itself durable. A design whose only evidence of loss is a log line or a counter held in memory does not meet this. Wave 1 also decides whether automated certificate renewal fails closed on audit failure; if it does, audit availability joins the CA key, the Postgres write and the leader as a dependency of renewal, and that audit write must not wait for a standby either.

## Obligations the waves carry

Each line is something the named wave must state, decide or test. None is decided here.

**Wave 0**
- A committed script defines the D14 measurement method.

**Wave 1**
- The renewal port and the credential a renewal presents.
- Renewal of gateway and server leaves, with credential hot reload on both.
- Renewal jitter, so renewals do not bunch.
- What an agent that has neither a machine certificate nor an enrollment token uses to return when its certificate has lapsed: after any lapse from wave 1 until wave 2 ships own-key renewal, and after a lapse of more than 30 days from then on (D6).
- The clock-skew tolerance on every certificate and CRL check.
- How the trust domain (the generated UUID, or the operator's name set at first boot) is stored, backed up, and shared between servers, and the documented migration that changes it (D3).
- How a gateway's CRL pull is authenticated.
- The enterprise prerequisites for importing a customer intermediate, and for automated renewal under it: the enrollment protocol, the outbound flow and ports to the corporate CA, custody of the enrollment credential, the CA template and the approval lead time (D4); and whether operator-supplied gateway and server certificates from a CA Yuzu does not issue under stay supported on the gateway-to-server hop (D1, Open questions).
- The runbooks: restarting gateways during a CA outage (D7); signing the offline root's CRL and rotating an intermediate (D4, D7); changing the trust domain (D3).

**Wave 2**
- The enrollment sequence: the CSR; which trust anchors admit a machine certificate; the challenge, single-use and with an expiry; and how an unenrolled agent trusts the gateway.
- How agents find an open enrollment port.
- The fleet-recovery runbook after a long outage: the 30-day own-key window, mass re-enrollment, and enrollment-port capacity (D6).
- Where a gateway's zone comes from until wave 4 puts it in the certificate, and the per-listener TLS version setting that follows from it (D8).
- How the agent obtains the signing server's certificate and the issuing chain, how it refreshes them across a server-leaf renewal and an intermediate renewal or rotation, and how often it receives the CRL when the gateway list is unchanged (D5).
- The gateway closes an agent's connection when the server ends a revoked session.
- `forwarded_for` cannot work on a strict main port, and PROXY protocol must be parsed before the kTLS handshake.
- How a response carrying a signed result, the signing certificate's `ca_issued` record and the issuing intermediate's certificate are kept for the 13-month evidence window when the response retention setting is shorter, and the export to the customer's archive (D5).
- How agents already running behind a gateway get the wave-2 agent binary. Nathan Dornbrook confirms the pilot check before wave 2 merges (decided 2026-10-30), and the wave 2 PR description records his confirmation and its date.

**Wave 4**
- The rolling-restart runbook: drain before stop, the stop grace, and how long restarting N gateways takes (D11).
- Refusing to drain the last gateway.
- What aborting or extending a drain does to agents already moved.
- Operator surfaces for gateway drain and server drain: REST and MCP, with a dashboard twin, a securable, a step-up row and audit, plus read access to the gateway list (ADR-1005).

**Wave 5**
- The source of ring membership and its hysteresis.
- Re-attestation when an agent's owning server changes.

**Wave 6: replication observability**
- Per-standby replication lag (bytes and seconds), the standby count and which standbys are synchronous, and the failover lag cap, as metrics. Each failover leaves an audit record and log line with the old primary's last position, the promoted position, the gap and the timeline change, so an operator can learn how much a real failover lost. Pages only when the primary is unreachable (or its writes are blocked under strict mode) and no standby is promotable, because someone must then act; no promotable standby while the primary is healthy opens a ticket; lag below the cap is a dashboard, and a completed failover that lost writes opens a ticket, not a page.

**Observability and readiness (waves 1 to 5, each for what it adds)**
- Metrics for CRL age, fail-closed state, refusals by reason, CA signing rate, enrollment-port saturation, certificate-expiry horizons, drain progress, drains that ended at the hard deadline with agents still attached (a ticket), bare stops that ran a fast drain, and ring membership. A gateway or server certificate renewal that keeps failing pages, as does a gateway or server certificate with less than a quarter of its lifetime left; the expiry horizons themselves, and agent certificate expiry, are a dashboard. These replace the existing day-band rules for gateway and server certificates (`YuzuCertificateExpir*`, `YuzuGatewayCertificateExpir*`, warning from 30 days), which would fire without end on a 7-day certificate. An intermediate renewal that keeps failing escalates (D4), timed against the issuance cutover (notAfter minus 7 days), not against notAfter: a ticket first, then a page that lands before the cutover, whose responder action is the manual CSR. CRL age is exported per issuer. If wave 1 makes a lapsed root CRL fail gateways closed, the root's CRL has an escalating alert timed against its nextUpdate, and the responder action is the offline signing procedure wave 1 writes (D7). Each page names the responder's action.
- Alerts from wave 1: entry into fail-closed pages before wave 4 (no weight zero yet), and from wave 4 only when the gateways still ready cannot carry the agents (one gateway failing closed among others with spare capacity opens a ticket; time in fail-closed is a metric, and the page closes on exit); so does a gateway CRL nearing the 15-minute fail-closed bound, because someone must restore the gateway's path to a server or the CRL signer. A condition seen on many gateways at once (a stalled signer) pages once for the fleet, not once per gateway. An audit write failing during a routine CRL re-sign pages once as one condition, not once per tick, and its page names the responder's action: restore audit writes, because until then no new revocation can be made. Buffered audit rows that are lost page, and the buffer's depth and age are metrics. A revocation refused for an audit failure or an unconfirmed standby is counted by reason and shown to the operator as not done (Audit and evidence).
- Clock health: agents counted by clock state (NTP-synchronised and agreeing; using server-signed time because NTP is unsynchronised or absent; using it because the clocks disagree) is a dashboard, and a fleet fraction in the last two states above a threshold wave 2 sets opens a ticket. Each server exports its clock offset against its time source, and an offset beyond the skew tolerance pages, because every agent follows signed time (D6). A gateway that fails closed on its own clock says so in its alert (D7).
- Readiness: a fail-closed or draining gateway is not ready for new agents but stays live. From wave 4 a fail-closed gateway also has weight zero in the gateway list until it has a fresh CRL (D9). Until then, readiness is the only steer: a load balancer stops sending agents to it, but a gateway found by DNS still draws agents, which are refused and retry.

## Alternatives considered

- **One port that asks for a certificate but does not require one, at the agent edge.** This is what direct agent-to-server connections use. Rejected: every request needs a "did this connection present a certificate?" check, and one missed check is a hole. A separate port gives a guarantee the TLS layer enforces.
- **The customer's machine certificate on the main port.** Rejected for now. It ties certificate lifetimes, naming and revocation to the customer's PKI, needs a second path for customers without one, and runs into gRPC's PEM-only client key.
- **The gateway vouches for the agent, and the server trusts it.** Rejected: an internet-facing gateway that is compromised could impersonate every agent behind it.
- **Gateway-held per-agent state, or gateway links across communication domains.** Rejected: membership in an Erlang cluster is full control of every member, so a link never crosses a zone or an organisation (D10), and per-agent state at the gateway breaks free gateway choice. Fleet-level state any gateway could rebuild is allowed (conflict 5).
- **A per-session key between agent and server, with a MAC on every message, for D5.** Rejected: it does not survive a command sent by another server or a result redelivered through another gateway, and it proves nothing to a third party (D5).
- **The suggested-gateway list inside the GOAWAY frame, for D11.** Rejected: GOAWAY debug data carries no meaning by RFC 9113, and the agent's gRPC stack does not expose it.
- **OTP `ssl` as the default.** Rejected by the owner, on the measured memory and handshake rate. It is kept as the fallback and as the reference the shared test suite compares against.

## Consequences

- The release that ships wave 2 breaks every existing agent-to-gateway deployment: new port, new certificates, agents re-enroll. This is acceptable only because there are no production customers at the time of writing (2026-10-30); before wave 2 merges Nathan Dornbrook confirms that no pilot runs agents behind a gateway (D2), and if a pilot runs agents through a gateway the upgrade note becomes a merge gate.
- Wave 1 ships with an upgrade section in `docs/user-manual/upgrading.md`: what an install already past its first boot does at its first start on wave 1 (its trust domain, its issuing intermediate, and the leaves its root signed before); the move of the CA keys off the volume the gateway mounts, with the matching Compose file changes; and the gateway's move from pins to CA trust. It also ships a changelog fragment marked Breaking if any of these stops a running install.
- Wave 2 ships with an upgrade section in `docs/user-manual/upgrading.md` (the new enrollment port and its firewall rule; TLS 1.3 on internet-facing main ports and how a gateway's zone is set (D8); the upgrade order server, then gateway, then agents; re-enrollment and its prerequisites; roll-forward), a changelog fragment marked Breaking, and an update to `docs/user-manual/gateway.md`'s "Moving the agent edge to mutual TLS". The upgrade section also covers: load balancers and inspecting proxies in front of the main port must pass TCP through, since the gateway terminates mutual TLS; the machine-certificate prerequisites for enrollment by machine certificate; the agent's clock and NTP requirement (D6); and DNS discovery (D9).
- The CA signs far more often: each agent renews every 12 hours instead of about every eight months. At 1.2 million agents that is about 28 signatures per second, around the clock, before any mass re-enrollment. Its signing path, its `ca_issued` table and its CRL size must be measured before wave 2, not after. Nothing prunes `ca_issued` today, and D5's 13-month window keeps the record of every certificate that signed a kept result: at 1.2 million agents renewing twice a day, about 950 million rows, each with its PEM. Wave 1 sizes the table for that, and the passes that prune non-revoked `ca_issued` rows and `ca_crl_versions` rows follow the clock-guarded retention row of `.claude/routed-concerns.md`, and none removes a record, or a superseded intermediate's certificate, that a result still inside D5's 13-month window needs.
- The gateway gains C code that faces the internet. The fuzzing, ASan and advisory-tracking requirements in D8 are permanent.
- `docs/pki-architecture.md`, `docs/user-manual/gateway.md`, the reference composes and other compose files, the compose wizard, the agent and gateway installers, the gateway `sys.config` files and the environment examples all change with waves 1, 2, 4, 5 and 6.
- Wave 4 ships with an upgrade section: the 11-minute gateway stop grace on the customer's platform (Compose, systemd, Kubernetes, and container platforms that cap the grace below it), how a gateway learns the grace it has, and how long a rolling restart now takes (D11).
- The customer assurance package and shared-responsibility answers change with waves 1, 2 and 4: TLS 1.3 only on internet-facing gateways, the revocation bounds, CA key custody, the gateway reading commands and results in plaintext, the asynchronous replication loss, the 13-month evidence window, and `agent_id` as personal data. `docs/enterprise-readiness-soc2-first-customer.md`'s data-governance and retention tables (the response store's 90 days, the PKI inventory) change with wave 2, as do the manual's response-retention and privacy pages and any data-processing terms that state retention.
- The 13-month window sizes the response store as well as `ca_issued`: wave 2 measures the response volume it keeps at fleet scale.
- Replacing the day-band certificate alert rules (Observability) is an alerting change operators see; the wave that replaces them carries a migration note.
