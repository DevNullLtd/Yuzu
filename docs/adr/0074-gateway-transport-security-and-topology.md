## Context

### What runs today

| Hop | Today | Gap |
|---|---|---|
| Agent to server, direct | Mutual TLS. The agent presents its CA-issued leaf (`yuzu://<ca-fingerprint>/agent/<id>`, about a year, renewed at two thirds). Under the generated default certificates the port asks for a certificate but does not require one, so an unenrolled agent can bootstrap; the application enforces the rest. With operator-supplied certificates the port requires one (`server/core/src/grpc_tls_credentials.cpp`, `server.cpp`). | Only single-server installs use it. ADR-2002 section 2 makes the gateway mandatory in HA. |
| Agent to gateway (`:50051`) | One-way TLS (PKI PR5c). The gateway proves itself; it does not check the agent's certificate. The agent proves itself with its enrollment token, and heartbeats are bound to its Subscribe connection. | No transport identity for the agent at the edge that will face the internet. The enrollment token is presented only at first enrollment: the agent removes its token file once a registration is accepted (`agents/core/src/agent.cpp`), so after that an approved agent's `ProxyRegister` carries no per-agent secret. Revoking a gateway-proxied agent does not cut it off (`docs/auth-architecture.md`, "Gateway-proxied agents: revocation scope"). |
| Gateway to server (`:50055`) | Mutual TLS. The server admits the gateway by an SPKI pin fixed at boot. | Pins are per pair and do not scale to many gateways and many servers. No revocation. |
| Server to gateway management (`:50063`) | Strict mutual TLS. SPKI pin, or (opt-in, #6016) the server's URI SAN `yuzu://<install>/server` (the install id is derived from the CA fingerprint). | No CRL; a manual serial deny-list (`mgmt_peer_denied`) read at boot. Pins again. |

So gateway and server already authenticate each other in both directions. The missing link is the agent at the gateway.

### Why it matters now

- **Scale.** ADR-0069 sets 1.2 million agents and 100,000 per gateway.
- **SaaS.** In SaaS installs, gateways will face the internet. A compromised or impersonated gateway must not be able to act as an agent. **One install may host several customers (decided by Nathan Dornbrook on 2026-10-30).** **Yuzu also ships single-tenant installs, one customer per install, the on-premises norm (decided by Nathan Dornbrook on 2026-11-01).** One tenant boundary serves both modes (D3). The tenant is designed as a security boundary for identities, CRLs and revocation, routes, gateway domains, RBAC and dispatch, stores and audit. Identities, CRLs and revocation, routes and gateway domains carry it from waves 1 to 4 (D3, D5, D7, D9, D10). The RBAC, dispatch, store and audit walls do not exist until the tenancy ADR's walls are built, so single-tenant installs are the only supported mode until then (Consequences).
- **Customers' PKI.** Most target customers already deploy a machine identity certificate (on Windows, in the certificate store behind CNG, often non-exportable or in the TPM). The direction of travel is SPIFFE/SPIRE for workload identity and RATS for attestation.
- **Topology.** The product needs agents that know several gateways, gateways that can be drained for maintenance, and gateways that use several servers writing to replicated Postgres (ADR-2002 section 7g).

### Measurements behind the transport choice (rocky9, 2026-10-28)

These come from branch `perf/gateway-idle-mem-ktls` (a kTLS handover NIF) and are not yet in the repository. Wave 0 commits the measurements the waves gate on to the repository, as an artefact, before they gate anything.

| Measure | OTP `ssl` | kTLS NIF |
|---|---|---|
| OS anonymous memory per idle agent (100 Windows agents, TLS 1.2) | 85.0 KB | 48.1 KB |
| Processes per agent | 6 | 3 |
| Handshakes per second, 4 cores | about 2,500 to 3,000 | about 6,000 to 6,600 |

The kTLS NIF was fuzzed for 91.2 million executions (92% line coverage, one bug found and fixed) and ran clean under ASan inside the BEAM. It can verify no peer certificate today.

## Decision

### D1. Gateway and server: CA trust, then identity, then revocation

All three, in this order:

1. **Trust our CA, not per-pair pins.** Gateways and servers admit each other by a certificate chaining to the install CA (or the customer's intermediate, D4). SPKI pins stay as an optional extra, not the default.
2. **Identity in the certificate.** Every certificate carries a URI SAN that names the role and the instance (D3). Each side checks the role it expects: a gateway is not a server, and an agent is neither.
3. **Revocation.** Every hop checks the revocation list (D7).

### D2. The agent edge: a separate enrollment port, and a strict main port

- **Main port.** It requires a valid client certificate at the TLS layer. A connection without one never reaches application code.
- **Enrollment port.** It accepts connections without a certificate, and the only thing it serves is enrollment. It has its own rate limit and connection cap at all times. The port is certless and faces the internet, so its cap must not be holdable by clients that never enroll: wave 2 must show that per-source limits (or an equivalent) keep it usable, and set a recovery target for a mass re-enrollment after an outage longer than a day.
- **Clean break.** This ships as a breaking change in the next release, with no fallback to the single-port behaviour. There are no production customers at the time of writing (2026-10-30). Before wave 2 merges, Nathan Dornbrook confirms that no pilot runs agents behind a gateway, and the wave 2 PR records it (decided by Nathan Dornbrook on 2026-10-30); if a pilot does, the upgrade note becomes a merge gate.
- **A routed-concern rule changes with it.** `.claude/routed-concerns-access-control.md` (the PKI row) forbids an `auth_fun` on the `:50051` agent listener, because it would reject every certless peer and stop agent bootstrap fleet-wide. That rule exists because today one port does both jobs. The change that splits the ports must amend the row in the same PR, with `security-guardian`: certless bootstrap moves to the enrollment port, which must never require a certificate.
- **Open: the direct port.** Whether the direct agent-to-server port of single-server installs gets the same split into an enrollment port and a strict main port. Wave 2 decides.

### D3. Identities are SPIFFE IDs

The URI SAN takes the SPIFFE form, `spiffe://<trust-domain>/<role>/<name>`. Examples: `spiffe://<trust-domain>/agent/<agent_id>`, `.../gateway/<name>`, `.../server/<name>`. For an agent or a gateway the path also carries the tenant (below).

- **The tenant is in the path (decided by Nathan Dornbrook on 2026-10-30, with multi-tenant hosting).** An agent or gateway identity takes the form `spiffe://<trust-domain>/tenant/<tenant_id>/<role>/<name>`, for example `.../tenant/<tenant_id>/agent/<agent_id>`. A server serves every tenant of the install, so its identity carries no tenant. `<tenant_id>` is an opaque id the server assigns, never the customer's name, because the certificate is visible on the wire wherever TLS 1.2 is allowed (D8). The CA takes the tenant from the server's record of the agent or gateway, never from the request, and a renewal keeps it. At enrollment the server assigns an agent's tenant from the tenant recorded with its enrollment credential, never from the request; a single-tenant install has one tenant, so nothing is chosen. Wave 2 states how an enrollment credential names its tenant, and wave 1 states how a gateway's tenant record is created. **What a tenant id is, and where it is kept (decided by Nathan Dornbrook on 2026-11-01, before wave 1):** a tenant id is a random UUID with a display name, kept in one Postgres `tenants` table that every agent and gateway record references. Only the UUID enters an identity; the display name stays in the table and never appears in a certificate. A single-tenant install has exactly one row. The tenancy ADR builds on this table before wave 4, with no later migration. One trust domain still covers the install: a trust domain per tenant would give each tenant its own CA and bundle, which the tenancy ADR may still choose, but D3's install UUID stands until it does. Wave 1 issues the tenant segment from the start, and creates the install's first tenant id at first boot together with the trust domain, so that admitting a second tenant later is not a second identity migration (one URI SAN per certificate, below). Every check of an agent or gateway identity compares the tenant segment byte-exact, like the rest of the path.
- **Two install modes, one tenant boundary (decided by Nathan Dornbrook on 2026-11-01; amends the decision of 2026-10-30).** Yuzu ships single-tenant installs (one customer per install, the on-premises norm) and multi-tenant SaaS installs. The tenant boundary is designed once and applies in both. A single-tenant install is exactly one tenant: the id created at first boot (above) is its only tenant, and every identity, CRL scope (D7), communication domain (D10) and route claim (D10) carries that one id. Its operators configure nothing about tenants and see no change in behaviour: no tenant setting, no tenant choice at enrollment, revocation or drain, and no cross-tenant machinery to set up. The operator never sets or chooses the id; it appears in certificates, in signed messages and in the server's record, never as a setting. Every tenant check still runs in a single-tenant install, and always matches, so the two modes run the same code. A multi-tenant install differs only in holding more than one tenant, which needs the tenancy ADR's walls first (Consequences).

- **The trust domain (decided by Nathan Dornbrook on 2026-10-29)** is a random UUID generated once at install. The operator may set their own name at install time only; it never changes afterwards, except by a documented migration. It is not derived from the CA fingerprint: rotating the CA, or importing a customer intermediate (D4), would then rename every identity in the fleet. The SPIFFE standard itself advises a random name such as a UUID when no operator chooses one.
- **How an install sets its own trust domain (decided by Nathan Dornbrook on 2026-10-30):** an environment variable, with a matching Compose Wizard field, read only at first boot and locked afterwards. A different value at a later start stops startup with a clear error; an unset variable at a later start uses the stored domain. Changing the domain is the documented migration, never a setting. The value must match the SPIFFE trust-domain grammar (lowercase letters, digits, `.`, `-` and `_`); any other value stops first boot.
- **An existing install's first start on wave 1 counts as its first boot (decided by Nathan Dornbrook on 2026-10-31).** It reads the setting, or makes a fresh random UUID, then locks the trust domain, and it creates its issuing intermediate (D4), unless the install is already in subordinate mode (see Open questions), and its first tenant id (above), as a new install does. The new trust domain has no link to the existing `yuzu://<install>` code, whose install id comes from the CA fingerprint. In the same migration, every existing agent and gateway record is bound to that first tenant id, once, and the binding is audited. The lock, the first tenant id and every migration binding commit in one transaction, with the durability D13 requires of tenant bindings. That transaction has one winner across server replicas started together (for example a fleet-wide advisory lock or a singleton-key insert, re-reading the lock once held): a replica that loses adopts the stored trust domain and first tenant id and binds nothing. Wave 1 tests concurrent first starts, and states what startup does when that transaction's audit write fails, when no standby confirms it, and at fleet scale (Open questions). Wave 1 tests a failover right after the migration. D13's rule that a missing binding is refused applies after that migration, never during it. So a single-tenant install sees no change in behaviour (this carries the decisions of 2026-10-31 and 2026-11-01 above).
- **One URI SAN per certificate.** The SPIFFE X.509 standard says a verifier must reject a certificate with more than one. So the existing `yuzu://<ca-fingerprint>/agent/<id>` and `yuzu://<ca-fingerprint>/server` URIs cannot sit beside the new ones in one certificate. The migration is: verifiers accept either form for a window, then issuance flips to `spiffe://`. **The window ends at wave 2 (decided by Nathan Dornbrook on 2026-10-30):** from wave 2, verifiers accept only the SPIFFE form. Before wave 2 merges, a check shows that no server certificate, gateway certificate or management-port pin still uses `yuzu://`. An agent leaf issued before wave 1 still carries `yuzu://` for up to a year; wave 2's re-enrollment (Consequences) replaces it, and the upgrade section says so. The CA alone chooses the SAN; a requester never does (`sign_agent_csr` already ignores the CSR's subject and SAN).
- **The role comes from the SPIFFE path, never from the EKU.** The same standard says that when a leaf carries an EKU it must list both `serverAuth` and `clientAuth`. So every leaf carries both, and the EKU no longer tells a gateway from a server or an agent. The management port's existing `serverAuth` check still passes; it simply stops being a role check.
- A SPIRE server can later replace the issuer without changing what the main port checks.

### D4. Who issues the main-port certificate

- **Yuzu issues it**, always, as a short-lived certificate with a SPIFFE ID (D6).
- **The customer's machine certificate is an enrollment credential only.** On the enrollment port the agent proves it holds the machine certificate by signing a server challenge through the platform key store (Windows CNG, macOS Keychain, Linux file or PKCS#11). That signature is application-layer, so a non-exportable or TPM-held key works. It does not need gRPC to hold the private key.
  - This matters because gRPC 1.76 (the vcpkg pin) takes the client key as PEM and has no public private-key signing hook. So the machine certificate cannot be presented on the main port as it stands.
- **The enrollment token stays a supported credential** for machines without a machine certificate.
- **Customer PKI as the root of trust:** a customer may import an intermediate CA signed by their own root, and Yuzu issues from it. Customer-issued main-port certificates (the customer's CA issuing to agents directly) are not offered at first, and the design must not rule them out; until a later decision offers them, every leaf is Yuzu-issued (below).
- **Operator-supplied certificates only through subordinate mode (decided by Nathan Dornbrook on 2026-11-01).** An operator who wants their corporate CA in the chain uses subordinate mode: the corporate CA signs Yuzu's intermediate, and every leaf is Yuzu-issued. Verifiers validate the full chain to the trust root configured for the install (the Yuzu root by default, the corporate root in subordinate mode), so a root-signed CRL that revokes an intermediate can be checked (D7); trust anchored on the intermediate alone would never consult it. Verifiers also refuse a leaf whose direct issuer is not one of Yuzu's issuing intermediates, matched by name and key, the old and the new one both during a renewal overlap (below). So a leaf the corporate CA mints directly, or through a sibling intermediate, is refused. Fully external server or gateway leaves, issued by a CA Yuzu does not issue under, are not accepted on any hop from wave 1. An install that uses operator-supplied server or gateway certificates today moves to subordinate mode at wave 1 (Consequences).
- **Default:** a customer who brings nothing gets a Yuzu-generated root and issuing intermediate (below).
- **An issuing intermediate in the default install (decided by Nathan Dornbrook on 2026-10-30).** The default install creates a root and an issuing intermediate at first boot, and only the intermediate signs leaves. **By default the root key stays online, behind `KeyProvider`, and the intermediate renews itself automatically before it expires (decided by Nathan Dornbrook on 2026-11-01).** Keeping the root offline or in an HSM is an opt-in, with manual renewal ceremonies and alerts months ahead of the intermediate's expiry. Wave 1 states the default intermediate's lifetime and renewal lead time, the schedule of the root's CRL, and what an operator who opts into an offline root must do for both. No HSM `KeyProvider` exists today (`FileKeyProvider` only); wave 1 states whether it adds one.
- **Key custody.** The issuing intermediate's key and the root's key must never sit on a volume, host or container a gateway can read. Today the reference gateway rig mounts the `certs` volume, CA key included (mode 0600, owned by the server's user), into the gateway container; wave 1 states where both keys live, and where the secrets KEK that shares that volume lives. Until no gateway can read the issuing key, a gateway compromised to container root can sign certificates, and the limit D10 puts on a compromised gateway (it controls only its own domain) does not hold.
- **Intermediate renewal under a customer's root (subordinate mode) is automated (decided by Nathan Dornbrook on 2026-10-30).** Yuzu requests renewal from the corporate CA through a standard enrollment protocol (EST, ACME or SCEP, whichever the CA supports). The fallback is a manual CSR and an escalating alert. The old and new intermediates are both trusted during an overlap. In either mode, wave 1 states how the direct-issuer set reaches every verifier, agents included. Every verifier holds a new intermediate before the first leaf is issued under it, and a returning agent gets the current set, authenticated by the root, from the enrollment port. The set carries a version number that only goes up. A verifier refuses a set older than the one it holds, so a replayed set cannot bring back a removed intermediate. Wave 1 states whether the set also expires. Wave 1 tests a verifier whose set is out of date, and a replayed older set. No leaf outlives its issuing intermediate: issuance moves to the new intermediate at least one leaf lifetime (7 days) before the old one's notAfter. Wave 1 states the renewal lead time against that, and what happens if no renewal completes in time.
- **Later:** TPM or RATS evidence is added at the enrollment step.

### D5. Agent identity reaches the server end to end

The gateway checks the agent's certificate, but the server does not trust the gateway's word alone. The owner chose this so that a compromised internet-facing gateway can drop or delay traffic but cannot impersonate an agent, or forge or alter what passes between agent and server.

**Decided on 2026-10-29.** Three kinds of signature, together:

1. **Per session.** The agent signs a server-issued challenge at the start of every session with its own key. The server verifies the signature against the certificate it issued, and refuses a revoked or mismatched agent.
2. **Every command** is signed by the server that issues it, with that server's own CA-issued key (its SPIFFE ID, `.../server/<name>`). The agent verifies it whichever server sent it and whichever gateway carried it.
3. **Every result** is signed by the agent. **The gateway list and drain suggestions** (D9, D11) are server-signed in the same way.

**Decided for ADR-0073 by Nathan Dornbrook on 2026-10-30, and binding here:** after a reattach the server sends a signed challenge, and the agent must answer it before its route is published or any command is routed to it, so a reattach never bypasses the per-session signature; and the agent signs its StatusTags deltas and its topology report, and the server rejects any that a gateway has altered (ADR-0073, PR #6704).

Each signature is over the whole message: for a command, the plugin, action and parameters; for a result, its status and payload; for the gateway list, the list itself. Each also binds the agent id, the agent's tenant, the command or execution id, the signer's identity and an expiry. The per-session signature covers the server's challenge. **Signatures are bound to the tenant (decided by Nathan Dornbrook on 2026-10-30, with multi-tenant hosting).** The agent refuses a command, gateway list or drain suggestion that names a tenant other than the one in its own certificate (D3), and the server refuses a result, session signature or route claim whose signed tenant differs from the tenant it holds for that agent, or from the tenant of the gateway that carried it (D10). Wave 2 delivers this binding for commands, results, session signatures and route claims; wave 4 for the gateway list and drain suggestion, which ship then (D9, D11).

**A server's signing key is revoked by the ban list only (decided by Nathan Dornbrook on 2026-10-30).** Server signing keys keep their normal lifetime (7 days, D6) and are not shortened. A revoked server key goes on the CRL; agents receive the CRL with their server-signed gateway list, and servers share it through `ca_store`. Wave 4 must make sure that a gateway list signed by a stolen key cannot bring back a CRL from before that key's revocation: the agent judges a CRL by the CA's signature and its number, never by the list that carries it. Wave 4 states whether the agent keeps its highest CRL number per issuer across a restart, and what freshness rule it applies to a CRL that arrives with a gateway list; a rule that resets on restart needs its own Accepted-risks row. **Agents receive the CRL with the server-signed gateway list from wave 4, not earlier (decided by Nathan Dornbrook on 2026-10-30).** The list ships in wave 4 (D9). In waves 2 and 3 a stolen server key is therefore bounded only by its 7-day certificate lifetime, even after it is revoked (Accepted risks). Wave 4 also states how soon after a server-key revocation the new CRL reaches every connected agent. **An agent holding an out-of-date CRL (decided by Nathan Dornbrook on 2026-10-30; from wave 4).** While its newest CRL is up to 7 days old (the server-certificate lifetime, D6), judged on the agent's clock rule (D6), the agent carries on. Beyond that it must fetch a fresh CRL before it obeys any command. Wave 4 states how the agent reports each such refusal (counted per gateway, shown to the operator as not done) and whether it then tries another gateway. A protective action still runs, subject to its signed expiry (below). The CRL reaches an agent through the gateway that holds it, so that gateway can withhold it. A stolen server key therefore stays usable until it is revoked and that revocation reaches the agents; for the agents of a gateway that withholds the CRL, until the key's certificate expires. That bound holds only if a key cannot extend its own life: wave 2 must ensure that no signed time decides the expiry of the key that signed it, and that signed time moves an agent's estimate only as D6 allows (the most recent fresh signed time, with a large forward leap held as suspect). D6's rule bounds forward leaps only; a backward move and a series of small forward leaps are recorded in Accepted risks (the server-signed time row).

A replayed command is a duplicate to ADR-2002 WS-0's durable command idempotency only while WS-0's terminal ring still holds it (a bounded ring, `kMaxDedupRows` in `command_dedup_store.hpp`), and only while the agent's dedup store is healthy: a degraded store fails open by design (`docs/command-dedup.md`). The ring is bounded by count, not by time, and evicts in claim order, not signing order, so no fixed expiry is guaranteed to stay inside it. Wave 2 must design and test a replay bar that still holds after a row is evicted, after the store is recreated, and when the agent's clock is skewed, using only times the server signs; this ADR does not choose the mechanism. While the store is degraded, wave 2 must either refuse signed commands outside the protective set or record that residual; a protective action is never refused because the store is degraded (below). The protective set (`common/include/yuzu/protective_actions.hpp`) passes every enablement gate, but `quarantine`, `unquarantine` and `whitelist` each change a device's containment or allow-list, so a replay of any of them can loosen containment; and no `__guard__` dispatch takes the dedup claim, even with a healthy store, so the dedup store gives it no replay bar; its signed expiry acts as one (below). Wave 2 must give these actions a replay bar that does not depend on the dedup store; only `status` needs none. **That bar may refuse `quarantine`, `unquarantine`, `whitelist` or a `__guard__` dispatch only for a proven replay, never because a store is degraded (decided by Nathan Dornbrook on 2026-10-30).** A store that is degraded, unreadable or recreated, or a check that could not complete, is never proof; what counts as proof is wave 2's design, but proof may rest only on server-signed data and on agent-local state that wave 2 shows is healthy (never the degraded or recreated dedup store), so that nothing an on-path gateway can block or delay is needed to establish it (otherwise a gateway could make every replay unprovable, and so executed). Remembering a prior receipt needs agent-local state; server-signed data alone can show only that a command is superseded or stale (for example, through a signed per-device containment generation). **A signed expiry counts as proof of replay (decided by Nathan Dornbrook on 2026-10-30):** it may refuse all four protective actions (`quarantine`, `unquarantine`, `whitelist`, `__guard__`), and all four are treated alike. Expiry is judged against server-signed time, as the replay bar above already requires, never against a device clock that has not been checked. D6 sets the rule: the agent uses its own clock only when the OS reports NTP-synchronised and that clock agrees with the server-signed time; otherwise it uses the most recent server-signed time, advanced by the time elapsed since it arrived, which a gateway can neither replay nor freeze. Accepted consequence: a device whose clock is badly wrong may refuse a genuine lockdown (Accepted risks). A protective action whose replay cannot be proven, inside its validity window, executes (accepted by Nathan Dornbrook on 2026-10-30; Accepted risks); wave 2 sets the expiry length, longer than the clock-skew tolerance and the delivery delays the design creates (a drain window, D11; a re-drive, wave 4). A re-drive re-signs the command with a fresh expiry rather than resending an expired one, and only after re-authorising it against the issuing operator's current authority and the dispatch chokepoint (`dispatch_confined_arms`); a re-drive refused that way is shown to the operator as not done. It is re-driven only while no later containment-changing action (`quarantine`, `unquarantine`, `whitelist`) has been issued for that device, judged against the device's durable `QuarantineStore` record (which D13 keeps across a failover), never the command outbox (for example, by a signed per-device containment generation); a `__guard__` dispatch is superseded only by a later `__guard__` push to that device. A re-driven `quarantine` or `whitelist` carries the stored allow-list and reason (`redispatch_stored_containment`), never the original command's parameters. A superseded one is dropped and shown to the operator as superseded; that is a dispatch decision, not a refusal by an enablement gate. A refusal for a proven replay (a signed expiry included) is the single exception to the rule that no enablement gate may refuse a protective action (see Rules this design re-opens). If the agent refuses a containment action, the server's quarantine record must not show a state the device is not in: today the server's release of a quarantine record does not depend on any agent answer (`release_device`, called from the REST release route). The expiry also bounds how long a gateway can hold back a command, a protective action included. Liveness heartbeats stay unsigned.

Why signed messages rather than a key agreed per session with a MAC on every message: any server may send a command straight to the gateway that holds the agent (D12), and a drained agent delivers its result through another gateway, in another session, possibly to another server (D11, D12). A signed message survives both unchanged; a per-session key would have to be shared between servers, which is a new secret store. A signed result kept in Postgres is also evidence anyone can check later from the agent's key, which a MAC is not. The survey below found the same rule elsewhere: a relay that must read, store and forward messages (TUF mirrors, Tailscale's Tailnet Lock key distribution) uses signed messages; a relay that moves opaque bytes (WireGuard through Tailscale's DERP relays, SSH through Teleport's proxy) uses a per-session key.

**What D5 deliberately does not give, stated plainly:**
- **Confidentiality from the gateway.** The gateway still reads commands and results in plaintext. Hiding them would need encryption to the agent's key, a separate decision for SaaS.
- **Honest heartbeats.** A compromised gateway can report a dead agent as alive. The lie lasts until the next signed result or the next session start.

**Signed-result evidence window (decided by Nathan Dornbrook on 2026-10-30): a fixed 13 months,** one SOC 2 audit year plus a month. **What the window keeps (decided by Nathan Dornbrook on 2026-11-01, refining that decision).** The context is regulated financial-services customers under SOC 2 Type 2, whose auditor samples control evidence from across the audit year and must be able to read it.
- **Control-evidence results are kept in full, signed, for 13 months:** the results of mutating and protective commands, policy remediations and compliance verdicts, and who ordered each (the dispatch and audit records, whose retention matches, Audit and evidence). Wave 2 states how a result is classed as control evidence, derived rather than hand-kept (for example, from the capability catalogue: every pair not classed read-only, and the protective set), and every result produced for a policy check or compliance verdict is control evidence, whatever the pair's class.
- **Routine results keep the response retention setting (90 days by default), with a 13-month signed receipt:** the result's hash, its signature and its signing certificate's record. The receipt proves that a copy kept elsewhere is the result the agent signed.
- **Every result can also be streamed to the customer's own archive** (SIEM or WORM storage), for rules longer than 13 months.

Within the window, what a kept result or a receipt needs to be checked is kept too, whatever the response retention setting: the signing certificate's `ca_issued` record, and the certificate of the intermediate that issued it (kept after any D4 renewal or rotation). The registry plugin's writes are mutating, so their responses, `old=`/`new=` values included, are control evidence and kept 13 months; a Forensics read is routine and keeps only its receipt past the response retention. Wave 2 states the export's permission (the stored-response read gate through the list-read chokepoint `authorize_list_read`, filtered to the caller's per-agent confinement, plus the Forensics tier for Forensics rows), its REST and MCP twins and step-up classification (ADR-1005), the audit row it writes (who exported which range), which fails closed and an integrity check that shows the archive is complete. The response pruner is a wall-clock bulk delete, so it follows the clock-guarded retention row, and it keeps what a control-evidence result or a receipt inside the window needs (the result or receipt, its `ca_issued` record, its issuing intermediate's certificate, and the CRL versions that show its revocation status when it was signed).

**To measure in wave 2:** the agent's cost of signing each result, and the server's verification rate, at the result rate of the 5,000-agent rig, alongside D14's handshake budget.

### D6. Certificate lifetimes and revocation

- **Agent certificates** last 24 hours and are renewed at half-life. At 100,000 agents per gateway, renewing every 12 hours, that is about 2.3 renewals per second per gateway.
- **Expired certificates.** An agent whose certificate expired (a server outage longer than a day, or a laptop off over a weekend) cannot use the main port and must go back through the enrollment port. The agent decides that its certificate has expired from its own leaf's notAfter (judged by the agent's clock rule below), never from a TLS alert: a gateway holding a stale CRL also refuses it, and treating that refusal as expiry would send the whole fleet to the enrollment port while the CA is stalled. Wave 2's chaos tests must show that a stale gateway CRL causes no re-enrollment. **A recently expired certificate may renew there on its own key for 30 days after its notAfter (decided by Nathan Dornbrook on 2026-10-30),** and only if the append-only revoked set and the agent DENY show no revocation. After 30 days the agent must re-enroll with an enrollment token or a machine certificate. Wave 2 must measure a mass re-enrollment after an outage. Prior art for renewing on its own key: Teleport's bound-keypair joining, where a bot whose certificates lapsed signs a server challenge with its bound private key, a generation counter refuses a cloned credential, and automatic recoveries are capped.
- **Renewal generation counter (decided by Nathan Dornbrook on 2026-10-31).** Each agent renewal carries the next number in a per-agent sequence, a renewal on an expired certificate's own key included. The server keeps the latest number per agent, refuses a renewal that repeats it or goes backwards, and raises it as a possible clone (Observability). The counter row is a store that must survive a failover (D13). Wave 1 adds the counter with renewal, and states where the agent keeps its number.
- **Gateway and server certificates** last 7 days, on the same revocation list.
- **Revocation scope, not yet settled.** With renewal at half-life an agent holds two valid leaves for about 12 hours, so revoking one serial leaves the other valid. Today's block on re-issuing to a revoked agent (`server.cpp`) lasts until the revoked certificate's notAfter, so with 24-hour certificates it lapses within a day instead of about a year. And with CRL pruning (D7) plus renewal on an expired certificate's own key, a revoked and expired agent is on neither list. Wave 1 must state the revocation scope (every live serial of an identity) and what blocks re-issuance (the append-only revoked set and the agent DENY, never the published CRL). A revoke and a renewal of the same identity must not interleave so that the renewal escapes: a certificate issued while that identity's revoke commits is covered by it (for example, revoke and issuance take one per-identity lock, and issuance re-checks the revoked set and the DENY inside its own transaction). Wave 1 tests a revoke racing a half-life renewal; wave 2 tests one racing a renewal on an expired certificate's own key.
- These replace today's one-year agent leaf and the server and gateway leaves sized to the CA's life.
- **The agent's clock (decided by Nathan Dornbrook on 2026-10-30):** the agent trusts the server's signed time, and also checks that the OS has an accurate NTP service. This is the wave-2 requirement that follows from that decision, to be confirmed in wave 2:
  - every session, and every answer on the enrollment port, carries a server-signed time;
  - the agent also reads the OS time-sync state, through a direct interface before a subprocess (ADR-3002's acquisition ladder; for example the kernel's synchronisation status through `adjtimex` on Linux, or the W32Time status on Windows); any subprocess it runs needs a row in `docs/agent-spawn-sink-manifest.md`, and a probe only reads the state (`sntp`, for example, sends its own NTP queries);
  - when the OS reports NTP-synchronised and the agent's clock agrees with the signed time within a tolerance, the agent uses its own clock;
  - when NTP is unsynchronised or absent, or the two disagree beyond the tolerance, the agent judges expiry (its certificate's, and a signed message's, D5) against server-signed time only, advanced as the next sub-bullet requires, and ignores its own clock entirely: it never takes the later of its own clock and the signed time (decided by Nathan Dornbrook on 2026-10-30). It reports a clock-skew or NTP health signal to the server, which operators can see.
  - whatever wave 2 confirms, a gateway must not be able to replay an old signed time or freeze it by forwarding no newer one, or the expiry no longer bounds how long a gateway can hold back a command (D5). For example: the signed time answers a nonce the agent chose, and the agent adds the time elapsed since it received it on a clock that keeps running through sleep (`CLOCK_BOOTTIME` or the platform's equivalent, which on Windows is not `QueryUnbiasedInterruptTime`), also through a VM pause or snapshot restore, or the agent fetches a fresh signed time after one. An agent with an untrusted clock that the main port refuses fetches a fresh signed time from the enrollment port before it decides its certificate has expired.
  - a server's clock can be wrong too. **The agent follows the most recent signed time it has received, not the highest it has seen (decided by Nathan Dornbrook on 2026-10-31).** So agents that followed a server with a fast clock come back when it is corrected (a large backward correction once a second server confirms it, below), and do not go on refusing genuine protective actions as expired or deciding their certificates have expired. The most recent means the most recently received fresh signed time (one answering a nonce the agent chose, above), so a gateway cannot move the estimate back by replaying an older one. **A signed time that leaps more than 1 hour beyond the time elapsed since the previous one is held as suspect, and not used, until a second server confirms it (decided by Nathan Dornbrook on 2026-10-31).** The 1-hour rule catches one large leap, not a series of smaller ones from a server that stays fast or from a stolen server key; the next signed time from a correct server corrects that drift, unless a gateway carries only the bad server's times (D5's withholding case), or the drift the agent followed exceeds the backward cap (below), when that correction is itself held until a server other than the drifting one confirms it. **A signed time that moves the estimate backwards by more than a set step at once is held as suspect, and not used, until a second server confirms it, mirroring the 1-hour forward hold (decided by Nathan Dornbrook on 2026-11-01).** The step is a few minutes; wave 2 sets its exact value and proves it with a Done-when test. In a single-server install, where no second server exists to confirm, an agent held on an unconfirmed step (a backward step past the cap, or a forward leap past 1 hour) counts toward one fleet-level operator alert whose action depends on the direction (Observability). Wave 2 also covers an install with more than one server where the only server that could confirm is the one whose clock drifted (Open questions). Until wave 2 settles what confirms a step there (Open questions), an agent held ahead of real time by an unconfirmed backward step refuses genuine protective actions as expired and treats its own certificate as expired. Both holds compare two signed times on one continuous boot clock; what they compare against after a reboot, a power-off or a snapshot restore is open for wave 2 (Open questions). A series of backward steps each within the cap, like a series of forward leaps each under 1 hour, is not caught. Both residuals are recorded in Accepted risks (the server-signed time row). Wave 2's chaos tests hold a server's clock forward for many signing intervals, then correct it, and step one forward by more than an hour.

### D7. Revocation at a gateway that keeps no state of its own

- The gateway pulls the revocation list from the server every 60 seconds and refuses revoked agents at the handshake. That stops a revoked agent before it costs a session, memory and an upstream call. Session resumption would skip that check, so the main port issues no resumable sessions, or revalidates the leaf on resumption exactly as a full handshake does (notAfter, the CRL, and the gateway's fail-closed state) and accepts no 0-RTT early data; wave 2 states which, on both TLS paths, and tests that a revoked agent cannot resume.
- It keeps the last good list if a pull fails, and fails closed (refuses new agent handshakes) after 15 minutes without a good pull, or sooner if the held CRL's nextUpdate passes first. A good pull returns a CRL signed within the last 15 minutes (by its thisUpdate) whose nextUpdate is still in the future: a pull that only returns the same list again, because the signer has stalled, is not one, whatever the list's nextUpdate. Fail-closed state, CRL age, their alerts and readiness all follow the same rule, so a stalled signer is seen even while pulls succeed.
- **The gateway's own hop must survive a stale list.** D1.3's revocation check on the gateway-to-server hop, combined with a stale CRL, could lock a gateway out of the server it needs for a fresh list. Wave 1 must show that a gateway with a stale list can still fetch a fresh one without skipping revocation for anything else: for example, an exemption limited to the CRL-pull call, which carries no commands, with the fetched CRL verified against the CA's signature before use, and accepted only if its CRL number is not lower than the highest the gateway has seen from that issuer (and, if equal, it is the same list) and its nextUpdate is still in the future, so a replayed older CRL is refused. Restoring `ca_store` from a backup must neither lower the CRL number, or every gateway would refuse every new list, nor re-use a number for a different list; wave 1 tests a restore. The 15-minute fail-closed refuses new agent handshakes. Because D10's distribution links check the same CRL, and OTP `ssl` refuses a certificate whose CRL is past its nextUpdate, it also refuses new gateway-to-gateway links: a cluster that loses a link during a CA outage longer than 15 minutes cannot re-form it until a fresh list arrives. Wave 4 states whether distribution links fail closed, or are exempted from the CRL's freshness only, still checked against the last good list and never exempted from revocation as the CRL pull is, and tests a link reconnect during such an outage.
- **Under several servers (D12),** the server that owns an agent's stream must learn of a revocation made on another server. How is not yet designed; wave 5 decides.
- The server ends a revoked agent's live session immediately.
- **The window a revoked agent still has, stated plainly:** up to one poll (60 s) when everything is up; about two minutes across a Postgres failover (D13's 60 s plus a poll), provided the revocation survives the failover (D13's requirement for revocation; a revocation the standby never confirmed is shown to the operator as not done, so they can re-issue it); up to 15 minutes when the gateway can reach no server, which is the fail-closed bound. The server's own check at session start (D5) closes it earlier whenever the server is reachable.
- **Two 15-minute clocks coincide:** the CRL's fail-closed bound and the gateway's CONNECTED resend, which slows after 15 minutes of refusals (`notify_unacked_slow_after_ms`). An outage of 20 to 30 minutes with revocation on must be tested.
- The list is the CRL `CaStore::publish_next_crl` already publishes (ADR-2002 section 8).
- **CRL signing becomes a 15-minute dependency, and it is decoupled from the standby (decided by Nathan Dornbrook on 2026-10-30).** A 15-minute nextUpdate (see the test below) means the server must re-sign the CRL at least every 15 minutes, so CRL freshness then depends on the CA key, the leader and a write to the primary. The signer re-signs with margin inside the nextUpdate, so a missed tick or a slow pull does not reach the bound, and each re-sign takes a new CRL number; wave 1 sets the period and the retention of `ca_crl_versions` rows at that rate. The period is chosen against failover time, plus the 60-second pull, plus the clock-skew tolerance between gateway and signer (wave 1 states that tolerance, since a good pull is judged by thisUpdate on the gateway's clock; a gateway whose own clock is off by more than the tolerance, in either direction, therefore fails closed while the signer is healthy, its fail-closed alert names the clock, and wave 1's chaos tests skew one gateway's clock both ways), with immediate retry on a failed tick. The server exports the age of its newest published CRL, and a ticket-level alert on that age fires before the gateway page does. Leadership is part of the dependency: a server becomes leader only by writing a new leader epoch (`leader_elector.cpp`), and the CRL tick runs only on the leader, so CRL re-signing must not depend on a leader-epoch write that waits for a standby. Waves 1 and 6 resolve this together with D13's leader-epoch requirement (for example, the CRL publish runs without the leader gate, since `publish_next_crl`'s table lock already serialises signers, or the epoch scheme does not wait). The first example, if chosen, re-opens clause (3) of the fenced leader election row and the CRL job's classification in `background_jobs.hpp`, and has every replica re-sign, so wave 1 sizes `ca_crl_versions` retention for that rate. Today the CRL carries a 7-day nextUpdate and is re-published about every 6 days, from a leader-gated tick (`crl_publisher.cpp`, `server.cpp`). Losing a standby, or a Postgres failover, must not make gateways fail closed: CRL signing never waits for a standby to confirm, whatever durability wave 1 gives revocation and issuance (D13), and whichever profile the operator chose, strict mode (`YUZU_PG_SYNC_STRICT=true`) included; under strict mode that means the CRL publish and any audit write it needs commit without waiting for a standby (for example with `SET LOCAL synchronous_commit = local`), and the leader-epoch write is resolved under D13's leader-epoch requirement, which a local-only epoch commit does not meet. A primary that stays unreachable past the bound, with no failover, still fails gateways closed; that is the 15-minute bound working as designed. Wave 1 designs the decoupling, and its chaos tests show a CRL signed and pulled within the bound with every standby lost, and across a failover; wave 6 repeats the standby-loss test with strict mode on. Open for wave 1: a server that checks gateway certificates against a stale list would drop its gateway connections and their live sessions too; wave 1 decides whether servers check the `ca_issued` revoked set instead of the published list.
- **The CRL number never goes backwards or repeats across a failover, and gateways stay stateless (decided by Nathan Dornbrook on 2026-10-30).** With asynchronous replication (D13) a failover can lose the `ca_crl_versions` rows of lists already published, so a number counted on from those rows could repeat one a gateway already holds, or go lower. Servers therefore derive the CRL number from the signing time, so it never repeats or goes back after a failover. Gateways keep, for each CRL issuer (the root's CRL over intermediates, and the CRL of each issuing intermediate over leaves, two of them during a D4 overlap; an issuer is its name together with its key, the CRL's authority key identifier, so an old and a new intermediate under one name keep separate numbers, and wave 1 tests an overlap where both sign in the same second), the highest CRL number they have seen from that issuer, in memory only, and accept no list from that issuer below it, nor a different list under the same number; RFC 5280 numbers CRLs per issuer. In memory means for the life of the gateway's node, not of the process that pulls: a crash and supervisor restart of that process is not a gateway restart and must not reset the number. A gateway that restarts trusts the first CRL it fetches from an issuing intermediate, provided that fetch is a good pull (above). A gateway that restarts while no good pull is possible starts fail-closed, without the 15 minutes its held list gave it. So restarting gateways during a CA outage takes them out of service; the runbook says so, and wave 1 tests a restart during a stalled signer. Separately, wave 1 sets the matching rule for the root's CRL, whose schedule is not 15 minutes. Gateways keep no state across a restart (conflict 5 is unchanged). Wave 1 designs the derivation and tests it on a failover that loses published rows. A number derived from time goes backwards if the server that signs next has a clock behind the one that signed last, so wave 1 keeps it above the last published number within the clock-skew tolerance, and tests it under skew. A clock that is ahead is the worse case: one signed list with an outlier number raises every gateway's highest number, and every later list is refused until that gateway restarts. Wave 1 bounds how far one list can move a gateway's number (for example, a gateway refuses a list whose thisUpdate is ahead of its own clock by more than the clock-skew tolerance, so an outlier never becomes its highest number), and tests a forward clock step on the signer followed by its correction. If wave 1 leaves a gateway restart as the recovery, that outage gets its own Accepted-risks row. The restart rule leaves a window, recorded in Accepted risks: a restarted gateway accepts any older list signed within the last 15 minutes whose nextUpdate is still in the future (the good-pull rule above).
- **Expired entries leave the CRL (decided 2026-10-29).** The published CRL drops a revoked certificate only after it has appeared on one scheduled CRL issued after its notAfter, as RFC 5280 allows. The revoked rows in `ca_issued` stay append-only, exactly as today: only the published list shrinks, never the table. With 24-hour agent certificates the list then only holds certificates revoked in about the last day. Even 1% of 1.2 million agents revoked in one day is about 12,000 entries, roughly 0.45 MB, so no delta or Bloom-filter form is needed. A mass revocation (every agent behind a compromised gateway, a fleet-wide re-key) is handled by rotating the issuing intermediate, not by growing the list. Today a default install has no issuing intermediate: it signs leaves from the Yuzu root, and Yuzu never signs CA intermediates itself (`docs/pki-architecture.md`). From wave 1 the default install has one (D4, decided by Nathan Dornbrook on 2026-10-30), so a mass revocation there is an intermediate rotation too, not a root rotation. A rotation cuts off the old intermediate's leaves only once verifiers stop trusting it: the root signs a CRL that revokes the old intermediate, or every verifier drops it from its trust; until then those leaves stay valid to their notAfter (24 hours for agents, 7 days for gateways and servers). Short of every verifier dropping it from its trust, that root-signed CRL is the only way to revoke a compromised intermediate key. Wave 1 decides how a root kept offline or in an HSM issues that CRL and on what schedule (its nextUpdate cannot be 15 minutes), and whether gateways, servers and agents check the intermediate level of the chain, together with the customer-intermediate question below. If they do, a root CRL past its nextUpdate refuses every leaf of every hop at once, so wave 1 states what a lapsed root CRL does, adds an escalating alert on the root CRL's age that gives the operator of an offline root days rather than minutes, and lets the root CRL lapse in its chaos tests.
- **A routed-concern rule changes with it, in wave 1, not now.** The PKI row in `.claude/routed-concerns-access-control.md` says each CRL is a superset of the last. Pruning by expiry breaks that wording, though not the append-only table under it. ADR-2002 section 8 says the same (each CRL is a superset of the one before it), and wave 1 amends that sentence too. Pruning also breaks the count-based CRL freshness self-heal: `has_unpublished_revocations` (`ca_store.cpp`) compares the latest CRL's revoked count with the revoked rows, so wave 1 must re-key it to the non-expired revoked set in the same change. The wave-1 change that prunes the CRL amends the row in the same PR, with `security-guardian`.
- **To test in wave 1:** if the CRL's nextUpdate is set 15 minutes ahead, OpenSSL itself refuses a stale list (at the leaf level; the intermediate level follows the root CRL's schedule), so the 15-minute fail-closed bound becomes a property of the signed CRL, the same on both TLS paths at the agent edge (the gateway's own pull is the exception above).
- **Revocation per tenant (decided by Nathan Dornbrook on 2026-10-30, with multi-tenant hosting).** A gateway accepts on its main port only agent leaves of its own tenant: the identity check in Erlang (D8) compares the tenant segment (D3) with the tenant in the gateway's own certificate, after the chain and CRL checks. Wave 2 delivers this check, with the strict main port. A revocation is made within one tenant: a tenant's operator can revoke only that tenant's identities. A mass revocation for one tenant (an intermediate rotation, above) must not cut off another tenant's agents, so once a second tenant exists a mass revocation can no longer be a rotation of one install-wide issuing intermediate. The leading candidate is one issuing intermediate per tenant, which also keeps each tenant's CRL to its own revocations. Wave 1 builds the default install's issuing intermediate so that one per tenant can be added later; the tenancy ADR chooses, and decides whether verifiers bind a leaf's tenant to its issuer's tenant (Consequences). A single-tenant install has one tenant, so its one issuing intermediate is already that tenant's, and its revocation works as described above.
- **Customer intermediates (D4):** checking every level of the chain needs a CRL from the customer's root for the intermediate, which Yuzu cannot produce. Either the leaf alone is checked, or the customer supplies their root's CRL; wave 1 decides. Full-chain validation to the install's trust root (D4) is the target. If only the leaf is checked, a compromised intermediate is revoked by removing it from the direct-issuer set (D4) on every verifier. Wave 1 states which of the two it uses, and tests it.

### D8. kTLS is the default at the agent edge; OTP `ssl` is the fallback

The reasons are the measurements above, and that nginx and HAProxy run the same design: OpenSSL's TLS state machine and X.509 code in their own process, then (where enabled) kernel record encryption. **Neither makes kTLS a default (verified 2026-10-29).** nginx offers it as an opt-in since 1.21.4 (2021), through `ssl_conf_command Options KTLS`. HAProxy offers it as an experimental option since 3.3 (2025), through `ktls on`, refused unless the configuration also sets `expose-experimental-directives`. Our default is therefore a stronger position than either, but only if the requirements below are met; they are what make it acceptable. HAProxy, like the gateway, is one multi-threaded process, so a memory-safety bug there also costs every connection; nginx isolates it to one worker.

**TLS version (decided by Nathan Dornbrook on 2026-10-30).** `agent_id` is personal data (a GDPR online identifier). That makes four more things wave requirements: (1) wave 1 inventories where `agent_id` is written (log lines, metric labels, audit rows, the SPIFFE SAN in `ca_issued`, responses), and no metric label or unbounded log field carries it; (2) each store holding it states its retention basis, and what erasure means for a decommissioned device. **The `agent_id` in the permanent revoked set (the revoked `ca_issued` rows) stays readable forever, and there is no erasure route (decided by Nathan Dornbrook on 2026-11-01).** The reasoning, recorded as an erasure exception for customers' privacy teams: the revoked set is security-necessary, because a revocation must never be undoable, and erasing or blanking the identifier would let a revoked identity be issued a certificate again (D6's block on re-issuance reads the revoked set by identity). The right to erasure applies to data no longer needed for its purpose and has exceptions (GDPR Article 17); this identifier stays needed for as long as the revocation must hold, which is for ever. The revoked set is what stops a revoked identity from being issued a certificate again. Each customer states its own legal grounds in its own records. An erasure request that reaches this identifier is answered by citing this exception, not by deletion. The exception covers only `agent_id` in revoked `ca_issued` rows; every other store holding it erases or minimises under item (2). It is not a general exemption; the other revoked-row columns are undecided. A revoked `ca_issued` row also keeps other columns (`cert_pem`, `issued_by`, `revocation_reason`, `enrollment_request_id`); which of them stay readable, and whether any are minimised after the 13-month window without deleting the row (the `ca_issued_keep_revoked` trigger forbids deletion), is for wave 1 (Open questions); (3) the manual's privacy and data-retention pages say it is personal data; and (4) the audit and export verbs D5 and D7 add do not put it in free-text fields. TLS 1.2 sends the client certificate in the clear, so on an internet-facing gateway a passive observer reads every agent's SPIFFE ID, and so its `agent_id`. Internet-facing gateways (the zone, D10) therefore require TLS 1.3 on the main port, so the client certificate is never sent in the clear. **TLS 1.3 is the default everywhere (decided by Nathan Dornbrook on 2026-10-31):** on a gateway with no zone set, on the enrollment port, and on the direct agent-to-server port, as well as on internet-facing main ports. "Everywhere" means every agent-facing port: the gateway's main and enrollment ports, labelled with a zone or not, and the direct server port. Whether the other hops (gateway to server, management, Erlang distribution) also move to TLS 1.3 is open (Open questions). Only an internal gateway may be explicitly configured to allow TLS 1.2, so allowing it is always a deliberate setting, never a default or the result of a missing label. Until wave 4 puts the zone in the gateway certificate (D10), wave 2 states where a gateway's zone comes from. The requirement holds on both TLS paths: the OTP `ssl` fallback on an internet-facing main port also requires TLS 1.3. Both paths are pinned to TLS 1.2 today (`yuzu_grpc_listener:ssl_opts/1` sets `{versions, ['tlsv1.2']}` with TLS 1.2-only options that OTP refuses on a TLS 1.3-only listener, the kTLS branch's NIF builds one-version contexts, and the shipped `sys.config` files pin the upstream client to TLS 1.2), so wave 2 makes the version a per-listener setting. D14's figures were measured on TLS 1.2; wave 2 re-measures them on TLS 1.3 before they gate an internet-facing gateway. A TLS 1.3 peer can send KeyUpdate to change keys mid-connection. Under kTLS the kernel must install the new receive key, and only newer kernels can (the rekey support is documented for Linux 6.14). Rocky 9's 5.14 cannot: there a KeyUpdate ends the connection (item K2 of BigColin's review, 2026-10; no Yuzu agent stack was seen to send one). Wave 2 handles that limit, and needs two things:
- **A KeyUpdate policy:** refuse it and close the connection, or require a kernel with rekey support on gateway hosts, or keep the receive side in user space.
- **A KeyUpdate rate limit** whatever the policy, because each KeyUpdate costs CPU. HAProxy added one (100 per second per connection by default) to stop a KeyUpdate flood; the lesson applies with or without kTLS. On the OTP `ssl` fallback path the policy is not available: OTP answers every peer KeyUpdate itself and offers no way to refuse one (`tls_gen_connection_1_3`, OTP 28.4). But it reports each one: the `{keep_secrets, {keylog, Fun}}` callback (OTP 27.3.1 and later) runs on every key update. **Decided by Nathan Dornbrook on 2026-10-31:** an internet-facing gateway on a kernel too old for kTLS rekey may use the OTP `ssl` fallback, with KeyUpdate rate-limited there as well: a connection that asks for more than a few KeyUpdates per hour is closed. Wave 2 sets the exact limit, counts KeyUpdates in that callback, and closes the connection past the limit. The callback receives live traffic secrets, so it must discard them and never log them. The callback cannot raise (it catches everything), and the message it sends carries only a count, never a secret. A close from inside the callback fails (`calling_self`), is caught and logged by OTP, and leaves the connection open, so it signals the close out of the connection process. Wave 2 states how the limit fails closed when a count cannot be delivered (a lost message or a dead receiver), and that messages are coalesced so a flood does not fill one mailbox. It also fires during the handshake, which the count must allow for. Fallback: on an OTP that lacks the hook, an internet-facing gateway on an old kernel does not start on the fallback.

Because memory safety is vital, these are requirements, not options:
- a pinned OpenSSL version, with its security advisories tracked and acted on;
- continuous fuzzing of our C code in CI, plus an ASan build exercised by the test suite. These apply to gateway C from the trim NIF onward, not from wave 2. CI compiles the trim NIF and eunit loads it, but no CI job fuzzes gateway C or builds it with ASan today (the NIF's build script ignores sanitizer flags). Wave 0 adds an ASan run for the trim NIF, which takes no input and so has nothing to fuzz; continuous fuzzing starts with the kTLS NIF in wave 2;
- one shared test suite proving the kTLS and OTP `ssl` paths accept and refuse exactly the same certificates (chain, SAN, EKU, expiry, revocation);
- security review of the C code before it ships enabled.

The difference from nginx is recorded: nginx runs handshakes in worker processes, so a crash costs one worker. Our handshake runs inside the Erlang VM, so a crash costs the gateway. Whether to move handshakes out of the VM later is an open item (see Open questions).

**Where the agent-certificate checks run (decided by Nathan on 2026-10-28):**
- **In C:** OpenSSL checks the chain and the revocation list during the handshake. The NIF sets `SSL_VERIFY_PEER` with fail-if-no-peer-certificate, the CA store, which holds the trust root configured for the install (the Yuzu root, or the corporate root in subordinate mode) and the allowed direct issuers (D4), and the CRL. A bad chain or a revoked certificate is refused before the handshake completes. Our C stays small: configuring OpenSSL and handing the verified peer certificate to Erlang.
- **In Erlang:** the gateway checks the SPIFFE identity and the EKU of the verified certificate just after the handshake, before any gRPC request is served. Identity rules will change as SPIFFE and customer intermediates arrive, so they live where they are easy to change and test.
- **The same split on the fallback path:** OTP `ssl` checks chain and CRL, and the same Erlang identity check runs. The shared accept/refuse suite covers both.

The kTLS branch (`perf/gateway-idle-mem-ktls`, not on `dev`) currently refuses `ktls` together with `verify_peer`; that refusal goes away.

### D9. Discovery and choosing a gateway

- **"Use DNS" is a design principle.** An agent finds its first gateway by DNS.
- **After first contact,** the server gives the agent the current gateway list, with weights and draining state. The agent caches it on disk for the next start.
- **Which gateways the list holds (decided by Nathan Dornbrook on 2026-10-30).** Only gateways of the agent's own tenant, never another tenant's. Within the tenant, by device class: a fixed machine (a server or a desktop) gets only its own zone's gateways, which keeps ADR-2002 section 7's "no cross-zone failover" for it; a roaming device (a laptop) gets both the internal and the internet-facing gateways of its tenant, and prefers an internal one whenever one is reachable, so latency weighting applies among internal gateways first and among internet-facing ones only when no internal one answers. This amends ADR-2002 section 7 for roaming devices (its dated update). Who classifies a device as roaming is open for wave 4 (Open questions).
- **Choosing:** weighted random choice, with the weight from measured round-trip time, so the nearest gateway in time weighs most and agents do not all pile onto one. Jittered back-off between attempts. Failover down the list.
- **Draining gateways** have weight zero.
- **A fail-closed gateway** (D7) has weight zero until it has a fresh CRL, then returns to its measured weight in the next server-signed list (decided by Nathan Dornbrook on 2026-10-30; wave 4). Wave 4 states how soon after recovery the list is re-signed and pushed, and adds hysteresis so a flapping gateway does not re-sign and push the list fleet-wide on every change. If every gateway in the list has weight zero, the agent still tries them all, as equals, with jittered back-off. Wave 4 tests this. Wave 4 states how the server learns that a gateway has failed closed, including for one that reaches no server. When the CRL returns, every gateway leaves fail-closed together; wave 4 states the agents' back-off cap and so the recovery time, and tests the recovery as well as the outage, including the enrollment-port load from agents fetching a signed time (D6).
- No region or site field in the first version: latency weighting covers it. The weight function stays pluggable, because round-trip time does not see a LAN boundary (a per-campus site gateway, for example).
- **When every cached entry fails** (all drained or dead), the agent goes back to DNS. The cached list carries an expiry; to be set in wave 4, preferably per entry by the server, as Teleport's proxies do.
- **Any gateway list that reaches the agent through a gateway is signed by the server** (D5), and the agent refuses one that is not. Otherwise a compromised gateway could steer agents to endpoints of its choosing. Those could not impersonate the server, but they could hold agents captive.

### D10. How gateways know about one another

- **Within one communication domain (below):** gateways may form an Erlang cluster (the existing `yuzu_gw_cluster_discovery` and per-agent `pg` lookup; there is no hash ring, #4556). The cluster's own connections run over TLS (`inet_tls_dist`) with CA-issued certificates. Membership in an Erlang cluster is full control of every member. D1.2's role check applies: distribution admits only gateway identities of its own communication domain (the zone and organisation in the certificate, below), with chain and CRL checked. Under D3 agent leaves carry both `serverAuth` and `clientAuth` and chain to the same CA, so a chain-only check would admit an agent leaf to the cluster.
- **Bounded communication domains (decided by Nathan Dornbrook on 2026-10-30).** A domain is a zone (internet-facing or internal) together with one organisation (tenant). Gateway-to-gateway links stay inside one domain and never cross a domain boundary: an internet-facing gateway may link with the internet-facing gateways of the same organisation, but never with an internal gateway, and never with the internet-facing gateways of another organisation. This keeps ADR-2002 section 7's rule that a cluster does not span trust zones, and adds the organisation as a second boundary. The organisation is the tenant of D3 and of multi-tenant hosting (decided by Nathan Dornbrook on 2026-10-30), so a domain never spans tenants. **One cluster per region inside a domain (decided by Nathan Dornbrook on 2026-10-30).** A cluster does not span a WAN, which keeps ADR-2002 section 7: one domain's gateways in different regions form one cluster per region, and the regions coordinate through the servers and Postgres. Because membership in an Erlang cluster is full control of every member, a compromised gateway controls every gateway in its cluster, and no gateway outside it through the cluster; until wave 2 it can still claim agents of any domain or organisation through the server (conflict 1), and until wave 4 any agent of its own tenant whose session it carries (below).
- **Per-gateway agent scoping, #5578's R-6 (decided by Nathan Dornbrook on 2026-10-30; the tenant refusal from wave 2 (D5), the zone refusal in wave 4).** A gateway may carry only agents of its own tenant and zone. The server refuses a route claim (the `agent_routes` write) for an agent of another tenant, or of another zone, judged against the tenant and zone in the gateway's certificate and the server's record of the agent; it is refused and counted by reason, never written. A roaming device (D9) is allowed in both zones of its own tenant, never in another tenant's. From wave 2 a route claim also needs the server's verification of the session's agent signature (conflict 1), so from wave 4 a compromised gateway can claim only agents of its own tenant and zone that actually hold a session through it.
- **Link identity (decided by Nathan Dornbrook on 2026-10-30; delivered in wave 4).** Gateways link by mutual TLS, and each gateway certificate names its zone and its organisation (for example in the SPIFFE path, D3). Every link checks both, and is refused on any mismatch. OTP checks a distribution peer's certificate only when the link is set up, so wave 4 also disconnects every live link to a member whose certificate is revoked or has expired (once the CRL lists it, or at its notAfter), and tests it; wave 1's credential hot reload covers the distribution certificate too. Yuzu has no organisation or tenant concept today: one install has one CA and one trust domain (D3), and "tenant" in the code means an identity provider's tenant. The tenancy ADR defines what a tenant is and where the server records it (Consequences); it appears in the certificate as D3's tenant segment, which wave 1 already issues, and wave 4 adds the gateway's zone to its certificate alongside it. The CA takes a gateway's zone and organisation from the server's record of that gateway, never from the request, and a renewal keeps them; wave 4 states how that record is set. A change to it takes effect only by revoking every live certificate of that gateway (a renewal leaves two, and a live link may have been set up with the older one) and issuing one under the new domain. Wave 1's block on re-issuing to a revoked identity and its revoke/issue interlock must not refuse or revoke that new certificate, so wave 4 states how a domain move differs from a compromise revoke: only an audited operator change to the server's record authorises it, never the request; a compromise revoke blocks re-issuance to that gateway under every domain; and wave 4 states the authenticated channel the moved gateway uses to receive its new certificate. Once the CRL lists those serials, the moved gateway keeps no live link into its old domain (the revoked-member disconnect above). Erlang distribution runs over that mutual TLS and admits a peer by that identity; OTP's handshake still checks the shared cookie, which is no longer the admission control. The gateway already refuses to boot on the shipped default cookie, an empty one, or one shorter than 32 characters (`check_distribution_cookie`, #659, #4555), unless `YUZU_GW_ALLOW_DEFAULT_COOKIE=1` is set for dev and CI, and wave 4 keeps that refusal. **The override stays, as a clearly named lab-only switch (decided by Nathan Dornbrook on 2026-10-31):** it takes effect only when Erlang distribution listens on loopback, and it logs a loud warning at boot. Loopback means the distribution listener (`inet_dist_use_interface`) and EPMD (`ERL_EPMD_ADDRESS`) are both bound to loopback; the loopback addresses are 127.0.0.0/8, ::1, and the IPv4-mapped `::ffff:127.0.0.0/104` (the same addresses seen through a dual-stack socket), and a node in a shared or host network namespace is not loopback; it is never judged from the node name. It is judged from the effective listen addresses at boot; an unset `inet_dist_use_interface` (all interfaces) is not loopback; a node without EPMD is judged by its distribution listener alone. Where the gateway did not start EPMD itself and cannot read its bound address, the node is not loopback and the switch does not take effect; wave 4 states how it reads that address. Wave 4 adds the loopback condition and raises the existing boot warning to a loud (critical) one. Wave 4 also moves every place that sets `YUZU_GW_ALLOW_DEFAULT_COOKIE` to a loopback-bound node or a generated cookie: the shipped composes (reference-gateway, demo, viz-uat, full-uat, sanitizer-uat), the Compose Wizard hint, and the CI jobs in `ci.yml`, `nightly.yml` and `sanitizer-tests.yml`; it also updates the gateway eunit modules that set it, and the guidance in `docs/user-manual/gateway.md`, `docs/user-manual/upgrading.md` and `gateway/config/vm.args.src`, for the new name and the loopback condition. The current name, `YUZU_GW_ALLOW_DEFAULT_COOKIE`, does not say lab-only, so wave 4 renames it to a name that does; how the old name is treated is for wave 4.
- **New in wave 4:** TLS distribution with CA-issued certificates naming zone and organisation (today distribution is plaintext, and the cookie is its only authentication; node names are IP literals, `yuzu_gw@<ip>` from `gateway-entrypoint.sh`, and OTP's TLS distribution checks the dialled peer's certificate against that host by default, so wave 4 either puts the address in the certificate or replaces the host check with the identity check); the domain check on every link; and a `cluster_id` mismatch check at join, which guards against misconfiguration only, because admission is the distribution certificate.
- **Across domains,** gateways coordinate only through the server.
- **Either way,** every gateway reports health, load, draining and CRL (fail-closed) state to the server, because the server owns the gateway list agents receive (D9).

### D11. Draining a gateway

1. **The order:** an operator issues it through the dashboard, REST API or MCP, RBAC-gated and audited, reaching the gateway through the server (or through the cluster). Automation uses the same API.
2. **What agents receive (decided 2026-10-29):** the gateway sets its weight to zero. Each agent first receives, on its own stream, a short suggested list of other gateways signed by the server (D5). Then the gateway sends an HTTP/2 GOAWAY in two phases: a first one that stops new streams, and a final one after a jittered delay. The GOAWAY carries nothing in its debug data: RFC 9113 says that data is for diagnostics only, and the agent's gRPC stack does not hand it to the application. The agent reconnects by its normal weighted choice. Cowboy already sends a two-phase GOAWAY when a listener shuts down; the per-connection trigger, the batches and the jitter are new.
3. **Pace:** the two-phase GOAWAY goes out in staggered, jittered batches over an operator-set window, 10 minutes by default, so no other gateway takes a storm. The gateway exits when empty or at a hard deadline.
4. **Commands in flight:** the agent reconnects elsewhere and delivers the result there. The server must accept a result for a command it sent through a different gateway. The durable command idempotency of ADR-2002 WS-0 and the execution ids carry it. **This is new code on both sides.** Today a gateway drops a response for a command it did not dispatch (the orphaned-response path in `yuzu_gw_agent`); it must forward it upstream instead. And nothing re-drives an operator command whose result was lost on the drained stream (the command outbox covers scheduled runs only), so wave 4 builds the re-drive, with WS-0 replaying the stored outcome.
5. **The enrollment port** stops accepting new connections at the start of the drain window.
6. **Drain and stop (decided by Nathan Dornbrook on 2026-10-30; wave 4).** A drain is an explicit step before a stop, an API or MCP call, and the stop waits for it. A bare stop runs a fast drain that fits the platform's stop grace; wave 4 makes sure a fast drain never pushes its peers above D14's reconnect rate, even under a short grace (for example by leaving the remaining agents to their ordinary jittered back-off). Today the shipped Compose files, the files the Compose Wizard generates and the systemd unit give a gateway 40 seconds to stop (`stop_grace_period: 40s`, `TimeoutStopSec=40`, sized to the planned stop's 20-second `shutdown_flush_budget_ms`). The server has 210 seconds in the shipped Compose files and its systemd unit; the Compose Wizard's server block sets none, so Docker's 10-second default applies (#4950). **Wave 4 raises the stop grace to 11 minutes (decided by Nathan Dornbrook on 2026-10-30 for the Compose files, and on 2026-10-31 for the systemd unit and the server):** for the gateway, in the shipped Compose files, the files the Compose Wizard generates and the gateway's systemd unit; and for the server, in the shipped Compose files, the files the Compose Wizard generates, the server's systemd unit, and Kubernetes manifests. Any Kubernetes manifests Yuzu ships, for either, will use 11 minutes (none ship today). Wave 4 updates every place that states the server's 210-second grace: the unit, the source comments in `server.cpp`, `shutdown_drain_rules.hpp` and `guardian_ingest.hpp`, `docs/user-manual/server-admin.md`, and `docs/user-manual/upgrading.md`'s stacked-shutdown and Kubernetes guidance. A fast drain with no other gateway to move agents to ends at once instead of waiting out the grace (every shipped Compose file but the cluster reference runs one gateway). Wave 4 reconciles the drain with `shutdown_flush_budget_ms` (default 20 seconds, at most 10 minutes). Wave 4 states how a drain window longer than the platform's stop grace is prevented (for example, a boot check of the drain window plus the final GOAWAY delay plus `shutdown_flush_budget_ms` against a configured stop grace).

### D12. Several servers

1. **All servers active.** Singleton jobs run on the elected leader of ADR-2002 sections 3 and 6.
2. **Each gateway connects to every server** (ADR-2002 section 7g). Each agent's stream goes to one server, chosen by consistent hashing on `agent_id`. When a server is lost or drained, only its agents move.
3. **Reaching an agent:** Postgres records which gateway holds which agent (`agent_routes`). Any server sends a command straight to that gateway's management port. **This is new server code.** As of `origin/dev@fbd8b5409`, `AgentRegistry::send_to` (`server/core/src/agent_registry.cpp`) returns false for an agent not in that server's own memory, so a dispatch handled by a server that does not own the agent reaches nobody. With N gateways each connected to M servers, the upstream permit model (#6057) must also be re-derived. The result returns through the server that owns the agent's stream and lands in Postgres. The gateway part is new too: today a result returns on the dispatching server's SendCommand stream.
4. **Gateways find servers by DNS.**
5. **Draining a server:** it stops taking new agent streams, and its agents are rehashed onto the others in staggered batches.

### D13. Postgres

- **Replication: asynchronous by default (decided by Nathan Dornbrook on 2026-10-30; conflict 8).** An earlier draft of this decision required one synchronous standby that never degrades to the primary alone; that rule is dropped. Many enterprise data-centre pairs are more than 2 ms apart, and a commit that waits for a standby in the other data centre on every write is too slow there. No commit waits for a standby by default, except a transaction D13's per-store requirements below make wait. ADR-2002 section 11's synchronous profiles stay available as an operator's choice. An operator who chooses `quorum3` or `sync2` keeps RPO zero only while a synchronous standby is up; in exchange every commit waits one round trip to that standby, `quorum3` without strict mode silently falls back to asynchronous when every standby is lost, `sync2` stalls every write when its one standby is lost, and strict mode blocks writes for longer after a failover. `docs/user-manual/ha-postgres.md` states these trade-offs next to the profile table from wave 6. The shipped Patroni profile is unchanged until wave 6 changes its default (conflict 8).
- **RPO zero for acknowledged writes is no longer a target.** A failover can lose every write the old primary acknowledged but had not yet sent to the standby that is promoted. How much is lost depends on replication lag at the moment of failure; wave 6 measures it, and this ADR sets no bound on it. A failover tool may cap it: the shipped Patroni rig refuses to promote a standby more than 1 MiB behind (`maximum_lag_on_failover`, `patroni-entrypoint.sh`), which bounds the loss but can leave no standby to promote, so write downtime then has no bound. Wave 6 sets that cap deliberately, as the trade between the loss and the 60-second target, and tests a failover in which every standby lags past it. The cap also decides fleet admission: with no standby promoted the primary stays unreachable, and after 15 minutes every gateway fails closed (D7).
- **What a failover can lose, and what each store must meet.** For each store below, the named wave must design how its loss is prevented or made harmless, and prove it on a failover that loses acknowledged writes. These are requirements; the mechanisms are not decided.
  - **Revocation** (the revoked rows of `ca_issued`). Lost means a revoked certificate becomes valid again. Requirement (wave 1): a revocation the server has acknowledged, or that any published CRL has carried, survives a failover, and no CRL is signed that omits an unexpired revocation an earlier published CRL carried. Gateways run no superset check of their own, so a later list that drops such a revocation would make the certificate valid again. Wave 1 may meet this by making the revocation write wait for a standby (not the CRL re-signing, which never waits, D7), or by recovering published revocations from somewhere other than the primary; either way it states what a revoke does while every standby is lost. A revocation the standby has not confirmed is shown to the operator as not done, so the operator can re-issue it (decided by Nathan Dornbrook on 2026-10-30).
  - **Issuance** (the issued rows of `ca_issued`). Lost means a certificate is in use that the database does not know, so it cannot be revoked by serial. Requirement (wave 1): every issued certificate can still be revoked after a failover.
  - **Tenant ids and tenant bindings** (each agent's and gateway's tenant, D3; from wave 4 a gateway's zone and an agent's device class, D9, D10). Lost means an agent or gateway holds a certificate naming a tenant id the server no longer holds, or a binding the server no longer has, so every check of its tenant fails. Requirement (wave 1): every tenant id survives a failover and a restore, and is never re-created. A binding survives every failover its certificate's issuance survives. A missing binding is refused, never filled from the install's first tenant. Wave 1 states what an agent refused for a missing binding does (it re-enrols), and shows the refusal to the operator. This one may not be recorded as accepted.
  - **Renewal generation counter** (the latest number per agent, D6). Lost means the stored number goes backwards, so a clone presenting a number the lost rows had already used is accepted. Requirement (wave 1): no renewal is acknowledged with a number a failover can lose, so the stored number never goes back below one the server has acknowledged. This one may not be recorded as accepted. Wave 1 states what renewal does while every standby is lost, and the rule for counters after a restore (a restored counter is lower by design, so the first renewal after a restore is never trusted on its number alone). A rule that stops renewals until a standby returns lets 24-hour certificates expire across the fleet within a day; if wave 1 cannot meet both this requirement and fleet availability, it goes to the owner.
  - **CRL number** (`ca_crl_versions`). Lost means a number counted on from these rows is re-used or goes backwards, so gateways refuse the next list. Requirement (wave 1): the number is derived from the signing time, so a lost row neither re-uses nor lowers it, and a gateway that has restarted or is new trusts its first good pull of an issuing intermediate's CRL (the root's CRL: wave 1, D7) (D7, decided by Nathan Dornbrook on 2026-10-30; Accepted risks).
  - **Trust domain and CA hierarchy.** Lost means a second first boot, which renames every identity. Requirement (wave 1): the locked trust domain and every root and intermediate record (certificates and `key_ref`s, and superseded intermediates kept for D5's 13 months) survive a failover and a restore. A start that finds a locked-trust-domain marker, an issuing intermediate created by wave 1's first boot, or a SPIFFE-form certificate it issued, but no stored trust domain, refuses to start and never runs first boot again (the lock, D3). Certificates issued before wave 1 (`yuzu://` form) do not trigger it: an install's first start on wave 1 is the one first boot it runs (D3). The locked-trust-domain marker is stored apart from the trust-domain row (a separate table or record), so no single lost row removes both; wave 1 tests a start with only the trust-domain row missing. This one may not be recorded as accepted.
  - **Audit rows** (the durable audit queue included). Lost means a gap in the audit evidence. Requirement (wave 6, with `compliance-officer`): state whether an acknowledged audit row must survive a failover, and how. Whatever the general answer, the audit row for a revocation, an issuance, an access revocation or a quarantine change commits in the same transaction as the act, or with the same or stronger durability: an act that survives a failover must not lose the record of who did it and when. One exception is decided (Audit and evidence): a revocation made while audit writes fail is held in the durable queue, and when even the queue's reserved space runs out, its row can be lost and the durable loss marker records the loss (Accepted risks, the revocation-during-audit-outage row).
  - **Access revocations and containment** (operator sessions and logouts, API token revocation, SCIM, OIDC and SAML deprovision, user deactivation, RBAC unassignment, and `QuarantineStore` records and allow-lists). Lost means a revoked session or token, or a deprovisioned operator, works again; or a contained device is treated as dispatchable, or an older allow-list is pushed again by the stored-containment re-dispatch. Requirement (wave 6): an acknowledged revocation or quarantine change survives a failover, or its loss fails closed (for example, every session and token older than the replication lag must authenticate again); wave 6 defines what failing closed means for each. This one may not be recorded as accepted.
  - **Agent routes.** Lost means a stale route. Requirement (wave 6): routes are rebuilt from live connections (the reconcile, #5649) as agents reconnect, and a lost route row never leaves an agent unreachable once it has reconnected.
  - **Command outbox and dispatch.** Lost means a command is driven again or not at all. Requirement (wave 6): a command whose dispatch row is lost is shown to the operator as not done, never as done; a command driven again is a duplicate to the agent only within WS-0's ring and while its store is healthy (D5), so the re-drive must stay within that; a protective action, which the ring may not cover (`__guard__` never takes the claim), is bounded by supersession against the durable containment record instead (D5).
  - **Leader epoch** (`leader_epoch_seq` and `leader_state` in the `leader_elector` schema). Lost means an epoch is issued twice, so a new leader and a paused former leader both pass the epoch fence and a fenced claim can be made twice (ADR-2002 section 6). Requirement (wave 6): no epoch is ever issued twice across a failover. This one may not be recorded as accepted.
  - **RBAC write generation** (`rbac_meta.write_generation` in the `rbac_store` schema). Lost means the generation goes backwards, and a server that saw the lost value ignores later grant changes, so it serves a revoked grant while every refresh succeeds. Requirement (wave 6): no server ignores a grant change made after a failover. This one may not be recorded as accepted.
  - **Event outbox** (`event_outbox`, and its role as the schedule runner's spent-ticket record). Lost means a server polling forward from its last-seen position skips new events with no visible gap (the poller's position is a transaction-id horizon the promoted primary can issue again), an event id names two events, or a spent approval ticket can be spent again. Requirement (wave 6): no event is skipped and no event id names two events across a failover, and a lost spent-ticket row never lets an approval run twice. This one may not be recorded as accepted.
  - **Execute-once claims** (`DeploymentRunStore`'s `claim_for_exec`, and the policy remediation claim). Lost means a mutating step runs twice: a reclaimed deployment step is sent under a new command id, which WS-0's dedup does not absorb. Requirement (wave 6): a lost claim never causes a second execution of a mutating step. This one may not be recorded as accepted.
  - **Restores.** A restore from backup rewinds every store above further than a failover does. A restore of a backup taken before an install's first wave-1 start must not run first boot again: wave 1 detects it from a marker held outside the database, written in an order with the first-start transaction that survives a crash on either side of its commit (D3, wave 1 row), and refuses to start, and the upgrade section requires a backup taken after the first wave-1 start (D3). Every requirement above holds for a restore as well as a failover; waves 1 and 6 each write the post-restore runbook for their stores (for example: re-apply revocations made after the backup, and force sessions and tokens to authenticate again). A CRL number derived from the signing time (D7) is already past every published number after a restore, provided the signer's clock is within the tolerance; the runbook covers a signer whose clock is not.
  - **Every other store.** Requirement (wave 6): list what a failover can lose there, and either close it or record it as accepted.
  - **The failover loss record.** Requirement (wave 6): every promotion writes a durable record of what the failover may have lost (the time range and the WAL position lost, from the promoted standby's last received position), written at promotion, never by the failing primary, and raises the alert the wave 6 observability obligation sets for it (a completed failover that lost writes opens a ticket, not a page; a page only when the primary is unreachable and no standby is promotable). The stores above that rely on a loss record (the durable audit queue, Audit and evidence; audit rows; the command outbox) cite this one.
- **The leading candidate for revocation, issuance, the renewal counter, tenant bindings and possibly audit, not a decision:** per-transaction synchronous commit, where only those transactions wait for a standby (Postgres `SET LOCAL synchronous_commit`) and every other write stays asynchronous. Each such transaction then takes one round trip to the standby. Revocations are rare, so that costs little; issuance is not rare (about 28 signatures per second at 1.2 million agents, see Consequences), so wave 1 measures the cost on the signing path before choosing it, the renewal counter's write included, since every renewal makes one. It works only where a standby is named as synchronous: on the shipped `async` profile (`synchronous_mode: false`, so `synchronous_standby_names` is empty) the setting waits for the local flush only, and gives no durability. If it is chosen, "asynchronous by default" is delivered as Patroni's synchronous mode (which also limits promotion to the synchronous set) with a cluster-wide `synchronous_commit = local`, not as the `async` profile. Choosing it means wave 1 must also state what such a transaction does while no standby is reachable (wait, which holds up revocation, or proceed, which re-opens the loss; Patroni without strict mode clears the synchronous standby list when every standby is lost, so a wait silently becomes proceed). A synchronous wait that ends early leaves the transaction committed locally but not replicated, and Postgres still reports the commit to the client as successful, with only a warning. Wave 1 must treat such a commit as not durable: it neither acknowledges the revoke nor publishes it until replication is confirmed, and the CRL publisher, not only the revoke handler, excludes a revocation whose replication is unconfirmed (`publish_next_crl` reads every committed revoked row). That covers every way a wait ends early: the pool's `statement_timeout` (30 s by default, `pg_pool.hpp`), a terminated backend, a client disconnect, the synchronous standby list being cleared, and a primary restart during the wait. CRL signing must not wait on a standby either way (D7).
- **Failover:** Yuzu depends on no particular HA tool. It reaches Postgres by one DNS name, or a multi-host DSN, with `target_session_attrs=read-write`. Patroni is the documented on-premises reference; a managed service is the SaaS choice. Whatever HA tool is used must not break the per-store requirements above.
- **Targets:** write downtime under 60 seconds per failover. This is a target, unmeasured until wave 6. While Postgres is unreachable, servers fail closed for writes. **That is not true of every store today:** `ResponseStore` logs a failed store under pool pressure and drops the response (BigColin's test run RR7, 2026-10-28, at 5,000 agents: one of seven runs lost 1,989 of 4,941 responses with the default pool of 16). A synchronous standby, where an operator chooses one, lengthens every commit and makes that likelier. This decision therefore includes a concrete change: bounded retry, or an explicit error, for response storage, and a pool size measured with the default asynchronous replication and with a synchronous standby.
- **Reads:** no reads from standbys in the first version.
- **Leadership** is re-elected after every failover, and every singleton job must tolerate that.
- **Several servers need more than this ADR.** Multi-server operation (D12, wave 5) also requires ADR-2002's safe-to-scale gate (`docs/ha-delivery-matrix.md`, including #6528 and #6535). Wave 5's rig does not lift it.

### D14. The gateway budget

This replaces the 8 KiB-per-connection goal set on 2026-10-26.

These are targets, not yet evidence. On merged `dev` the gateway holds about 320 to 470 KB per agent at 5,000 agents (Nathan's 5,000-agent suite; BigColin RR7, RSS). The 48.1 KB above is the kTLS branch at 100 agents with one-way TLS. Wave 0 measures a common baseline at 5,000 and 10,000 agents, with one method (OS anonymous memory plus kernel, after settling, TLS on), on merged `dev` and on the kTLS branch, before the CI check becomes a gate.

- **Goal, per box:** one gateway on 8 cores and 16 GB holds 100,000 idle agents with mutual TLS. It must stay inside:
  - memory under 8 GB;
  - idle CPU under 2 cores;
  - a full reconnect of all 100,000 agents within 60 seconds (about 1,700 handshakes per second, plus the D5 signature checks). RR7 registered about 290 agents per second against the about 1,700 needed; the likely bottleneck is the server's Register path (and the D5 verification, whose CPU cost is not yet budgeted), not the handshake;
  - memory back within 5% of its pre-storm level within 2 minutes.
- **CI regression check, per agent:** 64 KiB per idle agent, all-in including the kernel's per-connection memory. The check is measured with the ADR-0073 heartbeat (liveness only, no fleet snapshot), so until ADR-0073 lands it does not measure the heartbeat that ships.

The memory measures in this ADR's companion change (on `dev` since commit 857ac374e) are: a garbage collection of the large processes after an agent-count drop, plus a second pass 30 seconds later; and a periodic `malloc_trim(0)` through a small NIF. The periodic trim runs every 5 minutes by default (`trim_interval_ms`; 0 turns it off). Only the trim after an agent-count drop was measured; the periodic trim was not. **The periodic trim stays on by default, as merged in #6713 (decided by Nathan Dornbrook on 2026-11-01).** The post-merge review of #6713 measures its cost and benefit on Rocky, and the default goes off if it saves nothing or costs CPU. The trim acts on glibc only, and does nothing on the default musl image. `+MMmcs 0` and `MALLOC_ARENA_MAX=2` are not in it: they are deferred to the hibernation work, because they gave no measurable memory gain and had a measured idle-CPU cost.

`malloc_trim` is a glibc feature. It acts on the chiselled Ubuntu image (`Dockerfile.gateway.chisel`), where it was measured. The default image (`Dockerfile.gateway`) is Alpine with musl, and musl has no `malloc_trim`. musl's allocator returns freed memory differently, and that is not yet measured. The glibc builders (the chisel builder, CI, and the Meson-driven gateway build on Linux) already compile the trim NIF (`gateway/apps/yuzu_gw/rebar.config`, `c_src/build_mem_trim_nif.sh`). Only the Alpine builder in `Dockerfile.gateway` has no C toolchain; the kTLS NIF must add one there (`build-base`, `openssl-dev`, `linux-headers`), and its rebar pre_hook must match musl targets too, because the trim NIF's `-linux-gnu-` filter skips Alpine. Both NIFs are Linux-only: Windows and macOS gateway builds skip them. kTLS itself does not need glibc. Checked on 2026-10-28: the NIF builds without warnings against musl in `erlang:28-alpine` (with `openssl-dev` and `linux-headers`) and loads in the BEAM there. What kTLS needs is the host kernel's `tls` module, because a container shares the host's kernel and cannot load modules itself.

Several standing rules, and one earlier ADR, say the opposite of a decision above. Until the named wave amends each one, with `security-guardian`, the current rule stands and code must follow it.

- **No `auth_fun` on the `:50051` agent listener** (the PKI row of `.claude/routed-concerns-access-control.md`; D2). It is also enforced in code: the gateway refuses to boot with `auth_fun_on_agent_listener` (`yuzu_grpc_listener.erl`), and the manual's stage 3 in `docs/user-manual/gateway.md` ("Moving the agent edge to mutual TLS") says the same. The enrollment port also needs a per-listener method allow-list, which the layer does not have: new code. **Wave 2.**
- **Each CRL is a superset of the last** (the PKI row; D7). **Wave 1.**
- **`CaStore::publish_next_crl` is the single CRL publisher, numbering `MAX(version)+1` with no gaps** (the PKI row; ADR-2002 section 8, update of 2026-09-23). Wave 1 states how a root CRL signed outside the server (an offline or HSM root) is recorded through that same path, never through a second one. **Wave 1.**

## Conflicts this ADR creates, to resolve in wave 0

1. **Cluster affinity against free gateway choice. Decided on 2026-10-29: affinity is dropped.** #4669 made an agent's home cluster sticky (`agent_routes.home_cluster_id`), so another cluster cannot claim and answer for it. D9 and D11 move agents between gateways freely, possibly across clusters. The #4669 admission check is to be removed now, ahead of D5 and wave 4 (below); the choice of gateway is free from wave 4, and affinity is neither an admission rule nor kept as a preference.
   - **The risk this carries, stated plainly:** until D5 lands in wave 2, a compromised gateway that holds a valid gateway certificate can claim any agent's route. D5's per-session signature and signed commands and results close it only if the route write (`agent_routes`, written today on the gateway's CONNECTED notification and asserted by the gateway) changes only after the server has verified that session's agent signature. Wave 2 makes it so. D5 does not stop a gateway that holds the agent from reading command payloads (a D5 non-goal). From wave 2 the server also refuses a route claim for an agent of another tenant, and from wave 4 one outside the gateway's zone (D10, #5578 R-6).
   - **Affinity is dropped now (decided by Nathan Dornbrook on 2026-10-30, re-confirming the decision of 2026-10-29).** Removing the #4669 admission check does not wait for D5 or for wave 4, and Nathan accepts the route-claim gap by name until wave 2 (Accepted risks).
2. **D5's scope. Decided on 2026-10-29:** signed commands, signed results and a signed gateway list, on top of the per-session signature (see D5).
3. **#5649. Still open: a proof obligation for wave 5.** D12 point 2 chooses stickiness on the gateway side (one owning server per agent). Wave 5 must show the reconcile correct when that owner changes (server loss or drain).
4. **ADR-0073's budget text. Done:** ADR-0073 is in PR #6704 and was revised there to cite D14 instead of the 8 KiB goal, and to re-cite the gateway after the merge of PR #5695.
5. **"The gateway adds no state." Decided on 2026-10-29:** both this ADR and ADR-0073 say instead that the gateway keeps **no per-agent state beyond the connection**. Fleet-level state that any gateway could rebuild is allowed: the cached CRL and the highest CRL number seen from each issuer (in memory only, D7), the drain flag, the cached gateway list, and cluster membership. ADR-0073's part is done: PR #6704 uses this wording. Today's gateway already keeps two kinds of per-agent state beyond the connection: per-agent `pg` groups across cluster members, and the DISCONNECTED resend window after a connection ends. Wave 4 keeps each as rebuildable state or changes it.
6. **Erlang clusters and the server's `cluster_id`. Decided on 2026-10-29: one Erlang cluster is one `cluster_id`.** The server already routes by a `cluster_id` per gateway session (ADR-2002 WS-4 4.3). Every member of a cluster (D10) is configured with the same id. Wave 4 adds a mismatch check at join, which guards against misconfiguration only: admission is the distribution certificate.
7. **The design target.** ADR-0069 records 100,000 agents per gateway. Dave has been steering to a solid 5,000 per gateway now, nothing that blocks 50,000 and beyond, and 500,000 as the long-term horizon. **Decided by Nathan on 2026-10-28** (Dave to see): waves 1 to 5 must pass at 5,000 agents on both rigs, with nothing that blocks 50,000; wave 6 tests failover under a 5,000-agent load; wave 7 is the 100,000-agent per-box budget (D14); 500,000 stays the long-term horizon, outside this programme.
8. **D13 against ADR-2002 section 11. Decided by Nathan Dornbrook on 2026-10-30: asynchronous replication is the default, and D13's one synchronous standby that never degrades is dropped.** Section 11 specified one primary plus two synchronous standbys (`ANY 1`), failing closed when both are lost. WS-7 measured that this strict mode blocks writes for minutes after a single failover, so the shipped Patroni default is the `quorum3` profile without strict mode (`YUZU_PG_DURABILITY` defaults to `quorum3` and `YUZU_PG_SYNC_STRICT` to false in `deploy/docker/ha-postgres/patroni-entrypoint.sh`): non-strict synchronous replication, where every commit waits for one standby while any standby is up and replication degrades to asynchronous only when every standby is lost. The decided default is asynchronous: no commit waits for a standby, except a transaction D13's per-store requirements make wait. The reason: many enterprise data-centre pairs are more than 2 ms apart, too far for a standby wait on every commit. RPO zero for acknowledged writes is no longer a target; what a failover can lose is accepted (Accepted risks), and each store's loss must meet the requirement D13 sets for it in wave 1 or wave 6. ADR-2002 sections 11 and 13 carry a dated update to match. Wave 6 changes the shipped profile's default on the existing Patroni rig (`deploy/docker/docker-compose.ha-postgres.yml`), not a new one; until then the shipped default is unchanged.

## Audit and evidence

The waves add audit records or metrics for: certificate issuance, renewal and revocation; CRL publication and gateway pulls; handshake refusals by reason; entry into and exit from fail-closed; enrollment by machine certificate; D5 signature refusals; the drain lifecycle (order, abort, completion); and changes to the gateway list the server signs. Each wave must add the audit verbs, metrics and alerts it introduces to its Done-when before it closes; the cells below do not list them yet. Audit records go to the existing audit log, with its `AuditLog:Read` gate. **The default retention for all audit rows rises from 365 days to 13 months (decided by Nathan Dornbrook on 2026-11-01),** matching D5's evidence window, so the audit rows around a kept result (who ordered it, and its approval) last as long as the result. This is a code change outside this ADR's text: its own small PR in wave 2, the wave that adds the evidence window, changing the default that `AuditStore::cleanup_once` applies and following the clock-guarded retention row. That PR states the day count it uses for 13 months. It updates `docs/user-manual/audit-log.md` (the settings table and the Retention paragraphs that state 365 days, and the QUIET-threshold arithmetic derived from the 365-day window), the `--audit-retention-days` / `YUZU_AUDIT_RETENTION_DAYS` default wherever the server-admin or configuration docs list it, `deploy/config/yuzu-server.env.example`, and `docs/enterprise-readiness-soc2-first-customer.md`. It carries a `changelog.d/` fragment whose upgrade note says an install with an explicit setting is unchanged, and that rows already removed under the 365-day default are not recovered, so the 13-month window fills from the upgrade onward. An operator may still set another value; the manual's audit-log page says a value below 13 months falls short of the evidence window. The retention basis for audit rows is the SOC 2 evidence window; the audit-log manual page states it as the retention basis for the `agent_id` and operator identities those rows hold (D8, item 2). Issuance records and CRL versions stay in `ca_store`, where a revoked row is never deleted. Mutations fail closed on audit failure (ADR-1005), with two exceptions, both decided by Nathan Dornbrook on 2026-10-30. First, a routine automated CRL re-sign continues when its audit write fails. Second, a revocation takes effect immediately when its audit write fails: its audit row is held in a durable server-side queue and written to the audit log on recovery, and the outage pages. The second supersedes, for revocation only, the earlier rule of the same day that a new revocation fails closed on audit failure. Un-revoking (lifting an agent DENY, for example; a revoked certificate is never un-revoked), and every other act that loosens a control, still fails closed on audit failure: it is refused and shown to the operator as not done. So anything that can break audit writes can delay an un-revoke or a loosening act, never a revocation, except an outage of the primary itself, in which the revocation cannot commit and is shown to the operator as not done.

Today's revoke commits the revocation before its audit row (`revoke_core`, `ca_routes.cpp`); from wave 1 the revocation's audit row commits in the same transaction as the revocation, into the audit log or, while audit writes fail, into the durable queue (D13's audit requirement, applied to revocation in wave 1). Wave 1 decides whether the revocation record in `ca_store` carries the acting principal in the same transaction as the revocation, so a lost audit row still leaves attribution. If it does not, the revocation-audit Accepted-risks row says attribution is lost with the row (Open questions). A routine re-sign is the scheduled tick, never the publish that follows an operator's revoke; it publishes only revocations already committed with their audit row, in the log or the queue, so neither exception carries a revocation that has no record, and neither holds back a committed one.

So audit availability is not a 15-minute dependency of CRL freshness (D7), nor of revocation. Both exceptions use one durable server-side queue. Wave 1 designs it: where it is held, its bound, and what a server restart does to it. A drained row carries the time Postgres records for the act (the DB-clock rule, #3715), marked as written late, with an ordering sequence; order is decided by the sequence, never by a replica's clock, so a later loosening act is never recorded before the revocation it reverses. Wave 1 states this and tests it. **A full queue (decided by Nathan Dornbrook on 2026-10-30):** routine re-signing carries on, and the server writes a durable marker ("N audit rows lost between X and Y") and pages. Revocation audit rows have reserved space in the queue and are the last to be dropped. Whatever bound wave 1 sets, queued rows are never lost silently: an overflow, or a restart (a crash included) or leader change that loses queued rows, leaves that durable marker and pages. The marker is not written by the failing path: it is written when a row is dropped, or derived at the next start or leader change by reconciling the durable `ca_crl_versions` rows and revocations against the audit rows that exist. A failover that loses queued rows or `ca_crl_versions` rows defeats that reconciliation, so D13's failover loss record must cover it. A design whose only evidence of loss is a log line or a counter held in memory does not meet this. Wave 1 also decides whether automated certificate renewal fails closed on audit failure; if it does, audit availability joins the CA key, the Postgres write and the leader as a dependency of renewal, and that audit write must not wait for a standby either.

- Re-attestation when an agent's owning server changes.

**Wave 6: replication observability**
- Per-standby replication lag (bytes and seconds), the standby count and which standbys are synchronous, and the failover lag cap, as metrics. Each failover leaves an audit record and log line with the old primary's last position, the promoted position, the gap and the timeline change, so an operator can learn how much a real failover lost. Pages only when the primary is unreachable (or its writes are blocked under strict mode) and no standby is promotable, because someone must then act; no promotable standby while the primary is healthy opens a ticket; lag below the cap is a dashboard, and a completed failover that lost writes opens a ticket, not a page.

**Observability and readiness (waves 1 to 6, each for what it adds)**
- Metrics for CRL age, fail-closed state, refusals by reason, CA signing rate, enrollment-port saturation, certificate-expiry horizons, drain progress, drains that ended at the hard deadline with agents still attached (a ticket), bare stops that ran a fast drain, and ring membership. A gateway or server certificate renewal that keeps failing pages, as does a gateway or server certificate with less than a quarter of its lifetime left; the expiry horizons themselves, and agent certificate expiry, are a dashboard. These replace the existing day-band rules for gateway and server certificates (`YuzuCertificateExpir*`, `YuzuGatewayCertificateExpir*`, warning from 30 days), which would fire without end on a 7-day certificate. With the opt-in offline root, the manual renewal ceremony is alerted months ahead of the intermediate's expiry (D4). An intermediate renewal that keeps failing escalates (D4), timed against the issuance cutover (notAfter minus 7 days), not against notAfter: a ticket first, then a page that lands before the cutover, whose responder action is the manual CSR. CRL age is exported per issuer. If wave 1 makes a lapsed root CRL fail gateways closed, the root's CRL has an escalating alert timed against its nextUpdate, and the responder action is the offline signing procedure wave 1 writes (D7). Each page names the responder's action.
- Alerts from wave 1: entry into fail-closed pages before wave 4 (no weight zero yet), and from wave 4 only when the gateways still ready leave too little capacity for the agents (confirmed by Nathan Dornbrook on 2026-11-01; one gateway failing closed among others with spare capacity raises a ticket or warning; time in fail-closed is a metric, and the page closes on exit). A gateway CRL nearing the 15-minute fail-closed bound pages before wave 4; from wave 4 it pages only under the same capacity condition (decision 88), and otherwise raises a ticket. Its responder action is to restore the gateway's path to a server or the CRL signer. A condition seen on many gateways at once (a stalled signer) pages once for the fleet, not once per gateway. An audit outage during a routine CRL re-sign or a revocation pages once as one condition, not once per tick, and its page names the responder's action: restore audit writes, because until then audit rows queue up and no un-revoke or other loosening act can be made. Queued audit rows that are lost page (the durable loss marker). That page names its action: record the gap (X to Y, N rows) in the evidence register and tell the compliance owner. It fires once per marker and closes when that marker is acknowledged. The queue's depth, age and remaining reserved space for revocation rows are metrics. A loosening act refused for an audit failure, or a revocation refused for an unconfirmed standby, is counted by reason and shown to the operator as not done (Audit and evidence). A renewal refused for a repeated or backward generation number raises a possible-clone alert, which names the responder's action: investigate, and revoke the identity if it is cloned (D6). Wave 1 states its severity, grouping and suppression: a single possible clone is a ticket, grouped per fleet with a rate, never a per-agent page; a retried renewal whose reply was lost (same number, key and request) raises nothing; the post-restore rule and a failover loss record suppress it for the affected window; a rate threshold wave 1 sets may page.
- Alert obligations: each alert a wave ships has a `runbook_url` and a named owning role, follows the prefix and label conventions of `docs/observability-conventions.md`, and has a rule test proving it can fire (the shipped-alert gate: `tests/prometheus/yuzu-alerts.test.yml`, run by `tests/prometheus/run_promtool_tests.py`).
- Clock health: agents counted by clock state (NTP-synchronised and agreeing; using server-signed time because NTP is unsynchronised or absent; using it because the clocks disagree) is a dashboard, and a fleet fraction in the last two states above a threshold wave 2 sets opens a ticket. Each server exports its clock offset against its time source, and an offset beyond the skew tolerance pages, because every agent follows signed time (D6). A gateway that fails closed on its own clock says so in its alert (D7). In a single-server install, agents held on an unconfirmed time step (D6) raise one fleet-level operator alert, not one per agent, whose responder action names the direction and is the same for both: verify the server's clock against an independent time source, correct it only if it is wrong, and release the hold only once it is correct, through wave 2's confirmation rule. Either direction can be a correction of a wrong clock or a fault of a right one: a slow server clock stepped forward by NTP after boot leaps forward, and an RTC reset, a restored server snapshot or a wrong NTP source steps a clock back. If the release is an operator act, it is an audited REST and MCP action that records which source was checked (A5); if wave 2 chooses an automatic confirmation rule, it states how the clock is verified without an operator. Wave 2 sets the server clock-offset page threshold below the backward cap, so a server drifting far enough to cause a hold pages before agents are held (wave 2).
- Operator surfaces: each operator-visible state this ADR adds (a revocation or command shown as not done, superseded, the clock-skew or NTP signal, the audit loss marker, the possible-clone refusal, the failover loss record, a refused missing tenant binding, `crl_stale` refusals) is readable through versioned REST and MCP twins under a named securable, with an A4 error envelope and a truthful `retry_after_ms`. The wave that adds the state names its audit verb (ADR-1005; agentic-first A1, A4, A5). List reads of per-agent states (possible clone, missing tenant binding, clock skew) go through `authorize_list_read` (ADR-0017), never a bare global gate.
- Readiness: a fail-closed or draining gateway is not ready for new agents but stays live. From wave 4 a fail-closed gateway also has weight zero in the gateway list until it has a fresh CRL (D9). Until then, readiness is the only steer: a load balancer stops sending agents to it, but a gateway found by DNS still draws agents, which are refused and retry.

## Alternatives considered

- **One port that asks for a certificate but does not require one, at the agent edge.** This is what direct agent-to-server connections use. Rejected: every request needs a "did this connection present a certificate?" check, and one missed check is a hole. A separate port gives a guarantee the TLS layer enforces.
- **The customer's machine certificate on the main port.** Rejected for now. It ties certificate lifetimes, naming and revocation to the customer's PKI, needs a second path for customers without one, and runs into gRPC's PEM-only client key.
- **The gateway vouches for the agent, and the server trusts it.** Rejected: an internet-facing gateway that is compromised could impersonate every agent behind it.
- **Gateway-held per-agent state, or gateway links across communication domains.** Rejected: membership in an Erlang cluster is full control of every member, so a link never crosses a zone or an organisation (D10), and per-agent state at the gateway breaks free gateway choice. Fleet-level state any gateway could rebuild is allowed (conflict 5).
- **A per-session key between agent and server, with a MAC on every message, for D5.** Rejected: it does not survive a command sent by another server or a result redelivered through another gateway, and it proves nothing to a third party (D5).
- **The suggested-gateway list inside the GOAWAY frame, for D11.** Rejected: GOAWAY debug data carries no meaning by RFC 9113, and the agent's gRPC stack does not expose it.
- **OTP `ssl` as the default.** Rejected by the owner, on the measured memory and handshake rate. It is kept as the fallback and as the reference the shared test suite compares against.

## Consequences

- The release that ships wave 2 breaks every existing agent-to-gateway deployment: new port, new certificates, agents re-enroll. This is acceptable only because there are no production customers at the time of writing (2026-10-30); before wave 2 merges Nathan Dornbrook confirms that no pilot runs agents behind a gateway (D2), and if a pilot runs agents through a gateway the upgrade note becomes a merge gate.
- Wave 1 ships with an upgrade section in `docs/user-manual/upgrading.md`: that an install already past its first boot treats its first start on wave 1 as a first boot (its trust domain from the setting or a fresh UUID, then locked; its first tenant id; its new issuing intermediate; and what happens to the leaves its root signed before) (D3), and that a backup is taken after that first start, since a restore of an earlier one refuses to start (D13); that operator-supplied server and gateway certificates are accepted only through subordinate mode, and how an install using them moves (D4); the move of the CA keys off the volume the gateway mounts, with the matching Compose file changes; and the gateway's move from pins to CA trust. It ships a changelog fragment marked Breaking: an install using operator-supplied server or gateway certificates stops being accepted at wave 1 unless it has moved to subordinate mode. The upgrade section says whether that move is made before or during the upgrade.
- Wave 2 ships with an upgrade section in `docs/user-manual/upgrading.md` (the new enrollment port and its firewall rule; TLS 1.3 by default on every agent-facing port, how a gateway's zone is set, and how an internal gateway is configured to allow TLS 1.2 (D8); the upgrade order server, then gateway, then agents; re-enrollment and its prerequisites; roll-forward), a changelog fragment marked Breaking, and an update to `docs/user-manual/gateway.md`'s "Moving the agent edge to mutual TLS". The upgrade section also covers: load balancers and inspecting proxies in front of the main port must pass TCP through, since the gateway terminates mutual TLS; the machine-certificate prerequisites for enrollment by machine certificate; the agent's clock and NTP requirement (D6); DNS discovery (D9); and that the default audit retention rises from 365 days to 13 months (an explicitly configured value is unchanged; storage grows accordingly; customers update retention statements in their privacy documents).
- The CA signs far more often: each agent renews every 12 hours instead of about every eight months. At 1.2 million agents that is about 28 signatures per second, around the clock, before any mass re-enrollment. Its signing path, its `ca_issued` table and its CRL size must be measured before wave 2, not after. Nothing prunes `ca_issued` today, and D5's 13-month window keeps the record of every certificate that signed a kept result or a receipt, and every result has one of the two: at 1.2 million agents renewing twice a day, about 950 million rows, each with its PEM. Wave 1 sizes the table for that, and the passes that prune non-revoked `ca_issued` rows and `ca_crl_versions` rows follow the clock-guarded retention row of `.claude/routed-concerns.md`, and none removes a record, or a superseded intermediate's certificate, that a result still inside D5's 13-month window needs.
- The gateway gains C code that faces the internet. The fuzzing, ASan and advisory-tracking requirements in D8 are permanent.
- `docs/pki-architecture.md`, `docs/user-manual/gateway.md`, the reference composes and other compose files, the Compose Wizard, the agent and gateway installers, the gateway `sys.config` files and the environment examples all change with waves 1, 2, 4, 5 and 6.
- Wave 4 ships with an upgrade section: the 11-minute stop grace for gateways and servers on the customer's platform (Compose, systemd, Kubernetes, and container platforms that cap the grace below it), how a gateway learns the grace it has, and how long a rolling restart now takes (D11). It states the server's grace before the raise: 210 seconds in the shipped Compose files and its systemd unit, and Docker's 10-second default in a file the Compose Wizard generated, whose server block sets none (#4950). The raise covers the shipped Compose files, the files the Compose Wizard generates, the systemd units, and Kubernetes manifests (none ship today). The upgrade does not change a grace the operator holds: a previously generated wizard file, a Compose override or a systemd drop-in keeps its value until it is regenerated or raised by hand.
- The customer assurance package and shared-responsibility answers change with waves 1, 2 and 4: TLS 1.3 by default on every agent-facing port (the gateway's main and enrollment ports, labelled with a zone or not, and the direct server port), with TLS 1.2 only on an internal gateway configured for it, the revocation bounds, CA key custody, the gateway reading commands and results in plaintext, the asynchronous replication loss, the 13-month evidence window and 13-month audit retention, `agent_id` as personal data, with the erasure exception for the revoked set (D8), and the tenancy answer: single-tenant installs are the supported mode; no claim of isolation between tenants is made until the tenancy ADR's walls ship; the DPA and shared-responsibility answers state one customer per install. TLS 1.3 is claimed for agent-facing ports only; the gateway-to-server, management and distribution hops are not claimed as TLS 1.3 until that Open question closes. The assurance answers state that the 13-month claim holds in full only 13 months after the wave 2 upgrade. Audit rows removed under the earlier 365-day default, and results from before signed results existed, are not recovered. `docs/enterprise-readiness-soc2-first-customer.md`'s data-governance and retention tables (the response store's 90 days, the audit log's 365 days, the PKI inventory) change with wave 2, as do the manual's response-retention and privacy pages and any data-processing terms that state retention.
- The erasure exception for `agent_id` in the revoked set (D8) is a standing privacy residual. The assurance package states it, and it is re-confirmed at each wave end.
- The 13-month window sizes the response store (control-evidence results, and a receipt for every result) and the audit log, as well as `ca_issued`: wave 2 measures both at fleet scale.
- Replacing the day-band certificate alert rules (Observability) is an alerting change operators see; the wave that replaces them carries a migration note.
- **A tenancy ADR is required before wave 4, and it covers both install modes.** Multi-tenant hosting (decided by Nathan Dornbrook on 2026-10-30) needs tenant walls this ADR does not design: RBAC and dispatch (a tenant's operators reach only that tenant's agents, through `dispatch_confined_arms` and the list-read chokepoint), every server store, and audit (a tenant's rows, its readers, its export, and whether retention settings and the 13-month evidence window are per tenant or per install). That ADR builds on what D3 settles before wave 1, with no later migration: a tenant id is a random UUID with a display name, kept in one Postgres `tenants` table that every agent and gateway record references (decided by Nathan Dornbrook on 2026-11-01). D3's tenant segment, D7's per-tenant revocation and D10's domains rely on that table. Because the boundary is designed once for both modes (decided by Nathan Dornbrook on 2026-11-01), the tenancy ADR also states how a single-tenant install holds its one tenant behind the same walls, with nothing for its operators to configure and no change they would see (D3). Wave 4 stays the deadline. Wave 1 issues the tenant segment from the server's record, and wave 2 refuses by tenant, route claims included (D5, D7, D10). But wave 4 is the first wave that refuses route claims by zone and gateway links by organisation and zone (D10), and the first whose code lets a second tenant's gateways, and through them its agents, reach a shared install. That code runs in both modes, so it is built against the tenancy ADR's model of a tenant, not against a single-tenant shortcut that a later SaaS install would have to replace. Until that ADR is accepted and its walls are built, single-tenant installs are the supported mode: one customer per install, and the manual and the customer assurance answers say so. Multi-tenant SaaS hosting waits for those walls.
