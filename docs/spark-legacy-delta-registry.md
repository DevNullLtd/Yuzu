# Spark / legacy Guardian detection: intentional delta registry

Captured against `origin/dev @ b16e5836d` (2026-08-23). Authority: ADR-0021 Decision 11
amendment ("incremental per-consumer cutover... with the three gates applied per rung");
`docs/spark-stage2-guardian-consumer-design.md` §R2 consequence 2 (origin ruling, quoted
below); `docs/user-manual/guaranteed-state.md` "Per-rung default posture" table.

## Why this doc exists

> "Parity needs an intentional-delta registry. Legacy silently no-ops where spark
> reports `unsupported`. Zero-tolerance parity cannot be literal across that dimension;
> rung 10's gate artifact must carry the documented delta list, or the gate fails
> spuriously and gets quietly weakened until it means nothing."
> — `spark-stage2-guardian-consumer-design.md`, §R2 consequence 2

The design doc's PR-2 ("thin cutover") and rung-10 ladder entries both list this
registry as a named flip-gating deliverable (R2 consequence 2, pulled forward from
rung 10 because 7.7b changes the behavior it classifies): §PR-2 (`spark-stage2-guardian-
consumer-design.md`, and the 7.7b bullet list restating it) calls it "shipped ahead of
the flip, F12/#3386: `docs/spark-legacy-delta-registry.md`"; the numbered rung-10 ladder
item phrases the same fact as "shipped ahead of schedule, F12/#3386: ..." — different
wording, same claim. The intent both sites express: every observed difference between a
legacy-detection run and a spark-detection run at parity-capture time must classify as
either a row in this table ("expected, already decided") or a genuine regression ("new,
investigate"). This is that table.

**A third bucket exists and must not be silently folded into the first: a row whose
Epistemic status is `open-question`.** Such a row documents a real, observed difference
that has NOT been ruled deliberate — it is tracked, not dismissed. A diff line may be
classified "expected" against a `verified`/`likely` row; it may **not** be waved through
against an `open-question` row. Treat a diff matching an open row the same as a genuine
regression: it blocks the parity gate until the linked issue resolves and the row is
re-stamped `verified`/`likely`. (D3 held this status until 2026-08-23, when #3388 was
**ruled**, and until 2026-08-26 when the ruling's fix merged (PR #3518) — see D3's own
Ruling and Epistemic cells. No row currently carries `open-question` status.)

**Every row below is an at-the-flip delta, not a live one.** `GuardianEngine`'s
`prefer_spark` constructor parameter defaults `false` (`guardian_engine.hpp`), and the
sole production call site (`agent.cpp`, `std::make_unique<GuardianEngine>(kv_store_.get(),
cfg_.agent_id)`) omits it, taking the default. `reconcile_rule_locked` only reaches a
spark placement decision when `prefer_spark_ && spark_availability_ == Available`. So
today, fleet-wide, every row's "Spark" column is dormant and every row's "Legacy" column
is what every agent actually does.

**The only production lever once `prefer_spark` flips is `--spark-disable`**
(`YUZU_AGENT_SPARK_DISABLE`, boot-time only). It does not touch `prefer_spark` itself —
it sets `SparkAvailability::SparkDisabled`, which `guardian_backend_from_state()` maps to
the `legacy` backend label regardless of `prefer_spark`, restoring the full legacy path.

**Re-verification obligation.** Every row's `verified <SHA>` stamp is a point-in-time fact
about code that is still under active development, not a durable guarantee. `verified
<SHA>` records that a claim was checked, not that it stays true. **F14's first step is
re-verifying every row against flip-time HEAD and re-stamping the SHA** — treat this as a
precondition of the flip, not an optional refresh. A row whose cited symbol no longer
exists or no longer behaves as described is itself a flip blocker until corrected.
**Carve-out (added round 7, 2026-09-07): this rule does not apply to a row stamped
`design-approved <date>` (below) until the design's own first code PR lands** — such a
row's "Verify at" symbols are explicitly not-yet-implemented by definition, so "the cited
symbol no longer exists" is not a meaningful check against it yet; F14 re-verifies it
once it carries a real `verified <SHA>` stamp instead. **Lightweight recurring
touchpoint (Gate 6 compliance-officer), reusing `spark-flip-gate.md`'s own "Last full
re-verification" convention rather than inventing a new numeric bound**: a
`design-approved` row is re-confirmed still current (still matches the underlying
design doc, still not superseded, still correctly not-yet-implemented) at every later
PR-0-adjacent doc touch on the same design — not left to sit unexamined for an
unbounded period on the strength of one original approval date.

**Not this doc:**
- `docs/enterprise-parity-plan.md` — competitor feature parity, unrelated.
- `docs/capability-registries/spark_mechanisms.tsv` — per-OS mechanism capability
  registry (a *different* "registry"; this doc cites it, doesn't duplicate it).
- `docs/user-manual/guaranteed-state.md` "Upgrading from a detect-only build" —
  `enforcement_mode` defaulting to `enforce` + Baseline gating; not spark-related despite
  the name collision.

## How to add a row

One row per **deliberate** legacy-vs-spark behavioral difference, only after re-verifying
the current code (cite the symbol, not a line number — line refs drift, verified twice
already in this subsystem's own history). Each row is an `### <ID> — <one-line title>`
heading followed by a table with columns **Delta** (the heading itself) | **Legacy** |
**Spark** | **Why deliberate** | **Operator symptom** | **Verify at** | **Epistemic**.
Epistemic values: `verified <SHA>` (I read the code myself, this date), `likely`
(inferred from adjacent verified facts, not directly re-read), `open-question` (found
during this pass, no existing ruling covers it — flag, don't invent a rationale; may be
combined with a verification stamp, e.g. `open-question, verified <SHA>`, when the
*difference* is confirmed but its *disposition* isn't ruled — no row currently
illustrates this combined form; D3 carried it until its 2026-08-23 ruling, see its
Ruling/Epistemic cells), `design-approved <date>` (added round 7, 2026-09-07: the delta
is ruled and reviewed — external review rounds against a committed design doc, not a
guess — but the code implementing it does not exist yet, so there is nothing to `verify
<SHA>` against; see the re-verification-obligation carve-out above. Re-stamp `verified
<SHA>` once the design's own first code PR lands; do not leave a row `design-approved`
past that point).

Placement: pick the lettered section (A backend selection, B enforcement, C
placement/platform, D event streams, E cadence/resource) whose description above fits;
IDs are sequential within that letter (the next row after D9 is D10, not D1a or
E-something). Insert the new `### <ID> — ...` block right after the last existing row in
that section, ahead of that section's one closing `---` — there is a single `---` per
section, not one between every row, so do not add a separator between rows.

Two permitted variants: a row gating on a still-open flip-ladder decision (e.g. flip-ladder
decision D4 — a numbering tracked in the operator's local flip-ladder plan, distinct from
this doc's own row IDs; disambiguated as "flip-ladder decision Dn" everywhere it's cited)
may
add an 8th **Ruling** field instead of leaving "Why deliberate" empty; a row describing a
multi-OS delta (e.g. C2) may replace the single Legacy/Spark pair with a platform matrix
table. Both stay within the same intent — state what's known, cite where to verify,
never invent a rationale for what isn't ruled yet.

## A. Backend selection (agent-wide)

### A1 — `spark_failed` / `unwired` refuse the legacy fallback

| | |
|---|---|
| **Legacy** | N/A — this state only exists when `prefer_spark=true` |
| **Spark** | Every rule is withdrawn from legacy and left unarmed. Nothing enforces, nothing detects, for the whole agent, until the operator intervenes. |
| **Why deliberate** | "SparkFailed and Unwired NEVER fall back to legacy - a failure must be visible (errored), never silently absorbed (mutual exclusion)." Ruling R1 (design doc, backend-selection table + correlated-outage note). |
| **Operator symptom** | `yuzu.guardian_backend` heartbeat tag reads `spark_failed` or `unwired` for the affected agent. **No fleet-level Prometheus gauge exists for this today** — `yuzu_fleet_spark_failed{os}` is adjacent but not identical (it tracks SparkEngine boot failure only, not a post-boot wiring failure or `Unwired`). A fleet-wide SparkEngine boot throw is a correlated-outage tail: every agent in the cohort loses enforcement simultaneously until `--spark-disable` is set. |
| **Verify at** | `GuardianEngine::reconcile_rule_locked`'s `SparkFailed`/`Unwired` guard (withdraws legacy, `unsupported_rules_.erase`, returns false); `GuardianEngine::wire_spark_engine()`'s `!engine` branch ("spark path unavailable... never silently substituted"); `guardian_backend_from_state()` / `guardian_backend_label()` in `guardian_backend.hpp`. |
| **Epistemic** | verified b16e5836d |

### A3 — Push acknowledgment is asynchronous under spark

| | |
|---|---|
| **Legacy** | `apply_rules` acknowledges the policy generation synchronously: every legacy guard's `start()` call runs inline, so by the time `apply_rules` returns, every rule that will ever arm this generation already has. A rule whose guard fails to start is acknowledged anyway, silently stranded `Inert` — legacy has no mechanism to hold the acknowledgment on a failed arm. |
| **Spark** | `apply_rules` accepts a push immediately and returns without waiting for any backend OS call — the rearm window this design exists to shrink. The policy generation reported to the server (`policy_generation()`) is the *acknowledged* value, which only advances once every accepted rule's arm has resolved: `Armed` (committed), or `Wedged` after K=3 identical same-generation re-applies of a wedged (dispatched-and-timed-out, still-claimed) key (the fleet signal is `yuzu.guardian_arm_failed>0` - implemented rung 9c PR-3 (#4329, merged 2026-09-14)). Durability is a function of ACKNOWLEDGMENT, not of the failure itself: `server.cpp`'s heartbeat-reconcile only re-pushes a generation while `agent_gen < current` (the agent's own reported, acknowledged generation trails the server's target) - once a generation is acknowledged, whether by full success or by this row's own K-waiver, the server stops resending it, and nothing further resets `resolved_failed` for it. Before that point, while the generation is still being actively retried (NOT yet acknowledged), the signal is genuinely non-durable: `decide_retry()` forces Reapply whenever `resolved_failed>0`, and each Reapply's `begin_application()` resets it to 0 unconditionally at the START of that retry, regardless of the retry's own eventual outcome - so an in-flight, not-yet-wedged failure oscillates across ticks rather than holding steady. **The K=3 wedge waiver is implemented, rung 9c PR-5e (#4221, not yet merged as of this writing - see `docs/spark-stage2-guardian-consumer-design.md`'s "as implemented (rung 9c PR-5e)" stamp for the full mechanism, including the K-eligibility settling requirement a naive `resolved_failed == failed_receipts.size()` check alone would miss):** a wedged key's generation now advances after exactly 3 identical same-generation re-applies, once `receipt_wedge_k_eligible()` confirms the remaining failure is still a genuinely-outstanding, settled Wedged episode. **The re-apply count is a single counter shared across the whole application-sequence, not per-rule/per-key** - `Application::reapply_count` tracks how many times the OPERATOR'S OWN push content has been identically re-observed, not how many times any one key was itself wedged; a specific key can therefore be waived the very first time it is ever observed wedged if an unrelated sibling key's own ordinary (non-Wedged), now-cleared failure already funded the counter on earlier re-applies. This is the deliberate, reviewed consequence of decision 1 rejecting a finer-grained per-rule retry-credit ledger (see `docs/spark-stage2-guardian-consumer-design.md`'s R5.3 "as implemented" stamp) - it does not weaken the single safety invariant K-waiver must never break (a waived receipt is, at the moment of waiver, still genuinely Wedged and still its key's FIFO-front claim), only how many of the operator's own retries a freshly-wedged key is guaranteed before that becomes possible. A wedged key stays wedged until its worker returns or the agent restarts — a later policy change re-evaluates the rule but cannot by itself re-attempt the arm; **resolved by ruling 14(a), 2026-09-08 (#4148): only a dispatched-and-timed-out, still-claimed key is K-qualifying; a congestion-only queue-wait expiry or an admission-time `CapacityExhausted` holds the acknowledgment instead, so the refusal list that follows is consistent with R5.2's resolved callout**). A plain arm refusal (a dispatched call that returned a failure - backend refused or worker threw - or an admission rejection such as quota/queue exhaustion, where no call was attempted) holds the acknowledgment indefinitely, unlike legacy's silent `Inert` strand - matching R5.3's own "K is not a generation-wide liveness bound." |
| **Why deliberate** | ADR-0021 Decision 8: "The generation counter is a reconcile trigger only, never a compliance signal" — the warrant for treating acceptance and acknowledgment as genuinely separate. Confirmed zero-wire-protocol-change: `get_status()` is dead in production and solicited `__guard__` replies are dropped by the server, so `yuzu.guardian_generation` was already the only channel that mattered. |
| **Operator symptom** | A push may take up to several heartbeat ticks (bounded drain, matching the existing lifecycle-journal 4-batch/1024-record shape) to acknowledge after `apply_rules` returns, rather than acknowledging in the same call. `yuzu.guardian_arm_pending` / `yuzu.guardian_arm_failed` (heartbeat tags, implemented rung 9c PR-3, #4329, merged 2026-09-14 - `GuardianArmAckLedger::arm_stats()`/`GuardianEngine::arm_stats()`, re-statable gauges, NOT gated on "an application exists" alone since `apply_rules()` opens one unconditionally regardless of `prefer_spark_` - see `docs/spark-stage2-guardian-consumer-design.md`'s "AS IMPLEMENTED (PR-3)" note) surface this window; a rule wedged via K stays reported as failed on the health tag for as long as the CURRENT application observes it. **Correction (rung 9c PR-5e, #4221 - Fable-reviewed governance finding): the previous version of this row claimed "a K-waived acknowledgment can never silently zero the fleet-visible failure signal" - that is FALSE.** `arm_stats()`/`arm_failed` is scoped to the CURRENT application only (§R5.3's own "Both mechanisms are scoped to the current application/claim only" - not the durable, cross-application gauge a fleet dashboard would need, which remains unbuilt): any DISTINCT later push (one that simply omits the still-wedged rule, or changes its content) calls `begin_application()`, which resets `resolved_failed`/`failed_receipts` to empty unconditionally, regardless of whether the previously-wedged rule ever actually recovered. An operator relying on `arm_failed` as a durable signal across a rule's removal-then-return, not just within one still-open application, needs the still-unbuilt cross-application gauge - track this gap under #4221's own follow-ups, not as a property this row can claim today. **A second, noisier symptom** (Gate 6 enterprise-readiness): a genuine refusal (not a wedge — a rule that is actively refused, throws, or hits a full arm queue) holds the *whole generation's* acknowledgment indefinitely, not just that one rule's — so the server's 25s `full_sync=true` retry becomes a live, repeating full re-apply of the entire push until an operator fixes the one bad rule, even if every other rule in the push armed cleanly on the first attempt. An operator should not read "policy generation behind" as "most rules unarmed" — it can mean "one rule out of many is refusing." |
| **Verify at** | `GuardianSparkRuntime::attach_rule`'s per-key state machine (`guardian_spark_runtime.cpp`, implemented in rung 9c PR-1: `KeyClaim`/`claims_`, `on_arm_complete`) and `GuardianEngine::apply_rules`'s accepted-vs-acknowledged bookkeeping (`guardian_engine.cpp`/`guardian_engine.hpp`, implemented in rung 9c PR-2: `GuardianArmAckLedger`, `can_advance()`, merged as PR #4318, `a27ec4549baa`, 2026-09-13); the K=3 wedge waiver (`GuardianArmAckLedger::begin_application()`'s `reapply_count`, `can_advance()`'s K-waiver branch, `GuardianSparkRuntime::receipt_wedge_k_eligible()` and `receipt_recovery_status()` - the latter the atomic recovery-scan-loop probe added to close an adversarial-review-found TOCTOU, implemented rung 9c PR-5e, #4221); see the design doc's PR ladder. |
| **Epistemic** | `design-approved 2026-09-07` — six external review rounds against the (uncommitted) plan document (Astra/Codex ×4, Fable ×multiple, Kimi K3 ×2), then a seventh, an adversarial review of the committed PR-0 transcription (`docs/spark-stage2-guardian-consumer-design.md` §R5 and this row) — **corrected round, 2026-09-07: earlier wording attributed all seven rounds to §R5 directly (which existed for none of the first six) and dropped Codex/"×multiple" from the roster; both now match this doc's own front-matter split.** R5.1/R5.2's mechanics are implemented by rung 9c PR-1 (their "Verify at" symbols exist); **R5.3's accepted-vs-acknowledged bookkeeping is now also implemented, rung 9c PR-2 (merged 2026-09-13, PR #4318) — corrected here, 2026-09-13, superseding the prior "PR-2, not yet implemented" wording.** **Row-specific override of "How to add a row"'s general first-code-PR trigger (Gate 6 enterprise-readiness, 2026-09-07) still applies, unchanged by this correction:** this row's Spark column describes the WHOLE mechanism (R5.2's per-key state machine AND R5.3's accepted-vs-acknowledged bookkeeping), which per the design's own ladder spans PR-1 through PR-6, not one PR — re-stamping `verified <SHA>` before every "Verify at" symbol exists (PR-4 through
PR-6 still don't - PR-3 merged 2026-09-14, #4329, but whether it added a "Verify at"

## C. Placement / platform

### C1 — `unsupported` is a distinct, per-rule terminal state (not a legacy fallthrough)

| | |
|---|---|
| **Legacy** | A guard whose mechanism doesn't exist on this platform is a compile-time stub returning `false` from `start()`. No distinct state, no per-rule tracking, no heartbeat surface, no counter — just an unarmed rule and a warn log blending "unsupported platform" with "authoring fault" into one string. |
| **Spark** | `RulePlacement::Unsupported` (a recognized spark type with no *registered-and-functional* mechanism on this host) is a terminal state distinct from both `Arm` and agent-wide `SparkFailed`/`Unwired`. Withdraws from both backends, records the rule_id in `unsupported_rules_` (erased on every other outcome, so the map is exact), edge-logs only on a genuine transition ("new, or a different type than before"). |
| **Why deliberate** | Ruling R2 + F7 (#3321): "Legacy already no-ops there; what changes is reporting" — since rung 5 deletes the legacy backend entirely, there is no fallthrough target left, so building the fallthrough once at rung 2 is building it twice. |
| **Operator symptom** | `yuzu.spark_<mechanism>_unsupported` per-agent heartbeat tag → `yuzu_fleet_spark_unsupported{os,mechanism}` fleet gauge (a live, current-value gauge — it can legally decrease). **Caveat, not a universal guarantee:** `classify()` keys off registered-AND-ARMABLE (not boot-inert) capability, so a mechanism that started but couldn't bind its OS facility (no systemd bus in a container, `OpenSCManager` access denied) lands a rule in `Unsupported` on a platform where legacy might otherwise have worked. **FIXED (#4685):** a TRANSIENT runtime cause — a File worker or Registry sweeper that failed three consecutive passes — no longer lands a rule here at all: `boot_inert` (additive, `SparkMechanismStats`) is what `classify()`'s capability set now reads, and it stays FALSE for a merely runtime-degraded mechanism, so the rule stays `Arm`/Committed with coverage reported `None` until the mechanism's next successful pass, recovering with no push or restart needed. Cross-check `yuzu_fleet_spark_mechanisms{os,mechanism}` + that mechanism's boot logs before assuming "routine cross-platform gap"; the Unsupported-branch log line itself now says which case it is (`warn` for boot-inert, `info` for never-registered). |
| **Verify at** | `reconcile_rule_locked`'s `RulePlacement::Unsupported` branch; `classify()` in `guardian_spark_bridge.hpp`; `guardian_unsupported_heartbeat.hpp`; `agent_registry.cpp`'s `yuzu_fleet_spark_unsupported` gauge set; `SparkMechanismStats::boot_inert` in `spark_mechanism.hpp` (#4685). |
| **Epistemic** | **FIXED (#4685), restamped against this issue's own PR** (code read + the PR's own targeted test suite, not yet a governed merge SHA at the time this cell was restamped): `SparkMechanismStats` gained an additive `boot_inert` field, declared after `inert` for designated-initializer order; `spark_file.cpp`/`spark_registry.cpp` split their single `inert_` atomic into `boot_inert_` (written only by `start()`) and `degraded_` (written only by the runtime worker/sweeper), with `stats()` deriving `.inert` as boot OR degraded and `.boot_inert = boot` from one pair of local reads; `spark_service.cpp` (no runtime-inert concept) reports `.boot_inert` as the same atomic as `.inert`. `reconcile_rule_locked()`'s capability set now filters on `!ms.boot_inert`, so a rule reconciled during a runtime-degraded episode Arms instead of landing `Unsupported`, and nothing needs to "re-reconcile when `inert` clears" (the pre-fix gap this cell used to describe) because the rule was never withdrawn from spark in the first place. The prior verification's citations (Registry's `kSweeperInertAfterFailures`/`sweeper_main()`, the File-worker half from #4658) still hold structurally, just against the split fields rather than the single `inert_` bit. |

### C3 — File: legacy detects a rename of the watched directory itself in real time; spark does not (2026-09, found alongside PR #4748)

| | |
|---|---|
| **Legacy** | `guard_file.cpp` opens a SECOND, dedicated handle (P) on X's parent directory (X = the target file's parent, or its nearest existing ancestor) purely to watch for X's own name changing — a directory-name-only `ReadDirectoryChangesW`/`ReadDirectoryChangesExW` read, bound to X's resolved path and retained across ordinary re-arms. X's own handle is opened `FILE_SHARE_DELETE`, so a rename of X gives NO completion on X's own handle (it silently follows X to the new name) — P exists specifically to make that rename visible: a record naming X (or carrying X's FileId, when the extended notify API is available) triggers an immediate reconcile, so the guarded file is reported absent at its original path (or a `file-hash-equals` rule reports it can no longer verify) as soon as the kernel delivers the notification. |
| **Spark** | `spark_file.cpp` has no equivalent second handle. It opens X the same `FILE_SHARE_DELETE` way (one occurrence in the file) and separately maintains an ancestor-shelter watch for the case where X does not exist at all — a *different* failure mode (X missing) from P's (X exists, but was renamed/moved). ### D5 — Restart re-arms both backends' compliant edge pre-network, but only spark's boot-time edge reliably reaches the server

| | |
|---|---|
| **Legacy** | File/Registry/Windows-Service **do** re-fire `guard.compliant` in-process on every restart: `guard_registry.cpp`/`guard_file.cpp`/`guard_service.cpp` each carry an identical per-guard-instance `last_compliant` (`std::optional<bool>`) that starts `nullopt`; `start_local()`'s restart re-arm loop spawns a **fresh** guard thread per cached enabled rule (arming a legacy guard spawns a `std::thread`), so `last_compliant` resets and the guard fires `guard.compliant` on the first reconcile again. ### D10 — Spark reads go through a bounded, bulkheaded I/O admission layer; legacy reads have none

| | |
|---|---|
| **Legacy** | Each guard runs its own read on its own thread, unbounded — no admission control, no per-class concurrency cap, no deadline. A wedged read (a stalled network/FUSE mount, a hung SCM call, a wedged sd-bus broker) blocks that guard's thread indefinitely; there is no shared quota across guards to protect one type from starving another. |
| **Spark** | Every read is dispatched through `GuardianIoExecutor`, a per-type bulkhead with a per-executor-instance ceiling (the state reader and the arm/disarm runtime each own an instance and admit independently; the process-wide figure is the sum). Default class quotas: File 4, Registry 3, Service 3 (`kMaxProcessIoWorkers = 10`, derived as the exact sum so no class can starve another — a class cap always binds before the process bound can). Each class also carries its own absolute deadline (file-hash ~15s, file-metadata-only/registry/service 5s). A read that can't get an admission slot (`CapacityExhausted`), that's already in flight for the same key (`AlreadyRunning`, single-flighted), or that exceeds its deadline (`Timeout`), or that is refused at the per-instance physical alive-worker ceiling (`CeilingExhausted`, `kMaxAliveIoWorkers = 20`: workers still alive past `fn()` inside their completion callbacks while quota is free - rung 9c PR-1, §A3; reachable only on an executor instance that also serves `submit()`, i.e. the arm/disarm executor - the state reader's own instance runs `run()` only, whose workers hold quota until their payload is destroyed (`~TicketCore`, the same moment their alive count releases), so its alive count never exceeds its quota total and a READ cannot see it) degrades to Unknown rather than blocking or hanging — the wedged worker is decoupled (a D-state syscall can't be cancelled or joined), not force-killed, and its liveness feeds the F3 orphan-exit obligation (see E2). **#3816 (exactly-once delivery):** `run()` delivers every result `fn()` returns normally to exactly one of its return value or an optional `on_abandoned(T&&)` callback invoked when the caller already gave up — never both, never neither (a thrown `fn()`/`WorkerThrew` has no `T` to deliver and correctly reaches neither destination). The state reader's reads need no callback: a late read is pure wasted work, nothing escapes to clean up. Since rung 9c PR-1, `GuardianSparkRuntime`'s ARM consumer dispatches through the non-waiting `submit()` form instead (one `on_complete` callback per admitted operation, fired exactly once on the worker thread after `fn()` returns, with the quota slot and single-flight key released at `fn()` return; the runtime's per-key claim decides whether a late success commits or is disarmed). Its DISARMS deliberately stay on the bounded `run()` form in PR-1 (`submit_disarm_off_lock` from the driving thread, and the drain's own compensating disarm on the worker): the caller waits anyway, `run()` keeps the class quota for the call, and the per-key claim FIFO supplies same-key ordering. `on_abandoned` is used by the state reader only. |
| **Why deliberate** | R3 (design doc rung-9a decision record): a bulkhead is necessary once reads are dispatched from a shared scheduler across many rules/keys concurrently, which legacy's one-guard-one-thread model never needed. See R3 for the full starvation derivation and the `total_quota{8}`-vs-`sum(10)` history; the shipped design makes cross-class starvation structurally impossible rather than merely less likely. |
| **Operator symptom** | Under read contention (many rules, a slow mechanism, a stalled filesystem) spark can produce `guard.unhealthy` traffic (via the Unknown→health-stream path, D1/D6) that has no legacy analog — a purely spark-introduced fault *source*, not just a different classification of a fault legacy would also have hit. Counted via `GuardianIoExecutor::Counters` (`timed_out`, `rejected_capacity`, `rejected_key`, `launch_failures`, `worker_exceptions`, and `abandoned`/`abandonment_cleanup_failures` since #3816, and `rejected_ceiling`/`completed_after_stop`/`completion_failures` since rung 9c PR-1) per class — the general per-class egress for all of them stays open as **#3415**, deliberately scoped to a separate follow-up ("rung 9c PR-3a"), scheduled after PR-3 and before PR-5's fault-validation work (`~/.claude/plans/spark-rung9c-pr3-telemetry-KICKOFF-v2.md` Decision 2). **One field, `rejected_ceiling`, is the narrow exception**: rung 9c PR-3 (#4329, merged 2026-09-14) wires it alone as `yuzu.guardian_io_arm_disarm_rejected_ceiling`/`yuzu_fleet_guardian_io_arm_disarm_rejected_ceiling` (R5.1's own flagged ask, a plain monitor-only counter — see `docs/spark-stage2-guardian-consumer-design.md`'s "AS IMPLEMENTED (PR-3)" note), summed only across the arm/disarm executor instance (the state reader's own instance runs `run()` only and structurally cannot reach `CeilingExhausted`, per this row's own text above). A windowed "currently under repeated ceiling pressure" detector was proposed for PR-3 and explicitly DEFERRED to rung 9c PR-6 (Dave's ruling, Decision 3) rather than shipping an unmeasured threshold now — do not mistake the plain counter for that detector. Verify current wiring before relying on fleet-level visibility into any OTHER field in this counter family. |
| **Verify at** | `guardian_io_executor.hpp` (`GuardianIoExecutor::Config` defaults, `kMaxProcessIoWorkers`, `IoFailure` enum); `guardian_state_reader.hpp` header comment (per-class deadlines, single-flight, decouple-not-cancel contract) confirming production wiring. |

### D11 — Recovery from Unknown force-emits a compliance event even when the value didn't change

| | |
|---|---|
| **Legacy** | Registry and Service: no comparable concept, unchanged (D1, D6) — no Unknown/health state at all, so there is no "recovery from Unknown" transition to force anything on; a compliance event fires only on a genuine compliant/drifted value transition. **File (2026-09, PR #4748, see D1's update)** now has a narrow permanent-disable health state, but needs none of this row's forcing mechanism: `GuardianEngine` reconstructs a whole new `FileGuard` instance on every reconcile that touches a rule_id — including the re-arm (policy re-push or agent restart) that is File's *only* path off the disabled state — and a fresh instance's `last_compliant` starts at `nullopt`, not `true`/`false`. `report_compliant()`'s own edge check (`if (last_compliant == true) return;`) is therefore false on that instance's very first evaluation regardless of the observed value, so the first post-re-arm eval **always** emits a real `guard.compliant` (or `drift.detected`) event and clears the server-side `errored` state — the same net effect as Spark's forced re-emit here, achieved by fresh-instance construction rather than an explicit edge-cache reset. ### D13 — Legacy sink delivery is now detached, bounded, and gap-tracked, but stays non-coalescing FIFO where Spark's outbox coalesces (#4783)

| | |
|---|---|
| **Legacy** | Since #4783, `GuardianEngine::emit_guard_event()` no longer calls the injected `EventSink` directly on the guard's own detection thread — it enqueues onto `GuardianLegacySinkExecutor` (`guardian_legacy_sink_executor.hpp`), a detached, bounded (`max_events`/`max_bytes`), pure-FIFO sender: two events for the same `rule_id` are never coalesced or reordered, unlike Spark's outbox (D9 below). A refusal (capacity, admission failure) or a failed/throwing send opens a sticky per-rule integrity gap (`GapRecord`, keyed by `rule_id`); `GuardianEngine::legacy_sink_kick()`, driven by the agent heartbeat and deliberately independent of `prefer_spark_`, relaunches a stranded sender and, for up to `kMaxGapRepairsPerKick` (32) open gaps not already mid-repair, synthesizes a `guard.unhealthy` report (fixed `kLegacySinkDeliveryGapDetail` detail string, `"legacy-sink-delivery-gap"`) via `emit_guard_event(..., is_gap_repair=true, gap.last_lost)`. A **correctness defect found in the initial commit-4 design** (any `is_gap_repair=true` send that came back `Sent` erased the gap unconditionally) is closed by two mechanisms, both needed: (1) SEQ-GUARDED CLEARING — every `offer()` call is assigned a strictly increasing admission-time sequence number, and a delivery (real or repair) is allowed to clear the gap only if its own sequence number is strictly newer than `GapRecord::lost_seq`, the highest sequence number of any loss recorded against that rule — an already-in-flight OLDER send completing `Sent` after a NEWER loss for the same rule must not erase evidence of that newer loss; (2) DEQUEUE-TIME SUPERSESSION — a queued repair is re-validated against the rule's LIVE gap state again immediately before its send runs (not only when it was queued): if the gap no longer exists, or `GapRecord::repair_seq` no longer names this specific item (a newer loss or a newer repair superseded it, or the gap was queued after already being re-cleared by a fresh real event so it was never stamped with a live `repair_seq` at all — a rule has at most one live `repair_seq` outstanding at a time), the repair is skipped, never sent, and counted in `repairs_suppressed`. On top of both, the repair event's wire timestamp is stamped with the gap's own `last_lost` time, never the kick's wall-clock `now`, so a real verdict delivered between two losses is never overwritten by a stale repair covering only the earlier one — belt-and-braces alongside the seq guard and dequeue check, and alongside the server's own `updated_at >=` upsert guard (D11). **Before #4783**, the send was synchronous, unbounded, and ran on the guard's own detection thread: a stalled-but-not-dead stream write (gateway up, not draining) could block that guard's detection indefinitely, and — because both `apply_rules`'s `full_sync` teardown and `GuardianEngine::stop()` join every guard thread while holding `mtx_` — could also stall every OTHER rule's arm/withdraw in the same reconcile pass, not just the stalled rule's own reporting. **Gate 4 UP-3 (restart durability, fixed):** the gap ledger and loss counters above were originally pure in-process `GuardianLegacySinkExecutor::State` fields — nothing survived an agent restart, so a restart mid-outage made the fleet gauge read "resolved," identical to a genuine repair, with no way for an operator to tell the two apart. `GuardianLegacySinkExecutor::snapshot()`/`restore()` now make a SMALL restart-durable marker — the `Stats` counters plus one `GapSnapshotEntry` per open gap (rule_id/guard_type/rule_name/lost count/first_lost/last_lost; deliberately NOT the queued event payload itself, in-flight send state, or in-process sequencing) — persist to the agent's own `KvStore` under the fixed key `legacy_sink_loss_ledger` (`kKvNamespace`), written from `legacy_sink_kick()` (gated on a `change_gen` token so an unchanged ledger is not rewritten every heartbeat) and unconditionally from `stop()`'s final flush, and restored in `start_local()` strictly before the rule re-arm loop. Restart semantics: if the link is back up before the rule's next real transition, that transition's own arm-time verdict clears the restored gap legitimately (restore() resets `lost_seq` to 0, so ANY subsequent delivery clears it); if the link is still down, the gap stays open and `legacy_sink_kick()`'s repair loop resumes once reachable, stamped with the gap's ORIGINAL pre-restart `last_lost` (never the restart time). **Gate 4 UP-4 (interior-loss visibility, accepted trade-off, NOT fixed):** an interior compliance transition (e.g. `drift.detected`) can still be silently and permanently lost if it is refused at capacity while the rule's bracketing events both succeed — the gap self-clears on the later successful event (SEQ-GUARDED CLEARING above) with no repair ever firing, so the server's audit HISTORY shows continuous compliance through a window that was, for a time, a real violation, even though CURRENT state is accurate. This is an accepted design trade-off (D1d) — closing it fully needs a durable spool of the lost event's own content, which is explicitly OUT of scope here and tracked as a separate follow-up issue (#4888). The loss is never silent, though: it is counted (`events_lost`, now restart-durable per UP-3), attributed in the agent log by `rule_id` at the moment of loss (a firewalled `spdlog::warn` on the rule's first loss this process, then `spdlog::info` every 100th loss thereafter — `GuardianLegacySinkExecutor::log_loss()`), and fleet-visible (`yuzu_fleet_guardian_legacy_sink_events_lost`). |
| **Spark** | `GuardianOutbox` (D9) is FIFO but per-(domain,rule_id)-**coalesced** — a churning rule's repeated pushes collapse into one queued entry, trading delivery-order fidelity for bounded memory under a noisy rule. `GuardianLegacySinkExecutor` deliberately does NOT do this: `drift.detected`/`drift.remediated`/`remediation.failed`/`guard.compliant`/`guard.unhealthy` are distinct census signals the server orders by arrival, so collapsing two different event types for the same rule into one slot would be a correctness bug, not just a cardinality reduction (the executor's own QUEUE POLICY doc comment). Spark's own loss/repair story is unchanged and remains D9's; this row narrows D9's legacy side only. |
| **Why deliberate** | #4783 delivery plan (`.claude/plans/4783-legacy-guard-sink-blocking-PLAN-v2.md`): decouple the producer from the send, mirroring the outbox/state-reader detached-worker shape, without adopting the outbox's coalescing — a legacy `GuardDrift` sink call has no later "re-offer" to fall back on: the guard already committed its decider state (`last_compliant` etc.) before calling the sink, and `GuardSink` returns void, so a coalesced-away event here is a permanent edge loss with no local record to rebuild it from. That is why the sticky gap ledger exists instead of relying on coalescing alone to bound memory, and why a lost edge needs an explicit synthesized repair rather than "the next push will naturally supersede it." |
| **Operator symptom** | A Guardian rule's detection thread no longer wedges — and no longer risks stalling sibling rules' arm/disarm during a reconcile — when the agent's connection is stalled-but-not-dead. A genuine delivery loss is now visible fleet-wide as `yuzu_fleet_guardian_legacy_sink_events_lost` (cumulative) and `yuzu_fleet_guardian_legacy_sink_gap_rules` (currently open), both monitor-only gauges (`docs/user-manual/metrics.md`); a persistently non-zero gap-rules count means repair reports are also failing to land, not just the original report. |
| **Verify at** | `agents/core/src/guardian_legacy_sink_executor.hpp` (class doc comment: SEQ-GUARDED CLEARING, DEQUEUE-TIME SUPERSESSION, the loss-accounting table, and the "Known limitations" block for UP-3/UP-4; `GapSnapshotEntry`/`Snapshot`/`snapshot()`/`restore()`/`log_loss()`); `guardian_engine.cpp`'s `emit_guard_event()`/`legacy_sink_kick()`/`start_local()`/`stop()` and the `legacy_sink_snapshot_to_json`/`read_legacy_sink_loss_record`/`persist_legacy_sink_loss_ledger` helpers; `guardian_engine.hpp`'s `legacy_sink_kick()`/`start_local()`/`stop()` doc comments; `guardian_health_heartbeat.hpp` (`kGuardianLegacySinkEventsLostTag`/`kGuardianLegacySinkGapRulesTag`); `server/core/src/guardian_health_fleet_tags.hpp` (HELP text - restart-durability + what `gap_rules` counts); `tests/unit/test_guardian_legacy_sink_executor.cpp` (seq-guard/dequeue-supersession regressions, plus the UP-3/UP-4 `snapshot()`/`restore()`/per-loss-log cases) and `tests/unit/test_guardian_engine_legacy_sink.cpp` (same, plus the UP-3 restart/self-heal/stop()-flush KV-wiring cases). |
| **Epistemic** | verified 49fc3da33 for the pre-UP-3/UP-4 mechanism; the UP-3/UP-4 restart-durability + per-loss-log addition in this cell is reasoned-from-code as of the commit landing it (see this file's own git blame for D13 — not independently re-verified by a second pass at the time of writing). |

## E. Cadence / resource

### E1 — Spark runs a scheduled convergence sweep across every rule; legacy is mostly notification-driven

| | |
|---|---|
| **Legacy** | No **compliance-detection** polling loop for any of the four guards — File/Registry/Service block on kernel notification primitives with an `INFINITE` healthy-wait. Not purely notification-driven overall, though: degraded-path retries run on a timer regardless (30 s arm-fail/absent retry across the Windows guards and systemd's absent retry), and legacy systemd **already** runs a steady 60 s healthy-reconcile safety poll (`kHealthyReconcileMs`) independent of `prefer_spark` — that cadence exists today and is not a cost the flip introduces; exclude it from any flip-attributed resource delta for Linux Service. |
| **Spark** | `ConvergenceScheduler` runs one thread per type lane plus a priority lane, each on its own cadence with ±20% jitter: service 60 s, registry 60 s, file 600 s, priority (pending-initial backstop) 5 s. A file-lane byte-level token bucket (size+mtime skip before re-hash) is explicitly **deferred to rung 5** — "against rung 4's fake instant reader there is nothing to budget, so wiring them here would be untested theatre." The journal replay path has its own separate, active token bucket (0.1 batch/s, burst 5 — see D2), not to be confused with the deferred file-lane one. |
| **Why deliberate** | Spark's mechanisms don't all carry native change-notification for every read path (e.g. dead-reckoning a file's compliance without a kernel event on every convergence tick); the scheduled sweep is how it converges independent of notification delivery. Ruling: flip-ladder decision D2 (distinct from this doc's own row D2) — token bucket formally deferred to rung 5, confirmed at F11. |
| **Operator symptom** | Periodic reads themselves are a resource delta the flip introduces (CPU/IO wake-ups on 60 s/600 s/5 s cadences per agent, independent of whether anything is actually drifted) — sized against `docs/spark-rebuild-baselines/stage0-resource-baseline.md` as part of F14's evidence, not restated here. For Linux Service specifically, subtract legacy systemd's pre-existing 60 s reconcile cadence from that delta — it's already incurred today, so attributing it to the flip would overstate the new cost. |
| **Verify at** | `guardian_convergence_scheduler.hpp` `Config` (`service_cadence_ms`, `registry_cadence_ms`, `file_cadence_ms`, `priority_poll_ms`, `jitter_pct`); its header comment on the deferred token bucket. |
| **Epistemic** | verified b16e5836d |

### E2 — Shutdown: spark may force a hard, nonzero-code process exit; legacy joins its threads

| | |
|---|---|
| **Legacy** | Each guard thread is stopped and `.join()`-ed cleanly (`guard_file.cpp`, `guard_registry.cpp`, `guard_service.cpp`, `guard_systemd.cpp` all join their worker thread on `stop()`). |
| **Spark** | A detached Guardian I/O worker cannot always be joined within a bounded grace (`kOrphanDrainGrace`, 3 s). When that grace expires, `main.cpp`/`service_win.cpp` call `hard_exit()` (`TerminateProcess` on Windows to avoid the loader lock, `::_exit()` on POSIX for async-signal-safety) with a nonzero code, rather than race normal C++ teardown against a worker that may still be executing library code. The orphan count that gates that grace is the PHYSICAL alive-worker count (`GuardianIoExecutor::active_worker_count()`, released in `~TicketCore` when the worker's payload is destroyed inside the thread trampoline, the latest point a detached worker can self-observe before its OS thread exits; the uncounted tail is the `State` release, a `notify_all`, the payload deallocation, the trampoline epilogue and the CRT thread exit - process-lifetime runtime code only, never the Guardian/OpenSSL/libsystemd/Win32-RPC code F3 keeps out of DSO teardown; no grace covers that tail, since `wait_for_workers_to_drain` returns on the first zero and the shutdown paths skip the wait when the initial sample is zero - identical for every `run()` worker since rung 7, accepted), which includes a `submit()` worker that has returned from its backend call and is still running its completion callback while holding no quota (#4147, rung 9c PR-1). |
| **Why deliberate** | F3 (`hard_exit.hpp`): callers must pass a nonzero code specifically so systemd/SCM observe a real failure exit rather than a clean shutdown — an intentional signal to the service supervisor, not a bug being papered over. |
| **Operator symptom** | Under spark, a slow/stuck drain can make agent shutdown/restart look like a **crash** to systemd/SCM (nonzero exit) where the equivalent legacy shutdown would report clean. Cross-platform crash-loop backstop parity (Windows SCM / macOS launchd / Docker restart policy vs Linux's `StartLimitIntervalSec`/`StartLimitBurst`) is tracked separately (#2241, Linux-only today). |
| **Verify at** | `hard_exit.hpp` (`kOrphanDrainGrace`, nonzero-code contract); `main.cpp`'s `on_signal_hard_exit` signal handler and its orphan-worker grace-expiry check in the main shutdown path; `service_win.cpp`'s SCM stop handler; contrast `guard_file.cpp`/`guard_registry.cpp`/`guard_service.cpp`/`guard_systemd.cpp`, each of which `.join()`s its worker thread on `stop()`. |
| **Epistemic** | verified b16e5836d |

## F. Expected parity (not deltas — listed so an F14 reviewer doesn't misflag these)

- **Compliance/drift event fields are byte-identical** between legacy and spark via the
  shared `apply_drift_to_event` builder — only `event_id`/`timestamp` differ, by design
  (stamped at enqueue, not at send).
- **`get_status()` is universally fail-closed for both backends** — every rule reports
  `status="errored"`, `guard_healthy=false` regardless of backend or actual per-rule
  state ("under-reporting here is fail-closed; the prior 'armed ⇒ compliant/healthy' was
  the silently-deaf failure class"). There is no `unsupported`/`armed`/`pending` status
  token on REST/MCP yet — `status_for_rule()` exists but is deliberately unwired
  (rung 4).
- **Linux without `YUZU_HAVE_LIBSYSTEMD`:** both backends go dark for Service
  simultaneously — the same build flag gates both `spark_service.cpp` and
  `guard_systemd.cpp`. Not an independent spark-vs-legacy gap.
- **macOS: zero detection under both backends today** — see C2. The flip does not
  create this; it only makes it visible via `unsupported`.
- **Registry hive-root validation** is equally lax on both backends (spark's stricter
  early version was corrected to match legacy's laxity — only `hive` required).
