| **`browser_inventory` plugin (Forensics, default-off, per-user browser data)** — reads per-user Chromium-family browser profile state (`browsers`/`profiles` actions; the per-profile `extensions` action follows as its own PR). CATASTROPHIC-IF-VIOLATED: it must never emit a browsing-account identifier, browsing history, cookies or bookmarks — no `gaia_id`, no e-mail address, no Chromium `info_cache` `user_name`/`gaia_name` field, in any row, on any OS leg. **Amended 2026-09-22 (Alex):** the LOCAL OS/home-directory account name (e.g. the `alice` in `/home/alice`) is explicitly PERMITTED on the `profiles` row — it disambiguates which of several local users on a shared machine a profile belongs to, is machine-local, and is not itself a personal/cloud identifier; it is NOT covered by the identifiers this clause forbids. `BrowserProfileRow` (the pure JSON row model in `browser_inventory_parsers.hpp`) still has no such field and never will — the local username is added only when the Linux leg formats the wire row (`browser_inventory_linux_parsers.hpp`'s `linux_profile_rows_at`), never inside the parser. **Second amendment 2026-09-22 (Alex, adversarial-review finding):** the `profiles` row's `display_name` (`BrowserProfileRow.display_name`, sourced from Chromium's `info_cache[dir].name`) is ALSO explicitly ACCEPTED as a residual-risk exception, not a struct field to strip — Chromium-family browsers commonly auto-populate a profile's display name from the signed-in account's real name, so this field CAN legitimately carry a personal name even though it is never a structured `gaia_id`/`user_name`/`gaia_name` JSON key; the README's "PRIVACY CONTRACT" and this row must both say so plainly rather than claim `display_name` is never an account/real-name field. A reviewer adding a NEW free-text field sourced from browser-controlled JSON must weigh this same risk explicitly, not assume `BrowserProfileRow`'s lack of a named identifier field is sufficient. A reviewer adding a `gaia_id`/`user_name`(browsing-account)/e-mail/history/cookie/bookmark field to `BrowserProfileRow` or any wire-row builder must re-verify this invariant, not just compile-check it. **Third amendment 2026-09-22 (Alex, adversarial-review finding):** the second amendment's residual-risk acceptance does NOT cover an e-mail-shaped value — an e-mail address is a browsing-account identifier under the headline clause above, unconditionally forbidden regardless of which field carries it. Both `profile_dir` (the `info_cache` key itself — some Chromium builds, notably a signed-in Edge profile, key it by the account e-mail) and `display_name` are free-text fields that can carry this shape, so `profiles_from_local_state` (`browser_inventory_parsers.hpp`) now redacts either field to the fixed literal `[redacted-email]` (`looks_like_email_address`/`kRedactedEmailPlaceholder`) whenever the value CONTAINS an e-mail-shaped substring — decorated, embedded or several addresses, not only a bare address (round-2 finding 2026-09-23) — a coarse shape heuristic that over-matches by design, never RFC 5322 validation; see the README — BEFORE `BrowserProfileRow` is built — enforcement by value, not by the struct's field absence, since these two fields necessarily exist for the plugin to do its job. A reviewer relying on "the struct has no such field" as this row's whole enforcement story is exactly the gap that let the e-mail case reach the wire once already; the value-level filter is the closure, and it must survive any future refactor of `profiles_from_local_state`. Ships DEFAULT-OFF behind the server-side plugin-config kill switch (`PluginConfigStore::seed_kill_switch_default_off`, the `execution_artifacts` precedent — do NOT model this on `app_usage`'s `tar_config` check, a different mechanism) and gates at `Forensics:Read`/`AdminOrApproval`, single-target only, same boundary as `execution_artifacts`/`app_usage`. **Fourth amendment 2026-09-23 (Alex, this PR's own local code-review/adversarial-review gates — labelled by GATE ROUND, not calendar date, to avoid colliding with the third amendment's "round-2 finding 2026-09-23" which is a different, earlier fix):** the third amendment's substring scan initially still under-matched RFC 5322 CFWS (folding whitespace and parenthesized comments, including nested comments and backslash-escaped quoted-pairs) on the DOMAIN side of `@` and around domain dots — `alice@ example.com`, `alice@(comment)example.com` and `alice@(escaped\)paren)example.com` all reached the wire unredacted. `skip_cfws()` (`browser_inventory_parsers.hpp`) now closes this, called immediately after `@` and at the top of every domain-label/dot scan iteration. Empirically fuzz-verified (2M-iteration ASan/UBSan probe, this PR's governance record) with no bounds/underflow defect and no further under-match found beyond the already-accepted "unterminated comment ⇒ no match" contract (documented in `skip_cfws`'s own doc comment, unchanged in intent since it was first introduced). | `agents/plugins/browser_inventory/README.md` | `security-guardian`+`cpp-safety` on `agents/plugins/browser_inventory/`, `plugin_action_catalogue_browser_inventory.hpp` |
| **`runtimes` plugin — read-only installed .NET/JVM runtime inventory (`Inventory`, no subprocess; machine-scope roots only, a per-user root would reclassify this row).** Invariants a reviewer must keep: (1) no subprocess (no `java`/`dotnet` is ever run) and no followed symlink: every directory is opened `O_NOFOLLOW` hop by hop from an already-open parent and enumerated only through `walk_dir_capped`; (2) a failed or skipped read is a `linux:runtimes:<cause>` token and status CONSTRAINED, never an empty `supported` — an absent candidate (ENOENT), a covered alias, an alias, non-directory, vanished or non-version entry, an absent `shared`/`sdk` under an existing dotnet root and a directory that is not a JVM home are the only silent cases, so `supported` + zero rows reads "none found at the standard roots" and no doc may say "none installed";
